The tool call nobody read

Original: AI Agent Engineering Interview #3 · The Tool-Call Trap

1The question

“To save money, you move your agent off DeepSeek and onto Qwen. You keep the prompts and the tool definitions exactly as they were. Now the tools simply never run. There's no error and no crash anywhere. What went wrong?” Senior AI Engineer interview, Google DeepMind

DeepSeek and Qwen are two families of open-weight models: you download them and run them on your own servers, usually behind serving software such as vLLM.

2The trap

Trap A: “Qwen is weaker at using tools. Switch back.”

Trap B: “Make the prompt shout louder: ‘You MUST call a tool.’”

Both blame the model. But the model most likely did ask for the tool, and nobody on your side understood the request. Find where the message got lost before blaming the sender.

3Your 30-second answer

“Tool calling has two layers. The tool definitions I send are a standard JSON format, so the swap didn't touch them. But the text a model writes when it wants a tool is its own family's style, learned in training. A parser in the serving stack has to recognise that style and turn it into a structured tool call.

I changed the model and left the parser set for DeepSeek. So Qwen wrote a fine tool call, the parser didn't recognise it and passed it on as ordinary text, and my agent loop saw ‘no tool call, finished’ and stopped. Nothing failed, because a plain-text reply is a legal reply. The fix is to treat the model, its chat template and its parser as one versioned unit, refuse to start if they don't match, and run a test before every deploy that fails if a known prompt stops producing a tool call.”

4The idea in plain words

Picture an office with a mail clerk. Your old assistant writes every request to another team on a red form. The clerk's one rule: “Red form? Send it to that team. Anything else? Deliver it to the customer.”

You hire a cheaper assistant. She's just as good, but where she trained, requests go on blue forms. On day one she writes a perfect request, on blue. The clerk sees no red form and delivers it to the customer as a letter. Nobody complains: she did her job, and he followed his rule.

That is this bug. In guide 1 you met the tool call: the model asks your code to run something. Underneath:

  • A model only reads and writes one long string of text. A chat template, shipped with each model, flattens your messages and tool definitions into the exact layout that model was trained on. That's the assistant's training.
  • When the model wants a tool, it writes the request in its family's own markup. Hugging Face's docs show one model wrapping the call in <tool_call> tags, another putting each argument in its own <parameter> tag. That's the colour of the form.
  • A tool-call parser in the serving software scans the output for that markup and lifts it into a structured tool_calls field. That's the clerk. In vLLM you pick it with a flag. For the versions in the docs, that's hermes for Qwen2.5 and deepseek_v3 for DeepSeek-V3.
Before: model and parser match
DeepSeek writes a call→DeepSeek parser finds it→Tool runs
After: new model, old parser
Qwen writes a call→DeepSeek parser finds nothing→Shown as text, loop stops
Think about it. Why did nothing raise an error? Because “I found no tool call” is a normal result. Models may answer in plain words, so a parser that finds nothing it knows looks exactly like a model that chose not to use a tool. Only a test that already knows the right answer can tell them apart.

5How it works: finding it and fencing it off

  1. Look at the raw text first. Open a reply where a tool should have run. If the text contains tool-call markup, the model did its part and the parser missed it.
  2. Render with the model's own template. Hugging Face's apply_chat_template uses the template stored with the model. A hand-written prompt copied from the old model is a second way to break things.
  3. Pin the parser to the model. Keep model version, template and parser together as one config, and refuse to start if the parser doesn't match the model family.
  4. Add a canary test. Before every deploy, send a prompt that must call a tool and fail the build if tool_calls comes back empty.
  5. Alarm in production. Alert when tool-call markup appears in plain replies, or when tool calls drop to zero.

Worked example (a picture built from the sources below; no single source shows this exact run). The agent asks for the price of an item. Qwen2.5 writes its request between <tool_call> tags, the Hermes style its template uses. The server still runs vLLM's deepseek_v3 parser, which looks for DeepSeek's markup and finds none. The example parser in vLLM's docs returns tools_called=False, an empty tool_calls and the text as content, so a parser that finds nothing hands the text on as ordinary content. An OpenAI-style response would then show finish_reason: "stop" (a natural end) instead of "tool_calls". The agent loop reads “no tool calls, so this is the final answer”, ends after one turn, and the user sees raw tags. Every field is legal, and the error log stays empty.

6Follow-ups they'll ask

Couldn't the parser just raise an error when it finds nothing?

No. Most replies legitimately have no tool call, so “nothing found” must be allowed. The check has to live where the right answer is known: a test with a prompt that must call a tool.

When would you say the new model really is worse at tools?

Only after the template and parser are proven to match. Then run both models on a fixed set of prompts with known correct calls and compare.

What can the canary miss?

Problems that show up only in long conversations or with several calls at once. Add a case each time you find a gap.

7Check yourself

Which part of tool calling stayed the same in the swap, and which part changed?

The tool definitions (standard JSON) stayed the same. The markup the model writes when it calls a tool changed, because each family learned its own style.

Why does the agent loop stop instead of crashing?

It sees no tool calls and a normal finish reason, which is exactly what a finished answer looks like, so it returns the text as the final reply.

Name the three things you'd version together, and the test that guards them.

The model version, its chat template and its tool-call parser. The guard is a canary test that fails the deploy if a known prompt stops producing a parsed tool call.

8Words to know

Chat template
A small script shipped with each model that turns messages and tools into the one string the model was trained to read.
Tool-call parser
Code in the serving software that finds the model's tool-call markup and turns it into a structured tool_calls field.
Finish reason
A field in the response saying why the model stopped: "tool_calls" if it called a tool, "stop" at a natural end.
Canary test
A small check that runs a known case before release and fails loudly if it breaks.
