The failure it kept rereading

Original: LLM Inference Interview Questions #14 · The Context Poisoning Trap

1The question

“A trace shows your agent sending the same malformed call to a broken edit tool eleven times running. So you add a line to the system prompt: when a tool fails, note it and switch approach. Now the agent reports failures far more often, yet finishes no more tasks. Why didn't the line help, and what would?” Senior AI Engineer interview, Anthropic

This builds on Day 122, “Agents 2: failure modes, spend caps, tracing, multi-agent”. The system prompt holds an app's standing instructions to the model (guide 12). Each tool call and its result go back into the model's context on every later step (guide 3), and a long context full of look-alikes makes models worse (guide 7).

2The trap

Trap A: “The instruction isn't strong enough. Spell out the error handling in more detail.”

Trap B: “Raise the step limit so it has room to find another way.”

Both leave the eleven failures where the model reads them on every step. More instructions add text; more steps add failures.

3Your 30-second answer

“The new line changes what the model writes, not what it reads. After eleven identical failures, much of the recent context is one pattern: this call, this error. Models continue the patterns in their context. Sinha et al. found models make more mistakes when the history holds their own earlier errors; prompting them to re-check their work gave mixed results, while cutting the history helped one model on their task. Manus warns that a context full of similar actions makes an agent repeat them.

So I'd fix it in the harness: block an identical failing call after two tries, collapse the failed attempts into one short note saying what failed and why, and repair or hide the broken tool. One failure, with its error, is worth keeping. Eleven copies teach the wrong lesson.”

4The idea in plain words

A piano student pencils the fingering she tries above a hard bar. It doesn't work, so she tries again, and pencils it again, and again. After eleven tries the bar is covered in the same wrong fingering, and her eyes follow the pencil every time she reaches it.

Her teacher adds a sticky note: “If you miss, write ‘missed’ and try something else.” Now each attempt ends with a twelfth mark, ‘missed’. She notices her misses better. She still plays what the page shows.

What works is a rubber: erase the eleven marks, write one line, “3-4-5 doesn't fit here”. The model is the student, and its context is the pencilled page.

What the model rereads on step 12
Task→Call edit(bad args) → error→…the same, 10 more times→Call 12: the same
After the harness steps in
Task→Note: edit fails on these args, error X; tool disabled→Next call: a different tool
Think about it. The new prompt line made the agent write “tool failed, noting it” after each failure. Where does that sentence go? Into the context, beside the failure. Detection went up because the model is writing about failures; nothing removed them (our reasoning).

5How it works: why it repeats, and what the harness does

  1. Errors breed errors. Sinha et al. (ICLR 2026) gave models a long, simple task, keeping a running sum of numbers looked up in a word-to-number table, and planted errors in their chat history. With more planted errors, accuracy at turn 100 “consistently degrades further”: models “become more likely to make mistakes when the context contains their errors from prior turns”. The authors call this self-conditioning, and bigger models didn't escape it. That held for ordinary models: Qwen3 with thinking on, reasoning at length before each answer, did not self-condition in their test.
  2. Prompting to self-check fell short. In their appendix, asking models to re-check their earlier answers gave “mixed” results: it helped Gemma3 early, then used up its context, and did little for Qwen3 thinking models. For Gemma3 12B, keeping only the most recent turns made performance improve “significantly”, on a task where old turns aren't needed.
  3. Repeats make repeats likelier. Xu et al. (NeurIPS 2022) found, in a 750M-parameter model like GPT-2 Large, that “the more times a sentence is repeated in the context, the higher the probability of continuing to generate that sentence”. That was text, not tool calls (our inference that it carries over). Manus (2025) reports it from practice: “Language models are excellent mimics”.
  4. The harness fixes it. Our design: after two identical failures (same tool, arguments and error), refuse the next and say why. Replace the run of failures with one note: the tool, the arguments, the error. Remove each failed call together with its result, or the history breaks the call-and-result pairing (guide 3). Then repair the tool, or hide it; Manus blocks tools by masking, so the tool stays defined but the model can't pick it. This departs from guide 6's add-only advice on purpose: there, summaries dropped detail the agent needed, runs got longer and every rewrite lost the prompt cache; here the note keeps the error, only identical copies go, and the cache is lost for one step, only when the blocker fires.

An illustration, with our own numbers. Eleven failed calls at 150 tokens each are 1,650 tokens of one pattern; the collapsed note is about 40. Anthropic's context engineering guide (2025) sets the aim: “the smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome”.

Where the premise outruns the evidence. Sinha et al.'s task is synthetic, a reasoning model may be less affected, and Manus and Anthropic report practice, not controlled tests on tool calls. And no context edit fixes a broken tool; the agent needs a working alternative (our reasoning).

6Follow-ups they'll ask

Manus says to leave failures in the context. Doesn't collapsing them contradict that?

Manus's point is that a failed action with its error steers the model away from repeating it. The same post warns that a context full of similar action-and-result pairs makes the model follow the pattern. Keep one failure and its error as a note; drop the copies (our reconciliation of the two). Manus's own fix for copycat runs is small variation in wording and format; ours is removing the copies.

Won't rewriting the history break the prompt cache?

Yes: cached pricing needs the prompt to start with exactly the same text as before (guide 6), so a rewrite makes everything after it full price for one step. Collapse only when the repeat-blocker fires, not every turn, and the cost is small next to eleven wasted calls (our reasoning).

How would you decide when to stop retrying?

Count identical calls (same tool, same arguments, same error) in a row; after two, the harness blocks the third and says why. After a few different failures in a row, end the run with a clear error or hand it to a person. The thresholds are our choice; tune them on real traces.

7Check yourself

Why doesn't a prompt line telling an agent to note failures and switch approach raise task success?

It changes what the model writes, not what it reads: the run of identical failures stays in context, and models continue patterns. Sinha et al. found prompting models to re-check their work gave mixed results, while cutting the history helped one model on their task.

What is self-conditioning, in Sinha et al.'s study?

Models become more likely to make mistakes when their context holds their own earlier errors. They showed it by planting errors in chat histories on a long running-sum task; larger models were affected too, though Qwen3 with thinking on was not.

Name three harness changes for an agent stuck repeating a failing tool call.

Block identical failing calls after a couple of tries; collapse the failed attempts, each call with its result, into one note with the error; and repair, replace or hide the broken tool.
