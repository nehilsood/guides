The split that leaked

Original: AI Agent Engineering Interview #11 · The Near-Duplicate Leakage Trap

1The question

“You collected code from GitHub, set aside a random 5% of the files for testing, and trained a new code model on the rest. On those test files it shows a big jump. Before telling anyone, what would you suspect first about the way the split was made?” Senior ML Engineer interview, Google DeepMind

The files kept back are the test set; the rest is the training set. The test set only means something if the model has never seen it, the same idea as the held-back prompts in guide 9.

2The trap

Trap A: “Overfitting. Look at the training curves.”

Trap B: “The new model is just better. Announce it.”

Overfitting means fitting the training set so closely that new data goes worse, and a fair test set is what catches it. The worry here is that the test set itself holds copies of training files, so memorising scores well. That's a fault in the split, and no training curve will show it.

3Your 30-second answer

“I'd suspect the test files aren't new. GitHub is full of copies: forks, libraries pasted into many repos, files copied between projects. One study found 70% of GitHub's code was copies of files that already existed. A random split by file puts one copy in training and its twin in the test set, so the jump may be memory, not skill. Bigger models tend to gain most from that.

So first I'd measure how many test files have an exact or near copy in training. Then I'd re-split by group, keeping whole repos, forks and clusters of near-copies on one side, or by date, testing only on code written after the training data. Then I'd re-run both models. If the jump shrinks, it was leakage.”

4The idea in plain words

A teacher builds an exam by picking 5% of the questions in the textbook at random. The other 95% become homework, with answers.

But the book reprints many questions, sometimes with different numbers. A student who memorised the homework answers aces the exam without understanding anything.

The fix: keep each question and its reprints on the same side, or write the exam from questions published after the homework.

When test data has already been seen in training, that's leakage. A reprint with small changes is a near-duplicate. Keeping related files together is a group split; using only newer files for testing is a time-based split.

Random split by file
Shuffle all files→95% train, 5% test→Twins on both sides
Group split
Group copies together→Whole groups to one side→No twin crosses
Think about it. A file has exactly one twin somewhere in your corpus, and you split at random, 95% training and 5% test. If the file lands in the test set, how likely is its twin to be in training? About 95%. A random split sends almost every copied test file's twin into training.

5How it works: checking a code split

  1. Expect copies. DéjàVu (Lopes et al., 2017) looked at 4.5 million GitHub projects in Java, C++, Python and JavaScript, leaving out forks. Its headline: “70% of the code on GitHub consists of clones of previously created files.” In JavaScript only 6% of files were distinct, and in a sample of its copied files, 78 of 80 came from npm packages committed along with the project. A library copied into a repo like that is vendored code.
  2. Measure the overlap. Count test files with an exact or near twin in training. The Stack found near-duplicates with MinHash, a quick fingerprint that estimates how many words two files share, and counted two files as similar when that overlap (their Jaccard similarity) exceeded 0.85.
  3. Re-split by group. Keep each repo whole. Then join its fork network, which GitHub's docs describe as “the upstream repository, its forks, and forks of those forks.” Then join clusters of near-duplicates, so a library pasted into many repos lands on one side.
  4. Or split by time. Test only on code written after the training data was collected. LiveCodeBench tags each problem with its release date; the DeepSeek model's score “starkly drops” on problems released after August 2023, a sign the older ones had leaked into training.
  5. Re-run and report the gap. Score both models on the clean split. The drop from the random split is your leakage estimate.

Worked example, with real numbers. How much does the split matter? Allamanis (2019) measured duplicates across popular code datasets. In the Java-Large dataset, a random 60/40 split by file left an expected 24.1% of the test set as duplicates of training files. Splitting by project cut that to 8.9%: much better, not zero, because copies cross projects. His conclusion: reported scores are “sometimes inflated by up to 100% when testing on duplicated code corpora.” He also found: “Powerful models that have larger capacity are impacted more by code duplication.” That's why a new, bigger model's jump deserves suspicion first.

6Follow-ups they'll ask

Why not just hash every file and drop exact copies?

A hash only matches byte-identical files. A copy with a renamed variable or a changed licence header slips through. In The Stack, after exact copies were already removed, near-duplicate detection still found 38.6% of the files in its permissive-licence set.

Is splitting by repository enough?

It's the minimum. In Allamanis's 2019 study, the Java-Large dataset split by project still had 8.9% of its test set duplicated in training, against an expected 24.1% with a random 60/40 split by file. Forks and pasted-in libraries cross repositories, so group by fork network and by near-duplicate cluster too.

A time-based split makes the test harder. How do you tell that apart from leakage?

Our reasoning: re-run the previous model on the same new split. A harder test lowers both models' scores. Leakage mostly shows up as the new model's lead shrinking, because the copies it had memorised are no longer in the test.

7Check yourself

Why does a random split by file leak on GitHub data?

GitHub is full of copies; the DéjàVu study found 70% of files in 4.5 million non-fork projects were clones. A random split by file puts copies on both sides, so many test files have a twin in training.

Name three kinds of group to keep on one side of a code split.

Whole repositories, fork networks (a repo, its forks and their forks), and clusters of near-duplicate files found with a method such as MinHash. Or split by date instead.

How do you find out whether a big jump came from leakage?

Count test files with an exact or near copy in training. Re-split by group or by date, re-run both models, and compare. If the new model's lead shrinks on the clean split, leakage explains that part of the jump.

8Words to know

Leakage
Test data the model has already seen in training, so the score measures memory.
Near-duplicate
A copy with small changes: renamed variables, a different header.
Fork network
A repository, its forks, and forks of those forks.
Vendored code
A library's files copied into a project's own repository.
Time-based split
Testing only on data created after the training data was collected.
