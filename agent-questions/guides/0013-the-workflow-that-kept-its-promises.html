The workflow that kept its promises

Original: AI Agent Engineering Interview #6 · The Benchmark Autonomy Trap

1The question

“Last year you built a fixed LLM workflow for buying supplies: a hard-coded list of approved vendors, set steps, and the cheapest offer wins. Now a newer model, left to run the whole job as an open-ended agent, scores higher on your benchmark. Should you delete the old workflow?” Senior AI Engineer interview, Google

The benchmark here is your own test set: past tasks with known good outcomes, scored as a percentage. A workflow and an agent are the two designs from guide 1: your code picks the steps, or the model does.

2The trap

Trap A: “Delete it. The model is better now, so the fixed steps are just in its way.”

Trap B: “Keep it. You can never trust an agent.”

Both decide before asking what the workflow was for. Its job wasn't only to score well. It was to make some mistakes impossible.

3Your 30-second answer

“Not straight away. I built that workflow for its promises, not its score: only approved vendors, always the cheapest. If my benchmark came from the workflow's own past runs, no case in it ever let those promises break.

So first I list each promise and move it into code the agent can't talk its way past, like an order tool that only accepts approved vendors. Then I test each promise as pass or fail, over many runs. I switch over gradually, and I delete the workflow last.”

4The idea in plain words

Your office has a buying clerk with a rule card: “Buy only from these five suppliers. Pick the cheapest.” It's dull, and it works.

A clever new hire arrives. You test both of them on last year's 100 orders, and the new hire finds better deals more often. Time to tear up the rule card?

Look at where the test came from. If it's built from last year's orders, every one of them went to one of the five suppliers, because the rule card made sure of it. So the test never asked: “A stranger offers a much cheaper price. Do you take it?” The new hire might take that deal. The test can't tell you, because that situation never appears in it.

The rule card is a set of guarantees: promises that hold every single time, like the guide 3 invariants. A score is an average over the cases you happened to collect. Guarantees are about the cases you made impossible, and impossible cases leave no examples behind.

What the benchmark measures
Past orders→All from approved vendors→Average score
What the workflow promised
Any order, ever→Never an unapproved vendor→Pass or fail, every time
Think about it. Say your benchmark was built from last year's real orders, a typical setup. How many of them went to an unapproved vendor? None. The workflow made that impossible. So how many points could an agent lose on the benchmark for breaking that rule? Also none. The test is blind to exactly the thing you'd most hate to get wrong.

5How it works: replacing a workflow safely

  1. Write down every promise. Approved vendors only, cheapest wins, a manager approves before the order, a spending cap. Read the code, not just the docs, since some promises live in one quiet line.
  2. Ask whether the benchmark can see each one. If no case tempts the agent to break a promise, the score says nothing about it. Add cases that do: a cheaper unapproved vendor, or a vendor page with planted instructions, the guide 12 attack.
  3. Move each promise into code. The order tool rejects any vendor not on the list. The price rule is checked in code. Now the agent can be as free as it likes inside the fence.
  4. Test promises as pass or fail, over many runs. One break is a failure, not a slightly lower average.
  5. Switch gradually. Run the agent alongside the workflow on real orders and compare. Move traffic over in steps. Delete the workflow last: until then it's your way back.

Why was the old workflow hard to hijack? The design patterns paper (2025) names the shape: in Plan-Then-Execute, the agent fixes its list of actions first, so data it reads later can't make it leave the plan. The authors note this doesn't stop every injection, but it protects which actions run. A fixed workflow has that by design. A free-form agent gives it up unless you rebuild it in code.

Worked example, with real numbers. Averages hide how often an agent fails. τ-bench (Yao et al., 2024) tests customer-service agents that must follow a policy document, like an airline's change rules. It introduced pass^k: the chance that all k tries at the same task succeed. GPT-4o's average success on its retail tasks was about 61%. But the chance of getting the same task right in all 8 of 8 tries fell to under 25%. Same agent, same tasks. One number sounds decent, the other doesn't.

An illustration, with my own numbers: say the agent picks an approved vendor in 999 of every 1,000 orders. That's 99.9%, which sounds perfect. At 10,000 orders a year, it's about 10 orders to unapproved vendors. The old workflow's number was zero, by construction.

6Follow-ups they'll ask

So should the agent never replace the workflow?

It can, once every promise lives in code and passes its tests. Then the agent decides only what was never promised, like how to compare messy offers. Anthropic's advice fits: workflows give “predictability and consistency for well-defined tasks”, agents suit work that needs flexibility.

Why does the agent score higher at all?

Find out which cases it wins. If it wins on messy orders the fixed steps handled badly, that's real value worth keeping, inside the fence.

What else does the switch cost?

Anthropic's guide warns that agentic systems often trade speed and cost for better results. Compare cost per correct order, not just the score.

7Check yourself

Why can't a benchmark built from the workflow's own past runs see its guarantees?

The workflow never broke them, so no case in the data shows a promise being broken, or even tempts the agent to break one.

What is pass^k, and why does it suit a guarantee?

The chance that all k tries at the same task succeed. A guarantee has to hold every time, so you care about the worst run, not the average.

Put the safe switch in order.

List the promises, move each into code, test them pass or fail with tempting cases, run the agent alongside the workflow, and delete the workflow last.

8Words to know

Guarantee
A promise that holds every time, usually because code makes breaking it impossible.
pass^k
The chance that all k tries at the same task succeed. It falls fast when an agent is inconsistent.
Plan-Then-Execute
Fixing the actions before reading untrusted data, so that data can't change what runs.
