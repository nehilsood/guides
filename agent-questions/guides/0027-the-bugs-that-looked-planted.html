The bugs that looked planted

Original: AI Agent Engineering Interview #22 · The Synthetic Bug Trap

1The question

“To train an agent that fixes bugs across whole repositories with reinforcement learning, you need about 50,000 environments it can run. Real pull requests give you 3,000. Planting bugs in working repos gives you as many as you like. What's the catch, and how would you mix the two?” Senior AI Engineer interview, Google DeepMind

A pull request is a proposed code change that teammates review; a real one that fixed a bug gives you the broken code, the issue and the tests that prove the fix. Reinforcement learning is training by trial and score: the agent attempts a fix and is rewarded when the tests pass. An environment is the runnable copy of the repo, issue and tests it practises on.

2The trap

Trap A: “Made-up data is worse. Train only on the 3,000 real ones.”

Trap B: “Volume wins. Plant 50,000 bugs and train on those.”

Both treat the source as a quality label. The question is whether planted bugs train the skills real bugs need.

3Your 30-second answer

“The catch is that planted bugs don't look like real ones. In SWE-Lego's data, synthetic bugs touched 1 file on average against 3.7 for real ones, and half were logic slips, against 30% of real bugs. Those studies fine-tuned on a stronger agent's successful runs rather than running reinforcement learning, so the next step is my reasoning: RL rewards whatever passes the tests, so an agent trained mostly on planted bugs can learn habits that only work on them.

They're still valuable: cheap, endless, and far more often solved. So I'd use planted bugs for breadth, made realistically, for example by undoing real pull requests. I'd use real pull requests for depth: sample them more often and keep a held-out slice. That slice decides the mix: when adding planted bugs stops lifting the score on held-out real bugs, stop.”

4The idea in plain words

A proofreading course has few real manuscripts with real mistakes, so its software makes more by swapping letters in clean articles (“teh”, “recieve”). Trainees practise without limit and ace the course.

Then they meet a real manuscript. Its mistakes are a missing word, a wrong date, a sentence that contradicts page three. The trainees scan for swapped letters, find none, and pass it. They learned to spot the software's kind of mistake, not a writer's.

The course still helps, if its planted mistakes look like a writer's and a few real manuscripts are kept back for the final exam.

In reinforcement learning (RL), the score is the reward; here, 1 if the tests pass, else 0. The model being trained is the policy, and one full attempt is a rollout.

One training step
Environment: repo + issue + tests→Policy attempts a fix (a rollout)→Tests give the reward↺ nudge the policy
Think about it. Planted bugs average one file, 19 changed lines; say the failing test names the function. What's the quickest way to earn the reward, and would it help on a real bug across four files?

5How it works: the catch, then the mix

  1. Real environments are scarce. SWE-Gym (Pan et al., ICML 2025) has 2,438 real Python tasks, each runnable, with unit tests. SWE-smith's authors estimate that 50,000 tasks built that way would need 50 to 150 TB of storage.
  2. Planted bugs scale. SWE-smith (Yang et al., 2025) made 50,000 tasks from 128 repos for about $1,360 (with issue text written for 10,000 of them) and 295 GB. Its methods include model-modified and model-rewritten functions, random code edits and “PR mirror”, which undoes a real pull request. A model fine-tuned on runs from these tasks, SWE-agent-LM-32B, scored 40.2% on SWE-bench Verified.
  3. The catch is the kind of bug. SWE-Lego (Tao et al., 2026) found real tasks touched 3.7 files and 138.0 lines on average, synthetic ones 1.0 and 18.8. Logic slips were 29.9% of real bugs and 49.4% of synthetic; interface mismatches (calling code the wrong way) 26.6% against 12.8%. BugPilot (Sonwane et al., 2025) says deliberately written bugs “induce an out-of-distribution effect”: training data unlike what the model will meet. None of these studies ran RL: they fine-tuned on a stronger agent's successful runs, so carrying their results over to RL is my reasoning.
  4. Environments can teach shortcuts. In SWE-smith, an agent trained on issue texts that showed the failing test later tried to reproduce the bug in only 127 of 500 SWE-bench Verified runs, against 379 for one trained on model-written issues. The authors: “leaking the evaluation criteria causes the model to skip over writing a reproduction script”. My reasoning: RL pays for passing, not for how, so any habit that passes planted bugs grows stronger.
  5. How you plant matters. SWE-smith trained on 1,000 tasks of each kind: model-modified bugs gave 5.7% on SWE-bench Verified, PR mirrors 9.2%, with the other two close to PR mirrors. BugPilot keeps bugs an agent causes by accident while adding a feature; they beat other bug sets by 2% with half the data.
  6. The mix, my suggestions. Hold out real tasks from repos not used in training as the yardstick. Plant bugs realistically, reweight their kinds towards the real mix, and sample real tasks more often. Never show the test in issue text. Grow the planted share only while the held-out real score rises.

Worked example, with real numbers. SWE-Lego ran a teacher agent (Qwen3-Coder-480B) on every task and kept runs that passed all tests:

TasksSuccessful runsShareFiles / lines changed
Real18,4095,01027%3.7 / 138.0
Synthetic13,7109,10066%1.0 / 18.8

Synthetic tasks yielded more than twice the share of usable runs (66% against 27%), but on bugs about a seventh the size by lines changed. SWE-Lego's words: real data gives “depth”, synthetic gives “breadth”.

6Follow-ups they'll ask

Aren't planted bugs simply easier?

It depends on how they are planted. SWE-smith's difficulty model (1 easy, 5 medium, 9 hard) rated model-modified bugs 3.3 and random-edit bugs 3.6 on average, against 5.01 for full SWE-bench and 3.96 for SWE-bench Verified; rewritten functions (5.27) and combined bugs (5.72) rated harder. In the BugPilot study Claude Sonnet 4 solved 65.9% of SWE-smith tasks against 70.8% of SWE-bench Verified.

What ratio of real to planted would you start with?

No study I found gives one that transfers; SWE-Lego used about 18,000 real and 14,000 synthetic tasks. I'd train small runs at a few ratios and keep the best on held-out real bugs from unseen repos.

How do you stop the agent learning a planted-bug shortcut?

Remove the clue. In SWE-smith, issue texts that showed the failing test cut later reproduction attempts from 379 to 127 of 500 runs. My suggestions: write issues the way users do, add multi-file bugs such as BugPilot's feature-add bugs, and read rollouts that pass suspiciously fast.

7Check yourself

In reinforcement learning for a bug-fixing agent, what are the environment and the reward?

The environment is a runnable copy of a repo with a bug, the issue text and the tests. The reward is the score for one attempt: 1 if the tests pass after the agent's fix, otherwise 0.

How did real and synthetic bugs differ in the SWE-Lego dataset?

Real tasks touched 3.7 files and 138.0 lines on average, synthetic ones 1.0 file and 18.8 lines. Logic slips were 29.9% of real bugs but 49.4% of synthetic ones.

Which SWE-smith finding shows an environment teaching a shortcut?

An agent trained on issue texts that showed the failing test later tried to reproduce the bug in only 127 of 500 SWE-bench Verified runs, against 379 for one trained on model-written issue texts.
