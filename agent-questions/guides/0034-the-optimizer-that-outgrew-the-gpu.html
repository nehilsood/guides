The optimizer that outgrew the GPU

Original: Advanced NLP Interview Questions #12 · The Optimizer State Memory Trap

1The question

“A 7-billion-parameter training run worked fine with plain SGD. You swap in Adam so it converges faster, change nothing else, and every GPU runs out of memory at once. It's the same model, so where did the memory go?” Senior Machine Learning Engineer interview, Google DeepMind

This builds on Day 42's Adam and on yesterday's guide 33, which showed what Adam's two running averages, m and v, buy: a step size per weight. Today is what they cost. A parameter is one weight. Plain SGD (Day 42's update without momentum) keeps nothing between steps.

2The trap

Trap A: “Adam does more maths per step, so it needs more memory.”

Trap B: “Halve the batch size and it'll fit.”

The extra maths is a handful of operations per weight. The cost is what Adam stores between steps, and the batch size doesn't touch that.

3Your 30-second answer

“The model didn't grow; what training stores per weight did. Plain SGD keeps nothing between steps. Adam keeps two numbers per weight, its momentum and its average squared gradient, and in mixed-precision training both sit in 4-byte numbers beside a 4-byte master copy of the weights.

The ZeRO paper counts 16 bytes per parameter: 2 for the working weights, 2 for gradients, 12 for that master copy and Adam's state. For 7 billion parameters that's 112 GB before activations (the layer outputs kept for backprop), eight times the 14 GB of weights, and if each GPU holds the whole model, as in plain data parallelism, all of it sits on every GPU. Fixes: split Adam's state across GPUs, as ZeRO does; store it in 8 bits; or use Adafactor, which keeps far less. A smaller batch only trims activations.”

4The idea in plain words

A school office keeps a quick index card per pupil, with rounded marks, small enough to flip through fast. The full file sits in a cabinet with every mark to the decimal, so small changes add up instead of being rounded away.

A new progress policy arrives: for every pupil, keep two more full-size sheets, a running average of recent marks and one of how much they swing. Not one new pupil, yet the office needs several more cabinets. And every branch office keeps its own copy of everything.

The cards are the working weights in 2-byte numbers (fp16); the cabinet file is a 4-byte (fp32) master copy. Using both is mixed precision: the forward and backward passes run in fp16 for speed, and the update is applied to the fp32 copy. The two sheets are Adam's m and v, its optimizer state. The branch offices are data parallelism: every GPU holds the whole model and trains on its own slice of each batch.

Think about it. If every number took 2 bytes, Adam would store weights, gradients, m and v: four times the weights. The post counts every number at 2 bytes, which gives the common “3–4× the weights” rule. With the 4-byte master copy, m and v of mixed precision, what multiple is it? Count it in the table below before you read on.

5How it works: count the bytes, then cut them

Count. ZeRO (Rajbhandari et al., 2019) lists what mixed-precision Adam holds per parameter. The 7B column and the SGD row, which uses the same accounting without m and v, are our arithmetic.

Stored per parameterBytes7B model
fp16 weights214 GB
fp16 gradients214 GB
fp32 master weights428 GB
fp32 momentum (m)428 GB
fp32 squared-gradient average (v)428 GB
Adam total16112 GB
Plain SGD (first three rows)856 GB

So the switch doubles model-state memory, 56 GB to 112 GB, and Adam's 16 bytes are eight times the 2-byte weights. On a GPU with 80 GB (our example size), the SGD run's model states fit and the Adam run's cannot.

Where the premise outruns the evidence. The “3–4×” rule holds when weights and state share one precision (all fp32: 16 bytes, 4× the 4-byte weights), but undercounts mixed precision by about half. It also leaves out activations, the layer outputs saved in the forward pass for backprop (Day 38). ZeRO puts them at about 60 GB for a 1.5B GPT-2 (OpenAI's language model) at sequence length 1K and batch 32.

Cut.

  1. Split the state across GPUs. Plain data parallelism, ZeRO says, “replicates the entire model states” on every GPU. ZeRO's first stage gives each GPU only its share of the fp32 master copy and Adam's state, so each keeps 4 bytes per parameter plus 12 ÷ N on N GPUs. For a 7.5B model on 64 GPUs, per-GPU model state falls from 120 GB to 31.4 GB; splitting the gradients too gives 16.6 GB.
  2. Store the state in 8 bits. Dettmers et al. (ICLR 2022): 32-bit Adam state takes 8 bytes per parameter, and their 8-bit version takes 2, matching 32-bit results on their tasks, up to a 1.5B language model. For 7B, that is 56 GB of state down to 14 GB (our arithmetic).
  3. Keep less state. Adafactor (Shazeer and Stern, 2018) stores only row and column sums of v for each weight matrix and drops momentum, with results comparable to Adam on WMT 2014 English–German translation.
  4. Recompute activations. Activation checkpointing saves only some layer outputs and recomputes the rest during backprop. ZeRO cites it cutting that 60 GB to about 8 GB, at 33% extra computation.

Worked example, with real numbers. ZeRO's own case: GPT-2 with 1.5 billion parameters needs 3 GB for its fp16 weights, yet “cannot be trained on a single GPU with 32GB memory”. At 16 bytes per parameter, its model states alone take at least 24 GB, before any activations.

6Follow-ups they'll ask

Would SGD with momentum have crashed too?

It stores one extra number per weight, not two. Dettmers et al. put 32-bit momentum at 4 bytes per parameter and 32-bit Adam at 8. With ZeRO's mixed-precision accounting that's 12 bytes per parameter, 84 GB for 7 billion (our arithmetic), so on an 80 GB GPU (our example size) it would fail too, though by less.

Why not keep everything in 2-byte numbers and drop the master copy?

ZeRO says the mixed-precision optimizer keeps fp32 copies “to effectively compute and apply the updates”. Our reasoning: an update is usually tiny next to the weight, and fp16 would round much of it away.

How would you size memory before launching?

Model states: 16 bytes × parameters for mixed-precision Adam. If ZeRO splits the 12 bytes of fp32 master copy and Adam state across N GPUs, each GPU holds 4 + 12 ÷ N bytes per parameter. Then activations, which for a transformer, ZeRO says, grow with layers × hidden size × sequence length × batch size. Compare the sum with one GPU's memory.

7Check yourself

By ZeRO's count, what does mixed-precision Adam store per parameter?

2 bytes of fp16 weights, 2 of fp16 gradients, and 12 for the fp32 master weights, momentum and squared-gradient average: 16 bytes.

How much model-state memory does a 7B model need under mixed-precision Adam?

16 bytes × 7 billion = 112 GB, before activations. Plain SGD under the same accounting needs 56 GB.

Why doesn't halving the batch size fix an out-of-memory error caused by switching to Adam?

Batch size changes only the activations. Adam's extra state is a fixed amount per weight, the same at any batch size.
