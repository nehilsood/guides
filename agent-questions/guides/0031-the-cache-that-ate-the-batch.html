The cache that ate the batch

Original: AI Agent Engineering Interview #33 · The KV Cache Memory Trap

1The question

“Caching keys and values means each step only handles the newest token. So is the cache pure gain, or does it cost you something? What, exactly?” Senior ML Engineer interview, Google

This builds on yesterday's lesson, KV Cache and Prefix Caching. A KV cache stores each earlier token's keys and values (vectors that attention reads), per layer, so they aren't worked out again. Decode writes the answer one token per step.

2The trap

Trap A: “Yes, it's free. The cache remembers old keys and values, so each new token is cheap.”

Trap B: “It costs a bit of memory, but memory is cheap.”

Trap A skips the bill. Trap B skips its size. The interviewer wants the trade, with a number.

3Your 30-second answer

“Not free: I pay in memory to save arithmetic. Without the cache, every step redoes all earlier tokens' keys and values, at every layer. Queries aren't stored: a token's question only matters while that token is being written, so keeping it gains nothing.

What I pay: every layer keeps keys and values for every token of every request. On Llama 3.1 8B that's 128 KiB a token, so one 32k-token request holds 4 GiB. That memory could have held more requests side by side. Each step also reads all the model's weights plus the whole cache. So at long context, the limit is how much memory I have and how fast it can be read, not how fast the chip does arithmetic. The levers: share keys and values across heads, store fewer bits, allocate in small pages, share prompt starts, look back a fixed window. Each costs something.”

4The idea in plain words

You're replying to a long email thread, one word at a time. Without notes, you reread the whole thread before each word. With notes, you keep one index card per message, a label and its content, and glance over the cards instead. Much faster, but the cards fill a desk you share with colleagues, so fewer of them fit. And every word still means scanning every card.

The label is the key, the content the value. Your question for this word is the query: you need it for this word only. Every later word reads the cards, so they are kept; the question is not.

One decode step: only the new token is worked out
New token → its Q, K, V→Add K, V to the cache→Q reads every cached K, V↺ next token
Think about it. The cache grows with request length and with the number of requests run together (the batch). Double either and it doubles. The weights don't grow.

5How it works: the bill, then the levers

The bill. Per token: 2 (key and value) × layers × KV heads × head size × bytes per number. A KV head is one set of keys and values in a layer. Head size is how many numbers one head holds per token. For OPT-13B, which has a KV head per query head, the PagedAttention paper gets 2 × 5,120 (its full width) × 40 layers × 2 bytes, about 800 KB a token. It finds cache memory caps the batch: for a 13B model on a 40 GB A100, weights take about 65% of memory and the cache close to 30%.

Why decode is bandwidth-bound. Memory bandwidth is how fast data moves from GPU memory to the compute cores. A decode step does little maths but loads every weight and every cached key and value. Pope et al. find the weights dominate that load at small batches, and the cache at long contexts and big batches. FLOPs are the chip's arithmetic operations. More per second can't speed up a step that is waiting on memory.

Worked number, Llama 3.1 8B (the Llama 3 paper's 8B; its shape matches the Llama-3-8B in lesson 0008). Table 3 of the paper gives 32 layers, width 4,096, 32 query heads and 8 KV heads. A public copy of its config gives head size 128 (4,096 ÷ 32). At 2 bytes a number: 2 × 32 × 8 × 128 × 2 = 131,072 bytes (128 KiB) a token.

Llama 3.1 reads up to 128K tokens. A 32,768-token request needs 4 GiB. The lesson's 80 GiB card loses 16 GiB to the weights and 4 GiB to overhead. That leaves 60 GiB, so 15 such requests fit. All three rows below are my own arithmetic from Table 3 and that 60 GiB.

The levers, and their costs.

  1. Fewer KV heads. Multi-query attention (MQA) keeps one KV head for all query heads: much faster decoding, “minor” quality loss. Grouped-query attention (GQA) keeps a few, with quality close to full heads. Cost: the model must be trained that way, or uptrained (an existing model trained a little more; 5% of the original compute in the GQA paper).
  2. Smaller cache format. vLLM can store the cache in FP8 (8-bit numbers): 1 byte instead of 2, so half the size (my arithmetic). Cost: vLLM recommends calibrating on a dataset for best accuracy; some layer types are more sensitive.
  3. Paging. Older systems reserved space for each request's longest possible output, and only 20.4–38.2% held real tokens. vLLM's PagedAttention hands out small blocks on demand: near-zero waste, 2–4× the throughput (requests served per second). Cost: a 20–26% slower attention kernel (the GPU code that runs attention).
  4. Prefix sharing. Requests with the same system prompt point at the same cached blocks. Cost: only an exact match from the first token counts.
  5. Sliding window. Mistral 7B attends to the last 4,096 tokens per layer with a fixed rolling cache: 8× smaller at 32k, with no quality loss in their tests. Cost: older tokens are reached only indirectly, through the layers.

6Follow-ups they'll ask

Does prefix caching make tokens stream faster?

No. It skips prefill work (the pass over the prompt), so the first token comes sooner. Later decode steps still read the whole cache.

Why not use MQA everywhere?

Quality can drop. And split across 8 GPUs, one KV head can't be divided: the Llama 2 paper says you copy the cache to every GPU or split by batch.

What happens when the cache fills mid-answer?

vLLM pauses the newest requests. It moves their blocks to CPU memory, or drops them and rebuilds them later.

7Check yourself

Why are keys and values cached but not queries?

A token's query only matters while that token is being made. Its key and value are read by every later token.

Llama 3.1 8B, 2-byte cache: how much does a 16k-token request take?

128 KiB × 16,384 = 2 GiB. Half the 32k figure, because the cache grows with length.

Why don't more FLOPs fix slow long-context decode?

Each step waits on loading the weights and the whole cache.

8Words to know

Query, key, value
Attention's three vectors per token: the query asks, keys are matched to it, values are read.
Prefill / decode
Prefill reads the prompt in one pass. Decode writes one token per step.
Bandwidth-bound
Limited by how fast data moves from memory, not by the maths.
FLOPs
Arithmetic operations. A chip's speed at maths is how many it does per second.
