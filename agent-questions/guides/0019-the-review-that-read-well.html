The review that read well

Original: AI Agent Engineering Interview #8 · The Skill Evaluation Trap

1The question

“Half a year ago your team gave its coding agent a skill for reviewing code. No one has checked whether it makes reviews better. Using real pull requests, how would you keep measuring how good it is, and turn what you learn into specific changes to the skill?” Senior AI Engineer interview, Google

A pull request is a proposed code change that teammates review, line by line, before it is merged. A skill, from guide 9, is a folder of instructions the agent opens when a task needs it.

2The trap

Trap A: “Have a model grade every review comment out of ten, then ask it to rewrite the skill until the grades go up.”

Trap B: “Track the share of its comments that authors acted on. Higher is better.”

A grade shows how a comment reads, not what it changed. And the skill picks how many comments to post, so saying less raises the share.

3Your 30-second answer

“I'd measure what authors did with each comment, not how it reads. Six months of pull requests already hold the outcome: after each comment, a later commit either changed the lines it pointed at or didn't. So I label every comment acted on, pushed back or ignored.

I count acted-on comments per pull request, not as a share of comments posted, so the skill can't score by staying quiet, and I keep a no-skill slice to see what authors fix anyway. Then I group the ignored comments by the rule behind them, and reword or delete those rules. Each new version must beat the current one and no skill on live pull requests. A model judge only helps label diffs.”

4The idea in plain words

A teacher writes comments in the margins of a student's essay. Do they help?

You could ask another teacher to rate them as clear and well argued. That tells you how they read. Or you could open the next draft and check whether each sentence a comment pointed at changed. That tells you what they did. Ignored comments teach you something too: if half are about commas, stop writing about commas.

Asking a model to score a skill's comments is an LLM judge: one model grading another's output. It shows how a comment reads; later commits show what the author did.

Words a model wrote
The skill file→The comment it posts
Things a person did: the evidence
The author changes the line, or doesn't→The merged code holds up, or breaks
Think about it. My own numbers: the skill posts 10 comments per pull request and authors act on 5, a 50% share. Someone adds “only comment when you are certain”. Now it posts 3 and authors act on all 3: 100%. The share doubled, but authors fix 3 things per pull request instead of 5. Which version helps more?

5How it works: a feedback loop from real pull requests

  1. Label every past comment from what happened next. Microsoft researchers call a comment a change trigger when a later version of the pull request changes code near where it pointed; of distances up to ten lines, one worked best. Check the change came after the comment; mark “pushed back” if the author argued.
  2. Pick a count the skill can't game. Acted-on comments per pull request. My own addition: report bugs later fixed on lines the skill reviewed but never flagged, a number that only worsens when it says less.
  3. Keep a no-skill slice. Authors fix some things anyway, and an always-on skill has no baseline. Start an A/B test on a random share of pull requests; Anthropic's skill guide puts “Establish baseline” before writing instructions.
  4. Turn ignored comments into edits. Group them by the rule behind them. Reword a rule that's right but unclear, delete one that's mostly ignored.
  5. Gate every edit. Replay it on past pull requests, then run it live against the current version and no skill. If no skill does as well, delete the skill: once loaded, its tokens compete with everything else in the context.

Google runs a similar loop on clicks for automated code checks. Its Tricorder platform posts analyzer findings into code review, with Not useful and Please fix buttons. It defines an effective false positive as “any report from the tool where a user chooses not to take action to resolve the report”. An analyzer with a not-useful rate of 10% or more goes on probation; above 25% it may be turned off. The fix “may be as simple as updating the wording of results”.

Worked example, with real numbers. In Bosu, Greiler and Bird (2015), a change within one line marked a comment its author rated useful with 88% precision and 78% recall (guide 9's two measures). Of about 1.5 million human comments in five Microsoft projects, 64–68% were classed useful; first-time reviewers of a file managed 32–37%.

A 2024 industry study of an LLM reviewer built on Qodo PR Agent covered 4,335 pull requests, 1,568 reviewed by the tool. Developers marked 73.8% of its comments Resolved, a label the authors note some may have used loosely, while average closure time rose from 5 hours 52 minutes to 8 hours 20 minutes.

6Follow-ups they'll ask

Isn't an LLM judge faster than all this?

Use it for one narrow job: saying whether the diff that followed a comment addressed it. Grading quality rewards how a comment reads, and judges have known biases. In Zheng et al. (2023), padding an answer with a repeated list fooled Claude-v1 and GPT-3.5 in 91.3% of tries (GPT-4 in 8.7%), and GPT-4 gave the same verdict with the answers swapped only 65% of the time. Spot-check its labels against people.

The author changed the line. Did the comment cause it?

Not necessarily: a test may have failed, or a colleague said the same. Compare with pull requests where the skill was off, or wrote comments without posting them, and credit it only with the difference.

When would you delete the skill?

When it doesn't beat no skill on acted-on comments per pull request in a fair live test. Anthropic's skill guide says to measure the agent without the skill first, and a loaded skill's tokens compete with the rest of the context, so a useless skill still costs every review.

7Check yourself

What is a change trigger in the Bosu et al. Microsoft study?

A review comment followed, in a later version of the same pull request, by a code change within one line of the lines it pointed at. As a sign that the author found the comment useful, it had 88% precision and 78% recall.

Why is “share of a review skill's comments acted on” easy to game?

The skill decides how many comments to post. Posting fewer, safer comments raises the share while catching fewer problems. Count acted-on comments per pull request instead, and track missed bugs beside it.

What does Google's Tricorder do with an analyzer that developers find noisy?

It tracks the analyzer's not-useful rate from developers' clicks in code review. At 10% or more the analyzer goes on probation and its writer must show progress; above 25% it may be turned off. The fix can be as simple as rewording its messages.

8Words to know

LLM judge
One model asked to grade or compare another model's output.
Change trigger
A review comment followed by a code change right next to the lines it pointed at.
