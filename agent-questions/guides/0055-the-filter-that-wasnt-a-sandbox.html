The filter that wasn't a sandbox

Original: LLM Inference Interview Questions #13 · The AST Sandbox Trap

1The question

“Six weeks after launch, your code-running agent is breached. Security had approved it because every script it writes passes an AST filter first: no os, no subprocess, no double-underscore attributes. What kind of attack could that filter never have stopped?” Staff AI Engineer interview, Google

This builds on Day 143, “AI app architecture: gateway, guardrails, prompt-injection defences”. An AST (abstract syntax tree) is a program parsed into its parts, so a filter can reject banned parts before anything runs. Python's dunder names, like __class__, are its internal hooks. A sandbox is a sealed place to run code, with limits set from outside it (guide 5). A container is a program walled off from others on one machine; a microVM is a tiny virtual machine with its own kernel; audit hooks are checks Python runs before sensitive actions.

2The trap

Trap A: “Find the trick it used and add it to the blocklist.”

Trap B: “Swap the home-made filter for RestrictedPython, which is built for this.”

Both still try to make code safe by reading it. The danger is in what the code can reach once it runs.

3Your 30-second answer

“Anything that doesn't look dangerous in the source. The filter judges text; the attack lives in what the running code can reach. A banned attribute can hide in a string, because str.format looks attributes up by name; an allowed library can read files or open connections itself; a short loop can eat all the memory. A blocklist must name every path to danger, and Python has too many. Its own docs call audit hooks ‘not suitable for implementing a sandbox’, and RestrictedPython says it ‘is not a sandbox system’.

So the filter stays as a quick first check, and the boundary moves below Python: each script in a gVisor container or a Firecracker microVM, no network by default, no secrets inside, CPU, memory and time limits, a fresh box per run.”

4The idea in plain words

A museum guard checks every bag at the door for hammers and crowbars. Inside, the display cases are unlocked. A visitor with an empty bag walks out with a painting anyway: she used what was already in the room.

The bag check stops the obvious, but only what it was told to look for. Real museums lock the cases.

The AST filter is the bag check: a denylist, a list of banned things. Python is the room: every allowed object leads to others. Locking the cases means isolating the code from the computer it runs on. The kernel is the core of the operating system; programs ask it for files, network and memory through system calls. Isolation that sits at that level doesn't care how the code was written. And the code needn't come from a clever model: instructions planted in something the agent reads can ask for it (guide 12).

The approved design
Model writes a script→AST filter reads it→Runs with the server's files, network and keys
The fix
Model writes a script→Quick filter→Fresh microVM: no network, no secrets, hard limits→Only the output comes back
Think about it. An illustration; nothing is run. The filter bans the attribute __class__. A script contains the text "{0.__class__}" and passes it to format. What does the filter see? A string, which is allowed. What does Python do? Looks the attribute up by name and returns what it finds: data leaks out, though no code runs. The check and the action happen at different times.

5How it works: what reading the code misses, and where the wall goes

  1. Names can hide in strings. Python's format-string docs: “An expression of the form '.name' selects the named attribute using getattr()”. Armin Ronacher wrote in 2016 that this “came up as a way to bypass the Jinja2 Sandbox”.
  2. Allowed code reaches far. RestrictedPython's docs say compiling restricted code “is not sufficient as a sandbox environment, as all calls to libraries are still available”, and its front page that it “is not a sandbox system or a secured environment”.
  3. Harmless-looking code can exhaust the machine. Even ast.literal_eval, which runs no code, can on “a relatively small input” cause “memory exhaustion or to C stack exhaustion, crashing the process”, per the ast docs.
  4. In-process guards can be switched off. The sys docs say audit hooks “are not suitable for implementing a ‘sandbox’” and “malicious code can trivially disable or bypass” them.
  5. Put the wall below the language. gVisor sits under a container and moves the system interfaces into “a distinct, per-sandbox application kernel in order to minimize the risk of a container escape exploit”. Firecracker runs each workload in a microVM with “KVM-based isolation” (KVM is Linux's built-in support for virtual machines); its site claims boot in under 125 ms and under 5 MiB of overhead per VM. Guide 5's V8 isolate, a gVisor container and a microVM are three strengths of the same idea: a sealed box with limits set from outside.

An illustration, put together from the docs above; not a real breach. How four kinds of attack look to each layer:

Where the premise outruns the evidence. The question doesn't say how the breach happened, so any row is a candidate. And kernel isolation lowers risk rather than removing it: gVisor's own words are “minimize the risk”. Keep the filter, the limits and the isolation as layers (our reasoning).

6Follow-ups they'll ask

Would an allowlist, naming what's permitted instead of what's banned, fix the filter?

Better, but an allowed object still leads to others (a format string reaches attributes through getattr), and the code still runs inside your server. gVisor's docs make the same point about rule-based policies at the kernel level: “extremely difficult (if not impossible)” to define reliably for unknown programs. Keep it as a layer; isolate underneath.

gVisor or Firecracker?

gVisor puts its own kernel, written in Go and running as an ordinary user-space program, between the code and the host. Firecracker gives each workload a small virtual machine with its own kernel under KVM; its site claims boot in under 125 ms. Our summary: the VM is the thicker wall, gVisor the easier fit for container platforms, at a cost its docs name: “poor performance for system call heavy workloads”.

What goes in the sandbox's settings besides isolation?

No network unless a named host is needed; no credentials inside, so tools that need keys run outside it; CPU, memory and wall-clock limits; a read-only filesystem apart from a scratch folder; and a fresh sandbox for every run, thrown away afterwards (our checklist, in line with guide 5's Code Mode example).

7Check yourself

Why can't an AST blocklist make running untrusted Python safe?

It judges the source text, but the danger is what the running code can reach: attribute lookups hidden in strings (str.format calls getattr), allowed libraries that touch files or the network, and loops that exhaust memory or CPU.

What do Python's docs and RestrictedPython's docs say about using them as a sandbox?

Python's sys docs say audit hooks are “not suitable for implementing a ‘sandbox’” and can be bypassed; RestrictedPython's docs say it “is not a sandbox system or a secured environment”.

Where should the security boundary for agent-written code sit?

Below the language: a gVisor container or a Firecracker microVM, with no network by default, no secrets inside, CPU, memory and time limits, and a fresh sandbox per run. A code filter stays only as a quick first check.
