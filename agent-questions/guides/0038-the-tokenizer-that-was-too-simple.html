Agent question 38 · extra · Day 67 · about 10 minutes

The tokenizer that was too simple

Original: LLM System Design Interview #5 · The FLOPs Compression Hack

1The question

“Raw bytes instead of BPE: 256 symbols, next to no tokenizer code, and no string the model can't take in. A colleague wants to switch. What's the catch?” AI Engineer interview, OpenAI

This builds on Day 66: BPE starts from bytes and merges frequent pairs into tokens, and tokens are the unit of price and of context (“Your order will arrive in 20 minutes.” is 9 tokens; the Hindi version 37 in cl100k_base, 12 in o200k_base).

2The trap

Trap A: “Subword tokens mean something and bytes don't, so the model learns better from tokens.”

Trap B: “Bytes are fine. A 256-row embedding table even saves memory.”

Both miss the bill. The catch is length: every byte is a position the model must process, and attention's work grows with the square of the number of positions.

3Your 30-second answer

“The catch is sequence length. Studies put BPE tokens at about four bytes, so the same text becomes about four times as many positions. Attention scores every position against every earlier one, so that part of the work grows about sixteen-fold; every other layer, and the number of generation steps, grows about four-fold; and a fixed context window holds a quarter of the text. Hindi, in a script of three bytes a letter, gets longer still: 89 bytes against 37 for the same sentence in English.

And the benefit isn't unique: byte-level BPE, as in GPT-2, starts from the same 256 bytes, so it encodes any string too, then merges bytes into shorter sequences. ByT5 showed raw bytes can compete, but cost a third more pre-training time and up to ten times slower inference. Byte models that close the gap, like Meta's BLT, group bytes back into longer units.”

4The idea in plain words

At a networking evening the host insists every guest shakes hands with every other guest. With 12 guests that's 66 handshakes. Now each guest brings three friends: 48 guests, four times as many, but 1,128 handshakes, about seventeen times as many. The coat check, the name badges and the drinks only quadruple; the handshakes explode.

Positions in a transformer are the guests. Attention is the handshakes: each position scores itself and every earlier position (Day 57), so n positions make n(n+1)/2 scores. The MLP layers (Day 59) are the coat check: their work grows in step with n. A tokenizer decides how many guests arrive for the same text.

“Your order will arrive in 20 minutes.”
BPE: 9 positions, 45 scores→Bytes: 37 positions, 703 scores
Think about it. That sentence is 37 bytes and 9 tokens, 4.1 bytes a token. Why are the scores 15.6 times more, not 4.1? Because both sides of each score multiply: 37 × 38 ÷ 2 = 703 against 9 × 10 ÷ 2 = 45 (our arithmetic). For long texts the ratio approaches 4.1² ≈ 17.

5How it works: where the extra length costs

  1. How much longer is bytes? The ByT5 paper measured mT5's subword tokenizer over its multilingual training data at 4.1 bytes per token overall, from 2.5 for Maltese to 9.0 for Khmer. The BLT paper gives 3.7 bytes per token for Llama 2's BPE and 4.4 for Llama 3's. Longer tokens have a price: Llama 3 got there “at the cost of increasing the size of its embedding table 4x”, and every token also needs its own output score (our reading).
  2. Attention grows with the square. The Transformer paper lists self-attention's cost per layer as O(n² · d) for n positions of width d; ByT5 notes this “quadratic time and space complexity in the sequence length”. At 4× the length, that part costs about 16×.
  3. Everything else grows in step. The matrix multiplies outside attention, Day 59's MLP among them, do the same work per position, so 4× the positions is 4× the work, and Day 64's generate runs one pass per position it writes.
  4. Context shrinks. A window counted in positions holds a quarter of the text at 4 bytes a token (our arithmetic).
  5. “Never unknown” is already solved. GPT-2 runs BPE over bytes: it “only requires a base vocabulary of size 256”, so any string can be encoded, and merges make it short. Sennrich et al. introduced subword BPE in 2015 exactly to encode “rare and unknown words as sequences of subword units”.

An illustration, with our own counts. Day 66's two sentences, counted with tiktoken (bytes are UTF-8, where each Devanagari character takes 3 bytes). “Scores” is n(n+1)/2 for one attention layer.

A good tokenizer for a language is the one that makes raw bytes look worst. The byte model pays the same 89 positions for Hindi whichever BPE you compare it with.

What the byte models found. ByT5 used a standard Transformer on raw bytes and was competitive on quality and “significantly more robust to noise” such as typos, but its authors report “+33% pre-training time” and inference “up to 10× slower in the worst case”. GPT-2's authors note, citing earlier work, that byte-level language models were “not competitive with word-level LMs” at the time. MEGABYTE and BLT keep bytes as input but group them into patches, so the big model sees a shorter sequence; BLT reports matching Llama 3 at equal training compute while using up to 50% fewer FLOPs (arithmetic operations) when generating, with average patches of 6 to 8 bytes.

Where the premise outruns the evidence. “Sixteen times the cost” is the attention part only. Sarathi-Serve measured Mistral-7B and found linear layers “still contribute more than 80% to the total time even at high sequence lengths”, so for a model like that the whole bill sits nearer 4× than 16× (our inference).

6Follow-ups they'll ask

Then why not a far bigger vocabulary, with whole sentences as tokens?

Each token needs an embedding row and an output score, and rare tokens get few training examples. The BLT paper notes Llama 3 raised its average token from 3.7 to 4.4 bytes “at the cost of increasing the size of its embedding table 4x” over Llama 2.

Are there real advantages to bytes?

Yes. The ByT5 paper found byte models “significantly more robust to noise” such as typos and better on spelling-sensitive tasks, the same weakness Day 66 shows with counting the r's in “strawberry”.

How do byte models fix the length problem?

They shorten the sequence the big model sees. MEGABYTE cuts bytes into fixed patches with a small model inside each patch; Meta's BLT sizes patches by how predictable the next byte is, averaging 6 to 8 bytes, longer than Llama 3's 4.4-byte tokens.

7Check yourself

A text is 4 times longer in bytes than in tokens. Roughly how much more attention work is it as bytes, and why?

About 16 times, because each position scores every earlier one, so the number of scores grows with the square of the length. The rest of the model grows about 4 times.

Why isn't “bytes never hit an unknown token” a reason to drop BPE?

Byte-level BPE, as in GPT-2, also starts from all 256 bytes, so it can encode any string; its merges just make common text shorter.

Why does a byte model make a Hindi sentence so much longer than its English version?

Each Devanagari character takes 3 bytes in UTF-8, so Day 66's Hindi sentence is 89 bytes against 37 for the English. How much worse than BPE that is depends on the BPE: 5.7 times the attention scores in cl100k_base (English: 15.6 times), but 51 times in o200k_base.
