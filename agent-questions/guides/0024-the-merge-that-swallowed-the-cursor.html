The merge that swallowed the cursor

Original: AI Agent Engineering Interview #10 · The Prompt Boundary Tokenizer Trap

1The question

“A colleague retrained the tokenizer for our code model so that tokens can join across spaces. The same code now takes about 40% fewer tokens, and loss on held-out files went down. Why could autocomplete in the editor get worse once this ships, and what would you check before signing off?” Senior AI Engineer interview, Microsoft

Three training words. Tokens are the pieces of text a model reads; the tokenizer decides where the cuts go. Loss measures how surprised the model is by the real next token, averaged over tokens: lower is better. A held-out set is files kept out of training, so the score isn't on memorised text.

2The trap

Trap A: “Both dashboards went green, so sign it off.”

Trap B: “Never touch a tokenizer that works.” That rejects a real speed-up unmeasured.

Ask what text both numbers were measured on.

3Your 30-second answer

“Both numbers come from whole files read from the start. Autocomplete starts wherever the user stopped typing, and that's often in the middle of a token. Every merge deletes a place where a token can end, so joining across spaces means the cursor lands inside a token more often. Models do badly there: in one 2026 study, on code prompts built to end mid-token, a model's output began with the true continuation 5% of the time, against 88% when the same prompt was cut back to a token boundary.

Before approving, I'd compare bits per byte rather than loss per token, since bigger tokens change what loss averages over. Then I'd cut held-out files at real cursor positions and compare completions under both tokenizers, with and without a fix like token healing. Ship only if the cursor numbers hold up.”

4The idea in plain words

A fridge-poetry set has single letters plus whole-word magnets. A new set adds phrase magnets like “see you at”, so notes take far fewer magnets.

Now someone leaves a half-finished note: “see you at the ca”. You've only ever used “café” as one magnet, never finished a word from loose letters. You might add “café” after them (“cacafé”) or pick an odd word. The bigger the magnets, the more often a note stops inside one.

A tokenizer usually learns by BPE merges: start from single characters, then repeatedly join the most common neighbouring pair into a new token. Normally a pre-tokenization rule first splits text at spaces, so no merge crosses a space. Your colleague removed that rule.

Held-out loss: whole files, cut at the start
File start→Every token boundary is natural
Autocomplete: cut at the cursor
Code up to the cursor→Cut may fall inside a token→Model guesses from a state it never saw
Think about it. In training, the tokenizer always wrote .cache as one token. What has the model learned to expect after a lone . token, and is cache on that list?

5How it works: why the cursor suffers, and what to check

  1. The mid-token cut is a known failure. Xu et al. (February 2026) call it the partial token problem: a prompt ending “in the middle of the expected next-token”. They built 5,223 code prompts that end mid-token and asked the model to repeat a given line, so the right continuation was known. Qwen3-32B's output started with the right continuation only 5.05% of the time, against 88.48% with the same prompts cut back to the last token boundary. Larger models were equally or more affected.
  2. Splitting at spaces was only a partial guard. The SuperBPE authors (COLM 2025), who built a tokenizer that merges across spaces, note that splitting at spaces first helps mostly with English prompts that end before a space, and “cannot fix the underlying issue” for programming languages. My reasoning: removing the split takes away even that partial guard. Xu et al. warn that multi-word tokenizers may hit the problem “even in English use”.
  3. Code was already exposed. Xu et al. measured how often a Python punctuation boundary falls inside a token: 68.08% for Qwen3, Llama 3 and OLMo 2, against 25.11% for Gemma. In autocomplete, they add, users “may pause their typing anywhere”.
  4. Loss per token isn't comparable. Bigger tokens carry more text each, so each is harder to predict. SuperBPE compares models by bits per byte: total surprise divided by the text's size in bytes, which doesn't depend on the tokenizer. Even then, its models' bits per byte differed only slightly and ranked them differently from task scores.
  5. So measure the product. My checklist: bits per byte, then completions at real pause points from editor logs, old tokenizer against new, with and without a fix.

Worked example, an illustration with made-up tokenizations. Take this 30-character line: return self.cache.get(key). Splitting at spaces and punctuation gives 10 tokens: ···· return ·self . cache . get ( key ). Free merging gives 6: ····return ·self .cache .get( key ), which is 40% fewer.

Of the 29 positions inside the line, a cursor sits on a token edge at 9 under the old split (31%) and at 5 under the new (17%). The lost edges include the spot right after self., probably just where people pause for a suggestion.

6Follow-ups they'll ask

Can't we just turn on token healing and ship?

Not without measuring. Token healing, from the guidance library, backs up one token and forces the next token to start with the removed text. Xu et al. (2026) found it mixed: on code it lifted Qwen3-32B from 5.05% to 94.09%, but in German it stayed below the aligned score, and “it is not known in advance how far to back off”. An exact method they tested, ByteSampler, reached 100% on code for about one extra pass through the model.

Bits per byte improved too. Do you approve then?

Not on that alone. Bits per byte fixes the units, but it's still measured on whole files from the start, never at a cursor. In the SuperBPE study (COLM 2025), tiny bits-per-byte differences ranked its models differently from task scores. The deciding number is completion quality at real cursor positions.

Editors also send the code after the cursor. Does that matter?

Yes. In fill-in-the-middle completion the file is cut twice at the cursor. Phan et al. (2024) note such prompts “may terminate mid-token”; their byte-level method gained 18% on fill-in-the-middle coding benchmarks and beat token healing. My reasoning: healing repairs where the prompt ends, not the cut text after the cursor.

7Check yourself

Why can't you compare loss per token across two tokenizers?

Bigger tokens carry more text each, so loss per token measures something different under each tokenizer. Bits per byte divides total surprise by the text's size in bytes, which is the same for both.

What did Xu et al. (2026) find when code prompts ended in the middle of a token?

On 5,223 code prompts built to end mid-token, Qwen3-32B's output began with the true continuation 5.05% of the time, against 88.48% when each prompt was cut back to a token boundary. Larger models were equally or more affected.

A 30-character line has 10 tokens, then 6 after free merging. At how many of its 29 inside positions can a cursor sit on a token edge, before and after?

9 before (one fewer than the tokens) and 5 after: about 31% falls to 17%, so most pause points land inside a token.

8Words to know

BPE merge
Joining the most common neighbouring pair of tokens into a new, longer token.
Bits per byte
Total surprise over a text divided by its size in bytes: a loss that ignores the tokenizer.
