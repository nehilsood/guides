Agent question 53 · extra · Day 121 · about 10 minutes

The file it never looked for

Original: AI Agent Engineering Interview #34 · The 70B Scaling Trap

1The question

“Your lead wants a 70B model in place of your coding agent's 2B. The reason: it reported success, yet verify.py still fails on the real parser.py; the trace shows it wrote and tested a new parser.py without ever listing the folder. What would you try first?” Senior AI Engineer interview, Google DeepMind

This builds on Day 120, “Agents 1: tool calling and the agent loop”. “2B” means two billion weights (guide 25). The harness is the code around the model: its prompt, its tools and how results come back. SWE-bench is a set of real GitHub bugs an agent must fix so that hidden tests pass; SWE-bench Lite is 300 of its smaller bugs (both in guide 1).

2The trap

Trap A: “Small models are a false economy. The 70B will pay for itself in fewer failed runs.”

Trap B: “Add ‘ALWAYS check that files exist’ to the prompt, in capitals.”

Trap A blames the model, Trap B hopes a louder rule fixes it. But the harness let the agent choose what got checked, and that is cheaper to change than either.

3Your 30-second answer

“I'd change the harness first, because it let the agent decide both what to change and what to check. No tool call ever brought the real parser.py into the model's view, so it wrote one from the task's description and tested its own copy. So I'd put the folder listing in the first prompt and ask it to read before editing; make the file tool refuse to create a file that already exists, as Anthropic's SWE-bench edit tool does; and have the harness, not the agent, run verify.py on the real file and check the diff.

Harness changes move scores: with GPT-4 Turbo held fixed, SWE-agent, the research coding agent in guide 4, solved 18% of SWE-bench Lite against 11% for a plain shell. Then I'd rerun the same tasks on both models and compare cost per solved task.”

4The idea in plain words

A health inspector visits a restaurant and asks to test the chicken curry. The kitchen cooks her a fresh pan: hot, clean, perfect. She passes it. The curry going out to diners comes from the pot that has sat lukewarm since lunch, and nobody tests that.

Her test was fine, and so was the cooking. What failed is who picked the sample. Real inspectors take theirs from the pot being served, without warning.

In the agent's run, the kitchen and the inspector were the same: the agent wrote a file and chose to test it. And a model sees only what its tools bring into its context. The task named parser.py, but no call read the file, so the model worked from the words. Changing what goes into that context, which tools exist and who decides what counts as done is harness engineering.

The run that happened
Task names parser.py→Writes a new parser.py→Checks its own file→“Success”
The run the harness should force
Folder listing in the prompt→Read parser.py→Edit it→Harness runs verify.py
Think about it. Trap B's capital-letter rule asks the model to remember a check on every run. A create tool that refuses an existing path makes the check happen whether the model remembers or not. Which would you trust from a small model? (our reasoning)

5How it works: four harness changes, then the model question

  1. Put the workspace in view. Start the run with a listing of the working folder. Anthropic's SWE-bench agent prompt (January 2025) opens its steps with: “As a first step, it might be a good idea to explore the repo to familiarize yourself with its structure.”
  2. Make mistakes hard. The same post's edit tool says “The create command cannot be used if the specified path already exists as a file”, so writing a fresh parser.py over the real one should fail with an error the model reads (our reading). For SWE-bench, Anthropic “spent more time optimizing our tools than the overall prompt” (Building effective agents).
  3. Give useful feedback. SWE-agent's edit tool, which guide 4 walks through, applies an edit only “if it does not produce major errors”, as judged by a linter, a checker that spots syntax errors. Otherwise “Select errors from the linter are shown to the agent”.
  4. Let the harness decide success. Our design: the harness, not the agent, runs verify.py on a clean copy of the repository plus the agent's changes, and rejects a diff that adds a new parser.py instead of editing the original.
  5. Then compare models in the same harness. Anthropic's post: performance “can vary significantly based on this scaffolding, even when using the same underlying AI model”. SWE-agent's tools took GPT-4 Turbo from 11.0% with a plain shell to 18.0% on SWE-bench Lite (Tables 1 and 3), a “64% relative increase”; six runs of the full setup ranged from 17.3% to 18.7%. Fine-tuning the 2B instead would teach this harness's habits (guide 25), while harness changes travel: SWE-agent's interface solved 10.5% of full SWE-bench with Claude 3 Opus.

An illustration, with our own numbers. Say a run costs 1 cent on the 2B and 20 cents on the 70B, and after the harness fix the 2B solves 40 of 100 tasks and the 70B 55:

Model, same harnessCost per runSolved of 100Cost per solved task
2B1¢40100¢ ÷ 40 = 2.5¢
70B20¢552,000¢ ÷ 55 ≈ 36.4¢

The 70B solves 15 more tasks at about 14.5 times the cost per solve.

Where the premise outruns the evidence. None of these sources tested a 2B model; SWE-agent used GPT-4 Turbo and Claude 3 Opus. That harness fixes rescue the 2B is plausible for this failure, but it may still fail once it reads the file. The rerun decides (our reasoning).

6Follow-ups they'll ask

Why not fine-tune the 2B on runs that start by listing files?

You could, but fine-tuning on one harness's runs also teaches that harness's habits, and such a model can collapse in another harness (guide 25). Harness changes are cheaper to try and travel between models: SWE-agent's interface, built for GPT-4 Turbo, still solved 10.5% of the full benchmark with Claude 3 Opus.

How should the harness catch a fake success like this?

Never take the agent's word. The harness runs the real verify.py itself on a clean copy plus the agent's diff, and checks that the diff edits parser.py at its original path rather than creating a new file (our design). Anthropic's SWE-bench edit tool also refuses to create a file where one already exists.

When is the bigger model the right call?

When the same tasks still fail in a good harness, and the traces show the agent reading the right code and still fixing it wrongly, not failing to look. Anthropic notes that SWE-bench scores vary a lot with the scaffolding even for one model, so compare models in the same harness, on cost per solved task.

7Check yourself

Why didn't the coding agent's own passing check catch that it never fixed the real file?

It chose what to check: its own new copy of the file. A check means something only when the harness picks it and runs it against the real file (our reasoning).

Name three harness changes that stop a coding agent writing its own copy of a file it was asked to fix.

Show the folder listing at the start and ask it to read before editing; a create tool that refuses a path that already exists; and the harness, not the agent, runs the check on the real file and inspects the diff.

Why compare a 2B and a 70B coding agent in the same harness, on cost per solved task?

Harness changes alone move scores: SWE-agent's tools took GPT-4 Turbo from 11.0% with a plain shell to 18.0% on SWE-bench Lite. Compared in one harness, a cheaper model that solves somewhat fewer tasks can still cost far less per solved task.
