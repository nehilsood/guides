The fixes that piled up

Original: AI Agent Engineering Interview #24 · The Stateless Benchmark Trap

1The question

“On your internal benchmark, your coding agent solves most issues it's handed one at a time. But once it has merged 20 tasks one after another in the same repo, the team asks you to switch it off. What did your evaluation not see, and how would you measure it?” Senior AI Engineer interview, Microsoft

A benchmark like guide 1's SWE-bench scores each issue on its own: does the project's test suite pass after the agent's change?

2The trap

Trap A: “Make the benchmark harder: tougher issues, better tests.”

Trap B: “Give it a bigger context window so it remembers the earlier tasks.”

Trap A still scores one task at a time from a fresh repo; Trap B guesses at memory without looking at the code. The problem shows only when task 21 starts from what tasks 1 to 20 left behind.

3Your 30-second answer

“Our benchmark scored each task alone, starting from a clean repo that people wrote. In real use, every task starts from the code the agent left last time. So a shortcut that passes today becomes the base for tomorrow, and a pass or fail per task can't see that.

I'd measure it as a chain: run tasks in a row on one repo with no reset, keep every earlier task's tests running, and track the repo's health after each step, such as tangled functions and copied code. Then I'd compare with the same tasks scored one at a time. In a 2026 study, running the tasks as a chain dropped Claude Sonnet 4.5 from about 66% to 44%. That gap, and the slope of the health curve, are what we missed.”

4The idea in plain words

You hire a handyman and test him on twenty jobs. Each job is in an identical, freshly built show house, and every repair works.

Then he does twenty jobs in a row in your own house. Each repair works, but each leaves some tape, a spare wire, a second bracket. By job twenty he's working around his own leftovers.

The show-house test is a stateless evaluation: every task starts from the same clean code, reset after each one. Your house is a stateful one: each task starts from what the last one left. Earlier, messier changes making later tasks harder is spillover. The leftovers themselves are technical debt: messy code that makes every later change slower and riskier.

Stateless: reset after every task
Clean repo→One task→Score↺ reset to clean
Stateful: each task builds on the last
Task 1→Task 2 on task 1's code→… task 20→Score and health at each step
Think about it. Two agents each pass 19 of 20 tasks. Agent A writes a fresh copy of a helper function every time it needs one. Agent B reuses the one already there. A per-task score calls it a tie. Now a bug turns up in that helper. How many places does someone have to fix in each repo? In A's, up to twenty. In B's, one.

5How it works: measuring a run of tasks

  1. Find the reset. The SWE-STEPS authors point out that SWE-bench-style setups reset “to a clean, human-validated codebase” before each task. So the agent never has to live with its own changes.
  2. Run tasks as a chain. Take a run of pull requests from one repo's history and let the agent do them in order, carrying the repo forward.
  3. Keep every earlier test in scope. Last task's fail-to-pass tests, from guide 15, become this task's pass-to-pass tests. SWE-STEPS does this: obligations from earlier pull requests “remain in scope for later PRs”.
  4. Measure the repo, not just the tests. A function's cyclomatic complexity counts the separate paths through it; more branches, higher number. SlopCodeBench measures erosion, how much of the code's complexity sits in a few highly complex functions, and verbosity, the share of lines that are copies or known wasteful patterns. Plot them against the task number and look at the slope.
  5. Report the gap. Score the same tasks both ways; isolated minus chained is the cost of spillover. Add a small human review, because tests don't check whether code is fit to merge.

Worked example, with real numbers. SWE-STEPS (April 2026) built 168 tasks out of 963 pull requests from 6 popular Python projects, in chains of 3 to 11. In its smaller “Mini” set, Claude Sonnet 4.5 solved 53 of 80 pull requests when the repo was reset after each one (66.25%). Run as a chain, with the code, earlier tests and conversation all carried forward, it solved 35 of 80 (43.75%). On the larger “Lite” set, Gemini 3 Flash fell from 56.52% to 36.59%. And passing wasn't everything: on one project Gemini 3.0 Pro solved all 7 pull requests, yet its technical-debt score ended “significantly higher than human reference, which maintains near-zero debt.”

In SlopCodeBench (latest version May 2026), erosion rose in 77% of runs and verbosity in 75.5%. On average, functions with a complexity of 10 or more went from 3.6 to 23.7. Neither study runs exactly 20 tasks in a row; the 20 is the question's.

6Follow-ups they'll ask

Can't we just tell it to write clean code?

It helps the start, not the trend. In SlopCodeBench, explicit quality guidance cut the starting verbosity and erosion “by up to a third, without affecting degradation rates.” The code began cleaner and got worse just as fast, so measure the slope, not one snapshot.

Isn't this just the context window filling up over 20 tasks?

Not mainly. SlopCodeBench gives the agent no record of its earlier conversation at each step, only the code (“we do not provide the prior conversation's context”), and quality still fell in most runs. The damage lives in the repo, so a bigger memory won't remove it.

If the tests pass, why would the team care?

Because reviewers pay for what tests don't check. In METR's August 2025 study, Claude 3.7 Sonnet had an average success rate of 38% on 18 open-source issues, by the maintainers' tests, but none of the 15 changes reviewed by hand could be merged as-is. Even the ones that passed needed about 26 minutes of human fixing each: missing tests, documentation, lint and style problems.

7Check yourself

What does “stateless” mean for a coding benchmark?

Every task starts from the same clean, human-written version of the repo, which is reset after each task. The agent never has to build on its own earlier changes.

Name three things to track across a long chain of tasks in one repo.

Success at each step with no reset; whether earlier tasks' tests still pass; and the repo's health, such as complexity and copied code. Then compare with the same tasks scored one at a time.

What did the SWE-STEPS study find when it ran the tasks as a chain, with no reset between them?

Scores fell. On its Mini set, Claude Sonnet 4.5 went from 66.25% of pull requests solved with a reset after each one to 43.75% without. On its Lite set, Gemini 3 Flash went from 56.52% to 36.59%.

8Words to know

Stateless / stateful evaluation
Each task starts from clean code / from what the previous task left.
Spillover
Earlier flawed or messy changes making later tasks harder.
Technical debt
Messy code that makes every later change slower and riskier.
Cyclomatic complexity
The number of separate paths through a function. More branches, higher number.
