The team built for one shape

Original: AI Agent Engineering Interview #9 · The Role-Based Multi-Agent Trap

1The question

“You built an ‘AI software team’: a product-manager agent passes work to a coding agent, which passes it to a testing agent. On ordinary GitHub issues it does better than one agent alone. Give it a task with a different shape and it collapses. Why? And when is one well-run agent the better choice?” Senior AI Engineer interview, Google DeepMind

A multi-agent system splits one job across several model instances, each with its own prompt and its own context window. What one agent passes to the next is a handoff.

2The trap

Trap A: “Specialists do their jobs better. For the odd tasks, add another specialist.”

Trap B: “Multi-agent is hype. One agent always wins.”

Trap A credits the split for what it didn't buy, and adds a handoff. Trap B can't explain why the team won.

3Your 30-second answer

“Ordinary issues have the shape the team was built for: understand, write, test. So it's a good fixed pipeline. My reading: the win comes from that order of steps more than from the split, since the roles are often the same model with different prompts.

It breaks for two reasons. The shape is fixed, so when the tester finds the plan was wrong, there's no way back to the planner. And every handoff is a summary the sender chose: the receiver can't see what was dropped or ask, so it guesses. One agent wins when the subtasks share state, like edits to one repository, or when the plan may change mid-task. A team pays off when the work splits into independent parts, like parallel research.”

4The idea in plain words

A house extension goes down a line: the architect meets the owner and draws the plan, the builder builds from the drawing, the inspector checks the work against it. For a standard back room this is fast and reliable.

Then an owner says: “My mother uses a wheelchair and is moving in. Any ground-floor room will do, as long as she can get in.” The architect draws “ground-floor bedroom”. The builder adds the usual two steps at the door. The inspector can only send work back to the builder, who followed the drawing; nobody on the line can ask the owner. The wheelchair never made it onto the drawing.

Role team: shape fixed in advance
PM agent writes a spec→Coder sees only the spec→Tester sees only the code
One agent: one context, plan can change
Plan→Edit→Test↺ a failing test can change the plan
Think about it. The tester finds that the bug isn't where the spec said: the issue was misread. In the role team, which agent can fix the spec, and does it know? In one agent, what changes?

5How it works: why the team breaks, and when it doesn't

  1. The shape is a guess made before any task arrived. MetaGPT, a well-known role team, has product manager, architect, project manager, engineer and QA engineer agents “work in a sequential manner”, passing documents along. Its engineer can rerun its own code, but the role order is fixed: nearly a pipeline with job titles.
  2. Each handoff loses detail, silently. Cognition's first rule is “Share context, and share full agent traces, not just individual messages” (a trace is the log of every step). Its second: “Actions carry implicit decisions, and conflicting decisions carry bad results.” In its example, two subagents (helpers a main agent starts) building parts of a Flappy Bird game couldn't see each other's work: one misread its piece and built a Super Mario style background, the other built a bird that didn't look like a game asset.
  3. The roles weren't the expensive part. My reasoning: a role is a prompt one agent can take too; the separate context window is the cost.
  4. One agent wins on shared state. Anthropic says domains that “require all agents to share the same context or involve many dependencies between agents” are “not a good fit for multi-agent systems today”, and that “most coding tasks involve fewer truly parallelizable tasks than research.”
  5. A team wins on independent breadth. If you split, plan per task, not per job title, and brief each subagent fully: without detailed task descriptions, Anthropic found, agents “duplicate work, leave gaps, or fail to find necessary information”. My addition: let the planner change the plan as results come back.

Worked example, with real numbers. MAGIS (2024), a team of manager, repository custodian, developer and QA engineer agents, resolved 13.94% of a 25% subset of SWE-bench issues, an eight-fold increase over “the direct application of GPT-4”. Note the baseline: GPT-4 applied directly, by my reading one call with no loop. “Beats a single agent” depends on which agent.

MAST (Cemri et al., latest version October 2025) annotated over 1,600 traces from 7 multi-agent frameworks, including MetaGPT and ChatDev: 14 failure modes in three groups, system design, misalignment between agents, and checking the work. The most common, at 15.7%, was step repetition: redoing finished steps. In its ChatDev case study, with the same GPT-4o model, clearer role rules lifted success on its ProgramDev tasks from 25.0% to 34.4%, and a final check against the overall goal reached 40.6%: 9.4 and 15.6 points from design alone.

And the other side: Anthropic's research system, a Claude Opus 4 lead with Claude Sonnet 4 subagents searching in parallel, beat single-agent Opus 4 by 90.2% on its internal research eval; multi-agent systems like it use about 15× the tokens of a chat. Research splits into independent threads; a repository rarely does.

6Follow-ups they'll ask

Anthropic's multi-agent system beat a single agent by 90.2%. Doesn't that contradict you?

No. That was research: broad searching that splits into independent threads, at about 15 times the tokens of a chat. Anthropic itself says work needing shared context or many dependencies between agents isn't a good fit, and most coding tasks have fewer parallel parts.

Can't better handoff summaries fix it?

Partly. Cognition's rule is to share “full agent traces, not just individual messages”, because actions carry hidden decisions. But even perfect notes don't give a fixed PM → coder → tester line a way back from the tester to the planner. That needs replanning.

How do you keep the tester's viewpoint with one agent?

Ask the same agent to review its own diff as a strict tester, then run the real tests. The role costs a prompt; a separate agent costs a context boundary, and the tests are the outside check either way.

7Check yourself

What are MAST's three groups of multi-agent failures?

System design issues, misalignment between agents, and task verification. The MAST study found 14 failure modes in over 1,600 traces from 7 frameworks; the most common was step repetition at 15.7%.

Why doesn't MAGIS's eight-fold gain prove that role teams beat one agent?

Its baseline was GPT-4 applied directly to SWE-bench issues, which I read as one model call with no loop or tools, not a well-run single agent.

Give two signs that a coding task should stay with one agent.

The subtasks share state, such as edits to the same files, and the plan may need to change mid-task when tests reveal something. Anthropic names many dependencies between agents as a poor fit for multi-agent systems.

8Words to know

Multi-agent system
One job split across several model instances, each with its own prompt and context window.
Handoff
What one agent passes to the next: a summary the sender chose.
Subagent
An agent started by another agent to do one piece of the work and report back.
