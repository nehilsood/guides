The step that waited for memory

Original: LLM System Design Interview #14 · The Two Faces of Inference

1The question

“One model must serve two jobs: a chatbot whose first token has to appear fast, and an overnight run of document summaries where only total output per hour matters. How does each one load the GPU, and what trade-off sits underneath?” ML Engineer interview, Google

This builds on Day 73: prefill runs the whole prompt in one parallel pass and sets time to first token (TTFT); decode writes one token per pass and sets time per output token (TPOT), limited by reading weights and cache from memory. Guide 31 covered what the cache costs in memory, and defined FLOPs and memory bandwidth.

2The trap

Trap A: “Both need a faster GPU; buy more FLOPs.”

Trap B: “Batch everything as large as possible; throughput is what GPUs are for.”

A ignores that decode leaves most FLOPs idle. B ignores that a big batch makes the chatbot's users wait behind other people's prompts.

3Your 30-second answer

“It comes down to how much arithmetic each byte of weights buys. Every pass reads all the weights from GPU memory. Prefill uses each weight for every prompt token, so a 1,000-token prompt does about a thousand operations per byte loaded and is limited by arithmetic. Decode uses each weight once per request per step, so it mostly waits on memory.

I'd treat the summaries as mostly prefill: long documents in, short summaries out. That job runs near the chip's arithmetic limit and wants steady, full batches; no single summary is in a hurry. The chatbot's first token is a prefill too, and it, along with every streaming reply, waits whenever a long document's prefill holds the GPU. So the trade-off is throughput against latency. Chunked prefill, or separate GPUs for prefill and decode, eases it.”

4The idea in plain words

A translator's dictionary is so big it lives in the basement, and every pass she must carry all of it upstairs and back. Bring her a 1,000-word document and she looks up every word on one trip: the stairs are a small part of the job, and her reading speed sets the pace. Give her one word per trip and she spends nearly all her time on the stairs.

The basement is GPU memory, the stairs are memory bandwidth, the dictionary is the weights, and her reading speed is the chip's arithmetic. Prefill is the whole document. Decode is one word per trip, unless several clients' words share it: batching.

The useful number is arithmetic intensity: operations done per byte brought from memory (the roofline report by Williams, Waterman and Patterson calls it operational intensity). Its rule: speed is the lower of peak arithmetic and bandwidth times intensity. Below the “ridge point” where the two meet, you are memory-bound; above it, compute-bound.

Think about it. An fp16 weight is 2 bytes. In a matrix multiply each weight does one multiply and one add per token. How many operations per byte for a batch of n tokens? About n × 2 ÷ 2 = n. Decode with one request is about 1; a 1,000-token prefill about 1,000 (our arithmetic, ignoring the activations' own traffic).

5How it works: two phases, two limits

  1. Find the ridge, on paper. NVIDIA's A100 datasheet lists 312 TFLOPS (trillion operations a second) of 16-bit tensor-core arithmetic, without sparsity, and 2,039 GB/s of memory bandwidth for the 80 GB server-board (SXM) card. 312 ÷ 2.039 ≈ 153 operations per byte (our arithmetic).
  2. Prefill sits above it. A long prompt has intensity in the hundreds or thousands. Splitwise (Patel et al.) measured TTFT growing “almost linearly” with prompt length, “due to the prompt phase having high GPU utilization and being computationally bound”.
  3. Decode sits far below it. Sarathi-Serve (Agrawal et al.) found for Mistral-7B on one A100 that “the cost of linear operation for 1 decode token is nearly same as 128 prefill tokens”.
  4. Batching decode is cheap at first, until memory runs out. In Splitwise's tests of BLOOM-176B and Llama-70B on DGX-H100 machines (NVIDIA servers of eight H100 GPUs), decode throughput rose with batch size until memory ran out at a batch of 64, while time between tokens only doubled. The batch shares the weight reads, but each request's KV cache is its own and is read every step (guide 31).
  5. Long prefills stall everyone. While a new prompt's prefill runs, other users' decode steps wait. Sarathi-Serve calls these “generation stalls”: vLLM, an open-source serving engine, schedules “as many prefills as possible before resuming ongoing decodes” and showed one lasting “over several seconds” (Yi-34B on two A100s); Orca, which mixes both in one batch, still stalls because batches holding long prompts stay slow.

An illustration, with our own numbers. Llama 2 7B (Day 73: about 13.5 GB of fp16 weights, so about 6.75 billion weights and 13.5 billion operations per token) on that A100 at peak speeds. Weights only: each request's cache read adds to the memory time.

The two times match at about 153 tokens per pass, the ridge again, on paper. Sarathi-Serve's footnote expects compute-bound “at ∼200 tokens on A100 GPUs” in theory, but observed “∼500-600 tokens for higher tensor parallel dimensions” (a model split across GPUs).

Applied to the question (our reasoning). Splitwise lists summarisation as a batch task where “TTFT or TBT latency metrics are less important than throughput” (TBT: time between tokens, Day 73's TPOT). Long prompts and short outputs make it mostly prefill, already compute-bound. Sarathi-Serve slots prompt chunks into decode batches so new requests join “without pausing ongoing decodes”, with up to 2.6× more serving capacity than vLLM for Mistral-7B under tail-latency targets (limits on the slowest responses). Splitwise and DistServe put prefill and decode on separate GPUs.

6Follow-ups they'll ask

Would a GPU with more FLOPs help the chatbot or the batch job?

Mostly prefill: the chatbot's time to first token and the long summaries, both compute-bound. Decode waits on memory, so more bandwidth helps it more. Splitwise argues decode “does not need the compute capability of the latest GPUs”.

Why not batch decode to 1,000 requests and ignore latency?

Memory stops you first: every request keeps its own KV cache, so memory caps the batch. In Splitwise's tests of 176B and 70B models on H100 machines it ran out at 64, and time between tokens had already doubled, since each request's cache is read every step. On weights alone, a batch of n requests does about n operations per byte, so past about 153 requests (an A100's ridge, on paper) arithmetic becomes the limit too.

How does chunked prefill help the chatbot?

Sarathi-Serve splits a long prompt into near-equal chunks and adds one or more chunks to each decode batch, using arithmetic that decode leaves idle. Other users' next tokens no longer pause behind a whole prompt; the chunked prompt's own first token arrives a little later.

7Check yourself

What is arithmetic intensity, and roughly what is it for a decode step with one request?

Operations done per byte read from memory. An fp16 weight is 2 bytes and does 2 operations per token, so one request's decode step is about 1 operation per byte, far below the roughly 153 at which an A100's arithmetic becomes the limit on paper.

Why does a long prefill hurt other users' streaming?

While a long prompt's prefill runs, other users' decode steps wait for it, whether the server runs it before their steps or in the same batch. Sarathi-Serve measured such generation stalls in vLLM lasting over several seconds.

In Splitwise's tests, what happened as the decode batch grew to 64?

For BLOOM-176B and Llama-70B on DGX-H100 machines, decode throughput kept rising until memory ran out at a batch of 64, while time between tokens only doubled.
