The call with no answer

Original: AI Agent Engineering Interview #5 · The History Corruption Trap

1The question

“Your agent runs for hours and crashes halfway through. You reload its saved conversation to carry on, and the API refuses all of it, yet every message looks fine. Which rule did you break, and how do you make sure a crash can never leave you here again?” Senior AI Engineer interview, Anthropic

An invariant is a rule that must be true at every moment, the way a bank's books must always balance. The interviewer wants you to name the one the crash broke.

2The trap

Trap A: “The saved file got damaged. Throw it away and start the task again.”

Trap B: “Retry the request until it goes through.”

Nothing is damaged. The history is incomplete. Retrying sends the same gap again. Starting over throws away hours of work, and may repeat actions that already happened, like sending an email twice.

3Your 30-second answer

“The rule is: every tool call in the history must be answered by its result, with the same id, in the very next message. My agent saved the model's tool call, then crashed before it saved the result. So the history ends with a call that has no answer. Each message is valid on its own; it's the pair that's broken.

To make it impossible, I save a turn as one unit: the model's call message and all its results in a single database transaction, so a crash leaves both or neither. Tools with side effects get the call id as an idempotency key, so running them again can't do the work twice. And on resume I check the history first: any call without a result gets re-run if that's safe, or gets an error result saying it was interrupted, so the model can decide what to do.”

4The idea in plain words

Think of a busy restaurant's order book. The waiter writes “Ticket 12: one soup.” The kitchen's rule is strict: the next line in the book must be “Ticket 12: soup served.” Nothing else may go in between.

One night the power cuts out right after the waiter writes the order and before the kitchen writes its reply. The next morning the new manager opens the book, finds ticket 12 with no reply, and refuses to carry on. Was the soup made? Was it served? Was it paid for? The book can't say.

An agent's saved history works the same way. In guide 1's loop, each round adds two messages: the model's tool call (with an id, the ticket number) and then the tool result (carrying the same id). The API checks that every call is followed straight away by its result. A crash between the two leaves an unanswered ticket.

What was saved before the crash
User: the task→Model: call tool, id 12→(crash: no result)
What the resume code sends
…call id 12→User: “please continue”→Rejected

The fix is the restaurant writing the order and the reply on the same line, at the same moment. Databases call this a transaction: several changes saved as one, all or nothing.

Think about it. The tool actually ran before the crash, but its result was never saved. On resume, should you just run it again? If it only read a file, yes, no harm done. If it sent an email or charged a card, running it again does it twice. That's why the fix needs a second half: tools that are safe to repeat.

5How it works: closing the gap

  1. Know the rule exactly. In Anthropic's API, results must come straight after the message with the calls, and they must come first in that message. When the model calls several tools at once, all the results go back together in one message. OpenAI's API matches each result to its call by a call_id in the same way.
  2. Save a turn as one unit. Write the model's call message and all its results in one database transaction. SQLite's docs define this as atomic commit: either all the changes in a transaction happen or none do, even if the machine crashes or loses power.
  3. Make side effects safe to repeat. Pass the call id to the tool as an idempotency key. Stripe's API works this way: it saves the response to the first request with a given key and returns that saved response on retries, so a repeat can't do the same operation twice.
  4. Check the history before sending. On load, pair every call with its result. Re-run a missing one if it's safe; otherwise add a result marked as an error, saying the tool was interrupted and may or may not have run.
  5. Test the crash. In a test, kill the agent at every step boundary and check that resuming always produces a history the API accepts.

Worked example, built from Anthropic's docs example. The user asks for the weather in San Francisco. The model replies with a tool_use block for get_weather, id toolu_01A09q90qw90lq917835lq9, and the response's stop_reason is tool_use. Now this guide's own illustration: the agent saves that message and crashes. On restart it appends a plain user message, “please continue”, so the call is no longer followed by its result. When tool results aren't formatted correctly, the docs say you may see an error such as “tool_use ids were found without tool_result blocks immediately after”. The repair is one message with a tool_result carrying the same id. Since get_weather only reads, re-run it and send “15 degrees”. If it were risky, send “Interrupted before the result was saved” with is_error: true, and the model takes it from there.

6Follow-ups they'll ask

Why not just delete the unanswered call?

Dropping the whole unfinished turn gives a valid history, but the model forgets it may already have acted, and might act again. Keeping the call with an error result tells it the truth.

What if the model called three tools and the crash came after two finished?

All three results must go back together. Save the turn only once every result is in, or fill the missing one with an error result.

7Check yourself

State the rule the crash broke, in one sentence.

Every tool call must be followed, in the very next message, by a result with the same id.

Why does every message look fine while the API rejects the history?

The problem isn't in any one message. It's a missing partner: a call whose result was never saved.

Name the two halves of the fix.

Save each turn (call plus results) as one all-or-nothing unit, and make tools safe to repeat with an idempotency key. Then check the history on resume and repair any gap.

8Words to know

Invariant
A rule that must hold at every moment, not just most of the time.
Tool call id
The ticket number that links a tool call to its result.
Transaction (atomic commit)
Several changes saved as one: all of them happen, or none do.
Idempotency key
A unique key sent with a request so that repeating it returns the first result instead of doing the work again.
