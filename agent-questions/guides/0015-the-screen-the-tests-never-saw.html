The screen the tests never saw

Original: AI Agent Engineering Interview #23 · The Front-End Verification Trap

1The question

“Your coding agent fixes a bug in a web page. All the unit tests go green, yet anyone who opens the page can see it's still broken. How should the agent check its own work, and does that check need a model that can see images?” AI Engineer interview, Google

A unit test checks one small piece of code on its own. A model that can see takes images as input as well as text; people call it multimodal.

2The trap

Trap A: “Hand it a vision model and have it look at a screenshot.”

Trap B: “Write more unit tests.”

Neither asks why the tests passed. More unit tests are blind in the same place, and a vision model puts an opinion where a yes-or-no script would often do.

3Your 30-second answer

“Most likely the unit tests ran in a stand-in for the browser that never lays out or draws the page. Then they proved the button exists, not that a person can see or press it.

I'd make the agent check where the user is: in a real browser. First it writes a browser test that fails on the current code, for the reason in the bug report. Then it fixes the code until that test passes, and the old tests still pass. That's fail-to-pass: a test that fails before the fix and passes after, the way SWE-bench scores a fix.

For most bugs a text-only model reading the page's structure is enough. For bugs you can only see, I'd compare screenshots with a known-good one first, and bring in a vision model only where no reference exists.”

4The idea in plain words

A tailor checks a finished suit against the order form: navy wool, three buttons, two pockets. Every line ticks.

The customer puts it on, and the sleeves cover his hands. The form never had a line for “fits a real person”.

A good tailor fits twice: before the alteration and after.

A web page starts as the DOM, the tree of elements (buttons, text, boxes) it's built from. Front-end unit tests often run in jsdom, a copy of the DOM written in JavaScript that never works out where anything sits on screen. That's the order form. A real browser, driven by a script, is the fitting. A test that fails before the fix and passes after it is fail-to-pass.

Unit test in jsdom: reads the tree
Build the DOM→Is the button there?→Yes: pass
Real browser: builds the screen
Build, lay out, draw→Click where a person would→Covered: fail
Think about it. A Submit button sits under a cookie banner. Your unit test finds the button by its label and fires a click at it. Does it pass in jsdom? Yes: by our reasoning, nothing has a position there, so nothing can be on top. The test asked “is it there?” The user asks “can I press it?”

5How it works: checking a front-end fix

  1. Name what the old tests could see. jsdom's README lists layout, “the ability to calculate where elements will be visually laid out as a result of CSS”, as not implemented, and says it returns “zeros for many layout-related properties”. So overlap and clipping bugs can't show up there.
  2. Reproduce in a real browser first. The agent writes a test with a browser tool such as Playwright and checks it fails on the unchanged code, for the reported reason. Only then does it edit.
  3. Fix until it passes, and keep the old tests green. This is how SWE-bench, from guide 1, scores a fix: fail-to-pass tests must now pass, and pass-to-pass tests “are included to ensure that the revision does not break or violate any existing expected behavior.”
  4. Make the test act like a user. Playwright counts an element as visible when it “has non-empty bounding box and does not have visibility:hidden computed style”: it has a size on screen, and its own style doesn't hide it. A covered button meets that. A real click also checks that the element “is the hit target of the pointer event at the action point”, the thing on top where the click lands. A covered button fails.
  5. Bring in pixels only for bugs you can only see. For behaviour, a text-only model can read the accessibility tree, the browser's own list of each control's role, name and state. Microsoft's Playwright MCP, a browser tool for agents, does: “No vision models needed”. For looks, Playwright's screenshot test stores a reference on the first run and compares later runs against it. A vision model comes last, for bugs with no known-good picture.

Worked example, with real numbers. SWE-bench Multimodal (Yang et al., October 2024) collected 617 tasks from 17 JavaScript libraries, each with an image in the bug report or tests. Of the 557 whose bug report had an image, annotators judged it necessary for 465 (83.5%). So the bug often needs seeing; the check mostly doesn't: tasks are scored with fail-to-pass tests, and only 69 compare rendered screenshots “pixel-by-pixel”. The best system then, SWE-agent, solved 12%.

6Follow-ups they'll ask

The agent wrote the test itself. Couldn't it write one that always passes?

That's why the test must fail first, on the unchanged code, for the reported reason. A test that passes before and after measured nothing, which is why SWE-bench only keeps tasks with at least one test that goes from fail to pass. Undoing the fix and seeing the test fail again is a cheap extra proof.

So when is a model that can see worth it?

Our view: for bugs that live only in the pixels with no known-good screenshot to compare against, such as a page that doesn't match its design, or to read a screenshot in the bug report. The model writing the code can stay text-only; the seeing one is a checker at the end.

Does giving the model the image always help?

Not reliably. SWE-bench Multimodal tried its one-shot baseline (no agent loop) at three context sizes on its development set. Adding the bug report's images raised Claude 3.5 Sonnet from 7.6% to 13.7% solved with a 100K-token context, but lowered it from 9.4% to 7.8% with 32K. Measure it on your own tasks.

7Check yourself

Why can a jsdom unit test pass while a cookie banner covers the button?

jsdom builds the page's tree but doesn't do layout, returning zeros for many position and size values. So it can't know what sits on top; it only checks the button exists.

What do fail-to-pass and pass-to-pass tests each prove?

Fail-to-pass: the test can see the bug, and the fix removed it. Pass-to-pass: the fix didn't break what already worked. SWE-bench counts a fix only when both sets pass.

In Playwright, which catches a covered button: the visible check or a real click?

The click. Visible only means a non-empty box and no visibility:hidden, which a covered button has. A click first checks the button is the element on top where the click lands, so it fails.

8Words to know

jsdom
A copy of the browser's DOM in JavaScript, used for fast tests. No layout, no drawing.
Fail-to-pass / pass-to-pass
Tests that fail before the fix and pass after / passed before and must still pass.
Accessibility tree
The browser's text summary of the page: each control's role, name and state.
