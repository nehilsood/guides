The zero that still changed its mind

Original: Advanced NLP Interview #7 · The Temperature 0 Trap

1The question

“Set the temperature to zero, says a teammate, when the agent picks different tools on repeated runs of one input. What does that leave unsolved?” Senior AI Engineer interview, Google

This builds on Day 71: temperature divides the logits before the softmax, and near zero it becomes greedy, always the top token. Guide 39 showed that greedy's pick at each step isn't the best whole sequence.

2The trap

Trap A: “Temperature 0 is greedy, greedy is deterministic, done.”

Trap B: “GPUs are random; nothing can be done.”

A misses two things: servers don't compute the same numbers every time, and a consistent answer can be consistently wrong. B gives up on a cause that has been found and fixed.

3Your 30-second answer

“Two halves. First, temperature 0 makes the choice deterministic only if the logits are identical every run, and on a shared server they aren't. Thinking Machines sampled one prompt 1,000 times at temperature 0 and got 80 different completions. Their analysis: a request's numbers depend on how many other requests run alongside it, because that changes the order in which the GPU adds numbers up, and floating-point addition rounds differently in different orders. I'd expect a near-tie between two tokens to flip. GPU routines that add in a fixed order, however many requests share the run, made all 1,000 identical, at some cost in speed.

Second, determinism isn't correctness. Greedy picks the top token, so a wrong tool call the model slightly prefers now happens every time. I'd also validate calls and test the agent's behaviour.”

4The idea in plain words

Volunteers count an election by hand. To keep the arithmetic easy, each volunteer rounds their pile's total to the nearest ten before it's added in. How the ballots are split into piles depends on how many volunteers turned up that night. Most nights that changes nothing. In a near-tie, it decides who wins.

A GPU adds long lists of numbers the same way: in chunks, rounding at every step, because a floating-point number keeps only so many digits. The chunking a GPU routine (a kernel) picks can depend on how many requests run together in one batch, and the batch depends on how busy the server is. So the same prompt can get slightly different logits from one minute to the next.

Usually the top token still wins by a mile. But when two tokens are nearly tied, say search_orders and search_invoices as the next tool name (our example), a difference in the fifth decimal place can pick the other one. That is our reasoning: the top choice changes only if two logits sit within the rounding error. Everything after it then differs.

Think about it. The rounding is unavoidable; what fixes the count? Always split the ballots into the same piles, however many volunteers come. That is the idea Thinking Machines calls batch invariance: each kernel adds in the same order whatever the batch size. The price is a slower count on busy nights.

5How it works: the two halves

  1. Order changes the sum. “Defeating Nondeterminism in LLM Inference” (Horace He with others at Thinking Machines, Sept 2025) starts here: (0.1 + 1e20) − 1e20 gives 0, while 0.1 + (1e20 − 1e20) gives 0.1.
  2. The usual story is incomplete. The common explanation is parallel threads finishing in random order. The post says this “is not entirely wrong” but misses the picture: “running the same matrix multiplication on the same data repeatedly will always provide bitwise equal results” (identical to the last bit), and an LLM's forward pass is “run-to-run deterministic”.
  3. The batch is the hidden input. Their finding: “the primary reason nearly all LLM inference endpoints are nondeterministic is that the load (and thus batch-size) nondeterministically varies”. Three operations add across many numbers and need fixing: RMSNorm (a layer norm variant), matrix multiplication and attention.
  4. Fixing it is possible and costs speed. With their batch-invariant kernels, 1,000 runs gave one completion. Serving 1,000 short replies (90 to 110 tokens) from Qwen3-8B on one GPU took 26 s with the defaults of vLLM, an open-source serving engine, 55 s with their unoptimised deterministic version, 42 s with a better attention kernel. PyTorch's reproducibility notes (2.15) agree on the trade: “Deterministic operations are often slower”, and results aren't guaranteed to match across releases or platforms.
  5. The other half: consistent isn't right. Temperature 0 turns the model's preference into a fixed habit. If it slightly prefers the wrong tool for an input, it now picks it every time (guide 39's model error: the model's top choice can be the wrong one). So check tool calls against their schema and the task, test behaviour over varied inputs, and confirm “identical inputs” really are, down to timestamps in the prompt (our advice).

Worked example, with the post's numbers. Qwen3-235B-A22B-Instruct-2507, prompt “Tell me about Richard Feynman”, 1,000 completions of 1,000 tokens at temperature 0:

An illustration, with our own numbers. We added the same 4,096 float32 products (one logit's dot product) two ways in numpy: left to right gave −18.137648, sixteen partial sums gave −18.137726, a gap of about 0.00008. Two tool names whose logits sit closer than that can swap places.

Where the premise outruns the evidence. The post's experiments ran on its own setup. It argues the batch effect holds for nearly all endpoints, but a hosted API's internals aren't public, so other causes can't be ruled out there (our caution). And the question's “identical inputs” is worth checking first.

6Follow-ups they'll ask

If the forward pass is deterministic, why does the server look random to me?

The Thinking Machines post explains that the server is deterministic given all its requests, but other users' requests aren't your input: they set the batch size, which changes how the kernels add up your numbers, so your logits can differ run to run.

Should every agent run on batch-invariant kernels?

Only where bit-identical output is worth the cost: replaying a bug or research comparisons, say (our advice). In the Thinking Machines test, 1,000 short replies from Qwen3-8B took 42 s with their still unoptimised batch-invariant kernels against 26 s by default.

How would you make the tool choice reliable rather than just repeatable?

Check each call against the tool's schema and the user's request before running it, log the full input of every run, and measure how often the agent picks the right tool across varied inputs. A deterministic wrong answer is still wrong.

7Check yourself

Why can greedy decoding give different outputs for the same prompt on a busy server?

The batch size changes how the GPU kernels split their sums, and floating-point addition rounds differently in different orders. The logits shift slightly, enough to flip a near-tie between two tokens.

What is batch invariance?

A kernel property: it adds numbers in the same order whatever the batch size, so one request's result doesn't depend on what else runs with it. Thinking Machines needed it for RMSNorm, matrix multiplication and attention.

Why is temperature 0 only half a fix even on a perfectly deterministic server?

It makes the choice repeatable, not correct: if the model slightly prefers the wrong tool, greedy decoding picks that wrong tool every time.
