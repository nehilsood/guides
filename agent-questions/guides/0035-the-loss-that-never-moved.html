The loss that never moved

Original: Machine Learning System Design Interview #13 · The Flat Loss Trap

1The question

“You've coded up a Transformer from a fresh paper. Nothing crashes and the training loop turns over, but the loss is a flat line. What do you do first?” Senior ML interview, OpenAI

This builds on Day 43's lesson: gradients multiply layer by layer, so bad starting weights make them vanish or explode; dropout and batch norm behave differently in training and prediction; and a training loss flat from the start points to vanishing gradients or dead ReLU units. Today: telling those apart from a plain bug, fast. Guide 24 explains the loss itself.

2The trap

Trap A: “Lower the learning rate, and if that fails, try another optimizer.”

Trap B: “Give it longer. Big models start slowly.”

Both assume the code is right. A flat line can be a bug that stops learning altogether, and no setting fixes code that can't learn.

3Your 30-second answer

“Before touching any setting, I prove the code can learn at all. First, the loss at step zero: with a 32,000-token vocabulary and a near-uniform start it should be about ln 32,000, roughly 10.4. Far off means the loss or output layer is wrong.

Then I take one small batch, switch off dropout, and train on it alone. A working model drives that loss towards zero; Karpathy's recipe says that if it can't, there's a bug and you don't move on. If it fails, I check that every layer gets a nonzero gradient and that the optimizer really steps. Only once it can memorise one batch do I tune the learning rate. Tuning a model that can't learn just moves a flat line around.”

4The idea in plain words

You build an espresso machine from a kit. It powers on, the pump hums, and nothing comes out. You could try a finer grind, other beans, a hotter setting. Or you run plain water through it, no coffee at all.

Water is the easiest job the machine has. If water won't flow, it's the plumbing, and no bean will fix it. If it flows, now you tune the coffee.

Training on one tiny batch until the model memorises it is running water through. Overfitting (Day 14) is normally the enemy; here it is the test. A model with millions of weights should memorise a few examples easily. Goodfellow, Bengio and Courville put it this way: if you can't train a classifier to label a single example correctly, “there is a software defect preventing successful optimization on the training set.”

Prove it can learn, then tune
Loss at step 0→Overfit one tiny batch→Gradient in every layer?→Then tune
Think about it. The flat line sits at 10.37 with a 32,000-token vocabulary. What is the model predicting? ln 32,000 ≈ 10.37 is the loss of an even guess over every token (our arithmetic). It hasn't learned even which tokens are common, so nothing is learning at all.

5How it works: four steps, in order

  1. Check the loss at step 0. Karpathy's recipe (2019): “Verify that your loss starts at the correct loss value”, for example −log(1/n_classes) on a softmax, the layer that turns scores into probabilities (Day 36). For a language model the classes are the tokens, so that's ln of the vocabulary size.
  2. Overfit one batch. The recipe: train on “a single batch of only a few examples (e.g. as little as two)”, growing the model if needed, until the loss reaches its lowest possible value. If it doesn't, “there is a bug somewhere and we cannot continue to the next stage.” The recipe also turns off data augmentation (random changes to training examples, such as flips or crops) at this stage; we'd switch off dropout too, so a failure can't be noise. In PyTorch Lightning 2.6.6, Trainer(overfit_batches=10) trains on 10 fixed batches and also turns off shuffling.
  3. If it fails, follow the gradient. Log each layer's gradient size; a layer stuck at exactly zero never hears from the loss. Common culprits (our list): optimizer.step() never called, a learning-rate schedule that starts at 0, a .detach() that cuts the chain, labels not shifted by one token, an attention mask (later in the plan) that hides every token. Then Day 43's suspects: dead ReLUs, vanishing gradients from badly scaled starting weights. If you wrote a gradient by hand, the book's chapter 11 suggests comparing it with a numerical estimate.
  4. Only now tune. Learning rate first (Day 42), then the rest.

An illustration, with our own numbers. Same Transformer, vocabulary 32,000, three outcomes of the one-batch test:

One-batch resultWhat it saysNext move
Starts at 10.4, still 10.4 after 500 stepsNothing learns: a bugGradients per layer; is the step taken?
Starts at 10.4, falls to 0.02The code can learnBack to the full run: learning rate, data
Starts at 45Loss or output layer wrongFix the step-0 value first

Where the premise outruns the evidence. Passing the test proves the model can learn something, not the right thing. Karpathy's example of a silent bug (our link to the one-batch test): an off-by-one bug lets an autoregressive model (one that predicts each next token from the ones before) see the token it should predict; the loss would then fall too well (our inference). His warning about misconfigured networks is that “Most of the time it will train but silently work a bit worse.”

6Follow-ups they'll ask

It memorises one batch, but the full run is still flat. Now what?

The code can learn, so check the usual causes: the learning rate (try 0.1, 0.01, 0.001), starting weights, and the data. Karpathy's recipe says to look at exactly what enters the network, “immediately before your y_hat = model(x)”.

Can passing the one-batch test still hide a bug?

Yes: it only shows the model can learn something. Karpathy's example of a silent bug (our link to the one-batch test) is an off-by-one bug that lets an autoregressive model, which predicts each next token from earlier ones, see the token it should predict, so (our inference) the loss falls too well. Check the inputs and labels too.

Why switch off dropout for the test?

Dropout randomly zeroes units on every training pass, which fights memorising. Karpathy's recipe turns off data augmentation (random changes to training examples, such as flips or crops) at this stage for the same kind of reason; dropout is our addition. A failure then points at the code, not at noise.

7Check yourself

A language model has a 32,000-token vocabulary. What should its loss be at step zero?

About ln 32,000 ≈ 10.4, the loss of an even guess over every token. That is Karpathy's −log(1/n_classes) check.

Why overfit a single small batch before tuning anything?

A working model can memorise a few examples. If it can't drive that loss near zero, the code has a bug, and no learning rate or optimizer will fix it.

One layer's gradient is exactly zero at every step. What does that tell you?

The loss never reaches that layer, so its weights never change: something cuts the chain (a detach, an unused output) or its ReLU units are dead.
