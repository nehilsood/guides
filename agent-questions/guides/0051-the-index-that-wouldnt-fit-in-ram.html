The index that wouldn't fit in RAM

Original: RAG Interview Questions #8 · The IVF-PQ Compression Trick

1The question

“Finance wants the RAM bill for your vector index cut. It holds 200 million embeddings in HNSW, picked because it found 99% of the true nearest neighbours in the demo. What do you propose, and what do you give up?” Staff ML Engineer interview, Google

This builds on Day 108, “RAG 1: chunking, embeddings, vector search”. HNSW is a graph index: each vector links to a few dozen near neighbours, and a search hops along links towards the query. Recall here is the share of the true nearest neighbours a search finds, compared with checking every vector.

2The trap

Trap A: “HNSW won the benchmark. Buy more memory.”

Trap B: “Compress everything as hard as possible; recall barely moves.”

Both skip the sum: where do the bytes go, and how much recall does each byte buy?

3Your 30-second answer

“Moving off plain HNSW, which keeps every vector at full precision in RAM: 200 million vectors of 768 four-byte numbers is 614 GB, about 666 GB with 32 links each. The authors of Faiss, Meta's open vector-search library, say graph indexes suit cases with no memory limit, typically under 1M vectors; once vectors need compressing just to fit, their decision guide sends you to IVF.

I'd propose IVF-PQ. IVF groups the vectors into clusters and searches only the few nearest the query; PQ shrinks each vector to a 64-byte code. That's about 14 GB, ids included. What I give up is exactness: code distances are approximate, so I'd re-score the top few hundred against full vectors kept on disk, and tune clusters searched and code size on held-out queries, ones kept aside for testing (guide 24), until recall against exact search meets my target.”

4The idea in plain words

A police identikit doesn't keep a photo of every face. It has, say, 256 noses, 256 pairs of eyes and 256 mouths. A face is filed as “nose 17, eyes 203, mouth 88”. To match a witness, you work out once how close each of the 256 noses is to the one described, then score any filed face by adding up three looked-up numbers.

The files are kept by district, so you search only the districts nearest where the person was seen. Then you pull the real photos of the best 50 matches and look properly.

Filing faces as part numbers is product quantization (PQ): cut each vector into pieces and replace each piece with the number of its nearest stand-in from a small learned set. Searching by district is an inverted file (IVF): k-means clustering, which groups points around a set of centres, sorts the vectors into lists, one per centre, and a query opens only the closest few lists. Checking the photos is re-ranking.

One query
Find the nearest few lists→Score their 64-byte codes→Re-score the top few hundred with full vectors→Best chunks to the model
Think about it. Cut a 768-number vector into 64 pieces of 12 numbers, and store each piece as one byte. How big was a piece before? 12 numbers × 4 bytes = 48 bytes. Every piece shrinks 48 times, so the vector goes from 3,072 bytes to 64 (our arithmetic).

5How it works: price it, cluster, compress, re-rank, measure

  1. Do the sum. The Faiss guidelines give HNSW's memory as (d × 4 + M × 2 × 4) bytes per vector, where d is the vector length and M the links per vector, and say “all Faiss indexes are stored in RAM”. The index table gives IVF-PQ as the code size plus 8 bytes, “the vector id”. The links aren't the problem: the HNSW paper puts them at “about 60-450 bytes per object”. The full-precision vectors are.
  2. Cluster. For 100M to 1B vectors the guidelines suggest 1,048,576 lists, using a small HNSW to find the nearest list centres. Those centres stay full size: about 3.2 GB (our arithmetic). New vectors join their nearest list without retraining; retrain the centres if the data drifts (our reasoning). The Faiss paper notes its HNSW index doesn't support deleting or changing vectors.
  3. Compress. Jégou, Douze and Schmid split each vector into low-dimensional pieces and quantize each separately; distances “can be efficiently estimated from their codes”, and comparing the uncompressed query with the codes “increases precision”.
  4. Re-rank. Jégou et al. measure recall@R, the share of queries whose true nearest neighbour lands in the top R, which shows how often it is found “if a short-list of R vectors is verified using Euclidean distances”. Keep the full vectors on disk; each query reads only its short list.
  5. Measure. Run held-out queries through exact search once for the right answers, then sweep lists searched and code size. The Faiss paper: “To refine the index parameters, benchmarking should be used.”

Worked example, with real numbers. Jégou et al.'s Table V searches 1,000,991 GIST image vectors (960 numbers each) with tiny 8-byte codes. Comparing the query with every code took 17.2 ms and put the true nearest neighbour in the top 100 for 65.2% of queries. IVF with 1,024 lists, opening 8, compared only 27,818 codes in 8.8 ms and reached 68.2%: faster and no worse. Opening 1 list: 1.5 ms but 30.8%. The paper doesn't give the hardware beside the table, so read the times against each other, not as absolutes.

Where the premise outruns the evidence. Our reasoning: 99% in a demo says little about 200 million vectors, and recall against exact search isn't answer quality. What matters is whether the answering chunk reaches the model; measure that too.

6Follow-ups they'll ask

Why not keep HNSW but store compressed vectors in it?

Faiss offers that; benchmark it. But the links stay: 32 per vector is 256 bytes, 51.2 GB for 200 million (our arithmetic), four times the 64-byte codes. And the Faiss paper notes that beyond 10M vectors a graph's construction time “typically becomes the limiting factor”.

How do you pick the number of lists to search?

It's set at query time, so sweep it on held-out queries. In Jégou et al.'s test on a million image vectors with 8-byte codes, opening 8 of 1,024 lists instead of 1 lifted the share of queries with the true neighbour in the top 100 from 30.8% to 68.2%, and time from 1.5 to 8.8 ms, as the paper reports it (hardware not stated).

New documents arrive every day. Does that change the choice?

New codes can be added to their nearest IVF list without retraining; if the new data drifts from what the centres were trained on, retrain them (our reasoning). The Faiss paper notes that its HNSW index “does not support suppression and mutation”, so deleting or editing vectors there means rebuilding.

7Check yourself

How much RAM do 200 million 768-number float vectors need in plain HNSW, and in IVF-PQ with 64-byte codes?

3,072 bytes each is 614.4 GB; with 32 HNSW links (256 bytes more) about 665.6 GB. IVF-PQ stores 64 bytes plus an 8-byte id, 72 bytes, so 14.4 GB plus the list centres.

What do the IVF and PQ halves of IVF-PQ each do?

IVF sorts the vectors into lists around k-means centres, and a query opens only the few lists nearest it. PQ cuts each vector into pieces and stores each piece as the number of its nearest stand-in from a small learned set, usually one byte.

Why re-score IVF-PQ results with the full vectors?

Distances from the codes are estimates, so the true nearest neighbour can rank below near misses. Re-scoring a short list of a few hundred with exact distances fixes the order, and only those few full vectors need to be read from disk.
