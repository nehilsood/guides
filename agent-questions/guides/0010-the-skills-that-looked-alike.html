The skills that looked alike

Original: AI Agent Engineering Interview #2 · The Skill Overload Trap

1The question

“To make your coding agent smarter, you gave it 40 well-written skills, and its success rate fell. Each description is just a few lines, so the context window isn't the issue. What's really going wrong, and how would you prove it?” Senior AI Engineer interview, Anthropic

You met skills in guide 9: the agent always sees each skill's name and description, and opens the full SKILL.md only when it decides the skill applies.

2The trap

Trap A: “Too many tokens in the prompt. Shorten the descriptions.”

Trap B: “Delete skills until the score comes back.”

Trap A answers the question they ruled out, and shorter descriptions leave fewer words to tell neighbours apart. Trap B might delete the useful skills along with the harmful ones. Both skip the “prove it” half.

3Your 30-second answer

“Storing forty skills is cheap. Choosing among them isn't. On every turn the agent picks one of forty, or none, from short descriptions. Skills that sound alike make wrong picks likelier, and a wrong pick loads instructions the agent then follows. To prove it, I'd run the same tasks with 0, 10, 20 and 40 skills, add a version padded with filler of the same length, and grade the picks alone against an answer key. The fix: show only a few relevant skills at a time.”

4The idea in plain words

A café has 40 dishes on one page. Reading the menu takes a minute, so its length isn't the problem. The problem is that six of the dishes are nearly the same pasta, with slightly different names. You point at one, it's the wrong one, and now that's your lunch. You don't get to swap halfway through.

Choosing gets harder. Each new skill isn't just one more option. It's one more thing to mix up with every skill that sounds like it. Call these look-alike skills: descriptions close enough that the agent can't reliably tell them apart.

A wrong pick keeps steering. Opening a skill puts its instructions into the agent's context, written as orders: “always run the linter first”. The agent tends to follow them. Even with hand-written skills, SkillsBench saw skills lower the score on 13 of its 87 tasks, in some cases because a generic recipe pushed aside a better approach. Pick the wrong skill and that pull is worse. Call it instruction hijacking: a wrongly loaded skill pulling the agent off its task.

Every turn
40 descriptions + “none”→Look-alikes confused→Wrong skill opened
After a wrong pick
Wrong SKILL.md in context→Agent follows its orders→Task drifts
Think about it. Going from 39 skills to 40 adds one option. How many new pairs that could be mixed up does it add? Thirty-nine: the new skill can be confused with each of the others. And libraries don't grow evenly. Someone writes “debug failing test”, someone else later adds “fix flaky test”, and the new one lands right next to the old.

5How it works: proving it, then fixing it

  1. Sweep the count. Same tasks, same model, several runs each, with 0, 5, 10, 20 and 40 skills. If success falls as skills are added, the number matters.
  2. Add an equal-length control. A control is a version that changes only the thing you want to rule out. At 40, swap half the descriptions for filler text of the same length that names no skill. If the filler version holds up and the real one drops, length was never the cause.
  3. Grade the choice alone. Label each task with its right skill, or “none”, and record what the agent opens. A table of picked against correct shows exactly which pairs get confused. This separates choosing wrong from doing wrong.
  4. Force a wrong load. Take tasks the agent passes with no skills and load one plausible but wrong skill at the start. Any drop is hijacking, measured with the choice taken out.
  5. Fix and retest. Put a search step in front so the agent sees only a few relevant skills. Merge look-alikes. Make each description say when not to use it, naming its closest neighbour.

Worked example, with real numbers, built from two separate sources, not one experiment. Agents choose tools the same way they choose skills: from a name and a description. Anthropic's advanced tool use post (Nov 2025) says, beyond token cost, “The most common failures are wrong tool selection and incorrect parameters, especially when tools have similar names”, such as notification-send-user and notification-send-channel. Its Tool Search Tool lets the model search for tools instead of seeing them all. On Anthropic's internal tests with large tool libraries, accuracy rose from 49% to 74% for Opus 4, and from 79.5% to 88.1% for Opus 4.5. It also cut tokens by 85%, so on its own it can't say which cause mattered more. That's what your filler control is for.

For skills themselves, SkillsBench (latest version, June 2026) compared tasks given different numbers of hand-written skills. Tasks with one skill gained 18.0 points over no skills, tasks with 2–3 gained 19.0, and tasks with 4 or more gained only 10.1. The groups are different tasks, so this is a hint, not proof; the authors suggest the extra content adds overhead or conflicting guidance.

6Follow-ups they'll ask

The agent picks the right skill 92% of the time in your offline test. Why is success still down?

The choice happens on every turn. As an illustration with my own numbers: at 92% per turn, a 20-turn run with no wrong pick happens 0.92 multiplied by itself 20 times, about 19% of the time. It's guide 1's sum again.

What if all 40 are really needed?

Keep all 40 installed, but don't show them all. Anthropic suggests keeping your three to five most-used tools always loaded and letting search find the rest. Or show skills by project or by phase of the task.

Won't a smarter model fix it?

It helps: Opus 4.5 started far above Opus 4. But the search step still added about 8.6 points on top. Better models shrink the problem; they haven't removed it.

7Check yourself

Tokens are ruled out. What two costs of 40 skills remain?

Choosing: wrong picks among look-alikes, on every turn. And hijacking: a wrongly opened skill's instructions steer the rest of the run.

What does the equal-length filler control prove?

If the same amount of text without extra skills doesn't hurt, while real skills do, then length isn't the cause. The number of choices is.

Name two fixes that keep every skill installed.

A search step that shows only a few relevant skills per turn, and descriptions that say when not to use each skill (or showing skills only in the projects and phases where they apply).

8Words to know

Look-alike skills
Skills whose descriptions are too close for the agent to tell apart reliably.
Instruction hijacking
A wrongly opened skill's instructions pulling the agent off its real task.
Control
A test version that changes only the thing you want to rule out.
