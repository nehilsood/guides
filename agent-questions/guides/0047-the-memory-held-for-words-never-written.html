The memory held for words never written

Original: LLM System Design Interview #6 · When Memory Becomes the Enemy

1The question

“Caching each token's keys and values makes the next token cheap to generate. On a server running many requests at once, what problem does that cache create, and what's the fix in principle?” AI Engineer interview, Meta

This builds on Day 92, “Serving fast: continuous batching, paged attention, speculative decoding”. Guide 31 sized the cache: 128 KiB a token for Llama 3.1 8B. Guide 41 showed why generating tokens one at a time is memory-bound, so a server earns its throughput by batching many requests into each step. Continuous batching means a finished request leaves the batch at once and a waiting one takes its place, rather than the whole batch finishing together.

2The trap

Trap A: “The cache is big. Buy GPUs with more memory.”

Trap B: “Cap the context length so each request's cache stays small.”

Both treat the problem as the cache's size. In older servers, most of the memory set aside for caches held no tokens at all.

3Your 30-second answer

“The cache grows by one entry per token, and nobody knows in advance how long an answer will run. Older servers reserved one unbroken slab per request, so much of it sat empty: in Kwon et al.'s tests only 20.4% of cache memory held real token states when the server reserved the maximum length, and 38.2% even when it knew each answer's length. Decode is memory-bound, so throughput comes from batch size, and batch size is capped by how many caches fit.

PagedAttention stores each request's cache in fixed blocks, 16 tokens by default, placed anywhere in memory, with a table mapping positions to blocks, handed out as tokens arrive. Waste falls to under one block per request, and in their tests vLLM served 2 to 4 times the throughput of earlier serving systems.”

4The idea in plain words

A small cinema gives every booking a whole row of twenty seats, in case friends turn up. Most bookings are three people. Seventeen seats per row sit empty, and latecomers are turned away from a hall that's mostly air.

The new manager seats people in blocks of four, any free block anywhere, and keeps a list of which blocks belong to which party. A party that grows gets another block. No party wastes more than three seats, and the hall fills.

The rows are slabs reserved per request; the blocks are PagedAttention's blocks; the manager's list is the block table.

Think about it. Why can't the server reserve exactly what each request needs? It doesn't know: the answer could stop after ten tokens or run to the limit. Any guess either wastes memory or runs out mid-answer, so blocks are handed out as tokens arrive.

5How it works: where the memory went, then paging

  1. Three wastes. Kwon et al. (SOSP 2023) list them for a slab sized to the maximum length: “reserved slots for future tokens, internal fragmentation due to over-provisioning for potential maximum sequence lengths, and external fragmentation from the memory allocator”. The first is used eventually but blocks other requests meanwhile; the other two are never used. They tested three versions of an earlier server: token states filled 20.4% of cache memory when it reserved the maximum length, and 38.2% even when it was told each answer's true length.
  2. Blocks and a table. Borrowing paging from operating systems, PagedAttention splits a request's cache into fixed-size blocks anywhere in memory, tracked by a block table, and allocates a new block only when the last one fills. Blocks hold 16 tokens by default: much smaller and reading the cache uses the GPU's parallelism poorly; much larger and the last block wastes more and less can be shared. Waste happens only in each request's last block. In the paper's profiling, 96.3% of vLLM's cache held token states; the vLLM launch post puts waste under 4%, against 60% to 80% in existing systems. When free blocks run out, vLLM evicts whole requests and later either swaps their blocks back from CPU memory or rebuilds their cache by running the prompt and the tokens so far through the model in one pass.
  3. Sharing. When one prompt yields several answers, the prompt's blocks are stored once. A shared block is copied only when one answer needs to write into it (copy-on-write). Serving OPT-13B on the Alpaca trace (short instruction requests), this saved 6.1% to 9.8% of memory for parallel sampling and 37.6% to 55.2% for beam search, which keeps several candidate answers alive at once; on ShareGPT conversations, more: 16.2% to 30.5% and 44.3% to 66.3%.
  4. The costs. Looking up the table made the attention kernel (the GPU program that computes attention) 20% to 26% slower than that of FasterTransformer, NVIDIA's inference library. Yet throughput rose 2 to 4 times against FasterTransformer and the authors' versions of Orca, an earlier continuous-batching server, because far more requests fit in each batch.

An illustration, with our own numbers: Llama 3.1 8B at 128 KiB a token (guide 31), 60 GiB free for caches, a 2,048-token limit, and requests that end at 300 tokens.

Where the premise outruns the evidence. The 2 to 4 times is a headline across the paper's models and traces. On ShareGPT, vLLM sustained 1.7 to 2.7 times the request rate of the Orca version told each answer's true length. And for OPT-175B on Alpaca's short requests the gain over the better Orca versions was “less pronounced”: with plenty of memory, the systems became “compute-bound rather than memory-bound”.

6Follow-ups they'll ask

Why not blocks of one token, for zero waste?

Kwon et al. found tiny blocks don't use the GPU's parallelism well when reading the cache, and big blocks waste more in the last one and share less. Block size 16 balanced the two, so vLLM uses it by default.

What happens when memory runs out mid-answer?

vLLM picks requests to evict and frees their blocks. Later it either copies the blocks back from CPU memory, where they were swapped, or rebuilds the cache by running the prompt and the tokens so far through the model again in one pass.

Does paging help when you sample several answers per prompt?

Yes: the prompt's cache blocks are stored once and shared, and a block is copied only when one answer writes to it. Serving OPT-13B on the Alpaca trace, Kwon et al. saved 6.1% to 9.8% of memory for parallel sampling and 37.6% to 55.2% for beam search (which keeps several candidate answers alive); longer ShareGPT conversations saved more.

7Check yourself

What are the three wastes of reserving one maximum-length slab of KV cache per request?

Slots reserved for tokens not yet generated, internal fragmentation (room for a maximum length the request never reaches), and external fragmentation (gaps the allocator leaves between slabs).

At 128 KiB a token, how much cache does a 300-token request take in blocks of 16 tokens, and how much is wasted?

It needs 19 blocks, 304 token slots, so 38 MiB. Four slots are empty, 512 KiB.

Why does wasted KV cache memory cut a server's throughput?

Generating tokens is memory-bound: each step's time goes on reading weights and caches from memory, not on arithmetic. So throughput comes from batching many requests into each step. Every wasted megabyte is room another request's cache could have used.
