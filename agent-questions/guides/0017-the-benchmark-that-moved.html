The benchmark that moved

Original: AI Agent Engineering Interview #12 · The Execution Benchmark Trap

1The question

“Your team stopped scoring code by how closely it matches a reference answer and started actually running tests. This quarter, a model that everybody agrees is stronger gets a lower score than last quarter's model did, on the same Docker benchmark. What would you check before calling it a regression?” Senior AI Engineer interview, Meta

An execution-based eval runs the model's code against tests, like guide 1's SWE-bench. Docker packages each task's environment (operating system, Python, libraries) into an image; each run starts a fresh copy, a container. A regression means the new model really got worse. The harness, from guide 1, is the code and settings that run the model: its tools, prompts and limits.

2The trap

Trap A: “The numbers don't lie. The new model regressed; dig into its failures.”

Trap B: “Execution tests are flaky. Ignore the result.”

Trap A assumes only the model changed. Trap B throws away a real signal unexamined. List what else changed between the two runs, and test each one.

3Your 30-second answer

“A score belongs to three things: the model, the harness and the environment. Only the model has its name on it. Between quarters, images get rebuilt with newer libraries, and the harness gets new limits and tools.

So first I'd run each task's real fix, the gold patch, in today's containers. If a real fix fails, the task broke, not the model. Then I'd re-run last quarter's model on today's setup and compare the two side by side. I'd sort every failure: setup errors say nothing about the model, patches that didn't apply and timeouts need a look, and tests that ran and failed are the clearest signal. And I'd check the gap against noise, because a couple of points on 500 tasks can be chance.”

4The idea in plain words

After a month of eating well, the gym scale says you've gained two kilos.

Before blaming your diet, you'd ask: is it the same scale? Did someone move it onto the carpet? The easy test is to weigh a 5 kg dumbbell. If the scale reads 7, it's the scale.

A second test: ask a friend whose weight hasn't changed to step on. If they've “gained” two kilos as well, it's not you.

In a coding benchmark, the dumbbell is the gold patch: the fix the project's developers actually made, which should pass every time. The friend is last quarter's model, run again today. The scale is the harness plus the environment: the Docker image and every library inside it.

Check the benchmark
Gold patches in today's image→Any real fix failing?→Broken task: set aside
Check the comparison
Old and new model, same setup today→Compare task by task→Gap bigger than noise?
Think about it, with our own numbers. Last quarter's model scored 41% then. Today, on the rebuilt image, it scores 38%. The new model scores 39%. Which model got worse? Neither. The setup took three points off the same old model. On today's setup the two are level, within noise.

5How it works: before you call it a regression

  1. List what changed besides the model. “Same benchmark” usually means the same task list; the image under it may have been rebuilt. Harness version, limits, tools, prompt: each is a suspect.
  2. Run the gold patches in today's containers. The SWE-bench harness has a built-in mode “to verify the gold patches”. Any task whose real fix fails is broken. Images drift because, as the SWE-bench-Live authors put it, “When dependencies are not pinned to specific versions, tools like pip by default will resolve to the latest package versions”.
  3. Re-run last quarter's model on today's setup. Now both face the same benchmark, task by task.
  4. Sort every failure. Our rule of thumb: a setup error (failed build, out of memory) says nothing about the model. A patch that didn't apply, or a timeout, needs a look: it may be the model's broken diff or a loop, or the harness. Tests that ran and failed are the clearest model signal.
  5. Size the gap against noise. Anthropic's eval statistics post (November 2024) recommends reporting the standard error, how much a score would wobble by chance, and comparing two models question by question: “conducting a paired-differences test lets us eliminate the variance in question difficulty.”

Worked example, with real numbers. A broken task can look exactly like a model failure. In SWE-bench issue #681 (October 2026), the gold patch for a task from pvlib, a Python library, is scored unresolved. Its environment has NumPy 2.0.2, but that version of pvlib still uses np.Inf, which NumPy 2.0 removed, so the tests can't even load. The scorer still reported it as an ordinary failure, not a setup error, so any model's fix there is marked wrong.

The machine matters too. In Anthropic's infrastructure-noise study (February 2026), changing only the containers' resource limits moved Terminal-Bench 2.0, a benchmark of command-line tasks, by 6 points. Their advice: “leaderboard differences below 3 percentage points deserve skepticism” until the setups are documented and matched.

6Follow-ups they'll ask

All the gold patches pass. Is the setup cleared?

Only the tasks are. A gold patch is applied directly, so it never touches the agent's side: tools, prompts, time limits, memory. To check that side, re-run a model whose ability can't have changed, such as last quarter's, on today's setup.

How could a stronger model lose points to the setup?

Our guess: by doing more. Anthropic's 2026 infrastructure-noise study shows how that can cost points: some models start a Terminal-Bench task by installing a whole data-science stack, and under tight limits the container runs out of memory during that install, before the agent writes a line of solution code.

Why did moving to execution tests make this more likely?

Comparing text with a reference needs no environment. Running tests needs a working one, with the right library versions. Because pip installs the newest version of any unpinned library, an image rebuilt later can contain different code. The SWE-bench-Live team fixed this by only allowing versions released before each task's code.

7Check yourself

What three things does a coding-benchmark score depend on?

The model, the harness (tools, prompts, limits) and the environment (the Docker image and its library versions). Only the model's name goes on the score.

What does running the gold patches tell you?

Whether each task can still be solved in today's container. If the real fix fails, as with the pvlib task under NumPy 2.0.2 in SWE-bench issue #681, the task is broken and its failures say nothing about any model.

On the same 500 tasks, a new model scores 39% and the old one 38%. Is the new one clearly better?

No. At about 39% on 500 tasks, the standard error is about 2.2 points, bigger than the gap. Compare task by task and run more than once before claiming either way.

8Words to know

Gold patch
The fix the project's developers actually made for a task. It should always pass.
Docker image
A packaged environment (system, language, libraries) that each run starts from.
Environment drift
The setup changing over time, for example a rebuilt image pulling newer libraries.
Standard error
How much a score would wobble by chance if you re-ran it on a fresh set of similar tasks.
