Agent question 56 · extra · Day 151 · about 10 minutes

The dashboard that stayed green

Original: Machine Learning System Design Interview #21 · The Silent Feature Death

1The question

“The A/B readout for your new pricing model makes no sense, yet its service never threw an error: 99.9% uptime, 15 ms per request. The model passed every offline check before launch. Where do you look first, and what would you add so this can't hide again?” Senior ML system design interview, Facebook

This builds on Day 150, “Closing the loop: user feedback, monitoring, regression evals”. A feature is one input the model reads, such as a product's demand last hour or a competitor's price. A feature pipeline is the job that computes those inputs and stores them for the model to look up at request time. An A/B test splits users between the old and new model (guide 11); each group is an arm. Offline checks score a model on stored data before launch.

2The trap

Trap A: “Roll back to the old model.”

Trap B: “The service is healthy, so the model is simply worse. Cancel the launch.”

Both trust the service checks. If the inputs went stale, the old model reads the same stale inputs, and the new model was never really tested.

3Your 30-second answer

“I'd check the inputs before the model. Uptime and latency say the service answered, not that it answered from today's data. A feature job can stop updating, or start filling in a stand-in default value, and nothing errors: the model just scores old or empty inputs. Google's Rules of ML describes this: once a table its features come from stops updating, the system keeps working and decays gradually; Play once refreshed a table six months stale and install rate rose 2%.

So first: how old is each feature table, how often is each feature missing or at its default, and do logged serving values match what training saw? Then alert on those, as Google's ML Test Score recommends, and refuse to read an experiment whose inputs failed them.”

4The idea in plain words

A delivery driver's fuel gauge has come loose inside the tank, and since Tuesday the needle has sat at three-quarters. The engine runs sweetly, no warning light comes on, the satnav works. On Friday she plans a long route on what the needle shows, and runs dry between towns.

Nothing checked whether the needle had moved since Tuesday.

Service checks, such as uptime, latency and error counts, are the engine lights. A model's answers also depend on its inputs being current and filled in. An input that stopped updating is stale; the time since its last update is its freshness. When serving inputs differ from what the model trained on, that is training/serving skew.

What the dashboard watched
Request arrives→Model answers in 15 ms→No error: green
What it missed
Feature job stopped→Lookups return old values or defaults→Prices set from last week
Think about it. A competitor-price lookup fails and the code fills in −1, a value the model has seen before. Which check notices? Not the error count: nothing threw. Not latency: a default is fast. Only a check on the values themselves (our reasoning).

5How it works: why it hides, and the checks that find it

  1. Inputs can break without an error. Google's ML Test Score (Breck et al., IEEE Big Data 2017) warns that outages and changes upstream “can radically change the feature’s meaning” without producing values strange enough to trip other monitoring.
  2. Stale inputs decay slowly. Google's Rules of ML (Zinkevich), Rule #10: when a table the model's inputs are looked up from stops updating, behaviour stays “reasonably good, decaying gradually”. Its example: “Play once had a table that was stale for 6 months, and refreshing the table alone gave a boost of 2% in install rate.”
  3. Watch the age of every source. The ML Test Score's example is a table of the most popular items: “it is crucial to monitor the age of this table, so that if the process stops running, alerts will fire.” How old is too old? The ML Test Score suggests a small A/B test with older models to draw an age-against-quality curve; do the same per table (our extension).
  4. Watch the values. In Data Validation for Machine Learning (Breck et al., SysML 2019), a refactor makes a failed backend call pin one number to −1 for a slice of traffic, one subset of requests. The model keeps predicting, less accurately, and “the data looks perfectly fine for the training code, since -1 is an acceptable value”. Their system compares each feature's spread of values from day to day, and training against serving, and names the value that moved most. They dropped standard statistical tests such as chi-square, which flagged harmless noise in 100 million values in 7 of 10 trials.
  5. Compare training and serving. The ML Test Score: log a sample of serving traffic; where serving inputs become training data, tag each example so the two can be compared, since for the same example “the feature values should be perfectly identical at training and serving time”.
  6. Gate the readout. Our design: an A/B result counts only if freshness and coverage (how often each feature is filled in) checks passed in both arms for the whole test.

An illustration, with our own numbers. One test week, two kinds of check:

Where the premise outruns the evidence. In a real incident, check the experiment too: whether users were split as planned and the arms are the sizes expected. And the 2% is one table at one Google product, not a rule for how much staleness costs (our reasoning).

6Follow-ups they'll ask

Why not run a standard statistical test on each feature every day?

At production volumes it fires on harmless changes. Breck et al. (SysML 2019) mixed 0.01% noise into 100 million values and ran a chi-square test, a standard check of whether two distributions match: it raised a needless alert in 7 of 10 trials. They use the largest change in any one value's share instead, with thresholds like “allow changes of only up to 1% for each value”.

The model is retrained daily on its own logged traffic. Does that make it worse?

Yes, if the bug runs for days: in Breck et al.'s −1 example, served data becomes the next day's training data, so the bad values carry into the next model too. Retrain without the affected days once the feature is fixed (our reasoning). It's the same loop as a recommender learning from clicks it caused (Q50).

How fresh does each feature need to be?

Measure it. Rules of ML, Rule #8, asks how much quality drops with a model a day, a week or a quarter old; the ML Test Score suggests a small A/B test with older models to draw an age-against-quality curve. Do the same for each feature table, then set its age alert from the curve (our extension).

7Check yourself

Why can a model service show full uptime and no errors while its predictions are wrong?

Service checks test that it answered, not what it answered from. A feature job that stops updating, or a lookup that falls back to a default, raises no error; the model scores stale or empty inputs.

What does Google's Rules of ML report about a stale table at Play?

Rule #10 says Play once had a table stale for six months, and refreshing it alone raised install rate by 2%; stopped tables make systems decay gradually rather than fail.

Name three input checks that catch a silently broken feature pipeline.

The age of each feature table, with an alert if it stops updating; the share of requests where each feature is missing or at its default; and logged serving values compared with training values for the same examples.
