Agent question 49 · extra · Day 102 · about 10 minutes

The call that failed one token at a time

Original: Advanced NLP Interview #6 · The 99% Accuracy Trap

1The question

“Each token your model writes in a tool call is right 99% of the time, yet its JSON calls, about 300 tokens long, fail more often than they succeed. Why? What would you fix in the surrounding system, leaving the model alone?” Senior AI Engineer interview, Meta

This builds on Day 101, “Prompt engineering: instructions, examples, structured output”. Guide 1 introduced the tool call: the model asks your code to do something, here by writing a JSON object naming the tool and its arguments. Structured output means making the model's answer follow a fixed format, such as JSON that matches a schema: a description of which fields are allowed and what type each one holds.

2The trap

Trap A: “99% is excellent. The failures must come from a handful of bad prompts.”

Trap B: “Add ‘respond ONLY with valid JSON’ to the prompt, in capitals.”

Both judge the call by its per-token score. A call needs every token right, and small chances of a slip add up.

3Your 30-second answer

“Errors compound. If each token is right with probability 0.99, and we assume the slips are independent, a 300-token call is entirely right with probability 0.99 to the 300th, about 4.9%. So I'd make fewer tokens depend on the model.

Constrained decoding blocks, at every step, any token that would break the schema, so braces, quotes, key names and commas can't go wrong, and only the values are left to the model. A leaner schema shortens what's left. Then I'd validate every call and retry with the error message. How much this helps depends on where the slips were: if nearly all were in the structure, constraint fixes most failures; with a quarter in the values, over half the calls still fail first time; if most were in the values, it fixes few. So I'd sort a sample of failures by kind first.”

4The idea in plain words

You're typing a 300-character licence key from a printed card, in groups between dashes, and you slip about once every hundred characters. Three slips in a typical attempt: the key nearly always fails.

A better installer fills in the dashes, refuses characters that can't appear in a key, and checks the key's checksum, asking again when it fails.

One slip it can't stop: reading a B as an 8 when both are allowed. Constraining the format can't fix a mistake in the content.

Think about it. If per-token accuracy rose from 99% to 99.9%, how likely would a 300-token call be to come out entirely right? 0.999 to the 300th is about 74.1%. A tenfold cut in the error rate turns mostly failing into mostly working.

5How it works: the arithmetic, then the fixes

  1. Compounding (our arithmetic). Under independence, all-right probability is p to the n: 0.99300 ≈ 4.9%, 0.9980 ≈ 44.8%, 0.999300 ≈ 74.1%. Independence is our simplification: real slips can cluster after a first mistake or pile up on hard tokens, so treat this as direction, not forecast.
  2. Mask what can't be valid. Willard and Louf (2023) set the probability of every token that would break a regular expression (a pattern describing allowed text) or grammar to zero before sampling, using “a boolean mask” over the vocabulary, every token the model can pick. A precomputed index makes the check cost “O(1) on average” per token, “guaranteeing the structure of the generated text”. Their library is Outlines.
  3. Know your tool's limits. The grammars guide for llama.cpp, an open-source program for running models locally, says a grammar can “force the model to generate valid JSON”, and it converts “a subset” of JSON Schema, where “Unsupported features are skipped silently”. It also says the schema “is only used to constrain the model output and is not injected into the prompt”, adding: “This does not apply to tool calling, where schemas are injected into the prompt.” So outside tool calling, describe the fields in the prompt yourself.
  4. Validate, then retry. Our suggestion: check each call against the schema and the tool's own rules, such as whether that ID exists, and on failure retry with the error in the prompt.
  5. Watch the cost to reasoning. Tam et al. (2024) compared free-text answers with JSON mode (in the OpenAI and Gemini APIs, and on Llama-3-8B and Gemma-2-9B through Text-Generation-Inference; they assume it works like Willard and Louf's masking) and with looser format instructions. JSON mode lowered accuracy on reasoning tasks but matched or beat free text on classification. One cause: on one task GPT-3.5 Turbo's JSON-mode answers always put the “answer” key before the “reason” key, answering before reasoning. Our suggestion: put any reasoning field first, or reason in plain text and constrain only the call.

An illustration, with our own numbers. Take a 300-token call where 220 tokens are structure the schema fixes and 80 are values. Each call averages three slips either way. In case A slips fall evenly across all 300 tokens; in case B every slip is in a value, so each value token is right 96.25% of the time. Retries assume independent attempts.

Set-upRight first timeRight within 3 tries
Case A, no constraint4.9%14.0%
Case A, constrained44.8%83.1%
Case B, with or without constraint4.7%13.4%

Both cases average 99% per token; the constraint helps only where the slips were in the structure. Which case you're in is a measurement, not a guess.

Where the premise outruns the evidence. The question's “fail more often than they succeed” follows from 99% only if slips are independent and spread evenly, which no source here measured. A 99% average can hide 100% on 220 punctuation tokens and 96.25% on 80 values.

6Follow-ups they'll ask

Why not just retry until it parses?

At 99% per token over 300 tokens, a call is right 4.9% of the time, assuming independent slips; three independent tries lift that only to 14.0%, at up to triple the cost. Retrying works best after constraint has removed most of the ways to fail.

Can format restrictions cost anything?

In Tam et al.'s tests, JSON mode (on OpenAI and Gemini models, Llama-3-8B and Gemma-2-9B) lowered accuracy on reasoning tasks while matching or beating free text on classification, and looser formats generally did better on reasoning. llama.cpp's grammar guide also warns that unsupported schema features are skipped silently. Keep reasoning outside the JSON, or before the answer field, and test the grammar you actually get.

The JSON is now always valid. Is the call right?

Not necessarily. A grammar guarantees the shape, not the content: a valid call can name the wrong customer or the wrong unit. Check the values against the tool's rules, and where a field has few options, list them in the schema so the choice itself is constrained (our suggestion).

7Check yourself

If each token is right with probability 0.99, independently, how likely is a 300-token output to be entirely right? And at 0.999?

0.99300 ≈ 4.9%; 0.999300 ≈ 74.1%.

What does constrained decoding do at each generation step?

It sets the probability of every token that would break the required format to zero, so the model can only pick tokens that keep the output valid. This guarantees the structure, not the content.

When would constraining a tool call's JSON structure barely raise its success rate?

When the slips were in the values, not the structure. Masking braces and key names then removes almost no errors, and every wrong value still fails the call.
