After that the guides are independent. Each one stands alone and can be read in any order, so pick by which round is next.

Each guide opens with a flowchart you can walk in ninety seconds: the system, where it breaks, and what fixes it. All of them on one sheet, for printing.

What each guide contains, and how to work it

Every deep guide has the same moving parts, in this order. What the question is actually testing — four probes, because the question is never about the thing it names. The answer at three lengths: a thirty-second version that contains the thesis rather than the setup, a two-minute shape as numbered beats, and one line worth memorising verbatim. The fundamentals, each led by a plain-English statement before the precise term arrives. The mechanism, stated as something you could be wrong about. The measurement — what you would run to prove it, which is the half most candidates skip and the half that separates the answers. Twelve follow-ups with full written answers. And a numbers cheat sheet plus a glossary.

The last section of every guide is an evidence block: four rows where your own numbers go, and underneath them the answer those numbers earn, which refuses to read as finished while it still contains a figure nobody measured. Typed values are saved in that browser as you go.

Every guide also carries a spoken script — seventy-five to eighty-five seconds, four beats, situation / mechanism / what I did / what it cost, ending on the cost rather than the fix. Short lines, because you read a script aloud in short lines. It is the one thing on the page you cannot do silently, and it is the format both other projects settled on for the same reason.

The thirty-second answers are meant to be said out loud. Reading them silently feels like preparation and mostly is not.

The through-line, which is worth noticing before you start

All thirteen questions have the same shape. Each one hands you an answer that sounds sensible — cap the iterations, trim the descriptions, code can have bugs, the new model is worse, wrap it in retries, delete the scaffolding, let the agent write its own skills, have a judge score the reviews, specialised agents are better at their roles, shorter sequences plus lower loss means ship it, overfitting — add regularisation, read the failures and see what the model got wrong, add a readability reward and a latency penalty — and each one fails for the same reason: it argues in the units of the symptom rather than the units of the cause. A cap addresses latency when the defect is a missing stopping rule. Trimming addresses tokens when the defect is confusability. “Code is buggy” addresses correctness when the axis is boundedness. “The model is worse” addresses capability when the defect is a format contract — and it blames the component that changed instead of the one that should have changed with it. “Retry it” addresses flakiness when the defect is a broken invariant, so it re-sends the same bytes to the same validator and gets the same verdict forever. “The scaffolding is dead weight” addresses capability when the defect is measurement — it reads a score that could only ever have covered the part of the system that was free to vary, and deletes the part that was not. “Have the agent write its own skills” addresses engineering cost when the defect is provenance — it produces a document that is indistinguishable by inspection from a measured one, and the format grants it the same authority. “Have a judge score the reviews” addresses quality when the defect is evidence — it grades how a review reads, which is the one link in the chain no human ever acted on. “Specialised agents are better at their roles” addresses capability when the defect is topology — it credits a context boundary with delivering specialisation that a prompt already gave you for free, and bills you for the boundary anyway. “Shorter sequences plus lower loss means ship it” addresses compression when the defect is sampling — both numbers are real, and both were measured on text cut at offset zero, which is the one cut point no user in an editor has ever occupied. “Overfitting — add regularisation” addresses the gap between train and test when the defect is that there is no gap, because the test set is inside the training set — it reaches for the famous word, prescribes a cure that makes things worse, and never asks the only question that mattered, which is what one row of the evaluation was a sample of. “Read the failures and see what the model got wrong” addresses the model when the defect is the instrument — it assumes the answer key is still correct, starts with the most expensive activity available, and never notices that the two numbers being subtracted came out of two different machines. “Add a readability reward and a latency penalty” addresses the symptom list when the defect is the specification — it is a to-do list offered where a diagnosis was asked for, it treats a stopwatch and a learned judge as two coefficients on one sum, and it never notices that the four things the reviewers named were not absent from the objective at all. They were priced at zero, which is what made them available to spend.

So the move that works is the same one every time: name the mechanism in units the symptom does not use, then name the measurement that would prove you wrong. Thirteen questions, one habit.

Question 10 · Senior AI Engineer · model & serving round

The tokenizer that got better at everything except the cursor

“A teammate retrained our code tokenizer to merge freely across whitespace. Sequences got ~40% shorter and held-out loss improved. Why might IDE autocomplete get worse after we ship it, and what do you check before approving?”

  1. 0011 The Half-Typed Line unread

    Both numbers are real and both were measured on complete files. A tokenizer compresses and segments, and every merge you add deletes a boundary — so “40% fewer tokens” and “40% fewer places a cursor can stand” are one measurement written twice. Which of the four tokenizer layers actually changed, why fill-in-the-middle cuts the file twice, and why token healing is a mitigation with a residual rather than a fix.

Question 11 · Senior ML Engineer · data & evaluation round

The test set that was already in the training set

“You scraped GitHub, held out a random 5% of files as your test set, and your new code model just posted a big jump on it. Before you announce anything, what’s the first thing you’d suspect about how that split was built?”

  1. 0012 The Twin in the Test Set unread

    The split did exactly what shuffle=True promises — it partitioned rows, when what you needed partitioned was information. 428 million files on GitHub collapse to 85 million unique ones, in a corpus that already excludes forks, so a test file with even one twin has a 95% chance that twin is in training. Why grouping keys come from the claim rather than the data, why time orders events but not copies, and the one afternoon’s measurement that settles it.

    15 sections12 follow-ups5 checks, 1 gate

Question 12 · Senior AI Engineer · evaluation & infrastructure round

The benchmark that decayed between two quarters

“We moved our coding eval from reference-similarity scoring to execution-based tests. This quarter, a model everyone agrees is stronger scores lower than last quarter’s model on the same Docker benchmark. What do you investigate before you call it a regression?”

  1. 0013 The Score With Three Authors unread

    A benchmark score is a joint measurement of a model, a harness and an environment, and it gets written down under the model’s name. Execution-based scoring did not remove the reference — it compiled it into a test suite that now has a build, and software rots: 9.81% of untouched Dockerfiles build differently over nine months, and OpenAI retired SWE-bench Verified after finding 59.4% of the hard tasks it audited had flawed tests. Three controls, a four-bucket taxonomy, and the one re-run that turns a diagonal into a comparison.

Question 13 · Senior AI Engineer · training & alignment round

The reward that paid for one thing out of five

“Your RL reward for code generation is ‘all tests pass.’ Six weeks in, pass rates are up, but reviewers say the code is slow and full of unnecessary comments. What’s missing from your reward, and what breaks if you just add a readability judge?”

  1. 0014 Everything You Didn’t Pay For unread

    A reward function is a complete, literal price list, and four of the five dimensions your reviewers named are priced at zero — which does not mean ignored, it means available to spend. Slow code is purchased certainty. Then the trap: three of your four signals are programs and one is a player, a weighted sum is a Lagrangian relaxation with the price made negotiable, and on any group where every sample already passes, the gated bonus weight cancels out of the advantage entirely and the judge becomes the whole gradient.
