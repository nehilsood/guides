Question 8 · Google · senior AI engineer

What the Author Did Next

A code-review skill shipped six months ago and nobody knows if it helps. The trap is that the obvious fix — have a judge score the reviews — measures how good a review sounds, not whether a single line of code changed. This is the loop that measures the second thing.

The question, as asked

“Your team shipped a code-review skill for your coding agent six months ago. Nobody knows if it helps. How do you build a production feedback loop that measures its quality from real PRs and turns that evidence into concrete skill edits?”

00

What they are actually testing

Read the question slowly and you will notice it contains a complete engineering brief with one word doing all the work: quality. The interviewer never says what quality means, and the entire interview is whether you notice that you have to define it before you can build anything. There are four things being probed underneath.

P1

Do you know where a valid signal can possibly live?

A review comment produces text. Text can be scored. But the thing you care about is a change in the world — a line of code that is different because the comment existed. If you cannot say which of those two you are measuring, everything downstream is decoration.

P2

Can you break your own metric before they do?

Every candidate reaches acceptance rate. The separation is whether you volunteer the attack on it — that it is a ratio whose denominator the agent chooses — or whether the interviewer has to point it out to you.

P3

Do you know the difference between correlation and a counterfactual?

“The author fixed it” is not “the comment caused the fix.” Senior candidates reach for a holdout without being asked, because they know which direction that bias runs and that it is worst on exactly the comments that matter least.

P4

Can your loop return a negative?

A feedback loop that only ever produces edits is a justification machine. The question says “concrete skill edits”, and the strongest answer includes the edit nobody proposes: delete the file. If you have no kill condition, you have no experiment.

Not the same question as guide 0003 or guide 0008

Three questions in this series now involve the word skill, and they fail in three different places. 0003 is a selection failure: forty skills exist, the right one is not retrieved. 0008 is a provenance failure: the skill was written from the task description, so nothing in it was ever measured.

This one assumes both of those are fine. The skill is the only one in its category, it retrieves correctly every time, and a competent engineer wrote it from real review experience. It is an evaluation failure: the artefact went out of the door and nothing was ever attached to its output. 0008 asks where did this come from. 0009 asks what has it done since. They are the two halves of the same missing frontmatter, and section 08 writes both halves out together.

01

The answer, at three lengths

Lead with the definition of quality. Everything else in this answer is an implementation detail of that one choice, and if you get it out in the first sentence the rest of the conversation is you explaining a system rather than defending a metric.

Do not say I’d have an LLM judge score the reviews, then ask the model to improve the prompt.

Two defects, and the interviewer is holding both. The judge grades the review, so you learn how good a review sounds — and a review can sound excellent and be ignored by every author who reads it.

And “ask the model to improve the prompt” closes the loop inside the model. The thing proposing the edit and the thing judging it are the same process, which is the failure this series already took apart in guide 0008.

Say instead The skill is a hypothesis. Its outcome is what the author did with the comment, not what a judge thought of it.

This is the whole answer compressed. It names the unit of measurement — a human action in a repository — and it puts the skill in the category of things that can be wrong.

Then you have earned the right to describe the machinery: label from the diff, aggregate into failure clusters, propose bounded edits, gate each version against a no-skill baseline, and report precision beside a miss rate so that neither can be gamed alone.

Thirty seconds

“A skill is a hypothesis, not an asset. I’d measure it by what humans did with its output — every review comment gets labelled from the diff that followed it as addressed, ignored or pushed back — then cluster the ignored ones into failure modes, ship targeted diffs to SKILL.md rather than rewrites, and gate every version on held-out PRs against both the current version and no skill at all. And I’d report precision next to a miss rate, because acceptance alone is gamed by posting two safe nits per PR.”

Two minutes

“First, the good news: we already have the ground truth, it just is not labelled. Six months of PRs contain, for every comment the agent posted, the diff the author pushed afterwards. So in a week I can backfill a label set without shipping anything — addressed, ignored, pushed back — and get the failure clusters out of it. What backfill cannot give me is a no-skill arm, because the skill was on for all six months, so I’d start that holdout the same day.

Second, the metric. Acceptance rate is a ratio whose denominator the agent controls, so on its own it is Goodhart bait — post two trivial nits per PR and you score 100%. I pin the denominator externally, per PR or per hundred changed lines, and I always pair it with something the agent cannot shrink: defects that escaped to a revert, a hotfix or an incident on lines the review actually saw.

Third, causality. ‘Addressed’ is not ‘caused’ — authors fix obvious things anyway. So a small slice of comments becomes a ghost comment: the agent generates it, we log it, we do not post it, and we watch whether the line changed regardless. That gives the incremental number, and the gap between it and raw acceptance is itself a diagnostic.

Then the loop. Cluster the labelled comments with a reasoning model, have it propose bounded add, delete and replace edits to the skill, a human approves the diff, and the skill is versioned like code. Each version replays offline on held-out PRs to kill regressions cheaply, then canaries live on a fraction of PRs where the real outcome metric is measured — because replay tells you what the agent would post, never what a human would do.

And I’d audit the judge, because the judge is a model too. A labeller with a few per cent error does not just add noise, it shrinks every effect you are trying to see, which decides how much data you need before the gate means anything.”

One line, if they cut you off

“Measure the diff, not the review.”

Say it out loud · about 85 seconds

02

Fundamentals: where a signal can actually live

Almost every bad answer to this question comes from measuring one link too early in the chain. So draw the chain first. A code-review skill produces four things in sequence, and only one of them is evidence.

Link 1 The document

The skill itself. Readable, lintable, scoreable for structure and style. Tells you nothing about effect.

Link 2 The comment

What the agent posted. This is what a judge can grade, and grading it tells you how the comment reads.

Link 3 The author’s response

Changed the line, ignored it, argued back. A human acted. This is the first link that is evidence.

Link 4 What shipped

Did the merged code break? Reverts, hotfixes, incidents. Slow, sparse, and the only thing the business cares about.

Links 1 and 2 are things a model says. Links 3 and 4 are things a person did. The colour on this page is that distinction and nothing else.

Why link 2 feels like the answer and is not

Scoring the comment is seductive because it is cheap, immediate and dense: every comment gets a number, today, without instrumenting anything. The problem is that a review comment has no ground truth of its own. “Is this a good comment?” is not a question about the comment, it is a question about whether a specific human, on a specific afternoon, with a specific deadline, would act on it.

There is a published number that makes this concrete. A 2026 production study of enterprise agent skills ran paired live trials — the same task, same model, same sandbox, once with the skill and once without — across 947 scored pairs drawn from real production skills, and compared what the structural gates said about a skill against what an LLM judge said. The two agreed at ρ = 0.14. Two gates, both sitting upstream of any outcome, both claiming to measure skill quality, essentially unrelated to each other.

That is not an argument that link 1 and link 2 are worthless. Structure scans catch real authoring defects and judges catch real incoherence. It is an argument that they are upstream instruments: cheap, fast, useful for triage, and incapable of settling the question the interviewer asked.

The sentence to have ready

“You can grade the review. You cannot grade it against anything, because the only ground truth a review has is what the author did next.”

What the skill costs while you are not measuring it

The other half of the fundamentals is the denominator of the whole exercise: a skill is not free while it sits there unevaluated. Its description occupies the system prompt on every request whether it fires or not, and when it does fire the body enters the conversation and stays there for the rest of the run. Median skill documentation runs about 1,196 tokens. So an unmeasured skill is not a neutral asset parked on disk — it is a recurring charge against the context window of every review you run.

That is what “dead weight” means precisely, and it is why the honest framing is a hypothesis rather than an asset. An asset is something you own. A hypothesis is something that is costing you until it is confirmed.

03

You already have six months of ground truth

This is the move that separates a good answer from a confident one, and it takes ten seconds to say. The question is framed as though you are starting from nothing. You are not. Every comment the agent has posted since launch already has its outcome sitting next to it in version control.

For each comment, the repository knows: which file and line it was anchored to, what the diff looked like at that moment, what the author pushed afterwards, whether they replied, and whether the thread was resolved. That is a labelled dataset that was accruing the whole time nobody was looking at it. You do not need to ship anything to get it — you need a job that walks the history and a labeller.

The label

Three classes, and be specific about how each is decided, because the interviewer will ask:

  • Addressed — the lines the comment pointed at changed in a commit pushed after the comment, in a direction consistent with what it asked for. The timestamp ordering is load-bearing and it is the cheapest correctness check in the whole system; without it you will label comments as “addressed” that were posted after the fix.
  • Pushed back — the author replied disagreeing, or resolved the thread with no corresponding change. This is a different failure from being ignored and it clusters differently: pushback usually means the rule is wrong for this repo, while silence usually means the comment was not worth the interaction.
  • Ignored — no reply, no change, merged anyway. The largest bucket in most systems, and the one nobody looks at.

The judge here is doing a narrow, well-posed job: read the comment, read the subsequent diff hunk, decide which of three things happened. That is a far easier task than “rate this review out of ten”, and it is the reason a judge is defensible here and indefensible there. Judges are good at bounded comparisons against a visible artefact and bad at unbounded quality opinions.

The limit of backfill — volunteer this before they find it

Six months of history gives you rates, clusters and a precision estimate. It cannot give you a lift, because the skill was enabled for every one of those PRs. There is no control arm in the past and no way to manufacture one.

So the honest structure is two-track, and saying it this way is the whole point: backfill answers ‘what is it doing wrong’ this week; the holdout answers ‘is it worth anything’ in four weeks. Start both on day one, because the second one has a four-week latency you cannot compress and every week you delay it is a week you still cannot answer the interviewer’s actual question.

The number this immediately produces

Comment acceptance rate: addressed comments divided by comments posted. It is the right first metric and it is worth knowing what real systems look like before you quote your own. Google’s production system for resolving review comments with ML reports that “in deployment, code-change authors at Google address 7.5% of all reviewer comments by applying an ML-suggested edit” — while the same system’s offline evaluation “addresses 52% of comments with a target precision of 50%”.

Hold those two numbers next to each other, because the distance between them is the subject of section 08. Offline, the model can produce a usable suggestion for about half of all comments. In production, about one in thirteen comments actually ends in an applied edit. Nothing about the model changed between those two numbers. What changed is that humans got involved, and the deciding factor turned out to be something no offline metric measures at all: whether anyone previewed the suggestion. Google reports that authors previewed only around 20% of generated suggestions in beta, around 40% at launch, and that “40% to 50% of all previewed suggested edits are applied by code authors”. The acceptance rate was fine. The funnel in front of it was not.

04

The metric that grades itself

Acceptance rate is the correct first metric and it is also a trap, and the reason is structural rather than a matter of degree. Say the structure out loud and the interviewer knows you have shipped something.

acceptance = comments addressed ÷ comments posted comments posted ← chosen by the agent comments addressed ← chosen by the author

The denominator is under the control of the thing being measured. Any ratio with that property can be maximised without improving anything: raise the posting threshold until only the unmissable comments survive, and the ratio climbs towards one while the agent does less and less work. The agent does not need to be adversarial for this to happen, and that is the part worth stressing — nobody has to be gaming anything. A well-meaning edit that says “only comment when you are confident” produces exactly this, and the dashboard rewards it.

Illustrative figures, per PR. The arithmetic is the point, not the values: B is the worst agent in the room and it wins the metric outright. A single ratio does not merely mis-score B — it inverts the order of all three.

Notice what B actually did. It did not get better at review; it moved its operating point along the same curve, trading volume for precision. C moved the curve itself. A metric that cannot tell those two apart will happily hand you a version that scores higher and reviews worse, and it will do it repeatedly, because every round of optimisation finds the cheap direction first.

The distinction to name explicitly

An operating-point change trades one error type for the other at fixed capability. A capability change improves both at once, or improves one while holding the other fixed. Only the second is a better skill. So a comparison is only meaningful when the operating point is pinned, or when you report enough to see both axes at once.

Two fixes, and you want both

  • Pin the denominator externally. Stop dividing by what the agent chose to post. Divide by something the agent cannot move: addressed comments per PR, or per hundred changed lines. Now the strict version’s score collapses to 2 per PR against the loose version’s 9, which is the correct answer, and it is the correct answer for a reason worth saying — the denominator is now a property of the work, not of the reviewer.
  • Pair it with a quantity the agent can only make worse by saying less. Precision alone is maximised by silence. Escaped defects — bugs that reached production on lines the review saw and did not flag — is minimised by saying more. Report the pair and neither can be optimised alone. This is the same reason nobody ships a classifier on precision alone.

The doctor analogy in the newsletter is the version of this to use if the room is not technical: counting prescriptions tells you nothing, and a doctor who prescribes nothing has a perfect record. What matters is whether the patient got better.

05

“Addressed” is not “caused”

Here is the second structural problem, and it is the one most candidates never reach. Suppose your labelling is perfect and your denominator is pinned. You now know how many comments were followed by a matching fix. You still do not know how many fixes happened because of the comment.

Authors fix things for reasons that have nothing to do with your agent. They were mid-edit when the comment landed. A human reviewer said the same thing. CI failed. They reread their own diff and winced. Every one of those shows up in your data as an addressed comment, and every one of them inflates your number.

The direction of that bias is not random, and this is the sentence that makes the point land: the comments most likely to be marked addressed are the ones the author would have fixed anyway. An obvious missing null check gets fixed by everyone. A subtle ordering bug in an async handler gets fixed only if someone points at it. So naive acceptance rate systematically over-credits your least valuable comments and under-credits your most valuable ones. It is not just biased upward — it is biased in the direction that makes a useless skill look best.

The ghost comment

The fix is an intervention, and the cleanest version of it was invented by the advertising industry for exactly this problem — “would they have converted anyway?” The technique is ghost ads: for a random control slice, run the whole pipeline, log the ad that would have been served, then serve something else. The log entry becomes a counterfactual at no media cost.

Port it directly. For a random slice of PRs — three to five per cent is plenty — the agent runs normally, generates its comments, and the system logs them without posting them. Then you watch those exact lines. Did the author change them anyway?

incremental acceptance = fix rate on posted comments − fix rate on ghost comments posted 60% ← what the dashboard shows ghost 38% ← what would have happened regardless ---- incr. 22% ← what the skill is actually worth

Three things make this the right answer rather than a clever one. It is invisible to users, so nobody has to consent to a degraded experience. It costs one inference per suppressed comment and no engineering beyond a flag on the posting step. And the gap between the two rates is itself the diagnostic — a skill whose ghost rate nearly matches its posted rate is telling you that it mostly restates what the author already knows, which is a finding you will not get from any amount of judging.

The objection, and the answer

“You are deliberately withholding review comments from real PRs.” Yes, on a few per cent of them, and the honest response is to scope it rather than deny it: exclude anything the agent flags as security or data-loss, keep human review entirely untouched, and note that the alternative is shipping a review system whose value nobody has ever measured — which is also a risk, just an unowned one.

If the holdout is genuinely not allowed, say what you would fall back to and what it costs you: comment timing relative to the fix commit, comparison against PRs where the skill failed to retrieve, and a same-file before-and-after around the rollout date. All three are weaker, all three are confounded, and none of them gives you a clean number. Say that too.

06

The other half: what it did not say

Precision is the half you can see. The half that matters more is the comment that was never posted — the defect the review looked straight at and did not flag. That number has no natural home in any review dashboard, and building even a bad version of it is what makes the answer complete.

There is no true recall available. Recall needs a denominator of all defects present, and nobody has that. What you can build is a proxy from the defects that eventually announced themselves:

  • Reverts. A commit reverted within some window, where the reverted lines were inside a diff the agent reviewed. Cheap, unambiguous, and available today in git.
  • Hotfixes. A follow-up commit touching lines the agent saw, landing fast and outside the normal cadence. Noisier than reverts, and higher volume.
  • Incidents traced to a change. The strongest signal and the sparsest. If postmortems already name a culprit commit, you get this nearly free; if they do not, this row stays empty and you should say so.
State the limit before they state it for you

This is a lower bound with unknown coverage. It only counts defects that shipped and caused visible trouble and got traced back. Bugs caught by a human reviewer, by a test, or by the author, never appear. So the number to quote alongside it is traceability coverage — what fraction of your production incidents in the last quarter can be attributed to a specific merged change at all. For most teams that is well under half, and a recall proxy quoted without it is the kind of number that survives exactly one follow-up.

There is one more reason to put a miss rate in the loop, and it is the reason to mention the 2025 DORA findings if the conversation turns to whether any of this matters. Across a survey year in which AI adoption in software teams reached around 90%, the consistent finding was that AI correlates with higher throughput and worse delivery stability: more change failures, more rework. The plausible cause is volume — code is generated faster than the review and deployment machinery can absorb it. Which means a code-review agent is a control surface on precisely the failure mode that is getting worse, and an agent optimised for a metric that rewards saying less is a control surface pointed the wrong way.

07

Audit the judge, because it decides how much data you need

The judge is the one component in this system that is itself a model, and a noisy labeller does something worse than add noise. It systematically shrinks every effect you are trying to detect — towards zero, always, regardless of which arm is better. That is not a footnote about rigour, it is the thing that decides whether your gate can see a real improvement at all.

Why noise shrinks effects rather than blurring them

Take a binary label — addressed or not — and a judge that flips the correct answer with probability e, independently and in both directions. If the true rate in an arm is p, the judge reports p(1−e) + (1−p)e. Subtract two arms and everything cancels except one factor:

observed difference = true difference × (1 − 2e) e = the judge’s per-label error rate (1 − 2e) = the fraction of your real effect that survives

The mistake is easy to make in the other direction: you do not get an inflated effect or a random one. A 10 percentage-point real improvement, measured by a judge that is wrong 15% of the time, shows up as 7 points. Nothing in your dashboard says this happened. And because the noise also widens the confidence interval, you need more samples to establish a smaller-looking number — the penalty compounds, and it compounds quadratically.

Attenuation under symmetric independent label noise. The right-hand column is the extra data you need to detect the same true effect at the same power, which scales as 1 ÷ (1−2e)². At a quarter wrong, you are running a four-times-longer experiment to see half the effect.

The highlighted row is not arbitrary. A 2026 reliability study repeated identical evaluations on the same questions — same judge, same prompt, same inputs — and found that pairwise preferences “flip on average 13.6% of the time, with 28% of questions exceeding a 20% flip rate and one question reaching 56%”. If you model those flips as independent noise, a 13.6% disagreement between two draws implies a per-label error around 7%, which is the row above. Treat that as an order of magnitude rather than a measurement of your system — it is a different task on different models — but treat the method as the one to copy: call your judge twice on the same input and count how often it contradicts itself. It is the cheapest diagnostic in this entire guide and almost nobody runs it.

The failure that is worse than noise

Everything above assumes the judge’s errors are unrelated to which version produced the comment. When they are not, attenuation turns into bias, and bias does not shrink your effect — it manufactures one. If version B writes longer, more explanatory comments and the judge prefers longer text, B wins your gate on a property that has nothing to do with whether anyone acted on it. The same study found a significant first-position effect (72% A-majority, p = 0.024), cross-judge agreement of only “76% (κ = 0.51)”, and that “semantically equivalent prompt templates change majority outcomes in 25% of tested cases”.

The defences are mechanical and you should list them as a checklist rather than a caveat: blind the judge to which version produced the comment; randomise presentation order and average both orderings; control for length explicitly; and prefer the narrow labelling task — did these lines change — over any open scoring rubric, because a question with a visible answer in the diff leaves much less room for style to leak in.

What to actually report about your judge

  • Agreement with humans on a frozen calibration set. A few hundred comments, labelled once by people, kept forever. Report Cohen’s κ, not raw agreement — with three classes and one dominant class, raw agreement flatters everything.
  • Self-consistency. The repeated-call flip rate. This is your e, and it is what sets your sample sizes.
  • Sensitivity. Re-run with the prompt reworded and the order swapped, and report how often the majority verdict moves.
  • Version pinning. The judge model and its prompt are part of the measurement apparatus. Pin them like a schema, and when you change either, re-score the frozen set and publish the delta — because every historical comparison you have is denominated in the old judge.
08

From evidence to edits, and the edit nobody proposes

Now the loop closes. You have labelled comments, an incremental estimate, a miss rate and a judge you can quote an error bar for. Turning that into skill changes is four steps, and the fourth is where most teams quietly stop.

  1. Aggregate before you conclude

    One PR is an anecdote. Feed a few thousand labelled comments to a reasoning model and ask it to cluster the ignored and pushed back ones into named failure modes. The output should read like: suggestions that contradict repo conventions get ignored; nits on generated files get dismissed; missing-test flags get fixed. Each cluster needs a count and a handful of verbatim examples attached, because the next step is a human reading it.

    Cluster the accepted ones too. They tell you which sections of the file are load-bearing, and you need that before you start cutting.

  2. Propose a diff, not a rewrite

    Bounded edits — add a rule, delete a section, move rarely-fired guidance into a references/ file that loads on demand. The current optimiser work on skill documents does exactly this: a separate model turns scored rollouts into “bounded add/delete/replace edits on a single skill document”, and an edit is “accepted only when it strictly improves a held-out validation score”.

    The reason is not neatness. Repeated full rewrites of a context document have two documented pathologies: brevity bias, where each pass drops domain detail in favour of a cleaner summary, and context collapse, where iterative rewriting erodes specifics over time. A diff is also the only form a human can review in two minutes, which is what makes step 3 survive contact with a real team.

  3. A human approves, and the skill is versioned like code

    The agent proposes from evidence; the person edits for intent. That division matters because some of what is in the file is not a claim about the world at all — it is policy somebody decided, and policy does not get overruled by an acceptance rate. The review that catches this is a human one.

    Version it in the repo, with a changelog entry per edit naming the cluster it came from. Then a regression six weeks later is a git log, not an investigation.

  4. Gate every version — in two stages, against three arms

    Offline replay first, because it is cheap and it kills obvious regressions. Re-run the new version over held-out PRs and diff what it would post against what the current version posts. This tells you volume, overlap and what changed — and nothing about human behaviour. Use it to triage, never to decide.

    Then a live canary on a slice of real PRs, with three arms: the new version, the current version, and no skill at all. The third arm is the one teams drop, and it is the only one that can tell you the file is not worth its tokens.

Why offline replay cannot be the gate

The Google numbers from section 03 are the cleanest statement of this you can quote. Offline, the system “addresses 52% of comments with a target precision of 50%”. In production, authors address “7.5% of all reviewer comments” by applying a suggested edit. The model is identical in both. What sits between them is a human funnel — and the single largest lever turned out to be the preview rate, which rose from about 20% to about 40% on a UX change and roughly doubled the fraction of comments resolved this way.

No offline metric would ever have surfaced that. Replay tells you what the agent would post. Only production tells you what a person would do.

The loop has to be able to output “delete”

The same 2026 production study that gave us ρ = 0.14 ran paired live trials with and without each skill across 145 real skills and 947 scored pairs, and reports a mean composite skill lift of 0.213495% CI 0.1967–0.2301, with composite lift positive in “72.8% of paired cases”.

Read the second figure rather than the first. Skills help on average and roughly one paired case in four does not come out positive. Those cases exist in your repository too, and no amount of editing will fix a file whose problem is that it should not be loaded. If your feedback loop has no path to removal, it will spend the rest of its life generating reasons to keep every file it has.

Pre-register the kill condition

Before the canary starts, write down the number that ends it: if incremental addressed-comments-per-PR against the no-skill arm sits inside ±1 point after 1,500 PRs, the skill is retired. Pick the band and the sample before you see the data, because an ablation you would not act on is not an experiment, it is reassurance.

Retirement is also not binary. The cheap middle move is demotion: cut the body down to the rules that actually fire, push the rest into references/, and keep only the description in the system prompt. That recovers most of the context cost while keeping the coverage.

The real bug: the file has nowhere to record any of this

Guide 0008 ended on a missing frontmatter field — provenance, because a guess and a measurement are the same file type. This question is the other half of that same gap. A skill that has been running in production for six months has a history: what it was measured against, by which judge, on how many PRs, and when that decision expires. There is nowhere to put it, so it lives in a dashboard nobody opens or in the head of someone who has since changed teams.

--- name: code-review-python description: Review Python diffs for correctness and repo conventions # where it came from — guide 0008 provenance: curated authored_by: platform-eng, 2026-03-02 # what it has done since — this guide metric: addressed_per_pr # denominator pinned externally counterweight: escaped_defects on reviewed lines holdout: 4% ghost comments, generated and logged, not posted judge: judge-model-2026-07 @ t=0, 3-vote majority judge_audit: kappa 0.61 vs 412 human labels; self-flip 6.1%; 2026-08-14 vs_no_skill: +3.8 addressed/PR [+1.1, +6.4] n = 1,840 PRs incremental: +22pp over ghost baseline decided: keep, 2026-08-20 review: 2026-11-20, or on any judge change ---

Two things fall out of writing it down that are hard to get any other way. The claim acquires an expiry, so staleness has a deadline instead of waiting for an incident. And the numbers arrive with their intervals attached, which quietly ends the most common argument in this whole area — someone quoting a lift of “about four points” from a sample that could not have distinguished four points from zero.

09

Twelve follow-ups they will actually ask

These are ordered roughly as the conversation goes: the metric first, then causality, then the machinery, then the uncomfortable one at the end about what you would do with no budget and no instrumentation.

F1Why not just have a judge score the reviews? It is one afternoon of work.

Because it grades the wrong link in the chain. A judge scores how a comment reads, and a comment can read beautifully and be ignored by every author who sees it. There is no ground truth for “is this a good comment” that lives inside the comment.

The supporting evidence is that upstream instruments do not even agree with each other: in production skill evaluation, structural scanning and LLM-judge scoring correlate at ρ = 0.14. Both claim to measure quality, and they are measuring different things, neither of which is an outcome. Judges are still useful — but for the narrow, checkable labelling job in section 03, not as the arbiter of quality.

F2Concretely, what is the label and who produces it?

Three classes per comment — addressed, ignored, pushed back — decided by a judge that sees the comment and the diff that followed it. The decision is anchored to lines, not to sentiment: did the lines this comment pointed at change, after it was posted, in a direction consistent with what it asked for?

Two cheap guards that catch most of the errors. Enforce timestamp ordering, or you will label comments as addressed that arrived after the fix. And hold out a frozen human-labelled calibration set, a few hundred comments, to quote a κ against.

F3Acceptance rate is gameable. How do you stop it?

You cannot fix it in place, because the problem is structural: the denominator is chosen by the thing being measured. So do two things. Pin the denominator externally — addressed comments per PR, or per hundred changed lines, so raising the threshold reduces the score instead of raising it. And pair it with a quantity that only gets worse when the agent says less, which is escaped defects on reviewed lines.

The framing to offer is operating point versus capability. Raising a confidence threshold moves along the curve; a better skill moves the curve. A single ratio cannot tell those apart, and it will always find the cheap one first.

F4How do you know the comment caused the change, rather than coinciding with it?

You do not, without an intervention, so I would run one: ghost comments. On a few per cent of PRs the agent generates normally, the system logs the comments and does not post them, and we watch whether those lines changed anyway. Posted fix rate minus ghost fix rate is the incremental number.

The reason this matters more than it sounds is the direction of the bias. The comments most likely to be marked addressed are the ones the author would have fixed regardless, so raw acceptance over-credits the obvious comments and under-credits the subtle ones — it is biased in exactly the direction that makes a low-value skill look good.

F5Your recall proxy only sees bugs that shipped and got traced. Is it worth anything?

It is a lower bound with unknown coverage, and it is worth something as long as I quote it that way. It misses every defect caught by a human, a test or the author. So I report it next to traceability coverage — what fraction of last quarter’s incidents can be attributed to a specific merged change at all — which for most teams is under half.

Its real job is not to be accurate. Its job is to be a term that cannot be improved by staying quiet, so that precision has something pulling against it. A directionally correct counterweight beats a precise metric that can be gamed alone.

F6How many PRs before your gate means anything?

It depends on three things and I would rather give you the mechanics than a number I made up: the baseline rate, the effect I care about detecting, and the judge’s error rate. The first two are the usual proportion-test arithmetic. The third is the one people forget — label noise attenuates the observed difference by (1−2e), so the sample needed scales as 1∕(1−2e)².

A judge that is wrong 15% of the time turns a real 10-point effect into a measured 7, and needs roughly twice the data to establish it. That is why I measure the judge before I size the experiment, not after.

F7You upgrade the judge model. What breaks?

Every historical comparison, silently. All your past numbers are denominated in the old judge, and judges disagree with each other a lot — published cross-judge agreement on general evaluation tasks runs around 76%, κ = 0.51, and merely rewording the prompt template flips the majority verdict in about a quarter of cases.

So the judge model and its prompt are pinned like a schema version, and they are part of what a skill version was measured against. On any change, re-score the frozen calibration set, publish the delta, and re-baseline anything still in flight. The failure mode to name out loud is a quiet judge upgrade that shows up as a skill regression nobody can explain.

F8The model proposes the edit and the eval approves it. Why keep a human in the loop at all?

Because some of what is in the file is not a claim about the world, it is a decision somebody made — a house convention, a security rule, a compliance requirement. Those are not overruled by an acceptance rate, and a purely evidence-driven optimiser will delete them, correctly by its own lights, because nobody acts on them.

There is a second reason, which is the one from guide 0008: if the proposer and the approver are the same process, the loop is closed inside the model and the evidence never crosses a boundary. The agent proposes from evidence; the human edits for intent. Auto-application is defensible only where the gate is executable rather than another model.

F9Why bounded diffs rather than letting the model rewrite the skill each cycle?

Two documented pathologies of iterative rewriting. Brevity bias: each pass drops domain-specific detail in favour of a tidier summary, so the most valuable lines — the ones that are specific and slightly awkward — go first. Context collapse: repeated rewriting erodes detail over generations until the file is a well-written generality.

A diff is also auditable in two minutes, which is the only reason a human approval step survives in a real team, and it makes the change attributable: this line exists because of that failure cluster. The current skill-optimiser work restricts itself to bounded add, delete and replace edits accepted only on a strict held-out improvement, for the same reasons.

F10Offline replay on held-out PRs says the new version is 8 points better. Do you ship it?

No — I promote it to the canary. Replay can only tell me what the agent would post, because the humans in the held-out PRs never saw the new comments and cannot respond to them. It is excellent for killing regressions cheaply and useless as a final decision.

The number I would put in front of you is Google’s: offline, their system addresses 52% of comments at a 50% target precision; in production, authors address 7.5% of all reviewer comments with a suggested edit. Same model. The gap is the human funnel — and the biggest single lever they found was the preview rate, which no offline metric contains.

F11Suppose the answer is that the skill does nothing. What then?

Then it gets retired, and I would have written the condition down before the canary started: if incremental addressed-comments-per-PR against the no-skill arm sits inside a pre-registered band after a pre-registered sample, the skill goes. Deciding the band afterwards is how every negative result turns into “let’s try one more edit”.

This is not hypothetical. In paired production trials across 145 real skills, composite lift was positive in 72.8% of paired cases — so roughly one in four did not clear the bar. And retirement has a middle setting worth taking first: demote the body into references/, keep the description, recover most of the context cost without losing the coverage.

F12You have one engineer and two weeks. What do you actually do?

Week one is the backfill, because the data already exists: walk six months of PRs, label every agent comment against the diff that followed it, and produce three things — the addressed rate, the failure clusters, and a κ against two hundred comments I label by hand. That is a real answer to “does it help” delivered by Friday, and it needs no deploy.

Day one of week one, in parallel, I turn on the two things with latency: the ghost-comment holdout and the no-skill arm. Neither produces a number for a month, and neither can be recovered retroactively, so every day of delay is a day the real question stays unanswerable. Week two is the clustering and the first diff.

The lesson underneath all twelve: a feedback loop that can only propose improvements is not an evaluation of the skill, it is an advocate for it. The loop is only real once it is capable of returning a number that deletes the file.

Glossary

Twenty-two terms. If you can define these without hedging, the follow-ups in section 09 have nowhere left to go.

skill
A document loaded into a model’s context to shape how it performs a task. Its description sits in the system prompt on every request; its body loads on invocation and stays for the run.
outcome signal
A record of something a human did in response to the system’s output. The only class of signal on this page that counts as evidence.
comment acceptance rate
Addressed comments divided by comments posted. Correct first metric, and unusable alone because the agent chooses the denominator.
denominator pinning
Replacing an agent-controlled denominator with a unit of work the agent cannot change — per PR, per hundred changed lines.
operating point
Where a system sits on its own precision-versus-volume trade-off, set by a threshold. Moving it changes both numbers and improves nothing.
capability change
An improvement that moves the whole trade-off curve rather than sliding along it. The only kind worth shipping.
Goodhart’s law
When a measure becomes a target it stops being a good measure. Here: any ratio whose denominator the optimiser controls.
precision
Of what the agent said, how much was acted on. Maximised by silence, which is why it never travels alone.
recall proxy
A stand-in for the defects the review missed, built from reverts, hotfixes and traced incidents. A lower bound with unknown coverage.
escaped defect
A bug that reached production on lines the review saw and did not flag. The counterweight term.
traceability coverage
The fraction of incidents that can be attributed to a specific merged change. The number that makes a recall proxy honest.
counterfactual
What would have happened without the intervention. “Addressed” is an observation; the counterfactual is what turns it into a causal claim.
ghost comment
A comment generated and logged but deliberately not posted, so the same lines can be watched for a fix that happened anyway. Borrowed from ghost ads.
incrementality
The effect attributable to the intervention: posted fix rate minus ghost fix rate.
holdout
The slice deliberately excluded from treatment so it can serve as the control. Cannot be reconstructed after the fact, which is why it starts on day one.
no-skill arm
The control condition that runs the agent with the skill removed. The only arm that can conclude the file is not worth its tokens.
label noise
Error in the judge’s labels. Under symmetric independent noise at rate e, observed effects shrink by (1−2e).
attenuation
That shrinkage. It always pulls towards zero, so it hides real wins rather than inventing fake ones.
Cohen’s κ
Agreement corrected for the agreement you would get by chance. Reported instead of raw agreement because one class usually dominates.
calibration set
A frozen, human-labelled sample kept forever, re-scored whenever the judge or its prompt changes.
offline replay
Re-running a new version over past PRs. Shows what the agent would post; cannot show what a person would do.
pre-registration
Writing the decision rule — effect band, sample size, date — before the data arrives. What stops a negative result becoming one more edit.
