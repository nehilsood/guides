The Orphaned Call

Your agent crashed, you resumed it, and the API rejected the whole conversation — every message individually well-formed. The history is not corrupted. It is half-written, and the difference is the entire answer.

The question

"Your long-running agent crashes mid-task. You resume from the saved history, and the API rejects the entire conversation. Nothing looks malformed. What invariant did you break, and how do you guarantee a crash can never put you here again?"

The one-sentence answer

An agent's message history is not a chat log, it is a transaction log with referential integrity. Every tool_use block carries an id, and the API requires exactly one tool_result carrying that id in the immediately following message. Your process died in the window between persisting the call and persisting its result, so you saved half a transaction — a debit with no credit. Nothing looks malformed because nothing is malformed; what broke is a relationship between two messages, and it fails validation identically on every retry.

00

What the interviewer is actually testing

This is a distributed-systems question dressed as an API question. It gives you a failure with no bug in it — no bad code, no malformed payload, no flaky network — and watches whether you reach for a retry or for an invariant. Four things are being checked at once.

Probe 1

Do you know the difference between transient and deterministic failure?

Retries exist for faults that change if you wait: throttling, timeouts, a bad node. A 400 from a validator is a pure function of the request body. Reaching for retries here is the single clearest signal that a candidate has not internalised the taxonomy, which is why the newsletter names it as the thing not to say.

Probe 2

Can you state the invariant precisely?

Not "tool calls need results" but the actual rule: one tool_result per tool_use id, in the very next message, all of a parallel fan-out together, results before any text. Precision here is cheap to demonstrate and impossible to fake.

Probe 3

Do you see the second, worse half of the problem?

Repairing the transcript makes the API accept it. It does not tell you whether the refund went through. A candidate who fixes the ledger and stops has fixed the visible failure and left the expensive one. The word idempotency should arrive unprompted.

Probe 4

"Guarantee" — do you flinch at that word?

The question asks how you guarantee a crash can never put you here again. Guarantees come from making the bad state unrepresentable, not from remembering to handle it. That means the commit boundary, a validator on the send path, and a repair pass on resume — three places, not one patch.

Do not say

"The history got corrupted, so I'd wrap the API call in retries."

This is wrong three times over, and each one is worse than the last. Factually: nothing is corrupted. Every byte you wrote is the byte you meant to write; open the file and each message is valid JSON with valid fields. What is missing is a row you never got to. Mechanically: the API will reject that exact history on every attempt for the rest of time, because validation is deterministic. A retry with backoff turns a 200 ms failure into a 30-second failure that still fails — and if a supervisor restarts the crashed agent, you now have a hot loop re-sending an invalid body and paying for the round trips.

Diagnostically: "corrupted" is a word that ends investigation. It says the data is untrustworthy and the recovery is to throw it away. The truth is the opposite — the data is entirely trustworthy and incomplete in a way you can name, locate and repair in about twenty lines. Reaching for "corrupted" means you never looked.

In plain words

A bank transfer debits one account and credits another. If the machine dies between the two, every row in the ledger is still a perfectly good row. Nothing is smudged, nothing is unreadable. The ledger is broken anyway, because a ledger is not a list of rows — it is a set of rows that must balance. Retrying the audit does not make it balance.

01

The answer, at three lengths

Lead with the invariant, not the crash. The crash is the boring half — every system crashes. What the interviewer wants in the first thirty seconds is the sentence that reframes the history as a transaction log, because everything else follows from it.

Say this — 30 seconds

"Nothing is corrupted — the history is incomplete, and it breaks a referential invariant rather than a format one. The model emitted a tool_use block with an id. I persisted that assistant message. The process died before the tool result was written. On resume the history contains a call with no matching result, and the API requires every tool_use id to be answered by a tool_result with the same id in the very next message. So every message is individually valid and the conversation is not.

That is why retries are the wrong instinct: validation is a deterministic function of the body, so the same history fails identically forever. This is a debit with no credit, not a torn page.

The fix is three layers. Atomic turn commits — the call and its result are one transaction, so a crash leaves me with both or neither. Repair on resume — if I find an orphan I don't delete it, I inject a synthetic tool_result with is_error: true saying execution was interrupted and the outcome is unknown, so the model checks real state before acting. And idempotency for side effects, keyed on the tool call id, because replaying get_weather is free and replaying issue_refund charges the customer twice."

The two-minute version, as beats

  1. Reframe first, in one sentence. "Agent history is a transaction log, not a chat log." Every other sentence you say depends on the interviewer accepting that frame, so spend the first breath on it.
  2. State the invariant exactly. Each tool_use carries an id; each needs exactly one tool_result with that id, in the immediately following message, with no message in between. For a parallel fan-out, all the results travel in that one message. Precision is the whole point of this beat.
  3. Locate the crash in the window, not in the code. There is an interval between "assistant turn persisted" and "tool result persisted." Any death in that interval produces an orphan. It is not a bug you can find by reading the file; it is a property of where your commit boundary sits.
  4. Kill the retry idea explicitly. Transient faults deserve retries; deterministic validation failures deserve repair. Say the distinction out loud, because the question is constructed to see whether you have it.
  5. Give the three layers. Atomic turn commit, repair on resume with an explicit error result, idempotency keys on every side-effecting tool.
  6. Then take the two extra steps most candidates miss. A validator on the send path, so an invalid history is caught locally with a message you wrote instead of a 400 you have to decode. And pair-aware compaction, because in practice summarisation orphans more turns than crashes do.
  7. Close on the honest limit. Atomic commits fix the ledger. They cannot fix the world: you cannot make a remote refund and a local disk write atomic. That is why layer three is not optional — it is the only layer that addresses the half you cannot roll back.
The one line worth memorising

"Agent history isn't a chat log. It's a transaction log. Every tool call id needs exactly one matching result, so I commit the call and its result atomically, repair orphans with explicit error results, and make every side-effecting tool idempotent."

In plain words

You wrote "paid Ravi £40" in your notebook and then the pen ran out before you wrote what Ravi gave you back. Every line in the notebook is legible. The notebook is still unusable as an account, because an account is a set of matched pairs. And crucially: you now also do not know whether Ravi actually got the £40. Fixing the notebook does not answer that question. Only asking Ravi does.

02

Fundamentals: the history is a ledger

The mental model almost everyone starts with is "a list of messages I append to." That model is correct for a chatbot and wrong for an agent, and this question exists to find out which one you are carrying.

In plain words

A chat log is a diary: each line stands alone, and losing the last line costs you the last line. A ledger is double-entry: each line references another line, and losing one line invalidates the pair. The moment your model can call tools, your diary became a ledger and nobody told you.

The id is a foreign key

When the model decides to call a tool it emits a block carrying an id — toolu_01A09q90qw90lq917835lq9 in Anthropic's shape, a tool_call_id in OpenAI's. When you answer it, your result block carries that same id in its tool_use_id field. That is a foreign key, and the API is running referential-integrity validation on every single request. Two things follow immediately, and saying both is what makes the answer sound like experience rather than reading:

  • The relationship is the thing being validated, not the row. There is no schema you could apply to a single message that would catch this. Validity is a property of adjacent pairs. This is exactly why "nothing looks malformed" — you are looking at rows to find a problem that only exists between them.
  • It breaks in two directions. An orphaned call is a tool_use with no result: the crash case. An orphaned result is a tool_result whose id no longer exists in any preceding assistant message: the compaction case, and in production the more common of the two. A candidate who names only the first has read the question; one who names both has debugged it.

The exact rule, in the two shapes you will meet

The invariant is the same everywhere; the message shape differs, and knowing that the shapes differ is a small detail that lands well.

The detail that catches people

A failed tool is not a missing tool. If your tool threw, timed out, or was denied, the invariant still demands a result block — you send one with is_error: true and a description of what happened. The model reads it and adapts, usually by retrying with corrections or by telling the user. Dropping the result because "it failed" is how well-intentioned error handling creates the exact bug in this question.

This is worth saying out loud in the interview, because it reframes the synthetic repair result in layer two as the normal mechanism used for its normal purpose, not a hack.

Why the API is strict about it at all

It would be easy to read the strictness as pedantry. It is not. The model is trained on a format where a call is always followed by its outcome, so a history with a dangling call is off-distribution — you are asking it to continue text of a kind it has never seen. Worse, the plausible completions are the dangerous ones: the most natural continuation of "I called issue_refund and then nothing happened" is to call it again. The validator is refusing to let you put the model in a state where its best guess is a duplicate side effect.

So the 400 is not the API being difficult. It is the API catching, at the boundary, a bug that would otherwise surface as a second refund three turns later.

03

The unsafe window

You cannot find this bug by reading code, because no line of code is wrong. It lives in the interval between two writes — so the way to see it is to lay out one turn on a timeline and ask, at each tick, what a kill -9 would leave behind.

Two hazards, not one, and they need different fixes

The window contains two separate failures that people habitually merge, and separating them is the strongest move available in this answer.

Hazard A — the record is half-written

You have a call with no result. The consequence is a 400 and an agent that cannot resume at all.

This one is entirely within your control, because both halves are your own storage. Move the commit boundary so the pair is written together and hazard A is gone by construction.

Hazard B — the world is half-changed

The refund may have gone out. The email may have sent. You have no record either way, because the record was the thing that died.

This one is not within your control. Your database and a third party's API cannot be committed atomically. No amount of transactional storage closes this hazard.

A candidate who only fixes hazard A gives a good answer. A candidate who names hazard B, says plainly that it cannot be solved by storage, and then reaches for idempotency and reconciliation as the only available remedies, gives the answer the question was written for. The newsletter calls idempotency "the hidden trap"; it is hidden precisely because fixing hazard A makes the symptom disappear.

The sentence that separates them

"Atomic turn commits guarantee the ledger is consistent. They guarantee nothing about the world. That is why idempotency isn't a third nice-to-have — it is the only layer that addresses the half I cannot roll back."

04

Why retries cannot help

The question plants a wrong answer on purpose, and it is a wrong answer that works almost everywhere else. Being able to say exactly why it fails here is worth more than the fix itself.

A retry is a bet that the failure is a function of something other than your request — load, a node, a network path, a rate limit, a clock. Wait, and the something changes. That bet is correct for the overwhelming majority of failures you meet in production, which is why retry-with-backoff is muscle memory.

Request validation is the exception, because a validator is a pure function of the request body. Same bytes in, same verdict out, forever. There is no load condition, no jitter, no second endpoint that will feel differently about a dangling foreign key. So the retry is not merely useless — it is a loop that burns time, tokens and pager attention while converting a one-shot failure into a sustained one.

The rule to state, because it generalises past this question

Retry transport faults. Repair semantic faults. If the error is a verdict on the content you sent, the only move that can change the verdict is changing the content. Put differently: a 4xx is feedback, a 5xx is weather.

The failure mode retries actually create

It is worth naming what happens if you do wire the retry in, because it is not "nothing." A crashed agent is usually under a supervisor — systemd, Kubernetes, a job runner — that restarts it. The restarted process loads the same poisoned history, sends it, gets a 400, retries three times with backoff, exhausts the budget, crashes, and is restarted. You have built a poison-pill loop: a permanently failing unit of work that consumes retry budget forever and, in a shared queue, starves the tasks that would have succeeded.

The remedy for a poison pill is the same in every queueing system that has ever existed: detect it, stop reprocessing it, and move it somewhere a human or a repair routine can look at it. Which is exactly what "repair on resume" is — a dead-letter path with an automated fix attached.

05

Four ways you get an orphan

The interview hands you the crash. Production hands you the other three far more often, and volunteering them is what turns a correct answer into a credible one.

The crash mid-turn — an orphaned call

The case in the question. You persisted the assistant turn at t2, died before t5, and resumed with a tool_use nobody answered. Frequency depends entirely on how long your tools run and how often your process dies: rare for a chat endpoint, routine for a multi-hour agent on preemptible capacity.

The same shape arrives without any crash at all, from cancellation: a user hits Ctrl-C, closes the tab, or fires a slash command while a tool is in flight. The tool call is recorded, the result never arrives, and the session is wedged from the next message onward.

Compaction and truncation — an orphaned result

By far the most common cause in the wild, and the one that fills issue trackers. Your history outgrows the window, so something trims it: a sliding window, a summariser, a "drop the oldest N messages" rule. It removes the assistant message containing the tool_use and keeps the user message containing the tool_result, because to a message-level trimmer those are two unrelated items. Now you have a result referencing an id that no longer exists anywhere.

The tell is that it fires late — the session works for an hour and then wedges the moment the window fills. That delay is why it is so often misdiagnosed as flakiness.

Truncated generation — a call that was never really made

The response hits max_tokens partway through emitting a tool_use block. You get a block with a name, an id, and arguments that are empty or half-parsed JSON. If you persist and execute that turn, you run a tool with the wrong arguments; if you persist it and don't execute it, you have an orphan.

The correct handling is neither: check stop_reason before you commit anything, and on max_tokens discard the partial turn and re-request the same prefix with a larger budget. This is worth raising unprompted because several SDK and proxy layers have shipped bugs that overwrite the stop reason with tool_use whenever a tool block was started — so the signal you need is the signal most likely to have been swallowed before it reached you.

Partial fan-out — the parallel trap

The model calls five tools in one turn. Four return quickly; the fifth hangs. You cannot send four results and add the fifth later, because the protocol requires the whole set in one message. So a single slow tool holds the entire turn hostage, and a single dropped result invalidates the request exactly as if none had run.

The consequence is a design rule, not a patch: in a parallel fan-out, every tool needs a timeout, and a timeout must produce a result — an is_error block saying it timed out. The unit of commit is the whole fan-out, so the unit of error handling has to be too.

What they all share

Every one of the four is the same root defect wearing different clothes: some component treated the history as a list of independent messages when it is a list of dependent pairs. The crash treats a write as independent. The compactor treats a message as independent. The truncation handler treats a block as independent. The fan-out treats a result as independent. Name that once and all four fixes become obvious — every operation on history must be closed over turns.

06

Ten minutes to a diagnosis

A likely follow-up is "a session is wedged right now, users are blocked, go." The answer is short, because this is one of the rare production failures you can diagnose completely without deploying anything.

Read the error body, not the status code

The 400 tells you which direction the invariant broke, and the two directions have completely different causes. "tool_use ids were found without tool_result blocks immediately after" means a call lost its answer — look at crashes and cancellations. "unexpected tool_use_id found in tool_result blocks" means a result outlived its call — look at whatever trims your history. Thirty seconds, and you have halved the search.

Run the pairing check over the stored history

It is twenty lines and it names the exact message index. Walk the messages, collect every tool_use id in each assistant turn, and assert that the next message answers precisely that set — no more, no fewer, in the right position.

# the whole diagnosis, as a function you will keep afterwards def violations(messages): out = [] for i, m in enumerate(messages): if m["role"] != "assistant": continue calls = {b["id"] for b in blocks(m) if b["type"] == "tool_use"} if not calls: continue nxt = messages[i+1] if i+1 < len(messages) else None if nxt is None or nxt["role"] != "user": out.append((i, "orphaned call", calls)); continue answers = [b for b in blocks(nxt) if b["type"] == "tool_result"] got = {b["tool_use_id"] for b in answers} if calls - got: out.append((i, "unanswered", calls - got)) if got - calls: out.append((i+1, "orphaned result", got - calls)) # position matters too: results must lead the content array if blocks(nxt) and blocks(nxt)[0]["type"] != "tool_result": out.append((i+1, "text before results", None)) # and a result with no call anywhere before it return out

Find the write that did not happen

With the index in hand, pull the timestamps around it. An orphan whose neighbours are seconds apart and whose process exited between them is a crash. An orphan that appears at the moment your token count crossed a threshold is compaction. An orphan whose assistant turn carries stop_reason: "max_tokens" is truncation. An orphan preceded by a user-initiated cancel is the interrupt case. Four causes, four distinguishing marks, all of them already in your logs.

Unwedge the session, then decide about the world

Repair the transcript so the user is unblocked — inject the synthetic error result and let the run continue. Then, separately and without rushing, work out whether the interrupted tool had a side effect and whether it fired. These are two different jobs on two different clocks, and conflating them is how a five-minute outage turns into a duplicate payment.

If you have nothing stored at all

Some stacks keep history only in memory and rebuild it from an event stream. That is fine, and the check is the same — it just runs over the reconstructed list. What is not fine is discovering at this point that you never persisted the raw assistant turn, only a summary of it. If you cannot reconstruct the exact blocks you sent, you cannot repair them, and the honest answer to "how long to fix" becomes "after I ship logging."

07

The fix, as five things that each stop something different

The newsletter gives three layers. Three is the right answer and it is not quite the whole one — two more steps cover the production causes from section 05, and the value of listing all five is being able to say what each one does not stop.

Commit the turn atomically

Stop treating "append a message" as the unit of persistence. The unit is the turn: an assistant message containing calls, plus the user message answering all of them. Two implementations, and the choice between them is more interesting than either.

Buffer and commit the pair. Hold the assistant turn in memory, run the tools, then write both messages in one transaction. Simple, and the history is never observably invalid. Its weakness is severe for side-effecting tools: if you crash at t3, you have no record that you were about to do anything, so you cannot even begin to reconcile.

Write-ahead log, then reconcile. Before executing, append an intent record — the call, its id, its arguments, its idempotency key, status pending. Execute. Append the outcome. On startup, scan for intents with no outcome: each one is a known unknown, which is a far better thing to wake up to than a silent gap. More machinery, and the only option that gives hazard B anything to work with.

stopsOrphaned calls from crashes and cancellations, permanently and by construction. does not stopAnything about whether the tool's side effect fired. The buffer variant actively hides it.

Repair orphans on resume — never delete them

On startup, run the pairing check. For every unanswered call, inject a tool_result with is_error: true and content along the lines of "Execution was interrupted before completion. Outcome unknown — verify current state before retrying." The history is valid again and the model has been told the truth.

Deleting the orphaned call also satisfies the API, which is exactly why it is the trap. Deletion rewrites history so that the model believes it never made the call — so its most likely next action is to make it again, confidently, with no idea a refund may be in flight. You would be using a repair to manufacture a duplicate side effect. Deletion also invalidates every cached prefix from that point on, which is a real cost on long sessions.

stopsThe 400. The wedged session. The poison-pill restart loop. does not stopA duplicate effect — unless the tool is idempotent, "verify state" is advice the model cannot act on.

Make every side-effecting tool idempotent

The hidden layer, and the one the question is really hunting for. Replaying get_weather costs a request. Replaying issue_refund costs a customer twice. So every tool that changes the world takes an idempotency key, and the tool call id is an excellent choice: it is generated upstream, it is unique, and — the part that matters — it is already persisted, so the same key survives the crash and comes back on replay.

Borrow the semantics wholesale from payments, where this was settled a decade ago: the first request under a key has its status and body stored and returned verbatim to every later request with that key, for a bounded retention window — Stripe's is 24 hours; a mismatch between the stored parameters and the new ones is an error rather than a silent overwrite. If the downstream service honours keys, pass yours. If it does not, keep a dedupe table on your side keyed on the call id and check it before dispatch.

stopsDuplicate effects on replay — the expensive half, and the half nothing else touches. does not stopUncertainty. You still do not know whether it ran; you have only made it safe to find out by trying.

Validate on the send path

The same twenty-line check from section 06, called immediately before every request. If it fails, you raise locally with the message index and the offending id instead of shipping a body you already know is invalid and decoding a provider's prose afterwards.

It is the cheapest item on this list and the one that changes the class of the bug: an invalid history becomes an assertion failure in your own code, at the moment it was created, with your own wording. It catches all four causes from section 05 including ones you have not thought of yet, and it costs microseconds against a call that takes seconds.

stopsEvery future variant of this bug from reaching production as a mystery 400. does not stopThe bug being created. It converts a remote failure into a local one — which is most of the value, and not all of it.

Make compaction pair-aware

Any transform that removes messages — summarising, sliding windows, dropping the oldest, clearing tool output to save tokens — must operate on turns, never on messages. If a tool_use goes, its result goes with it. If a result is replaced with a placeholder, the call stays so the model still knows what it did.

Anthropic's own server-side context editing is worth naming here, because it is the vendor conceding the point: the clear_tool_uses strategy clears tool results once context crosses a threshold, preserves block pairing while doing it, keeps the calls by default so the model still sees which actions it took, and only removes the inputs too if you explicitly ask. That shape is not an accident — it is the naive version's bug, fixed in the product.

stopsThe most common production cause: orphaned results from truncation and summarisation. does not stopCrashes, cancellations or truncated generations. Different half of the problem entirely.
How to deliver all five without listing

"Three layers plus two. Atomic turn commits so a crash leaves me both halves or neither. Repair rather than delete on resume, with an explicit error result, so the model knows the outcome is unknown instead of believing it never called. Idempotency keyed on the call id, because that is the only layer that covers the side effect. Then a validator on the send path, so any future version of this bug is a local assertion rather than a provider 400 — and pair-aware compaction, because in production summarisation orphans more turns than crashes do."

08

How you would prove it — and prove the fix

"Guarantee" is the word in the question, and a guarantee you cannot demonstrate is a hope. This is the half most candidates skip, and it is unusually tractable here because the failure is deterministic: a deterministic bug can be tested exhaustively rather than sampled.

The test that actually matters: kill at every write point

The unsafe window has a finite number of interesting instants, so enumerate them instead of guessing. Give your history layer a fault-injection hook, run one scripted turn with a tool that has an observable side effect, and abort the process at each point in turn. Then restart and assert.

Two things make this table the centre of the answer. The history column is always "valid" — that is what "guarantee" means, and it is checkable by the same twenty-line function, which is why writing that function pays for itself three times. And the side-effect column is deliberately not always "exactly 1": aborting during execution genuinely leaves you unable to know, and the assertion that matters is never 2. Writing "0 or 1, never 2" in a test table is a more honest claim than "exactly once", and a more defensible one.

The property test, for the histories you did not think of

The crash matrix covers the cases you enumerated. Generate random histories — parallel fan-outs, errors, text interleaved with calls, nested sub-agent turns — apply a random mutation from the four causes in section 05, and assert that repair(history) always produces something the validator accepts and that repair is idempotent, so repair(repair(h)) == repair(h). That second property is easy to get wrong and unpleasant when you do: a repair pass that appends a fresh error block each time it runs will quietly grow a history by one message per restart.

The regression test the compaction bug needs

Take a long real history, run your compactor at a range of target sizes, and assert the output validates at every one. This catches the whole class, including the case where a summariser happens to be correct at 50% reduction and wrong at 80%.

What to watch in production

  • Orphans repaired on resume, as a counter. Not zero — crashes happen — but a step change means something upstream started producing them.
  • Send-path validation failures, which should be zero and are the alarm that a new code path is mangling history.
  • Idempotency-key collisions that returned a stored response, which is your direct measurement of how often replay is actually happening.
  • Interrupted side-effecting calls awaiting reconciliation, with an age. This is the queue that must not grow, and it is the one a finance or support team will eventually ask you about.
The framing for the whole section

"The failure is deterministic, so I can test it exhaustively rather than statistically. There are six interesting instants in a turn. I abort at each one, restart, and assert two things: the history always validates, and the side effect never happens twice. That second assertion is the one I would put in the deploy gate."

Twelve follow-ups, with answers

This is where the interview actually goes. Each answer is written as something you could say, not as notes to yourself.

F1

A production session is wedged right now and the user is blocked. You have ten minutes. Go.

"Read the error body first — it tells me which direction broke, and the two directions have different causes. Then run the pairing check over the stored history to get the exact message index. Then repair: inject an is_error result for any unanswered call, save, and let the run continue. That unblocks the user, and it is the whole of the urgent work."

"What I would not do in those ten minutes is decide what happened to the side effect. If the interrupted tool was issue_refund, that question needs the payment provider's records, not my guess, and it is not on the same clock as unblocking a session. I would flag the call id into a reconciliation queue and come back to it. Merging those two jobs under time pressure is how you turn an outage into a double payment."

F2

Why not just delete the orphaned tool_use? It is one line, and the API accepts the result.

"Because it is a lie that the model will act on. Deleting rewrites history so the model believes it never made the call. Its most natural next move is to make it again — and it will do so confidently, because from its point of view nothing has been tried. I would have used a repair to manufacture the duplicate side effect I was trying to avoid."

"The synthetic error result costs the same one line and says something true: this was attempted, it was interrupted, the outcome is unknown, check before you act. That is information the model can use — it will typically look up the order status before refunding again, which is exactly the behaviour I want. There is also a cheaper reason: deleting a message in the middle invalidates every cached prefix after it, so on a long session I pay for the whole history again."

"Deletion is a legitimate tool in one place — pair-aware compaction, where I remove the call and its result together and I am deliberately shortening the record. That is a different operation from erasing one half of a pair."

F3

Your synthetic result says "outcome unknown." Isn't that just passing the buck to the model?

"It is delegating, and it is delegating to the only component that can do anything useful with it. I genuinely do not know whether the tool ran — that is not a gap in my engineering, it is the actual epistemic state after a crash mid-call. Writing anything more definite would be fabricating."

"What makes the delegation work is that I pair it with a way to find out. The error content should not just say 'unknown', it should say what to do: 'call get_refund_status(order_id) before retrying.' Now the model has a cheap, read-only route to ground truth, and models are good at taking that route when it is offered. If the tool has no such route — a fire-and-forget email send, say — then the model cannot resolve it either, and the honest design is to escalate to a human rather than pretend."

"And it is not an exotic mechanism. is_error results are the normal way a failed tool is reported; the model is trained to handle them. I am using the documented path for exactly what it is for."

F4

Make the turn commit actually atomic. Your history is in Postgres and the tool hits a third-party API.

"I can't, and I would say so immediately, because pretending otherwise is the trap. There is no atomic commit spanning my database and someone else's API — that is a distributed transaction, and even with two-phase commit the remote side would have to participate, which a payments API is never going to do. So the honest goal is not atomicity across the boundary, it is recoverability across it."

"Concretely, the write-ahead variant. Inside one Postgres transaction I write the assistant turn and an intent row: call id, tool, arguments, idempotency key, status pending. Commit. Then dispatch. Then a second transaction writes the result and flips the intent to done. A crash anywhere leaves exactly one of three states, all of them recoverable: no intent — nothing happened; intent pending — may or may not have happened, reconcile it; intent done — it happened. The bad state, 'something happened and there is no trace', is the one I have made unrepresentable."

"This is the outbox pattern with a reconciliation loop instead of an ordering guarantee, and the same shape you would use for any effect that escapes your transaction boundary. If the team is already running a durable execution engine, I would let it own this rather than hand-roll — but the engine provides the same three states, it does not conjure a cross-system transaction either."

F5

Parallel tool calls. Five go out, four return in 200 ms, one hangs for ten minutes. What do you commit?

"Nothing, until the set is complete — which is the constraint the protocol imposes rather than a choice I am making. All the results have to arrive in one message, so partial commits are not expressible. That makes the slowest tool the latency of the turn, and it makes a hung tool an indefinite hang of the entire agent."

"Which means timeouts are load-bearing, not hygiene. Every tool in a fan-out gets a deadline, and a deadline that fires must produce a tool_result with is_error saying it timed out — not an exception that drops the block. So the turn commits at the deadline, with four real results and one explicit failure, and the model decides whether to retry that one call, proceed without it, or tell the user. Those are all reasonable, and the model can only choose if I told it."

"Two refinements if it matters. Give the deadline per-tool rather than per-turn, because a database read and a web crawl do not deserve the same budget. And if a genuinely long tool is a real requirement, do not model it as a blocking call at all — return a handle immediately and add a check_status tool, which turns a ten-minute hang into two fast turns the agent can interleave with other work."

F6

Your idempotency key is the tool call id. On resume the model regenerates the call and gets a new id. Now what?

"That is the sharp edge in the whole design, and it is worth being precise about when the id works and when it doesn't. The call id is a perfect key for replaying a persisted call — I crashed after dispatch, I still have the row, I re-dispatch with the same key, the downstream deduplicates. That covers my own retry path completely."

"It is the wrong key for a regenerated call, because a new id is a new key and deduplication silently stops working. The model deciding to call issue_refund again after seeing my interrupted-result is a new intent as far as the key is concerned, even though it is the same real-world action."

"So the key has to be derived from the intent, not the message. For anything with real money attached I would key on something semantically stable — refund for order 8812, or a hash of (tool name, canonicalised arguments, task id) — and keep the call id as the key only for the mechanical replay path. The general rule: a key generated by the model protects you from your own retries; a key derived from the operation protects you from the model's. And where neither is available, the guard is not a key at all, it is the read-only status check before acting — which is why the repair message points at one."

F7

Compaction is the real-world cause. How do you shorten a long history without breaking the invariant?

"Operate on turns, never on messages. A turn is the assistant message plus the user message answering it; that is the atom. Anything a compactor removes, replaces or summarises has to be a whole number of turns."

"In practice I would do it in that order of aggression. First, replace old tool results with short placeholders but keep the calls, so the model still knows what it did and the pairing survives — that is where almost all the tokens are, and it is the cheapest thing that works. Then drop whole old turns, both halves together. Only then summarise, and a summary replaces a contiguous run of complete turns with a single message, never splits one."

"Anthropic ships this server-side now, which I would point at as confirmation rather than as the whole answer: the tool-clearing strategy fires at a token threshold, preserves block pairing, and keeps the calls unless you explicitly ask it to clear inputs too. That shape is the naive compactor's bug already fixed. And whichever route I take, the send-path validator runs afterwards — compaction is exactly the code most likely to reintroduce this, so it is the code I least want to trust."

F8

The response came back with stop_reason: "max_tokens" partway through a tool_use block. What do you persist?

"Nothing from that turn. A truncated tool call is not a tool call — the arguments are partial JSON or empty, so executing it means running a real tool with wrong inputs, and persisting it without executing means an orphan. Both bad, and the third option is clean: discard the partial assistant turn and re-request the same prefix with a larger max_tokens. The prefix is unchanged, so it is a cache hit and cheap."

"The thing I would flag is that this depends on a signal that is easy to lose. Several SDKs, proxies and format translators have shipped bugs where any started tool block overwrites the stop reason with tool_use, so a truncated generation is reported as a completed call and you execute it with empty arguments. So I check stop_reason before I commit anything, and I would add a cheap belt-and-braces assertion: if a tool call's arguments fail schema validation, treat it as a truncation candidate rather than dispatching it."

"The same care applies to pause_turn on long server-tool runs — there the correct move is the opposite, append the assistant content unchanged and continue, and the documented mistake is fabricating an empty client result to fill the gap. Both are cases of 'the turn is not finished', and both go wrong when code assumes every response is a complete turn."

F9

Why hand-roll any of this? Use Temporal, Restate or a checkpointing framework and move on.

"For a long-running agent I probably would, and I would say why in one sentence: durable execution gives me the crash-consistency and the replay semantics for free, which is layers one and two done properly by people who do only that. Checkpoint after each step, replay the event history on recovery, and completed steps are not re-executed."

"What I would not do is treat it as the end of the conversation, because the guarantee has a specific edge. The engine gives exactly-once semantics for workflow steps, by replaying its own history. Activities that touch the outside world are at-least-once by default, and they have to be: when a network call times out, the caller cannot know whether the far side committed. No engine can close that, because the uncertainty is in the network, not in the engine. So idempotency keys and reconciliation stay my job either way."

"And there is a fit question. These engines want deterministic workflow code, and an agent loop calling a nondeterministic model is a slightly awkward guest — the usual pattern is to push every model call into an activity so its output is recorded and replayed rather than regenerated. Worth knowing before you adopt. If the agent is short-lived and in-process, the WAL-and-reconcile pattern is a few hundred lines and no new infrastructure, and I would start there."

F10

How do you test this? "Crash it" is not a test plan.

"Three tiers. The crash matrix first: a fault-injection hook in the history layer, one scripted turn with an observable side effect, abort at each of the six interesting instants, restart, and assert the history always validates and the effect never fires twice. Six deterministic tests, and the failure is deterministic so they are not flaky."

"Then a property test for the histories I did not enumerate — generate random histories with fan-outs, errors and interleaved text, apply a random mutation from the four known causes, and assert that repair always yields something the validator accepts and that repair is idempotent. That second property matters more than it sounds: a repair that appends a fresh block every run grows the history by a message per restart, and you only notice weeks later."

"Then a compaction regression: take a long real history, compact it at a spread of target sizes, assert validity at every one. That is the tier that catches the cause that actually fires in production."

F11

What does all this cost, and when would you not do it?

"The layers are not equally priced, so I would not buy them as a bundle. The send-path validator is microseconds against a call that takes seconds — I would put that in any agent on day one, including a prototype, because it costs nothing and converts a mystery into a message. Pair-aware compaction is free too; it is a constraint on code you were writing anyway."

"Atomic turn commits cost a schema change and some care around the transaction boundary. Worth it the moment the agent runs long enough to be worth resuming — if a crash means 'start over' and nobody minds, there is no orphan to repair because there is no resume."

"Idempotency is the expensive one and the only one with a real scope question, because it is not a change to my agent, it is a change to every tool and sometimes to services other teams own. So I would scope it by blast radius rather than apply it uniformly: read-only tools need nothing, cheap-to-repeat writes need nothing, and the small set that moves money, sends messages to humans, or provisions resources gets a key and a reconciliation path. In most agents that set is under ten tools, and naming it is a half-day of thinking that saves an incident."

F12

The tool was issue_refund. On resume you genuinely cannot tell whether it ran. What do you actually do?

"Ask the system that knows. Almost every side effect worth worrying about leaves a record somewhere I can query — the payment provider has the refund, the mail service has the send, the cloud API has the resource. So the first move is a read-only reconciliation query keyed on my own reference: did a refund for order 8812 land in the window between my intent row and now? That is why the intent row carries a timestamp and a business reference, not just the call id."

"If the answer is yes, I write the outcome, repair the turn with a result saying it succeeded, and the agent proceeds correctly. If no, I re-dispatch under the same idempotency key, which is safe by construction. Either way the uncertainty is resolved by evidence rather than by guessing, and that is the whole design goal — not to avoid uncertainty, which is impossible, but to make sure every uncertainty has a cheap way to be settled."

"And if there is genuinely no way to check — a fire-and-forget call with no read path — then I would not let the agent decide. It goes to a human queue with the full context. That is not a failure of the design; it is the design telling the truth about a tool that should never have been fire-and-forget. The lesson I would take back to the tool authors is that every side-effecting tool needs a read-only twin, and that requirement belongs in the tool review, not in the incident."

Glossary

Every term above, in one line each. If you cannot define these cold, the follow-ups will find it.

Orphaned tool call
A tool_use block whose id is never answered by a tool_result. The crash direction of the invariant break.
Orphaned tool result
A tool_result whose tool_use_id refers to a call no longer present. The compaction direction, and the more common one in production.
The invariant
Exactly one tool_result per tool_use id, in the immediately following message, all of a parallel set together, results before any text.
Referential integrity
The database property that every foreign key points at a row that exists. The tool call id is a foreign key; the API validates it on every request.
Transient vs deterministic failure
Transient depends on time or infrastructure and deserves a retry. Deterministic is a function of the bytes you sent and deserves a repair.
Poison pill
A unit of work that fails permanently and is retried forever, consuming budget and starving healthy work. What an unrepaired history becomes under a supervisor.
Unsafe window
The interval between persisting a tool call and persisting its result. Its width is the duration of your slowest tool.
Atomic turn commit
Making the assistant call and its results one unit of persistence, so a crash leaves both or neither.
Write-ahead log
Recording the intent to act before acting, so recovery can distinguish "never started" from "may have finished". The oldest fix in this family.
Intent record
The row a WAL writes before dispatch: call id, tool, arguments, idempotency key, status. A pending one is a known unknown.
Idempotency key
A caller-supplied identifier that lets a service recognise a repeat of the same operation and return the first result instead of performing it again.
Reconciliation
Querying the system of record to discover whether an effect actually occurred, rather than inferring it from your own logs.
Read-only twin
For every side-effecting tool, a cheap query that reveals whether the effect happened. Without one, an interrupted call cannot be resolved by anybody.
Compensating action
An operation that undoes an effect you cannot roll back — a credit against a charge. The saga alternative to a transaction.
Outbox pattern
Writing an effect's intent into your own transaction and dispatching it separately, so the intent and your state commit together.
Durable execution
An engine that persists workflow state after every step and replays history on recovery, so completed steps are not re-run. Temporal, Restate, DBOS, Inngest and framework checkpointers.
At-least-once
The delivery guarantee any external call actually has: a timeout leaves the caller unable to know whether the far side committed.
is_error
The flag on a tool_result that reports a failed execution to the model. The normal error path, and the mechanism orphan repair borrows.
Context editing
Server-side clearing of old tool output at a token threshold. Anthropic's strategy preserves block pairing by design.
pause_turn
A stop reason meaning the server paused a long turn. You continue by appending the assistant content unchanged — never by fabricating a tool result.
