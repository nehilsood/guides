Senior AI Engineer / Interview prep — Question 2

The 41‑Way Decision

You added forty skills and success went down. The interviewer has already told you it isn't tokens. Here is what actually broke, why the obvious fix makes it worse, and the six experiments that prove it.

00

The question, and what it's really testing

Read the trap before you answer

The interviewer asks

“You gave your coding agent 40 carefully written skills to make it smarter, and task success went down. Each skill description is only a few lines, so it's not a context-budget problem. What's actually breaking, and how would you prove it?”

Two sentences in that question are doing all the work, and most candidates walk past both.

“It's not a context-budget problem.” They have pre-emptively deleted the easy answer. If you reply “trim the descriptions” or “you're blowing the context window,” you have answered a question they explicitly did not ask. That is the single fastest way to fail this round.

“How would you prove it?” This is half the question, and it is the half that separates a senior engineer from a well-read one. Anyone can name a plausible cause. They want to know whether you can design an experiment that distinguishes your cause from the three other plausible ones.

What they are actually probing

  • Do you know what a skill is at runtime — not what the docs say it is?
  • Do you understand that adding a capability is not free even when it is cheap to store?
  • Can you tell the difference between choosing wrong and doing wrong?
  • Do you know that loaded instructions have power over the model, and that nobody unloads them?
  • Can you turn “the agent seems confused” into a number with a confidence interval?

Do not say

“Too many tokens in the system prompt — trim the descriptions.” They ruled it out. Worse, it is backwards: shorter descriptions are harder to tell apart, so trimming makes selection less accurate. You would be prescribing the disease.

Also avoid: “the model just isn't good enough at tool use,” “use a bigger context window,” and any answer that jumps to a fix without a measurement plan.

01

The answer, at three lengths

Memorise the 30-second one; the rest is scaffolding

The 30-second answersay this first

“Nothing broke in storage. It broke in selection and in commitment.

Forty skills means the agent runs a 41-way decision — forty skills plus 'none' — on every single turn. That decision gets harder not because of token count but because of overlap: each new skill that sounds like an existing one shrinks the gap between the right answer and the nearest wrong one. And short descriptions make that gap smaller, not bigger.

Then the second failure: choosing is not free. Opening a SKILL.md injects a few hundred lines of imperative text into context. The model follows it. Nothing unloads it. So one wrong pick doesn't cost you one turn, it steers the rest of the session.

To prove it I'd do three things: sweep the number of exposed skills against a token-matched inert control, to show it's decision load and not context; run selection-only evals with a gold label per task, to split routing error from execution error; and force-load an irrelevant skill onto tasks the agent already passes, to isolate hijacking with selection held constant.”

The two-minute version — the shapeif they let you keep going
  1. Reframe the cost. Skills have three costs: storage (cheap, and they've ruled it out), decision (a discrimination problem that scales with confusability), and commitment (a loaded skill is standing orders, not a reference page).
  2. Name break #1 — selection. Confusability, not count. Pairwise collisions grow roughly with N², attention splits between near-duplicates, and list position biases the pick.
  3. Name break #2 — hijacking. The load is a state change. Recent, imperative, un-removable text out-competes a task description from twenty turns ago.
  4. Show the symptom map. Three distinct observable failures: false triggers, wrong picks, and thrash. Each has its own metric and its own fix.
  5. Lay out the proof. Six experiments, in dependency order, with the controls that kill the rival explanations.
  6. Fix it by leverage. Retrieve instead of expose; write for contrast instead of brevity; merge the duplicates the confusion matrix hands you; scope loads; gate the library with an eval in CI.

The line that lands

“You didn't give the agent forty capabilities. You gave it a forty-one-way exam question it has to re-sit on every turn, and a rulebook it can't put down.”

Say it out loud · about 75 seconds

The three above are written answers. This one is a script — four beats, short lines, built to be said. A spoken answer to “you gave your coding agent 40 skills and task success went down. What’s breaking, and how would you prove it?” Read it aloud, then say it again with the page covered.

  1. Situation

    We added forty skills to make the coding agent smarter, and task success went down.

    Each description is a few lines, so it isn’t a context-budget problem.

  2. Mechanism

    Two things broke, not one.

    Selection: every turn is now a forty-one-way decision, and short descriptions make it worse rather than better — brevity strips the contrast the model needs to tell two neighbours apart.

    Hijacking: loading a skill is a state change. Its instructions are imperative, recent, and they never unload, so they keep steering turns they have nothing to do with.

  3. What I did

    I’d settle it with a token-matched inert control first — forty skills of identical length that do nothing. If success still drops, it was never the budget.

    Then a confusion matrix over selections to find the pairs worth merging, and retrieval instead of exposure, so the agent chooses between five candidates rather than forty-one.

  4. What it cost

    Retrieval adds a hop and it can miss. And writing for contrast makes descriptions longer, which is the opposite of everyone’s instinct — it’s still the right trade.

02

Fundamentals: what a skill actually is at runtime

You cannot diagnose this without the three layers

A skill is not a function the model calls. It is a folder of instructions the model can choose to paste into its own context. Under progressive disclosure it arrives in three stages:

Level 1
Name + descriptionIn the system prompt from turn zero, for every installed skill. This is the menu.
always loaded
~20–50 tokens each
Level 2
The body of SKILL.mdLoaded only when the model decides this skill applies. Injected into the conversation as instructions to follow.
on demand
hundreds–thousands
Level 3
Linked files, scripts, referencesRead only if Level 2 tells the model to read them. Can include executable code.
on demand
unbounded

In plain words: Level 1 is the table of contents. Level 2 is the chapter. Level 3 is the appendix. The agent reads the table of contents on every turn and decides whether to open a chapter.

Here is the observation the whole answer hangs on:

The pivot

The layer that is cheap and the layer that is dangerous are different layers.

The interviewer's “only a few lines” is a statement about Level 1. It is true, and it is irrelevant. The damage happens at the decision boundary between L1 and L2 — a 41-way choice repeated every turn — and inside L2, where a few hundred lines of imperative prose start governing the agent's behaviour.

Three costs, only one of which they ruled out

CostWhat it isScales withRuled out?
StorageTokens occupied by L1 descriptionsN × description lengthYes — by the premise
DecisionAccuracy of an (N+1)-way choice, every turnConfusability — roughly N² pairwise collisionsNo
CommitmentBehavioural drift once L2 is in contextForcefulness × persistence of loaded textNo

When you say this out loud in the interview, say the table. It is the cleanest possible demonstration that you heard the constraint and worked around it rather than ignoring it.

03

Break #1 — Selection. It's confusability, not count

Why forty good skills beat eight only in theory

Every turn, the agent solves a classification problem: given what the user just said and everything that has happened, which of these forty-one options applies? Forty skills, plus the option of none.

That problem does not get harder in proportion to N. It gets harder in proportion to how much the options sound like each other.

The quantity that actually matters: margin

For any given task, the model produces something like a score for each skill. What determines whether it picks right is not the score of the correct skill — it's the gap between the correct skill and the best wrong one. Call it the margin.

In plain words: it doesn't matter how good the right answer looks. It matters how much better it looks than the runner-up. Add a skill that sounds like an existing skill and you have just promoted the runner-up.

This is why the arithmetic is worse than it looks. Going from 39 skills to 40 adds one option, but it adds 39 new pairs that could be confused. Collision opportunities grow roughly with N². And the way a real library grows — someone writes debug-failing-test, someone else later writes fix-flaky-test — guarantees the new ones land near the old ones. You are not sampling uniformly from concept space. You are clustering.

A confusability map of six skills

What the published numbers look like

Three mechanisms behind the numbers

1 — Attention splits between near-duplicates

Attention is a softmax over the whole context. Two descriptions that occupy nearly the same semantic region divide the probability mass that should have gone to one of them. Neither wins cleanly, and the decision falls to noise — or to whichever one happens to sit in a favourable position.

2 — Position matters, which means your list order is a confound

Items in the middle of a long list get chosen measurably less often than items at the ends. In one study at 741 tools, items at the beginning and end scored 31–32% while middle positions fell as low as 22%. If you never shuffle the order across eval runs, you are measuring your list's layout, not your skills.

3 — Raw accuracy is meaningless without chance correction

With 40 options, random guessing is 2.5%. Quoting “the router is 60% accurate” says nothing until you say what chance was and how confusable the distractors were. The clean framing is information-theoretic: bits over random, log₂(P_observed / P_random) — each bit is one doubling of selectivity over chance. It lets you compare a top-3 menu against a top-40 menu honestly.

Rule of thumb to quote

Across the literature the workable zone is roughly 10–20 options visible per reasoning context. Above 40–50, most production workflows need an architectural intervention rather than better prose. Your 40 skills sit exactly on the cliff edge.

04

Break #2 — Hijacking. A load is a state change

The part that separates a senior answer

Most candidates stop at selection. That is the half of the answer a good blog post would give you. The other half is what happens after the pick — and it is why the damage doesn't stay contained to one turn.

When a skill opens, its body does not arrive as reference material. It arrives as instructions: “Always run the linter first.” “Never edit files under vendor/.” “Follow the checklist below in order.” The model was trained to obey instruction-shaped text in its context. It has no reliable way to mark a block as “a procedure for a task I am not currently doing.”

In plain words: a skill is not a book on the shelf. It's a manager walking into the room and giving orders. Pick the wrong skill and you haven't wasted a lookup — you've taken instructions from the wrong manager, and nobody ever tells them to leave.

Four properties that make a wrong load expensive

PropertyWhat happensWhy it beats the system prompt
ImperativeSkill bodies are written as commands, because good skills are written as commands.Command-shaped text wins attention over descriptive text. The better the skill is written, the harder it pulls.
RecentThe skill lands at the end of context; the user's actual goal was stated twenty turns ago.Recency and salience favour the newcomer. The original task decays into background.
StickyThere is no unload. The text stays for the remainder of the session.Contamination is not per-turn, it is per-session. One bad pick taxes every turn after it.
CompositionalLoad two skills and their rules interleave, sometimes contradicting.The model resolves the conflict silently and unpredictably, with no error surfaced to you.

The irony worth saying out loud

“Carefully written” makes hijacking worse. A vague skill gets ignored. A forcefully written skill with a numbered procedure and hard prohibitions gets followed — including on the 30% of tasks where it was selected by mistake. The team's craftsmanship is amplifying the failure.

The adversarial version — same mechanism, sharper teeth

This is not only a benign-failure story. The exact property that lets a mis-picked skill steer behaviour is the property that makes skills an attack surface. It is worth 30 seconds in the interview because it proves you understand the mechanism rather than just the symptom.

  • Tool poisoning — instructions hidden in a description or schema, which the model reads and the human reviewing the UI never sees. Publicly demonstrated in April 2025 against a production IDE agent: a benign-looking add tool whose description instructed the agent to read ~/.ssh/id_rsa and exfiltrate it.
  • Cross-server shadowing — one server's tool description redefines the behaviour of a different, trusted server's tool. Demonstrated by silently re-routing a trusted send_email tool to an attacker address.
  • The supply-chain numbers — an analysis of 42,447 community skills found 26.1% contained at least one vulnerability (13.3% data-exfiltration patterns, 11.8% privilege escalation), roughly 5.2% showed high-severity patterns consistent with deliberate malice, and skills that bundle executable scripts were 2.12× more likely to be vulnerable than instruction-only skills.

The connective tissue: an installed skill is trusted instruction text executing inside your agent's context. Whether it misbehaves because an attacker wrote it or because your own router picked it for the wrong task, the failure path is identical.

Context rot compounds it

Separately from selection, model reliability degrades as context grows — and specifically in the presence of distractors: material topically related to the question that does not answer it. A single distractor measurably lowers performance; four compound it. A wrongly-loaded SKILL.md is a perfect distractor: several hundred lines, highly on-topic, completely wrong for this task.

05

What “success went down” actually decomposes into

Three symptoms, three metrics, three different fixes

“Task success fell 11 points” is a lagging, aggregate number. It mixes at least five failure modes. Before you can fix anything you have to split it — and being able to name the split from memory is what makes you sound like you've actually run this.

The sentence that gets funded

Don't report “success went down 11 points.” Report: “of the 11 points, 6 are false triggers, 3 are wrong picks inside the testing cluster, 2 are hijack residue after a wrong load, and 0 are execution.” That is a work plan. The first version is a complaint.

06

Why “trim the descriptions” moves in the wrong direction

The rebuttal, in one breath

A description has exactly one job: let the model tell this skill apart from the other thirty-nine. That is a job you do with contrast, not with brevity.

Shorten debug-failing-test and fix-flaky-test and they converge on the same handful of tokens — test, fail, fix. You have shrunk the margin you needed. Selection accuracy falls. The intervention that “saves tokens” is the intervention that causes the failure it's meant to fix.

Say this

“Descriptions should get longer and more specific, not shorter — but there should be fewer of them visible at once. Compression belongs in the routing architecture, not in the prose.”

07

How you'd prove it — six experiments

Half the question lives here. Design the controls, not just the tests.

The structure to state before you give any detail: isolate the layer, then attribute the loss. First prove the damage is a function of menu size and not context size. Then split routing error from execution error. Then isolate hijacking with routing held constant. Everything else is bookkeeping.

Instrument first

None of this works without per-turn logging. For every turn record: the turn context, the set of skills offered and their order, which skill (if any) was opened, the gold label, and whether the task eventually succeeded. If you only have end-to-end task success, you have one number and five hypotheses.

The headline experiment

Dose–response sweep, with a token-matched inert control

Hold the task set, model, and seeds fixed. Vary only the number of skills exposed: 0, 5, 10, 20, 40. Three or more repeats each. Plot task success against N.

The control that makes it airtight: add a fifth arm at N = 40 where twenty of the skills are inert — real descriptions, but for skills the router can never actually select. Token count matches the broken arm. If the inert arm holds up and the live arm degrades, you have directly falsified the context-budget explanation the interviewer already rejected — and you've shown you can prove a negative, not just assert one.

This one chart ends the argument in a design review.

Split the error

Offline selection-only evaluation

Build a labelled set: a few hundred real task prompts, each tagged with a gold skill — including none, which should be 20–30% of the set. Run selection only. Do not execute anything.

Report four things: top-1 accuracy (chance-corrected), abstention accuracy on the none cases, the full confusion matrix, and the distribution of the top-1-to-top-2 score gap.

If offline selection is 55% at N = 40 and 90% at N = 8 on identical prompts, you are done diagnosing. The router is the bug, execution is fine, and you found it in an afternoon without running a single agent trajectory.

Explain the matrix

Overlay embeddings on the confusion matrix

Embed all 40 descriptions, compute pairwise cosine similarity, cluster. Then overlay the error pairs from E2. High-similarity pairs that are also high-error pairs are your merge-or-rewrite list.

This converts “the model is confused” into “these six pairs are functionally duplicates and account for 71% of wrong picks.” That is a specific, closable ticket.

Isolate hijacking

Forced-load counterfactual

Take the tasks the agent passes with zero skills installed. Now force-load one irrelevant-but-plausible skill at turn one — no routing decision involved, you inject it. Re-run the same tasks.

Selection is held perfectly constant, because there is no selection. If success drops, the only remaining explanation is that the loaded content is steering behaviour. That is hijacking, measured in isolation.

Then quantify the shape of it: diff the action traces and count steps that follow the injected skill's procedure or vocabulary rather than the user's request. Add a persistence arm — measure success on turns 5–20 after the load against a never-loaded control — to put a number on stickiness.

Find the peak

Greedy forward selection for marginal value

Start with zero skills. Add the single skill that improves success most. Repeat. The curve almost always peaks well before 40 and then declines — and the peak is your actual budget.

Full leave-one-out is cleaner but costs 40 runs; run it on a cheap task subset if you can afford it. Either way the output is the thing nobody has: a ranked list of which skills are net-negative. A skill whose removal improves success is not an underperforming skill, it is a liability.

Don't fool yourself

Controls, statistics, and the attribution ledger

Shuffle the order of the skill list across runs. If success varies with position, part of your loss is positional bias, not description quality — and any result from a fixed-order eval is partly an artefact.

Pair your comparisons on identical tasks, fix seeds, bootstrap the confidence intervals. A 3–5 point success delta needs hundreds of tasks to separate from noise; be honest about that before you present.

Close with the ledger — every failure bucketed into the five modes from section 05, summing to the observed drop. That is the deliverable.

Senior move

Volunteer what would falsify you. “If the N-sweep is flat and the inert arm degrades too, I'm wrong about decision load and it really is a context-length effect — then I'd look at position and at total prompt length instead.” Interviewers weight this heavily. Almost nobody offers it.

08

The fix, ordered by leverage

They will ask. Lead with architecture, not prose.

Biggest lever

Retrieve, don't expose

Stop putting forty descriptions in the system prompt. Put a search step in front of them and surface the top three to seven for the current query. This is the intervention with the published numbers behind it: 13.6% → 43.1% on a large MCP catalogue, and 79.5% → 88.1% for a frontier model with Tool Search, at 85% less context.

The library can stay large. The menu must stay small.

Prose, done right

Write descriptions for contrast, not brevity

Every description gets an explicit use when and a do NOT use when, and the “do not” clause should name the sibling it is most often confused with. Namespace by domain so the prefix does discriminative work: test_debug_failure, test_stabilise_flaky, review_pull_request. Prefix and suffix schemes have non-trivial and model-specific effects — pick yours from your own eval, not from taste.

Subtraction

Merge the duplicates, delete the net-negatives

E3 hands you the merge list; E5 hands you the delete list. Collapse the four testing skills into one with branches. A skill that never wins a row in the confusion matrix is costing you margin and buying nothing.

Scoping

Gate by context so the live menu is always small

Expose skills conditionally — by repository, by file type, by phase of the task. Or route hierarchically: pick a category first, then a skill within it, turning one 41-way decision into two 6-way decisions. Where the work genuinely partitions, give each subagent a narrow catalogue and let the orchestrator route.

Blast radius

Bound what a load can do

Default skills to reference voice; use imperative voice only where a procedure genuinely must be followed. Open every skill body with an explicit scope line (“applies only when … ; if the task is not that, ignore the rest of this file”). Support unload or turn-based expiry. Re-assert the user's actual goal after a load lands.

Security

Treat the skill library as a supply chain

Review, pin, and version skills like dependencies. Scan descriptions and schemas for injection patterns. Hold bundled executable scripts to a higher bar — they carry roughly twice the vulnerability rate of instruction-only skills. Human review of the rendered UI is not review; the model reads the full text.

Keeps it fixed

Gate the library with the selection eval in CI

Every new skill must clear two bars before merge: it wins its own tasks, and it does not degrade selection accuracy on anyone else's. Give every skill an owner and a deprecation policy, and set a hard budget for how many may be visible in any one scope.

The one-liner: a skill isn't done when it's written, it's done when it wins its own eval without costing anyone else theirs.

09

Twelve follow-ups they will actually ask

With the answer compressed to what you'd say out loud

F1“Your offline router hits 92% top-1. Why is task success still down?”

Because selection happens every turn, not once. Over a twenty-turn trajectory, 0.9220 ≈ 19% chance of a clean run. Per-turn accuracy compounds multiplicatively against you. On top of that, top-1 accuracy doesn't count the none cases at all, and it says nothing about hijack residue after the one turn that went wrong. End-to-end success is a product of per-turn correctness and per-error persistence — you have to measure both.

F2“We retrieve top-5 and recall@5 is 99%. Isn't selection solved?”

No — and this is the sharpest trap in the space. Retrieval and selection are different problems, and retrieval makes selection harder by construction: the five candidates you hand the model are, by definition, the five most semantically similar to the query. You have filtered out every easy distractor and handed over the maximally confusable set. High recall guarantees the answer is in there; it guarantees nothing about the model's ability to pick it out of four near-twins. Always measure downstream selection accuracy, never recall alone.

F3“How do you choose k?”

Adaptively, per query, not as a constant. Easy queries — where the right skill is already the top scorer — need k ≈ 2–3; hard ones where the gold sits sixth to twentieth need k ≈ 6. A fixed k pays the hard-query cost on every easy query. Expand k while the retriever's score gap is still narrow and stop when it opens up. Judge candidate k values on a chance-corrected metric, since raw accuracy at k=2 and k=20 are not comparable quantities.

F4“Isn't this just model capability? Won't the next model fix it?”

Partly, and the trend is real — with tool search the jump was 49% → 74% for one generation and 79.5% → 88.1% for the next, so the floor is rising fast. But notice that the gap persists: the frontier model still loses 8.5 points purely to menu size. The failure is architectural, not a knowledge deficit. You are asking a system to make a discrete choice over a confusable set, with no ground-truth feedback and no ability to revise. Better models shift the cliff; they don't remove it. Design as if it's there.

F5“A teammate proposes a meta-skill that teaches the model how to pick skills.”

It makes things worse for a subtle reason: the meta-skill is itself always-on instruction text competing for the same attention, and it becomes option 42 in the menu it is supposed to arbitrate. You've put the router inside the thing being routed. Routing logic belongs out of band — a retrieval step or a classifier that runs before the model sees a menu at all — precisely so it isn't subject to the failure mode it's meant to prevent.

F6“How would you catch this in production, not in an eval?”

Make three things first-class SLIs. Skill open distribution — a long tail of skills with near-zero opens is dead weight costing margin; a skill with a very high open rate is probably over-triggering. Open-to-value ratio per skill: opened, then never referenced downstream. False-trigger rate on a sampled, human-labelled stream. Then run a permanent shadow arm with a reduced skill set; when the shadow beats production, you have your answer and your rollout plan in one.

F7“One skill tests beautifully alone and terribly in the library. Delete it?”

Not yet — that's a margin problem, not a quality problem, and the three fixes are ordered. First rewrite for contrast against whatever it collides with in the confusion matrix, naming the sibling explicitly. Second, namespace it so the prefix carries discriminative signal. Third, scope it so it is only visible where it applies. Delete only if its marginal contribution stays negative after all three. The general principle: evaluate skills by marginal contribution to the library, never by isolated quality.

F8“How do you know this isn't just context rot from a longer prompt?”

The token-matched inert arm in E1. Same token count, same position in the prompt, same prose style — but the extra descriptions correspond to skills the router can't select. If that arm holds and the live arm degrades, length is not the variable. It's the cleanest available separation of “more text” from “more choices,” and it's the specific experiment that answers the constraint they put in the question.

F9“Can't you fix hijacking with a stronger system prompt?”

Weakly, and it degrades as the session runs. You're asking a stable instruction from turn zero to out-compete a freshly injected, forcefully worded, on-topic procedure at the end of context. Recency and imperativeness are on the wrong side of that fight. Structural fixes win: scope statements inside the skill body, unload or expiry, and re-asserting the goal after a load. Use the system prompt as reinforcement, never as the mechanism.

F10“What if all forty really are needed?”

Then they're needed at different times, and the fix is dynamic scoping rather than deletion. Keep the library at forty and the visible menu at five. Partition by phase (plan / implement / review), by repository, or by file type. Where the work genuinely decomposes, hand each subagent a narrow catalogue and let an orchestrator route between them — which is just hierarchical routing with process isolation and the bonus that a hijack can't cross the boundary.

F11“What's the latency and cost story?”

Dominated by thrash, not by tokens. Every open is a round trip, and a mis-pick costs an open, the wasted turns that follow, and often a corrective loop on top. The tail is what hurts: p99 is set by the trajectories that opened three skills before finding the right one. Retrieval cuts context roughly 85% in the published numbers, but the bigger win is turn count. Watch out for the trap where a self-correction loop and skill thrash compound each other — that's the same tail-latency failure wearing a different hat.

F12“How do you stop this regressing as the library grows to 200?”

Treat skills as code. Selection eval in CI, and a new skill blocks on not degrading anyone else's accuracy. An owner per skill and a deprecation policy, so nothing survives on inertia. A hard cap on skills visible per scope, enforced at build time. A scheduled re-run of the greedy forward-selection curve — the peak moves as the library changes, and you want to notice before success does.

Prior art: an industry that already solved this

A 20-second aside that shows range

Hospital pharmacy has spent decades on exactly this failure mode, under the name LASA — look-alike, sound-alike. As a formulary grows, the dominant error stops being “we lack the drug” and becomes “we picked the neighbouring one.” Their fixes map onto ours almost line for line:

If the conversation gets philosophical, this is the point to make: this isn't an LLM quirk. It's what happens to any system that makes a discrete choice from a growing set of similar options under time pressure. We just rebuilt the problem in a new substrate.

Glossary

Use the words precisely; they're listening for it

TermMeaning
Progressive disclosureLoading a skill in stages — name and description always, body on demand, linked files only if the body asks.
MarginScore gap between the correct option and the best incorrect one. The quantity that actually determines selection accuracy.
ConfusabilityHow semantically close the options are. The real driver of difficulty; count is only a proxy for it.
Irrelevance / abstention accuracyFraction of cases where no tool applies and the model correctly calls none. Measures false triggers, which top-1 accuracy hides entirely.
Chance correctionReporting accuracy relative to random guessing, e.g. bits over random = log₂(P_obs / P_rand). Required whenever N differs between arms.
Positional biasSystematic under-selection of options in the middle of a long list, independent of their content.
DistractorContent topically related to the query that does not answer it. Degrades accuracy; effects compound with count.
Context rotMeasurable decline in reliability as input length grows, observed across every frontier model tested.
Instruction hijackingText loaded into context redirecting the agent's behaviour away from the user's actual goal. Benign when a wrong skill loads; adversarial when the text was written to do it.
Tool poisoningAdversarial instructions hidden in tool descriptions or schemas — read by the model, invisible in the human-facing UI.
Cross-server shadowingOne server's tool description overriding the behaviour of a different, trusted server's tool.
Marginal contributionChange in task success from adding or removing one skill, holding everything else fixed. The only correct way to value a skill.

If you remember only three things. One: the cost of a skill is the decision it forces, not the tokens it occupies — and short descriptions make that decision harder, not easier. Two: opening a skill is a state change, not a lookup; the instructions stay, and they steer.
