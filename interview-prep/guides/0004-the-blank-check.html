The Blank Check

Code execution wins on turns and success rate. Here is the bill that comes with it, and why it stops being a prompt decision and starts being an infrastructure one.

The question

"Your agent has 70 REST tools and needs 12 sequential calls to compare smartphone prices across 4 countries. Switching to code execution raises success rates and cuts turns. So why isn't code execution the default for every agent?"

The one-sentence answer

Because code isn't another tool — it's a meta-tool, and the thing that makes it win is the same thing that makes it expensive: it replaces a finite, schema-checkable menu of actions with an unbounded action space. The gains are real and free; the containment that makes them safe to keep is neither. Code execution is the default wherever somebody has already paid for a sandbox, and it isn't the default everywhere because most teams haven't.

00

What the interviewer is actually testing

The question looks like a comparison. It is not. It hands you a win and asks whether you can price it — which is a seniority probe wearing an architecture costume. Four things are being checked at once.

Probe 1

Can you name the mechanism, not the vibe?

Why does code win? If your answer is "fewer round trips", you've described the symptom. The mechanism is that one program expresses a whole tree of calls — loops, branches, variables, intermediate data that never enters the context window.

Probe 2

Do you think about the action space?

70 JSON tools is a set you can enumerate, validate, and reason about exhaustively. "Anything Python can do" is not. Whether you reach for that distinction unprompted is most of the signal in this question.

Probe 3

Have you ever had to run untrusted code?

Anyone who has knows the words: sandbox, egress allowlist, pinned dependencies, secret broker, kill switch. Anyone who hasn't says "we'd validate the code first," which is the halting problem with extra steps.

Probe 4

Do you reason in blast radius?

The senior move is not listing risks — it's assuming the worst case happens and asking what survives it. "If this program does the most damaging thing it is capable of, what breaks, and who finds out?"

Do not say

"Because code can have bugs, so JSON tool calls are safer."

This loses the room in one sentence, for a specific reason: JSON tool calls have bugs too. A model can pass a malformed date, the wrong customer ID, or a limit of 100000 through a perfectly valid schema. Bugginess is not the axis. The axis is boundedness — whether the set of things that can happen is enumerable in advance. A schema gives you that; an interpreter does not.

01

The answer, at three lengths

Lead with the thesis. Interviewers interrupt, so the first thirty seconds must contain the trade, not the setup.

Say this — 30 seconds

"Because code isn't another tool in the list — it's a meta-tool. A JSON call is one function with a schema I can validate. A program is a tree of calls with loops, variables, and every library it can import. That's exactly why it wins: twelve round trips collapse into one program, and the intermediate data never touches the context window.

But the property that makes it win is that the action space became unbounded, and that's the property I now have to pay for. With 70 tools I could enumerate every legal action ahead of time. With code I can't, so predictability has to come from the runtime instead of the schema — a sandbox, hard resource limits, deny-by-default egress, pinned dependencies, and credentials that never enter the execution environment. Code execution buys fewer turns and higher success by expanding the action space; you only get to keep those gains once a sandbox contains the blast radius. It isn't the default everywhere because that containment is infrastructure, not a prompt change."

Say this — the two-minute shape (add these beats)
  1. Grant the win, with the mechanism. "In your example the 12 calls are a loop over 4 countries. In code that's four lines and one round trip; as JSON calls it's 12 model turns, each paying prefill on a context that now also carries every intermediate result. Published numbers for this pattern are large — a Drive-to-Salesforce workflow going from ~150K tokens to ~2K, and around 38% fewer billed input tokens on a 75-tool benchmark with no accuracy change."
  2. Name the trade in one word: boundedness. "Schema validation is a decidable check on a finite action set. 'Does this program do anything dangerous?' is not decidable in general. So I've moved from a static guarantee to a runtime one."
  3. Enumerate the new failure classes, not generic 'bugs'. "Non-termination, resource exhaustion, partial side effects when the program dies mid-sequence, unbounded irreversible writes, supply chain via imports, and prompt injection that now escalates from 'wrong tool call' to arbitrary code execution."
  4. Reach for blast radius. "So the design question I'd actually ask is: if this program does the worst thing it's capable of, what breaks? That question orders the whole control list."
  5. List the controls, cheapest first. "Sandbox — container, gVisor, or microVM depending on what the code is derived from. Hard caps on wall clock, CPU, memory, disk, process count. Network deny by default with a per-task allowlist. Dependencies pinned and mirrored, no arbitrary installs. Secrets outside the sandbox, with tools authenticating through a proxy."
  6. Refuse the binary. "And I wouldn't ship it as either/or. The shape I want is code for orchestration and schema-validated calls for the irreversible actions — the program calls my declared tools, not the open internet. That keeps per-action authorization on the things that can't be undone while still collapsing twelve turns into one."
  7. Say where JSON still wins. "Single-call tasks, where a sandbox cold start costs more than the round trip it saves. High-stakes actions that need a human in the loop per call. Weak models that can't write reliable code. Regulated environments that need an auditable record of every individual action."
The line that lands

"Code execution buys fewer turns and higher success by expanding the action space. You only get to keep those gains once a sandbox contains the blast radius — which is why it's a platform decision, not a prompting decision."

Say it out loud · about 75 seconds

The three above are written answers. This one is a script — four beats, short lines, built to be said. A spoken answer to “code execution raises success and cuts turns. So why isn’t it the default for every agent?” Read it aloud, then say it again with the page covered.

  1. Situation

    Seventy REST tools, twelve sequential calls to compare prices across four countries.

    Switching to code execution cuts that to one turn and raises the success rate. So why isn’t it the default?

  2. Mechanism

    Because code isn’t another tool. It’s a meta-tool.

    A JSON call is one function with a schema I can validate. A program is anything Python can do. I didn’t add a tool — I replaced a finite, checkable menu with an unbounded action space.

    That’s exactly what makes it win, and it’s the same property I now have to pay for.

  3. What I did

    A sandbox, so nothing runs on the host. Hard caps on wall-clock, CPU, memory and disk, enforced outside the interpreter. Deny-by-default egress with a per-task allowlist. Pinned dependencies from a vetted mirror, baked into the image.

    And no secrets inside it: tools authenticate through a proxy, so the agent gets capabilities and never keys.

  4. What it cost

    A sandbox per task, and somebody to run it. That’s the real answer to why it isn’t the default — it is the default wherever a team already paid for one.

    And none of it stops a legitimate, authorised, irreversible write.

02

Fundamentals: what you actually changed

Before you can price the trade, you have to be precise about what a tool call is and what a program is. They are not two flavours of the same thing.

In plain words

A JSON tool call is ordering from a menu. There are 70 dishes, you pick one, and the kitchen checks your order against the menu before cooking. Code execution hands the agent the keys to the kitchen. It can now make anything — including things that were never on the menu, and including a fire.

One call is a node. One program is a tree.

Fundamental — where the turns actually go
JSON path: 12 × (prefill(context_so_far) + decode(call) + network + result→context) context grows monotonically; prefill cost grows with it Code path: 1 × (prefill(context) + decode(program)) + sandbox_exec intermediate data never enters context at all

Two separate savings are bundled together here and it is worth splitting them out loud: latency (one model round trip instead of twelve, each with its own time-to-first-token) and context (the 40-row price table gets filtered in the runtime, and only the answer is returned). The second is usually the bigger number.

The published gains, so you can quote one

The nuance that marks you out

"I'd be careful quoting 98% token reduction as if it were a property of code execution. It's a property of tasks that move a lot of intermediate data. Your price-comparison example is exactly that shape, so it'll benefit. A single-call lookup gets nothing and pays a sandbox cold start. The gain is workload-dependent, and I'd want the number from our own traces before it goes in a design doc."

03

The trade: a menu for a blank check

One property changed, and everything downstream follows from it. Say this part slowly.

Property70 JSON toolsCode execution
Action spaceFinite and enumerable: 70 functions × their parameter domainsUnbounded: anything the interpreter and its importable libraries can express

Unit of authorizationOne call. You can require approval per actionOne program. Approval happens before you know what it will do
ObservabilityEvery action is a structured, logged, replayable eventYou log a program and its output; what happened in between is yours to instrument
Blast radius of one mistakeOne bad call. Bounded by that tool's own permissionsA loop. The same mistake, 10,000 times, in eight seconds
ComposabilityThe model composes, one step per turnThe program composes: loops, conditionals, error handling, libraries
Context cost of resultsEvery intermediate result passes through the context windowIntermediates stay in the runtime; only the answer returns

Fundamental — why "just validate the code" is not an answer

Somebody will suggest static analysis of the generated program. It helps, and you should have it, but be clear about its ceiling: deciding whether an arbitrary program has a given non-trivial behaviour is undecidable — that is Rice's theorem, and the halting problem is the special case everyone knows. Practically this means a linter can catch os.system, but it cannot catch getattr(__import__(base64.b64decode(x)), y)(), and an allowlist of imports is defeated by anything that can reach the network. Static analysis is a filter, never a boundary. The boundary has to be the runtime, because the runtime is the only place where the question becomes decidable: it doesn't ask what the program will do, it stops what the program is doing.

In plain words

You cannot read a recipe and be certain the kitchen won't catch fire. You can, however, install a fire door, a gas cut-off and a smoke alarm. The industry moved from checking the order to containing the kitchen because the first one stopped being possible.

04

Six failure classes you didn't have before

Not "bugs". Six named classes, each with a distinct mechanism and a distinct control. Naming them in this shape is what separates an answer from a list of worries.

ClassMechanismWhy the JSON path didn't have itControl
1 · Non-termination while True:, a retry loop with no bound, a regex with catastrophic backtracking A tool call either returns or times out. There is no loop construct to run away with Wall-clock timeout + hard kill, enforced outside the interpreter
2 · Resource exhaustion Unbounded list growth, a fork bomb, writing until the disk fills, pulling a 40 GB file The tool implementation owned its own resource use; the model couldn't allocate cgroups: memory, CPU shares, PID count, disk quota, open FDs
3 · Mid-sequence death Syntactically valid code that raises on line 40, after lines 1–39 already wrote to production Each call was its own transaction boundary; the agent observed each result before continuing Idempotency keys, dry-run mode, staged writes, compensating actions
4 · Unbounded side effects A loop issues 10,000 writes before a human could possibly intervene One call, one action, one approval opportunity Rate limits and quotas at the tool proxy, not in the program
5 · Supply chain The program imports a package; the package owns the runtime; the runtime reaches your systems There was nothing to import. The tool surface was code you wrote Pinned versions, hash-verified, from a vetted mirror; no arbitrary installs
6 · Injection → execution Untrusted text in a tool result becomes instructions that become a program that runs Injection could still pick a wrong tool — but only from your 70, with your schemas Egress allowlist, credential isolation, and treating tool output as data

Class 5 deserves its own paragraph, because the number is worse than people expect

The supply-chain exposure here is not the classic one where a dependency you chose turns out to be malicious. It is newer and sharper: the model invents a package name that doesn't exist, and an attacker registers it. That attack has a name — slopsquatting — and a measurement. A USENIX Security 2025 study across 576,000 generated code samples from 16 models found roughly 19.7% of recommended packages were hallucinations. Packages registered against those hallucinated names have accumulated tens of thousands of downloads.

Say this, it is specific and few candidates have it

"The import statement is the part I'd lock down first, because the failure mode isn't 'we picked a bad library' — it's that the model will confidently import a package that has never existed, and roughly a fifth of its package suggestions are in that category. That turns 'no arbitrary pip install' from a hygiene rule into a load-bearing control. The sandbox image ships with a fixed, vetted set, and an unknown import is a hard failure, not a network fetch."

Class 6 is the one that changes the threat model

Prompt injection existed before code execution. What changes is the ceiling. With 70 JSON tools, a successful injection gets the attacker one of your 70 tools with your schemas — bad, bounded. With code execution, a successful injection gets the attacker arbitrary code running inside your infrastructure. Same entry point, categorically different payload.

Fundamental — the lethal trifecta

Simon Willison's framing is the cleanest way to say this out loud. An agent is exposed when it combines three things: access to private data, exposure to untrusted content, and the ability to communicate externally. Any two are survivable. All three, and any attacker who can get text in front of the agent can get data out of it.

Code execution does not add a fourth item — it makes the third one trivially available. Without it, exfiltration needs a tool that happens to make outbound calls. With it, the attacker has sockets. This is exactly why egress control, not code review, is the control that matters: you cannot reliably stop the agent from being persuaded, so you stop the bytes from leaving.

In plain words

You can't stop someone from slipping a note to the chef. What you can do is make sure the back door is locked, so whatever the note says, nothing walks out of the building.

05

Blast radius: the frame that makes it a senior answer

Junior answers enumerate risks. Senior answers assume the risk has already happened and ask what is still standing. The question is always the same one.

The question to ask out loud

"If this program does the most damaging thing it is capable of — not the most likely thing — what breaks, how far does it reach, how long before we know, and can we undo it?"

"The rings handle the security failure modes well. They do nothing about the one that has actually hurt people most: a program that is perfectly contained, perfectly authorised, and deletes the wrong 4,000 rows. That's why I'd keep destructive operations behind declared tools with per-call authorization even in a code-execution agent — so the loop can orchestrate, but the irreversible step still passes through something that can say no."

06

What you build before you ship it

Five controls. For each one, say what it stops and what it does not — the second half is what proves you've operated this rather than read about it.

Sandbox — isolate the execution, never run on the host

Pick the isolation strength from the provenance of the code. Code derived from your own prompts and your own data is a different threat than code derived from a web page the agent just read.

Stops

Host filesystem access, cross-tenant reads, most escape paths, persistent compromise (the sandbox is destroyed per task).

Does not stop

Anything the sandbox is legitimately allowed to do: calling your APIs with the credentials you gave it, and sending data to an allowed destination.

Resource limits — hard caps, enforced from outside

Wall clock, CPU shares, resident memory, disk quota, process/thread count, open file descriptors. The enforcement has to live outside the interpreter: a timeout the program can catch is not a timeout, and a memory limit inside the same process is a suggestion.

Stops

Infinite loops, memory bombs, fork bombs, disk fills, and — usefully — most accidental cost blowouts.

Does not stop

A program that stays comfortably inside every limit and makes 9,000 legitimate API calls in its 60-second budget.

Network egress control — deny by default, allowlist per task

This is the highest-leverage control in the list, because it is the one that converts "the agent was manipulated" into "the agent was manipulated and nothing left the building." Allowlist by destination host, scoped to what this task needs rather than what the platform supports.

Stops

Exfiltration, command-and-control, second-stage payload fetches, and the unvetted package install — one control, four failure modes.

Does not stop

Exfiltration through an allowed destination. If the agent may write to your ticketing system, data can leave in a ticket. Allowlisting a domain allowlists everything on it.

Dependency control — pinned, hashed, mirrored, pre-baked

The sandbox image ships with the libraries the task needs, at pinned versions with verified hashes, from a mirror you control. An import of something not in the image is a hard failure with a clear error, not a network fetch. This is the direct answer to hallucinated package names.

Stops

Slopsquatting, typosquatting, a compromised new release landing in production the hour it is published.

Does not stop

A vulnerability in a library you vetted and pinned. Pinning freezes the risk; it does not remove it. You still need to move the pin on a schedule.

Credential isolation — secrets never enter the sandbox

The program calls a local tool proxy; the proxy holds the credentials and attaches them on the way out. The agent gets capabilities, never keys. Scope tokens to the task, make them short-lived, and make the proxy the place where rate limits and per-action authorization live.

Stops

A sandbox escape or a leaked program from becoming durable access to production. It also gives you a per-action audit log for free, which the program itself cannot forge.

Does not stop

Misuse of the capability while the task is running. The proxy will happily perform every action it was told to authorise, which is why the proxy is also where quotas belong.

The trade-off sentence for this table

"The axis is isolation strength against cold start, and the honest position in 2026 is that the gap has mostly closed — a microVM at ~125 ms is no longer a good enough reason to accept a shared kernel. What actually decides it is provenance: if the program can be influenced by content the agent fetched, I want a kernel boundary, not a namespace."

07

So when is JSON still the right answer?

The question says "why isn't it the default for every agent". Answering only "because security" is half a mark. There are workloads where code execution is simply the wrong shape, and naming them shows you've thought past the headline.

SituationWhy code execution loses
One or two calls per taskYou pay a sandbox cold start and a longer generation to save one round trip. Below roughly three or four dependent calls, the arithmetic goes the other way
Irreversible, high-stakes actionsRefunds, deletes, sends, payments. You want per-action authorization, and a program is authorised before anyone knows what it will do
Weak or small modelsThe whole gain assumes the model writes correct code. A model that can reliably emit valid JSON against a schema may not reliably write a working loop — and a broken program fails the entire task, where a bad JSON call fails one step and can be retried
Regulated and audited environments"Show me every action taken on this account" is answerable from a tool-call log by construction. From a program log it is answerable only if you instrumented the proxy for it
Tiny tool surfaceWith five tools there is no context pressure to relieve and no composition worth expressing. Code adds a runtime to operate for nothing
No platform to run it onThe real reason it isn't the default. Five controls, an image pipeline, an egress proxy and a secret broker is a team-quarter of work — not a flag you flip
Latency-critical single hopsSandbox provisioning sits on the critical path. For a p99-sensitive single call, that is pure added tail

The answer is not either/or, and saying so is the strongest move available

The shape that actually ships is code for orchestration, declared tools for effects. The program runs in the sandbox and expresses the loop, the filtering and the control flow — but every call it makes goes through your declared tool surface, with its schema, its authorization and its audit trail. The agent gets composition; you keep the boundedness exactly where boundedness was load-bearing.

This is not a hypothetical design: it is the shape of Anthropic's programmatic tool calling, where the model writes code that invokes your tools inside a container rather than making open network calls, and of Cloudflare's Code Mode, where a generated TypeScript API is called from a sandboxed V8 isolate. Both give you the turn collapse and the context saving while keeping the action space anchored to a surface you defined.

Say this if they push on "so which would you choose?"

"I'd refuse the binary, because the interesting variable isn't code-versus-JSON — it's what the code is allowed to call. Let the program do arbitrary computation over data, and let every side effect go through declared tools behind a proxy. Reads and transformations go in the sandbox; writes stay schema-checked and individually authorised. That gets me the 12-turns-to-1 collapse on your price comparison without handing the model an open socket."

In plain words

Give the agent the kitchen, but keep the till behind the counter. It can cook whatever it likes; it still has to ask before it takes money out.

08

How you'd prove it, and what you'd put on the dashboard

If the interviewer asks "how would you decide?", this is the answer: a two-arm comparison plus a red-team suite. Do not offer opinions where a measurement is available.

The A/B you'd actually run

Same task set, same model, two harnesses. Run the price-comparison workload and a control workload of single-call tasks, so the result tells you where the crossover is rather than which arm wins on average.

And a red-team suite, because a safety claim without an adversary is a wish

Run a standing set of hostile tasks against the harness and require them all to fail safely: a non-terminating program, a memory bomb, a program that tries to read ~/.ssh/id_rsa, one that tries to reach an unlisted host, one that imports a package that does not exist, and an injected instruction planted in tool output. This is the genre that RedCode formalised — 4,050 risky execution cases across 25 vulnerability types, which found high attack success rates across 19 models and three agent frameworks, and one finding worth quoting: agents refuse dangerous operations described in code far less often than the same operations described in natural language.

The sentence that gets the work funded

"I'd report two numbers together and never separately: the efficiency win, and the blast-radius test pass rate. The first one alone is how a team ships code execution in a week and has an incident in the second week."

09

Follow-ups they will ask

Twelve probes, ordered roughly by likelihood. Each answer is written to be said out loud in under a minute.

F1

"You said the action space is unbounded. Can't you just restrict the language — no imports, no sockets, a subset of Python?"

You can, and it genuinely helps, but be honest about what you've built. A restricted interpreter is a language-level control, and language-level controls have a long history of being escaped — Python's rexec and Bastion modules were both withdrawn from the standard library precisely because they could not be made safe. Anything that can reach __builtins__, __subclasses__, or a C extension is a way out.

So I'd use it as defence in depth on top of a sandbox, never instead of one. And there is a version that does work: a capability-based runtime like WASM, where the boundary is deny-by-default at the runtime rather than a blocklist bolted onto a permissive one. The distinction I'd want to be judged on is blocklist versus allowlist — a subset defined by removal is a filter; a runtime that has no filesystem unless you hand it one is a boundary.

F2

"Sandbox cold start is 150 ms. Doesn't that eat the latency win you just claimed?"

It eats it on short tasks, which is exactly why I'd want the crossover measured rather than assumed. On your 12-call example, twelve model round trips at even 400 ms each is ~5 seconds; a 150 ms cold start against that is noise. On a single-call task, the same 150 ms is the whole story, and JSON wins.

Operationally there are three levers. Keep a warm pool so provisioning is off the critical path. Reuse one sandbox across a session rather than per call, accepting that you've weakened the per-task blast-radius reset and deciding that deliberately. Or pick a lighter isolation layer for low-provenance work — WASM starts in under a millisecond. The point is that it's a routing decision per task shape, not a platform-wide one.

F3

"Your egress allowlist permits our internal API. The attacker exfiltrates through it. Now what?"

Correct, and that's the right question to ask — an allowlist bounds the destination, not the content. Three things follow. First, scope the allowlist per task rather than per platform: this run needs the pricing API, so that is all it gets, and the ticketing system isn't reachable at all. Second, put the tool proxy in the path so egress is not raw HTTP — the proxy sees structured calls, can rate-limit them, and can flag a call whose payload is three orders of magnitude larger than the schema expects. Third, accept the residual and manage it at the trifecta level: if a task genuinely needs private data, untrusted content and a write path, that combination is the thing to remove, by splitting it into two agents where the one that reads untrusted content has no private data.

And I'd say plainly that this is a mitigation, not a solution. Prompt injection is not solved. The design goal is that no single failure is catastrophic, not that the agent is incorruptible.

F4

"The program dies halfway through after making six of twelve writes. How do you handle that?"

This is the failure class I'd worry about most in practice, because it's the one that isn't about attackers — it's ordinary Tuesday behaviour. The JSON path had transaction boundaries for free: one call, one observation, one decision. A program deletes that.

Four controls, in order of how much I'd fight for them. Make every mutating tool idempotent with a caller-supplied key, so replay is safe and the recovery path is "run it again". Offer a dry-run mode so the program can compute its full plan before any effects, and the effects are applied in one reviewable batch at the end. Make the proxy's log the source of truth for what happened, so recovery doesn't depend on the program's own bookkeeping. And where the operations are genuinely coupled, expose a single compound tool that owns the transaction in your code rather than in the model's — this is a case where the right answer is to move logic out of the agent entirely.

F5

"Doesn't code execution also fix the tool-selection problem? You could skip loading 70 schemas."

It helps a great deal, and for a reason worth stating precisely: the tools become a filesystem the agent explores on demand instead of 70 definitions sitting in the system prompt, so discovery becomes progressive rather than upfront. Anthropic's deferred-loading numbers are in that spirit — around 85% less context, with measured success going from 79.5% to 88.1% on one of their tool-heavy evaluations.

But I'd resist the framing that it fixes selection. The agent still has to choose the right stub, and it now chooses from a directory rather than a menu — which is a retrieval problem layered on top of a selection problem, not a removal of one. The failure just moves: instead of picking the wrong tool, it imports the wrong stub, or invents one. The honest claim is that code execution fixes the context cost of a large tool surface and leaves the confusability largely where it was.

F6

"We already run in Kubernetes with resource limits. Isn't that enough?"

It's ring 2 and part of ring 4, which is real progress, but a standard pod is a namespace boundary over a shared kernel. For model-authored code that can be influenced by content the agent fetched, that's the layer I'd want to upgrade — a kernel exploit from inside the pod reaches the node and every other workload on it.

The upgrade path is usually cheap: a gVisor or Kata runtime class, so the same manifests get a real kernel boundary without rewriting the platform. I'd also check the things Kubernetes doesn't give you by default and that matter more than the isolation layer — deny-by-default egress with a NetworkPolicy plus a proxy, no service-account token mounted into the pod, a read-only root filesystem, and a PID limit, because a fork bomb inside a memory limit is still a fork bomb.

F7

"How do you audit what the agent did, if it's a program rather than a list of calls?"

You don't audit the program — you audit the boundary. Every effect goes through the tool proxy, so the proxy's log is the record: caller, task ID, tool, arguments, result, timestamp. That log is outside the sandbox, so the program cannot forge or omit from it, which is a strictly stronger property than a tool-call log the model itself produced.

On top of that I'd retain the program source keyed to the task, and hash it, so an incident can be reconstructed exactly. And I'd flag the gap honestly: the JSON path gave you an audit trail by construction, and here you get one only because you built the proxy. If the proxy is optional in the architecture, the audit trail is optional too.

F8

"Doesn't the model need to be much stronger to write correct code? Isn't that a hidden cost?"

Yes, and it's the cost people forget because the published wins are all measured on frontier models. Two asymmetries matter. A malformed JSON call fails one step and the agent retries with the observation in hand; a broken program can fail the whole task, and a subtly broken program — an off-by-one in the country loop — returns a confident wrong answer with no error at all. That second one is the expensive case, because nothing in the harness flags it.

What I'd do about it: let the sandbox return stack traces so the model can iterate rather than restart, keep tasks small enough that a program is twenty lines rather than two hundred, and route by capability — a cheap model on the JSON path, the stronger model on the code path — rather than committing the whole fleet to one format.

F9

"Give me the number. When is the crossover?"

I'd give the shape of the arithmetic rather than pretend to a constant, because the constant is workload-specific. Code wins when (N − 1) × turn_cost exceeds sandbox_cost + Δgeneration, where N is the number of dependent calls — independent calls can already be batched in parallel on the JSON path, so they don't count toward the win.

With a 400 ms turn and a 150 ms warm-pool start, the break-even is around two to three dependent calls on latency alone. On tokens the crossover comes earlier whenever intermediate results are large, because that saving scales with payload size rather than call count — one call returning a 50,000-token transcript can justify the code path on its own. Your 12-call example is comfortably past both thresholds, which is why it was chosen.

F10

"What if the code execution environment is a vendor's, not yours?"

Then you've outsourced rings 2 and 3 and you still own rings 4 and 5 — and that split is the thing to be explicit about, because it's where people get surprised. The vendor runs the sandbox and the limits. You still decide which credentials exist inside it, what it is allowed to reach, and what happens to data that goes in.

The questions I'd ask before adopting one: what is the isolation layer, is it per-task or per-tenant, is it destroyed after each run, what is the default egress posture, where do my secrets live, what is retained and for how long, and can I get the execution logs. If the default egress posture is "open", that is a deal-breaker regardless of how good the isolation is, because ring 4 is the one that stops exfiltration.

F11

"Hasn't the industry solved this before? Why is it hard now?"

It has, and I think the closest precedent is the web browser — which is genuinely encouraging and genuinely sobering. In 1995 the industry decided to download arbitrary code from strangers and run it on every desktop in the world. The answer was never "verify the JavaScript is safe"; it was thirty years of layered containment: the same-origin policy, then sandboxed renderers, then Content Security Policy, then per-origin process isolation after Spectre.

The encouraging half is that the pattern works — running untrusted code turned out to be a solvable engineering problem. The sobering half is the timeline, and the fact that every one of those layers was added after an exploit class made it unavoidable. Agent sandboxes are somewhere around 2004 on that curve. The specific thing that is harder this time is that the browser's untrusted input is code, which you can contain, while ours is natural language that becomes code — so the boundary between instructions and data is inside the model, where no runtime control can reach it.

F12

"You have one week. What do you build first?"

Egress deny-by-default, then credential isolation, then a wall-clock kill. Those three in that order, because they are the ones where the failure is unrecoverable: data that has left cannot be recalled, and a leaked long-lived key outlives the incident. Resource limits and dependency pinning are week two — a runaway loop costs money and wakes someone up, but it's recoverable.

And I'd ship it scoped rather than general: one task shape, one allowlisted destination, one tool surface behind the proxy, with the JSON path still live as the fallback. Then measure the crossover on real traffic before widening it. The failure mode I'd be trying hardest to avoid is turning it on everywhere because the token graph looked good.

Glossary

Meta-tool
A tool whose outputs are themselves programs over other tools. Code execution is one; so is any tool that returns a plan the agent then executes.
Action space
The set of things an agent can do at one step. Finite and enumerable for a tool menu; unbounded for an interpreter. Almost every consequence in this question follows from that one difference.
CodeAct
The pattern of having the agent emit executable Python as its action, rather than a JSON call or free text. Named by the 2024 ICML paper of the same idea.
Programmatic tool calling
The hybrid: the model writes code, but the code calls your declared tools inside a container rather than making open network calls. Keeps the schema boundary on effects.
Progressive disclosure
Loading tool definitions on demand instead of all upfront — as a filesystem of stubs the agent explores, rather than 70 schemas in the system prompt.
Blast radius
What breaks if this component does the worst thing it is capable of. The organising question for every control in this answer.
Lethal trifecta
Private data + untrusted content + external communication. Any two are survivable; all three make exfiltration a matter of getting text in front of the agent.
Slopsquatting
Registering a package name that models hallucinate, so the next agent that imports it installs the attacker's code. Distinct from typosquatting: the name was never a typo, it was invented.
microVM
A minimal virtual machine with its own guest kernel (Firecracker, Kata). An attacker must escape the guest kernel and the hypervisor, unlike a container that shares the host kernel.
gVisor
A user-space kernel that intercepts syscalls and services them in Go, so sandboxed code never talks to the host kernel directly. Between containers and microVMs on both isolation and overhead.
Egress allowlist
Deny all outbound network by default; permit named destinations for this task. The single highest-leverage control, because it converts "the agent was manipulated" into "and nothing left."
Credential broker / tool proxy
A component outside the sandbox that holds secrets and attaches them to outbound calls. The program receives capabilities, never keys — and the proxy's log becomes an audit trail the program cannot forge.
Idempotency key
A caller-supplied identifier that makes repeating an operation safe. The control that turns "the program died after six of twelve writes" into "run it again."
Rice's theorem
Any non-trivial semantic property of programs is undecidable. The formal reason static analysis of generated code is a filter and not a boundary.

One last thing to have ready

If they ask what you'd want to know before deciding, the best answer is a question about provenance: "where does the input to this program come from?" An agent that only ever sees data your systems produced is a very different risk from one that reads web pages, email or customer tickets. The first can probably live in a hardened container. The second needs a kernel boundary, a locked egress, and the assumption that the program is written by an attacker — because occasionally it will be.
