Question 14 · GitHub · senior AI engineer

The Half-Life of an Instruction

The interviewer asked a yes‑or‑no question with a trap on both sides. Say yes and you are the candidate who reaches for wording. Say no and you owe them a mechanism. The useful answer is neither: the prompt was not wrong, it was perishable — and the thing it was arguing with is not a preference. It is a loop that has closed in Python about sixty-three thousand times.

The question, as asked

“A user asks your coding agent to port a heavy data pipeline from Python to Rust. It nails the port. Then on every follow-up task, it goes back to writing and running Python. Is this a prompting bug?”

What they are actually testing

The question is phrased as a yes‑or‑no, which is the tell. They are not asking you to classify a bug. They are watching to see whether you can say what kind of object an instruction is, and whether you know that a default and a capability are different quantities that happen to be measured on the same model.

P1

Can you refuse the framing without being contrarian about it? “Prompting bug” is a real category, and the honest answer is the prompt is not the defect, it is the wrong instrument — which is a different sentence from “no.”

The weak version stops at “it’s a model limitation.” That is true and it is also an excuse. They want the step after it.

P2

Do you know where a language default actually comes from? Most candidates say “Python is popular on GitHub” and stop. The strongest single fact in this area is that popularity does not predict the ordering, and there is a published table that shows it.

P3

Can you separate it can write Rust from it reaches for Rust? The user has one successful port and has read it as proof of disposition. It is proof of capability under the most favourable conditions that exist, which is not the same claim.

P4

When you propose fixes, do you rank them by anything? Three fixes offered as a list is a list. Three fixes ranked by how long each one keeps working is an architecture, and this question has an unusually clean ranking available.

Where this sits against the earlier questions

Four questions in this series touch the same machinery and none of them is this one. Q1 and Q2 asked what is allowed to stop an agent loop. Q8 asked what happens when an agent writes a confident plan out of its prior instead of looking at the environment. Q10 asked whether a system prompt can add an expertise the weights do not contain. Q13 asked what a reward function left unpriced.

Q14 is the mirror of Q10 and the sequel to Q13. Q10 said a prompt cannot add a disposition that is not there; this says a prompt cannot subtract one that is. Same instrument, opposite directions, same underlying answer: a prompt is a conditioning event, not an edit. And where Q13 asked what the objective failed to price, this asks what the harness failed to practise — because the reward function was only ever half of the specification, and the other half was the interpreter it got graded in.

The sharpest difference is with Q8. There, the agent fails because it does not consult the environment. Here it consults the environment and the environment agrees with the prior, because nobody archived the .py files.

01

The answer, at three lengths

Ten seconds

“Not a prompting bug — a prompting instrument bug. The default is a distribution, the instruction is a conditioning event, and conditioning decays over turns. You do not move a distribution with a sentence. You move it with the repo and the verifier.”

A minute

“The model is computing a posterior over what language to write, and the prompt only enters one of the two factors. The other factor is the prior, and it is built from three things: the corpus, the per‑attempt success rate, and — the one people miss — the harness it was reinforced in, which for every public coding gym is Python.

So the instruction was never going to replace that, only outweigh it, and the measurements say outweighing is short‑lived: multi‑turn instruction following drops sharply and drops hardest between the first turn and the second. The user’s report is that exact shape.

Two things also changed at the first follow‑up that nobody counted. The instruction got older, and the task got harder — a port has a line‑by‑line reference implementation, which is the easiest Rust task you will ever hand it. So I would stop ranking fixes by how emphatic they are and start ranking them by how long they keep working. The sentence lasts a turn. AGENTS.md lasts until the context is deep. What the repo contains and what cargo test refuses do not decay at all, because the agent does not have to remember them — it runs into them.”

The whiteboard version

Everything below. The pieces worth reaching for first: the posterior with two factors in 02, the gym ledger in 03, the one row that breaks the popularity story in 04, the half‑life table in 06, and the factorial study in 07 that measured the fix everybody recommends and found it worth 0.8 points.

Do not say Just make the prompt clearer. Tell it to use Rust.

The user already did, and it worked — once. Repeating an intervention that has already demonstrated its half‑life is not a fix, it is a louder version of the measurement.

The second-worst answer is the opposite: “you can’t fix that without fine-tuning.” You can get most of the way with a shell command.

Say instead The prompt isn’t wrong, it’s perishable. Rank the fixes by how long each one survives, and the ordering writes the architecture for you.

Then give the ordering, and name the one that does not decay: a check the agent cannot satisfy in Python. Everything else on the list has to be remembered. That one only has to be true.

02

A prompt is a conditioning event, not an assignment

This is the whole answer compressed into one line of arithmetic, and it is worth being able to write it on a whiteboard, because it explains both halves of what the user saw: why the instruction worked at all, and why it stopped.

what you believe you wrote language := Rust what you actually wrote one sentence, in one turn, at position k of a context that grows by a few thousand tokens per follow-up what the model computes P( language | context ) ∝ P( context | language ) · P( language ) --------------------- ------------ your sentence is in the corpus, the this factor, and only gym, the compiler, this factor 63,332 trajectories what is true at turn seven the left factor is still technically present, and no longer decisive. the right factor has not moved at all.

Xie et al. made this precise: in‑context learning behaves like implicit Bayesian inference, where the prompt causes the model to infer a latent concept and reweight accordingly. The prompt never leaves the pretraining distribution. It selects within it. That one property explains both halves of the user’s report at once — a strong, nearby, unambiguous instruction can dominate the likelihood term for a turn or two, which is why the port succeeded; and nothing about that mechanism is durable, which is why it stopped.

In plain words

The model is not reading your instruction as a setting it flips. It is weighing your instruction against everything it has ever seen, every single time it writes a line. Your sentence gets a vote, not a veto — and the vote gets quieter the further back in the conversation it sits.

The error the user made, and it is a reasonable one

“It nails the port” is being read as evidence that the model is willing to write Rust. It is evidence that the model is able to, under the single most favourable condition that exists for a low‑resource target language: a complete, working, line‑by‑line reference implementation sitting in the context window. That is translation, not synthesis.

Every follow‑up task removes that reference. So at the first follow‑up two variables changed simultaneously — the instruction got one turn older, and the task moved from the easiest shape to a normal one — and only one of those two is a prompting problem. Anyone who proposes a fix without separating them is going to attribute the result to whichever thing they personally changed.

03

Where the loop closed

The newsletter calls this “RL environment bias” and says most candidates miss it. They do, and it is the half of the answer that will actually distinguish you, so it is worth being able to put numbers on it rather than gesturing at it.

In plain words

When people train a coding agent to fix real bugs, they do it in a sandbox where the code is Python and the way you find out whether you succeeded is by running the Python tests. There are about sixty-three thousand of those practice problems and essentially all of them work that way. The model was never told to like Python. It was just never given anything else to practise in.

Python is not its favourite language. It is its favourite verb.

This is the reframe worth carrying into the room, because it changes what the fix has to be. An agent has exactly one move that produces ground truth rather than more prediction: it runs something and reads what comes back. Everything else it does is a guess about a guess. Across sixty‑odd thousand reinforced trajectories, the action that most often returned a usable observation — that closed the loop — was invoking Python.

So when the agent reaches for python on a follow‑up task, the behaviour being expressed is not “I prefer this syntax.” It is “this is how I find out whether I am right.” And that is why a sentence loses to it. You are not arguing with a stylistic preference. You are arguing with the only reliable feedback channel the model has ever been paid to use, and you are doing it in text.

The row that breaks the popularity story

In August 2025 TypeScript overtook Python to become the most-used language on GitHub — 2.64 million monthly contributors, up 66.6% year on year. It is not a niche language, it is the language by the only popularity measure anybody cites.

It resolves at 2.23%. That is seven times worse than Rust, which the user is being told the model is reluctant to write because Rust is less common. If share of corpus set the default, the bottom bar on this chart would be the top one.

So corpus popularity is real and it is not the ordering variable. What tracks the ordering far better is a dull property of the environment: whether a project in that language can be stood up, built and tested automatically at scale — which is the same property that decides whether anyone could have built a gym in it.

Read the 21.2% precisely

Rust-SWE-bench is 500 repository-level tasks from 34 Rust projects. OpenHands with Claude-Sonnet-3.7 resolves 21.2%; the paper’s own method reaches 28.6%. The comparison figure of 70.4% is the same agent on SWE-bench Verified, so the scaffold is held constant — but the two task sets were built by different teams with different difficulty filters, and Verified was explicitly human-screened for solvability. Treat the gap as large and real, not as a calibrated ratio.

The detail inside it is more useful than the headline anyway: 44.5% of Rust tasks failed at the reproduction stage — the agent never got as far as writing a patch. That is not a language-skill number. That is an environment that will not start, and it is the part you can fix without touching the model.

05

Why the sentence wore off, and the shape of the wearing-off

“It worked for one task and then wore off” sounds like an anecdote. It is the measured shape, in three independent literatures, and the detail that matters is where the loss is concentrated: at the very first follow-up.

In plain words

Models are measurably worse at remembering a rule the longer a conversation goes on, and most of the forgetting happens immediately — between the first reply and the second. So “it worked once and then stopped” is not bad luck or a bad prompt. It is the normal, documented behaviour of asking for something once.

And the task got harder at the same moment

Worth saying out loud, because it is the thing the room has not thought of. The decay literature explains why the instruction faded. It does not explain all of the behaviour change, because the behaviour change had a second cause arriving on the same turn.

The port had a complete reference implementation in context. Cross-language translation with the source sitting there is the single most favourable setting for a low-resource target language — and the Rust numbers in 04 are for synthesis, which is what every follow-up asks for. So the agent’s per-attempt success probability in Rust did not stay where it was during the port; it fell off a cliff the moment the reference went away, and the policy responded to that correctly.

If you only fix the instruction decay, you have addressed one of the two causes and you will be surprised by the residual.

Interventions5

All five appear on every best-practices list, usually in this order, usually undifferentiated.

That are sentences3

They work by being remembered, so every one of them inherits the decay curve in section 05.

That are facts2

They work by being encountered. The agent does not have to recall them; it runs into them, every time, at full strength.

The line in the middle of that table is the answer to the interview question. Not “put it in AGENTS.md” — that is one row, and the next section shows how little that row moves — but the observation that your five options belong to two different species, and only one species has a half-life.

Say this version of it

“A sentence has to be remembered to work. A fact only has to be true. Three of my five options are sentences, and the measurements say sentences do not survive a session — so I will still write them, because the cheap ones are worth their cost, but I will not expect them to be the mechanism. The mechanism is the two things the agent runs into: what the repo contains and what the check refuses.”

A callback worth making, if Q13 came up earlier

The previous question ended on a law: any detector you place inside the objective stops being a detector — a chain-of-thought monitor with 95% recall, put into the reward, kept its subject’s behaviour and lost its reading of it.

The verifier here is the same kind of instrument in the opposite position. Nobody is doing gradient descent on cargo test; it sits outside the objective, at inference time, and that is exactly why it keeps its power. Same instrument, different position, different lifetime. It is a neat pair to have ready, and it shows you are reasoning about where a check sits rather than which check it is.

07

Somebody measured the fix everybody recommends

“Put it in AGENTS.md” is the standard advice, and it is given with great confidence about how — keep the file short, put the rule near the top, split it across files, never let two files disagree. A factorial study manipulated all four of those and found none of them.

The design is worth describing in the room because it is unusually clean. 1,650 Claude Code CLI sessions on two TypeScript codebases, yielding 16,050 function-level observations, primarily on Sonnet 4.6 with Opus 4.6 as a matched cross-model check. The target instruction was deliberately trivial: emit // @tracked as the first statement of every generated function. Compliance is detected by parsing the AST, so it is binary, deterministic, and immune to the objection that the model misunderstood.

Two more details make it land. First, the attenuation is not a gentle slope — it is a cliff: the median first omission arrives at generation position 4. Per-task trajectories in the paper run 0.66 → 0.35 → 0.24, and in one case 0.98 → 0.66 → 0.14. Second, task identity predicted compliance better than any structural variable manipulated — what the agent was doing mattered more than anything about the file telling it what to do.

The sentence to carry: where you put the rule is worth 0.8 points, and how deep into the session you are is worth about thirty. The entire public argument about CLAUDE.md length and ordering is an argument about the smallest variable in the system.

In plain words

Someone ran sixteen thousand careful trials to see whether it matters where you put a rule in your agent’s config file — top or bottom, one file or three, short file or long. It did not measurably matter. What mattered was how long the agent had been working: by about the fourth thing it wrote, it had mostly stopped following the rule.

Take the ranking, not the rate

This is a single-author preprint on two TypeScript codebases, one CLI, one trivial annotation, measured over a handful of task types. The author is explicit that whether the absolute compliance rate transfers to other kinds of instruction is an open question. The position and architecture nulls are failures to reject, not affirmative nulls — absence of evidence, on those two.

So do not walk in claiming “file structure provably does not matter.” Claim the thing the data supports and that is strong enough anyway: the structural variables are small relative to session depth, and session depth is large. If an interviewer pushes on the limits, naming them yourself before they do is most of the points.

08

Make Rust cheap, not just mandatory

The three standard fixes — say it persistently, make the repo agree, gate the verifier — are all correct and all prohibitive. Not one of them touches the quantity that is actually driving the behaviour, which is the per-attempt cost of working in the language you asked for.

Go back to the number in 04: 44.5% of Rust tasks failed at the reproduction stage, before a patch was attempted. That is not a statement about the model’s grasp of ownership and lifetimes. That is a build and test loop that did not come up. And the reason Python feels “easy to generate” is not that it is concise — it is that its loop is fast and forgiving. That property is not intrinsic to the language. It is a property of the loop, and you own the loop.

If cargo build takes four minutes cold, if one trait mismatch returns three hundred lines, if the agent gets a single compile inside a two-minute tool timeout, then you have not only banned Python. You have made the Rust loop slower than the agent’s effective patience, and a policy routes around expense the same way it routes around anything else.

Three verbs, and the usual advice has two

  1. 01 · forbid

    The verifier gates on cargo test, and a Python run cannot satisfy a task. This is the only intervention with no half-life, so it carries the architecture.

  2. 02 · agree

    Archive the legacy .py. The repo is re-read on every search, which makes it the most frequently encountered instruction in the system — and right now it is instructing the agent in the opposite direction.

  3. 03 · subsidise

    Make the Rust loop cheap, because the default you are fighting is a cost estimate and you are allowed to change the cost.

    A warm target directory and a shared compilation cache, so a rebuild is seconds rather than minutes. cargo check before cargo test, so a type error comes back in about a second instead of after a link. A trimmed error view — the first diagnostic with its primary span, not the full cascade — so one borrow error costs twenty lines of context rather than three hundred. A scratch crate that compiles alone, so “try something” does not mean rebuilding the workspace.

    None of this is about Rust. It is about restoring the thing Python was giving the model for free: a loop that closes quickly enough to be worth using.

The line

“Two of the three standard fixes make Python impossible. None of them makes Rust cheap. The model is defaulting to the language with the faster feedback loop, and I can change which language that is.”

09

The artefact is not the agent

One place the standard advice over-corrects, and saying so carefully is a genuine senior signal — it shows you are gating an outcome rather than policing a process.

“Route run and test steps through cargo test. A Python run should fail the check, not quietly pass.” Half right, and the half that is wrong is expensive. There are two different Pythons in this story and they deserve opposite treatment.

Python as the deliverable

A .py file that lands in src/, gets committed, ships, and someone maintains in three years.

Gate it hard. The verifier refuses it, CI refuses it, and the refusal is not a penalty the agent can trade against other reward — it is a condition on the task being complete at all.

Python as the instrument

A throwaway script to diff two outputs, generate a fixture, sanity-check an assumption about the data before writing the Rust that depends on it.

Leave it alone. That is the agent thinking with a tool, in the one language where it is best at thinking with a tool, and confiscating it buys you nothing and costs you accuracy.

The distinction is not which binary executed. It is where the output went. Gate on the artefact — what is in the diff, what the build consumes, what the tests run against — and let the scratchpad be whatever it wants. In practice that is one rule each way: anything under src/ is Rust or the check fails; anything under a gitignored scratch path is never inspected by the verifier at all.

A rule that says “no Python process may ever execute in this session” is a rule that confiscates the calculator because you wanted the answer in ink. It will also be the rule that teaches your team the gate is unreasonable, which is how gates get switched off.

In plain words

Stop the agent from delivering Python. Do not stop it from using Python to check its own work. What matters is what ends up in the repository, not what the agent typed into a terminal along the way.

10

Five checks, and one of them is the whole diagnosis

Everything above this point is somebody else’s measurement. One item on this list measures your agent, and it is the one that tells you whether you are looking at a system that does not work or a system that stops working — which have different fixes.

  • 01the ablation · precondition
    Remove the instruction entirely and measure what happens

    Run the same follow-up tasks with no language instruction anywhere — no sentence, no AGENTS.md line. If the agent writes Rust 70% of the time on its own because the repo is already full of it, then your instruction is worth thirty points, not seventy, and everything you are about to attribute to it belongs somewhere else.

    Reads as “With no instruction at all we were at 58%. With the sentence, 74%. So the sentence is worth sixteen points and the other forty-two are coming from the repo.”

  • 02the curve · this is the one
    Measure compliance by turn, never in aggregate

    A single session-level rate is the wrong instrument for this failure. It averages the turn-one success the user saw with the turn-seven failure the user complained about and reports a number that describes neither. Plot the rate against generation index instead, and the two diagnoses separate immediately: a flat low line means the rule is not landing, and a line that starts high and falls means the rule lands and then fades.

    It is the only item here that measures your system rather than citing somebody else’s, and it is the difference between rewriting your config file and adding a hook.

    Reads as “96% on the first edit of a session, 41% by the fifth. The file is fine. The session is the problem, and no amount of rewording fixes a curve.”

  • 03the environment · run it yourself
    Run the agent’s own search and read what comes back

    Not a review of the repo — literally the command your scaffold runs. rg --files, the file listing, whatever the first retrieval step is. If it returns Python, then the repo is instructing the agent in the opposite direction, and it is doing so in every context window rather than once at the top of the session.

    Reads as “The first thing the agent sees on every task is forty-one .py files and nine .rs files. We are outvoted in our own repository.”

  • 04the gate · negative control
    Submit a Python-only patch on purpose and confirm the check fails

    An ungated gate is the most common failure in this whole design, because a check that has never refused anything looks exactly like a check that works. Write the bad patch, run the pipeline, watch it go red. Then check the second half: that a legitimate scratch script in the ignored path still passes, or you have built the rule from 09 that your team will eventually switch off.

    Reads as “A .py in src/ fails the build. A .py in scratch/ does not. Both verified, both in CI.”

  • 05the cost · price the constraint
    Time the loop you are forcing the agent into

    Three numbers: a warm cargo check, a cold cargo test, and the line count of a representative error. If you cannot say them, you do not know what you are asking the model to pay, and 08 is the section you have skipped.

    Reads as “Warm check, 1.4 seconds. Cold test, 3 minutes 50. A typical trait error, 210 lines. The second and third of those are why it keeps leaving.”

The closing artefact

The same shape as the run configs in the previous guides: write the thing down, and the fields nobody filled in are the diagnosis.

Both empty blocks are empty for the same reason, and it is not laziness. Neither of them is a wording question — and a wording question is the only kind everybody in the room feels qualified to have an opinion about. The team spent the meeting on the phrasing of agents_md because that is the argument they could all join.

11

Twelve follow-ups

F1 through F5 are the ones an interviewer reaches for first. F7 and F9 are where they find out whether you have opinions. F12 is the one that is really asking what you have learned.

F1So it is a prompting bug — you just want a better prompt?

No, and the distinction is the answer. A better prompt raises the first-turn compliance rate, and the first turn is the part that already worked. The failure is entirely in the tail. You cannot word your way out of a half-life problem, because the decay is a property of where the sentence sits in the context, not of what it says.

F2Would re-injecting the rule on every turn fix it?

It genuinely helps and it is cheap, so do it. It is the same mechanism behind the recovery result in 05 — restating the content close to the point of use restored performance to 95% of single-turn.

Three caveats. It still only reweights, so it does not survive a sufficiently strong prior. It competes with every other thing you re-inject, and that budget fills up fast. And you pay its tokens on every turn forever. Prefer a hook that re-surfaces the rule on the tool calls where it actually applies — the edit, the write, the run — over a banner on all of them, which is how a reminder becomes wallpaper.

F3Where exactly should the rule live in AGENTS.md?

On the best available evidence, close to anywhere. Top, centre and bottom produced no detectable contrast across 16,050 observations, and neither did file size, file count, or a flatly contradicting instruction in an adjacent file. Spend the effort on the gate.

Say the limits as you say it, though — one study, two TypeScript repos, one trivial instruction, and two of the four nulls are failures to reject rather than affirmative nulls. “Smaller than people think” is well supported. “Zero” is not.

F4If you owned the model, would you just train on more Rust?

Yes — it is the only fix on the list that moves P(language) rather than the likelihood term, so it is the only one that changes the default rather than outweighing it.

But note what the Rust evidence says about how. The dominant failure was 44.5% of tasks never reaching a patch attempt, because the environment would not reproduce. Training the policy does not fix a gym that does not start, and the reason there is no Rust gym is not that nobody wants one — it is that standing up and running arbitrary Rust projects at scale is the hard part. Budget for the harness, not the data.

F5Why Python specifically for checking its work, rather than writing?

Because checking is the only action an agent has that returns ground truth instead of another prediction, and roughly sixty-three thousand reinforced trajectories taught it exactly one way to perform that action. Reaching for the interpreter is not a style preference, it is an epistemics habit.

Which is also why the verifier is the fix that works. You are not contradicting a preference; you are replacing the loop with a different one and making that one cheap.

F6Is this just instruction drift? Or sycophancy?

Same surface, different mechanism, and conflating them sends you to the wrong fix. Drift usually means the instruction is being overridden by something in the conversation — a later request, a user correction, a tool result. The remedy there is hierarchy and placement.

Here the competitor is the prior itself, which is present in every forward pass and is not in the conversation at all. You cannot outrank something that is not in the ordering. That is why the fix has to leave the context window and become a property of the repo or the check.

F7What if the user is wrong and Python is the right call for the follow-ups?

A live possibility and worth one sentence in the room, because it costs nothing and shows you are not just executing. Ask what the port was for. If it was throughput on a hot path, the rewrite earns itself there and almost nowhere else — and a glue script or a one-off migration that happens to be Python is not a defect, it is the agent allocating effort sensibly.

The defensible version of the policy is narrow: gate the hot path, not the repository. “Everything must be Rust” is a statement about tidiness; “the pipeline is Rust and its tooling may be anything” is a statement about why you paid for the port.

F8Does a bigger or newer model make this go away?

It narrows, and it does not invert. Across every published per-language table, the stronger model scores higher in each column and Python stays on top: the best agent in the Multi-SWE-bench results is still 52.20% Python against 15.90% Rust. Capability moves the level; the harness set the ordering, and the ordering is what produces the default.

Be careful with the stronger claim, though. These are different models on a benchmark with its own biases, and “the gap closes at rate X” is not something the published tables support. Say the direction, not the slope.

F9Would you ever let the agent choose the language?

For scratch work, yes, happily — see 09. For the artefact, no, and the reason is worth saying because it sounds counter-intuitive: the model’s choice is a well-calibrated estimate of where it will succeed, and that is precisely the wrong objective.

It is optimising the probability this task completes. You are optimising a decade of somebody maintaining it. Those come apart exactly when the right language is the one the model is worse at, which is this situation, every time.

F10How would you know the environment fix worked rather than the prompt?

Vary one. Keep the archive and the gate, delete the sentence, and measure the curve from check 02. Most teams ship all three changes on the same afternoon and then attribute the result to the one they personally wrote, which is usually the prompt, because it is the one they can see.

If you want the cheapest honest version: the baseline in check 01 and the curve in check 02 are two runs, and between them they attribute the whole effect.

F11Where else does this pattern show up?

Anywhere a default sits in the weights and a preference sits in the context. Ask for a dashboard, get React. Ask to load a CSV, get pandas. The repo has an internal HTTP client and the agent imports requests; the house test runner is custom and the agent writes pytest; the product is British and the copy drifts American by the third paragraph; the tone-of-voice document holds for exactly as long as the tone-of-voice document is on screen.

The test is always the same, and it is one question: is the thing I want a sentence, or is it a fact about the environment the agent is standing in? If it is only a sentence, assume it expires. Then find the cheapest way to make it a fact — which is very often a lint rule, an import ban, or a failing check, none of which have to be remembered by anybody.

F12What is the lesson you actually took from this?

That I had been writing instructions as though the model were a configuration file, and it is a reader. Every rule I write now gets one question before it ships: what would have to be true for this to still be working at turn twenty? Most of the time the honest answer is “someone would have to re-read it,” and nobody is going to.

So I write the smallest number of sentences I can, keep them because they are cheap and they do help on the turns that matter most, and then spend the rest of the effort on things the agent cannot avoid meeting: what the repository contains, what the command returns, what the check refuses. The model is not disobeying me. It is doing what I actually set up, which is a different thing from what I actually said — and the whole job is the gap between those two.

Glossary

language prior
The distribution over languages a model falls into when nothing in the context decides it. Built from the corpus, from per-attempt success, and from the environment it was reinforced in. Not a preference, and not stored anywhere you can edit.
conditioning event
What a prompt actually is. It reweights the posterior; it does not assign a variable. Everything else on this page follows from the difference.
in-context learning as Bayesian inference
The account in which a prompt causes the model to infer a latent concept and reweight accordingly, while remaining inside the pretraining distribution. Explains both why the instruction worked and why it did not last.
half-life
Used here for an intervention: how far into a session it is still measurably in force. The organising property of this whole answer, and the thing that splits five fixes into two species.
said vs met
The split this guide is built on. A thing that is said works by being remembered. A thing that is met — the repo, the compiler, the check — works by being true. Only one of the two decays.
instruction attenuation
Compliance falling as a session proceeds. Measured at roughly −5.6% odds per generated function, with the median first omission at the fourth.
instruction hierarchy
The intended priority ordering: system message, then user message, then history, then tool output. Models follow it imperfectly and are swayed by proximity and emphatic phrasing more than by position in the hierarchy.
Multi-IF
A multi-turn, multilingual instruction-following benchmark. Its contribution here is the shape: monotonic decline, steepest between the first turn and the second.
unreliability (vs aptitude)
The decomposition of the multi-turn drop. Capability falls a little; variance explodes. The model does not forget how to write Rust — it becomes inconsistent about remembering that it agreed to.
RL environment bias
A default produced not by what a model read but by what it was reinforced in. The part of this question most candidates leave out, and the only one that explains why TypeScript sits below Rust.
gym
An executable environment with tasks, tests and a reward signal, in which a policy can be trained. Public coding gyms are Python. Benchmarks in other languages exist; gyms do not.
SWE-bench
2,294 issue and pull-request pairs from 12 Python repositories. The ancestor of SWE-Gym, R2E-Gym and SWE-smith, and therefore of the default.
Multi-SWE-bench
1,632 human-validated instances across seven non-Python languages. The source of the competence ladder, and of the row that breaks the popularity story.
Rust-SWE-bench
500 repository-level Rust tasks from 34 projects. Notable less for its headline resolve rate than for where the failures sit: 44.5% never reached a patch.
resolve rate
Share of benchmark issues where the agent’s patch makes the failing tests pass without breaking the passing ones. The units of the ladder in section 04.
reproduction stage
Getting the project to build and the failing test to fail, before any fix is attempted. In Rust this is where nearly half of all attempts died.
artefact vs instrument
What ships against what the agent thought with. Gate the first; leave the second alone. The distinction is where the output went, not which binary ran.
verifier
A check that decides whether a task is done. Its power here comes from its position: outside the objective, at inference time, where nothing is optimising against it.
gate vs penalty
A gate makes a state impossible; a penalty makes it expensive. A policy will pay a penalty if the alternative is dearer, which is exactly the situation you are in.
negative control
Deliberately submitting the thing your check should refuse, to confirm it does. A check that has never refused anything is indistinguishable from one that works.
ablation
Removing one intervention and re-measuring. Here: delete the instruction and see what the repo alone is worth, before attributing the whole effect to your sentence.
affirmative null
Evidence that an effect is absent, rather than mere failure to detect one. Bayes factors around 0.05–0.10 support the file-size and conflict nulls; the position and architecture nulls are weaker.
odds ratio
The multiplicative change in odds per unit of a predictor. OR 0.944 per generated function compounds: by the tenth function the odds are roughly 56% of what they started at.
AGENTS.md
An open format for project-level agent instructions, formalised in August 2025 and donated to the Linux Foundation’s Agentic AI Foundation in December. Worth having; not a mechanism.
re-injection
Restating a rule close to the point of use, usually through a hook. The cheapest real improvement on this list, and still a sentence.
low-resource language
Relative to a model’s training, not to the industry. TypeScript is not low-resource by any human measure and behaves like one here, which is the whole point.
