Question 11 · Google DeepMind · senior ML engineer

The Twin in the Test Set

You scraped GitHub, held out a random 5% of files, and the new model jumped. The split did exactly what shuffle=True promises: it drew rows uniformly at random. The trouble is that on GitHub a row is not a unit of information — seventy per cent of files are copies of a file that already exists — so the shuffle took a copy of the answer and put it on the other side of the line.

The question, as asked

“You scraped GitHub, held out a random 5% of files as your test set, and your new code model just posted a big jump on it. Before you announce anything, what’s the first thing you’d suspect about how that split was built?”

What they are actually testing

The question gives you a result and asks what you suspect about the procedure. That phrasing is the tell. They are not asking you to debug a model. They are asking whether you treat an evaluation as a measurement with a method, or as a number that arrives.

P1

Can you tell two diseases apart that share one symptom?

Overfitting and leakage both look like “the number is too good.” They have opposite fixes. Overfitting means the model learned the training set and the held-out set punishes it — so you regularise. Leakage means the held-out set is the training set, the training curves look healthy, and regularising makes things worse, because you are penalising the model for learning data you are about to score it on. A candidate who says “overfitting, add regularisation” has reached for the famous word rather than the mechanism.

P2

Do you know what the thing you scraped actually contains?

“GitHub is duplicated” is a vibe. “Four hundred and twenty-eight million files collapse to eighty-five million unique ones, in a corpus that already excludes forks” is a fact, and it is published. The difference between those two sentences is the difference between a worry and a review.

P3

Is grouping one of the first things you reach for, or one of the last?

Senior practitioners in any field with repeated measurements — medical imaging, speech, recommender systems, genomics — ask “what is one row a sample of?” before they ask anything about the model. The habit transfers. If you have ever had to split by patient rather than by scan, you already know this question; the only new thing is which key GitHub needs.

P4

Can you turn a suspicion into a cheap measurement with a decision attached?

Suspicion is free and nobody is impressed by it. The senior move is to name a number you can have by tomorrow that settles it — and to say in advance what each outcome would mean. The number is in section 09, it costs one afternoon, and you already have both of the artefacts it needs.

01

The answer, at three lengths

Lead with the suspicion, because that is literally what was asked. Then earn it with the corpus, and close with the one measurement that settles it. Do not start with MinHash — the tool is the fourth sentence, not the first.

Ten seconds

“That the split was random at the file level. On a GitHub scrape that isn’t really a split — most files are copies of a file that already exists, so a random cut puts twins on both sides of it. Before I suspect anything about the model, I’d suspect the test set is partly inside the training set.”

A minute

“Random splitting assumes rows are exchangeable — that one file is one independent draw. GitHub violates that badly. Lopes and colleagues measured 428 million files across four languages and found 85 million unique ones, in a corpus that had already excluded forks. Vendored dependencies, copied solutions, re-licensed libraries, and plain copy-paste do most of it.”

“The arithmetic is unforgiving. Take a test file that has exactly one twin somewhere in the corpus — the mildest possible case. With a 5% test fraction, the chance that twin landed in training is 95%. Clusters are usually much bigger than two, so in practice most of my test set has already been seen, and scoring it measures retrieval from weights rather than generalisation.”

“So the first thing I’d do costs an afternoon, not a retrain: near-dedup with MinHash, re-split by duplicate cluster and fork network, and re-run the same evaluation. I don’t need the new number to be good. I need the gap between the two numbers, because that gap is the leakage estimate, and it is the only thing I’d be willing to put in an announcement.”

Three minutes

Everything above, then the shape of a split you would defend:

Dedup before you split, not after. Exact hashing is not enough — the same file differs by a licence header or a version bump. MinHash over token 5-grams with an LSH index and a Jaccard threshold around 0.7 is what the open code corpora actually use. Then take connected components to turn pairs into clusters — and put a cap and a re-verification step on that, because near-duplication is not transitive and one bad edge chains unrelated files into a mega-cluster.

Split by group, and be explicit about which group. The unit is the duplicate cluster unioned with the fork network unioned with the repository. Repository alone is the floor, not the answer: vendored code crosses repositories, which is exactly why a repo split still leaks.

Split by time as well, and say which clock. Train before a cutoff, test on repositories created after it, because that is how the model gets used. But be honest that a timestamp on a commit is not the age of the code — vendored libraries are decades older than the commit that added them — so time orders events and does not order copies. Time and grouping fix different leaks.

Then audit, because every dedup has a residual. Bucket each test item by its maximum similarity to anything in training and report the headline metric per bucket. If the jump lives in the high-overlap bucket, you measured memorisation. Riddell and colleagues did exactly this on HumanEval: StarCoderBase scored 75.0 on the decile most similar to training and 31.3 on the decile least similar. Two other models scored zero on that bottom decile.

And say what the split licenses. “This model is better” is not a claim a split can support. “This model is better on code with no near-twin in our training corpus, measured on repositories created after March” is — and it is a sentence you can defend in front of anyone.

Do not say Overfitting. I’d check the training curves and add regularisation.

Wrong organ. Overfitting is a gap between train and test; this is the absence of a gap because there is no real test. The training curves will look fine, because nothing went wrong during training. Regularisation will reduce the number without telling you why, and you will have paid capability for a symptom.

The second-worst answer is the opposite reflex: “dedup the data.” True, insufficient, and it skips the part they asked about. The question was about the split.

Say instead On code, a random file split measures memorisation, not generalisation. I’d dedup near-duplicates, split by fork cluster and by time, and trust the jump only if it holds on examples with no near-twin in training.

Names the mechanism, names the fix, and attaches a condition to the belief. The last clause is the one that reads senior: it is a pre-registered reason to stop believing your own result.

In plain words

A test set is meant to hold examples the model has never learned from. Shuffling files gives you that only if every file carries its own information, and on GitHub most files are copies of another file. So a copy of a test file usually sits in training, and the score measures recall rather than skill. The fix is to decide what one row really stands for and split on that unit, not on the row.

02

A split is a claim, and the shuffle makes the wrong one

Before any of the GitHub specifics, the thing worth being able to say cleanly: what is a held-out set for, and what exactly does randomising it buy you? Almost everyone can answer the first. The second is where the question lives.

A test set exists to estimate one quantity: how the model will do on inputs it has not learned from. That needs two properties, and they are not the same property.

  • Representativeness. The test items should look like what the model will meet in deployment. This is the one everybody checks.
  • Informational disjointness. The test items must not already be inside the thing you trained on. This is the one shuffle=True is assumed to deliver, and the assumption is doing all the work.

Randomising rows gives you disjointness of rows. It gives you disjointness of information only when one row is one independent piece of information. That is the exchangeability assumption, and it is a claim about the data, not about the code:

WHAT YOU MEANT TO ESTIMATE E[ loss(model, x) ] over x the model has not learned from WHAT A RANDOM FILE SPLIT ESTIMATES E[ loss(model, x) ] over x not literally present in train — a copy of x may be present, and usually is THE TWO AGREE ONLY IF every file’s content appears in the corpus exactly once

The split did what it promised. It drew rows uniformly at random. The defect is not in train_test_split; it is in the sentence nobody wrote down, which is that a file is a unit of information. On GitHub that sentence is false for most files, and the function has no way to know.

Three different things are called “leakage”

Worth separating out loud, because an interviewer may move between them and the fixes do not transfer:

  1. Target leakage

    A feature contains the answer. The classic tabular ML bug — account_closed_date in a churn model.

    Fix: remove the feature. Nothing to do with splitting.

  2. Train / test contamination

    The test item, or something indistinguishable from it, is in your training set. This question.

    Fix: group-aware splitting. You control both sides, so this one is entirely yours to solve.

  3. Benchmark contamination

    A public benchmark leaked into a pretraining corpus you did not build and cannot inspect. HumanEval inside The Stack; LeetCode solutions inside everything.

    Fix: you cannot un-train it. You either measure it (section 05) or move to data created after the model’s cutoff (section 08).

Figure 1 · DéjàVu, OOPSLA 2017. “70% of the code on GitHub consists of clones of previously created files.” Three similarity levels were used: a file hash for byte-identical copies, a token hash that survives changes to whitespace, comments and ordering, and SourcererCC at 80% token similarity for files edited after copying. The sentence that makes this an interview answer

That corpus contains no forks. The study analysed 4.5 million non-fork projects, explicitly excluding forks because “we expect [them] to contain duplication.” Everything in Figure 1 is what is left after the obvious cause has been removed.

Which reorders the newsletter’s own list. Forks are the cause everyone names first, they are a single column in the GitHub API, and they are the cheapest thing on the list to remove. They are also not the problem. A candidate who says “I’d drop the forks” has named the one fix you can apply in an afternoon and will not notice the difference afterwards.

Five ways a copy gets in, ranked by how much they actually cost you

  1. 1 · Vendored code

    Third-party libraries committed into the repository under vendor/, third_party/ or node_modules/. This is the big one.

    DéjàVu traced JavaScript’s 94% clone rate to exactly this: packages committed as if they were application code. A small minority of repositories contributes the overwhelming majority of the duplicated files, which is why “most repos look fine” is not reassurance.

  2. 2 · Near-duplicates

    Same file, different licence header. Same file, one renamed variable. Same file, a version bump. Exact hashing sees two distinct files; a human sees one.

  3. 3 · Copied solutions

    The same answer to a popular problem, pasted into thousands of repositories. LessLeak-Bench, auditing 83 SE benchmarks, found leetcode appearing eight times in the names of the top twenty leaking repositories alone.

  4. 4 · Forks

    Thousands of copies of one popular repository at different paths. Real, easy to find, and — per Figure 1 — not where the mass is.

  5. 5 · Sibling files

    Zero duplication required. Two files from the same repository share helpers, identifiers, idioms and style. Train on models.py, test on utils.py, and the model already knows the API it is being asked to invent.

    This one survives every dedup you can run, which is why the grouping key has to include the repository even after the clusters are correct.

In plain words

A random split decides each file’s side on its own, like a separate coin flip. Hold out 5% and a file with even one twin has a 95% chance that the twin landed in training, and bigger groups of copies are near-certain to leak. A bigger test set barely helps. The fix is to move each group of copies to one side together.

The corpus numbers tell you duplication exists. They do not yet tell you it reaches your test set. That step is one line of arithmetic, and it is the part of this answer that an interviewer will remember, because it converts “I’d be worried about duplicates” into a figure with a reason attached.

That last column is worth saying out loud in an interview. A 5% test set in which four rows in five are contaminated is not a 5% test set that reads a bit high. It is a 1% test set, with the confidence interval of a 1% test set, wearing the error bars of a 5% one.

The one line of arithmetic

A uniform random file split assigns every file independently. So for a file whose content appears k times in the corpus, the chance that at least one of its k−1 twins landed in training is just the chance they did not all land in test:

P(a test file’s twin is in training) = 1 − f^(k−1) f = test fraction k = number of copies of this content k = 2 k = 3 k = 5 k = 10 f = 0.05 95.00% 99.75% 99.9994% ≈100% f = 0.10 90.00% 99.00% 99.99% ≈100% f = 0.50 50.00% 75.00% 93.75% 99.80%

Three things fall out of this table, and the third is the one that closes the argument.

  1. The floor is 95%

    k = 2 is the mildest duplicate that can exist — one file, one twin, somewhere in four hundred million. At a 5% split it still leaks 95% of the time. There is no gentle version of this failure.

  2. Test-set size does not save you

    Look down the f column rather than across. Going from a 5% test set to a 50% test set — an absurd, unaffordable change — takes a cluster of five from 99.9994% to 93.75%. You cannot buy your way out of a grouping problem with more held-out data, because the quantity you are fighting is exponential in cluster size and only linear in your budget.

  3. So the corpus number becomes a test-set number

    DéjàVu puts at least 70% of files in a cluster of size two or more. Multiply by the 95% floor and roughly two-thirds of a random 5% test set already has a twin in training — before anyone touches a model.

    That is a floor on both factors: 70% is the published lower bound, and real clusters are far larger than two. Derived here, not published. Say so if you use it — the derivation is the credible part, and it takes one sentence.

    LessLeak-Bench: on the APPS benchmark, StarCoder-7B’s Pass@1 is 4.9 times higher on leaked samples than on non-leaked ones.

  2. 53%

    And CommitBench — built deliberately from a far wider set of repositories — shows “negligible” difference between the two splits. Hold those two facts together, because section 09 is built on them.

  3. ≥70% → ≤23%

    SWE-bench Pro holds out whole private repositories instead of trusting a public set. Agents reporting over 70% Pass@1 on SWE-bench Verified resolve ≤23.3% of the public tier and ≤17.8% of the commercial tier. GPT-5 goes from 23.1% to 14.9% crossing from public repositories to private ones.

The objection you should raise before the interviewer does

Similarity to training correlates with popularity, and popularity correlates with easiness. A problem that appears a thousand times on GitHub is usually a problem that appears a thousand times because it is a common, well-understood thing to write. So part of any top-decile-versus-bottom-decile gap is difficulty, not memorisation, and a careful reader should say so unprompted.

Two things rescue the measurement. First, the direction of the confound is known and you can bound it: hold difficulty roughly fixed by comparing two models on the same buckets, since the confound hits both equally and the difference of differences does not. Second, the decision you need does not require separating them. If your model’s entire advantage sits in the high-overlap bucket, then whatever the cause, you have no evidence it will help on code your users write tomorrow — and that, not the attribution, is what the announcement would have claimed.

In plain words

Near-dedup finds files that are the same apart from small edits, like a new licence header or a renamed variable, which an exact hash treats as different. It compares files by how many five-token snippets they share, and a hashing shortcut finds the close pairs without comparing every pair. Linking those pairs into groups can chain unrelated files into one giant group. So the big groups get re-checked by computing the true similarity of sampled pairs.

06

Near-dedup, and the two places it breaks

You need this mechanically, because the follow-up is always “how?” and a vague gesture at MinHash is worse than not mentioning it. It is four ideas, none of them hard, and one of them has a failure mode that is far more interesting than the algorithm.

Start from why the cheap thing fails. An exact hash is a function of every byte, so a file that differs by a licence header, a renamed variable or a version string hashes to something completely unrelated. That is not an edge case — it is the dominant kind of duplication in real repositories, and DéjàVu measured 46% near-duplicate clones in Java against 40% byte-identical ones.

So you need a similarity that survives small edits, and a way to find it without comparing every pair. At 428 million files, every pair is about 1017 comparisons, which is not a budget problem but a physics one.

1. SHINGLES S(x) = { every 5-gram of tokens in x } (tokens, not characters — whitespace and comments stop mattering, which is the point) 2. JACCARD J(a,b) = |S(a) ∩ S(b)| / |S(a) ∪ S(b)| 0 … 1 the honest answer, and far too slow to compute pairwise 3. MINHASH hᵢ(x) = min over s ∈ S(x) of hashᵢ(s) P[ hᵢ(a) = hᵢ(b) ] = J(a,b) ← the whole trick keep 256 of these: a fixed-size signature that estimates J to roughly ±0.06, whatever the file size 4. LSH split the signature into b bands of r rows two files are candidates if ANY band matches exactly tunes the cut-off to about (1/b)^(1/r) IN PRACTICE The Stack / StarCoder: 256 permutations, 5-gram, J ≥ 0.7

Break #1 — near-duplication is not transitive, and connected components assume it is

LSH gives you pairs. A split needs clusters, because the rule you want to enforce is “every copy on the same side,” and that is a statement about a whole group. The standard move is to build a graph with one node per file and one edge per similar pair, then take connected components with union-find.

That step silently asserts transitivity. If A is 0.72 similar to B, and B is 0.72 similar to C, connected components puts A and C in one group even when they share almost nothing. With a non-trivial false-positive rate, a single borderline edge merges two unrelated clusters, and then a single borderline edge between those merges them with a third. The 2026 entity-resolution survey puts it plainly: assuming “A matches B” and “B matches C” implies “A matches C” “lets a single bad link chain hundreds of records together, so every cross-group merge must be actively re-verified.”

Break #2 — the threshold is a decision, and it is a different decision for training than for splitting

Every number in the pipeline above is an operating point on a precision/recall curve, and the right operating point depends on what the clustering is for. These two uses get conflated constantly and they pull in different directions for different reasons:

Using the clusters to…A false positive costsA false negative costsSo bias toward
Filter training dataYou drop a file you could have trained on. Cheap — you have plenty.You train twice on the same content. Mild: wasted compute, more memorisation.Recall, mildly. BigCode found that skipping the double-check entirely and treating every LSH candidate as a duplicate gave the best downstream model.
Define a splitYou move a file to the wrong side. You lose a test row.A twin straddles the line. Your headline number is wrong and nothing tells you.Recall, hard. The two errors are not remotely the same size.

This asymmetry is the reason to say “I’d run the split clustering at a looser threshold than the training filter” rather than quoting one number for both. A false negative in a training filter wastes a little compute. A false negative in a split invalidates an announcement, and it does so silently — which is the property that makes it worth more care than it costs.

The honest limitation to volunteer: none of this catches semantic duplication. Two implementations of the same algorithm with different identifiers, different structure and the same behaviour share almost no 5-grams, and MinHash will never see them. Embedding-based or behavioural matching finds some of those; Riddell and colleagues used a semantic matcher precisely because surface comparison is not enough. It is also slower, fuzzier and much harder to defend a threshold for. Saying “my dedup has a known blind spot and here is its shape” is a stronger position than claiming the clusters are complete.

07

The group is a property of the claim, not of the data

“Split by fork cluster” is good advice and it is not a definition. There is no single correct grouping key sitting in the corpus waiting to be found. The key is determined by the sentence you want to be allowed to say at the end — which means you have to write that sentence first, and almost nobody does.

The operative question for any candidate key is narrow: what could the model have learned from the training side that makes this test item easy for the wrong reason? Every answer to that question names a key, and the keys nest.

The problem that appears the moment you do this properly

Union the three keys together and you have done another connected-components pass, with the same chaining risk as section 06 and a much more concrete cause. One vendored library sitting in ten thousand otherwise unrelated repositories links all ten thousand repositories into one group. Do that across a few popular packages and a large fraction of your corpus is a single group, and a group-aware split of it is either impossible or useless.

This is the point at which most teams quietly abandon the grouped split and go back to the random one. It is also the point where the right answer stops being “group harder” and becomes a different question entirely.

Three things you can do with a copy, and only one of them is grouping

The giant-group problem dissolves once you stop treating every duplicate the same way. A copy can be deleted, grouped, or kept and weighted — and choosing correctly per cause is what keeps the partition tractable:

  1. Delete

    Vendored dependency trees. node_modules/, vendor/, third_party/, checked-in minified bundles, generated protobuf stubs.

    This is not your code, your users do not write it, and it is the single largest source of duplication in the corpus. Removing it by path is cheap, happens before any hashing, and it is what stops the union-find from collapsing. Do this first and the clusters you are left with are the interesting ones.

  2. Group

    Forks, copy-pasted solutions, re-licensed files, siblings. Genuine, meaningful code that happens to exist more than once.

    These belong on one side of the line together. They are also, after the deletion pass, a much smaller and much better-behaved graph.

  3. Keep and weight

    Training only, and worth saying because it pre-empts the strongest objection to all of this. Duplication in the training corpus is a frequency question, not a leakage question — you may legitimately want the model to see common idioms more often than rare ones, and down-weighting beats deleting when the duplicate reflects real-world prevalence.

    The rule that keeps the two apart: you may choose to train on duplicates. You may never score on them.

In plain words

A time split trains on older code and tests on newer code, so it blocks leaks you never thought to list. But the dates in a scrape say when code was committed or a repository was made, not when the code was written. An old library copied into a new repository lands on the test side while the original sits in training. So use time and grouping together, because each catches what the other misses.

08

Time orders events. It does not order copies.

The temporal split is the other half of the standard answer and it is worth more than it is usually given credit for — for a reason that is not the reason people give. It is also, on a scrape, much harder than it sounds, because the timestamp you have is almost never the timestamp you want.

The usual argument is deployment realism: train on code written before a cutoff, test on repositories created after it, because that is how the model will be used. True, and the field has built real infrastructure on it. LiveCodeBench tags every problem with a release date and evaluates over time windows, so a model can be scored only on problems published after its own cutoff — and the characteristic signature of contamination is visible directly in the plot: a model’s score drops sharply at the boundary of its training data. SWE-rebench continuously harvests fresh tasks and compares them against SWE-bench Verified for the same purpose. SWE-bench Pro takes the structural version and keeps an entire tier of private repositories that nobody can scrape.

The real reason a temporal split is worth having

It is the only defence that works against the leak channel you did not think of.

A group-aware split requires you to enumerate the ways a copy can arrive. Forks, vendoring, copy-paste, siblings — you fix the ones you listed, and the ones you did not list go straight through. A temporal cutoff needs no enumeration at all: code that did not exist when you trained cannot have been in your training set, whatever the mechanism would have been.

Grouping is precise and requires a complete list. Time is blunt and requires nothing. That is why mature evaluations use both, and why “I’d do a grouped split” is a weaker answer than “I’d do a grouped split and a temporal one, because they fail differently.”

Which clock, though

Now the part that is specific to scraped code, and the part most candidates miss. A temporal split needs the date the code was written. A scrape gives you none of these things:

  1. Commit timestamp

    The date somebody committed this file to this repository. For vendored code, that is the date it was copied in — which can be fifteen years after it was written. It is also author-supplied metadata and freely rewritable.

  2. Repo created_at

    When the repository was made. Says nothing about the age of what is inside it: a repository created last month can be a mirror of a project from 2009.

  3. File mtime

    The moment your scraper cloned it. Carries no information whatsoever and is nevertheless occasionally used.

So the failure is concrete and easy to state: a 2014 library vendored into a repository created in 2026 lands cleanly on the “after the cutoff” side of your temporal split, while the 2014 original sits in training. Nothing about the cutoff noticed, because copying is not an event in the file’s own timeline. Time orders events. It does not order copies.

In plain words

Before announcing, measure how big the leak is on your own data. Re-split so whole groups of copies stay on one side, run the old and new models again, and compare with the random split. The difference between the two is how much of the jump was the model recalling answers it had already seen. It costs an afternoon and no retraining.

09

What you check before you announce

Five checks. One of them is a gate and the other four are permits, and the distinction matters because an interviewer is listening for whether you can rank your own list. If you have time for exactly one thing before the announcement goes out, it is number two, and it costs an afternoon.

  1. Check 1 · unitspermit
    What is one row a sample of — and how was the 5% drawn?

    Ask it out loud and watch what happens. “Five per cent of files” and “five per cent of repositories” are different experiments with the same number attached, and a surprising number of teams do not know which one their pipeline did because the splitting happens three layers down in a data loader someone wrote in a hurry.

    Also ask when the split was created. A split generated fresh on every run with a new seed is not a held-out set at all — it is a slow leak, because across enough runs every file eventually sits in training.

    If this is unanswerable the rest of the list is academic. Go and read the data loader.

  2. Check 2 · the gapgate
    Re-split by cluster, re-run both models, and report the difference between the two numbers.

    This is the whole review compressed into one measurement. Strip vendored paths, cluster what is left, hold out whole clusters to the same budget, and run the identical evaluation. You do not need the grouped number to be good. You need the gap, because the gap between a random split and a grouped split on your corpus is a direct estimate of how much of your headline was memorisation.

    And the gap is genuinely corpus-specific, which is why no amount of reading substitutes for running it. On MCMD, moving to a repository-based split cost 53%. On CommitBench, built from a far wider pool of repositories, the same change was “negligible.” Identical procedure, two corpora, two completely different answers. Yours is one of those and you do not know which.

    It is the gate for a reason the other four are not: it is the only item on this list that measures your own data rather than citing somebody else’s. Everything above is evidence that the problem exists in general. This is the number that says whether it exists in yours.

    Cost One afternoon. No retraining, no new labels, no new eval harness — you already have the corpus, the models and the scoring code. The only new artefact is a different list of file paths.

  3. Check 3 · residualpermit
    Bucket every test item by its maximum similarity to training, and report the headline per bucket.

    Every dedup has a residual and the residual is invisible in the average. Build a nearest-neighbour index over the training side, score each test item by its closest match, and split the metric into buckets — exact match, high overlap, moderate, and none. This is the measurement Riddell and colleagues used to get 75.0 against 31.3 on the same benchmark on the same day.

    One detail decides whether the audit is worth anything: the index has to use the same notion of similarity the clustering used. Dedup on token 5-grams and then audit with embeddings and you have measured a different leak than the one you tried to fix, and the clean-looking result tells you nothing about the grouping you actually shipped.

    Report it bucketed, never only averaged. An average over four buckets is exactly the artefact that hid the problem in the first place.

  4. Check 4 · the clockpermit
    Add a temporal cutoff, name which timestamp you used, and re-run the baseline on the same set.

    Time catches the leak channels you failed to enumerate, which is the one thing grouping structurally cannot do. But say which field you split on and what it actually means — repo_created_at is not the age of the code — and accept that vendored code walks straight through a temporal cutoff.

    The baseline re-run is the non-negotiable half. Without it a drop is uninterpretable: distribution shift moves both models down and preserves the gap, leakage collapses the gap. One extra run of a model you already have separates them.

    Say whose cutoff. If you fine-tuned somebody else’s checkpoint you do not know the base model’s cutoff, and claiming a clean temporal split without that caveat is a claim you cannot support.

  5. Check 5 · cluster hygienepermit
    Report the largest component’s share of the corpus, and re-verify the big ones.

    A dedup that chained itself into one giant component looks, from the outside, exactly like a dedup that worked: files went down, clusters exist, the pipeline exited zero. Publishing the largest-component share makes the difference visible in one number. Sample pairs from inside the biggest components, compute true Jaccard rather than the MinHash estimate, and check whether a component is one thing or two things joined by a single edge.

    And do the deletion pass before any of this. Stripping node_modules/, vendor/ and third_party/ by path is the largest single lever available, it is nearly free, and it is what stops one popular package from linking ten thousand unrelated repositories into a single ungroupable blob.

    Big is not the same as wrong. DéjàVu’s largest clone group held over 65,000 files and was entirely correct. The test is whether it survives re-verification, not whether it is large.

The artefact: a split manifest

None of the above survives the week unless it is written down next to the evaluation and reviewed like code. A split is a scientific instrument and it currently ships with no documentation at all. This is the shape of the thing that fixes that:

Twelve follow-ups

The first four are mechanical and you should be fluent. Five through eight are where the interview is actually decided, because each one has an obvious wrong answer that sounds right. The last four are about judgement and have no single correct answer — only better and worse reasoning.

F1Why not just hash the files? Exact matching is cheap and has no threshold to argue about.

Because it has already been tried, by competent people, on a public corpus, and it was not enough. StarCoderData was decontaminated against HumanEval and MBPP with string matching before release. Riddell and colleagues then searched it and still found exact matches for 18.9% of HumanEval and 20.8% of MBPP.

The mechanism is simple: a hash is a function of every byte, so a licence header, a version bump or one renamed identifier produces a completely unrelated digest. DéjàVu measured this directly — Java has 40% byte-identical duplicates and 46% near-duplicates, so moving from exact to near matching found a further sixth of the corpus. Exact hashing is a cheap first pass and I would still run it, because it is free and it removes the easy mass before the expensive stage.

F2You run the pipeline and a third of your corpus ends up in one cluster. What happened?

Almost certainly transitive chaining. LSH produces pairs; connected components turns pairs into groups and in doing so asserts that near-duplication is transitive, which it is not. A single false-positive edge merges two unrelated clusters, and once a few of those exist the components cascade.

The second possibility is that it is correct, and I would check that before assuming a bug: DéjàVu’s largest clone group had over 65,000 files in it, and was real. So the diagnosis is re-verification, not a size cap — sample pairs from inside the component, compute true Jaccard, and see whether it is one dense blob or two blobs joined by one edge.

The fix that actually works is upstream of all of it: delete vendored paths before hashing. One popular package checked into ten thousand repositories links all ten thousand into one group, and removing it by path costs nothing and dissolves most of the problem.

F3Defend 0.7. Why not 0.8, or 0.5?

Honestly: because it is what the open code corpora converged on, and because it was arrived at by someone moving off a worse value. SantaCoder started at unigram shingles with a 0.85 threshold, found unigrams generated far too many false positives, and moved to 5-grams at 0.7 — which removed a further 16–20% of files from an already-deduplicated dataset. The shingle size and the threshold trade off against each other and it is not meaningful to quote one without the other.

What I would not do is quote the same number for two different jobs. For a training filter and for a split, the error costs are asymmetric in different ways. Over-removing from training wastes a little data you have plenty of; BigCode found that skipping the verification step entirely and treating every LSH candidate as a duplicate actually gave the best downstream model. Over-removing from a split costs you test rows. Under-removing from a split leaves a twin across the line and silently invalidates the headline. So I would run the split clustering looser than the training filter, and say that is a deliberate choice rather than an oversight.

F4Suppose the training corpus is already deduplicated. Do I still need a grouped split?

Yes, and the two are doing different jobs. Deduplicating the training corpus changes what the model saw — it reduces memorisation and, per the BigCode and SantaCoder results, generally improves the model. A grouped split changes what the evaluation measures. Neither implies the other.

The concrete case: dedup collapses a cluster of five copies to one surviving file. That file is still in the corpus, and a random split can still put it in training while a near-duplicate that fell under your threshold goes to test. Dedup reduces the number of twins; it does not change the rule that a random split assigns whatever twins remain independently.

F5Is removing duplicates not throwing away signal? Real code is duplicated too — that is the deployment distribution.

This is the strongest objection on the list and it is partly right, so I would concede the valid half immediately. For training, duplication is a frequency question. Common idioms genuinely are common, and down-weighting a duplicated file is often better than deleting it, because deleting it distorts the prior in the other direction.

For evaluation the argument does not transfer, and the reason is specific. A test set is not supposed to reproduce the deployment distribution of content; it is supposed to estimate performance on inputs the model did not learn from. If your users really do write code that already exists in your training set, then you should measure that explicitly as its own bucket, not let it hide inside an aggregate that also claims to measure novel code. One sentence covers it: you may choose to train on duplicates; you may never score on them without saying so.

F6Fine — I will split by repository. Is that enough?

It is the floor, not the answer, and it is a real improvement: a repository split blocks sibling files, which is the one leak no dedup catches. It cost MCMD 53% relative to a random split, so it is clearly doing something.

What it does not block is the largest source of duplication. Vendored code crosses repositories by definition — that is what vendoring is — so the same library sits in a thousand repositories, and a repository split puts some in train and some in test with no difficulty at all. Forks are separate repositories. A LeetCode solution pasted into four hundred personal repositories is four hundred repositories. The repository boundary is simply not the boundary duplication respects.

F7Walk me through the temporal split. Which timestamp do you use?

None of the available ones mean what I want, so the first move is to say what I actually need: the date the code was written, which a scrape does not contain. The commit timestamp is when it was committed to this repository, which for vendored code is the copy date and can be fifteen years late. repo_created_at is when somebody made the repository, which says nothing about the age of its contents. File mtime is when my scraper cloned it.

I would use repo_created_at anyway, because it is the most defensible of a bad set and it matches the deployment story — new repositories are what the model will meet. But I would record in the manifest that the field does not mean what its name suggests, and I would state the resulting hole explicitly: a 2014 library vendored into a 2026 repository lands on the test side while the original sits in training. Time orders events. Copying is not an event in a file’s timeline.

F8A temporal split makes the test set harder for reasons unrelated to leakage. How do you separate the two?

Re-run the previous model on the same temporal test set. The absolute scores are not what the announcement was about — the gap between the two models is.

Distribution shift moves both models down together and preserves the gap, because the new test set is simply harder and both feel it equally. Leakage attacks the gap specifically, because the new model’s advantage lived in items that had already been seen, and removing those items removes the advantage. If both scores fall and the gap survives, I had a harder test set and a real improvement. If the gap collapses, I had a contaminated one.

That is one extra evaluation run of a checkpoint I already have, and it is the cheapest decisive measurement in this whole area.

F9Could you not just rank test items by loss and inspect the low-perplexity tail?

It is the obvious idea and it has been tested and it does not work. LessLeak-Bench looked directly and reported that “the Perplexity of leaked samples is not necessarily lower than that of non-leaked samples” — and that above a perplexity of 10, leaked samples actually outnumber clean ones.

Which makes sense once stated: perplexity confounds memorisation with difficulty, with length, with how stereotyped the code is, and with the model’s general competence on that language. Provenance is a question about where a string came from, and the instrument for that is searching the corpus, not interrogating the model about its own memory.

F10Your audit shows the entire gain sits in the high-overlap bucket. Is the model worthless?

No — it is a model whose benefit you have now located, which is strictly better than a model whose benefit you were guessing about. Three cases, and they have different answers.

If the product is autocomplete inside a company’s own monorepo, then recognising code that resembles code already in that repository is the job, and memorisation is a feature rather than a bug. In that case I would stop calling it a generalisation benchmark and start measuring it on the population it serves. If the claim was generalisation to unfamiliar code, I have no evidence for it, and the correct action is to retract the claim rather than the model. And if the gain is large in the high-overlap bucket and merely small in the clean one, that is a genuine, narrower, defensible result — it is just a different announcement.

The output of a review like this should rarely be “ship” or “revert.” It is almost always narrow the claim to the population the evidence covers, which is why the manifest has a narrow_to field.

F11Now do it on a hundred terabytes. What breaks first?

Not the MinHash. A 256-permutation signature is about a kilobyte per file and computing it is embarrassingly parallel. LSH banding is a group-by on band hashes, which is a shuffle — large, but a solved kind of large.

What breaks is the union-find over the resulting edge set, because it is inherently sequential and the edge list runs to hundreds of millions of pairs. The practical answers are an iterative distributed algorithm — large-star / small-star contraction, which repeatedly points each node at the smallest id in its neighbourhood until the edges stabilise — or filtering hard enough that the graph fits on one big-memory machine.

The more useful answer is that for a split audit you do not need the full clustering at all. Full clustering is an all-pairs problem over the corpus. Checking whether test items have twins in training is a one-sided lookup: index the training side once, then query it with each test item. That is linear in the test set, which at 5% is twenty times cheaper, and it answers the question you actually asked.

F12What is the generalisable lesson here, beyond code?

That every evaluation has a unit of independence hidden inside it, and the name of the evaluation almost never mentions it. “Held-out 5%” tells you the size and says nothing about the unit, and the unit is where the entire validity of the number lives. Medical imaging learned it as the patient, speech as the speaker, recommenders as the user, chemistry as the scaffold. Code has not settled on a word for it yet, which is exactly why a random file split still looks reasonable to a lot of people.

The habit is not suspicion of good results — suspicion is free and it makes you tiresome in a review. It is one question, asked early and without any edge to it, of any number anyone shows you including your own: what was one row of this a sample of? If nobody in the room can answer that in a sentence, nothing else about the number is worth discussing yet.
