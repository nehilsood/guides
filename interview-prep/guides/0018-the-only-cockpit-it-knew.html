Question 17 · Google DeepMind · senior AI engineer

The Only Cockpit It Knew

An agent fine-tuned on 50,000 trajectories works in the harness the data came from and falls apart in a different one. The weights and the task are the same. Supervised fine-tuning copied every token the teacher wrote, and most of those tokens belonged to the harness, not the task. So the model learned to fly one cockpit. It did not learn to fly.

The question, as asked

“You fine-tuned an agent on 50K trajectories, all collected through one agent harness. A customer runs it in a different harness on the same kind of task, and performance collapses. Same weights, same task. What did your model actually learn?”

What they are actually testing

The trap is in the phrase “same weights, same task”. It invites you to look for the difference somewhere small, like a system prompt. The interviewer wants you to see that the difference is in what the weights contain, and that it went in during training.

Probe 1

Do you know what supervised fine-tuning actually optimises?

It does not optimise “solve the task”. It makes every token the teacher wrote more likely, given everything before it. The loss has no idea which tokens are the reasoning and which are the angle brackets around a tool call.

Probe 2

Can you explain why it collapses instead of getting a bit worse?

That is the difference between knowing the word “overfitting” and knowing imitation learning. One unfamiliar step puts the model in a state it has never seen. Its next action is worse, which makes the next state stranger still. There is a 2010 theorem for exactly this, and it says the damage can grow with the square of the trajectory length.

Probe 3

Do you look for the fix in the prompt or in the data?

A prompt changes what the model reads. The habits live in what the model is. A senior answer puts the fix where the defect went in: the training data, how it is stored, and how it is tested.

Probe 4

Would you prove it before you fix it?

“It learned the dialect” is a hypothesis. There is a cheap experiment that tests it before anyone collects a new trajectory, and it also gets the customer working this week. Section 06 is that experiment.

Where this sits next to the other guides

Q4 (0005) is the closest neighbour, and it owns the serving-time half of this: the chat template, the tool-call parser, and the contract between them, when you swap the model under a fixed harness. This question is the reverse. The harness changes under a fixed model, and the format is not a config file that drifted. It is baked into the weights by training. This guide only points at 0005 for “match the serving template”. It does not re-teach it.

Q12 (0013) owns the idea that a score is model × harness × environment reported as a property of one of them. That guide is about reading a number honestly. This one is about why, after narrow fine-tuning, the harness term stops being small. Q14 (0015) showed a training environment shaping a default (every coding gym is Python). Here the environment shapes the interface the model expects. Q15 (0016) treated the observation format as a question of what a screenshot can carry. Here the observation format is a distribution the model was trained on, and changing it is a shift.

01

The answer, at three lengths

Say the thirty-second version out loud before reading further. It has the whole thesis in it, so the rest of the page is the support for each sentence.

30 seconds

It learned the task and the harness together, and it can’t tell them apart. SFT puts loss on every token the teacher wrote, so the model learned that harness’s tool-call syntax, its tools, how its observations look, and its habits, as hard as it learned the fix. In a new harness the first unfamiliar observation pushes it off the training distribution, and imitation errors compound, so it collapses instead of degrading. The fix is in the data: store trajectories in a harness-neutral format, train on several harnesses, and gate releases on a harness it never trained in.

2 minutes
  1. What SFT copies. Next-token loss on every assistant token. Nothing in the loss marks the reasoning as more important than the brackets.
  2. The five things it copied besides the task. Tool-call syntax, the action space, the observation format, the context conventions, and habits like path names.
  3. Why it collapses. Teacher forcing only ever showed it prefixes from harness A. In harness B the state is unfamiliar from step one, and behaviour cloning error can grow as T²ε, not Tε.
  4. It has been measured. A 32B SWE model scores 52.6% in the harness it was trained in and 8.4% in another, because the new parser can’t read its tool calls. Base models without the fine-tune don’t diverge like that.
  5. Prove it first. Put a thin adapter in front of harness B that translates to A’s dialect. If the score comes back, it was the dialect.
  6. Fix the data. Store once in a neutral schema (the Agent Data Protocol), render into several harnesses, randomise tool names and formats, mix task sources, and evaluate on a held-out harness.
One line

“If every trajectory came from one harness, I didn’t ship an agent. I shipped a model of that harness.”

The tempting answer The new harness has a different system prompt. Tweak the prompt, add a few examples, maybe collect more data.

It treats a training-data problem as a prompt problem. A prompt can tell the model the new tool names. It cannot undo 50,000 examples of the old ones, and it does nothing about observations that look foreign.

“More data” from the same harness makes it worse. You get a stronger model of harness A.

The answer that gets the job The model learned the trajectory, not the task. The fix lives in the data and in what we test on.

Name what the loss copied, explain the compounding, show the measurement that separates dialect from task, and then fix the pipeline: neutral storage, several harnesses, randomised dialects and held-out-harness evals.

02

The fundamentals, in plain words first

Six ideas carry the whole answer. Each one starts with the plain version. The precise version follows, because the interviewer will use the precise words.

A harness

The cockpit around the model: the loop, the tools, the prompt, and the code that reads what the model writes.

Also called a scaffold. A coding harness like OpenHands, SWE-agent, Claude Code or mini-swe-agent decides: which tools exist (bash, a file editor, a patch tool), how a tool call must be written (JSON, XML-style tags, a code block), how results come back (truncated at 100 lines? with line numbers?), what the system prompt says, and how long histories are trimmed. The model only ever sees text. The harness decides what that text looks like.

mini-swe-agent is about a hundred lines of Python with one tool, bash. OpenHands has a dedicated file editor with its own commands. Same job, very different text.

A trajectory

The recording of one attempt: the task, then the model’s action, the result, the next action, and so on.

System prompt, user task, then alternating assistant action and observation turns until the agent stops. The 50,000 trajectories in the question were each recorded inside one harness, so every action is written in that harness’s syntax and every observation is formatted by that harness.

Supervised fine-tuning (SFT)

Show the model the recording and make it more likely to write exactly what the teacher wrote.

The loss is next-token cross-entropy on the assistant tokens. Observations are usually masked, so they get no loss, but the model still conditions on them. The important part: every assistant token gets the same weight. The model is pushed as hard to reproduce </parameter> as it is to reproduce the line that fixes the bug.

Teacher forcing

During training the model never sees its own mistakes. Every step starts from the teacher’s perfect history.

At step 12 of training, the context is the teacher’s steps 1–11, not the model’s. That makes training fast and stable. It also means the model has never practised recovering from a bad state, because it has never been in one. Ranzato et al. (ICLR 2016) named the result exposure bias: the model is only exposed to the training distribution, never to its own predictions.

Distribution shift and compounding error

A small mistake leads to an unusual situation, and the model is worse at unusual situations, so the next mistake is more likely.

In imitation learning this is covariate shift: the states the learner visits differ from the states the teacher visited. Ross & Bagnell (AISTATS 2010) proved that a policy with error ε on the teacher’s states can have total cost that grows as T²ε over a T-step task, and that the bound is tight. Ordinary supervised learning grows as Tε. DAgger (Ross, Gordon & Bagnell, AISTATS 2011) gets back to linear by training on states the learner itself visits.

Chat template and tool-call format

The exact characters that wrap each message and each tool call.

Special tokens for roles, the format for a tool call (Hermes-style JSON in tags, XML parameters, a fenced code block), and the format of the result. Guide 0005 covers the serving side in detail. The point for this question: the format a model saw during fine-tuning is the format it now produces by reflex.

The format is learned first

Agent-FLAN (Findings of ACL 2024) watched this happen in the loss curves. On ReAct and JSON-formatted agent data, the loss on format tokens dropped to 0.04 while the loss on content stayed at 0.54. Their words: “the model quickly gets overfitted to the format itself.” The format is the easy, repeated, low-entropy part of every example, so it is learned first and most completely. That is why the habits are so strong.

In plain words

Imagine learning to cook from 50,000 videos filmed in one kitchen. You learn the recipes. You also learn that the salt is in the second drawer and the oven knob turns left. In a new kitchen you still know the recipes, but your hands go to the wrong drawer, and the first dish goes wrong before you have started cooking.

04

Why it falls off a cliff instead of a slope

If the model only lost a bit of skill, scores would drop a little. They drop by half or more. The reason is that an agent acts many times in a row, and each action changes what it sees next.

During training, every step starts from the teacher’s history. So the model only learned “what to do next, given a good history from harness A”. In harness B the history stops looking like that from the very first observation. The model is less accurate there, so it makes a mistake. That mistake produces an observation (an error message, an empty file) it has also never seen, so the next step is even less accurate.

Now apply it to the question. In harness B, ε is not 0.01 any more. The “teacher’s states” were harness A’s states, and the model is in harness B’s from step zero. So the base error is high and the compounding multiplies it. That is why the collapse looks like a cliff.

Low training loss is a promise about states the model visited. It promises nothing about states it never saw.
The training did it, not the base model

The DCAS study (ASE ’26) ran open SWE models on SWE-bench Verified in four harnesses: OpenHands, Claude Code, OpenCode and mini-swe-agent. The untrained base models did vary by harness, but less. In the authors’ words, the spread within each base-model row is smaller than the spread within any fine-tuned row, so “whatever causes the post-fine-tuning divergence is therefore something installed by training.” They also note that SWE-Gym, Nebius, SWE-Lego and CoderForge all collected their training trajectories only in OpenHands.

In plain words

A model trained only on perfect recordings has never been lost, so it has never learned to find its way back. In a new harness it is a little lost from the first step, and each wrong turn takes it somewhere even less familiar. That is why it doesn’t just get a bit worse. It gets lost.

Two labs now say it in plain text. That is a cleaner taxonomy than the newsletter’s five items, and worth quoting.

06

Tell dialect from task before you fix anything

“It learned the dialect” is a hypothesis. The other hypothesis is that it never learned the task well and harness A was hiding it. They need different fixes, and one cheap experiment separates them.

The adapter test

Write a thin adapter between the model and harness B. Going in, it renders B’s observations the way harness A would have: A’s truncation, A’s system prompt, A’s tool names. Coming out, it parses the model’s A-style tool calls and turns them into B’s actions. Same weights, same tasks, same harness B underneath. Only the dialect at the boundary changes.

  • Score comes most of the way back: the model knows the task and only speaks one dialect. It is a data-format problem, and the fix in section 07 will work.
  • Score stays low: the dialect is not the main problem. The model leaned on harness A’s structure to plan, or the tasks really differ. DCAS argues planning structure is often the hidden part (section 08).
  • Score comes partway back: the usual case. The gap between the adapter score and the home-harness score is the part the adapter could not translate. That remaining gap is your real target.

The adapter is also what you ship to the customer this week. It is a patch, not a fix. It ties the customer to your old dialect, and every new harness needs another one.

Read the first failure, not the last

Take 50 failed runs in harness B and label the first step that went wrong. A dialect failure shows up early and looks mechanical: a call the parser rejected, a tool name that doesn’t exist, a path from the old harness, an observation the model misread. A task failure shows up later and looks like a wrong plan. If most first failures are in the first three steps and are mechanical, you have your answer before writing any code.

In plain words

Before retraining anything, put a translator in front of the new harness so it talks to the model in the old harness’s language. If the model suddenly does fine, it knew the job all along and only spoke one language. If it still fails, the problem is deeper, and new data in more formats won’t be enough on its own.

07

The fix lives in the data

The model can only separate the task from the conventions if the conventions vary in its training data. Every item below makes them vary, or checks that they did.

  • 1 · several harnesses

    Collect or render the same kind of task through several harnesses.

    It is the only way the task becomes the constant and the dialect the variable. Qwen3-Coder-Next trains across six frameworks: SWE-agent, mini-SWE-agent, OpenHands, Claude Code, Qwen Code and Terminus. Devstral added “pseudo-scaffolds” and both XML and native function-calling formats “to improve generalization to diverse scaffolds”.

  • 2 · store neutral

    Store each trajectory once in a harness-neutral schema, then render it into each target harness.

    This is the Agent Data Protocol (ADP, ICLR 2026 oral). Its actions are API calls, code or messages. Its observations are text or web, and a web observation keeps both the raw HTML and the accessibility tree (plus an optional screenshot), so each harness can render the view it uses. Converting is N+M work instead of N×M. See the figure below.

  • 3 · randomise

    Rewrite the dialect on purpose: tool names, argument conventions, output formats, prompt templates.

    KAT-Coder-V2.5 does exactly this, “while preserving their underlying functionality”, and calls it domain randomization at the environment level. Qwen trains with 21 tool-call templates. KAT’s rule is the useful one: what matters is not the number of harnesses but whether they vary along the dimensions that matter (call protocol, context management, control flow).

  • 4 · mix sources

    Mix task sources, not just harnesses.

    In ADP, the mixture beat single-source training even on the source’s own benchmark. SWE-bench Verified on OpenHands, Qwen-2.5-7B: SWE-smith only 1.0%, ADP mix 10.4%. GAIA: 0.6% vs 9.1%. AgentTuning saw the same thing in 2023: agent-only training dropped held-out performance to 0.09 against 0.67 for a mixed set.

  • 5 · own states

    Add data from the model’s own rollouts in the target harnesses.

    This is the DAgger lesson from section 04: train on states the learner visits, not only the teacher’s. In practice that means on-policy RL, or rejection-sampled rollouts, run in several harnesses. KAT puts its harness diversity into the RL rollouts. SandMLE found its SFT models brittle outside their data-generation scaffold while its RL-trained models adapted.

  • 6 · held-out harness

    Gate every release on a harness the model never trained in, and serve with the exact template it was trained on.

    DCAS: a score without the scaffold is “methodologically incomplete”, and a published score should include at least one scaffold outside the training distribution. When you read other people’s numbers, check whether they are best-of across harnesses. Template drift at serving time is the same bug at the token level (guide 0005).

In plain words

Keep the recordings in one plain, neutral format that says what the agent did, not how a particular harness wrote it down. Then print them out in several harnesses’ styles for training, and scramble the tool names and formats on purpose. When the wrapping keeps changing and the job stays the same, the model has to learn the job.

08

Where the fix runs out

A strong answer names the limits of its own fix. Four are worth having ready, and the first one is measured.

More formats is not always enough

Nex-N1 was trained on trajectories from over 200 frameworks and environments in seven tool-call formats. In the DCAS runs it still dropped from a reported 50.5% on OpenHands to 26.2% on OpenCode and 15.6% on mini-swe-agent. DCAS concludes that “simply broadening the training distribution by mixing scaffolds is therefore not sufficient”. They argue the model also leans on the harness’s planning structure (a plan file, a fixed loop). Their fix was small: 576 planning-aware trajectories from one harness. It gained on unseen harnesses (OpenCode +3.4, mini-swe-agent +7.0) and scored 57.2% on a newer Claude Code version with updated tool schemas. So vary the format, and also teach the model to bring its own plan. This matches KAT’s third form, control-flow overfitting.

The collapse is mostly a narrow-SFT problem

Broadly trained models hold up much better. DeepSeek-V4.1-Flash spans 65.5 to 74.2 on DeepSWE across eight harness configurations. The Scaffold Effect in Coding Agents (2026) found 0–8 point pass-rate differences across three harnesses for two general models, though up to 40× differences in tokens per solved task. So don’t claim every model collapses. The claim is about a model fine-tuned narrowly on one harness’s data.

Rendering is not free

A trajectory recorded in harness A and rendered into harness B is partly invented. B’s edit tool might return a diff where A’s returned a snippet, and some of A’s actions have no clean equivalent in B. A neutral schema also tends toward the lowest common denominator, which is why ADP keeps both HTML and the accessibility tree instead of picking one. Mark every trajectory as native or rendered, and where you can, replay rendered ones in the real harness to check them.

Sometimes a harness-specific model is the right product

A model co-designed with its own agent product can be tuned hard for that harness, and that is a reasonable choice. The bug is not the specialisation. The bug is shipping a specialised model as if it were general, with only home-harness numbers to show for it.

09

What to carry forward

Six things. The first is a sentence to say. The rest are changes to a pipeline, and each one names what it checks.

  • 1 · the claim

    SFT learns the trajectory, not the task. Every token of harness syntax got the same loss as the fix.

    Back it with the format-loss result: 0.04 on format vs 0.54 on content (Agent-FLAN).

  • 2 · the shape

    It collapses because errors compound: T²ε for cloning on the teacher’s states, Tε for training on your own.

    That one formula answers “why not graceful?” and also points at the fix (own-state data).

  • 3 · the control

    Always run the base model in both harnesses. The gap your fine-tune added is the tuned gap minus the base gap.

    DCAS used exactly this to show the divergence was “installed by training”.

  • 4 · the test

    Run the adapter test before collecting a single new trajectory.

    It separates dialect from task, and it is the customer’s stopgap this week.

  • 5 · the pipeline

    Store neutral, render to several harnesses, randomise the dialect, mix task sources, add own-state rollouts.

    And teach planning, not only formats, because format variety alone was measured to fall short.

  • 6 · the gate

    No release without a held-out-harness score next to the home-harness score.

    And every trajectory carries a field saying which harness produced it. Without that field you cannot even compute the mix.

The artefact to leave behind

Two small files. The first is one trajectory, stored neutral. The second is the dataset manifest, with the two fields most teams don’t have. The null values are deliberate: they are the numbers the interviewer will ask for, and an honest null beats an invented figure.

10

Five checks, and one is the gate

In the order you would run them. The second decides what kind of problem you have, so it is the one to describe first if you only get to describe one.

  1. 01the control
    Run the base model, before fine-tuning, in both harnesses.

    Same tasks, same turn limit. Some harnesses are simply harder; the base gap tells you how much.

    what it tells youHow much of the collapse your fine-tune caused. If the base model has the same gap, this was never a training-data problem.

  2. 02the gate · no new data needed
    Put an adapter in front of harness B that speaks harness A’s dialect, and re-run.

    Render B’s observations A’s way, parse A-style calls into B’s actions. Report three numbers: home harness, B raw, B through the adapter.

    why this oneIt is the only check that separates “learned the dialect” from “never learned the task”, and those need different fixes. It also gives the customer something this week.

  3. 03first-failure triage
    Label the first wrong step in 50 failed harness-B runs.

    Buckets: unparseable call, unknown tool, old-harness habit (paths, commands), misread observation, wrong plan.

    what it tells youWhich of the five dialect items is doing the damage, so the data fix targets it instead of everything.

  4. 04the perturbation sweep
    Inside harness A, change one convention at a time and measure the drop.

    Rename the tools. Reorder the arguments. Change the truncation marker. Move the repo from /workspace to /testbed. Reword the system prompt.

    what it tells youA dialect-sensitivity profile you can track across training runs. A robust model barely moves. A harness-overfit model drops on the first rename.

  5. 05leave one harness out
    Train on all harnesses but one, evaluate on the one you left out, and rotate.

    Then plot the held-out score against the number of training harnesses.

    what it tells youWhether adding harnesses still buys generalisation, or whether, as DCAS found, you have hit the point where planning structure is the bottleneck.

11

Twelve follow-ups

The first four are the ones that usually get asked. The last two are where it goes if the conversation is going well.

F1Isn’t this just overfitting? Add regularisation or more data.

It is overfitting, but to the wrong thing for those cures to help. Regularisation fights memorising individual examples. Here the model generalised perfectly well across 50,000 examples; what it generalised was harness A, because harness A was in every one of them. More data from harness A makes a better model of harness A. The cure for a constant you don’t want learned is to make it vary.

F2Why can’t I fix it with the system prompt and a few examples in harness B?

You can fix some of it. A prompt with the new tool names and two worked examples may bring back some parseable calls. It can’t fix observations that look foreign on every step, and it is fighting 50,000 examples of the old habits with a few hundred tokens of context. MiniMax-M2 ignored an explicit instruction to use /testbed and scored zero. Use the prompt as a patch, and measure how much it recovers. Don’t call it the fix.

F3How do you know it learned the dialect and not just a worse version of the task?

The adapter test. Translate harness B into A’s dialect at the boundary, keep everything else the same, and re-score. If the score comes back, the task knowledge was there. Then confirm with first-failure triage: dialect failures are early and mechanical, task failures are late and look like wrong plans.

F4Why does it collapse rather than degrade gracefully?

Teacher forcing. Training only ever showed it the teacher’s history in harness A. In harness B the history is unfamiliar from the first observation, so the per-step error is high. And each mistake produces a new observation it has never seen, so errors compound. Ross & Bagnell proved the cost of cloning can grow as T²ε, and the bound is tight. Training on its own states (DAgger, or on-policy RL) brings it back to Tε.

F5How many harnesses is enough?

At least three, so you can train on two and hold one out. After that, count the dimensions, not the harnesses: tool-call protocol, action set, observation format, context management, control flow. KAT’s point is that diversity has to fall on the dimensions that matter. Then answer it empirically with the leave-one-out curve from check 05.

F6Isn’t rendering one harness’s trajectory into another harness just fake data?

Partly, yes. The actions translate well, but the observations are what the original harness returned, not what the new one would have. Some actions have no clean equivalent. So mark rendered trajectories in the provenance, check a sample by replaying them in the real harness, and keep some native data in each target harness. Rendered data teaches the format. Native data teaches what the format’s results look like.

F7Would RL fix this on its own?

RL fixes the compounding part, because it trains on states the model itself reaches. That is the DAgger idea. But RL in one harness overfits that harness just as well. KAT-Coder names format, context-structure and control-flow overfitting in its RL setting and fixes it by varying the harness during rollouts. So RL plus harness diversity, not RL instead of it.

F8What does a format like ADP actually buy you?

Three things. Converter work goes from N×M to N+M: the paper estimates about 489,200 lines of converter code against 12,592 for 100 harnesses. A new harness costs one small renderer, about 77 lines on average. And because each record keeps what was done rather than how one harness wrote it, you can render the same data into new harnesses later. That makes “train on several harnesses” cheap enough to actually do.

F9The customer needs it working this week. What do you do?

Ship the adapter: translate their harness into the dialect the model knows, at the boundary. It is the same code as the diagnostic in check 02, so you get the measurement and the patch together. Be clear that it is a patch: it locks them to your old dialect, and the real fix is the next training run.

F10A model card says 70% on SWE-bench Verified. What do you ask?

Which harness, and was it the one the training data came from? Is it best-of across several harnesses? Is it pass@1? DCAS calls a score without its scaffold “methodologically incomplete” and asks for at least one scaffold outside training. The good model cards now report several: DeepSeek-V4.1-Flash reports eight harness configurations. Guide 0013 has the general version of this question.

F11You added more formats and the held-out score barely moved. Now what?

Then the model is leaning on something other than the format, and the measured candidate is planning structure: the harness’s plan file, loop and stopping rules. Nex-N1 trained on seven formats and still dropped to 15.6% in mini-swe-agent. DCAS got gains on unseen harnesses from only 576 trajectories that taught the model to plan for itself. So look at first failures again. If they are late and look like lost plans, teach the plan, not more syntax.

F12If you could give the team one rule, what is it?

“Every trajectory records which harness produced it, and no model ships without a score on a harness it never trained in.” The first half makes the problem visible in the data. The second makes it visible before the customer finds it.

Glossary

harness / scaffold
Everything around the model in an agent: the loop, tools, prompt, parser, observation formatting and history handling.
trajectory
One recorded attempt: task, then alternating actions and observations until the agent stops.
SFT
Supervised fine-tuning: next-token loss on the teacher’s assistant tokens. Every assistant token is weighted the same.
loss mask
Which tokens get loss. Observations are usually masked out, so the model conditions on them but is never graded on them.
teacher forcing
Training each step on the teacher’s history, never on the model’s own earlier outputs.
exposure bias
The gap that teacher forcing leaves: the model was only exposed to the training distribution, never to its own predictions (Ranzato et al., 2016).
behaviour cloning
Imitation learning by supervised learning on expert actions. Agent SFT on trajectories is behaviour cloning.
covariate shift
The states the learner visits differ from the states it was trained on. In this question it starts at step zero.
compounding error
Each mistake leads to a less familiar state, which makes the next mistake more likely. Bounded by T²ε for behaviour cloning.
DAgger
Dataset Aggregation: run the learner, have the expert label the states it reached, add them to training. Brings the bound back to linear in T.
dialect
This guide’s word for a harness’s conventions: call syntax, tool set, observation format, context layout, habits.
harness overfitting
Learning to solve the task under one harness’s conventions. KAT-Coder splits it into format, context-structure and control-flow overfitting.
accessibility tree
A structured, compact view of a web page (roles and names of elements). An alternative to raw HTML as a web observation.
interlingua
A neutral intermediate format. Each source converts into it once and each target renders from it once.
ADP
Agent Data Protocol: a neutral schema of API, code and message actions and text and web observations, with converters to OpenHands, SWE-agent and AgentLab.
domain randomisation
Varying the parts of the environment you want the model to ignore. Here: tool names, formats, prompts, context layout.
held-out harness
A harness that is never used for training or tuning, kept only to measure transfer.
adapter (shim)
A translation layer at the model’s boundary that makes a new harness look like the old one. A diagnostic and a stopgap, not a fix.
