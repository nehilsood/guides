Question 9 · Google DeepMind · senior AI engineer

The Frozen Org Chart

A PM agent, a coder agent and a tester agent beat one agent on standard GitHub issues, then fall over the moment a task has a different shape. The trap is that the pipeline was never an architecture. It is a guess about the shape of every task, made before any task arrived — and you pay for that guess twice.

The question, as asked

“Your ‘AI software team’ of PM agent → coder agent → tester agent beats a single agent on standard GitHub issues. But the moment a task doesn’t fit that shape, it falls apart. Why? And when does one well-managed agent beat the whole team?”

00

What they are actually testing

This question has an unusual shape: it hands you a win and asks you to explain it away. The pipeline really does beat the single agent on that benchmark. A weak answer either denies the win or celebrates it. The answer they want explains why the win is real, why it does not generalise, and what it was actually a win of — and that requires taking apart a word the question never defines: team. Four things are being probed underneath.

P1

Do you know what an agent boundary costs and what it buys?

Every candidate can say “handoffs lose information.” Far fewer can say what a handoff is — a compression step, chosen by the sender, that the receiver cannot undo and is never told happened. Until you can price the boundary you cannot reason about when to pay for one.

P2

Can you separate the two axes hiding inside “multi-agent”?

How many context windows the work runs in, and when the structure was decided, are independent choices. Almost every public argument about this topic is two people on opposite ends of one axis pointing at the other. If you cannot pull them apart you will end up defending a slogan.

P3

Do you know why “specialised agents” is the wrong noun?

The interviewer has pre-loaded the wrong answer for you, and it is wrong in a specific way: it credits the split with a benefit the split does not deliver. Role specialisation is a prompt. It is free. The context boundary is the expensive half, and the pipeline sells them to you as one thing.

P4

Can you say when the team is right?

The second half of the question — “when does one well-managed agent beat the whole team” — is a test for one-directional answers. If your position is “multi-agent is bad” you fail it, because the same week’s evidence contains a multi-agent system beating a single agent by ninety per cent. You need a rule that outputs both answers.

Not the same question as guide 0007

These two sit close together and the interviewer may well probe the seam, so keep the boundary sharp. 0007 asks when do you commit — a free-form agent outscored a fixed workflow, and the answer is about which guarantees the scaffolding was silently providing. It is a question about control flow and constraints inside one process.

0010 assumes that is settled and asks a different question: where do you cut. Given work that has to get done, how many context windows should it run in, and what decides where the seams go. You can have a rigid workflow in one agent and a free-form agent per node of a graph; the two questions are genuinely orthogonal. 0007 is about the plan’s rigidity. 0010 is about its shape, and about who is allowed to redraw it.

01

The answer, at three lengths

Lead with the reframe, because the reframe is the answer. The pipeline is not an architecture; it is a structural prior. Everything else follows from saying that sentence first.

Thirty seconds

“Because the pipeline is not an architecture — it is a hard-coded guess about the shape of the task, and it charges you twice. Once because the org chart is the plan, so when the test reveals the spec was wrong there is no edge back to the spec and nowhere for that information to go. And once at every boundary, because a handoff is a lossy compression chosen by the sender, and the receiver can neither see what was dropped nor go back and ask. Meanwhile the specialisation it sold you was free: you can tell one model to review its own diff as a tester would, in one context window, for nothing. So decompose by the task’s dependency graph rather than by job titles, verify each node, and let a manager redraw the graph when reality disagrees. And the moment two subtasks touch the same mutable state — which in a repository is nearly always — one agent with compaction, a plan file and a scratchpad wins.”

Two minutes

Open by separating two things that get bundled: how many context windows the work runs in, and when the structure was decided. A role pipeline is the corner where both are set to their worst value — many windows, decided before the task existed — and that is why it feels like two failures stacked, because it is.

Then explain the win. It is real, and it is a win of the sequence, not the split: spec, then implement, then test is a genuinely good prior for a standard GitHub issue. The benchmark contains almost nothing else, so the prior is right almost every time and the architecture gets the credit.

Then price the boundary. A handoff is compression the sender chooses, the receiver cannot audit, and nothing in the system reports. When the receiver is missing something it does not stop — it assumes, and proceeds confidently. That is why in a taxonomy of 1,642 annotated multi-agent traces the top failure mode is not lost information, it is step repetition at 15.7%: agents redoing work they cannot see was already done.

Close with the rule. Cross a boundary only when you can name the gate it passed — shared state says no outright, and breadth, resource, isolation or latency can say yes. If nothing says yes, merge the nodes. If the plan can be wrong, give the planner the authority and the budget to redraw the graph mid-run.

At the whiteboard

Draw the three boxes and the two arrows they gave you. Then draw the arrow they did not give you — tester back to PM — and say: this is the edge the task needs and the architecture cannot express. That single missing arrow is the whole first failure mode, and it is a better explanation than any paragraph.

Then annotate each existing arrow with two numbers: the size of what crosses it, and the size of the trace it was made from. Say you would log that ratio in production, because it is the one number nobody measures and it tells you which edges are lying to each other.

Finish by rewriting the diagram as nodes with acceptance checks and edges with justifications, and mark the one edge you would delete on day one.

Do not say Specialised agents are better at their roles. The single agent just gets overloaded with context.

Both halves are backwards. The first credits the split with specialisation you already had for free — the PM agent and the coder agent are, in nearly every implementation, the same checkpoint with a different system prompt. The second blames the single agent for the one problem that actually has known engineering answers.

And the diagnosis prescribes the wrong fix. It leads to “add another specialist” and “write better summaries”, which are the two changes that make this system worse.

Say instead Role-based teams bake one task shape into the architecture and leak context at every handoff. Decompose by a per-task dependency graph with replanning. If the subtasks are not truly separable, one agent with good context management wins.

Then earn each clause: the missing tester-to-spec edge for the first, the compression-chosen-by-the-sender argument for the second, and the shared-state test for the third.

02

Fundamentals: the two axes nobody separates

“Multi-agent” is not one decision. It is two, and they are independent. Almost every public argument on this subject is two people standing at opposite ends of one axis, pointing at the other. Pull them apart and the question mostly answers itself.

Axis one: how many context windows does the work run in? This is a question about information. One window means every observation the system has ever made is available to the next decision. More windows mean the system holds more total material than any one model can attend to, at the price of a compression step at every seam.

Axis two: when was the structure decided? This is a question about the plan. Fixed before deployment means a reusable template you can debug, benchmark and cost out in advance. Generated per task means the shape fits this task. Revised during the run means a late observation is allowed to change an early decision.

Neither axis implies the other. You can have a rigid three-step script running entirely in one context window, and you can have a fleet of agents whose graph is rewritten every ninety seconds. Six combinations, and they behave nothing like each other.

Top-right is the corner where both axes are set to their least forgiving value at once, which is exactly why the failure feels like two problems stacked — it is two problems, one per axis.

The disagreement that is not a disagreement

Two pieces get quoted at each other constantly. Cognition’s Don’t Build Multi-Agents argues for a single-threaded linear agent with continuous context. Anthropic’s research-system write-up reports multi-agent beating single-agent Opus 4 by 90.2%. Put them on the grid and they are in different columns, for a reason Anthropic states in the same post: “most coding tasks involve fewer truly parallelizable tasks than research”, and “domains that require all agents to share the same context or involve many dependencies between agents are not a good fit.”

Cognition is describing coding, where a repository is shared mutable state and every subtask writes to it. Anthropic is describing breadth-first research, where four subagents read four disjoint corners of the web and write nothing. Same rule, two answers. If your response to this question is a position rather than a rule, you have picked one of these quotes and thrown away the other.

03

Why “specialised agents” is the wrong noun

The interviewer pre-loads a wrong answer and tells you it is backwards. It is worth being precise about which part is backwards, because the precision is the answer to the whole first half of the question.

Start with what an org chart is actually for. A company employs a product manager, an engineer and a QA lead as three people because no one person holds all three skills at a professional standard. The boundary between them is not a feature. It is a cost — meetings, documents, misunderstandings, the thing the QA lead knows that never reaches the PM — and organisations accept that cost because it is the price of access to expertise that is otherwise unavailable. The boundary buys you a skill you could not otherwise have.

Now price the same trade in your system. Your PM agent and your coder agent are, in nearly every implementation anyone actually ships, the same model checkpoint with a different system prompt. The expertise was never scarce. There is no skill sitting behind that boundary that the single agent did not already have in the same weights.

The sentence to have ready

Role specialisation is a prompt, and a prompt is free. The context boundary is expensive. The pipeline bundles the free thing with the expensive thing and charges you for both.

You can have the role without the boundary. Telling one agent “now read your own diff the way a hostile QA engineer would, and list what you would reject” changes its priors in exactly the way the tester agent’s system prompt does — and costs you a few hundred tokens inside a window that already contains the repository, the spec, and every observation made so far. That is not a worse tester. It is a tester that can see the reasoning behind the code it is reviewing.

What is scarce for a language model is not skill. It is sustained attention over a single coherent state — and the pipeline spends that scarce thing in order to buy the abundant one. That is the sense in which the pre-loaded answer is backwards: not slightly wrong about a trade-off, but inverted about which resource is short.

None of which means an agent boundary is never justified. It means role is not the justification. A boundary earns its place when something genuinely differs across it — a cheaper model, a narrower tool scope, a credential the other side must not hold, a body of material too large to read in one window. Those are real, they are covered in section 06, and not one of them is a job title.

Conway, inverted

Conway’s law, 1968: an organisation that designs a system will produce a design whose structure is a copy of the organisation’s communication structure. It is normally quoted as a warning about accident — your three teams will ship three services whether or not the problem has three parts.

A role-based agent pipeline inverts it into something stranger. Nobody here has three teams. Somebody looked at how humans divide software work and shipped the org chart itself as the architecture, on purpose, as the design. MAST’s authors arrive at the same place from the data: their conclusion is that many failures “arise from the challenges in organisational design and agent coordination rather than the limitations of individual agents”, and that “even organisations of sophisticated individuals can fail catastrophically if the organisation structure is flawed.”

04

What a handoff actually is

“Lossy handoff” is the phrase everybody reaches for and almost nobody unpacks. Unpack it and you get four properties. Three of them are obvious. The fourth is the one that makes the other three dangerous, and it is the one to say out loud.

  • Lossy

    By construction, not by accident. The summary is smaller than the trace it was made from — that is the entire point of making it. A handoff that lost nothing would be a copy, and a copy would defeat the purpose of the boundary.

    This one is definitional. Nothing you do to the prompt changes it.

  • Sender-chosen

    The compressor decides what matters. The receiver bears the loss. And the sender is choosing without knowing what the receiver is going to need, because if it knew that it would have done the receiver’s job.

    This is the asymmetry that does the damage. The party that picks the payload is not the party that pays for the omission.

  • Irreversible

    The receiver cannot go back and look. In a role pipeline the PM agent’s context is gone by the time the tester needs it — there is no query interface to a finished agent’s trace, and in most implementations the trace was never persisted in a form anything could query.

    Note what this rules out: not just retrieval, but asking a question.

  • Silent

    Nothing in the system reports that information was dropped. No error, no gap marker, no drop in stated confidence. The summary arrives reading exactly as complete as a complete one would.

    This is the load-bearing property. A lossy channel that announced its losses would be fine — the receiver would ask, or stop. This one does not, so the receiver’s only available move is to assume, and then act on the assumption with full confidence.

Cognition’s write-up reaches the same place from a worked example rather than from first principles, and states it as their second principle: “Actions carry implicit decisions, and conflicting decisions carry bad results.” Their illustration is a Flappy Bird clone split across two subagents — one produces a Super Mario Bros background, the other a bird that does not look like a game asset, and a third agent is then handed the job of combining two miscommunications. Neither subagent made an error. Each made a reasonable decision the other could not see.

The number nobody logs

For every boundary in your system, log two figures: the size of what crossed it, and the size of the trace it was made from. The ratio is your compression factor per edge, and it is roughly one line of instrumentation.

You now have your edges ordered by risk, which you did not have before. An edge compressing 40,000 tokens of repository reading into a 300-token summary is doing something dramatic, silently, on every single run. Whether that is fine depends entirely on whether the edge passed a gate in section 06 — but you cannot even ask the question until the number exists, and in most systems it does not.

One honest complication before moving on. A single agent is not boundary-free. When it compacts — summarises a long context and reinitialises — that compaction has all four properties above. The advantage is not that the boundary disappeared. It is that there is now one boundary instead of n, and that one has two things the handoffs did not: the compressor and the reader are the same agent pursuing the same objective, so the sender-chosen problem largely dissolves; and the full trace is usually still on disk, so irreversibility becomes recoverable — the agent can re-read the file. Section 07 is about making both of those true on purpose rather than by luck.

So does the data refute the handoff argument? No — and getting this next step right is the difference between reciting the newsletter and understanding it. The folk theory has the mechanism right and the symptom wrong.

An agent that lost a detail in a handoff does not emit “I am missing a detail.” It cannot: nothing told it. It fills the gap with a plausible assumption and proceeds with full confidence — which an annotator labels a reasoning–action mismatch, or task derailment, or disobeying the spec. And look at the largest mode on the whole chart. Step repetition at 15.7% is very nearly a pure signature of not sharing a trace: an agent redoes work because it cannot see that the work was already done.

The operational consequence is what makes this worth saying in the room. If you go into your logs looking for handoffs that dropped something, you will not find them. What you will find is two agents who each did something entirely reasonable, and an output that is wrong. Knowing that in advance is the difference between a week of useful debugging and a week of reading summaries and finding nothing amiss in any of them.

The finding that cuts against “just share the full trace”

The same paper is blunt about the limits of the obvious fix. Its second stated insight: “Solutions focused on context or communication protocols are often insufficient for FC2 failures, which demand deeper social reasoning abilities from agents.” Inter-agent misalignment is 36.9% of failures and a wider pipe does not clear it.

Their two intervention studies point the same way, and neither is a bigger pipe. Adjusting ChatDev’s workflow so the CEO agent had the final say — a structural change — produced +9.4% task success with the same prompt and the same model. Adding a high-level objective verification step produced +15.6% on ProgramDev. Structure and verification moved the number. If you argue this question purely as “share more context”, a well-read interviewer has this ready.

The category totals are worth carrying too, because they tell you where to spend: 41.8% system design issues, 36.9% inter-agent misalignment, 21.3% task verification. Design and verification, not bandwidth. And the headline that sets the stakes: across the seven frameworks surveyed, observed failure rates ran from 41% to 86.7% — measured on different benchmarks, so not comparable to each other, but none of them anywhere near reliable.

06

Five gates, and only one of them is a veto

This is the part that turns a critique into a design procedure, and it is what the interviewer is fishing for with “when does one well-managed agent beat the whole team.” The rule is per-edge, not per-system: for every boundary you are about to draw, name the gate it passes. No gate, no edge.

  1. veto Shared state Do the two sides write to the same thing?

    If both halves of a split mutate the same artefact — a repository, a schema, a document, a running environment — they are not separable, and no amount of prompt quality fixes it. Each side is making decisions the other must honour, and neither can see them. This is Cognition’s second principle stated as a test.

    In software this veto fires far more often than people expect, because the repository is the state. A coder agent and a tester agent do not just exchange messages; they both have opinions about the same files.

    Observable Would you merge the two outputs or concatenate them? Merge means not separable. A sharper version: can each node finish without asking the node upstream a question? If it needs a round trip, that is not a graph edge, it is a conversation — and a conversation across a context boundary is the most expensive object in this entire design space.

  2. permit Breadth Does reading everything exceed one window?

    Four vendors, four hundred call sites, a literature search — when the material to be read is larger than any single context, subagents stop being a division of labour and become a compression strategy. Each explores in a clean window and returns something small. This is the cell Anthropic’s research system lives in, and it is the one place the 90.2% number applies.

    Observable Token count of the material against your window — discounted, because degradation starts well before the limit. Chroma’s context-rot work found reliability falling with input length across eighteen frontier models on tasks whose difficulty never changed.

  3. permit Resource Is something genuinely different on the other side?

    A stronger planner and a cheap executor. A narrower tool scope. A different rate limit or spend budget. These are real boundaries with real economics behind them, and they are the respectable relative of the role split — the difference being that you can name the resource.

    Observable Say the difference out loud. “Planner on the frontier model, forty executors on the small one” is a resource boundary. “Planner and coder, both on the frontier model, same tools” is a job title wearing a boundary’s clothes.

  4. permit Isolation Must one side be unable to do something?

    A verifier that can edit the thing it is judging is not a verifier. Untrusted content that reaches privileged tools is a security incident waiting to be written up. A trust or privilege boundary is one of the few reasons to split that has nothing to do with capacity or parallelism, and it is the reason the tester agent is often worth keeping even after you have merged everything else.

    Observable Name the capability the far side must not hold: write access, a credential, a network egress path. If you cannot name one, this gate did not fire.

  5. permit Latency Are the branches independent, and is wall-clock worth the bill?

    The weakest of the four permits and the one most often assumed rather than checked, because parallelism does not reduce the work — it multiplies it. Anthropic reports multi-agent systems using around 15× the tokens of a chat, with token usage alone explaining 80% of performance variance on their browsing evaluation. You are buying wall-clock with tokens.

    Observable Amdahl, on the back of an envelope. If 40% of the work genuinely parallelises across four branches, your ceiling is 1∕(0.6 + 0.4∕4) = 1.43× on latency — while you pay the full multiplied token cost on 100% of it. Decide whether 1.43× is worth that before you build it, not after.

How the gates combine

Shared state is a veto; the other four are permits. A permit does not survive a veto — “but they could run in parallel” is not an argument against two nodes writing to the same files, it is an argument for a race condition. And an edge that passes no permit at all is not neutral. It is a compression step you are paying for on every run, plus a conversation you have made impossible, in exchange for nothing.

Run this over the question’s own pipeline. PM→coder: same model, same repository, no isolation, nothing parallel. No permit, and the veto fires. Coder→tester: the veto still fires on the repository, but isolation is a genuine permit if the tester truly cannot write. So the honest redesign of “PM, coder, tester” is one agent that plans and implements with the plan on disk, and one isolated verifier that can read and run but not edit. Two nodes, one of which exists for a reason you can state in a sentence.

07

What “one well-managed agent” actually means

The second half of the question is the half most candidates wave at. “Good context management” is not a virtue, it is four specific mechanisms, and naming them is what separates an opinion from a design. Anthropic’s context-engineering guidance names the first three; the fourth is what stops the single largest failure mode on the chart in section 05.

  1. Compaction

    Take a context approaching its limit, summarise it, and reinitialise with the summary. The craft is entirely in what gets kept: tune the compaction prompt on real traces, maximising recall first so nothing relevant is lost, then tightening precision to drop the superfluous. This is a handoff with all four properties from section 04 — but it is the one boundary you own, and you can measure it.

  2. Structured note-taking

    Persistent memory outside the context window. NOTES.md, TODO.txt, a findings file — written by the agent, reloaded on demand. The property that matters is easy to miss: a file survives compaction, a message does not. Anything you cannot afford to lose belongs on disk rather than in the transcript.

  3. The plan as an artefact, not a message

    The plan is written to a file at the start, re-read each turn, and amended in place when it changes. In a role pipeline the plan is the org chart and it is frozen; here the plan is a document with a revision history, and the agent that wrote it is the agent that finds out it was wrong.

  4. A scratchpad of done, remaining, and blocked

    The cheapest of the four and the one that pays most directly. Step repetition is 15.7% of all observed multi-agent failures — the single largest mode — and it is almost definitionally impossible for an agent that can read a list of what it has already finished. Half that failure mode is a file.

What these four actually are

Look at the list again. An explicit plan. A record of state. A clear separation of phases. A check before moving on. Those are the pipeline’s virtues — every one of them is a thing the three-agent team was giving you, and every one is worth keeping.

The single agent keeps all of them and implements them as files inside one context rather than as boundaries between contexts. You keep the structure and throw away the seams. That reframing is the most useful thing on this page, because it means you are not arguing against structure — you are arguing that structure never required compression, and the pipeline only made it look that way.

So: when does one agent beat the team?

Three conditions, any one of which is sufficient on its own.

  • The subtasks share mutable state. The veto from section 06. In software this is nearly always true, because the repository is the state.
  • The plan can be wrong. Anything where a late observation should revise an early decision needs an edge the org chart cannot express. “The test reveals the spec was wrong” is not an exotic case — it is most of engineering.
  • The material fits in one window after compaction. If breadth was your only permit and compaction dissolves it, the permit is gone.

Coding hits the first two almost every time, which is why the single-agent result keeps holding there. mini-SWE-agent — roughly a hundred lines, one tool, not even using the model’s tool-calling interface — scores above 74% on SWE-bench Verified. Its authors built SWE-bench and SWE-agent, so this is not an outsider’s provocation; it is the benchmark’s own team demonstrating that the scaffolding had become the thing in the way.

Where the single agent loses, stated honestly

Do not oversell it, because an interviewer who has run one of these will know the failure modes. Context rot: reliability falls as input grows, on tasks whose difficulty never changes — Chroma measured this across eighteen frontier models, and found degradation is worse when the thing you need is only semantically similar to the question, and worse on coherent documents than on shuffled ones. A long single trace is not a neutral container.

Compaction is still lossy, and now every loss is yours. There is no natural checkpoint for a human to inspect, where a pipeline hands you one per stage for free. And an error committed early propagates through everything after it, which is exactly the argument the task-decoupling literature makes for scoped sub-contexts — Task-Decoupled Planning reports up to an 82% reduction in token consumption against a strong plan-and-act baseline precisely by confining reasoning to the active sub-goal. The single agent is the right default. It is not free.

08

Decompose by the graph — and give somebody the pencil

Everything so far has been about where not to cut. This is the constructive half: what you build when the gates do fire, and the part of “build a DAG” that candidates skip, which is who is allowed to redraw it once it is wrong.

Nodes are units of verifiable output, not job titles. The test for a node is not “is this a coherent role” but “can I state, before it runs, what output would count as this node succeeding?” If you cannot, you do not have a node — you have a phase, and a phase you cannot check is a phase you cannot replan around. MAST puts task verification at 21.3% of failures and notes that many production verifiers do only superficial checks — does it compile, are there leftover TODOs — while the actual objective goes unexamined.

Edges carry their justification. One of the five gates, named, per edge. This is the thing that makes the design reviewable by someone other than its author, and it is the artefact the pipeline was missing all along.

# the question is not "who are my agents". # it is "why does each boundary exist". task: migrate the auth service to the new token format nodes: - id: survey model: small ctx: fresh, read-only accept: a list of call sites, each with file:line - id: plan model: large ctx: survey output accept: an ordered edit list, every item naming a call site - id: edit model: large ctx: plan + repo write accept: the branch builds - id: verify model: small ctx: fresh, read + run, NO write accept: suite green, no call site left on the old format edges: survey -> plan gate: BREADTH # 340 call sites. reading them # all does not fit. this boundary # is a compression strategy, not # a role. plan -> edit gate: NONE # same model, same repo, nothing # parallel, no privilege split. # DELETE THIS EDGE. merged into # one loop, plan kept on disk. edit -> verify gate: ISOLATION # verify must not be able to edit # the thing it is judging. replan: trigger: verify fails twice on the same node | edit touches a file survey never saw | any node exceeds 2× its step budget authority: the plan node may rewrite nodes and edges below it budget: 3 rewrites, then stop and ask a human log: every rewrite, with the observation that caused it

The one field a role pipeline has nowhere to put is replan, and the one line in it that nobody writes is the last. Log every rewrite with the observation that caused it and you have, after a month, a list of the places your structural prior was wrong — which is the only data that tells you what the next version of the system should look like.

Replanning needs three things or it is not a feature, it is a loop. A trigger, so it fires on evidence rather than on vibes. An authority, so it is unambiguous which node may edit which part of the graph — a node rewriting its own ancestors is how you get a cycle in something you called a DAG. And a budget, because an agent allowed to replan without bound will replan instead of finishing; that is the same failure guide 0001 is about, wearing different clothes.

Do not skip straight to dynamic

The strongest version of this answer includes knowing when the boring option is correct, and the workflow-optimisation survey states the conditions crisply. A fixed template is enough when three things hold at once: the operator space is small enough to search, the evaluator is trustworthy enough to tell candidates apart, and the workload is repetitive enough that a reusable template is worth optimising. When those hold, “a well-searched template can dominate ad hoc runtime generation because it is cheaper, easier to debug, and easier to benchmark.”

Which is, read honestly, a description of the standard-GitHub-issue benchmark the question opens with. So do not tell the interviewer their pipeline was stupid. Tell them their pipeline was a correct answer to a workload whose repetitiveness they have now left behind — and that the trigger for moving is measurable: how often the plan gets violated. Count the runs where a node produces output its successor cannot use. When that count stops being rare, the template has stopped fitting, and that is the number that buys the dynamic version, not an argument.

09

Twelve follow-ups, with answers

These are the questions that come after the reframe lands. Several are designed to catch a candidate who has memorised “multi-agent bad” — F3 and F6 in particular are traps for exactly that, and answering them well is worth more than the opening.

F1Our pipeline genuinely does beat the single agent on these issues. Are you telling me that result is an illusion?

No. It is a real win on a task distribution that happens to match the prior, and I would say so first. What I would question is what it is a win of — and that is answerable in a day rather than in an argument.

Run the ablation: one agent, one context window, same model, same tools, instructed to work through the same three phases in order with the plan written to a file. If the score holds, the asset was the sequence and the split was overhead. If it drops, you have learned which boundary was load-bearing and you can keep that one and gate it properly. It costs a day of compute and almost nobody runs it, because the pipeline is already shipped and the result can only be awkward.

F2Define “lossy handoff” precisely. Then tell me what you would log.

A compression step chosen by the sender, unauditable by the receiver, and unreported by the system — so when the receiver is missing something, its only available move is to assume, and it assumes confidently.

Two things to log. Compression factor per edge: the size of what crosses the boundary against the size of the trace it was made from. That orders your edges by risk and takes about a line. Precondition failure rate: how often a node produces output its successor cannot actually use. The first tells you which seams are dramatic; the second tells you which ones are already breaking.

F3The MAST taxonomy puts context loss at 2.8% of failures and withheld information at 0.85%. Doesn’t that undercut your whole story?

It undercuts the symptom, not the mechanism, and the distinction is operationally useful. An agent that lost a detail does not report a gap — nothing told it there was one. It fills the gap and proceeds, and an annotator records that as a reasoning–action mismatch, task derailment, or disobeying the spec. Meanwhile the single largest mode on the chart is step repetition at 15.7%, which is close to a pure signature of agents not sharing a trace.

There is a second point worth making. Those annotations are of observed failures. A handoff loss that the receiver papers over successfully never appears in the data at all. So 2.8% is a floor on how often loss is visible, not a ceiling on how often it happens.

F4Who builds the DAG, and what stops it being nonsense?

A planning call emits it, and then code validates it, not a model. Four checks, all cheap: the graph is acyclic; every node carries an acceptance check; every edge names a gate from a closed vocabulary; every node’s declared inputs are produced by some ancestor. Fail any one and you reject the plan and re-ask with the violation quoted.

That is what makes dynamic structure debuggable rather than chaotic. The graph is a schema-checked artefact, so a bad plan is caught deterministically before anything runs, rather than discovered three nodes later by a confused executor.

F5What triggers a replan, and what stops it thrashing?

Named triggers, explicit authority, and a budget. Triggers fire on evidence — a node failing its acceptance check twice, an executor touching material the survey never saw, a node blowing past its step budget. Authority says which node may rewrite which part of the graph, because a node rewriting its own ancestors is how you get a cycle in the thing you called a DAG.

The anti-thrash rule is a monotonic progress check: a replan that does not reduce the set of open acceptance checks did not accomplish anything. Two of those in a row is an escalation to a human, not a third attempt. Without that you have rebuilt the unbounded self-correction loop from guide 0001 with a graph on top of it.

F6Anthropic reports multi-agent beating a single agent by 90.2%. You have just spent ten minutes telling me not to build one.

Different cell of the grid, and they say so in the same write-up: “most coding tasks involve fewer truly parallelizable tasks than research”, and domains requiring shared context or many inter-agent dependencies “are not a good fit.” Their case is breadth-first research — subagents reading disjoint corners of the web, mutating nothing, returning summaries. That passes the breadth permit cleanly and never trips the shared-state veto. A repository trips it on the first write.

The caveat I would volunteer, because it is the most important line in that post for this argument: they also report those systems using roughly 15× the tokens of a chat, and that token usage alone explains 80% of performance variance on their browsing evaluation. Which means an architecture comparison that does not equalise token spend is partly measuring the budget. Some of that 90.2% is architecture and some of it is money.

F7How many subagents should a lead spawn?

It is not a number you choose. It is the count of edges that passed a gate, which means the task determines it and the architecture does not. If you are picking between three and five by feel, the gates have not been applied — and Anthropic’s own guidance is that the lead scales the count to query complexity, which is the same rule stated as a behaviour.

The related failure is worth naming: they report that without detailed task descriptions, subagents “duplicate work, leave gaps, or fail to find necessary information.” Which is step repetition and context loss, arriving by the front door, in the system that is held up as the success case.

F8What is the failure mode of your approach? Sell me the case against dynamic graphs.

Four real costs. Planning becomes the bottleneck and a single point of failure — you have added a component whose mistakes are the whole system’s mistakes. A per-run graph is unreproducible, so regressions are hard to attribute: was that the model, the plan, or the task. Benchmarking gets substantially harder when the structure is a variable. And the elaborate system is more system to get wrong — MAST’s largest failure category is system design issues at 41.8%, not model limitations.

Which is why I would not start here. Start with the template, measure how often it is violated, and let that number buy the dynamic version.

F9How do you verify a node’s output?

Defined when the node is created, never after — a check written once you have seen the output is a rationalisation. Prefer external checks to model opinions: does it compile, does the suite pass, does it parse against a schema, is every item in this list traceable to a real file and line. Where a model check is unavoidable, make the task narrow and bounded rather than an open quality rating.

MAST is pointed about how this goes wrong in production: verifiers “perform only superficial checks, despite being prompted to perform thorough verification, such as checking if the code compiles or if there are leftover TODO comments” — while the task objective itself is never examined. Adding a high-level objective verification step to ChatDev bought +15.6% on ProgramDev. Verification is not a formality; it is the third-largest lever in the taxonomy.

F10Your single agent runs out of context. Then what?

In order. Compact, with the compaction prompt tuned on real traces — recall first, then precision. Keep the plan and the scratchpad on disk so they survive compaction, because a message does not and a file does. Clear stale tool results rather than carrying them forward.

If after all of that the reading still does not fit, the breadth gate has fired and subagents are now justified — but in a specific shape: one main loop carries the state; subagents are stateless workers with narrow scope that return small structured results. Notice this is not the role pipeline. Nobody is handing state to anybody. The lead never stops being the one place the plan lives.

F11We have this pipeline in production. Migrate it without a rewrite.

You do not rewrite it, you remove seams one at a time. Week one: annotate every existing edge with the gate it passes, and log the compression factor across each. You will usually find that the dramatic compressions and the ungated edges are the same edges.

Then delete them in order, highest compression first. A deletion here is a merge — two system prompts become one prompt inside one loop — which is a far smaller change than it sounds, ships behind a flag, and reverts cleanly. Measure per deletion, so each merge carries its own before and after rather than arriving as one undifferentiated rewrite that nobody can attribute.

F12One week, this system, starting Monday. What do you actually do?

Monday: instrument the boundaries — compression factor per edge and precondition failure rate per edge. Tuesday: the F1 ablation, one agent doing the three phases in sequence with the plan on disk, same model and tools. Wednesday to Thursday: delete the ungated edges, biggest compression first, one at a time, measuring each. Friday: write an acceptance check for every node that survived, because the nodes you kept are the ones you will be replanning around.

The lesson underneath all twelve: an org chart is a decomposition somebody committed to before they had seen the task. The senior move is not fewer agents, and it is not more agents. It is refusing to commit to the shape of the work until the work has told you what shape it is.

12

Glossary

The vocabulary this answer runs on. If you can use eight of these correctly and unhurriedly, the room will assume you have built one of these systems, because people who have not built one do not talk this way.

Structural prior
An assumption about the shape of the task, baked into the architecture rather than inferred from the task. “Spec, then implement, then test” is one. It is not wrong; it is just a bet, and a frozen one.
Agent boundary
Any point where work crosses from one context window into another. The unit this entire question is about. Every one of them is a compression step whether or not anyone designed it as one.
Handoff
What crosses a boundary. Lossy by construction, chosen by the sender, unauditable by the receiver, and unreported by the system.
Compression factor
Size of what crossed an edge over size of the trace it was made from. One line of instrumentation; orders your edges by risk.
Context fragmentation
The state of a system in which no single component holds the full picture, and each component’s picture is a different subset. The disease; the handoff is the vector.
Context rot
Degradation in model reliability as input length grows, with task difficulty held constant. The reason a single window is not an unlimited resource.
Compaction
Summarising a context near its limit and reinitialising with the summary. Tune for recall first, then precision. A handoff to yourself, and the one boundary you own.
Structured note-taking
Persistent memory in files outside the window. The operative property: a file survives compaction, a message does not.
Plan artefact
The plan as a file that is re-read and amended, rather than a message that scrolls away or an org chart that cannot change.
DAG
Directed acyclic graph. Here: nodes are units of verifiable output and edges are dependencies. “Acyclic” is the part replanning threatens, which is why authority has to be explicit.
Acceptance check
The condition, written before a node runs, that says what its output must satisfy. A node without one cannot be replanned around, because nothing can tell you it failed.
Gate
The named reason an edge is allowed to exist: shared state (a veto), breadth, resource, isolation, latency. No gate, no edge.
Shared mutable state
Anything two nodes both write to — a repository, a schema, an environment. Its presence is a veto on splitting, no matter what else is true.
Replanning
Rewriting the graph mid-run in response to what execution revealed. Needs a trigger, an authority and a budget, or it is a loop.
In-execution editing
The survey’s term for structure revised during a run, as against fixed templates and per-run generation. The third rung of the ladder.
Pre-execution generation
Building a run-specific graph once, before execution. The middle rung: fit to the task, but still committed before contact.
Agentic computation graph
The survey’s neutral name for any workflow of model calls, tools and checks — deliberately chosen so static and dynamic systems can be compared on one axis.
Orchestrator–worker
A lead agent that plans and holds state, with stateless workers of narrow scope returning small results. The shape that survives when the breadth gate genuinely fires.
Assembly line
MAST’s architecture label for MetaGPT, and the question’s own analogy. Unbeatable at the ten-thousandth identical car, useless when the customer orders a boat.
Step repetition
An agent redoing work already done elsewhere in the system. 15.7% of observed failures, the largest single mode, and mostly a symptom of not sharing a trace.
Reasoning–action mismatch
A gap between an agent’s stated reasoning and what it actually did. 13.2% of failures, and the label a papered-over handoff loss tends to get.
Coordination tax
Everything you pay for a boundary — tokens, latency, lost detail, unaskable questions — regardless of whether the boundary bought you anything.
Amdahl’s law
Speedup is capped by the fraction of work that cannot be parallelised. The sentence that turns “we can run these at once” into a number.
Conway’s law
Melvin Conway, 1968: a system’s design mirrors the communication structure of the organisation that built it. Here it is not an accident — the org chart was shipped as the architecture on purpose.
