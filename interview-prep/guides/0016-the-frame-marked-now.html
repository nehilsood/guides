Question 15 · Google DeepMind · senior AI engineer

The Frame Marked Now

A computer-use agent appends every screenshot to its context. At step 80 of a 300-step workflow it starts redoing work it has already done. The team wants a 2M-token window. The window is the wrong noun. Nothing in that context says which picture is the present — and a picture could not have said it anyway.

The question, as asked

“Our computer-use agent appends every screenshot and action to its context. It’s solid on 15-step web tasks. But on a 300-step desktop workflow, around step 80 it starts redoing actions it already took. The team wants to switch to a 2M-token context model. Why won’t that fix it?”

What they are actually testing

The question hands you a capacity story and waits to see whether you buy it. Four things are being checked, and only the first one is about context windows.

P1

Can you tell a capacity problem from an information problem?

A bigger window is the right answer to “it does not fit”. The symptom described is not that it does not fit — it is that the agent believes something false about the world. Those have different fixes, and only one of them is purchasable.

P2

Will you do the arithmetic, or describe it?

Everyone in this conversation can say “screenshots are expensive”. The candidate who gets the offer says how expensive, for this resolution, on this model tier, at this step — and notices that the answer changed in the last year.

P3

Do you know what a screenshot is?

It is an observation, not a state. Two different spreadsheets render identical pixels. This is the half of the answer that survives any window size, any model, and any amount of attention, because it is about what is in the bits.

P4

Does your fix have a failure mode, and can you name it before they do?

“Keep a text ledger” is correct and it introduces a new bug: when a written note and the screen disagree, models side with the note. The senior answer ships the ledger and the rule that keeps it honest.

Where this sits against the other questions in this series

Q2 (0003) was the closest neighbour and it is worth saying out loud, because the mechanism looks identical: forty skill descriptions competed for attention and the near-duplicates split it. The difference is what the duplicates are. There they were a menu you wrote, fixed in the prompt, and the agent had to choose among them. Here they are observations the agent generated itself, one per step, growing without bound, and the agent is not choosing among them — it is trying to work out which one is true now. A menu has no tense. A transcript does.

Q5 (0006) owns the mechanics of shortening a history without corrupting it, and this page leans on it rather than repeating it: the moment you adopt periodic compaction you inherit that invariant, and a fold that drops a tool_use but keeps its tool_result is a 400, not a quality regression.

Q9 (0010) asked how many context windows the work should occupy, and used context management as the argument for one agent over a pipeline. This question starts after that one is settled. The agent count is one. The question is what goes in the window.

Q1 (0001) asked when a loop should be allowed to stop. Section 09 needs that distinction and inverts it: a cap is a budget, and what this agent is missing is a detector.

01

The answer, at three lengths

Lead with the reframe, because the interviewer has deliberately given you a capacity framing to see whether you accept it.

Fifteen seconds

“Because the window isn’t the binding constraint — the information is. By step 80 that context holds eighty photographs of the same spreadsheet and nothing in it says which one is now. A bigger window buys more photographs.”

One minute

“Two separate things are wrong and the window fixes neither. First, cost: each call re-sends the whole history, so total input grows with the square of the step count — about 70 million tokens over a 300-step run at 1,560 tokens a frame, and roughly 121 million if you are on a high-resolution tier. Caching changes that invoice. It does not change what the model attends over.”

“Second, and this is the actual bug: eighty near-identical frames are eighty high-similarity distractors. Chroma measured exactly this across eighteen models — a single distractor degrades retrieval, four compound it, and the closer the distractor is to the thing you want, the worse it gets. A screenshot of the same spreadsheet one action ago is the most similar wrong answer that exists. So the agent resolves ‘is B7 filled?’ against the wrong frame and types the value again.”

“The fix is to stop using pixels as memory. Keep the current frame and the last two — enough to check whether the last action landed. Keep the full action history as text, because a click costs twenty tokens and a frame costs fifteen hundred. Keep a typed progress ledger. Compact periodically. And add a loop guard that forces a replan rather than a third attempt.”

Two minutes

Add the two things that turn this from a good answer into a senior one.

“There is a deeper reason the window can never fix this, and it is not about attention at all. A screenshot is a rendering of program state, and rendering is not injective — different states produce identical pixels. A cell showing 1,240 may hold a literal or a formula; rows may be hidden; the value may be rounded. So there is no window size, and no vision model however good, that recovers the state from the picture. The information the agent needs was never in the context. Salesforce’s StateAct paper makes that the architecture: read and write program state through code, quarantine the GUI to a subagent, and on OSWorld 2.0 the same Claude backbone goes from 20.6% to 26.9% at about a ninth of the cost.”

“And I’d flag the hazard in my own fix before you do. Once memory is text, a stale line in the ledger outranks a correct screenshot. That is measured: on 310 probes across five models, when serialised structure and pixels disagree, models follow the structure 41–79% of the time despite reading the pixels correctly, and the wrong belief converts to a wrong action at near unity. Humans do that 3% of the time. So the ledger gets one rule: it may record what happened, never what is. Events are append-only and cannot become false. State claims get re-read, every time, from the state channel.”

Don’t say Use a longer context window so the agent can see its full history.

It treats a memory-design problem as a capacity problem, and it is the answer the question was built to elicit.

It also quietly assumes the full history is worth seeing. Most of it is eighty renderings of a moment that has passed.

Say instead The window isn’t full, it’s degenerate — and even a perfect frame wouldn’t carry the state.

Then price it, name the distractor mechanism, and give the five things worth carrying forward.

Close on the rule that keeps the fix safe: a ledger may remember events, never state.

02

Three curves, and the bug is on none of them

“Cost grows quadratically” is true twice over and explains nothing about step 80. Separating the curves is the fastest way to show you are reasoning about the symptom rather than reciting the topic.

The interviewer gave you a very specific shape: fine at fifteen steps, fine for a while at three hundred, then around step 80 a behavioural change. Three quantities grow as that run proceeds, and it is worth being explicit about which ones could produce an elbow at 80 and which ones could not.

  1. Curve 1 · billing

    Total input tokens grow with the square of the step count. Every call re-sends the whole history, so after N steps you have paid for s × N(N+1)/2 tokens of screenshot, where s is the per-frame cost.

    This is real money and it is smooth. A smooth curve does not have an elbow at 80.

  2. Curve 2 · compute

    Attention is quadratic in sequence length within a single forward pass. This is a different quadratic from the first one and people routinely conflate them: the first is about re-sending, the second is about one pass over a long input.

    It governs latency and serving cost. It is also smooth, and it is not an accuracy claim.

  3. Curve 3 · accuracy

    Reliability falls as input grows, at constant task difficulty. This is the one that can produce a threshold, because it interacts with the content of what accumulated rather than only its size.

    And what accumulated here is not generic length. It is eighty near-duplicates of the one thing the agent keeps asking about.

So the honest sentence is: the first two curves are the reason this design is unaffordable, and the third is the reason it is wrong. The team is proposing to fix a problem on curve 3 by buying headroom on curve 1.

The caching point, stated precisely

Prompt caching does help, and it helps a lot: reads bill at roughly 0.1× and the prefix of an append-only transcript is perfectly stable, which is the best case caching has. Writes cost about 1.25× at the five-minute TTL, so the break-even is two reads, and every hit refreshes the clock.

But what caching changes is what you are charged for recomputing. The tokens are still in the sequence; the model still attends over all of them. A cache hit is a billing event, not a shorter context. If someone offers caching as the answer to the step-80 behaviour, that single sentence is the whole rebuttal.

In plain words

Money and speed get worse smoothly as the run goes on. Accuracy got worse suddenly, at a particular step. Those need different explanations, and a bigger window only addresses the smooth ones.

03

Do the arithmetic, because the arithmetic moved

The per-screenshot figure everyone quotes is about 1,500 tokens. That number is correct for one model tier and roughly 1.7× low for the tier most current models are on — which is enough to change whether the premise of the question is even true.

Claude does not price an image by its file size. It cuts the image into 28×28-pixel patches and charges one visual token per patch, so an image costs ceil(w/28) × ceil(h/28) tokens, and each model has a maximum long edge and a maximum visual-token count above which the image is downscaled first. There are two tiers, and a desktop screenshot sits right where they diverge.

# a 1920x1080 desktop screenshot, both tiers standard tier long edge 1568 px, cap 1568 tokens downscaled to 1456 x 819 patches ceil(1456/28) x ceil(819/28) = 52 x 30 cost 1,560 tokens high-resolution long edge 2576 px, cap 4784 tokens (Claude 4.7 and later) not downscaled 1920 x 1080 patches ceil(1920/28) x ceil(1080/28) = 69 x 39 cost 2,691 tokens

So “about 1.5k a frame” is the standard-tier answer, and it is exactly right there. On a high-resolution-tier model the same screenshot costs 2,691 — 72% more — and nothing in the application changed.

The premise is configuration-dependent, and nobody checked

“The window isn’t full, it’s noisy” is the right diagnosis and it is not a fact you can assert without knowing the tier. On a standard-tier model, step 80 is 124,800 tokens of pixels and the window genuinely is not full. On a high-resolution-tier model it is 215,280 and the window is over-full with screenshots before you have added a single word of text — at which point the harness is silently dropping frames, or the request is failing, and the elbow at step 80 has a much more boring explanation than attention.

“Before I argue about attention, I want the token count per frame on the model we are actually running, because at 1080p on a high-res tier this design runs out of window at step 75 and the symptom you are describing starts at 80.” That is worth more than the rest of the answer, because it is the only part that could be wrong and could be checked this afternoon.

Two hard limits sit underneath the token arithmetic and are worth knowing because they fail loudly rather than gradually. The API accepts at most 100 images per request on models with a 200k-token window, and 600 otherwise — and screenshots nested inside tool_result blocks count. A 300-step run that appends every frame is therefore not merely expensive on a 200k model; it becomes an invalid_request_error at step 101. Separately, once a request carries more than 20 images a stricter per-image dimension cap applies to all of them, and images returned to the computer-use tool that exceed the model’s limits are rejected rather than downscaled, so the harness has to resize before returning them.

One thing this does not buy you

Uploading frames through the Files API and referencing them by file_id is good practice and it solves a different problem. It keeps the HTTP payload small as the conversation grows, which helps latency and request-size limits. It does not reduce the visual-token count and it does not shorten the sequence the model attends over. Bandwidth and attention are separate budgets, and only one of them is the bug here.

04

Not noisy. Degenerate.

“Context rot” is the right pointer and it undersells the case. Eighty near-identical screenshots are not generic noise — they are the single worst input shape in the published results, and there is a measurement that matches this context almost exactly.

Chroma’s July 2025 report evaluated 18 frontier models across Anthropic, OpenAI, Google and Alibaba, and its controlling idea is the one that matters here: hold task difficulty constant and vary only input length. Performance falls anyway, on every model, including on tasks that are trivial at short length. Advertised context and effective context are different quantities. But the headline is the least useful part of the paper; the conditions are where the argument is.

  1. Similarity

    Performance degrades faster when the thing you want resembles the thing you do not. Needles were built at a range of semantic distances from the question — cosine similarity 0.445 to 0.775 on one corpus, 0.521 to 0.829 on another — and low-similarity pairs degraded fastest with length.

    Invert it for this case. An old screenshot of the same spreadsheet is not a low-similarity distractor. It is the highest-similarity wrong answer that could exist for the question “what is on screen now”.

  2. Distractors

    One distractor is enough to measure. Starting from a high-similarity needle, adding a single semantically similar but incorrect passage reduced performance against baseline; four compounded it; and the effect was non-uniform, with some distractors far worse than others.

    The agent in this question is adding one distractor per step, by design, for three hundred steps.

  3. Structure

    A coherently ordered haystack scored worse than a randomly shuffled one, on all 18 models. This is counter-intuitive and it is the result to quote if someone proposes that careful chronological ordering will rescue the design.

    Whatever is protecting the model, it is not narrative structure in the context. The transcript being in the right order does not make the right frame findable.

  4. Repetition

    The closest analogue in the paper is the simplest task in it. Models were asked to replicate a sequence of repeated words containing one unique word, at lengths from 25 to 10,000, across 1,090 variations. As length grew they misplaced the unique word, under-generated, and eventually produced noise.

    That is this context, abstracted: a long run of near-identical items with exactly one that is different, and the task is to say which. The agent’s context is a repeated-words problem where the repeated word costs 2,691 tokens.

There is one more result worth carrying, because it predicts the form of the failure rather than its size. On LongMemEval, with roughly 113k-token conversations, the largest drops appeared between a focused ~300-token prompt and the full one — and the models split by vendor in how they fail. Claude models tend to abstain when uncertain; GPT models tend to hallucinate. An agent that abstains stalls. An agent that hallucinates a belief about an empty cell types the value in again.

Read this evidence precisely

These are retrieval probes with known ground truth, run in a single call. They are not agent rollouts, there is no tool use, and nothing in them measures a 300-step desktop workflow. What transfers is the ordering of mechanisms — that high-similarity distractors are the expensive kind, that quantity of them compounds, that coherent ordering does not protect you — and that ordering is exactly what you need to argue the design. The magnitudes do not transfer, and if you quote a specific percentage drop as though it applied to this agent you will deserve the follow-up you get.

05

A screenshot is not a state

Everything so far is an argument about attention, and attention arguments can always be answered with “the next model will be better at it”. This section cannot be. It is the half of the answer that holds at any window size, with any vision model, forever.

Write down what the agent actually has. There is a true program state s — the files, the application backends, the DOM, the cell contents. The agent never sees s. It sees s through a channel, and it has two available.

# the two channels onto the same state pixel channel o_pix = f_render(s) a screenshot state channel o_state = g(s) a shell command, a workbook read, a DOM serialisation # f_render is not injective. many distinct states render to indistinguishable pixels, so f_render has no inverse, and no perceptual model, however good, can in general recover s from o_pix over the substate a task touches, g is effectively invertible: load_workbook(...)["B7"].value recovers the formula exactly

The spreadsheet in the question is the textbook case. A cell displaying 1,240 may hold the literal 1240 or =SUM(B2:B6). The displayed value may be rounded. The rows that determine it may be hidden or scrolled out of frame. All of those states produce the same picture, and the picture is all the agent has.

This is why the redo happens. Picking the newest of eighty frames is the second problem; the first is that “the cell is empty” and “I filled the cell and the view has not refreshed, or has scrolled, or is showing a cached render” are the same screenshot. No amount of context tells them apart, because the difference was never photographed.

The strongest version of “a 2M window will not fix it”

Imagine the best possible version of the team’s proposal: a two-million-token window, perfect attention, every frame correctly timestamped and ordered, no distractor effects at all. The agent asks: does B7 contain a formula?

It still cannot answer. The information is not degraded in that context, or crowded out, or hard to attend to. It is absent. A larger window is a larger container for a channel that never carried the bits.

And the error compounds in a way that explains why 15-step tasks are fine. A single lossy read is almost always harmless — you glance at the screen, you are right. A lossy read used as a per-step proxy over hundreds of dependent operations accumulates drift, and a long-horizon task is judged on the artefact it leaves behind rather than on any frame along the way. Fifteen steps is inside the tolerance. Three hundred is not.

Where this argument stops, and say so before they ask

The state channel gives you nothing when the task’s deliverable is the rendering. Image editing, layout, chart appearance, anything WYSIWYG: there the screen is not a lossy proxy for the thing being judged, it is the thing being judged, and reading the DOM tells you nothing about whether the slide looks right. The claim is not “pixels are inferior”. It is “pixels are the wrong channel for questions about content the screen does not show” — and knowing which questions those are is the actual engineering.

In plain words

A photo of a spreadsheet cannot tell you whether a number was typed in or calculated. So no matter how many photos you keep, or how well the model reads them, some questions the agent needs to answer were never answerable from pictures.

06

Somebody built it, and the numbers are public

The scenario in this question is not hypothetical. It is the median task on the current long-horizon computer-use benchmark, and the architecture being argued for has been built on the same backbone and measured against it.

OSWorld 2.0 (Yuan et al., June 2026) is 108 long-horizon desktop workflows. The median task takes a skilled human about 1.6 hours of active operation — roughly 48× the original OSWorld — and leading agents average more than 300 steps per task against about 30 on version 1. The best reported agents complete 20.6%. The paper’s own conclusion names the gap as memory and error recovery rather than perception.

So when the interviewer says “a 300-step desktop workflow”, they are describing the benchmark’s central regime, not an edge case. That is worth saying: it signals you know where the field actually is, and it reframes the question from “our agent has a bug” to “our agent has the open problem”.

StateAct (Salesforce AI Research, July 2026) is the architecture this answer has been describing, built and ablated. Its main agent works on program state through persistent bash, Python and a file editor; a GUI subagent handles screenshot-and-click only where it is needed; compaction summarises the oldest prefix at an assistant boundary and strips images while preserving state facts; and an independent finish gate re-reads the persisted artefact without seeing the agent’s own account of its work.

The result that stops this becoming “delete the pixels”

The same paper reports a code-only variant with no GUI subagent at all. It reaches 45.9% partial — below the screenshot-driven baseline’s 54.8%. Taken to its logical end, “memory should be text” is worse than the naive design it is criticising.

So the claim is not that pixels are bad. It is that pixels are bad as memory. They remain the right channel for perception, for the 1.1% of steps where something genuinely has to be seen and clicked, and for checking that the last action landed. Keep them. Keep three of them.

07

The fix has a failure mode, and it is worse than the bug

“Pixels are for perception, memory should be text.” Correct, and incomplete in a way that will cost you the loop if you stop there. Once memory is text, a stale line of text outranks a correct screenshot — and that is measured, not speculated.

Do GUI Agents Believe Their Eyes? (Zhang and Yang, July 2026) builds 310 probes across web, mobile and desktop, and runs a paired intervention: show a model a screenshot and a serialised structure that disagree, with the pixels defined as ground truth, and record which one it believes. The models could all read the pixels — image-only accuracy ran 0.86 to 0.93. They sided with the text anyway.

The perception–fusion gap is the fraction of probes a model reads correctly on its own and then hands to the text once both are present. Every model showed a positive gap, every cluster-robust interval excluded zero, and the human rate of deferring to contradicting text is an order of magnitude below every model tested. This is not a small-model artefact; GPT-5.4 sits at 0.51.

Three details turn this from an interesting result into something you can act on.

  1. It is causal

    Ablating the conflicting serialised value flipped the belief back to the pixels in 0.63 of structure-following cases, against 0.03 for ablating a random token — roughly a 19-fold difference. The copied text is driving the belief, not correlated with it.

  2. It reaches the action

    On AndroidWorld, action error was under 5% when the channels agreed and 0.91 to 1.00 when they conflicted. On 36 audited conflicts the wrong action landed on an incorrect page 25 times. A mis-sourced belief is not a scoring curiosity; it is a click.

  3. It tracks the interface, not the model

    Coordinate-emitting GUI agents barely budged (0.03–0.07). Index-based agents were hijacked at 0.96–0.97, the same as general vision models. The vulnerability belongs to the action format you chose, which is a design decision, not a model property.

Now map it onto the proposed fix. A progress ledger is serialised structure. A ledger line reading B7: filled that has gone stale is precisely the paper’s structure-swap condition, manufactured by your own architecture and injected on every single step. You have taken a context the model was confused by and replaced it with a context the model will confidently believe.

The paper’s own mitigation is the shape of the answer: a training-free, source-aware re-grounding gate — ask whether the pixels show what the text claims before acting on it — cut structure-following action error by 24 to 44 percentage points, and on stale-reference probes cut deference from 0.69–0.95 to 0.07 or below, while leaving the agreement case untouched. That is cheap, and it is a gate rather than a prompt.

Hold this one at the right strength

These are deliberately manufactured conflicts, and the study defines the pixels as ground truth, which is a reasonable convention for a UI and not a law — there are real cases where the accessibility tree is right and the render is stale. Two of the five models are open 7–8B checkpoints and carry the largest gaps. What survives all of that is the direction and the human comparison: models systematically over-trust serialised text relative to their own correct perception, and people do not. Quote the direction and the 0.03, not a single model’s number.

08

A ledger may remember events. It must never remember state.

This is the rule that makes the text ledger safe, and it is one question applied to every line you are tempted to write down: can this sentence become false while the agent is not looking?

The newsletter’s progress ledger has three slots — subgoals done, subgoals pending, facts extracted — and they are not the same kind of claim. “Subgoals done” is a record of history. “Subgoals pending” is a derived judgement about the present. Mixing them in one structure is how the ledger goes quietly wrong, and section 07 is the measurement of what happens next: the model believes the stale half over its own eyes.

How big does the ledger have to be?

“Compact every N steps” leaves the obvious question open, and most teams answer it with a percentage of the window — a budget with no theory behind it. There is now a theory. Context Compaction Theory (Tirmazi, Markelon, Bishop and Mitzenmacher, August 2026) formalises compaction as two games: selection, where you keep a subset of what you have under a budget, and generation, where you may write any message you like of bounded length. Its main result is clean enough to quote:

# Theorem 1, informally the minimum budget at which a generation algorithm answers a query set within error e equals the one-way communication complexity of the induced communication problem # Theorem 3 generation can beat selection by a factor of log n: where generation needs n bits, selection can require n·log(n)

Two things fall out of that, and both are directly usable in the room.

The ledger’s size is set by the queries, not by the window. You cannot ask how big the ledger should be until you have written down what it must answer — have I already done X, what have I extracted, what is left. Once that query set is fixed there is a minimum, and it is a property of the task rather than a preference. It is also the answer to “why not keep the last K messages”: selection is provably the weaker instrument, and a summary can be a log factor more efficient than a subset of the transcript.

And a general-purpose summariser is not near that bound. The paper’s case study ran Anthropic’s compaction endpoint over 15,000 items on set-membership queries and found error rates close to random guessing, against a Bloom filter of the same size. Whatever an LLM summariser is good at, it is not losslessly carrying an enumerable set across a fold — which means the thing you must not hand it is the checklist. Compact the narration. Leave the typed ledger alone.

Do not over-claim the compaction result

Set membership is close to the worst case for a summariser: incompressible by construction, no structure to exploit, and compared against a data structure purpose-built for exactly that query with one-sided error. Real agent state is enormously more compressible, and a summariser does fine on it. The transferable claim is the ranking, not the gap — for facts that are enumerable and must be answered exactly, structure beats prose — plus the genuinely useful reframe that there is a lower bound at all, and that it is a function of your query set.

In plain words

Write down what you did, never what is currently true. “I typed 42 into B7” stays true forever. “B7 is empty” can turn false the moment anything happens, and a note that has turned false is worse than no note, because the model trusts it.

09

The loop guard is a detector, not a budget

The last item on the fix list is the one most likely to be built wrong, because the obvious equality test is the one section 05 just ruled out.

The reference implementation is public. Magentic-One (Microsoft Research, 2024) runs its orchestrator as two nested loops: an outer loop maintaining a task ledger of facts, guesses and plan, and an inner loop maintaining a progress ledger that is rebuilt every iteration by answering five questions — is the request satisfied, is the team looping or repeating itself, is forward progress being made, who should act next, and what should they be told. A stall counter increments whenever a loop is detected or progress stops. While it stays at or below a threshold of two, the run continues; above it, the orchestrator rewrites the task ledger, revises the plan, and restarts the inner loop.

Note the shape: the guard does not end the run. It triggers a replan, and it gives the agent a small budget of recoveries before it does — which is what separates a loop guard from the cap in Q1. A cap fires on a count and knows nothing about what happened. A guard fires on evidence. One is a budget, the other is an instrument, and an agent that repeats an action at step 80 has a detection problem rather than a stopping problem.

The correction, and it follows from section 05

The usual formulation is “if the same action hits the same screen state twice, force a replan”. Comparing screens is the wrong equality test, and it fails in both directions for the same reason the pixels failed as memory.

False positives, because rendering is not injective: the agent writes a value into a row that is scrolled out of view, the screen is byte-identical, and the guard fires on a step that actually worked. False negatives, because rendering is not stable either: a blinking caret, the clock in the menu bar, a tooltip, a hover highlight, a one-pixel antialiasing difference. Hash the pixels and the hash never repeats, so the guard never fires at all — which is the more common outcome in practice and the harder one to notice, because a guard that never fires looks exactly like a guard that is not needed.

Compare state. A hash of the substate the task touches, read through the state channel, or the action signature paired with its observed effect on that substate. Same instrument, correct input.

One more property worth borrowing from Q9, which worked this out for a different reason: a replan needs a trigger, an authority and a budget. The trigger is the stall counter. The authority is which part of the plan may be rewritten. The budget stops the agent replanning its way through the afternoon — a replan that does not reduce the set of open subgoals accomplished nothing, and two of those in a row is a human.

What to carry forward, and what it costs

The fix list, in the order you should say it, with the one addition that the measurements in sections 07 and 08 force. This is the part of the answer the interviewer is waiting for; everything before it was earning the right to be believed.

  1. 1 · Pixels

    The current frame and the last two. Drop the rest.

    Two and not one, for a specific reason: a single frame shows you the present but cannot tell you whether anything changed, and “did my last action land” is a question about a difference. The window is a verification device, not a memory.

  2. 2 · Actions

    The full history, as text, in the past tense.

    About 20 tokens a click against 2,691 for a frame. Keeping every action for a 300-step run costs ~6,000 tokens — less than three screenshots. There is no version of this trade-off that favours the pixels.

  3. 3 · Ledger

    Typed, append-only, events and extracts only.

    Per section 08: no line in it may assert the present. Subgoals done, facts extracted with their provenance, artefacts written and where. Status is derived at read time, not stored.

  4. 4 · Compaction

    Every N steps, fold the narration and strip the images. Never fold the ledger.

    Images are stripped at the fold rather than summarised, because a prose description of a screenshot is the stale state claim of section 08 with extra steps. And the fold must be pair-aware: dropping a tool_use while keeping its tool_result is an API error, not a quality regression.

  5. 5 · Loop guard

    On state equality, with a threshold, triggering a replan.

    Not pixel equality (section 09). Not a retry — a third attempt at an action that has already failed twice is the behaviour you are trying to stop.

  6. 6 · Re-read

    Before acting on a precondition, read it. Every time.

    This is the sixth item and it is not on the usual list. It is the operational form of the ledger law, and it is the intervention that was actually measured: the source-aware re-grounding gate in section 07 cut conflict-case action error by 24–44 points and stale-reference deference to 0.07, without touching the cases where the channels agreed.

Five checks, and one of them is the whole diagnosis

Every claim above is falsifiable on this team’s own agent inside a day. The second one is the check that separates a candidate who has read about context rot from one who would find out whether it is what is happening here.

  1. 01The ablation

    Re-run the same tasks with a three-frame window and change nothing else.

    Same model, same prompts, same tools, same tasks. If success is unchanged or better, the frames were never carrying memory and the whole cost saving is free. If it drops, something in the discarded frames mattered and you can go and find out what — a better position than theorising about it.

    Watch forRun it on the 15-step tasks too. If the window hurts there and helps at 300, the right design is adaptive and you have just found the crossover.

  2. 02The gate · the only one that answers the question asked

    Plot the step at which the first redundant action occurs, as a distribution, against the number of frames retained.

    The interviewer did not give you a success rate. They gave you a step index — “around step 80” — and a success rate is precisely the statistic that destroys it. Averaging a 300-step run into one number mixes the 79 steps that worked with the one that did not and reports something that describes neither.

    Retain 3 frames, 10, 40, everything. For each, record the distribution of the first repeated action. If the curve moves right as you retain fewer frames, the distractors are the mechanism and the fix is the fix. If it does not move at all, the problem is not context at all — it is that the state was never observable from the screen (section 05), and you have just saved yourself from shipping the wrong repair.

    Why it is the gateIt is the only check whose outcome changes what you build. Every other check on this list confirms or prices a decision; this one chooses between two different diagnoses that have the same symptom.

  3. 03The conflict probe

    Inject one deliberately stale ledger line and see whether the agent believes it over the screen.

    This is section 07’s experimental design shrunk to a unit test, and it costs an afternoon. Write B7: filled into the ledger when B7 is visibly empty, and record what the agent does. A healthy agent re-reads. An unhealthy one proceeds, and you have measured your own perception–fusion gap before it costs you a run.

    Run it both waysAlso inject a stale line that is harmless. If the agent re-reads everything on every step you have bought correctness with latency, and that is a trade you should make deliberately rather than discover.

  4. 04The guard’s negative control

    Make the agent legitimately repeat an action and confirm the loop guard stays quiet.

    Typing the same value into two different cells is two identical actions with two different effects. A guard keyed on the action alone fires; a guard keyed on action-plus-state-effect does not. Without this control you cannot tell a working guard from one that has never fired, and both look identical in a green test run.

    The paired positiveThen force a real loop and confirm it fires within the threshold, and that what follows is a replan rather than a third attempt.

  5. 05Price it, and count the images

    Tokens per step, cache hit rate, dollars per task — and the maximum number of image blocks in any single request.

    The first three turn an architectural opinion into a business case. The fourth is a correctness check wearing a cost check’s clothes: if that count exceeds 100 on a 200k-context model, or 600 on any other, the run is not expensive, it is invalid, and no amount of attention analysis will explain the failure.

    Also logThe per-frame visual-token count your harness is actually sending. Everyone assumes 1,500. Half of them are sending 2,691.

12

Twelve follow-ups

Roughly in the order they arrive. F2, F4 and F8 are the ones that are really checking whether you understood the answer or memorised it.

F1So a bigger window is never useful?

“It is useful whenever the information you need is genuinely present in the context and genuinely does not fit — a long document you have to read end to end, a codebase you want in one pass, a transcript you are summarising. Those are capacity problems and capacity is the right purchase.”

“This is not one. Two reasons. The information about whether B7 holds a formula was never in any frame, so no window contains it. And the thing that grows is the distractor count: at 2,691 tokens a frame, a 2M window holds 743 screenshots. You have not removed the near-duplicates, you have bought room for 743 of them.”

F2We already have prompt caching. Doesn’t that solve it?

“It solves the invoice and nothing else. An append-only transcript is the ideal caching shape — a stable prefix, reads at about 0.1×, writes at 1.25× on the five-minute TTL so you break even after two reads, and every hit refreshes the clock.”

“But a cache hit means the model did not have to recompute those tokens. It does not mean they are not in the sequence. The attention pattern is identical whether the KV came from cache or from the GPU. If caching fixed context rot it would be the first optimisation in history that improved accuracy by changing where the bytes were stored.”

F3Why three frames? Why not one, or ten?

“Three is a starting point, not a principle, and I would sweep it — that is check 01. But there is a floor and it is two, not one. Verifying that an action landed is a question about a difference, and you cannot take a difference with one sample. One frame tells you what the screen shows; two tell you whether your click did anything.”

“The third is slack for actions whose effect is delayed by a render or a network round trip. If the sweep says the right number is six on this application, it is six. What it will not say is eighty.”

F4Then why not drop screenshots entirely and read the accessibility tree?

“That is the state channel and it is most of the win — in the StateAct results the GUI subagent was needed on 1.1% of main-agent steps. But the same paper has the number that stops me saying ‘entirely’: the code-only variant with no GUI path at all scored 45.9% partial against the screenshot baseline’s 54.8%. Removing pixels was worse than the design we are criticising.”

“And there is a second-order effect I would watch. The belief study found the vulnerability tracks the action interface: coordinate-emitting agents stayed visually grounded at 0.03–0.07 structure-following, index-based ones were hijacked at 0.96. So moving to a tree-indexed action space is not a neutral refactor — it is the configuration that over-trusts the tree.”

F5What exactly goes in the progress ledger?

“One test on every line: can this sentence become false while the agent is not looking? step 46: typed 42 into B7 cannot — the past is fixed. B7 is empty can, one action later. Events and extracts go in; state claims and derived statuses stay out.”

“Extracts carry their source, because ‘totals 42.10, 18.75’ is only safe if the PDF it came from is immutable — put the path and the hash in the line and it becomes checkable rather than trusted. And status is derived at read time from the events, never stored, because a stored status is a cache and nobody wrote the invalidation.”

F6How do you compact a history without corrupting it?

“Operate on turns, never on individual messages. A tool_result whose tool_use has been folded away is an orphan and the API rejects the next request outright — that is a hard failure, not a quality regression, and compaction is by far the most common way to cause it in production.”

“Then: fold narration, strip images at an assistant boundary, and never fold the typed ledger. A prose summary of a screenshot is a state claim with extra steps, which is the thing section 08 forbids. The ledger is already the compacted form; summarising it again only loses information.”

F7Isn’t the real answer to split this across several agents?

“Delegation is useful here, and for one reason only: a subagent is a fresh context. That is a context-management device, not an organisation chart, and StateAct uses it that way — hand a subgoal to a new agent so the main agent’s window stays focused.”

“But the same paper tested depth and found flat delegation beat both recursive variants, 61.6 against 57.6 and 57.9. So: one main agent, shallow delegation, state-grounded. The failure mode of the alternative is the one in Q9 — every handoff is a lossy, sender-chosen, silent boundary, and you have added several to fix a problem caused by one window being badly managed.”

F8It repeated an action. Isn’t that just a stopping problem — cap the retries?

“A cap would stop the symptom and teach you nothing, and it is the Q1 trap: a cap fires on a count, a guard fires on evidence. But the deeper point is that this is not a stopping failure at all. The agent is not persisting at something it knows has failed. It believes the action never happened.”

“That is a belief error, and the instrument for a belief error is a re-read, not a budget. Capping retries on an agent that thinks it is doing something for the first time just makes it give up on the first thing instead.”

F9What about tasks where the screen really is the point?

“Then the state channel gives me nothing and I should say so rather than force it. Image editing, layout, chart appearance, anything WYSIWYG: the rendering is not a lossy proxy for the deliverable, it is the deliverable, and reading the DOM tells me nothing about whether the slide looks right.”

“The engineering is deciding this per subgoal rather than per application. ‘Does this question concern content the screen does not show?’ is the test, and most desktop workflows have a handful of genuinely visual subgoals embedded in a mass of state manipulation.”

F10How would you know the fix worked?

“The first-repeat-step distribution moves right or it did not work, and that is the only metric that answers the question you asked me. The conflict probe from check 03 confirms the new ledger did not import a new failure. And cost per task tells me whether I can afford to run the experiment at scale.”

“One attribution trap. Success rate will go up for reasons unrelated to attention — fewer dropped frames, no request rejections, shorter latency, more tasks finishing inside the budget. If I only report success rate I will claim credit for fixing context rot when I actually fixed an invalid request, and the next team to hit this will be misled by my write-up.”

F11Where else does this pattern show up?

“Anywhere an agent appends observations to a transcript and then queries the transcript. Re-reading the same file after editing it and keeping both copies. Tailing a log and accumulating every poll. A browser agent dumping the DOM each step. A retrieval loop that pulls back the same chunk under four different queries. A CI log pasted in full on every iteration of a fix-and-rerun cycle.”

“The test is the same two questions every time. Am I storing an observation where I should be storing an event? And am I caching a claim I ought to be re-reading? Those catch it before it becomes a 300-step bug.”

F12If you had to leave the team with one sentence, what is it?

“The context is a transcript, and they have been asking it questions only a database can answer. A transcript is a record of what was said and seen, in order. It is excellent at ‘what happened’ and it has no opinion whatsoever about ‘what is true right now’ — every entry in it was true once, and nothing marks which ones still are.”

“So before anything goes into a context I would ask what tense it is in. If it is past tense, append it, it is free and it stays true. If it is present tense, do not store it at all — go and read it when you need it. Almost everything that went wrong in this run is one team writing present-tense facts into a past-tense structure, and the window size was never going to have an opinion about that.”

Glossary

Every term used above, in the sense this page uses it.

accessibility tree
The structured description of a UI exposed by the operating system or browser for assistive technology. One concrete form of the state channel, and the thing an index-based agent addresses its clicks to.
append-only
A structure you may add to but never edit. The property that makes an event ledger safe: nothing already written can be made wrong by something that happens later.
attention budget
The informal name for the fact that a model’s ability to use its context does not scale with the context’s size. Spending it on duplicates is spending it.
cache
A stored copy of something whose authoritative version lives elsewhere. Used on this page as an accusation: a state claim in a ledger is a cache, and the bug is always the missing invalidation.
compaction
Folding an older stretch of history into a summary and continuing from it. Here: folds narration, strips images, never touches the typed ledger.
context rot
Reliability falling as input length grows with task difficulty held constant. Measured by Chroma across 18 models. Not a synonym for “the window is full”.
coordinate action
An action space where the agent emits pixel coordinates. Measurably more resistant to being misled by contradicting serialised text than an index-based space, because the coordinate has to come from the image.
derived status
A conclusion computed from evidence, such as “subgoal 3 complete”. Cheap to recompute, dangerous to store, because it can be falsified by changes to anything it was derived from.
distractor
Content that resembles the answer and is not it. The expensive kind of context, and the kind an appended screenshot history is made entirely of.
effective context
The input length over which a model actually performs, as opposed to the length it will accept. The gap between the two is the subject of this question.
event
A past-tense record of something that happened: who did what, when, with what result. The only kind of claim an agent may safely remember indefinitely.
extract
A value lifted out of a source and written down. Safe to remember only when carried with its provenance — path, version or hash — so it can be re-derived rather than trusted.
finish gate
An independent check that re-reads the persisted artefact and ignores the agent’s account of its own work. Worth 4.1 partial points in the StateAct ablation.
first-repeat step
The step index at which an agent first performs a redundant action. The diagnostic statistic for this failure, and the one a session-level success rate destroys.
injective
A function that maps distinct inputs to distinct outputs, and therefore has an inverse. Rendering is not injective, which is the formal content of “a screenshot is not a state”.
loop guard
A detector that fires when the agent repeats itself without progress, and triggers a replan. Distinct from an iteration cap, which fires on a count and knows nothing.
one-way communication complexity
The minimum number of bits one party must send another so the second can answer a query set. Proved equal to the minimum compaction budget, which is why ledger size is a function of your queries.
OSWorld 2.0
108 long-horizon desktop workflows, median ~1.6 h of skilled human operation, 300+ agent steps per task. The benchmark this question’s scenario sits in the middle of.
pair-aware compaction
A fold that removes a tool call and its result together. The alternative produces an orphaned tool_result, which the API rejects outright.
perception–fusion gap
The fraction of cases a model reads correctly on its own and then abandons once contradicting text is also present. Positive for every model tested; 0.03 for humans.
pixel channel
Observing state by rendering it and looking at the result. Lossy and non-invertible, and the only channel available for genuinely visual questions.
program state
The files, application backends and DOM that actually hold the task data — as opposed to the picture of them. What a long-horizon task is ultimately judged on.
progress ledger
Structured state the agent maintains across steps. In Magentic-One, rebuilt every iteration by answering five questions, one of which is whether the agent is looping.
prompt caching
Reusing computed attention state for an unchanged prefix. Reads at ~0.1×, writes at ~1.25×. Changes the bill, not the sequence.
re-grounding gate
A check that asks whether the pixels support what the text claims before acting on it. Cut conflict-case action error by 24–44 points without touching the agreement case.
stall counter
A count of consecutive iterations without forward progress. Below threshold, continue; above it, rewrite the plan. A budget for recovery, not for the task.
state channel
Observing state by querying it directly — a shell command, a workbook read, a DOM serialisation. Effectively invertible over the substate a task touches.
visual token
One 28×28-pixel patch of an image. The unit a screenshot is billed and attended in: 2,691 of them for a 1080p frame on a high-resolution tier.
