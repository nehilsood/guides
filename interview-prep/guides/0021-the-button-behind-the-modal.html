Question 20 · Google · AI engineer

The Button Behind the Modal

Every unit test passed because every unit test was asking whether the button exists. The user was asking whether they could see it and press it. Those are different questions, answered by different machinery, and a simulated DOM never runs the machinery that answers the second one. So the agent has to check its fix where the user lives: in a real browser, with a test that fails before the fix and passes after it. Pixels come in only when the bug is one you can only see.

The question, as asked

“Your coding agent fixes a front-end bug. Every unit test passes. The UI is still visibly broken. How should the agent verify its own fix, and do you actually need a multimodal model to do it?”

00

What they are actually testing

On the surface this is a tooling question: Playwright or a vision model. Underneath it is the oldest question in testing, the oracle problem. Whatever decides “fixed” can only judge what it can observe. The interviewer wants to hear you ask what each check can see before you pick one.

Probe 1

Do you know why green tests and a broken screen can both be true?

Component tests usually run in jsdom, a JavaScript copy of the DOM with no layout and no paint. It never works out where anything is on screen or what sits on top of what. Every bug that lives in those stages is invisible to it by construction, not by bad luck.

Probe 2

Do you reproduce before you fix?

A check written after the fix proves nothing: it may never have been able to fail. The senior habit is red first. Write a browser test that fails on the current code, for the reason in the bug report, then fix until it passes. Anyone who has seen SWE-bench will know this as fail-to-pass.

Probe 3

Can you match the check to the kind of bug?

“Present”, “visible”, “clickable” and “looks right” are four different questions. A cheap, deterministic check answers the first three. Only the last needs pixels, and even then a screenshot compared with a known-good one comes before a model’s opinion.

Probe 4

Do you know where a vision model belongs, and what it gets wrong?

The model that edits the code and the model that checks the screen do not have to be the same one. A vision model as a checker is slow, gives different answers on reruns and misses small defects, often while saying the page looks fine. Use it where nothing cheaper can see the bug, and measure how often it misses.

01

The answer, at three lengths

Say the thirty-second version out loud before reading on. Everything after it supports one of its sentences.

30 seconds

The unit tests ran in a fake DOM that never lays out or paints the page, so they can only tell you an element exists, not that a person can see it or press it. I’d make the agent reproduce the bug in a real browser first, with a Playwright test that fails on the current code for the reason in the report, then fix until it passes and keep it as a regression test. For behaviour bugs a text-only model plus the browser and its accessibility tree is enough. For bugs you can only see, I’d add pixels: a screenshot compared with a known-good one first, and a vision model as the checker only where there is no reference, measured on planted defects.

2 minutes
  1. Say why the tests lied. jsdom builds the DOM and runs your JavaScript, but it never computes layout, paints, or checks which element is on top at a point. A button can be present, have the right label, pass every assertion, and sit under a modal.
  2. Split the question into four. Is it present (in the DOM)? Visible (rendered with a size, not hidden)? Hittable (the top element where a click lands)? Right (looks the way the design says)? Each needs a different check.
  3. Red before green, in a real browser. The agent writes a Playwright test that reproduces the bug and runs it on the current code. It must fail, and the failure message must match the bug. Only then does it edit.
  4. Assert what the user would do. Click the button the way a person would, rather than only checking it is visible. In Playwright a click refuses to go through if another element would receive it, which is exactly the covered-button bug. A plain visibility check does not catch it.
  5. Pick the cheapest check that can see the bug. Behaviour: DOM and accessibility tree. Overlap, clipping, off-screen: geometry from the real layout. Regressions in appearance: screenshot against a known-good one. Only taste and design fidelity with no reference need a vision model.
  6. Keep the editor and the checker separate. A text-only model can drive the whole edit loop. A vision model, if needed, is a checker called at the end, tested on screens with known defects so you know how often it says “looks fine” when it isn’t.
One line

“A unit test proves the button exists. The user needs it visible, on top and clickable. Reproduce the bug in a real browser first, and bring in pixels only for bugs you can only see.”

The two tempting answers “Give it a vision model and let it look at a screenshot.” Or: “Add more unit tests.”

The first spends the slowest, least reliable check on bugs a script could catch, and it can say “looks fine” about a page that isn’t. The second adds more checks that are blind in exactly the same place as the ones that already passed.

Neither asks what the existing tests could observe, which is the reason they passed.

The answer that gets the job The tests checked the code, not the screen. I’d reproduce it in a real browser, red before green, and add pixels only where the bug is visual.

Name the stage the unit tests skip, split “works” into present, visible, hittable and right, write a browser test that fails first, pick the cheapest check that can see the bug class, and put a vision model at the end as a measured checker, not in the driver’s seat.

02

The fundamentals, in plain words first

Seven ideas carry the whole answer. Each starts with the plain version. The precise version follows, because the interviewer will use the precise words.

How a browser turns code into a screen

HTML becomes a tree of elements. Then the browser works out styles, sizes and positions, paints, and stacks the layers.

The stages, in order: build the DOM (the tree of elements), compute styles for each element, run layout (every box gets a size and a position), paint (pixels for each box), and composite (stack the painted layers in z-order to make the final picture). When you click, the browser runs a hit test: which element is on top at that point. That element gets the click, whatever is underneath.

jsdom, and what “unit test” usually means on the front end

A copy of the browser’s DOM written in JavaScript, so tests run fast in Node. It has the tree but no screen.

Jest and Vitest component tests normally render into jsdom. It parses HTML, runs your scripts and fires events, so logic, state and text can all be checked. It does not do layout: sizes and positions come back as zeros, and stylesheets that a bundler handles are often not loaded at all. A test there can confirm an error message was put in the DOM. It cannot tell whether a person would ever see it.

A real browser under automation

The actual browser engine, driven by a script that clicks, types and reads the page the way a person would.

Playwright (or Puppeteer, Selenium) launches Chromium, Firefox or WebKit, often headless, and runs every rendering stage. Its locators find elements by role and name, the way a user would describe them. Its actions wait until an element is actually ready to use. Its assertions retry until they pass or time out. The cost: seconds per test instead of milliseconds, and a real server to test against.

The accessibility tree

The browser’s own text summary of the page for screen readers: every control’s role, name and state.

It is derived from the DOM and the computed styles, so display:none content drops out, and a properly built modal (with aria-modal or inert) hides the page behind it. A text-only model can read it like a document: “button ‘Submit’, disabled; alert ‘Name is required’”. It is how many browser agents see a page without a single screenshot.

Fail-to-pass

A test that fails on the broken code and passes on the fixed code. Proof that the test can see the bug and that the fix removed it.

The term comes from SWE-bench, which scores a patch with two sets of tests: FAIL_TO_PASS (fail before the fix, must pass after) and PASS_TO_PASS (passed before, must still pass, so nothing else broke). A test that passes on both versions measured nothing about this bug.

The oracle

Whatever decides whether the output is right. It can only judge what it can observe.

In testing, the oracle problem is that deciding “correct” is often harder than producing an output. A unit test is an oracle that observes the DOM. A screenshot diff observes pixels against a reference. A vision model observes pixels against its own idea of “looks right”. Pick the oracle by asking whether the bug is inside its field of view.

Multimodal, and what “pixels in the loop” means

A model that takes images as input. Pixels in the loop means some check looks at the rendered picture.

That check can be plain code (compare against a stored screenshot, count differing pixels) or a vision-language model asked “is anything overlapping or cut off?”. Neither has to be the model writing the code. The question “do you need a multimodal model?” really asks which role needs to see pixels, if any.

Guide 0019 covers what goes wrong when that vision model’s verdict becomes a training reward. This page uses it as one check among several.

03

What the unit test never ran

The green tests weren’t wrong. They answered a smaller question than the one the user asks. Line up the browser’s stages against what each kind of test actually executes, and the gap is plain to see.

DOMthe element tree Stylewhich rules apply Layoutsize and position Paint + compositepixels, stacked Hit testwho gets the click
jsdom unit test Built. Scripts run, events fire, text is there. Partly. Inline styles and loaded stylesheets; CSS a bundler handles is often missing. Not run. Sizes and positions read back as 0. Not run. There is no picture. Not run. click() sends an event straight to the element.
Real browser + Playwright Built. Every rule, every media query. Real boxes at a real viewport size. Real pixels, one engine and one font set. A click lands on whatever is on top.
The user Gets the result of all five stages, on their own screen size, browser and fonts.

Read it as a field of view. A check can only fail on a bug that lives in a stage it ran. Everything right of the first hatched cell is outside a jsdom test’s view, so a bug there passes every time, however many tests you write.

Bugs that live in the hatched cells

  • Covered: a modal, sticky header, cookie banner or toast sits on top (z-index, stacking context).
  • Clipped or off-screen: overflow:hidden cuts off the error message; the button is pushed below the fold or outside a fixed-height panel.
  • Hidden by CSS jsdom never loaded: a class sets display:none or opacity:0, so a check in jsdom sees no reason to call it hidden.
  • Only at some sizes: a media query breaks the layout at 390 pixels wide, and jsdom has no width.
  • Looks wrong: overlapping text, wrong colour or contrast, a broken image, a font that didn’t load, a misaligned grid.
  • Only in one engine: fine in Chromium, broken in Safari’s WebKit.

In plain words

A unit test on the front end reads the page’s blueprint. It never builds the page. If the problem is in how the page was built, how big things ended up or what ended up on top, the blueprint looks fine.

04

Present, visible, hittable, right

“The button works” is four claims stacked on top of each other. Each one needs a check that can see it, and the newsletter’s own advice, “assert it’s visible, not just present”, stops one claim short for the very bug it describes.

A screenshot compared with a known-good one, or a vision model asked a specific question about it.

Assert what the user does, not what the DOM holds. A user doesn’t check that a button is visible. They press it.

This is why the senior answer is phrased as actions. “Fill the name with nothing, press Submit, expect an alert saying the name is required” exercises every claim at once: the button must be on top to be pressed, the press must reach the handler, and the alert must render with a size. Playwright’s actions refuse to act on an element that isn’t stable, enabled and on top, and that is exactly the check a person makes without thinking.

One trap inside the fix

click({ force: true }) turns those checks off and fires the click anyway. So does dispatching the event by hand. An agent that hits “intercepts pointer events” and reaches for force has made the test pass by blinding it. Treat force: true and dispatchEvent('click') in an agent’s test as a red flag your harness can grep for.

05

Fail-to-pass, done properly

The newsletter’s core instruction is right: reproduce first. The detail that makes it work is what you check on each run, because a reproduction can be wrong in four ways and only one of the four outcomes means anything.

After the fixTest fails
After the fixTest passes
Before the fixTest fails
The fix didn’t workOr the test checks something the fix can’t change. Read the new failure before editing again.
Fail-to-passThe test could see the bug, and the fix removed it. The only outcome that counts, if the failure was for the right reason.
Before the fixTest passes
Not a reproductionIt never saw the bug. Something in it differs from the report: viewport, data, browser, timing.
Proves nothingPassing on both versions is the green unit test all over again. This is what a check written after the fix usually looks like.

Red, then green, for the same reason. The top-right cell is necessary but not enough: a locator typo also fails before the fix, and a flaky test can pass after it by luck.

// e2e/signup-submit-reachable.spec.ts written by the agent before any edit test('submit is reachable on a phone-sized screen (#482)', async ({ page }) => { await page.setViewportSize({ width: 390, height: 844 }); // the size in the bug report await page.goto('/signup'); await page.getByLabel('Name').fill(''); await page.getByRole('button', { name: 'Submit' }).click(); // before the fix: times out, // div.cookie-banner intercepts pointer events await expect(page.getByRole('alert')).toHaveText('Name is required'); });

What the agent checks, in order

  1. 01 · from the report

    Write the steps a person took, at the size and in the browser they used.

    Viewport, data, logged-in state and browser engine are part of the bug. A reproduction at the default 1280 × 720 often passes before the fix, which lands it in the bottom-left cell.

  2. 02 · red

    Run it on the current code. It must fail.

    If it passes, the agent hasn’t found the bug yet and must not start editing. That’s a finding in itself: tell the person who filed the report what you tried.

  3. 03 · right reason

    Read the failure and match it to the report.

    “Intercepts pointer events, from div.cookie-banner” matches “I can’t press Submit on my phone”. “Locator not found” or a timeout on page load does not. A mismatched failure means the test is broken, not the app.

  4. 04 · not flaky

    Run it several times before and after.

    Front-end tests fail at random for reasons like animations, slow network and timing. Five out of five red, then five out of five green, is cheap insurance against “fixing” a flake.

  5. 05 · green + nothing else

    After the fix, the new test passes and every old test still passes.

    That is SWE-bench’s FAIL_TO_PASS plus PASS_TO_PASS. Moving a banner can cover something else, so the existing browser tests matter as much as the new one.

  6. 06 · revert

    Undo the source change, keep the test, run it: red again.

    This closes the loophole where the agent wrote both the test and the fix. If the test passes with the fix reverted, it was never checking the fix. It takes one extra run.

In plain words

Before fixing anything, prove you can make the bug happen on demand, in a real browser, for the reason the user described. Then fix it, prove it’s gone, and prove that undoing your fix brings it back. Keep the test so it can never quietly return.

06

The ladder: the cheapest check that can see the bug

The newsletter splits bugs into “behaviour” and “visual” and puts pixels on the visual side. There is a rung in between that does most of the visual work without a single pixel: geometry from the browser’s real layout.

Climb only as far as the bug. Each rung up costs more time and more noise. Rungs 1 and 2 are where a text-only model is entirely at home. Rungs 3 and 4 still need no image: the browser hands back numbers. Pixels start at rung 5.

Most “visual” bugs are geometry

Overlap is two boxes that intersect. Clipping is content wider than its container: scrollWidth > clientWidth. Off-screen is a box outside the viewport. Too small to tap is a box under 24 by 24 CSS pixels, the WCAG 2.2 minimum. All of these are numbers the real browser has already worked out, and a script can assert them exactly, every run, with no model involved.

What geometry can’t see: colour that looks wrong, an image that rendered as a grey box, a font that fell back, a chart drawn on a <canvas>, and whether the page matches what the designer drew. Those need pixels.

07

So, do you need a multimodal model?

Ask it per role, not per system. An agent that fixes front-end bugs has several jobs, and only some of them involve looking at a picture. Most of them don’t need a model at all.

Role in the loopWhat it readsNeeds pixels?Needs a vision model?
Editor: reads code, writes the fixSource files, test output, the browser’s text reportsNoNo
Reproducer: writes and runs the browser testAccessibility snapshot, console, network, failure messagesNoNo
Behaviour, interaction and geometry checksAssertions on the DOM, actions and layout numbersNoNo: plain code
Appearance check against a referenceTwo screenshotsYesNo: a pixel diff
Design check with no referenceA screenshot, a mock, a rubricYesyes

Two rows out of six need a vision model, and neither one drives the loop. That is the pattern the newsletter describes: a text model edits, and a vision model, when needed, is a checker at the end. The last row is the case people forget: if the task itself arrives as a picture, whoever reads the task has to see it.

What the evidence says about giving the editor eyes

  1. 01 · tools

    The most-used browser tool for agents works without vision by default.

    Microsoft’s Playwright MCP server describes itself as using “Playwright’s accessibility tree, not pixel-based input”, with “no vision models needed”. Coordinate clicking on screenshots is an extra mode you have to switch on.

  2. 02 · benchmark

    On front-end issues, the images mattered, but visual tools didn’t reliably help.

    SWE-bench Multimodal has 617 tasks from 17 JavaScript libraries. Annotators judged the image essential for 83.5% of the tasks that had one. The best system resolved about 12%. Giving the agent browser and screenshot tools helped GPT-4o in one setup, made Claude 3.5 Sonnet worse, and nearly tripled the runs that hit the cost limit.

  3. 03 · leaderboard

    A text-only model did top a web-design leaderboard, but in June, and briefly.

    GLM-5.2, which takes text only, reached #1 on Design Arena’s single-turn HTML web-design board in June 2026 (Elo 1360). Design Arena put it down to good templates and libraries that “just work”, without vision. By October other models led the board. It shows that writing good front-end code doesn’t require eyes. It doesn’t show that checking it doesn’t.

In plain words

The model fixing the code can be blind, as long as something at the end can see. Most of the time that “something” is a browser reporting facts as text. A model that looks at pictures is needed only when the question is about how the page looks and there’s nothing to compare it with.

08

When the checker looks at pixels

There are two kinds of pixel check, and they fail in opposite ways. A screenshot diff is strict and literal: it flags changes that don’t matter. A vision model is loose and confident: it misses changes that do.

Screenshot against a known-good one

Playwright’s toHaveScreenshot() stores a reference image and fails when a new one differs by more than a threshold. Its own docs warn that rendering “can vary based on the host OS, version, settings, hardware, power source” and headless mode. In a study of 235 flaky UI tests, 45.1% were caused by waiting wrongly for something to finish (rendering, animation, network) and 18.7% by the environment, including layout differences between platforms. The fixes are known: generate and compare in the same pinned container, keep animations off (the default), hide the text cursor, mask dates and avatars, and allow a small tolerance.

A vision model as the judge

A vision model needs no reference, which is its whole appeal. The measured weakness lands right on this question’s bug. UI-Lens (CVPR 2026) tested ten models on 4,759 expert-labelled pages and found that for defects needing exact element boundaries, “performance is near random”: average F1 of 31.21% on container overlap and 20.36% on text overflow. Those are exactly the bugs rung 4 checks as numbers, with no misses.

Ranking pages is not finding the defect

ArtifactsBench uses a vision model to score generated front-ends from screenshots and reports 94.4% ranking consistency with WebDev Arena’s human votes. That is real, and it answers a different question: which of two models makes better pages on average, over many tasks. Verifying one fix asks whether this page has this defect. A judge can rank systems well and still miss the overlap on the page in front of it.

  1. 01 · narrow question

    Ask about one named defect, on a crop.

    “Is any text in this crop overlapping or cut off? Answer yes or no, then point to it.” A specific question about a zoomed region beats “does this look right?” on a downscaled full page.

  2. 02 · pairs

    Show before and after, or design and build.

    Comparing two images is an easier task than judging one cold, and it matches what you want to know: did the fix change the right thing and nothing else?

  3. 03 · no narrative

    Don’t pass the agent’s own claim.

    “I fixed the overlap” in the prompt pulls the verdict toward yes. Give the checker the screen and the question, never the editor’s summary. Guide 0019 has the numbers on that pull.

  4. 04 · make it point

    Require coordinates, then check them with the browser.

    If it says the label at (120, 340) is cut off, ask the browser what is at that point and whether it overflows. A claim you can verify with geometry is worth more than one you can’t.

  5. 05 · measured

    Know its miss rate on planted defects before it gates anything.

    Re-run each screen a few times too. A checker whose verdict changes between runs is a sampler, and one “looks fine” from it is weak evidence.

09

It already happened, in public

Every piece of this answer has been written down by someone who hit it: the labs building coding agents, the browser tool’s own maintainers, and the benchmarks.

  1. Anthropic · 2025

    Unit tests and curl said done. End to end, it wasn’t.

    In “Effective harnesses for long-running agents”, Claude would “make code changes, and even do testing with unit tests or curl commands against a development server, but would fail [to] recognize that the feature didn’t work end-to-end.” It “mostly did well at verifying features end-to-end once explicitly prompted to use browser automation tools and do all testing as a human user would.” And a blind spot in the checker became a blind spot in the code: Claude “can’t see browser-native alert modals through the Puppeteer MCP, and features relying on these modals tended to be buggier as a result.”

  2. Vendor guidance

    Both big coding agents’ docs say: give it a check that sees the result.

    Claude Code’s best practices: “Give Claude a check it can run: tests, a build, a screenshot to compare … Without a check it can run, ‘looks done’ is the only signal available.” OpenAI’s Codex front-end guide uses Playwright so “Codex can open the app in a real browser, compare the implementation to the screenshots you provided”, and says to compare against them, “not just whether the page builds.”

  3. Playwright · 2021

    “Visible” was never going to mean “not covered”.

    Issue #9923, “isVisible returns true when an element is completely overlapped by another element”, was closed as won’t-fix. The maintainer pointed to the actionability rules and suggested click({ trial: true }), which runs the hit-target check without clicking.

  4. SWT-bench · 2024

    Agents can write reproduction tests, and most of them don’t yet reproduce.

    On 276 Python issues, the best agent’s tests failed before the fix 46.4% of the time, but only 19.2% failed before and passed after the real fix. The rest failed for some other reason. Still, filtering an agent’s patches with its own tests roughly doubled precision, to 47.8%. Reproduction is worth doing, and worth checking.

  5. SWE-bench M · 2024

    Systems built for Python back-end issues struggled on visual JavaScript ones.

    The paper’s own summary: “top-performing SWE-bench systems struggle with SWE-bench M.” The best system resolved about 12%, well below what the same systems scored on the Python set at the time.

In plain words

The people who build these agents saw the same thing: the agent said “done” because its checks couldn’t see the problem. It got better when it was told to test like a person in a real browser, and features it couldn’t see stayed buggy.

10

Where this argument runs out

The ladder assumes the page is made of DOM elements, that a known-good picture exists or can be described, and that one browser stands in for every user. Each assumption breaks somewhere real.

Five places the ladder doesn’t reach

Canvas, WebGL, maps, video. The whole interface is one <canvas> element. Rungs 1 to 4 see a single box. You need pixels, or a test hook where the app reports its own scene state (“marker at lat, lng is selected”).

Design quality. “Does this look good?” has no reference and no rubric that fits in a test. A vision model can flag the obvious, but taste and brand fit still end at a person.

The user’s actual device. Headless Chromium on Linux is not Safari on an iPhone. WebKit in Playwright gets you close, emulation gets you sizes, but fonts, scrollbars, safe areas and touch behaviour can still differ. Real devices are a separate, slower check.

Accessibility beyond rules. Automated scanners catch rule violations (missing label, low contrast), not whether a screen-reader user can actually finish the task. A role-based test that completes the flow by keyboard goes further, and still isn’t a person.

The test the agent wrote. The same agent wrote the reproduction and the fix, so a weak test and a weak fix can agree. Red first and the revert run close most of that gap. Hidden acceptance tests written by someone else close the rest, which is how SWE-bench scores agents in the first place.

In plain words

Some screens aren’t made of elements a script can read, some questions are about taste, and some users are on devices you didn’t test. Know which of those your bug falls into, and say so instead of claiming the browser test covered it.

11

Five checks, and one is the gate

In the order an agent would run them for a single fix. Only one decides whether “verified” means anything. The others decide how far up the ladder to climb.

  1. Check 01the gate Red for the right reason, and red again on revert

    A browser test that reproduces the report fails on the current code, five runs out of five, and the failure message names the bug (“intercepts pointer events”, not “locator not found”). After the fix it passes five out of five. With the fix reverted and the test kept, it fails again.

    If any part of that is missing, nothing after it counts. A visual check on a fix whose bug was never reproduced is a guess with a screenshot attached.

    Tells youthe test can see this bug, and the change is what made it pass.

  2. Check 02a minute Name the bug class, and the rung that can see it

    Behaviour, interaction, geometry, appearance or design. Write it down before choosing the check. Most reports that say “looks broken” turn out to be interaction or geometry once someone reproduces them.

    Tells youwhether any pixels are needed at all.

  3. Check 03seconds per run Act like the user, at the user’s size

    Real clicks and key presses, no force, at the viewport and in the engine from the report, plus one other size and one other engine. Add geometry assertions for overlap and overflow where the bug is about layout.

    Tells youthe fix holds beyond the one screen the agent happened to test.

  4. Check 04once, then cheap Measure the pixel checker before trusting it

    For screenshot diffs: pin the browser, fonts and data, turn off animations, and check that the same page twice gives zero difference. For a vision model: plant known defects (an overlap, a clipped label, a wrong colour) in screens it hasn’t seen, and count how often it says “looks fine” anyway.

    Tells youthe miss rate, which decides whether this checker can stop a bad fix or only start a conversation.

  5. Check 05a minute Nothing else broke, and the test stays

    The existing browser tests still pass (pass-to-pass), the new reproduction is committed next to them, and if a screenshot was the check, the new known-good image goes in with a person’s approval.

    Tells youthis bug can’t come back without a red build.

Twelve follow-ups

The likely next questions, with answers you can say in under a minute.

F1“Why isn’t ‘assert it’s visible’ enough?”

Because in Playwright “visible” means the element has a box and isn’t hidden by its own CSS. A button under a modal passes that. What catches it is a real click, which checks the element is the one that would receive the event, or elementFromPoint at its centre. Assert the action, not the state.

F2“The agent writes the test and the fix. Can’t it just write a test that passes?”

That’s why red comes first and the failure has to match the report: a test that passes on broken code is rejected before any edit. The revert run catches a test that passes regardless of the fix. For high-stakes changes, a hidden acceptance test written by someone else is the final word.

F3“Screenshot tests are flaky. Why would I trust them?”

They’re flaky when the environment moves: fonts, anti-aliasing, animations, live data, a different OS. Run them in a pinned container, turn off animations, mask dates and avatars, and set a small pixel threshold. Then prove it: the same page twice must diff to zero. And use them for regressions against a known-good image, not for judging a brand-new screen.

F4“How does a text-only model ‘see’ a page?”

Through what the browser reports as text: the accessibility tree (roles, names, states), console errors, failed network requests, the DOM, and numbers from layout (boxes, computed styles, what elementFromPoint returns). That covers behaviour, interaction and geometry, which is most front-end bugs.

F5“When does the coding model itself need vision?”

When the input is an image: the bug report is a screenshot, the task is “build this mock”, or the interface is a canvas. Then the model that understands the task has to read pixels. When the task is in words and only the check is visual, a vision model can sit at the end as the checker instead.

F6“How would you know whether the vision checker is any good?”

Build a small set of screens with defects you planted on purpose, plus clean ones. Measure misses (said fine, wasn’t) and false alarms separately, and run each screen a few times to see whether the verdict changes. The miss rate decides whether it can block a merge or only add a comment. Guide 0019 covers why one overall agreement number hides exactly this.

F7“Isn’t this too slow for an agent loop?”

Run only the reproduction during the loop: one test, one browser, a few seconds. Run the rest at the end: other sizes, other engines, the existing suite, any screenshot or vision checks. Unit tests stay in the loop too, for logic, because they are fast and they still catch what they can see.

F8“The bug only happens sometimes. Now what?”

Make the timing part of the test: slow the network, throttle the CPU, wait on the condition rather than a fixed delay, and repeat the run until it reproduces. Record a trace (Playwright’s trace viewer stores each step’s DOM and a screenshot) so the agent can read what was on screen at the moment it failed.

F9“Should the agent read screenshots while it debugs, even for behaviour bugs?”

It can help a model that is good at it, but it isn’t free. Images cost many more tokens than an accessibility snapshot, and a long run full of screenshots fills the context with near-duplicates, the problem guide 0016 is about. Default to text, and take a screenshot when the next decision depends on how the page looks.

F10“Where does accessibility fit?”

It comes free with doing this well. Finding elements by role and name means the test fails if a screen reader couldn’t find them either. Add an automated scan for rule violations, and know its limit: it finds missing labels and low contrast, not whether the flow is usable without a mouse.

F11“What does the agent hand the reviewer?”

The diff, the reproduction test, its red and green runs with the failure message, the revert result, the browsers and sizes covered, and a before-and-after screenshot pair for a person to glance at. The screenshot is for the human. The verdict comes from the test.

F12“How do you know this is working across hundreds of fixes?”

Track the share of UI fixes that came with a fail-to-pass reproduction, the share whose failure matched the report, the vision checker’s miss rate on planted defects, and the escape rate: UI bugs reopened after the agent marked them verified. Escapes, read by hand, show which rung was missing.

Glossary

DOM
The tree of elements the browser builds from HTML, which scripts read and change.
layout · reflow
The stage where every element gets a size and a position.
paint · composite
Drawing each element’s pixels, then stacking the layers in z-order into the final picture.
hit test
Working out which element is on top at a point, which is the one that gets a click there.
z-index · stacking context
The CSS rules that decide which element sits on top when two overlap.
jsdom
A JavaScript copy of the DOM used by Jest and Vitest. Runs scripts and events; no layout, no paint.
Playwright
A library that drives real Chromium, Firefox and WebKit browsers for testing.
locator
Playwright’s way of finding an element, ideally by role and name as a user would describe it.
actionability
The checks Playwright makes before acting: visible, stable, enabled, and the hit target.
accessibility tree
The browser’s text summary of controls (role, name, state) for screen readers, and for text-only agents.
fail-to-pass · pass-to-pass
Tests that must fail before the fix and pass after it; tests that must pass both before and after.
reproduction
A test that makes the reported bug happen on demand, for the reason in the report.
oracle
Whatever decides whether an output is correct. It can only judge what it can observe.
visual regression test
A screenshot compared with a stored known-good one, failing above a pixel threshold.
vision-language model
A model that takes images and text. Here, used as a checker that looks at screenshots.
flaky test
A test that passes and fails on the same code, usually from timing or environment.
force click
click({ force: true }): skips the actionability checks. In a verification test, it hides the bug.
revert run
This guide’s check that the test fails again with the fix undone, so it really tests the fix.
