Question 19 · Google · senior AI engineer

Who Reads the Failing Test

A fixed pipeline beating your agent is not a verdict on loops. It is a reading of how your model was trained. A loop adds two things: more steps that can go wrong, and the chance to read what went wrong and try something different. The second one is a skill the model has to have been taught. If it wasn’t, the loop only adds steps.

The question, as asked

“A fixed localize → patch pipeline, with no tool loop and no verification step, beats your full coding agent on SWE-bench. Does that mean agent loops aren’t worth it?”

00

What they are actually testing

The question is set up as an architecture debate: pipelines against agents. The interviewer wants to hear you refuse that framing. The result is a fact about this model, in this harness, at this point in its training, and it tells you where to look next.

Probe 1

Can you separate architecture from training?

The same two designs have swapped places in public. In 2024 a fixed pipeline (Agentless) beat most open agents on SWE-bench. Once models were trained on agent trajectories, simple loops pulled far ahead. The designs didn’t change. The models did.

Probe 2

Can you say exactly what a loop adds?

Two things that pull in opposite directions. More steps, each one a fresh chance to send a broken tool call, lose the thread or wander. And feedback, which only helps if the model can read a failing test and change course. A senior answer names both and says which one decides the result.

Probe 3

Do you diagnose before you decide?

“Read the trajectories” is the expected first move. The better answer says what you are sorting them into: wrong file, edit that didn’t apply, test output ignored, stopped too early or never stopped. Each bucket has a different owner and a different fix.

Probe 4

Do you know the fix, and keep the baseline?

Harness bugs get fixed in the harness. Missing loop skills get fixed in training: RL in real, executable repositories. And the pipeline stays, as the floor the agent has to beat at the same cost, or the extra steps are just latency and tokens.

Where this sits next to the other guides

Q6 (0007) is the mirror image: there the agent beat the fixed workflow, and the question was what the workflow had been guaranteeing that the benchmark couldn’t see. Here the workflow wins, and the question is what the agent is missing.

Q17 (0018) owns dialect: a model trained in one harness writes tool calls and edits that another harness can’t read, and the adapter test proves it. The newsletter’s “check the edit format” point is that guide’s ground. This one uses it as one bucket out of four and points there for the detail.

Q12 (0013) owns the idea that a score is written jointly by model, harness and environment. Q1 (0001) owns what a loop costs in latency. Q9 (0010) owns role pipelines (planner, coder, tester). New here: what a loop adds and loses per step, the difference between a test read by a script and a test read by the model, the revise-or-restart test, the four loop skills as things you can count in a log, and the pipeline as a standing floor.

The answer, at three lengths

Say the thirty-second version out loud before reading on. Everything after it supports one of its sentences.

30 seconds

No. It tells me this model gets less out of a loop than the loop costs it. A loop adds steps, and each step is another chance to break something. It also adds feedback, but feedback only helps if the model was trained to read a failing test and change course. 2 minutes
  1. Split what a loop adds. More steps, which cost reliability. Feedback, which can buy it back. The pipeline wins whenever the first outweighs the second.
  2. The pipeline reads tests too. Agentless runs tests and uses them to pick one patch out of several. The difference is who reads the result: a script choosing among drafts, or the model revising its own. Choosing needs no training. Revising does.

One line

“A loop is only worth it if the model learned to read the failing test. Otherwise it is the same guess made more times, with more ways to crash.”

The two tempting answers “Agents are overhyped, the simple pipeline wins, ship it.” Or: “SWE-bench is noisy, the agent is better in real life.”

Both treat the result as a verdict on a design. The first throws away the one thing that can improve with training. The second waves away a measurement it could have learned from.

Neither asks why the agent lost, which is the only question with an engineering answer.

The answer that gets the job It measures how well this model fits this loop, not how good loops can be. I’d find out which loop skill is missing before I touch the architecture.

Name what a loop adds and costs, show that the pipeline’s advantage is fewer chances to fail, diagnose from trajectories, fix the harness or the training depending on the bucket, and keep the pipeline as the floor.

02

The fundamentals, in plain words first

Seven ideas carry the whole answer. Each starts with the plain version. The precise version follows, because the interviewer will use the precise words.

A pipeline (a fixed workflow)

Code decides the steps. The model fills in each step and never chooses what happens next.

Agentless, the best-known example, does it like this: ask the model which files probably need editing, then which classes and functions inside them, then which exact lines. Then ask it for a patch, several times, and use tests to pick one. Every run takes the same path. The model is called a fixed number of times and never sees the result of its own work.

An agent loop

The model decides the next step, sees what happened, and decides again, until it chooses to stop.

The model gets tools: a shell, a file viewer, an editor. Each turn it writes a tool call, the harness runs it and pastes the result (the observation) back in. The model can open files, grep, edit, run the tests, read a stack trace and try again. It also decides when it is done. A run is a trajectory: every call and every observation, in order.

SWE-bench, and what “beats” means

Real GitHub issues from real Python projects. A fix counts only if hidden tests pass.

The full set is 2,294 issues from 12 repositories. Lite is a 300-issue subset. Verified is 500 issues that people checked were solvable and fairly tested. The system sees the issue text and the repository, writes a patch, and the patch is scored by tests it never saw. The headline number is the resolve rate: the share of issues fixed, usually from one attempt per issue (pass@1).

Localisation

Finding where the change goes. Both designs have to do it, and both can get it wrong.

A pipeline does it in fixed rounds, narrowing from files to functions to lines. An agent does it by searching and reading. A wrong file is fatal either way, which is why “wrong file” is the first bucket when you read failures: it is a failure the loop didn’t cause, so it doesn’t count against the loop.

An edit format

The exact way the model writes down a change: whole file, search-and-replace block, unified diff, or a tool call.

The same fix can be written many ways, and a model is much better at the ones it saw in training. A wrong line number in a diff, or a search block that doesn’t match the file exactly, and the edit simply doesn’t apply. Guide 0018 covers how a harness’s format gets baked into a model. Here it is one of four ways a loop can fail.

What the model was trained on

A model is good at what it practised. Writing a patch in one go and working through a loop are different practice.

Pretraining on code is full of finished changes: commits, diffs, fixed files. That teaches “issue in, patch out”, which is exactly the pipeline’s shape. It contains almost no examples of a model reading its own failing test and trying something else. Agentic post-training supplies them: run the model as an agent inside a real repository, run the hidden tests at the end, and reward the trajectories that passed (reinforcement learning), or fine-tune on trajectories that worked.

Compounding

Small chances of failure, repeated, add up to a large one.

If each step independently has a small chance ε of breaking the run, the chance of getting through T steps unbroken is (1 − ε)T. At 2% per step, 40 steps leaves you 45%. At 0.3%, it leaves 89%. Nothing about any single step looks bad. The loop’s length does the damage.

Guide 0018 covers a different compounding: imitation errors that push a model into states it never trained on. This page only needs the plain version.

03

Every step is a chance to fail

The newsletter’s key sentence is “the pipeline simply gives the model fewer chances”. Here is that sentence as arithmetic. Two dials decide whether a loop pays, and neither one is about architecture.

a toy model of one run (illustrative; the shape matters, not the exact numbers) s = chance a first attempt at the fix is right same model, so the same for both designs ε = chance any one step breaks the run bad call, edit that won't apply, lost thread T = steps in an agent run 40 here ρ = chance the next attempt is right, after seeing a failing test k = attempts the agent gets 4 here pipeline ≈ s # few steps, nothing to slip on loop ≈ (1 − ε)T × [ 1 − (1 − s)(1 − ρ)k−1 ] └ survives the steps ┘ └ gets it right within k tries ┘

The first bracket is what a loop costs: every step is a small tax, and forty small taxes compound. The second bracket is what a loop buys: more tries, each informed by the last failure. A pipeline pays almost none of the tax and buys none of the tries. Whether the loop wins depends on two numbers the model brings with it: how often it fumbles a step (ε), and how much a failing test actually helps its next try (ρ).

How to read it. Fixing only one dial gets you a few points past the floor. Fixing both gets you far past it. Agentic training moves both at once, which is why the reversal in public was so sharp. All numbers on this figure are made up to show the shape. The real ones come from your own trajectories, section 07.

Two things in the figure are worth saying out loud in the interview.

The break-even moves. With clumsy tool use, the loop needs the model to fix a failure 22% of the time just to tie the pipeline. With fluent tool use, 2% is enough. So the same model can lose to a pipeline in one harness and beat it in another, purely because the edit format or the tool output changed ε. That is the harness half of the answer, and it is cheap to fix.

Feedback can be worth almost nothing. At ρ = 5% the model sees the failing test and mostly writes the same fix again. Extra attempts then add steps without adding chances, and the loop is strictly worse. That is the training half of the answer, and it is not cheap to fix.

In plain words

A pipeline is one shot at the target from close range. A loop is a walk up to the target, a shot, a look at where it landed, and another shot. The walk has places to trip. The look only helps if you know how to adjust your aim. A shooter who trips often and never adjusts should stay where they are and take the one shot.

04

Who reads the failing test

The question says the pipeline has “no verification step”. The real Agentless does run tests. What it never does is show the results to the model. That difference, more than the loop itself, is what the result is about.

Here is what Agentless (version 2) actually does with each issue. It localises in three rounds, from files down to edit locations. It samples 40 candidate patches in search-and-replace format. It has the model write a reproduction test. Then, in the paper’s words, it “runs the set of regression tests on all the generated patches … keeps the patches with the lowest number of regression failures … runs the selected reproduction test and only keeps patches that output Issue resolved”, and takes a majority vote over what is left.

So tests are read, many times over. But they are read by a script, to pick one patch out of forty. The model wrote forty independent drafts and never saw a single test result. An agent does the opposite. It writes one draft, the model reads the failure, and the model writes the next draft.

Three ways to use a failing test

Each glyph is one attempt, read left to right like a pytest progress line. The amber ring marks the only thing a loop adds over a pipeline: an attempt that is different because of what the last one showed.

The one comparison that decides it

A sieve and a loop are both ways of getting more than one try. The sieve’s tries are independent: each draft has the model’s one-shot chance s of being right, and the script just has to recognise the right one. The loop’s tries are linked: each one has the last failure in its context. That can help a lot, if the model knows what to do with a stack trace. It can also hurt, because the wrong patch is right there and the model anchors on it.

revision beats a fresh draw only if ρ > s ρ = chance the next attempt is right, having read the failure s = chance a brand-new attempt is right, from the issue alone ρ < s the loop is a worse sieve: correlated tries, more steps # the 2024 picture ρ > s the loop does something no sieve can # what agentic training buys

That gives you a sharp version of the newsletter’s thesis: a loop is only an asset when revising beats restarting. Section 11 turns this into the gate: fork real runs at their first failing test and measure both.

It also explains why feedback isn’t automatically worth much. Olausson and colleagues measured self-repair on code at equal compute and found the gains “often modest, vary a lot between subsets of the data, and are sometimes not present at all”. Feedback quality was the bottleneck: when a person wrote the explanation of the bug instead of the model, GPT-4’s repair rate went from 33.3% to 52.6%. On SWE-bench, the hidden tests are hidden. The only feedback an agent gets is from tests and scripts it wrote itself, so writing a test that actually reproduces the bug is part of the skill.

Independent draws, on the other hand, are cheap and effective whenever something can recognise the right answer. In Large Language Monkeys, one open model’s SWE-bench Lite coverage went from 15.9% with one sample to 56% with 250. The catch is that 56% counts an issue solved if any sample passes the real tests, an oracle no deployed system has. Agentless’s generated tests and majority vote are a practical, imperfect stand-in for that oracle.

In plain words

There are two ways to use a failed exam. You can sit it again with a fresh head and hope for different questions to go well. Or you can read the marked paper, see what you got wrong, and fix exactly that. The second is better only if you can read the marking. A student who can’t read it does better just sitting the exam again.

07

Read the trajectories before you decide

The newsletter’s first instruction is the right one. Here is what reading them actually involves, and what the published failure studies say you will find.

The same failure study (Liu et al.) gives each design a clear fingerprint. In Agentless, 51.3% of failed issues contain a localisation error: the pipeline’s weak point is finding the code, and it never gets a second look. In the two agents, about half of failed issues contain an error in the iteration and validation phase (49.1% and 51.7%), a phase that Agentless doesn’t have at all. Most successful runs finish within about 25 rounds, and failed issues take on average 3.5 times more steps. Roughly 65% of root causes are flawed reasoning rather than missing knowledge or the environment.

Read that as a forecast for your own trajectories. If your agent is losing to a pipeline, expect the extra failures to live in the part of the run the pipeline doesn’t have: the edit-test-edit cycle. That is exactly where the four loop skills are used.

A reading procedure

  1. 01 · sample

    Take a hundred failed runs, not the worst ten.

    Stratify by repository and by run length. Long failures and short failures fail differently, and the short ones are often harness bugs.

  2. 02 · first fatal event

    Tag each run with the first thing that made success impossible.

    Not the last error message. A run that edited the wrong file at step 6 and then flailed for 40 steps is a localisation failure, not a stopping failure.

  3. 03 · count the cheap signals

    Add counters for what can be detected mechanically.

    Parse failures, edits that didn’t apply, identical consecutive edits, test runs per attempt, observation length per step, steps used against the limit. These give you ε and the bucket shares on every run from now on, not just the hundred you read.

  4. 04 · gradient or scatter

    Look at how each bucket is spread.

    If one bucket is mostly one tool, one error string or one repository, it is a harness problem. If it is spread thinly over everything, it is the model.

  5. 05 · fork the failures

    At each run’s first failing test, branch: continue, or restart fresh.

    This is check 02 and the only step that measures feedback use directly. Everything before it says where runs fail. This says whether the loop could ever pay.

Guide 0013 has a different four-way split, for a score that changed between runs (environment, harness, patch format, model). This one is for a loop that lost to a simpler design, so its buckets are loop skills.

08

Fix the model, not the loop

Once the cheap harness fixes are in, what is left is a model that never practised working in a loop. Deleting the loop hides that. Training fixes it.

Agentic post-training in one paragraph: put the model in a real repository inside a container, give it the same tools it will have in production, let it work an issue to the end, run the hidden tests, and reward the run if they pass. Repeat over thousands of issues. Every step of a winning run gets credit, including reading the stack trace and the second attempt that differed from the first. Patch-only training never shows the model those steps.

If you can’t train the model, because it is a vendor API, your options shrink to three: fix the harness side of ε, match the vendor’s own tool formats, and, if revise-or-restart says the model doesn’t use feedback, make the loop restart instead of revise. That last one quietly turns your agent back into a sieve, which is the honest design for that model.

In plain words

If a new driver keeps stalling a manual car, you can give them an automatic (fix the harness) or teach them the clutch (fix the training). Taking the car away and making them walk (delete the loop) does get them there without stalling, but it doesn’t make them a better driver, and it caps how far they can go.

09

Where this argument runs out

Five honest limits. Bring one up yourself before the interviewer does.

Pipelines are not just a 2024 relic

Kimi-Dev’s pipeline beat its own agent by 12 points in late 2025. If your model, budget and task are all pipeline-shaped, the pipeline can be the right product. Kimi-Dev’s authors also argue the two aren’t rivals: pipeline-style training builds “skill priors, including localization, code edit, and self-reflection” that make later agent training cheaper. A pipeline can be the curriculum, not just the competitor.

Sometimes architecture barely matters

Claude 3.5 Sonnet scored 49.0 to 53.0% across three very different designs. When a model is reasonably fit for both shapes, arguing about the design is arguing about four points. The bigger win can be combining them, since they solve different issues.

Feedback is only as good as the test that produced it

On SWE-bench the agent never sees the hidden tests. Its feedback comes from scripts it wrote itself, and a bad reproduction script gives confident wrong feedback. Low ρ can mean the model can’t read feedback, or that the feedback was poor. Check the agent’s own tests before blaming its reading.

The benchmark has its own error

Wang, Pradel and Liu found 7.8% of “solved” patches fail the project’s full test suite, inflating reported scores by 6.2 points. Contamination favours one-shot recall of a known fix, which is the pipeline’s shape. OpenAI has reportedly stopped reporting Verified for those reasons (I couldn’t open the post itself). Confirm a few-point gap on fresh issues before acting on it.

The two-dial model is mine

Section 03 is a teaching model, not a measured law. Real step failures aren’t independent, and attempts aren’t fixed in number. No paper I found measures step count against compounding failure for coding agents directly. The nearest are the 3.5× step ratio and the 53% of failures that hit the step limit. Use the model to explain the shape. Use your trajectories for the numbers.

10

Keep the pipeline, as the floor

The newsletter’s last line is the one most people skip. Even when the agent wins, the pipeline has three jobs left, and deleting it throws all three away.

  1. 01 · baseline

    The agent has to beat it at the same cost.

    A pipeline that draws four patches and an agent that runs forty steps are not the same spend. Compare them at equal dollars or equal model calls. If the agent only wins when it spends five times more, that is a pricing decision, not a capability result.

  2. 02 · fallback

    It is a known-good path when the agent fails loudly.

    A run that breaks early (no edit applied, budget gone, nothing changed) can be handed to the pipeline instead of returned empty. Run the cheap path first on easy issues and the loop on the rest, and you get most of both.

  3. 03 · re-measured

    The floor moves with every model.

    A new model raises the pipeline’s score too, because one-shot patch writing improves as well. The margin between agent and pipeline is the number to track per release, not the agent’s score alone. A shrinking margin means loop skills are falling behind patch skills.

The thing to carry forward

One record per model and harness pair, filled from trajectories rather than from a leaderboard. The values are an example. The two null fields are the ones almost nobody measures, and they are the ones that answer the question.

In plain words

Keep the simple version running next to the clever one. If the clever one can’t beat it at the same price, you have learned something about the clever one. If it can, the simple version is still your safety net and your measuring stick.

11

Five checks, and one is the gate

In the order you would run them. Only one decides whether the loop can ever pay. The others tell you where to spend the effort.

  1. Check 01a day Bucket a hundred failed runs

    Read them, don’t just count them. Tag each with its first fatal event: wrong file, edit that didn’t apply, test output ignored, stopped without testing, ran out of budget. Counters help (parse failures, apply failures, repeated identical edits), but the reading is where you find the bucket nobody predicted.

    Tells youwhich of the four loop skills is missing, and how much of the gap is the loop at all. Wrong-file failures belong to localisation, which the pipeline has too.

  2. Check 02the gate Revise or restart

    Take every run that reached a failing test. Fork it at that moment. One branch continues with the failure in context, as the agent would. The other starts a fresh attempt from the issue, with the same remaining budget. Compare how often each ends up passing.

    If continuing doesn’t beat restarting, the model is not using the feedback. The loop is a slow, correlated way of drawing more samples, and a pipeline that draws independent samples and picks with tests will beat it. No harness change fixes that. It is a training gap.

    Tells youρ against s, the one comparison that decides whether a loop can ever beat a sieve.

  3. Check 03an afternoon Transplant the localisation

    Give the agent the pipeline’s file and line predictions as a starting hint, and re-run. If the agent catches up, the pipeline’s edge was in finding the code, and the agent’s search tools or context handling are the problem, not its repair skill.

    Tells youwhether the gap is in search or in repair.

  4. Check 04an afternoon Swap the edit format

    Re-run with the edit format the model was trained on (its vendor’s patch tool, or plain search-and-replace) and with tool output truncated and line-numbered. Watch the per-step slip rate. This is guide 0018’s adapter test, aimed at one number.

    Tells youhow much of ε is the harness. That part is cheap to remove.

  5. Check 05a day Price-match the floor

    Give the pipeline the agent’s budget: more drafts, the same test-based selection. Report both at equal cost, with intervals. On a fresh set of issues too, not only the public benchmark, since a memorised fix helps the one-shot design more than the loop.

    Tells youthe honest margin, which is the number you report.

12

Twelve follow-ups

The likely next questions, with answers you can say in under a minute.

F1“Isn’t this just SWE-bench being noisy or contaminated?”

Noise is a reason to put intervals on both numbers, not a reason to dismiss the gap. Contamination is more interesting: if a model has seen the fix, writing it in one shot is exactly what a pipeline asks for, so leakage can favour the pipeline. That is a reason to re-run on fresh issues or your own repositories, not a reason to trust the agent.

F2“So when would you actually ship the pipeline?”

When the tasks are narrow and alike, when the latency or cost budget is tight, when every run must follow an auditable path, or when I can’t retrain the model and the harness fixes don’t close the gap. Often the answer is both: the pipeline first on easy issues, the agent on the rest.

F3“The model is a vendor API. You can’t retrain it. Now what?”

Fix the harness side of ε: use the edit format that vendor trained on, truncate and line-number tool output, lint edits before applying them. Then check revise-or-restart. If the model doesn’t use feedback, make the loop restart instead of revise: fresh attempts, chosen by tests. That turns the agent into a sieve, which is what the pipeline was already doing well. Or try a different model.

F4“How do you tell a harness bug from a model gap in a trajectory?”

Harness bugs repeat. The same tool, the same format error, the same truncated output, across many unrelated issues. Model gaps scatter across tasks and steps. If one bucket is dominated by one tool or one error string, look at the harness first.

F5“What does agentic RL actually teach that fine-tuning on patches doesn’t?”

It rewards whole trajectories by whether the hidden tests pass at the end, so everything in a winning run gets credit: the search that found the file, reading the stack trace, the second edit that differed from the first, and stopping once the tests pass. Fine-tuning on patches only ever shows the last step.

F6“Why not just add a retry to the pipeline when tests fail?”

You can, and it is worth being exact about what kind. “If the tests fail, generate again” is selection, and it works with any model. “Show the model the failure and ask again” is revision, and it only works if the model uses feedback. Check 02 tells you which one to build.

F7“Isn’t more test-time compute always better?”

Only if the extra attempts are different from each other and you can tell which one is right. Independent samples are diverse by construction. Retries inside one context are correlated with the first mistake, because the wrong patch is sitting right there. Extra compute on correlated attempts buys much less.

F8“What per-step slip rate is acceptable?”

Work backwards from run length. For your median run length T, pick ε so that (1 − ε)T stays near 0.9. At 40 steps that is about a quarter of a percent per step. Then measure the real ε per tool, because one bad tool usually accounts for most of it.

F9“How do you stop the agent wandering?”

In the harness, a step budget and a stall detector that notices the same state twice. Guide 0001 has the caveat: a cap is a budget, not a skill. The skill of stopping once the tests pass comes from training, where runs that finish cleanly are the ones that get rewarded.

F10“Does this apply outside coding?”

Anywhere a loop’s feedback has to be read by the model. Coding is the easy case because tests give a clear signal. In computer use the feedback is a screenshot, which is harder to read and easier to misread. Guide 0019 is what happens when the only signal is another model’s opinion.

F11“The agent is now five points ahead. Delete the pipeline?”

No. Five points at what cost? Is the margin still there on fresh issues? And will it still be there after the next model, which also improves the pipeline? Keep it as the floor and the fallback, and re-measure the margin every release.

F12“What would you report to leadership?”

Agent and pipeline at matched cost with intervals, on a fresh set. The failure buckets and how they moved. Revise-versus-restart. Per-step slip rate by tool. Then one sentence: whether the gap is in the harness (we fix it this sprint) or in the model (it needs training, or a different model).

Glossary

agent loop
The model chooses a tool call, sees the result, and chooses again until it decides to stop.
pipeline / workflow
Code fixes the sequence of steps. The model fills each step in but never chooses the next one.
Agentless
A 2024 pipeline for fixing GitHub issues: localise (files, then functions, then lines), sample several patches, and pick one using tests. No tool loop.
harness / scaffold
Everything around the model: tools, prompt, how calls are parsed, how results are shown, when the run stops.
trajectory
The full record of one agent run: every tool call and every observation, in order.
observation
What the harness pastes back after a tool call: file contents, command output, a test failure.
localisation
Finding where in the codebase the change belongs.
edit format
How a change is written down: whole file, search-and-replace block, unified diff, or a string-replace tool call.
resolve rate · pass@1
Share of issues fixed (hidden tests pass), from one attempt per issue.
pass@k · coverage
Share of issues where at least one of k attempts is right. Only useful in practice if something can pick the right one.
selection
Using feedback to choose among attempts. A script can do it. Needs no model skill.
revision
Using feedback to write a better next attempt. The model has to do it, and it has to have learned how.
ε · per-step slip rate
Chance that a single step breaks the run: a call that won’t parse, an edit that won’t apply.
ρ · revision rate
Chance that the attempt after a failing test is right. Compare it with s, the chance a fresh attempt is right.
revise or restart
This guide’s gate: fork failed runs at the first failing test and compare continuing against starting over.
agentic post-training
Training a model on agent runs, usually RL in executable repositories with hidden tests as the reward.
executable environment
A repository in a container where code can be run and tests can be executed, so a run can be scored automatically.
floor
The pipeline’s score at the agent’s budget. The agent has to beat it to justify its extra steps.
