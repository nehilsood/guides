Question 7 · OpenAI · senior AI engineer

The Closed Loop

Your PM wants the agent to write its own skills from the task description. Benchmarks say that makes it worse than having no skills at all — not merely no better. This is why the sign is negative, and what a skill has to be built from instead.

The question, as asked

“Your PM wants to save engineering time: ‘Just have the agent write its own skills from the task description.’ Benchmarks show this can make the agent worse. Why? And what should a skill actually be built from?”

00

What they are actually testing

The question has a tell in it. It does not ask “is this a good idea” — it hands you the empirical result and asks you to explain the sign. That is a mechanism question wearing a product question’s clothes, and there are four separate things being probed underneath it.

P1

Do you know what a skill does at inference time?

Not what it is on disk. A skill is not knowledge the model gains; it is a document the model is conditioned on. If you cannot say what conditioning does to an output distribution, you cannot explain why a bad one hurts.

P2

Can you explain worse, not just useless?

“It adds nothing” predicts zero. The benchmarks report a negative. Anyone can argue for zero; the hire is the person who can name the term that makes it go below zero.

P3

Do you have a source hierarchy, or just a preference?

“Use real runs” is the headline. The follow-up is always: which runs, verified by what, and what do you do when the verifier is itself a model?

P4

Will you kill your own artefact?

The last question in this family is always about measurement. A skill you cannot ablate is a skill you are keeping on faith, and a senior engineer volunteers the experiment before being asked for it.

Don’t say The model isn’t smart enough yet. Use a stronger model and a better prompt.

This locates the defect in capability. The defect is in the input. A stronger model writing a skill from the same task description produces a more fluent, more confident, more specific document containing exactly as much new information: none. Scaling the writer does not add a measurement.

Worse, it predicts the wrong thing. If capability were the problem, the gap would close as models improve. It does not, because the missing ingredient is contact with the environment, and no amount of parameters supplies that.

The move that scores Because the skill is a function of the context the model already had — so it adds no information, but it does add authority.

That single sentence answers “why worse” rather than “why useless”. It carries a claim about the source (a closed loop) and a claim about the effect (the model stops checking), and both are testable.

Then you get to the second half of the question, which is the half most candidates never reach: a skill is compressed experience, and experience has a provenance you can name.

Not the same question as “too many skills”

There is a neighbouring failure and interviewers sometimes probe whether you can tell them apart. Too many skills is a selection problem: the descriptions become confusable, retrieval picks the wrong one, and adding a good skill can still lower the score. This question is a provenance problem: one skill, correctly retrieved, correctly applied, and still harmful — because of where its contents came from.

They compound, and you should say so. But if you answer a provenance question with a selection argument, you have answered the wrong question confidently, which is the exact failure the page is about.

01

The answer, at three lengths

Have all three ready. The interviewer decides which one they wanted by how long they let you run.

Ten seconds

Because a skill written from the task description is a function of the context the model already had. It adds no information — but it does add authority, so the agent stops checking. A skill has to be compressed experience, not compressed intent.

Forty seconds

Whatever the model writes from a task description is sampled from its own prior. Nothing in that document was measured against the environment, so it carries zero information the agent did not already have in context. That predicts no gain. The reason it goes negative is that the document is not inert: the next agent reads SKILL.md as procedure, follows it literally, and stops exploring. So you have removed the agent’s uncertainty without removing its error — and the uncertainty was the part that made it read the page and discover that the search box ORs your terms.

On top of that you pay a permanent context tax for a conditional benefit: the description sits in the system prompt on every request, while the lift only arrives on the fraction of tasks where the skill is retrieved and happens to be right.

The fix is a source rule. Build skills from verified trajectories, gate on an executable outcome, distil failures into strategies rather than storing traces, and prove each one with an A/B against no-skill. If it cannot be ablated, it is a hypothesis, not a skill.

Two minutes

Start with what a skill is at runtime: a conditioning document. It does not give the model facts, it narrows the distribution over what the model does next. Narrowing helps only if the thing you condition on is correlated with success and not already implied by the context.

Now write down the generating process. “Write a skill from the task description” is S = f(T), where f is the model and T is already in context. The environment never appears on the right-hand side. So S is conditionally independent of the world given T: no measurement entered the document at any point. That is the closed loop, and it is why a better model does not fix it.

Three terms then decide the sign. Information gain: zero by construction. Context cost: strictly positive and paid on every request, because the description lives in the system prompt whether or not the skill fires. Confident-error cost: positive, because the agent treats the file as authoritative and follows it including the steps nobody asked for. Two positives against a zero. The benchmark result was not bad luck; it was the only sign those terms could produce — and SkillsBench measures it at −8.1 to −11.5 points against a no-skills baseline, while curated skills on the same tasks are worth +16.6.

Which tells you the axis is not human-versus-model. Curated skills work because a human is writing down things they learned by doing the task. The axis is experience versus intent. So build skills from real runs: induce recurring sub-routines from trajectories, admit only the ones an executed test or a judge confirms succeeded, turn failures into short strategies rather than stored traces, and feed back outcome signals like which review comments humans actually accepted. Then gate: verified, recurrent, and ablated — and keep a human editing for intent, because the agent proposes from evidence and the human is the one who knows what the team meant.

And the one thing I would change about the format itself: SKILL.md has no provenance field. A guess and a measurement get filed in the same drawer and are read with the same authority. Every skill we ship carries the run count, the eval it passed and the lift it earned, and anything without those is labelled a hypothesis.

02

Fundamentals: what a skill is at inference time

Everything downstream depends on getting this right, and most people carry a wrong model of it. A skill is not a plugin, not a memory, and not a capability. It is a block of text that gets concatenated into the prompt.

Which means a skill does exactly one thing: it narrows the distribution over the agent’s next actions. It cannot add an ability the model lacks. It cannot look anything up. It changes which of the behaviours the model could already produce it now produces more often.

Two costs, and only one of them is optional

The mechanics matter here because they explain why an unhelpful skill is not free. In the common file format, a skill has a short description in frontmatter and a longer body:

description -> loaded into the system prompt on EVERY request, whether used or not ~50-100 tokens, and it is what retrieval matches against body -> loaded only when the skill is actually invoked median skill documentation is about 1,196 tokens (SkillsBench) and once loaded it STAYS in context for the rest of the run

Read those two lines as an economics problem, because that is what they are. The description is a fixed cost on the whole request volume. The body is a variable cost on the invocation volume, and it is not a one-turn cost — an invoked skill sits in the transcript for every subsequent turn of that run.

The benefit, meanwhile, is conditional twice over: the skill has to be retrieved, and it has to be right. Nothing about the format makes the benefit as reliable as the cost.

In plain words

When the agent writes a skill from the task description, every word comes from what the model already believed, because its only input is text it can already see. Nothing was tried against the real system, so the skill holds no new facts. A smarter model only writes the same guess more smoothly. The fix is to let the real system answer first: run the task, check the result, then write down what happened.

03

The closed loop: why the source is the whole defect

Write down the generating process for each kind of skill and the argument finishes itself. One of them touches the environment. The other one never leaves the model.

“Have the agent write its own skills from the task description” is this:

S = f(T) where f is the model, T is the task description T is already in the agent's context when it runs the environment does not appear on the right-hand side

Because the environment is absent from that expression, S is conditionally independent of the world given T. Every claim in the document is a sample from the model’s prior, dressed as a finding. And since T is already in context, conditioning on S tells the agent nothing it was not already conditioned on.

Written a priori

The loop that never leaves the model

  1. task description
  2. model writes SKILL.md
  3. model reads SKILL.md
  4. model acts on its own prior, now stamped as procedure
environment · never touched
Induced from runs

The loop that has to cross something

  1. task
  2. agent runs the task
  3. the environment answers
  4. outcome verified by a test
  5. routine extracted from the verified trace
  6. model reads a skill that contains a measurement
environment · crossed twice

The whole argument is the two bands. Information can only enter a document by crossing the boundary between the model and the world, and only one of these processes crosses it. Everything else — fluency, structure, confidence, format — is identical between the two, which is exactly why the bad one is hard to spot by reading it.

What lives on the far side of that band

It is worth being concrete about what is actually over there, because this is the part that makes the argument land rather than sound like philosophy. The knowledge that decides whether an agent succeeds is overwhelmingly local and arbitrary:

  • the search box that ORs your terms instead of ANDing them, so a three-word query returns everything
  • the form field that silently resets when you change the one above it
  • the internal API that returns 200 with an error in the body
  • the repo convention that every reviewer enforces and no document states
  • the pagination default of 10 that makes an exhaustive search look complete when it isn’t

None of these are inferable. They are not consequences of the task description, they are not in the model’s general knowledge, and they have no reason to be true. They are facts about one system, discoverable only by running against it. A document written before the first run cannot contain any of them — and those are the only things in the document that would have been worth its tokens.

In plain words

Without a skill, an agent that is unsure checks its work: it reads the page, looks at what came back, and tries again when something looks off. A self-written skill holds the same guesses the model already had, but as firm steps in an official-looking file, so the agent follows them and stops checking. The guesses were always there; what goes missing is the checking that used to catch them. That is why the score falls below no skill at all.

04

Why it is worse than nothing, and not merely useless

Zero information predicts a flat line. The benchmarks report a drop. Something has to be actively doing damage, and the mechanism is more interesting than “wasted tokens”.

It removes the variance without removing the error

Consider what an agent does with no skill. It is uncertain, so it hedges: it reads the page before filling the form, it checks whether the search returned something plausible, it re-queries when the result set looks wrong. That behaviour is not virtue — it is what uncertainty looks like from the outside. The model does not know, so it goes and finds out.

Now give it a skill it wrote itself. The content of that skill is the model’s own guess about how the system behaves. The guess has not improved. What has changed is that it now arrives as a procedure, in an authoritative document, at the top of the context — and the agent follows it to the letter, including the steps nobody asked for.

So the damage is not that error was added. The error was already in the prior. The damage is that the error-correction was removed: the agent’s exploratory behaviour was the mechanism by which a wrong prior used to get fixed mid-run, and a confident procedure switches that mechanism off.

The sign was never in doubt

Put the three terms together and you can predict the benchmark result before you run it:

E[skill] = p(retrieved AND right) * lift the benefit - description tokens on EVERY request unconditional cost - p(retrieved AND wrong) * confident-error cost for an a priori skill: lift ......................... ~0 S = f(T), nothing was measured description cost ............. > 0 paid on 100% of requests, forever confident-error cost ......... > 0 authority without evidence ----------------------------------------------------------- E[skill] < 0 not bad luck - the only available sign

In plain words

For each source, ask what other than the model decided it was true. A test that ran, the real system’s reply, or a reviewer accepting a change all count; the model reading the task counts for nothing. A skill is worth the space it takes in the prompt only as far as something outside the model checked it.

06

Skill induction, concretely

“Induce skills from trajectories” is a phrase. Here is the loop it names, what the published systems actually do, and the two parameters that decide whether it works.

  1. Collect trajectories with their outcomes attached

    A trace without a verdict is not evidence of anything. The outcome field is the one that makes the rest of the pipeline possible, so if you are only going to instrument one thing, instrument that.

  2. Filter to the verified successes

    Executed test where you have one, judge model where you don’t, human label where the stakes justify it. Everything downstream inherits this filter’s error rate, which is the argument for making it executable wherever the task shape allows.

  3. Extract the recurring sub-routines

    This is the induction step: an LLM reads a pool of verified traces and writes out the routines that appear across them, either as text workflows or as code functions. The output is a candidate, not a skill.

    Pool it — induce from a set of traces rather than updating from one trace at a time. A library updated trace-by-trace becomes an append-only cache of one-offs.

  4. Require recurrence before admission

    The first parameter that decides everything. A routine seen once is a coincidence; the threshold is what separates a reusable workflow from a memorised episode. Pick a number, write it down, and tune it — too low and you are back to caching, too high and you never learn anything from the long tail.

  5. Distil the failures separately, as strategies

    Failed runs contain real information about the environment, but the wrong representation destroys it. “Here is a trace where we failed” teaches the shape of the failure. “Use a specific query; raise the page size” teaches the correction. One line, imperative, no narrative.

  6. Update by delta, never by rewrite

    The second parameter, and the one most teams get wrong. Regenerating the whole document each cycle causes two named failures: brevity bias, where the rewrite drops domain specifics in favour of a tidy summary, and context collapse, where repeated rewriting erodes detail until the playbook says nothing. Append and amend bullets; preserve what is already there.

What the published numbers look like when this works

Agent Workflow Memory induces reusable routines from past trajectories and supplies them selectively to later runs — offline from training examples, or online from test queries as they arrive. It reports +24.6% relative success on Mind2Web and +51.1% on WebArena, while also reducing the number of steps taken on the tasks it solves.

In plain words

A gate is a check every candidate skill has to pass before it ships. There are four: a test or a judge model confirmed the run worked, the same routine shows up across many separate runs, real tasks actually call the skill up, and it beats having no skill in a side-by-side test. Each skipped gate lets unproven text into the prompt, where its short description costs space on every request whether or not it helps.

07

The gates, and what dies at each one

A skill pipeline is an attrition process, and if yours is not throwing most candidates away it is not gating, it is collecting. Four gates, in this order, because each is cheaper than the next.

100 trajectories Everything the agent ran in the window, outcomes attached. Free — you are already logging it.
41 verified Gate 1 — outcome. An executed test or a judge confirms the run actually succeeded. Ungated, you are compressing your mistakes into procedure.
12 recurrent Gate 2 — recurrence. The routine appears across n distinct verified runs. Below the threshold it is an episode, and episodes belong in memory, not in a skill.
7 retrieved Gate 3 — retrieval. The description actually matches real incoming tasks at a measurable rate. A skill nobody retrieves still bills you for its description on every request.
3 ablated & admitted Gate 4 — ablation. Same tasks, with and against no skill, enough runs to separate the lift from noise. The survivors ship. Illustrative ratios — measure your own and the shape will hold.

The funnel is the answer to “this sounds expensive”. It is — but almost all of the cost is at gates 1 and 4, both of which are eval infrastructure you need anyway. The induction itself is the cheap part, which is precisely why teams do only the induction.

Three things people get wrong about the ablation

  • Ablate per skill, not per library. A library-level A/B hides a skill costing you 10 points behind two that gain 15. You will ship the harmful one forever and never see it.
  • Ablate against no skill, not against last week’s library. Comparing to the incumbent measures a delta against an unvalidated baseline. If the whole library is net-negative, every A/B against it looks like progress.
  • Log the retrieval rate alongside the lift. A +20-point conditional lift on a skill retrieved 2% of the time is worth 0.4 points of expected value, and it costs its description tokens on 100% of requests. That skill is negative and the headline number says it is excellent.
08

When intent is the right source — and the real bug in the format

An answer that only vetoes is half an answer, and the interviewer will find the exception if you don’t. There are two cases where writing a document before any run is exactly correct, and noticing what they have in common tells you what is actually broken.

Case 1 · Policy

“Never open a PR against main.” “Redact customer identifiers before they reach a third-party API.” “House style is British spelling.”

These are not knowledge and no amount of experience produces them — they are decisions somebody made. Intent is precisely the right source, because intent is what they are. The test is the same one as for an invariant: if the answer to “who signed off on this?” is a person or a policy rather than an engineer’s intuition, it is a rule, and rules get written down in advance by definition.

Case 2 · Bootstrapping, honestly labelled

A new system has no traces, so the first document is necessarily a guess. Writing it is fine. Calling it a skill is not. It is a hypothesis: it goes in with an explicit label, it goes straight into an A/B, and it is deleted or promoted on the result rather than left to accumulate authority by sitting there.

What both have in common: the document is fine, and what would have been harmful was the mislabelling. And that points at the thing actually worth fixing.

The real bug

SKILL.md has no provenance field. A measurement and a guess are the same file type, sit in the same directory, get loaded by the same mechanism, and are read by the agent with identical authority. The format has no way to say “this line came from 41 runs” and no way to say “this line is somebody’s hunch from before we shipped”.

That is why the PM’s suggestion sounds reasonable. It produces a file that is indistinguishable, by inspection, from a good one.

So add the field. This costs nothing, and it converts an argument you have to win in a meeting into a property of the artefact:

--- name: reconcile-invoice-lines description: ... provenance: induced # induced | curated | reference | policy | hypothesis runs: 41 verified, 2026-08-02..2026-08-19 verified_by: tests/e2e/reconcile_spec.py # executable, not a judge recurrence: seen in 12 of 41 ablation: +6.2pp vs no-skill (n=180, 2026-08-21) retrieval: fires on 31% of invoice tasks review: re-ablate 2026-11-21 --- # anything without runs/ablation carries provenance: hypothesis, # and hypotheses are deleted at the review date unless promoted.
Say this part — it is the difference between a critique and a plan

“I don’t want to block the PM’s idea, I want to route it. Let the agent draft candidates from task descriptions — that is genuinely cheap. They enter as hypotheses, they get an A/B like everything else, and the ones that earn a number get promoted. My objection isn’t to generating them. It’s to shipping them as though they were evidence.”

09

Twelve follow-ups they will actually ask

The first answer buys you these. Each one has a trap in it, and in most cases the trap is an invitation to overclaim.

F1Isn’t this just prompt engineering with extra steps?

Structurally, yes — and that is the point rather than an objection. Everything here is prompt content. What changes is the admission rule. Ordinary prompt engineering admits text because someone thought it would help; this admits text because a measurement said it did. Same artefact, different epistemics, and the benchmarks separate them by 25 points.

F2Your traces come from a mediocre agent. Aren’t you just compressing mediocrity?

Yes, and this is the sharpest objection on the list. Induction is bounded above by what the agent has managed to do, so you learn nothing about strategies it has never tried. Two honest answers.

First, the verification gate means you compress successful mediocrity, which is still a real lower bound — the routine worked, even if a better one exists. Second, you break the ceiling deliberately: keep a fraction of runs unskilled to preserve exploration, and let the failure-distillation path carry the information that the successful path cannot.

What you must not claim is that induction discovers optimal strategy. It compresses what worked. That is a different and more modest thing, and saying so is a credibility gain.

F3How many runs before you trust a routine?

There is no universal number and confident-sounding ones are a bad signal. What you should have is the shape: the threshold trades off coverage against overfitting, and it should be set from the cost asymmetry of your domain. Where a wrong skill is cheap, a low threshold is fine and you learn faster. Where a wrong skill is expensive, raise it until a bad routine has to survive several independent successes.

The thing to actually say: it is a tuned parameter with a metric attached — sweep it and watch the post-ablation admission rate. If almost everything you admit passes ablation, your threshold is too high and you are leaving information on the floor.

F4We have no executable test for these tasks. Now what?

Then the gate is a judge and you inherit its error rate, so you spend effort on the judge instead of pretending the problem is gone. Validate it against human labels on a sample, and report the false-accept rate specifically, because false accepts are what put a wrong skill in the library while false rejects only cost you coverage.

Also look harder for a partial check. A weak executable signal — did the record exist afterwards, did the endpoint return the id, did the file parse — is usually available and is worth more as a gate than a fluent judgement, because it cannot be talked into agreeing.

F5The environment changed and a skill is now wrong. How do you find out?

This is the failure mode nobody designs for and it is the strongest argument for the provenance frontmatter. Three layers. A review date per skill, so staleness has a deadline rather than waiting for an incident. Periodic re-ablation on current traffic — the same A/B, run again, which is why it must be automated the first time. And an alert on inversion: if the lift of an admitted skill crosses zero, that is a page, not a quarterly review item.

The sting is that a stale skill degrades exactly like an a priori one — it was evidence once and it is now an assumption with a document behind it. Provenance without an expiry date decays into the thing it was meant to prevent.

F6Two skills give contradictory instructions. What happens?

The model picks one, silently, and usually the one later in context or more specifically worded. There is no conflict resolution in the format — which is worth saying plainly because people assume there is.

Practically: detect it at induction time rather than at inference time. If a new candidate routine covers the same trigger as an existing skill, that is a merge or a replace decision for a human, not a second file. This is also the argument for delta updates over regeneration — amending a bullet keeps one document authoritative, whereas rewriting produces two documents that disagree.

F7Isn’t an induced skill just overfitting to your eval set?

It can be, and the test is already published. Induced workflows were evaluated across tasks, websites and domains, and the margin over baseline grew — 8.9 to 14.0 absolute points — as the train–test distribution gap widened. Memorisation does the opposite.

The reason is the recurrence gate: a routine that appears in twelve different verified runs is, by construction, not specific to one of them. Overfitting is what you get when you skip that gate and induce from single traces, which is exactly the append-only cache failure.

F8Why not just fine-tune on the verified trajectories instead?

Sometimes you should, and it is a fair question rather than a gotcha. The trade is legibility and latency of change. A skill is a text document: you can read it, diff it, argue with it in review, and delete it in one commit when the environment changes. Weights are none of those things, and the review-date discipline above is unimplementable against them.

The decision rule I would give: fine-tune for behaviour that is stable and high-volume, use skills for procedure that is specific and changes. If the routine is worth burning into weights, it has almost certainly earned a skill first — and the skill’s ablation number is the evidence for the fine-tune.

F9What stops the library growing forever?

Nothing in the pipeline as described, which is why the eviction rule has to be explicit. Admission is not the only gate: a skill that has not been retrieved in the last n days is paying its description tax for nothing and should be archived automatically. A skill whose re-ablation comes back inside the noise band gets the same treatment.

Make the constraint a number people can see — a token budget for the always-loaded descriptions, sized as a fraction of the context window. Then adding a skill means something has to justify its place, and the +19.0 vs +10.1 result stops being a slide and starts being a budget.

F10This is a quarter of work. What do you ship in a week?

Instrument outcomes on traces, and run one ablation on the documents you already load. That is the week, and it is the right week because both are prerequisites for everything else and both frequently produce a result on their own.

In my experience the first ablation is the thing that changes the conversation. Most teams are carrying context documents that have never been measured, and the null result on one of them — or the negative — is more persuasive about the whole approach than any argument from first principles.

F11Can the agent close the loop itself — induce, gate and promote, with no human?

Mechanically yes, and it is worth saying which part is actually load-bearing. The human is not there for the induction, which models do well. The human is there for intent: the agent can observe that a routine worked, but not that it is the routine we want — the fast path that skips the audit log also works.

So the split is: the agent proposes from evidence, the human edits for intent. And the autonomy you can safely extend scales with how executable your gate is. With a real test suite adjudicating outcomes, auto-promotion is defensible. With a judge model adjudicating, you have a model deciding what a model gets to believe, which is the closed loop again with more steps.

F12What’s the general lesson — the one you’d put on a slide?

A document’s authority should come from its provenance, not from its format. Everything on this page is that one sentence applied to skills. The reason an a priori skill is dangerous rather than merely useless is that the format grants it the same standing as a measurement, and nothing in the file says otherwise.

It generalises past agents, which is usually what the question is fishing for. The same failure is a runbook nobody has executed, a threshold copied from a blog post, a config comment that was true two migrations ago. In each case the artefact looks identical whether it was earned or assumed — so the fix is always the same: make the source a field, and make the field a requirement.
