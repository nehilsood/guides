Languages: Python, SQL, C++

A skills line is a list of promises. An interviewer picks the one you look least comfortable with and asks about that. Two of these three are backed by everything else on the page. The third is not, and this chapter is mostly about being ready for it.

The win

Have a concrete, specific answer for each named language — and a prepared, non-defensive sentence for the one where the honest answer is “less than the others, and here is exactly how much.”

The sentence that sounds fluent and gets you caught

“I'm proficient in Python, SQL and C++.” Proficient is a word that means nothing and invites a test. It also flattens a real ranking into a false equality, so the interviewer's next move is to find out which one is weakest — and now they are looking for it rather than being told.

The other trap is “I know async.” Everybody says it. The version that lands names a specific consequence: “the event loop is one thread, so CPU work in a handler makes every other request wait, and I check for that before anything else.” Same claim, and only one of them is checkable.

Start here — the plain version

Every item on a skills line is an invitation. Nobody asks about the language you obviously use all day. They scan for the one that looks least supported by the rest of the page. Then they ask about that. It is the cheapest way to find out whether the page is honest.

So this chapter is not a Python tutorial. It is an inventory. For each language: what on the résumé proves it, what the standard hard questions are, and what to say where the proof is thin.

The GIL
Python's global interpreter lock. Only one thread runs Python bytecode at a time, which is why threads do not speed up CPU work and do help with waiting.
Concurrency and parallelism
Concurrency is handling many things by interleaving. Parallelism is doing many things at literally the same moment. Async gives the first, processes give the second.
Event loop
The single thread that runs async code, switching between tasks whenever one awaits. Anything that does not await holds it, and nothing else runs.
Coroutine
A function that can pause at an await and resume later. Cheap to create, so thousands can wait at once for the cost of one thread.
Three-valued logic
SQL has true, false and unknown. A comparison with NULL is unknown, and a WHERE clause only keeps rows where the condition is true.
Query plan
What the database intends to do to answer a query. EXPLAIN shows it, and reading one is the difference between guessing at performance and knowing.
Partial index
An index over only the rows matching a condition. Made unique, it enforces a rule like “at most one live version per rubric” inside the database.
Window function
A calculation across a set of rows related to the current one, without collapsing them into groups. The thing people reach for GROUP BY for and should not.
RAII
The C++ idea that a resource's lifetime is tied to an object's scope. The nearest Python equivalent is a context manager, which is a useful way to answer.
Value semantics
In C++, assigning copies by default, and you opt into sharing. In Python, names refer to objects and nothing is copied unless you ask. The mental model differs more than the syntax does.
The technology — what each named thing is

The primer above names the ideas this line is tested on. This one names the machinery underneath, starting from the ground. A languages line invites the question “what actually runs my code”, and three answers are wanted, one per language.

Every entry answers four things. What it actually is, in plain words. Where it shows up in this work. What it buys, meaning what goes wrong without it. And the follow-up an interviewer asks once you have said the name.

CPython
the interpreter almost everyone meansPython is a language specification. CPython is the program that actually runs it, written in C, and it is what you get when you type python. It compiles your source into bytecode and executes that on a stack machine, and it manages memory by counting references, with a cycle collector behind that for objects which point at each other. In the app. Every Python system on this résumé runs on it. What it buys. Predictable memory behaviour and the entire C extension ecosystem, which is why numpy and pandas are fast at all. The follow-up. The GIL belongs to this entry, not to Python the language. Other implementations exist without one, and recent CPython ships an experimental free-threaded build, so “Python cannot do parallelism” is already the wrong sentence and a good place to show you know the difference.
Threads, processes, coroutines
threading, multiprocessing, asyncioThree ways to do more than one thing, and they are not interchangeable. Threads live in one process and share memory, so passing data between them is free, but the GIL stops them running Python code simultaneously. Processes each get their own interpreter and give genuine parallelism, at the cost of copying data across a process boundary. Coroutines are a single thread that switches voluntarily at each await. In the app. All three appear across these projects, and the choice is different each time. What it buys. Picking correctly is the difference between a tenfold speedup and no change at all. The follow-up. The rule is short enough to say from memory. Waiting on a network picks asyncio. Waiting inside a library that blocks and cannot be awaited picks threads. Burning CPU picks processes.
Type hints
and the checkers that read themAnnotations written into the source that the interpreter reads and then ignores. They change nothing at runtime on their own. What makes them useful is the tools that consume them: mypy or pyright read them ahead of time and fail a build, editors use them for completion, and libraries such as Pydantic read them at runtime to validate real data. In the app. Everything here leans on them, from FastAPI request models to structured model output schemas. What it buys. One declaration doing three jobs — documentation, static checking and runtime validation — instead of three that drift apart. The follow-up. Nothing checks them by default. An annotated function will accept entirely the wrong type without complaint unless something in your pipeline is actually looking, and plenty of codebases annotate without ever running a checker.
SQL engines
Postgres, Snowflake, BigQueryOne language, three machines built for different jobs. Postgres stores rows together and is built for transactions: fetch this customer, update that order. Snowflake and BigQuery store columns together and are built for scans: average this field over a billion rows. Columnar storage means a query touching three columns reads three columns, not the whole table. In the app. This résumé touches all three, and the same SQL performs completely differently on each. What it buys. Knowing which is which stops you carrying transactional habits into a warehouse, where they are expensive and useless. The follow-up. What actually changes. Indexes are central in Postgres and largely absent in the other two, where the equivalent levers are partitioning, clustering and simply how many bytes a query is forced to read.
B-tree index
the default indexWithout an index, finding a row means reading every row. A B-tree is a balanced tree of sorted keys where each node points at a page of the next level, so a lookup in a million rows costs three or four page reads instead of a million. Because the keys are stored in order, the same structure also serves range queries and sorting for free. In the app. It is the structure that the partial unique index in the primer is a variant of. What it buys. Lookups that stay fast as the table grows, which is the difference between a query at a thousand rows and the same query at ten million. The follow-up. When the planner deliberately ignores it. If a query is going to read most of the table anyway, a sequential scan is cheaper than jumping around through an index, so a selective index on an unselective query is dead weight. EXPLAIN is how you find out instead of guessing.
C++ standards
C++11 onwardsC++ is revised every three years and the revision decides what counts as idiomatic. C++11 was the break point: move semantics, auto, lambdas, smart pointers. C++17 added structured bindings and std::optional. C++20 added ranges, concepts and coroutines. Code written against different standards looks like different languages. In the app. The résumé says C++, which means nothing until you say which decade of it. What it buys. Naming the version tells an interviewer immediately how you write, before they have seen a line. The follow-up. Say the version you actually used and why. Pre-11 C++ full of raw new and delete is genuinely a different language from the modern one, and claiming the modern one while writing the old one falls apart on the first whiteboard question.
Smart pointers
unique_ptr, shared_ptr, weak_ptrSmall objects that own a piece of heap memory and free it automatically in their destructor, so the free happens when the owner goes out of scope rather than when you remember. unique_ptr means exactly one owner and costs nothing at runtime. shared_ptr keeps a reference count, freeing when the last owner dies, and pays an atomic increment for it. weak_ptr observes without owning, and is how you break a cycle. In the app. They are RAII made concrete, and RAII is in the primer above. What it buys. Memory safety without a garbage collector and without discipline, because the compiler inserts the free. The follow-up. Reach for unique_ptr first. Defaulting to shared_ptr usually means you have not decided who owns the thing, and two shared pointers pointing at each other leak forever, which is exactly what garbage collection would have handled.
Move semantics
and the rule of fiveBefore C++11, returning a large container by value meant copying every element. Move semantics added a second option: transfer the internals instead. The new object takes the old one's pointer to its data and the old one is left empty. A move constructor takes an rvalue reference, which is the compiler's way of marking a value nobody will use again. In the app. It is the change that made value semantics practical at scale. What it buys. Returning big objects by value becomes free, so the ugly workarounds — output parameters and raw pointers everywhere — stop being necessary. The follow-up. What state the moved-from object is in. It is not destroyed and it is not garbage. It is valid but unspecified, which means you may safely destroy it or assign a new value to it, and you must not read it and expect anything.
Undefined behaviour
the one that bitesOperations the standard deliberately gives no meaning to at all. Reading past the end of an array, dereferencing a dangling pointer, overflowing a signed integer. The standard does not say these fail, it says anything may happen, and the compiler is entitled to assume they never occur and optimise on that assumption. In the app. It is the single biggest difference between C++ and every managed language on this résumé. What it buys. Speed, honestly. The optimiser is fast precisely because it may assume you did not do these things. The follow-up. Why it is worse than an ordinary bug. It does not fail at the line that caused it. The compiler removes a null check you wrote three functions away because the earlier code proved the pointer could not be null, and the program works perfectly until the optimiser level changes.
Toolchain
compiler, linker, sanitizersC++ builds in stages and each fails differently. The compiler handles one translation unit at a time and never sees the others, so it checks declarations rather than definitions. The linker then joins them, which is why a missing definition arrives as a link error with no file and no line number. Sanitizers are instrumentation compiled into the binary that catches at runtime what neither stage can see. In the app. Debugging C++ is mostly knowing which of the three stages is complaining. What it buys. Reading the error correctly instead of editing at random, which on a large codebase is most of the time saved. The follow-up. Name a sanitizer. AddressSanitizer for memory errors and buffer overruns, UndefinedBehaviorSanitizer for the entry above, ThreadSanitizer for data races.

What actually backs each of the three

Python is on every line of the page. SQL is real and specific, across two very different engines. C++ has nothing behind it on this résumé, and pretending otherwise is the only way to lose this question.

That is more interesting than most people's SQL experience because it includes reading plans as a programmatic check.

The Python question that separates people

Nobody senior asks whether you know Python. They ask what happens when CPU work runs inside an async function. The answer tells them whether you have run an async service or read about one.

The event loop is one thread. A coroutine keeps the loop until it hits an await. If a handler spends 200 ms doing arithmetic with no await in it, the loop is held for 200 ms and every other request in the process waits, including ones that were nearly done.

This is not hypothetical for the systems on this résumé. The vendor-evaluation pipeline fires sixteen concurrent searches and three concurrent model calls in one gather. That shape is only cheap because every one of those tasks is waiting on a socket rather than computing.

The complete answer names the fix too: move CPU work to a thread pool via run_in_executor or asyncio.to_thread, and if it is heavy and genuinely parallel, to a process pool, because threads cannot escape the GIL for bytecode.

Plain meaningOne queue, one server. If a customer stands there doing a long sum, everybody behind them waits, even the ones who only wanted change.

The SQL question that separates people

NULL is not a value. It is the absence of one, and comparing with it gives neither true nor false. Most SQL bugs that survive review are a version of forgetting that.

WHERE col <> 'x' silently drops every row where col is NULL. Not because NULL equals 'x', but because the comparison evaluates to unknown, and WHERE keeps only rows that are true. The same trap lives in NOT IN against a subquery containing a NULL, which returns nothing at all.

The second question in this family is the plan. Being able to say what EXPLAIN shows — scan types, join order, estimated versus actual rows — is the difference between someone who writes SQL and someone who owns a database. In the debugger that check is not a habit, it is a code path: a generated query is sent as an EXPLAIN and the plan coming back is the proof it binds.

Plain meaningAn empty box is not the same as a box containing zero. Ask whether an empty box is not equal to x, and you get a shrug rather than a yes.

What to do about C++

There is one good answer and it has three parts. Say where it comes from, say what level it is at honestly, and then move to what you would do on day one. Do not improvise depth you do not have.

The failure mode is trying to hold a C++ conversation at the same depth as the Python one. An interviewer who writes C++ daily will find the floor in two questions, and what they remember is not the gap but the attempt to cover it.

The version that works is specific and short. It is from academic and on-device work rather than production services. It is at the level of reading and modifying rather than architecting. And here is the concept you do genuinely understand: RAII, and why it maps onto Python's context managers.

Then the real decision: if C++ is not going to be used in this role, the honest sentence costs nothing. If the role is C++ heavy, the right move is to take it off the page rather than defend it, because the line is doing you damage rather than good.

Plain meaningSay how much you have, not more. If a list item cannot survive one question, it is not helping you.

  1. What is CPython, and what is the GIL a property of?

    Python is a language specification. CPython is the program that actually runs it, written in C. It is what you get when you type python. It compiles your source into bytecode and executes that on a stack machine. Memory is managed by counting references, with a cycle collector behind it. What that buys is predictable memory behaviour and the whole C extension ecosystem, which is why numpy and pandas are fast at all. The GIL is a property of that implementation, not of the language. Other implementations do without one, and recent CPython ships an experimental free-threaded build. So the careful sentence is about CPython, not about Python.

    Red flag“Python can't do parallelism.” It is a statement about one interpreter, it is being actively unwound, and saying it flatly dates you.

  2. Threads, processes or asyncio. How do you choose?

    By what the code is waiting on. They are three genuinely different things. Threads live in one process and share memory, so passing data is free, but the GIL stops them running Python code at the same time. Processes each get their own interpreter and real parallelism, paying for it by copying data across a boundary. Coroutines are one thread switching voluntarily at each await. So waiting on a network picks asyncio, because one thread can hold thousands of those. Waiting inside a library that blocks and has no async version picks threads. Burning CPU picks processes. Choosing right is the difference between a tenfold speedup and no change.

    Red flagReaching for threads by default. They are the middle answer, and the reason to pick them is almost always that a library gave you no choice.

  3. What do Python type hints actually enforce?

    Nothing, on their own. The interpreter reads them and moves on. What makes them useful is the tools that consume them. A checker such as mypy or pyright runs ahead of time and fails your build. Editors use them for completion. A library such as Pydantic reads them at runtime and validates real data against them. What that buys is one declaration doing three jobs, rather than three that drift apart. Documentation, static checking and runtime validation all come from the same line. That last path is what everything else here leans on, from FastAPI request models to schema-constrained model output.

    Red flagCalling Python statically typed because the code has annotations. Annotated and checked are different, and only one of them is in your pipeline.

  4. You have written SQL against Postgres, Snowflake and BigQuery. What actually differs?

    The language barely changes. The machine underneath changes completely. Postgres stores rows together and is built for transactions: fetch this customer, update that order. Snowflake and BigQuery store columns together and are built for scans: average this field over a billion rows. Columnar storage means a query touching three columns reads three columns, not the whole table. So in Postgres indexes are central. In the other two they are largely absent, and the levers are partitioning, clustering and how many bytes the query is forced to read. Knowing which is which stops you carrying transactional habits into a warehouse, where they are expensive and useless.

    Red flagTreating SQL as one skill. The dialect is the easy part. Knowing which engine rewards which shape is the part being tested.

  5. What is a B-tree index, and when does the planner ignore one?

    Without an index, finding a row means reading every row. A B-tree is a balanced tree of sorted keys where each node points at a page of the next level. A lookup in a million rows costs three or four page reads instead of a million. Because the keys are stored in order, the same structure also serves ranges and sorting for free. What it buys is lookups that stay fast as the table grows. The planner ignores it when the query is going to read most of the table anyway, since reading sequentially beats jumping around. You find that out with explain rather than by guessing.

    Red flag“Add an index” as a reflex. An index that the planner never picks is write cost with no read benefit.

  6. Which C++ do you actually write?

    Say the standard. C++ is revised every three years, and the revision decides what counts as idiomatic. C++11 was the break point: move semantics, auto, lambdas, smart pointers. C++17 added structured bindings and optional. C++20 added ranges, concepts and coroutines. Code written against different standards looks like different languages. Pre-11 code full of raw new and delete genuinely is one. What naming the version buys is that an interviewer knows how you write before seeing a line. It turns a one-word skills entry into a claim somebody can check.

    Red flagListing C++ with no era attached. The interviewer's next question is which standard, and having no answer suggests the entry is old coursework.

  7. What do move semantics buy, and what is a moved-from object?

    Before C++11, returning a large container by value copied every element. Move semantics added a second option. The new object takes the old one's pointer to its data, and the old one is left empty. A move constructor takes an rvalue reference, which is the compiler's way of marking a value nobody will use again. What that buys is returning big objects by value for free. The ugly workarounds stop being necessary, meaning output parameters and raw pointers everywhere. The moved-from object is not destroyed and not garbage. It is valid but unspecified. You may destroy it or assign to it, and you must not read it.

    Red flagSaying the source becomes invalid. It stays valid on purpose, because its destructor still has to run.

  8. What is undefined behaviour, and why is it worse than an ordinary bug?

    It is an operation the standard deliberately gives no meaning to at all. Reading past an array, dereferencing a dangling pointer, overflowing a signed integer. The standard does not say these fail. It says anything may happen, and the compiler may assume they never occur. What that assumption buys is speed, honestly. The optimiser is fast precisely because it may assume you did not do these things. The cost is that it does not fail where you wrote it. It can delete a null check three functions away, because earlier code proved the pointer could not be null. The program works until the optimisation level changes.

    Red flag“It crashes.” Crashing is the good outcome. The dangerous one is code that runs correctly for a year and then does not.

These are the questions the line itself invites. Most of them arrive as small talk and are not small talk.

  1. Of the three, which are you strongest in, and what proves it?

    Python, and the rest of the page proves it. Async services on FastAPI, async SQLAlchemy over asyncpg, pandas in the forecasting layer, pydantic schemas constraining model output, pytest suites, and three different agent frameworks. SQL is second and specific. C++ is the weakest and I would say so unprompted.

    Red flagClaiming all three equally. The list is ordered on the page and an interviewer reads that order as a ranking anyway.

  2. What is the GIL and why does it matter to you?

    A lock that lets only one thread execute Python bytecode at a time. It means threads do not speed up CPU-bound work. They do help with work that waits. Everything I build is IO-bound, waiting on models and databases. So the GIL is mostly irrelevant to me until something starts computing.

    Red flagSaying Python cannot do parallelism. It can, with processes. The GIL constrains threads, not the language.

  3. When would you use asyncio, threads, or processes?

    Asyncio for many things waiting on the network, which is my normal case. Threads for blocking calls I cannot make awaitable, like a library with no async client. Processes for genuine CPU work, because that is the only way past the GIL. The question is always what the task is waiting on.

    Red flagRanking them by speed. They solve different problems and the choice follows from the workload.

  4. What does await actually do?

    It suspends the current coroutine and hands control back to the event loop. The loop is then free to run something else until the awaited thing is ready. It is a yield point, not a wait. That is why a function with no await never gives the loop a chance.

    Red flagDescribing it as “waiting for the result.” It is the opposite: it is the point where this task stops occupying the thread.

  5. When would you return a generator rather than a list?

    When the caller consumes items one at a time and the whole collection need not exist. The planner does exactly this. It pulls workflows from a queue and processes each immediately, so memory stays at one workflow. The cost is that you can only walk it once.

    Red flagSaying generators are faster. They are lazier. Total work is the same and peak memory is not.

  6. What does WHERE col <> 'x' return for rows where col is NULL?

    Nothing. Those rows are dropped. Comparing anything with NULL gives unknown rather than true or false, and WHERE only keeps rows that are true. To include them you need col <> 'x' OR col IS NULL. The same trap makes NOT IN against a subquery with a NULL return no rows at all.

    Red flagSaying they are included because NULL is different from x. It is the single most common SQL misconception and it is exactly what the question is testing.

  7. What do you look at first in a query plan?

    Whether the estimated row counts match the actual ones. If the estimate is wrong the whole plan is built on a wrong premise, and everything else you might fix is downstream of that. After that, scan types and join order. In the debugger, EXPLAIN is also a correctness check rather than a performance one.

    Red flagGoing straight to indexes. An index cannot fix a plan built on a cardinality estimate that is out by three orders of magnitude.

  8. When does an index not help?

    When the query touches a large fraction of the table, because a sequential scan beats random lookups past a certain share. Also when the predicate is not sargable, like wrapping the column in a function. And every index costs write throughput and space, so an unused one is pure overhead.

    Red flagTreating indexes as free. Naming the write cost is what makes the answer sound like production experience.

  9. Tell me about your C++.

    It is the weakest of the three and I would rather say that than let you find it. It comes from academic and on-device work rather than production services. It is at the level of reading and modifying rather than designing. I understand RAII well, partly because context managers are the same idea. If this role is C++ heavy, I would want to be honest about where I start.

    Red flagAttempting depth. Two follow-ups find the floor, and the attempt is what gets remembered rather than the gap.

  10. What is the riskiest claim on this line?

    C++, because nothing else on the page supports it. Python and SQL are both evidenced by the work described in every other bullet. C++ appears once, as a word, with no project behind it. Either it earns a line somewhere in the experience section or it should come off the skills line.

    Red flagNaming SQL. It is well supported by Postgres invariants and Snowflake plan validation, and undervaluing it wastes a genuine strength.

Deep dive

The Python and SQL questions a senior interviewer actually uses. None of these are trivia, and every one has a wrong answer that sounds right.

  • Blocking the loop
  • gather and cancellation
  • Async in a sync world
  • Pydantic versus dataclass
  • Mutable defaults
  • Context managers
  • Window functions
  • Partial unique indexes
  • Transactions and pooling
  • Warehouse versus OLTP
  • Parameterised queries
  • RAII and Python

  1. A handler does 200 ms of CPU work inside an async def. What happens?

    Every other request in that process waits 200 ms. The event loop is one thread, and a coroutine holds it until it awaits. Nothing about the function being async helps, because async is about yielding at IO. The fix is asyncio.to_thread for blocking calls, or a process pool if it is genuinely CPU-heavy.

    Red flagThinking only that request is slowed. The whole point of the question is that the cost lands on everybody else.

  2. You gather three calls and one raises. What happens to the other two?

    By default gather propagates the first exception immediately, and the other tasks keep running unless you cancel them. That is how you leak work. With return_exceptions=True you get results and exceptions together and can decide. In the Scout's three concurrent calls that distinction decides whether a partial result is usable.

    Red flagAssuming siblings are cancelled automatically. They are not, and that surprise is the reason the question gets asked.

  3. You need to call an async function from synchronous code. How?

    asyncio.run if there is no loop yet, which is the script case. If a loop is already running you cannot nest. The work then goes to the existing loop as a task, or onto a separate thread with its own loop. The real answer is usually that the boundary is in the wrong place.

    Red flagReaching for a nested event loop patch. It works and it hides a structural problem that will resurface.

  4. Pydantic model or dataclass?

    Dataclass when the data is already trusted and I want structure. Pydantic when it crosses a boundary and has to be validated or coerced. Everything coming back from a model is a boundary, which is why the scout claim schema and the debug solution are both pydantic. The validation is the feature, and it costs construction time.

    Red flagUsing pydantic for everything. It is a parser, and paying parsing cost on internal objects is waste.

  5. Why is a mutable default argument a bug?

    Because the default is evaluated once, when the function is defined, not on each call. So one list is shared by every call that omits the argument, and it accumulates. The fix is a None default and building the real value inside. It is the most common Python trap that survives code review.

    Red flagKnowing the rule without the reason. The reason is definition-time evaluation, and that explains several other Python behaviours too.

  6. What problem do context managers solve?

    Releasing something on every exit path, including exceptions, without repeating the cleanup. A database session is the case I care about: the middleware opens one per request and commits or rolls back on exit. That is also why background work cannot borrow it, because the request's scope has already closed.

    Red flagExplaining the protocol methods. The question is about guaranteed cleanup, not about __enter__.

  7. When do you reach for a window function?

    When I need a per-row value computed over related rows without collapsing them. Ranking runs within a workflow, or a running total, or comparing each row to its group's average. GROUP BY would fold the rows away and I would have to join back. A window keeps every row and adds the number.

    Red flagDescribing it as a faster GROUP BY. It answers a different question, and the difference is whether rows survive.

  8. Explain a partial unique index and why you used one.

    A unique index built only over rows matching a condition. In the rubric model it enforces at most one live version and at most one draft per rubric. Without it that rule lives in application code, which means a check-then-insert that two concurrent requests can both pass. The database makes it impossible rather than unlikely.

    Red flagSaying the application checks it. That is the answer the question exists to reject, because check-then-act races.

  9. What goes wrong holding a database session across an await on a model call?

    The session and its connection are held for the whole model call, which can be seconds. Pool connections are finite, so enough concurrent turns exhaust the pool and requests queue for a connection they do not need yet. Any transaction open across that window also holds locks for its duration.

    Red flagFraming it as style. It is a capacity bug, and it appears under load rather than in review.

  10. How is writing SQL for Snowflake different from writing it for Postgres?

    Different shapes of problem. Postgres is row-oriented and transactional, so indexes, isolation and constraints matter. Snowflake is columnar and analytical, so pruning, clustering and how much data a query scans matter, and there are no indexes to add. A query tuned for one is often nonsense in the other.

    Red flagTreating SQL as portable. Working with both is the interesting part of this claim and flattening them wastes it.

  11. Why do parameterised queries prevent injection when escaping does not?

    Because the query and the data travel separately. The statement is parsed first and the parameters are bound afterwards. So a value can never become syntax. Escaping instead tries to neutralise data inside a string that will still be parsed as one. That protection depends on getting the escaping exactly right every time.

    Red flagSaying parameters escape the input. They are not escaped, they are never parsed as SQL at all, and that difference is the whole answer.

  12. What is RAII, and what is the Python equivalent?

    Tying a resource's lifetime to an object's scope. Leaving the scope releases it, and an exception cannot skip that. The Python equivalent is a context manager, with with playing the role of the destructor. It is the C++ concept I am most confident about, because I use its equivalent constantly.

    Red flagOver-extending into move semantics or templates. Answer the concept you own and let the follow-up go where it goes.

A FastAPI handler declared async def spends 200 ms on pure computation with no await. What is the effect?

  1. The whole event loop blocks and every request waits
  2. The request is moved to a background worker thread
  3. Only that one request is slowed by the computation
  4. The framework logs a warning and retries it later

Everything waits. The event loop is a single thread and a coroutine holds it until it reaches an await. Two hundred milliseconds of arithmetic is two hundred milliseconds where no other request in the process can make progress, including ones that were about to finish.

Declaring a function async does not move it anywhere. The fix is explicit: asyncio.to_thread for a blocking call, or a process pool for real CPU work, because threads still cannot run Python bytecode in parallel.

A table has rows where col is NULL. What does WHERE col <> 'x' do with them?

  1. Excluded, because a comparison with NULL is unknown
  2. Included, because NULL differs from that string value
  3. Excluded, although only when that column is indexed
  4. Included, as the planner rewrites the whole predicate

They are dropped. NULL is the absence of a value, so comparing it to anything yields unknown rather than true or false, and WHERE keeps only rows where the condition is true. You need col <> 'x' OR col IS NULL to include them.

The second option is the intuition almost everybody has, and it is why this is a good interview question. The same rule is what makes NOT IN against a subquery containing a single NULL return no rows at all, which is a much harder bug to find.

Edges and exceptions

Three of these are about the résumé rather than the languages. That is the right balance for a skills line.

  • Asked to write C++ live
  • A Python question you cannot answer
  • Async made it slower
  • A query that passed review
  • Ordering the list
  • Adding a language
  • Rating yourself out of ten
  • What you would change

  1. The interviewer opens a shared editor and asks you to write C++.

    I would say up front that I will be slow and will want to check syntax, then attempt it anyway. Refusing is worse than struggling. What I would not do is pretend fluency while writing Python with semicolons. If it goes badly, I would solve the problem in pseudocode. The algorithm is the part I am confident about.

    Red flagDeclining outright. It confirms the line is decoration, which is worse than writing imperfect code.

  2. You get a Python question you genuinely do not know.

    Say so in one sentence. Then say what I would do to find out. Then offer the nearest thing I do know. Something like: I do not know how that is implemented. I would check the source. The related thing I am sure of is this. Guessing confidently is the only way to actually lose points.

    Red flagFilling the silence with plausible reasoning. An interviewer who asked the question knows the answer, and a confident wrong one is worse than a gap.

  3. Tell me about a time async made something slower.

    The general shape is a blocking call inside a coroutine. A synchronous client library, or a CPU step, sits in the middle of an async handler. Everything serialises behind it. Throughput falls below what a plain threaded server would have managed, because now there is one thread and it is busy.

    Red flagSaying it has never happened. It happens in every async codebase, and the useful answer is how you spot it, which is latency rising for unrelated endpoints.

  4. A SQL bug that passed code review. What kind?

    A NULL one, almost always, because it reads correctly. A NOT IN against a subquery that can contain NULL returns no rows, and the query looks perfect. Nothing errors, the result is just empty, which reads as “no matches” rather than as a bug. It is the SQL equivalent of a confident empty report.

    Red flagReaching for a performance example. The question says review, and review catches slow queries far more often than it catches three-valued logic.

  5. Does the order of the three languages matter?

    Yes, and it is read as a ranking whether or not it was meant as one. Python first is right. C++ last is right. What the order cannot fix is that the third item has no supporting evidence. Position does not substitute for a project.

    Red flagSaying it is alphabetical or arbitrary. Every list on a résumé is read as ordered by strength.

  6. What would you have to do before adding a fourth language to this line?

    Ship something in it that appears in the experience section. My own rule is that a skills line should only name things another bullet already proves. That test is what C++ currently fails, and applying it consistently is what makes the rest of the list credible.

    Red flagA threshold based on time spent. Months of exposure are not checkable and a shipped project is.

  7. Rate yourself out of ten in Python.

    I would replace the number with a boundary, because the scale means nothing shared. I am comfortable with async services, the concurrency model and the data layer. I am weaker on C extensions and interpreter internals. That tells you where I am useful and where I would need time, which is what the question is actually for.

    Red flagGiving a number. Eight means nothing, and every number you pick is either arrogant or undersells you.

  8. What would you change about this line?

    Either earn C++ or drop it. If the Samsung on-device work involved it, that belongs in the bullet rather than only here. If it did not, the line is stronger as Python and SQL, because two supported items beat three where one collapses under a single question.

    Red flagKeeping it because removing things from a résumé feels like losing ground. An unbacked item is a liability, not a spare point.

Probes to expect

  1. “Tell me about your C++.” The most predictable question on the whole skills section, because it is the one item with no project behind it. Being unprepared for a predictable question is the expensive part.
    Model answer — say yours first

    It is the weakest of the three and I would rather tell you than have you find it. It comes from academic and on-device work rather than production services, and it is at the level of reading and modifying rather than designing. The concept I am genuinely confident about is RAII, partly because Python's context managers are the same idea. If this role is C++ heavy, that is worth establishing now.

  2. “What happens if you do CPU work inside an async handler?” The standard test for whether someone has operated an async service or only written one. The wrong answer is that only that request is affected.
    Model answer — say yours first

    Every other request in the process waits. The loop is one thread and a coroutine holds it until it awaits, so two hundred milliseconds of computation is two hundred milliseconds where nothing else progresses, including requests that were nearly done. The tell in production is latency rising on endpoints that have nothing to do with the slow one. The fix is a thread for a blocking call, or a process for real CPU work.

  3. “How would you enforce that only one version of a record can be live?” A design question with an application-level answer and a database-level answer. Only one of them survives concurrency.
    Model answer — say yours first

    A partial unique index, in the database. A unique index over only the rows where the status is live means the second insert fails rather than succeeding. The application-level version is a check then an insert, and two concurrent requests can both pass the check. That is exactly how the rubric model does it, and there is a second partial index for drafts.

  4. “Give me a SQL bug you have actually shipped.” Fishing for whether your SQL is real. A NULL answer is more convincing than a performance one, because performance bugs are caught in review and NULL bugs are not.
    Model answer — say yours first

    The NULL family, because they read as correct. A NOT IN against a subquery that contains a single NULL returns no rows at all, and nothing errors. The query looks right, the result is empty, and empty reads as “no matches” rather than as a bug. It is the same failure shape as a research step that soft-fails and returns a confident empty report.

  5. “Rate your Python out of ten.” A question with no good numeric answer. Replacing the scale with a boundary is both more useful and more senior.
    Model answer — say yours first

    I would rather give you a boundary than a number, because the scale is not shared. I am comfortable with async services, the concurrency model, the data layer and testing. I am weaker on C extensions and interpreter internals, and I have never needed to profile at that level. That tells you where I would be productive immediately and where I would need time.

Chapter 0001 explains why the vendor pipeline uses async SQLAlchemy. Restate that reason in terms of the event loop, and say what would break the argument.

The service spends nearly all its wall-clock waiting on Gemini, on Tavily and on page fetches. Under synchronous IO each of those waits holds a worker thread, so concurrency costs threads. On an event loop a waiting task costs almost nothing, which is why sixteen concurrent searches and three concurrent model calls in one gather is affordable. What breaks the argument is CPU work: the moment a handler computes instead of waiting, the single-threaded loop becomes the bottleneck and a thread-per-request server would have done better.

Chapter 0001 · why async at all
Chapter 0006 uses a query plan as a correctness check rather than a performance one. Why is that unusual, and what does it prove?

Most people run EXPLAIN to find out why something is slow. Here it is run to find out whether a generated query is real: if a plan comes back, the statement parsed and every table and column in it resolved against the live warehouse. That is a binding check, which is precisely the class of error a model makes, since models rarely write ungrammatical SQL and often write SQL about columns that do not exist.
