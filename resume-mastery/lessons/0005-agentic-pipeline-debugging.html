Agentic pipeline-failure debugging

The interesting decision here is not the agents. It is the triage in front of them: most pipeline failures are not worth investigating, and a system that investigates all of them is unaffordable. This chapter also corrects one word in the résumé, and it is better to correct it yourself.

The win

Explain an autonomous system that can retrigger production, and make the interviewer comfortable rather than alarmed — because you can name every gate between a model's opinion and a pipeline actually running again.

The line being defended
“Built an agentic pipeline-failure debugger end-to-end (CrewAI) — triaging each failure against a vector store of past incidents, dispatching specialist crews for SQL, Python, file, and infrastructure faults in parallel, then reviewing their findings and either applying the fix or retriggering the pipeline unattended.”
Innovaccer · bullet 1 of 3
Say it out loud · about 75 seconds

A spoken answer to “tell me about the pipeline debugger.” Lead with the triage, because it is the judgment call. The autonomy lands better once the interviewer has heard how little of the work reaches it.

  1. Situation

    A data platform runs thousands of scheduled jobs and some fail every night. Someone on call reads each log and decides whether it matters.

    Most of it is repetitive, and most failures are not interesting.

  2. Mechanism

    The system is a state machine, not a conversation. Named steps, explicit routers, one readable control path.

    In front of everything is a cheap screener. It matches the log against past incidents and returns one of three categories: retry it, ignore it, or investigate it.

    That triage is the whole idea. Only the third branch costs anything, and it is the rare one.

  3. What I did

    On the investigate branch it can propose a fix and retrigger the pipeline unattended. So the part I would want you to push on is what stands in the way.

    Four things. The screener has to escalate. The solution's action field has to say apply. A router has to agree. And a feature flag with a hard retry threshold has to allow it.

  4. What it cost

    Two corrections I would rather make myself. My résumé says the specialists run in parallel. On the default path they do not.

    One agent holds them as five tools and reasons through them in sequence. There is a parallel branch, and it is behind a flag that is off.

    And the validation layer that proves a fix before applying it defaults to off. That is the first thing I would change.

The sentence that sounds fluent and gets you caught

“Specialist agents debug SQL, Python, file and infrastructure faults in parallel.” It is the résumé read aloud, and the default configuration does not do it. One question about the dispatcher gets there. Say “five tools on one reasoning agent by default, with a parallel branch behind a flag” instead, and you sound like someone who has read their own config.

The other trap is “it fixes pipelines automatically.” Said flat, it makes an interviewer nervous and they start looking for what you forgot. Said as “it can retrigger unattended, and here are the four gates,” the same fact reads as careful engineering.

Walk them through it · one failure, end to end

The say it out loud block is ninety seconds. This is the ten minutes after that, when they say “walk me through it.” One failed pipeline, followed from the log line to the moment it runs again. The failure is a stand-in. Every gate it passes through is real, and so are the defaults.

The picture. A hospital triage nurse. Almost nobody walking through the door needs a surgeon. The nurse does not treat anyone. The whole job is deciding who gets treated and how urgently, and that decision costs a minute rather than an afternoon.

The case. At two in the morning a nightly job fails. Its log ends in a Snowflake error about a column that does not exist. Twenty other jobs failed in the same window. Follow this one.

  1. The failure

    What happens. A scheduled job dies and the jobs downstream of it start failing too. Somebody on call would read the log and decide whether it matters.

    Concretely. Most nightly failures are timeouts, auth blips, or a file that never arrived. Most of them are not interesting.

    If they ask why. The obvious build is one agent that reads a log and debugs it. That works in a demo. In production it means paying full price for every uninteresting failure.

  2. The screener

    What happens. A cheap screener runs first. It reads the log and retrieves the five most similar past incidents from a vector store.

    Concretely. That store finds text by meaning rather than by keyword, so a new log matches old ones that read similarly even when the wording differs.

    If they ask why. The screener is built with DSPy rather than CrewAI, and that is deliberate. It has a typed signature, so the decision comes back as a named category instead of prose somebody has to parse.

  3. Three buckets

    What happens. The screener returns one of three answers. Retry it, overlook it, or investigate it.

    Concretely. Two of those cost almost nothing. Everything expensive in this system sits behind the third branch, and the third branch is the rare one.

    If they ask why. That triage is the whole idea. It is what made the expensive path affordable enough to leave running unattended.

  4. The flow

    What happens. Our failure comes back as investigate, and routing takes it down that branch.

    Concretely. This is a CrewAI Flow, which is a state machine. Named steps, explicit routers, and one readable control path in one class.

    If they ask why. It is not agents chatting until they agree. When it makes a wrong call, you can see which branch it took and why. That property is what makes it debuggable at all.

  5. The specialists

    What happens. Now the investigation runs. There are specialists for SQL, Python, file and infrastructure faults.

    Concretely. My résumé says they run in parallel. On the default path they do not. One lead manager holds them as five tools and reasons through them in sequence.

    If they ask why. The parallel branch exists and it is behind a flag that is off. I would rather correct that myself than have it found.

  6. The proposal

    What happens. The investigation produces a proposed solution, and that solution carries an action field.

    Concretely. For our case it proposes a column rename in the query and sets the action to apply.

  7. The gates

    What happens. This is the part worth pushing on, because the next step can rerun a production pipeline with nobody watching.

    Concretely. Four separate things have to agree. The screener must escalate. The action field must say apply. A router must agree. And a feature flag with a hard retry threshold must allow it.

    If they ask why. Being able to name all four is the difference between an interviewer feeling comfortable and feeling alarmed.

  8. The retrigger

    What happens. All four agree, the fix is applied, and the pipeline runs again unattended.

    Concretely. That single action is what makes every other design decision in this system matter.

  9. Its own retries

    What happens. The response reviewer catches its own errors and retries three times with exponential backoff.

    Concretely. That is sensible for a flaky model call. It is also where a small mistake turns into an expensive one, because a bad proposal gets three attempts rather than one.

  10. The asymmetry

    What happens. The screener can be wrong, and the two ways it is wrong are not equally bad.

    Concretely. A wrong retry is self-correcting, because the job simply fails again. A wrong overlook closes a real failure and nobody ever hears about it.

    If they ask why. If I were measuring one thing here it would be overlook precision, and we were not measuring it separately. The validation layer that proves a fix before applying it also defaults to off. That is the first thing I would change.

Start here — the plain version

A data platform runs thousands of scheduled jobs. Some fail every night. A human on call reads the log, works out whether it matters, and either reruns it, fixes something, or ignores it. Most of that work is repetitive, and most failures are not interesting.

This system does the first pass. It reads the error log and compares it against failures it has seen before. Then it sorts the failure into one of three buckets. Just retry it, ignore it, or this needs looking at. Only the third bucket costs anything. For that one it investigates, proposes a fix, reviews its own proposal, and can retrigger the pipeline without a person.

Pipeline
A scheduled data job. It reads from somewhere, transforms, and writes somewhere. When one fails, downstream jobs that depend on it fail too.
Triage
Deciding how much attention something deserves before spending any. The cheapest step in the system and the one that makes the rest affordable.
Vector store
A database that finds text by meaning rather than by keyword. Here it holds past incidents, so a new log can be matched against old ones that read similarly.
CrewAI
The framework this is built on. It supplies agents, tools, and a Flow, which is a state machine whose steps are decorated with @start, @listen and @router.
DSPy
A different framework, used only for the screener. It defines a typed signature of inputs and outputs, so the triage decision comes back as a named category rather than as prose to be parsed.
ReAct
A loop where a model reasons, calls a tool, reads the result, and reasons again. Sequential by nature, because each step depends on the last one's output.
Crew
A group of agents with tools, assigned to one kind of problem. There are crews for code, for files, and for documentation lookups.
Lead manager
An alternative to running crews separately. One agent holds all the specialist capabilities as tools and decides which to use. It is on by default.
Retrigger
Running the failed pipeline again, unattended, after applying a proposed fix. The action that makes every other design decision in this system matter.
Feature flag
An environment variable that turns behaviour on or off without a deploy. Several of the riskiest behaviours here sit behind one, and their defaults are worth knowing.
The technology — what each named thing is

The primer above names the parts of the debugging problem. This one names the frameworks, starting from the ground. Two of them are young enough that plenty of people say the word without being able to define it.

Every entry answers four things. What it actually is, in plain words. Where this system uses it. What it buys, meaning what goes wrong without it. And the follow-up an interviewer asks once you have said the name.

CrewAI
the framework in the bulletA Python framework for building systems where several model-driven workers cooperate. Its base unit is the Crew: a set of agents, each given a role, a goal and some tools, working through a list of tasks. You describe the team and the brief in Python, and it handles the prompting, the tool calls and the passing of one task's output into the next. In the app. One crew per fault type — SQL, Python, file and infrastructure. What it buys. Separation. Each crew's prompt, tools and permissions are scoped to one kind of failure, so the SQL specialist never sees infrastructure credentials and its instructions stay short enough to be reliable. The follow-up. A Crew is stateless and has no branching. It runs its tasks and returns a result. Everything about ordering, retries, and what happens next lives one level above it, which is the next entry.
Flow
Flow[PipelineDebuggerState]CrewAI's orchestration layer, and a genuinely different thing from a Crew. A Flow is an ordinary Python class whose methods are wired together with decorators. @start marks the entry point, @listen fires a method when a named earlier one finishes, and @router branches by returning a label. A typed state object is threaded through every step. In the app. Triage, dispatch, review, then apply or retrigger. What it buys. A state machine that is readable in one file and testable without calling a model at all. The branching lives in Python, where it can be unit tested, rather than in a prompt, where it cannot. The follow-up. Where the intelligence is. The Flow itself is deterministic. Only the crews inside it ask a model anything, and being able to point at that line is the whole answer.
Agent and Task
what a Crew is made ofAn agent is a role, a goal, a backstory and a set of tools it may use. A task is one piece of work with a description and an expected output, assigned to an agent. A crew is agents plus tasks, and that is the entire model. In the app. “Specialist crews for SQL, Python, file and infrastructure faults” is four of these, each with its own tools. What it buys. A place to put scope. Tools are attached per agent, so capability is bounded by construction rather than by instruction. The follow-up. What the role actually buys, and be honest. It is prompt text, not a capability. A named role gives the model a frame to answer within, and absolutely nothing stops it answering outside that frame. The tool list is the part with teeth.
DSPy
the other framework hereA library for programming language models instead of prompting them. Rather than writing prompt text, you declare a signature, which is a typed description of the transformation you want, and choose a module that implements it. DSPy generates the actual prompt, and an optimizer can then rewrite that prompt automatically by testing candidates against a metric and a small development set. In the app. The log screener, which has a fixed input and a fixed output type. What it buys. Prompts stop being strings people edit by hand and hope about. The declaration is version-controlled and typed, and the wording underneath can be regenerated rather than negotiated. The follow-up. Whether you actually ran an optimizer. Using the signatures for their structure and never optimizing is a perfectly legitimate answer, and a far better one than implying a tuning loop you did not run.
Signature
LogScreenerSignatureThe declaration itself. Named input fields, named output fields, and a docstring saying what the transformation is. Six lines, and not one word of prompt text. In the app. It is the short, showable artefact that names its own output type, which is the point of showing it. What it buys. The contract is visible at a glance. Anyone reading the class knows what goes in and what comes out without reading a paragraph of instructions to infer it. The follow-up. What DSPy does with it. It builds the prompt from the field names and the docstring, and parses the reply back into those fields. Which means renaming a field changes the prompt, and that is a surprising thing to discover during a rename.
ReAct
reason and actA loop rather than a single call. The model writes down a thought, chooses an action, sees the result of that action, and then goes round again with that result in view, until it decides it can answer. Reasoning and acting interleave instead of the model planning everything up front. In the app. Investigating a failure has exactly that shape. What it buys. The ability to follow evidence. You cannot know which log to read second until you have read the first, and a single-shot prompt has to guess the whole path in advance. The follow-up. The iteration cap. max_iter=10 exists because the loop has no natural end and a confused model will happily go round forever. What happens when the cap is hit is a design decision, not an error case, and you should have an answer for it.
Vector store
Chroma, via ChromadbRMA database that stores text as lists of numbers and searches by closeness rather than by matching words. Each past incident goes in as a vector, and a query returns the nearest ones. In the app. Looking up whether a failure resembles something already seen and solved. What it buys. Matching on meaning instead of wording. Two incidents describing the same root cause in entirely different words still land near each other, which keyword search would never connect. The follow-up. What is actually stored. The vector is one particular model's representation of that text. Change the embedding model and every stored vector is stale, because distances only mean anything within a single model's space. That is a migration, not a config change.
Embedding
the numbers themselvesA fixed-length list of numbers produced from a piece of text by a model, arranged so that texts with similar meaning end up close together in that space. Closeness is usually measured as cosine distance, the angle between two vectors. In the app. It is what turns “have we seen this before” from a search into a lookup. What it buys. Similarity that survives paraphrase, which is the only kind worth having when the input is a human-written error report. The follow-up. Where it fails. Two stack traces with completely different root causes can read almost identically, so nearest-neighbour retrieval hands back confident and wrong precedent. Nothing in the store flags this, so the guard has to be a distance threshold and a human check.
ThreadPoolExecutor
the parallel bitPython's built-in thread pool. You hand it callables, it hands back futures, and you collect results as they finish. The pool size caps how many run at once, which is three here. In the app. It is the actual mechanism behind the word “parallel” in the bullet. What it buys. Four crews investigating at the same time instead of one after another, so total time is roughly the slowest crew rather than the sum of all of them. The cap is what stops four simultaneous model calls becoming forty. The follow-up. The GIL, and say it before you are asked. Python threads do not execute bytecode simultaneously. What they overlap is waiting, which is all this needs, because every crew spends its time waiting on a model. Claiming true parallelism here would be wrong and easily caught.
Exponential backoff
2 ** retry_countDoubling the wait between attempts. One second, then two, then four, then eight. The idea is that a dependency which is struggling gets hit less often as it struggles more, instead of being hammered at a fixed rate by every client at once. In the app. Retriggering a pipeline that failed for an environmental reason is the whole unattended path. What it buys. Retries that help rather than finish the job off. A fixed-interval retry storm is how a recoverable outage becomes an unrecoverable one. The follow-up. Jitter. Plain doubling synchronises every retrying client onto the same instants, so they all come back together and the thundering herd survives the backoff. A real implementation randomises the wait, and naming that is the difference between having read about backoff and having run it.
Feature flag
USE_LEAD_MANAGER, ENABLE_RETRIGGER_PIPELINEA named switch, read at runtime, that changes behaviour without shipping new code. Deploy the code off, turn it on for one environment, turn it off again in seconds if it misbehaves. In the app. The autonomous half of this system is gated behind these. What it buys. It is the reason code that can retrigger a production pipeline was allowed anywhere near production. Shipping and enabling become separate decisions, and the off switch does not require a release. The follow-up. The default. A flag's default value is the real behaviour of the system, and a bullet that describes the branch nobody has ever turned on is describing something that did not happen. Know which way yours were set.

The shape: a state machine, not a conversation

It is a flow with named steps and explicit routing. Not agents chatting until they agree. You can read the whole control path in one class, which is the property that makes it debuggable.

PipelineDebuggerFlow extends Flow[PipelineDebuggerState]. Steps are decorated. @start loads the workflow data. @listen(start_flow) runs the screener. @router(screener) reads the screener's category and returns a branch name.

That matters for the same reason chapter 0001's orchestrator matters. The routing decisions are in one file, in order, and typed. A multi-agent system where agents decide what happens next has no such file, and no way to answer “why did it do that?”

Plain meaningThere is a flowchart, and it is written down. The agents do work inside the boxes. They do not draw the arrows.

The triage, which is the real idea

Three categories, and two of them cost almost nothing. Retry it, ignore it, or investigate it. Everything expensive sits behind that third branch.

The screener is a DSPy ReAct module over a LogScreenerSignature. It takes the logs, the node configuration, and context retrieved from a ChromaDB collection of known_issues at k=5. It returns an investigation, a resolution, a resolution_category, and a confidence.

The category is a typed literal with exactly three values. RETRY for transient faults: timeouts, auth blips, connection resets. OVERLOOK for things outside our control, like a file that was never going to arrive. INVESTIGATE for everything that actually needs work.

Say the economics out loud, because it is the part that shows judgment. If most nightly failures are transient and a large model investigation costs real money and minutes, then the screener is what makes the system deployable at all.

Plain meaningBefore calling the expensive specialist, ask a cheap question: is this worth anyone's time? Usually it is not.

The word in the résumé that needs correcting

The bullet says the specialists run in parallel. In the default configuration they do not. One agent holds them as tools and works through them in sequence. The parallel path exists and is not the default.

USE_LEAD_MANAGER defaults to true. On that path, LeadManagerCrew is a single agent with five tools: past incidents, file debugging, code debugging, workflow lineage, and infrastructure. It runs with reasoning=True and max_iter=10. A ReAct loop is sequential by construction, because each tool call is chosen after reading the previous result.

Only when the flag is off does the dispatcher use a ThreadPoolExecutor(max_workers=3) over the confluence, code and file crews. That branch is genuinely parallel, and it covers three of the four fault types — infrastructure is reached through the lead manager.

The correction to make, unprompted: the specialists are tools on one reasoning agent by default, and there is a parallel branch behind a flag. That sentence is more impressive than the résumé's, because it shows you know which branch is live.

Plain meaningOne investigator with five instruments, used one at a time. Not four investigators working at once. There is a mode that does that, and it is switched off.

What stands between a model's opinion and production

The system can rerun a production pipeline on its own. Four separate things have to agree before that happens, and every one of them is worth being able to name.

First, the screener has to route to INVESTIGATE. Second, the investigation has to produce a PipelineDebugSolution whose action is APPLY_RESOLUTION rather than MANUAL_INTERVENTION_REQUIRED. Third, action_router has to read that recommendation and return TRIGGER_RETRY. Fourth, ENABLE_RETRIGGER_PIPELINE has to be on, and RETRIGGER_PIPELINE_THRESHOLD bounds how many times.

The output model is typed, which is the same lesson as chapter 0001's grounding. The action is a literal with two values, and confidence is a float bounded between zero and one. A model cannot return “probably fine, go ahead” because the schema has no shape for it.

Plain meaningFour locks between a suggestion and a real rerun, and one of them is a switch an operator can flip.

Where it retries itself, and why that is the weak spot

The response reviewer catches its own errors and retries three times, with exponential backoff. That is sensible for a flaky model call. It is also the place where a small mistake becomes an expensive one.

response_reviewer wraps its crew call in a try block. On failure it increments a counter, sleeps 2 ** retry_count, and calls itself again, up to three attempts. That is a recursive retry, not a loop, and the distinction matters when you talk about it.

It is the right behaviour for a transient LiteLLM error. The thing to say before being asked is that a retry which re-runs a synthesis crew is not cheap, and that three attempts at up to four seconds of sleep sits inside whatever deadline the caller has. If nothing above it enforces a ceiling, the ladder is the deadline.

Plain meaningIf the summariser fails, try it again a few times, waiting longer each time. Just know what three attempts costs before promising a response time.

Every noun in the bullet, defined out loud, from the ground up. CrewAI and DSPy are both recent, and an interviewer who has used neither will ask you to define them before letting you argue about them. Each answer says what the thing is, what it does here, and what you would lose without it.

  1. What is CrewAI, and what is a Crew made of?

    CrewAI is a Python framework for building systems where several model-driven workers cooperate. A Crew is a set of agents and a set of tasks. Each agent has a role, a goal and tools it may use. Each task has a description, an expected output and an owner. You describe the team and the brief in Python. It handles the prompting, the tool calls, and the passing of one task's output into the next. What that buys here is separation. Each crew's prompt, tools and permissions are scoped to one kind of failure. The SQL specialist never sees infrastructure credentials, and its instructions stay short enough to be reliable. A Crew holds no state between runs and has no branching of its own.

    Red flagDescribing a Crew as the whole system. It is the worker. Everything about ordering and retries sits above it.

  2. What is a Flow, and why is it not just a bigger Crew?

    A Flow is CrewAI's orchestration layer, and a genuinely different thing. It is an ordinary Python class whose methods are wired together by decorators. Start marks the entry point, listen fires a method when a named earlier one finishes, and router branches by returning a label. A typed state object is threaded through every step. What that buys is a state machine you can read in one file and test without calling a model at all. The branching lives in Python, where it can be unit tested, rather than in a prompt, where it cannot. The Flow is deterministic code. Only the crews inside it ask a model anything, and being able to point at that line is the whole answer.

    Red flagImplying the model chooses the route. The router is a Python function reading state, and that is the reason the path is reproducible.

  3. What is DSPy, and what does a signature give you?

    DSPy lets you program a model instead of prompting it. Rather than writing prompt text, you declare a signature. That is named input fields, named output fields, and a line saying what the transformation is. A module implements that signature with a technique such as ReAct. DSPy then generates the actual prompt from the declaration. What it buys is prompts that stop being strings people edit by hand and hope about. The declaration is typed and version-controlled, and the wording underneath can be regenerated rather than argued over. An optimizer can go further and rewrite that prompt by testing candidates against a metric. Using the signatures without ever running an optimizer is a perfectly fair answer.

    Red flagImplying you compiled and optimized prompts if you did not. The declaration alone is worth having, and claiming the optimizer invites a question about the dev set.

  4. What is ReAct?

    A loop rather than a single call. The model writes down a thought, picks an action, and sees the result. Then it goes round again with that result in view, until it can answer. Reasoning and acting interleave instead of the model planning everything up front. What that buys is the ability to follow evidence. You cannot know which log to read second until you have read the first. A single-shot prompt has to guess the whole path in advance. The part worth naming is the iteration cap. The loop has no natural end and a confused model will go round forever. What happens when it runs out is a decision you made.

    Red flagCalling it a prompting style. It is a control loop with a budget, and the budget is the part that reaches production.

  5. What is a vector store, and what is actually stored in it?

    Embeddings. A model reads a piece of text and outputs a fixed-length list of numbers, placed so that texts meaning similar things land close together. Each past incident goes in as one of those. Retrieval is nearest neighbour, usually by cosine distance, rather than keyword match. What that buys is matching on meaning instead of wording. Two incidents describing the same root cause in entirely different words still land near each other, which keyword search would never connect. On human-written error reports that is the only kind of similarity worth having. The catch is that vectors are only comparable within one embedding model. Changing the model makes every stored vector meaningless, so it is a migration rather than a config change.

    Red flag“It searches semantically” with nothing behind it. Say what is stored, how distance is measured, and what makes the distance meaningless.

  6. You said crews run in parallel. What does a thread pool actually give you in Python?

    Overlapped waiting, not overlapped computation. A thread pool takes callables and hands back futures, with the pool size capping how many run at once. The GIL means two threads never run Python bytecode at the same instant. It is released around blocking calls, so three crews waiting on model responses do overlap. What that buys is a total time close to the slowest crew rather than the sum of all of them. The cap is what stops four simultaneous model calls becoming forty. That is the whole benefit here, and it is enough, because none of the work is CPU-bound. Say it before the interviewer says it to you.

    Red flagSaying “in parallel” and meaning cores. With threads in Python you get concurrency. Claiming parallelism invites the GIL question and you will lose it.

  7. What is exponential backoff, and what is missing from doubling alone?

    Backoff doubles the wait after each failure. One second, then two, then four, then eight. The idea is that a struggling dependency gets hit less often as it struggles more. Otherwise every client hammers it at a fixed rate at once. What that buys is retries that help instead of finishing the job off. A fixed-interval retry storm is how a recoverable outage becomes an unrecoverable one. What doubling alone lacks is jitter. Every client that failed at the same moment retries at the same moment. The pattern repeats at each step, so the herd survives the backoff. A real implementation randomises within the window. It also needs a ceiling and a give-up point.

    Red flagStopping at “we retry with backoff.” Jitter and a cap are the two follow-ups, and naming them unprompted is what separates read-about from run-in-production.

    Because the control path has to be readable. PipelineDebuggerFlow has decorated steps and explicit routers, so you can read what happens next in one file. A system where agents decide the sequence cannot answer why it did something, and this one can retrigger production.

    Red flag“That is how CrewAI works.” Flows are one option in CrewAI and crews talking is another. It was a choice.

  3. What are the three triage categories?

    RETRY, OVERLOOK and INVESTIGATE. Retry is for transient faults like timeouts and connection resets. Overlook is for things outside our control, such as a file that never arrived. Investigate is everything else, and it is the only branch that costs real money.

    Red flagDescribing it as classification. It is admission control, and saying so frames the whole system correctly.

  4. What is in the vector store?

    Past incidents and known issues, in ChromaDB collections. The screener retrieves the top five most similar entries and puts them in context before deciding. So the triage decision is informed by what happened last time a log looked like this one.

    Red flagCalling it RAG and stopping. Name what is retrieved and what it is used for, because the retrieval here feeds a routing decision rather than an answer.

  5. Why is the screener written in DSPy when everything else is CrewAI?

    Because the screener's output is a decision, not prose. A DSPy signature declares typed fields, so resolution_category comes back as one of three literals with a confidence float. There is no parsing step and no chance of a fourth category appearing. For a routing decision that is worth a second framework.

    Red flagSaying it was inherited. Two frameworks in one service needs a reason, and this one has a good one.

  6. What is a crew, concretely?

    A set of agents with tools and tasks, pointed at one kind of problem, run by a process. There are crews for code debugging, file issues and documentation lookups, plus a review crew that synthesises everything. Each one is a bundle of capability, not a personality.

    Red flagAnthropomorphising. “The SQL expert talks to the file expert” is how people describe systems they have not read.

  7. The bullet says the specialists run in parallel. Do they?

    Not on the default path, and I would correct that myself. USE_LEAD_MANAGER defaults to true. On that path one agent holds the specialists as five tools and works through them in a ReAct loop, which is sequential. There is a genuinely parallel branch behind the flag, using three worker threads.

    Red flagDefending the word “parallel.” One question about the dispatcher exposes it, and volunteering the correction costs nothing.

  8. What is this system actually allowed to do to production?

    Retrigger a failed pipeline, with a resolution applied, unattended. That is the strongest permission it has. It sits behind four gates. The screener has to route to investigate. The solution's action field has to say apply. The action router has to agree. And a feature flag with a retry threshold has to allow it.

    Red flagUnderselling it. If you describe it as advisory, the interviewer reads the bullet's word “unattended” and stops believing the rest.

  9. What does the investigation return?

    A typed PipelineDebugSolution. It carries the investigation text and a step-by-step resolution. It also carries an action that is either apply or manual intervention required. Then optional corrected code with its type, and a confidence bounded between zero and one. The action being a two-value literal is the part that matters.

    Red flagSaying it returns a recommendation. The shape is the safety property, in the same way the claim schema was in chapter 0001.

  10. What is the riskiest claim in this bullet?

    The word “parallel,” because the default configuration is sequential. The second riskiest is “infrastructure,” since infra is reached as a tool on the lead manager rather than as its own crew. Both are one question deep, so I would say them before being asked.

    Red flagNaming the autonomy as the risk. Autonomy is the impressive part and it is well gated. The wording is what will not survive contact.

Deep dive

The autonomy questions are the ones that decide this round. An interviewer is working out whether you understood what you were allowed to build.

  1. Walk me through the flow from failure to retrigger.

    Start loads the workflow data. The screener classifies. A router branches on the category. Investigate dispatches the lead manager or the parallel crews. Response review synthesises into a typed solution. An action router reads the recommendation. If it says apply, trigger retry calls retrigger_pipeline with the resolution attached.

    Red flagSkipping the routers. They are where the decisions live, and naming them shows you have read the control path rather than the README.

  2. Why put triage in front at all? Why not investigate everything?

    Cost and latency. A full investigation is a large-model reasoning loop with up to ten tool calls. Most nightly failures are timeouts and missing files. If every one of those triggered an investigation, the system would be too slow and too expensive. It would be turned off, which means it would not exist.

    Red flagFraming it as accuracy. It is admission control, and the honest reason is that the expensive path has to be rare.

  3. The retrieval feeds a routing decision rather than an answer. Why does that distinction matter?

    Because the failure modes are different. In normal retrieval, a bad chunk gives a worse answer. Here a bad chunk changes which branch runs. A misleading similar incident can turn an investigate into a retry, and the pipeline reruns and fails again with nobody looking. Retrieval quality becomes a control-flow property.

    Red flagTreating this as ordinary RAG. The consequence of a bad retrieval here is a wrong action, not a wrong sentence.

  4. Why k equals five, and what would you change it to?

    Five is a chosen default and I would say so. The tradeoff is real though. Too few and a genuinely known issue is missed. Too many and unrelated incidents dilute the context and pull the category around. What I would actually do is measure category stability as k varies, because that is the number that matters here.

    Red flagJustifying five after the fact. An unexamined k is normal and admitting it, then naming the experiment, is the stronger answer.

  5. Lead manager or separate crews. Which is better and why is the flag defaulted where it is?

    They optimise different things. The lead manager reasons across tools, so it can use a file finding to direct a code lookup. Separate crews are faster because they run together, but they cannot see each other's findings. Defaulting to the manager trades latency for the ability to follow a thread.

    Red flagSaying parallel is simply better. Parallel loses cross-tool reasoning, and knowing what you gave up is the point.

  6. Name everything between a model's opinion and a production rerun.

    Four things. The screener has to route to investigate. The solution's action field has to say apply rather than manual intervention required. The action router has to agree and return trigger retry. And ENABLE_RETRIGGER_PIPELINE has to be on, with a threshold bounding how many retriggers are allowed.

    Red flagNot having the list ready. This is the question the autonomy claim exists to invite, and hesitating here undoes the whole bullet.

  7. The response reviewer retries itself. Talk me through that.

    It wraps the crew call in a try block. On a model error it increments a counter and sleeps two to the power of that count. Then it calls itself again, to a maximum of three attempts. It is recursion rather than a loop. That is fine at three, and a higher bound would grow the stack.

    Red flagNot costing it. Three attempts with one, two and four second sleeps is seven seconds of sleep plus three synthesis runs, and that sits inside somebody's deadline.

  8. Both the screener and the solution return a confidence. What do you do with it?

    Honestly, less than we should. It is captured and available for thresholding but the routing is on category rather than on confidence. The obvious improvement is to require a minimum confidence before an autonomous retrigger, so a hesitant apply becomes a manual intervention instead of an action.

    Red flagClaiming it gates behaviour. If it does not, saying so and naming the improvement is better than being caught.

  9. The screener says RETRY and it is wrong. What happens?

    The pipeline reruns and fails the same way. That is mostly self-limiting, because a real fault does not fix itself, and the retrigger threshold bounds how many times. The genuine cost is delay: a real problem looks like a flaky one for another cycle, and nobody is paged in the meantime.

    Red flagCalling it harmless. It is the cheaper of the two wrong answers, and it still burns a scheduling window.

  10. And a wrong OVERLOOK?

    That one is worse, and I would volunteer it. Overlook closes the failure with no action and no rerun. A real fault classified as beyond our control simply disappears, and downstream jobs fail for reasons nobody connects back. Retry is self-correcting and overlook is not, so overlook is where I would want precision measured.

    Red flagTreating the three categories as equally risky. They are not, and knowing which one silently loses information is the senior observation.

  11. Tell me about the feature flags and their defaults.

    Three matter. USE_LEAD_MANAGER defaults true, which is why the default path is sequential. ENABLE_RETRIGGER_PIPELINE defaults true, so the autonomous action is on. And ENABLE_PIPELINE_VALIDATIONS defaults false, which is the one I would raise myself in any conversation about safety.

    Red flagNot knowing the defaults. A flag whose default you cannot state is a behaviour you do not control.

  12. How would you measure whether this system is working?

    Per category, not overall. Overlook precision, because a wrong overlook loses a real failure. Retrigger success rate, meaning the share of autonomous reruns that then pass. And the fraction of investigations a human later disagreed with. A single accuracy number across all three categories would hide the only one that matters.

    Red flagProposing one overall accuracy figure. The categories have different costs, so they need different metrics.

The screener classifies a failure as RETRY. What happens next?

  1. The flow retries it without dispatching any debugging crew
  2. A lead manager investigates using all five available tools
  3. Three specialist crews run in parallel against the logs
  4. The failure is recorded and the flow completes silently

The router returns RETRY and the expensive branch is never entered. That is the point of the triage: transient faults are the common case and they must not cost an investigation.

Completing silently is what OVERLOOK does, and the difference matters. A wrong RETRY is mostly self-correcting because the job fails again. A wrong OVERLOOK closes the incident and loses it.

With USE_LEAD_MANAGER at its default value, how do the specialist capabilities run?

  1. Sequentially, as tools inside one single reasoning loop
  2. In parallel, across a pool of independent threads
  3. Sequentially, but only after the screener has escalated
  4. In parallel, with one crew per separate fault

The flag defaults to true, so one agent holds past incidents, file, code, lineage and infra as five tools and works through them in a ReAct loop. A ReAct loop is sequential by construction, because each tool is chosen after reading the last result.

The parallel option is real but it is the other branch, and it uses three worker threads over confluence, code and file. The résumé says parallel, which describes the branch that is switched off.

Edges and exceptions

Autonomy invites hard questions and you want them, because the gating is genuinely good. The wording is the soft part, not the design.

  • A fix that makes it worse
  • Retrigger loops
  • A novel failure
  • Poisoned incident history
  • Two failures, same root cause
  • The vector store is down
  • Who is accountable
  • What you would change

  1. The system applies a fix that makes things worse. What stops that?

    Less than I would like, and that is the honest answer. The action field and the feature flag gate whether a fix is applied at all. What is missing is a validation layer proving the fix before it runs, and ENABLE_PIPELINE_VALIDATIONS defaults to false. Chapter 0006 is about that layer, and its default is the thing to know.

    Red flagClaiming validation always runs. The flag default says otherwise, and an interviewer who reads config will find it.

  2. What stops an infinite retrigger loop?

    RETRIGGER_PIPELINE_THRESHOLD, which defaults to one. So a failure gets one autonomous rerun and then stops being eligible. That is a blunt instrument and the right kind of blunt. A counter that a model cannot reason its way past is worth more here than a smarter rule.

    Red flagDescribing a clever adaptive policy. For an autonomous production action, the boring hard limit is the feature.

  3. A failure arrives that looks like nothing in the store. What happens?

    The screener retrieves five loosely similar incidents and still has to return a category. That is the uncomfortable case, because the retrieval is unconditional. There is no “nothing matched” branch. The safe design would be a similarity floor below which it routes to investigate by default, and that is not there.

    Red flagAssuming a low-similarity result is ignored. Top-k always returns k, and knowing that about your own retriever is the answer.

  4. Somebody resolves an incident incorrectly and it goes into the store. What then?

    It becomes evidence. The store is built from past incidents and their resolutions, so a wrong resolution teaches the screener to make the same mistake on similar logs. That is a data quality problem with a control-flow consequence, and it argues for the store being curated rather than appended to automatically.

    Red flagTreating the incident history as ground truth. People wrote it, under time pressure, at night.

  5. Twenty pipelines fail at once from one upstream outage. What does the system do?

    Twenty independent investigations, because nothing correlates them. Each one sees its own log and reaches its own conclusion, and they will mostly agree, expensively. The right shape is to cluster failures within a window before triage, and that does not exist. It is the change I would make first at scale.

    Red flagSaying the screener would catch it. The screener sees one log at a time and has no notion of a concurrent storm.

  6. ChromaDB is unavailable when a failure arrives.

    The screener loses its context and has to decide from the log alone. The important question is whether that degrades to investigate or to something cheaper. Failing towards investigate is the safe default, because it costs money rather than losing a failure. I would want that to be explicit rather than emergent.

    Red flagNot having a view. Every dependency has a failure behaviour, and the interviewer is asking which direction yours fails in.

  7. The system retriggers a pipeline at 3am and it corrupts a table. Who is accountable?

    The team that turned the flag on, and that is the correct answer rather than a deflection. The design makes it a deliberate decision. An operator sets ENABLE_RETRIGGER_PIPELINE and a threshold. What I would add before any post-mortem is an audit record. It should tie every autonomous action to the category, the solution and the confidence.

    Red flagBlaming the model. Autonomy is a configuration choice a human made, and saying so is what makes the design defensible.

  8. What would you change first?

    Turn the validation flag on and make it required before any autonomous apply. Then add a similarity floor to the screener so an unfamiliar failure routes to investigate rather than guessing. Third, cluster concurrent failures before triage. The first one is a config change with a real safety payoff.

    Red flagReaching for a better model. Everything limiting this system is a gate that is off or a policy that is missing.

Probes to expect

  1. “What stops this from breaking production?” The question every autonomous system gets. The gating here is genuinely good, so the only way to lose is to be vague about it.
    Model answer — say yours first

    Four gates, in order. The screener has to route to investigate rather than retry or overlook. The solution has to come back with its action field set to apply rather than manual intervention required. The action router has to agree. And a feature flag has to be on, with a threshold that defaults to a single retrigger per failure. I would also tell you what is missing: a validation layer exists and its flag defaults to off.

  2. “In parallel? Walk me through the dispatcher.” If the interviewer is technical they will ask this, and the résumé's wording does not survive it. Volunteer the correction before the question arrives.
    Model answer — say yours first

    I would correct my own wording there. The dispatcher branches on USE_LEAD_MANAGER, which defaults to true. On that path it is one agent with five tools, reasoning across them in sequence, capped at ten iterations. The other branch uses a three-worker thread pool over confluence, code and file, which is genuinely parallel, and it is not the default. Infrastructure is a tool rather than a crew in either case.

  3. “Which of your three categories is the dangerous one?” A good question, and the answer reveals whether you have thought about asymmetric error costs or just built a classifier.
    Model answer — say yours first

    Overlook. A wrong retry is largely self-correcting, because the job runs again and fails again, and the threshold bounds it. A wrong overlook closes the incident with no action and no rerun, so a real failure disappears and downstream jobs break for reasons nobody connects back to it. If I could measure one thing about this system it would be overlook precision.

  4. “Your retriever always returns five results. What if nothing is actually similar?” Tests whether you know how top-k behaves. Most candidates assume a relevance filter that is not there.
    Model answer — say yours first

    Then it returns the five least dissimilar things, and the screener still has to choose a category. There is no similarity floor and no nothing-matched branch, which is a real gap. The fix I would want is a distance threshold below which it routes to investigate by default, so an unfamiliar failure fails towards spending money rather than towards silence.

  5. “Twenty pipelines fail at once. What does your system do?” A scale question disguised as a correctness question. The honest answer names a missing feature.
    Model answer — say yours first

    Twenty independent investigations, because nothing correlates them. Each sees only its own log. They will mostly reach the same conclusion at twenty times the cost, and twenty retriggers may hit an upstream that is still down. The shape I would add is clustering failures inside a time window before triage, so one investigation covers the incident and the rest reference it.

The screener is a cheap gate in front of an expensive path, and the expensive path can be triggered many times at once. Which System Design School lesson names that pattern, and what is the number you should be able to give?

Lesson 0001's discipline. The investigation path is a large-model loop capped at ten tool calls, plus a review step that can retry itself three times with exponential sleeps. The worst case of that chain, summed, is the number to have ready. If nothing above it enforces a ceiling then the chain is the deadline, and here nothing above it does.
