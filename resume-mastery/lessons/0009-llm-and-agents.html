The sentence that sounds fluent and gets you caught

“I've built multi-agent systems with autonomous agents collaborating.” The word collaborating is the problem. It invites “so how does one agent know what another found?” and the honest answer is that they do not, because they never talk. That restriction is your best design decision and this sentence hides it.

The other trap is “the agent calls the tool.” It does not. It emits a request and your code decides. The distinction sounds pedantic and it is the entire security model, so an interviewer testing for depth will hear which version you used.

Walk them through it · one tool call, end to end

The say it out loud block is ninety seconds. This is the ten minutes after that, when they say “walk me through it.” One trip round an agent loop, followed from the model's first note to the answer. Then the boundary that matters more than the loop does.

The picture. Somebody very well read, locked in a room with a letterbox. They cannot look anything up and cannot do anything at all. They can write a note asking for one specific thing, and you slide the answer back through the slot. That loop is the whole of what people call an agent.

The case. A vendor has claimed something during an interview and the Scout needs to check it. Follow one round of the loop, then look at what is deliberately not allowed to happen.

  1. The model alone

    What happens. A language model produces text. That is the entire capability and everything else is built on top of it.

    Concretely. It cannot search, read a database, or call an API. Left by itself it can only write something that looks like an answer.

    What happens. We hand it a list of functions it is allowed to ask for, each with typed parameters.

    Concretely. One of them is a web search taking a query string. The model does not run it. It returns a request to run it.

    What happens. The model replies with a request to call search, and the query it wants.

    Concretely. My code is what executes it. The model never touches the network, and that is the security property rather than a detail of plumbing.

Start here — the plain version

A language model produces text. That is all it does. Everything called an agent is that one capability wrapped in a loop. The text can ask your code to do something and get an answer back.

The interesting engineering is never the model. It is the boundary around it: what the model is allowed to decide, what your code decides, and who is allowed to call whom. Most of this chapter is about that boundary, because it is what an interviewer is really testing.

Agent
A loop where a model is given tools, chooses one, sees the result, and chooses again. Without a loop and tools it is a prompt, not an agent.
Function calling
Giving the model a list of functions with typed parameters. It returns a request to call one. Your code executes it and hands back the result.
Tool
One such function. The description is part of the interface, because the description is how the model decides whether to reach for it.
ReAct
Reason, act, observe, repeat. The most common agent loop shape. Sequential by construction, because each action depends on the previous observation.
Orchestration
One component deciding the order of work. The opposite is choreography, where each component reacts to events and no single place holds the sequence.
Google ADK
An agent framework. Supplies agent types, a loop, session state, and hooks that run before or after a tool.
MCP
Model Context Protocol. A standard way to expose tools and data to a model, so a capability is described once rather than re-wrapped per framework.
Semantic routing
Choosing a branch by meaning rather than by keyword. A router reads an input and returns which path it belongs on.
MemGPT
A pattern where a model manages its own memory in tiers, paging things between its limited context and an external store.
Structured output
Forcing the reply into a schema. The safety property is that the schema has no shape for the answer you do not want.
The technology — what each named thing is

The primer above defines the patterns on this line. This one defines the models at the end of it, starting from the ground, along with the handful of knobs every one of them shares. Naming four families invites the question of what actually separates them.

Every entry answers four things. What it actually is, in plain words. Where it shows up in this work. What it buys, meaning what goes wrong without it. And the follow-up an interviewer asks once you have said the name.

Gemini
GoogleGoogle's family of large language models. Closed-weight, which means the parameters are never published and the only way to use it is to send text to Google's API and get text back. It comes in tiers that trade cost and speed against reasoning ability, and it carries a very long context window. Reached through the Google GenAI SDK, and also through an OpenAI-compatible shim. In the app. It is the model behind four of the systems on this résumé. What it buys. Native structured output, a long context, and tight integration with the rest of the Google stack these projects already run on. The follow-up. Which tier, and why. A pipeline with a retry loop multiplies its model calls, so tier choice is a cost decision you should be able to put an actual number against rather than a preference.
GPT
OpenAIOpenAI's model family, also closed-weight and API-only. Its lasting significance is less the models than the interface: the shape of its chat-completions request and response became the default that everyone else imitates, so an enormous amount of software speaks that shape regardless of which model is actually behind it. In the app. The gateway in chapter 0002 is OpenAI-compatible, which is a statement about this wire format and nothing else. What it buys. Portability. Serving that shape means every existing client library, evaluation harness and internal tool works against you unchanged. The follow-up. Compatible is not the same as used, and the two sound almost identical said out loud. Be explicit about which one you mean before an interviewer assumes the other.
Claude
AnthropicAnthropic's model family. Closed-weight and API-only, like the two above. It is known for long-context work and for tool use inside agent loops, and it is where the Model Context Protocol in the primer above originated. In the app. It is the third of the frontier API families, and a résumé line naming models is expected to be able to place all of them. What it buys. Knowing the landscape rather than one vendor, which is what a skills line is really claiming. The follow-up. Where you have actually used it, and if the honest answer is nowhere, say so plainly. A skills line naming four families with three untouched is a thing to correct on the page before the room, not during it.
Llama
Meta, open weightsMeta's model family, and the odd one out here. The parameters are published, so you can download them and run the model on your own hardware. That changes every deployment question at once. There is no per-token bill, no data leaving your network, and no dependency on somebody else's uptime. In exchange, the serving cost, the GPUs and the operations are all yours. In the app. It is the open-weight member of the list and the foundation the on-device work depends on. What it buys. The option to run offline, on a phone, or inside a network that forbids sending data out. No API-only model can do those at all. The follow-up. Open weights is not open source. You get the parameters under a licence with conditions attached. You do not get the training data, the training code, or an unrestricted right to do as you like with the result.
Context window
the working memoryThe total number of tokens the model can look at in one go, counting the prompt and the reply together. Anything outside it does not exist as far as the model is concerned. Frontier families now reach roughly a million tokens, which is a large book. In the app. Every retrieval design on this résumé exists because this number is finite. What it buys. A hard, checkable limit to design against. You can measure your prompt and know in advance whether it fits, rather than discovering truncation in production. The follow-up. Big is not free, and this is the trap. Cost and time-to-first-token both rise with what you send, attention quality sags in the middle of a very long context, and a large window is not a reason to stop retrieving.
Token
the unit of everythingModels do not see letters or words. Text is first cut into tokens, each roughly three quarters of an English word, and each token becomes a number. Output is generated one token at a time. Context is counted in tokens and billing is per thousand or per million of them. In the app. Every cost and latency answer on this line is denominated in them. What it buys. A single unit that makes cost, speed and context capacity all comparable and predictable before you run anything. The follow-up. Input and output are priced differently, with output usually several times dearer. So a verbose response format costs more than a terse one carrying exactly the same information, and that is a real lever on a bill.
Temperature
and the other sampling knobsAt each step the model produces a probability for every possible next token, and something has to choose one. Temperature controls how much that choice is allowed to wander. Near zero it almost always takes the most likely token. Higher values flatten the distribution and let unlikely tokens through. Top-p and top-k are different ways of cutting off the candidate list before sampling. In the app. Extraction, routing and scoring all want the low end. What it buys. One dial that moves output between reliable and varied, which are genuinely different jobs. The follow-up. Zero is not deterministic. Batch composition, hardware and floating-point ordering still shift the result, so reproducibility comes from recording outputs, never from a setting.
System prompt
the standing instructionText placed at the very front of the conversation that sets the model's role, its rules and its output format. It is marked differently from user turns and weighted more heavily, but underneath it is still just text sitting in the same context window. In the app. It is where agent roles, tool policies and output rules live in every agentic project here. What it buys. Behaviour set once instead of repeated in every request, and a single place to change it. The follow-up. It is not a security boundary, and this is the important part. Content that arrives later in the context can argue with it and sometimes win. That is the prompt-injection problem from chapter 0006, stated from the other side.
Fine-tuning
against prompting and retrievalContinuing to train the model on your own examples so that the weights themselves change. Full fine-tuning updates every parameter and is expensive. LoRA is the cheap standard: freeze the original weights and train small added matrices alongside them, which is a fraction of the cost and produces a small file rather than a new model. In the app. It is the third option whenever a model is not doing what you want. What it buys. Behaviour and format that stick without being restated in every prompt, and a shorter prompt as a result. The follow-up. The order to try them in. Prompting changes instructions. Retrieval changes available facts. Fine-tuning changes behaviour and style. Reaching for fine-tuning to fix a knowledge gap is the classic wrong answer, because the model will learn the shape of your facts without learning the facts.
Structured output
the feature under all of itSupplying a schema with the request so that generation is constrained to match it. The decoder is restricted rather than the model being asked nicely, so a reply that does not parse cannot be produced. Every family here supports some version of it under a different name. In the app. Every routing, extraction and scoring claim on this résumé depends on a parse that cannot fail. What it buys. The whole retry-on-bad-JSON layer disappears, along with its latency and its cost. The follow-up. Shape is not truth, and support is uneven between providers. A schema feature a provider only partly honours fails when you call it rather than when you write it, which is why the deterministic checks downstream are not optional.

What an agent actually is

A model, a list of tools, and a loop. The model proposes a call, your code runs it, the result goes back in, and it goes round again. Everything else is naming.

Be able to say this plainly, because vagueness here is the most common way to lose a senior LLM interview. The model never executes anything. It emits a request to call a named function with arguments, and it is your process that decides whether to honour that.

That last point is the whole security model. A tool is not something the model has. It is something you offer, and the offer is revocable, checkable and loggable on every single call.

Plain meaningThe model can ask for things. It cannot take them. Everything it asks for goes through code you wrote.

The boundary worth defending

The best answer about multi-agent systems on this résumé is a restriction, not a capability. Agents never call each other. One file composes them, and that is the only reason a deadline has one home.

The vendor-evaluation pipeline has three agents and a single orchestrator module. The Scout, the Evaluator and the Coordinator are functions taking inputs and returning values. None of them knows the others exist.

Say why, because the reasons are the answer. One readable control flow. One place to put a deadline. The ability to test a stage alone. With agents calling agents, a Scout timeout becomes an Evaluator problem and no file tells you which stage owns the budget.

The same shape appears twice more. Chapter 0003's ten sub-agents sit inside one ADK LoopAgent that sequences them. Chapter 0005's debugger is a Flow with decorated steps and explicit routers. In all three, the sequence is written down rather than negotiated.

Plain meaningThere is a conductor and there are musicians. The musicians never take cues from each other, which is why anyone can read the score.

Where each named thing is actually evidenced

Six of the ten items have a specific project behind them. Two models are named that appear nowhere. Knowing which is which is the difference between a list and a claim.

Google ADK is the strongest. Chapter 0003's retry loop is an ADK LoopAgent over ten sub-agents, exiting through EventActions.escalate. Chapter 0004 is a two-stage SequentialAgent with a before_tool_callback used as a precondition. That is framework knowledge at the level of its hooks, not its README.

MCP appears in three conditional sub-agents in chapter 0003: StatVar discovery, a spot check and error resolution. All three are optional, so the pipeline runs without them. That is worth stating accurately.

Function calling and multi-agent orchestration run through everything. Semantic routing is the DSPy screener in chapter 0005, which retrieves similar incidents and returns one of three typed categories. MemGPT is the Samsung dementia companion in chapter 0015.

Gemini is everywhere at CloudSufi. Claude is the model behind the pipeline debugger's crews. GPT is the weak one: what the gateway implements is OpenAI's API shape, not OpenAI's models. And Llama has nothing behind it at all.

Plain meaningMost of the list is real work. One model name describes a format rather than a model, and one is simply not there.

Semantic routing, and why it is riskier than it looks

Routing by meaning is retrieval with a consequence. An ordinary bad retrieval gives a worse answer. A bad routing decision sends the request down the wrong branch entirely.

The screener in chapter 0005 is the clean example. It embeds the error log, pulls the five most similar past incidents, and returns RETRY, OVERLOOK or INVESTIGATE as a typed literal with a confidence.

Two design choices there are worth naming. The output is a literal with exactly three values, so no fourth category can appear and nothing has to be parsed out of prose. And the retrieval is unconditional top-k, so it always returns five things even when nothing is actually similar.

That second one is the real risk. A routing decision built on five loosely related incidents is still a confident decision. The fix is a similarity floor below which it routes to the expensive branch by default, which is the safe direction.

Plain meaningIf the router is wrong, the request does not get a worse answer. It gets a different journey.

Choosing a model, and pinning it

Two model decisions appear across these systems. Pick the tier by what the step is for. And name the exact version, because an alias is a dependency that can change under you.

The tier choice is visible in chapter 0001. Scoring runs on the pro-tier model, because the interview is over and nobody is waiting, so better judgment is worth buying. Latency-sensitive paths use faster tiers.

The pinning lesson came the hard way, in chapter 0002. Model aliases plus a substring test meant every turn was diagnosed as an outage and silently retried on a fallback. Four days, 236 warnings, every request returning success.

Chapter 0004 shows the fix applied elsewhere: the lineage agent reads its model from a LINEAGE_MODEL variable defaulting to a named version. A pinned version fails loudly when it disappears. An alias fails quietly when it moves.

Plain meaningBuy the expensive model where judgment matters and nobody is waiting. And always say exactly which one, not “the latest.”

  1. You list Gemini, GPT, Claude and Llama. What actually separates them?

    Three are closed weights behind an API. The parameters are never published, and the only way to use them is to send text to somebody's server. Llama is open weights. You download the parameters and run the model on your own hardware. That difference changes an architecture rather than a preference. It decides whether data leaves your network. It decides whether you pay per token or per GPU hour. It decides whether the system can work offline or inside a network that forbids sending data out. Capability rankings move every few months. The deployment property does not, so lead with it.

    Red flagRanking them by benchmark. The ranking will be stale before the offer letter, and it tells the interviewer nothing about how you would choose.

  2. What does “open weights” mean, and how is it not open source?

    A model is billions of numbers learned during training. Open weights means those numbers are published, so you can download them and run the model yourself. What that buys is the option to run offline, on your own GPUs, or inside a network that forbids outbound calls. No API-only model can do those at all. What you do not get is the training data, the training code, or an unrestricted licence. Most of these come with conditions on scale and on use. So it buys self-hosting and privacy. It does not buy the ability to rebuild the model or fully audit what went into it.

    Red flagUsing open source and open weights interchangeably. The distinction is a licensing fact, and legal teams in regulated industries ask about it first.

  3. What is a context window, and why not just use a huge one?

    It is the total number of tokens the model can look at in one go, prompt and reply together. Anything outside it does not exist as far as the model is concerned. Frontier models now reach about a million tokens, which is a large book. What that buys is a hard, checkable limit to design against. You can measure your prompt and know in advance whether it fits, instead of discovering truncation in production. The reason not to fill it is that you pay for every token and wait for every token. Attention also thins in the middle of a very long context. A big window is not a replacement for retrieving the right thing.

    Red flag“Long context makes RAG obsolete.” It changes the cost curve. It does not change the fact that you still have to choose what goes in.

  4. What is temperature, and does zero give you determinism?

    At each step the model produces a probability for every possible next token, and something has to choose one. Temperature controls how much that choice may wander. Near zero it almost always takes the most likely token. Higher values flatten the distribution and let unlikely ones through. What it buys is one dial moving output between reliable and varied, which are genuinely different jobs. Extraction, routing and scoring all want the low end. But zero does not give determinism. Batch composition, hardware and floating-point ordering still move results between runs. If you need reproducibility, record the outputs. A setting is not a guarantee.

    Red flagPromising reproducible output from temperature zero. It is a common claim and it is wrong, and this is a question people ask precisely to see who repeats it.

  5. What is a system prompt, and what is it not?

    Text placed at the very front of the conversation, setting the model's role, its rules and its output format. It is marked differently from user turns and weighted more heavily. Underneath, it is still just text in the same context window. What it buys is behaviour set once rather than repeated in every request, and a single place to change it. What it is not is a security boundary. Anything arriving later in the context can argue with it and sometimes win. Untrusted text in the context is exactly the prompt-injection problem. Rules you must actually enforce belong in code.

    Red flagDescribing a prompt as a guardrail. A guardrail is something the model cannot get past, and a paragraph of instructions is not that.

  6. A model is not doing what you want. Prompt, retrieve, or fine-tune?

    In that order, and for different faults. Prompting fixes instructions it is not following, and costs one edit. Retrieval fixes facts it does not have, and the facts stay current because they live outside the model. Fine-tuning continues training on your examples so the weights change, and it fixes behaviour and output format you cannot get any other way. LoRA makes it cheap by freezing the original weights and training small added matrices. What that buys is style that sticks without being restated, and a shorter prompt. The classic mistake is fine-tuning to teach facts. The model learns the shape of your facts without learning the facts.

    Red flagNaming fine-tuning first. It is the most expensive option with the slowest feedback loop, and the interviewer is checking whether you know that.

  7. What actually drives the bill on an agent system?

    Tokens, multiplied by the number of calls. A token is a chunk of text about three quarters of a word, and everything is priced in them. An agent loop re-sends its history every turn, so the cost grows faster than the conversation does. Output tokens usually cost several times more than input, which makes a verbose response format genuinely expensive. Knowing the unit is what lets you predict a bill before running anything. The lever that matters most is how many calls a run makes. That is why a fixed sequence beats a loop deciding for itself.

    Red flagQuoting a per-token price as the answer. The multiplier is the call count, and that is an architecture decision rather than a vendor one.

Fundamentals

Question one gets asked in some form in every LLM interview. Question four is where most candidates overclaim.

  • Orchestration or choreography
  • What ADK gave you
  • What MCP is for
  • Semantic routing
  • Which models, honestly
  • The riskiest claim

  1. What is an agent?

    A model in a loop with tools. It is given a set of functions, it proposes a call, your code runs it, and the result goes back in. Then it decides again. Without the loop and the tools it is just a prompt with a nice name.

    Red flagDefining it by autonomy or goals. Those are properties of some agents. The loop and the tools are what make it one at all.

  2. When a model calls a function, who executes it?

    My code does. The model emits a request naming a function and its arguments. My process decides whether to honour that, runs it, and returns the result. The model never touches anything directly, which is why every tool call is a place I can validate, log or refuse.

    Red flagSaying the model executes it. This is the single most revealing misconception in LLM interviews, because the whole security model follows from it.

  3. Why does a tool's description matter so much?

    Because the description is the interface. The model chooses a tool by reading it, so a vague description means the tool gets used in the wrong situation. It is prompt text that behaves like an API contract, and it is edited far more casually than an API contract would be.

    Red flagTreating descriptions as documentation. They are dispatch logic, and changing one changes behaviour.

  4. What makes your system multi-agent rather than three function calls?

    Honestly, in the vendor platform it is three function calls with one composer, and that is on purpose. What makes it worth the name is that each stage carries its own prompt, schema and model tier. What it deliberately is not is autonomous: they never call each other.

    Red flagDefending the label. Conceding the structure and defending the constraint is a much stronger position, and it is the true one.

  5. Orchestration or choreography, and why?

    Orchestration, everywhere. One place holds the sequence, so there is one file to read and one place a deadline can live. Choreography spreads the control flow across components, which is fine for decoupled services and bad when you need to answer why the system did something.

    Red flagNot knowing the pair of terms. They are the standard vocabulary for the exact choice you made.

  6. What did Google ADK actually give you?

    The loop, sub-agent sequencing, session state between iterations, and lifecycle hooks. Two specifics I would cite. LoopAgent with EventActions.escalate as the early exit, in the schematization retry loop. And a before_tool_callback in the lineage agent, used to make a precondition unskippable.

    Red flagListing features. Name the two hooks you used and what each one bought, or it sounds like a framework you read about.

  7. What is MCP for?

    Describing a tool or data source once, in a standard shape, so any model client can use it without a bespoke wrapper. In the schematization pipeline it gives three sub-agents live access to the target knowledge graph. All three are conditional, so the pipeline still runs with MCP disabled.

    Red flagExplaining the protocol abstractly. Say what it bought in your system, which was a cheap live pre-check before an expensive subprocess.

  8. What is semantic routing, in your system?

    Choosing a branch by meaning. The debugger's screener embeds an error log, retrieves the five most similar past incidents, and returns one of three typed categories. That category decides whether the failure is retried, ignored, or investigated. The routing is the expensive decision, not the answer.

    Red flagDescribing it as classification. It is control flow, and framing it that way is what makes the risk visible.

  9. Which of those four models have you actually shipped on?

    Gemini extensively, across every CloudSufi system. Claude in the pipeline debugger's crews. GPT I would qualify: what I built is an OpenAI-compatible gateway, so it is the API shape rather than the model. Llama I would take off the line, because nothing on the page supports it.

    Red flagLetting four model names stand equally. Two are real, one is a format, and one is absent.

  10. What is the riskiest claim on this line?

    Llama, since no project on the page uses it. GPT is second, because implementing an OpenAI-compatible endpoint is not the same as building on GPT, and a careful reader will make that distinction. Everything else here is backed by a specific system I can describe in detail.

    Red flagNaming MemGPT. It is genuinely evidenced by the Samsung companion, and undervaluing it wastes a distinctive item.

This is the line the loop is about, so these go deeper than the other skills chapters. Several connect two systems, which is where senior signal lives.

  1. How does structured output make a system safer?

    By removing shapes rather than discouraging them. The scout claim schema has no form for an uncited claim, so an uncited claim cannot be emitted. The debug solution's action is a two-value literal, so it cannot return a hedge. A prompt asking for the same thing is advice a model can ignore.

    Red flagCalling it validation. Validation rejects bad output after the fact. A schema stops it being expressible, and that is a stronger property.

  2. When is an agent the wrong answer?

    Whenever the sequence is known in advance. If you can write the steps down, write them down. An agent is worth it when the path depends on what is found. The debugger's lead manager uses a file finding to direct a code lookup. Most pipelines are not that, including two of mine.

    Red flagAdvocating agents generally. The strongest thing you can say here is where you chose not to use one.

  3. Give me a framework hook you used for something non-obvious.

    The before_tool_callback in the lineage agent. The model sometimes called merge before the deterministic extraction had run, producing a graph with zero field mappings and no error. The callback runs extraction if it has not run. That turns a prompt-shaped hope into a precondition.

    Red flagNaming a hook without the failure it fixed. The failure is what makes it a real answer.

  4. When should tool calls run in sequence, and when in parallel?

    Sequence when a later call depends on an earlier result, which is what ReAct is. Parallel when they are independent. The vendor Scout runs three model calls concurrently because all three judge the same gathered sources. The debugger's lead manager is sequential because it reasons across tools.

    Red flagTreating parallel as the better default. Parallel loses cross-tool reasoning, and that loss is exactly why the debugger defaults the other way.

  5. Why MCP rather than writing the tool yourself?

    Because a capability described once is usable by every client. Writing it yourself means re-wrapping it per framework, and the wrappers drift. The honest counterpoint is that MCP adds a transport and a dependency. A local function would often do. That is why all three MCP sub-agents in the schematization pipeline are optional.

    Red flagSelling the protocol. The interesting answer includes why you made it optional.

  6. Why is the router's output a typed literal rather than text?

    Because the value is control flow. A category parsed out of prose can come back as a fourth thing nobody handled. The handler for that does not exist. A DSPy signature declares three literals and a confidence float. So the router cannot return a branch with no code behind it.

    Red flagFraming it as convenience. It is the same argument as structured output: remove the shape rather than handle it.

  7. Your router always retrieves five incidents. What if nothing is similar?

    It returns the five least dissimilar things and routes anyway. Top-k always returns k. There is no similarity floor and no nothing-matched branch, so an unfamiliar failure gets a confident category built on loose matches. The fix is a distance threshold that routes to the expensive branch by default.

    Red flagAssuming a relevance filter exists. It does not, and knowing that about your own retriever is the whole question.

  8. How do you choose between model tiers?

    By what the step is for and who is waiting. Scoring runs on the pro tier because the interview is over, nobody is waiting, and better judgment is worth buying. A live conversational turn uses a faster tier because a person is sitting there. The bake-off in chapter 0001 also showed the cheaper model erring in the more dangerous direction.

    Red flagChoosing on benchmark scores. The deciding factors are latency tolerance and which direction the errors go.

  9. Why pin a model version?

    Because an alias is a dependency that can change without a deploy. In the gateway, aliases plus a substring test meant every turn was diagnosed as an outage and silently retried on a fallback. Four days, 236 warnings, and every request returning success. A pinned version fails loudly when it goes away.

    Red flagCiting reproducibility alone. The real argument is failure mode: loud versus silent.

  10. Explain MemGPT's idea in one breath.

    The model manages its own memory in tiers. A small working context, and a larger external store it pages things in and out of. The model decides what is worth keeping and what to retrieve, so the effective memory is much larger than the context window. It is virtual memory with the model as the pager.

    Red flagDescribing it as RAG. Retrieval is read-only and driven by the query. Here the model also decides what to write, which is the difference.

  11. An agent loop grows its context every iteration. What do you do?

    Compact, and do it by structure rather than by truncation. The schematization retry loop splits feedback on its section headers, drops generation-only sections entirely, and compacts others. Blind truncation is the trap, because it usually cuts the newest errors, which are exactly what the next iteration needs.

    Red flagProposing a summarisation call. That adds a model call inside the loop and a new place to lose information.

  12. How do you evaluate an agent?

    Per decision, not end to end. For the router, per-category precision, because a wrong overlook loses a real failure while a wrong retry is self-correcting. For tool use, whether the right tool was chosen. For output, an oracle where one exists. A single end-to-end score averages away the only thing worth knowing.

    Red flagProposing one overall accuracy number. The decisions have different costs, so they need different metrics.

A model emits a function call in an agent loop. What actually executes that function?

  1. Your own code, once the model proposes a call
  2. The model itself, inside a sandbox the provider runs
  3. The framework alone, with no code that you control
  4. The provider, on their own side of the network

Your code. The model returns a request naming a function and its arguments, and your process decides whether to honour it. That is why every tool call is a point where you can validate, log or refuse.

Getting this wrong is the most revealing mistake in an LLM interview, because the entire security model follows from it. A tool is not something the model has. It is something you offer, on every single call.

Semantic routing picks one of three branches. What is the extra risk compared with ordinary retrieval?

  1. A bad match changes control flow, not just wording
  2. A bad match costs more tokens on every request
  3. A bad match is caught by the schema validator
  4. A bad match only degrades the final answer text

The consequence is a different journey, not a worse sentence. In ordinary retrieval a poor chunk gives a slightly worse answer. Here a misleading similar incident can turn an investigate into a retry, so the pipeline reruns and fails again with nobody looking.

A schema cannot catch it, which is the trap in the third option. The schema guarantees the category is one of three valid values. It has no opinion on whether it is the right one.

Edges and exceptions

Three of these are about the résumé and five about failure. That ratio is right for the line the whole loop is about.

  1. A tool returns text containing instructions. What stops the model following them?

    Structurally, nothing. Tool output enters the context as content and the model has no reliable way to tell data from instruction. That is the genuine open problem in agent design. What limits the damage is the boundary. Since my code executes every call, a tool cannot make the system do anything it was not already allowed to do.

    Red flagClaiming a prompt prevents it. Containment through what tools exist is the real mitigation, not instruction wording.

  2. An agent loops without converging. What stops it?

    A counter, and it has to be outside the model's reasoning. The debugger's lead manager caps at ten iterations. The schematization loop exits on quality acceptable, quality stagnant, or attempts exhausted. The stagnation exit is the interesting one: stop when the score stops moving, not only when it succeeds.

    Red flagRelying on the model deciding it is done. That is the thing that has already failed if you are asking the question.

  3. You add a tool and the model never uses it.

    Almost always the description, not the model. If the description does not clearly say when to reach for it, another tool wins. The second cause is overlap: two tools that sound similar split the choice unpredictably. I would debug it by reading the descriptions as if I were the model, with no other context.

    Red flagReaching for a bigger model. It is a documentation bug in a system where documentation is dispatch.

  4. How do you handle an agent that gives different answers on identical input?

    Measure it rather than assume temperature fixes it. In the vendor platform about one claim in five gets a different verdict on identical evidence, and pinning temperature to zero did not fix it. Nearly every flip sits on one category boundary, which points at the prompt's definition rather than at sampling.

    Red flagSaying temperature zero makes it deterministic. It does not, and having measured that is a much better answer than assuming it.

  5. The interviewer asks what you have done with Llama.

    Say it plainly. Nothing production. It is on the line as familiarity rather than shipped work, and it should either earn a project or come off. The nearest true thing is the on-device work at Samsung over a quantized small model, and that was MobileLLM rather than Llama.

    Red flagStretching the Samsung work to cover it. A different model family is a different model family, and the stretch is what gets caught.

  6. And GPT?

    I would qualify it immediately. What I built is an OpenAI-compatible gateway. So what I know deeply is the API contract: the chat-completions shape, streaming deltas, how tool calls are expressed. Behind that contract I was calling Gemini. That is genuinely useful knowledge, and it is not the same as building on GPT.

    Red flagLetting it stand unqualified. The gateway detail makes the distinction obvious to anyone who reads the bullet above it.

  7. You have used ADK, CrewAI and DSPy. Does framework knowledge transfer?

    The concepts do and the details do not. Every one of them has a loop, tools, state and hooks, so the third framework takes days rather than weeks. What does not transfer is the failure modes, and those are what matter. Tool-calling order variance in one, flow routing in another.

    Red flagClaiming frameworks are interchangeable. The concepts are, and the sharp edges are where all the real time goes.

  8. What would you change about this line?

    Drop Llama and qualify GPT, so every remaining item is backed by a system I can describe. I would also consider naming DSPy and CrewAI, since both are shipped and neither appears. The line currently names a model I have not used and omits two frameworks I have.

    Red flagOnly adding. The line is long already, and swapping the unbacked items for backed ones is the change that improves it.

Probes to expect

  1. “What is an agent, to you?” The opening question of most LLM loops. A vague answer sets the level for everything after it, and vagueness here is very common.
    Model answer — say yours first

    A model in a loop with tools. It is given typed functions, it proposes a call, my code executes it and returns the result, and it decides again. Without the loop and the tools it is a prompt. The part I would emphasise is that the model never executes anything itself. It emits a request and my process decides whether to honour it, which is where validation, logging and refusal all live.

  2. “Why is that multi-agent rather than three function calls?” The standard challenge, and the one where conceding beats defending. The restriction is the impressive part.
    Model answer — say yours first

    In the vendor platform it genuinely is three function calls with one composer, on purpose. Each stage has its own prompt, schema and model tier, which is what makes them worth separating. What it deliberately is not is autonomous: agents never call each other. That restriction is what gives one readable control flow, one place for a deadline, and a stage you can test alone. Agents-calling-agents was rejected, not unavailable.

  3. “How do you stop an agent doing something dangerous?” Testing whether you think about containment or about prompting. Only one of those answers holds up.
    Model answer — say yours first

    By controlling what tools exist, because that bounds what is reachable at all. Then by executing every call in my own code, where I can validate, log or refuse. Then by structured output, so a dangerous instruction has no shape to arrive in. Prompt wording is the weakest layer and I would not lead with it. In the debugger, the strongest control on generated SQL is an allowlist permitting only SELECT and EXPLAIN.

  4. “Which of these models have you actually used in production?” A direct audit of the second half of the line. Two of the four need qualifying and getting there first is worth a lot.
    Model answer — say yours first

    Gemini extensively, across every CloudSufi system, including a bake-off between its tiers on a fixed evidence payload. Claude in the pipeline debugger's crews. GPT I would qualify: I built an OpenAI-compatible gateway, so I know the API contract deeply, but the model behind it was Gemini. Llama has no project behind it and I would take it off the line.

  5. “Where did you decide not to use an agent?” A senior question, and a gift. It is the one place where restraint is the whole answer.
    Model answer — say yours first

    In the lineage agent, for the field mappings. Those come out of structured tables, so a parser is correct where a model would be plausible, and the mappings are extracted rather than generated. Also in the schematization pipeline's validation step, which is a subprocess rather than a judge model, because an oracle exists. The rule I use is that a model should only be asked questions with no deterministic answer.
