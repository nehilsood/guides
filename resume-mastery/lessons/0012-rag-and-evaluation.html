Say it out loud · about 75 seconds

For “how do you evaluate an LLM system?” — the question this whole line exists for. Answer with experiments rather than methodology, because almost nobody does.

    My starting question is always the same. Can something decide correctness by running the answer?

  3. What I did

    Three experiments I would point at. A bake-off replaying one fixed evidence payload through the real code path with only the model swapped, on label-free metrics.

    An A/B on transcript window size at 10, 20 and 40 entries, eight runs an arm.

    And a ground-truth audit, where I ran the hand-written answer keys through the same processor and found only 28 of 49 were valid.

    Two items on that line I would take off. Hybrid search and re-ranking do not appear in any system I built.

    And one place where I broke my own rule. Our 368-scenario harness scores generated code by embedding similarity, when the production path already has a validator that could just run it.

The sentence that sounds fluent and gets you caught

“We use LLM-as-a-judge to evaluate outputs.” Said flat, it suggests a judge is your default, and the follow-up is “why not just run it?” Lead with the oracle question instead. Then “and where nothing can run it, a judge” lands as a considered choice rather than a habit.

The other trap is “every claim is grounded in a cited source.” The schema guarantees a citation exists. It cannot guarantee the URL was in the evidence, that the source is reliable, or that the claim follows from it. Say the mechanism and its limit together, and measure the first gap as a fabrication rate.

Behavioural · the story for this bullet

For “tell me about a time you questioned a measurement” or “a result that turned out to mean something different.”

  1. Decision

    Whether to keep improving a system against a benchmark, or to stop and check whether the benchmark itself was sound.

  2. Situation

    Accuracy varied enormously between datasets and nobody could explain it. The assumption was that wide or messy inputs were the problem, so the proposed fix was prompt engineering.

  3. Action

    I tested the structural hypotheses properly, with rank correlations over seven features. All of them failed. The strongest was not statistically significant.

    When every hypothesis about the system fails, the next candidate is the measurement. So I ran the hand-written answer keys through the same processor the pipeline is validated with. Only 28 of 49 produced valid output.

  4. Result

    The real driver turned out to be schema vocabulary coverage by domain, which prompting cannot fix. The roadmap moved from prompt tuning to coverage and cleaning the reference files.

  5. What it cost

    It made our own numbers harder to present. I had to report that the benchmark was noisy in the same memo that reported results from it. That is uncomfortable and it is better than spending a quarter optimising against a ruler nobody had checked.

Start here — the plain version

Retrieval is fetching the right things before asking the model. Evaluation is finding out whether the answer was any good. They are on one résumé line and they are separate disciplines, and the second one is where this résumé is unusually strong.

The thread running through every evaluation item here is one question: does an oracle exist? If something can run the answer and say whether it worked, use that. If nothing can, you are reduced to comparison and judgment, and those have failure modes worth naming.

Embedding
A list of numbers representing a piece of text, arranged so that similar meanings are close together. Everything else in retrieval is built on this.
Vector search
Finding the nearest embeddings to a query's embedding. Fast and approximate, and it always returns k results whether or not any of them are relevant.
LLM-as-a-judge
Using a model to score another model's output. The right tool when there is no oracle, and a bad substitute when there is one.
Oracle
Something that can decide correctness without an opinion. A compiler, a query planner, a subprocess that either produces rows or does not.
A/B test
Running two configurations against the same workload and comparing. The value depends entirely on how many runs and how large the difference is.
Guardrail
A rule that stops bad output reaching anything. The strongest kind removes the shape entirely rather than filtering it afterwards.

The question underneath every evaluation decision

Does something exist that can decide correctness without an opinion? If yes, use it and do not ask a model. If no, then judgment and comparison, with their limits stated.

Three systems on this résumé answer yes and use the oracle. The schematization pipeline validates by running stat_var_processor.py as a subprocess and reading its exit code. The debugger validates generated SQL by sending it to Snowflake as an EXPLAIN. The lineage agent parses mapping tables rather than asking a model to read them.

One system answers no, correctly. Scoring an interview answer against written anchor prose has no oracle, so an LLM judge is the right tool. That is the Evaluator, and it is a genuine LLM-as-a-judge deployment rather than a buzzword.

And one place gets it wrong, which is worth being the one to point out. The debugger's 368-scenario harness scores generated code by embedding similarity, when the production path already has a validator that could just run it.

Three real experiments, which is the strongest material here

Most candidates answer “how do you evaluate?” with a methodology. You can answer it with three experiments you actually ran and what each one changed.

A model bake-off. One real evidence payload replayed through the actual report function with only the model swapped, so the evidence is fixed and the model is the single variable. It reported label-free metrics: citations naming a URL not in the evidence, verified claims lacking independent support, and verdict instability across an arm's own runs. It found the pro model meaningfully more conservative, and the cheaper model erring in the more dangerous direction.

An A/B on context size. The transcript window tested at 10, 20 and 40 entries against the live payload, with eight runs per arm. That is a real controlled experiment on a parameter people usually set by intuition.

A ground-truth audit. Running the hand-written answer keys through the same processor and finding only 28 of 49 produced valid output. That is the rarest of the three, because it questions the measuring instrument rather than the thing being measured.

In plain words

A model given the same evidence twice does not always reach the same verdict. Temperature is the setting that adds randomness to its output, and turning it to zero did not stop this. The clue is where the changes land: almost all between “no data” and “partial”. So the prompt’s definition of that line is the problem, not chance.

Reproducibility, measured rather than assumed

The claims report is not reproducible, and you know the number. About one claim in five gets a different verdict on identical evidence, and temperature zero did not fix it.

This is the answer to give when someone asks about non-determinism, because it is specific and it was measured. The important second half is where the instability sits: nearly every flip is on the no-data versus partial boundary, not on verified versus contradicted.

That location is the finding. It points at the prompt's definition of the boundary rather than at sampling, which is why pinning temperature did nothing. A sampling problem would scatter flips everywhere. A definition problem concentrates them on one line.

In plain words

Hybrid search runs keyword matching next to meaning-based search, so an exact token like an error code is not lost. Re-ranking uses a second, costlier model to reorder the first results and choose the few that go in. Neither is in any system here. The honest answer says so, then names where each would help.

What the retrieval half actually has

Embeddings and on-device retrieval are real. Hybrid search and re-ranking are the two items with nothing behind them. They are also the two an interviewer is most likely to probe on a RAG line.

Embeddings appear in three places. The ChromaDB incident store the debugger's screener retrieves from. The cosine scoring in its evaluation harness. And the type-distribution cosine inside the lineage agent's metric.

On-device RAG is the Samsung work, and it is a distinctive claim because the constraints are entirely different: a fixed memory ceiling, no batching, and a retrieval index that has to live on the device.

Hybrid search has no system behind it. The vendor platform does web search and vector retrieval, and those are two separate mechanisms in two separate systems rather than one hybrid retriever fusing keyword and vector scores.

Re-ranking has nothing. The screener retrieves five and uses them. There is no second-stage model reordering candidates anywhere.

  1. What is BM25, and why keep it once you have embeddings?

    BM25 is the ranking function classic search engines are built on. It works from three intuitions. A query word appearing more often is better, with sharply diminishing returns so repetition stops helping. A word that is rare across the collection counts for much more than a common one. And a long document is penalised, so it cannot win by containing everything. What that buys is exact matching on the tokens that carry the meaning. Keep it because embeddings blur exactly those. An error code, a product identifier or a column name is where vector search quietly returns something that reads similar and is wrong. Hybrid means running both and merging the ranked lists.

    Red flagTreating keyword search as the old way. It beats embeddings on exact identifiers, and that is a large share of real queries.

  2. What does a vector database actually do when you query it?

    Approximate nearest neighbour search. Finding the closest vectors exactly means comparing the query against every one, which does not scale past a few hundred thousand. Approximate search gives up a little correctness for an enormous speed gain. HNSW is the index almost everyone uses. It is a layered graph where the top layer has a few long-range links and each lower layer is denser. You enter at the top, walk greedily towards the query, drop a layer, and repeat. What it buys is millisecond search over millions of vectors, which is what makes this usable in a request path. Approximate means it can miss. Recall is a knob, and more of it costs latency.

    Red flagAssuming the search is exact. It is not, by design, and knowing recall is tunable is the difference between using a vector store and understanding one.

  3. If embeddings work, why re-rank at all?

    Because the two models are different shapes. A bi-encoder encodes query and document separately into vectors. Every document can therefore be embedded once in advance, and search becomes a distance comparison. A cross-encoder feeds the query and document through together, letting every word attend to every other, and outputs a relevance score. That is far more accurate and cannot be precomputed, because the score does not exist until the pair does. What the two-stage shape buys is accuracy where it counts and speed where it does not. You cannot cross-encode a million documents per query. You retrieve fifty cheaply and re-rank those, so first-stage recall caps everything the second stage can do.

    Red flagDescribing re-ranking as polish. It is a second model doing a harder job, and the reason it is second is pure arithmetic.

  4. How do you chunk documents, and what goes wrong?

    Documents are too long to retrieve whole, so they are split into pieces first. The split can be by fixed token count, by sentence, or along the document's own structure such as headings and tables. Overlap is usually added so an idea straddling a boundary survives in one of them. By structure where the document has any, and by token count with overlap where it does not. What it buys is precision, because retrieving a relevant paragraph beats retrieving the eighty-page document around it. What goes wrong is at both ends. Too small and the piece loses the context that made it meaningful. Too large and the embedding averages several topics into one point matching nothing well.

    Red flagQuoting a chunk size as though it were standard. The right size depends on the documents, and the honest answer says how you would find it.

  5. How do you show retrieval got better, separately from the answer?

    With retrieval metrics on a labelled set. Recall at k asks the blunt question of whether the right document appears in the top k at all. MRR takes one over the rank of the first correct hit, so finding it second is worth half of finding it first. nDCG allows graded relevance rather than yes or no, and discounts by position. What they buy is a measurement of the retriever alone, computable from labelled pairs with no model call. Measure these apart from generation, always. A bad answer from a good retrieval is a completely different bug from a bad answer from a bad one, and the fixes are different.

    Red flagOnly ever scoring the final answer. It conflates two systems, and you will spend weeks tuning the wrong one.

  6. You list MLflow. Which part of it did you use?

    MLflow is four things wearing one name. Tracking records the parameters, metrics and artefacts of each run so experiments stay comparable afterwards. The registry versions models and moves them through stages such as staging and production. Projects package code. Serving deploys. What tracking buys is experiments you can compare weeks later, instead of results living in a notebook and a memory. Tracking alone is a complete and honest answer. Naming the registry implies a deployment and promotion process, so only say it if there was one.

    Red flagLetting the tool name stand for a practice. If nothing was built around it, that is a wording fix on the résumé rather than a story to construct.

  7. How far do you trust a model judging another model?

    As far as you have calibrated it. Using a model to score outputs against a rubric exists because open-ended answers have no reference to compare against. There is nothing to assert equality with. What it buys is evaluation running on every change, instead of waiting for a human labelling round, which is what makes iteration possible at all. The known biases are consistent and documented. Judges prefer longer answers, prefer their own family's style, and shift when the judge model is upgraded underneath you. So pin the judge version, and check it against human labels at least once on a sample. Then quote the agreement rate alongside the score.

    Red flagQuoting a judge score with no human anchor. It is a number produced by the same class of system you are grading, and it needs one.

  8. How many samples does an A/B test need?

    Enough that the difference you saw is unlikely to be noise. The trap is that the number grows sharply as the effect you want to detect shrinks. Small improvements need far more data than people expect. What getting it right buys is the right to say a change helped, rather than that it appeared to. Decide the size before you look. A handful of runs per arm only detects a very large difference. The failure that voids a test is stopping the moment the result looks good. The threshold you crossed then no longer means what it claims, however clean everything else was.

    Red flagReporting a winner without the sample size. It is the first thing a careful interviewer asks, and a small number is better said by you.

  1. When is LLM-as-a-judge the right tool?

    Only when nothing can decide correctness by running the answer. Scoring an interview response against written anchor prose has no oracle, so a judge is right there. Validating generated SQL does have one, because the database can plan it. Using a judge where an oracle exists is choosing to be less correct for no benefit.

    Red flagSaying judges are unreliable. They are the correct tool for subjective questions. The skill is knowing which kind of question you have.

  2. What is an embedding, in one sentence?

    A list of numbers representing a piece of text, arranged so similar meanings sit close together. Similarity is then a distance calculation. That is also the limitation: it measures closeness in meaning, which is not the same as being correct or being the right thing to retrieve.

    Red flagDescribing it as a compressed representation. The useful property is that distance means something, not that it is smaller.

  3. What does top-k retrieval do when nothing is relevant?

    Returns k things anyway. It returns the least dissimilar items, not the relevant ones. In the debugger that matters more than usual, because the retrieved incidents feed a routing decision. So an unfamiliar failure still gets a confident category built on five loose matches, and there is no similarity floor.

    Red flagAssuming a relevance threshold exists by default. It does not, and this is the most common unexamined assumption in a RAG system.

  4. What is hybrid search, and have you built one?

    Fusing keyword and vector retrieval so exact tokens are not lost in a similarity space. It matters for things like error codes, where the literal string is the signal. I have not built one. My systems use web search in one place and vector retrieval in another, which is two mechanisms rather than a hybrid retriever.

    Red flagCounting two separate retrieval mechanisms as hybrid search. Hybrid means fused scoring in one retriever, and an interviewer will mean that.

  5. And re-ranking?

    A second, more expensive model reordering the candidates retrieval returned. You fetch twenty cheaply and let the re-ranker choose the five that go in context. I have not shipped one. The screener retrieves five and uses all five, which is exactly the situation a re-ranker would improve.

    Red flagExplaining it well and letting that imply you built one. The honest version plus naming where it would help is stronger.

  6. How do you make a model cite its sources?

    With the output schema, not the prompt. A claim carries a status and a sources array, and the decoder enforces that, so an uncited claim has no shape to arrive in. Asking nicely is advice a model can ignore. The limit is that a schema constrains shape and never string values, so citation fidelity is measured separately as a fabrication rate.

    Red flagStopping at the schema. Naming the limit in the same breath is what makes the claim survive a follow-up.

  7. Tell me about an A/B test you ran.

    Transcript window size in the gateway, tested at 10, 20 and 40 entries against the live payload, eight runs per arm. It is a parameter people usually set by intuition. The honest caveat is the sample. Eight runs per arm cannot separate a small effect from noise. So it settles a large difference and not a subtle one.

    Red flagQuoting a result without the sample size. The design is the impressive part and the sample is the limit.

  8. And the model bake-off?

    One real evidence payload replayed through the actual report function, with only the model swapped. So the evidence is fixed and the model is the single variable. Label-free metrics: citations naming a URL not in the evidence, verified claims lacking independent support, and verdict instability within an arm. The cheaper model erred in the more dangerous direction.

    Red flagDescribing it as a benchmark comparison. Replaying a fixed payload through the real code path is much stronger, and the difference is worth stating.

  9. Where does MLflow fit in what you built?

    It is a tracking component in the pipeline debugger's architecture. It is not something I built a workflow around. I would describe it as experiment and model tracking that was present, not as a system I designed. That is a thinner claim than the rest of this line, and I would rather say so.

    Red flagDescribing an MLflow workflow you did not own. It is a named component and the honest version is short.

  10. What is the riskiest claim on this line?

    Hybrid search and re-ranking. They are the two an interviewer probes first on a RAG line, and neither appears in any system I built. MLflow is third, as a component rather than work. The evaluation half of this line is genuinely strong. The retrieval half is where it thins out.

    Red flagNaming LLM-as-a-judge. The Evaluator is a real judge deployment with a real bake-off behind it, and undervaluing it wastes the best item on the line.

  1. Walk me through how you designed the bake-off.

    Fix everything except the variable. One real evidence payload, replayed through the actual report function, with only the model swapped. That matters because a benchmark run against synthetic inputs tells you about the benchmark. Replaying production code with production evidence tells you about your system.

    Red flagDescribing a benchmark suite. The strength here is that it is the real code path, not a proxy for it.

  2. What is a label-free metric and why use one?

    A measurement needing no ground-truth answer. Citations naming a URL not present in the evidence is checkable against the evidence itself. So is verdict instability across an arm's own repeated runs. They work where no labelled set exists, which is most real systems, and they are cheap to compute.

    Red flagAssuming evaluation needs labels. The best metrics in that bake-off need none, and that is why it could be run at all.

  3. Eight runs per arm. Is that enough?

    For a large effect, yes. For a subtle one, no, and I would say so before the result. Eight samples against a noisy latency distribution can separate a big difference and cannot settle a few percent. The design was sound and the sample bounds what it can conclude, which is a different statement from the result being wrong.

    Red flagDefending the sample. Naming what it can and cannot conclude is the answer, and it is the more confident position.

  4. One claim in five flips between runs. What does that tell you?

    Where it flips is the finding. Nearly every flip is on the no-data versus partial boundary, not between verified and contradicted. Random sampling would scatter disagreements everywhere. Concentration on one boundary points at the prompt's definition of that line, which is also why pinning temperature to zero did not fix it.

    Red flagReporting the rate without the location. The rate is a symptom and the location is the diagnosis.

  5. How do you know your judge is any good?

    Three ways, none of them complete. Agreement with a human on a sample. Self-consistency across repeated runs, which is the instability number. And whether its errors are biased in a direction that matters, which the bake-off found. The pro model was more conservative and the cheaper one erred towards over-claiming support.

    Red flagOnly naming human agreement. Direction of error matters more here, because over-claiming support is far worse than being cautious.

  6. What is a fabrication rate and why measure it separately?

    How often a cited URL is not actually in the evidence that was provided. It has to be separate because the schema forces a sources array to exist and cannot force its contents to be real. Structure guarantees a citation is present. Only measurement tells you it is genuine.

    Red flagTreating enforced citations as proof of grounding. The schema removes the uncited shape, not the wrong value.

  7. You checked your own ground truth. What made you do that?

    Accuracy varied wildly by domain and the structural explanations all failed. When every hypothesis about the system fails, the next candidate is the measurement. So I ran the hand-written answer keys through the same processor. Only 28 of 49 produced valid output. Part of the benchmark was measuring against broken references.

    Red flagPresenting it only as an excuse for low scores. It cuts both ways and saying so is what makes it credible.

  8. Your debugger harness scores generated code by cosine similarity. Defend or fix.

    Fix. For the prose fields, similarity is defensible because an investigation has no exact match. For the corrected-code field it is the weakest part, because the production path already validates SQL with EXPLAIN and Python with a parse. Scoring that field with the validator makes it deterministic and reuses code that exists.

    Red flagDefending it for consistency. The chapter's own rule says use the oracle, and this is where the résumé breaks its own rule.

  9. How would you choose k?

    By measuring what k changes downstream, not by measuring retrieval quality in isolation. In the debugger, k feeds a routing decision, so the number that matters is how stable the category is as k varies. Too few and a known issue is missed. Too many and unrelated incidents dilute the context and pull the category around.

    Red flagCiting recall at k. Recall is the intermediate metric, and the decision it feeds is what actually matters.

  10. What makes chunking hard?

    The chunk is both the retrieval unit and the context unit, and those want different sizes. Small chunks embed precisely and arrive without surrounding meaning. Large chunks carry context and blur the embedding. For an error log the natural boundary is the stack trace rather than a token count, and structure beats a fixed window whenever structure exists.

    Red flagRecommending a token count. The useful answer is to chunk on the document's own structure where it has one.

  11. What is different about retrieval on a device?

    The index has to fit alongside the model in a fixed memory budget. There is no server to fall back to. So the corpus is small and curated rather than large and general. It also cannot be updated by redeploying a service. That makes the freshness story completely different from a server-side system.

    Red flagDescribing it as the same thing, smaller. The absence of a fallback and the update path are the real differences.

  12. Rank your guardrails by how much they actually protect.

    Strongest is removing the shape: a schema with no field for an uncited claim, or an allowlist permitting only SELECT and EXPLAIN. Then deterministic validation before an action. Then output filters like the SAP name denylist. Weakest is prompt wording, which lowers a rate and guarantees nothing.

    Red flagListing them without ordering. The ranking is the judgment, and prompt wording being last is the part that matters.

When is LLM-as-a-judge the right tool for scoring an output?

  1. Only when no deterministic oracle exists for the task
  2. Whenever a second opinion would raise confidence in it
  3. Whenever running the output would be slow or costly
  4. Only when the original model was a cheaper variant

When nothing can decide by running the answer. Scoring an interview response against written anchor prose has no oracle, so a judge is correct there. Validating generated SQL does have one, because the planner can bind it.

Cost is not the deciding factor, which makes the third option tempting and wrong. A judge is cheaper than executing some things and it is still the weaker answer whenever execution is possible, because it trades a fact for an opinion.

Your A/B on transcript window size used eight runs per arm. What is the main limitation?

  1. Eight runs cannot separate a small effect from noise
  2. Eight runs cost more than the experiment was worth
  3. Eight runs bias the result towards the first arm
  4. Eight runs require a fresh model version each time

Statistical power. Against a noisy latency distribution, eight samples per arm can settle a large difference and cannot settle a few percent. The design is sound and the sample bounds what it is allowed to conclude.

Saying that yourself is stronger than being asked. It converts “here is a result” into “here is a result and here is what it can support,” which is the difference between running an experiment and quoting one.

Edges and exceptions

Retrieval fails quietly and evaluation fails flatteringly. Most of these are about noticing either one.

  • Retrieval returning nothing useful
  • A poisoned store
  • An eval set that ages
  • The judge shares the bias
  • Asked about re-ranking
  • Grounded and still wrong
  • Evaluating without labels
  • What you would change

  1. Retrieval returns five things and none are relevant. What happens downstream?

    The model answers anyway, using them. There is no similarity floor, so a genuinely novel input gets a confident answer built on loose matches. In the debugger that becomes a routing decision, so it is not a worse answer but a wrong branch. The fix is a distance threshold that fails towards the expensive path.

    Red flagSaying the model will recognise irrelevant context. Sometimes it does, and that is not a property you can depend on.

  2. Somebody resolves an incident wrongly and it goes into the store.

    It becomes evidence and teaches the screener to repeat the mistake on similar logs. That is a data-quality problem with a control-flow consequence, which is worse than a data-quality problem alone. It argues for the store being curated rather than appended to automatically, and nothing currently curates it.

    Red flagTreating the incident history as ground truth. People wrote it, under time pressure, at night.

  3. A fixed evaluation set was recorded once. What goes wrong over time?

    It ages, and a stale case is worse than no case. Ideal answers referencing tables that were since renamed will fail a correct system, and then passing them becomes the regression. Any fixed set needs an owner and a refresh cadence, and the 368-scenario set has neither documented.

    Red flagTreating a recorded dataset as permanent. It is a snapshot of a system that kept moving.

  4. What if the judge shares the generator's blind spot?

    Then the evaluation is systematically flattering and nothing in the harness will show it. It is the strongest argument for label-free structural metrics, which do not depend on a model's judgment at all. Checking whether a cited URL is in the evidence is arithmetic, and no shared bias survives it.

    Red flagProposing a different judge model. It reduces correlation and does not remove it, and structural checks do.

  5. The interviewer asks about your re-ranking work.

    Say I have not shipped one. Then say where it would go. The screener retrieves five incidents and uses all five, so a re-ranker over a wider candidate set is exactly the improvement. That turns an absence into a design answer, which is the best available outcome for an item with nothing behind it.

    Red flagDescribing the technique fluently and letting it imply experience. The follow-up is always which model and on what data.

  6. Every claim has a citation and the report is still wrong.

    Entirely possible, and it is the honest limit of schema-enforced grounding. The schema removes uncited claims. It cannot check that the URL was in the evidence, that the source is reliable, or that the claim follows from it. Those are three separate problems and only the first is measured, as a fabrication rate.

    Red flagTreating grounding as a correctness guarantee. It is a structural guarantee, and the difference is the whole answer.

  7. You have no labelled data at all. How do you evaluate?

    Structural and consistency metrics first, because they need no labels. Is every citation present in the evidence. Does the same input give the same verdict across runs. Does the output satisfy an invariant. Then a small hand-labelled sample for calibration, sized for a regression gate rather than a population estimate.

    Red flagSaying you cannot evaluate without labels. The best metrics in your own bake-off needed none.

Probes to expect

  1. “How do you evaluate an LLM system?” The central question of a senior AI loop. Most candidates answer with methodology. You can answer with three experiments and what each one changed.
    Model answer — say yours first

    I start by asking whether an oracle exists. Three of my systems have one and use it: a subprocess running the real processor, a query planner explaining generated SQL, and a parser rather than a model on structured tables. Where none exists, three things I actually ran. A bake-off replaying one fixed evidence payload through the real code path with only the model swapped, on label-free metrics. An A/B on transcript window size at 10, 20 and 40 entries with eight runs an arm. And an audit of my own ground truth, which found only 28 of 49 reference files were valid.

  2. “How do you know your judge model is right?” The standard follow-up to any LLM-as-a-judge claim. The strong answer includes direction of error, which most people never measure.
    Model answer — say yours first

    Three angles, none complete. Agreement with a human on a sample. Self-consistency across repeated runs, which for us is about one claim in five flipping on identical evidence. And the direction the errors go, which the bake-off measured: the pro model was more conservative, and the cheaper one erred towards calling unverifiable things partially supported. That last direction is the dangerous one, and it is why the tier choice was not just about cost.

  3. “Tell me about your hybrid search implementation.” A direct audit of an item with nothing behind it. Conceding and redirecting to where it would help is the only good outcome.
    Model answer — say yours first

    I have not built one, and I would rather say that than stretch. My systems use web search in one place and vector retrieval in another, which is two mechanisms rather than a fused retriever. Where it would genuinely help is the debugger's incident screener: error logs contain exact tokens like codes and table names, and those are precisely what a pure vector search loses. A keyword arm fused with the vector arm would improve that routing decision.

  4. “Your retriever always returns five results. Is that a problem?” Tests whether you know how top-k behaves and whether you have thought about it in your own system.
    Model answer — say yours first

    Yes, and more than usual here, because those five feed a routing decision rather than an answer. Top-k always returns k, so a genuinely novel failure gets the five least dissimilar incidents and a confident category built on them. There is no similarity floor. What I would add is a distance threshold below which it routes to the expensive investigate branch by default, so an unfamiliar input fails towards spending money rather than towards silence.

  5. “What is the weakest part of your evaluation work?” An invitation to be honest. There is a specific, defensible answer that also shows you apply your own rule consistently.
    Model answer — say yours first

    The 368-scenario harness scoring generated code by embedding similarity. For the prose fields that is defensible, since an investigation has no exact match. For the corrected-code field it breaks my own rule, because the production path already validates SQL with EXPLAIN and Python with a parse. The oracle exists and the harness does not use it. That is the first thing I would change, and it is reusing code rather than writing any.

The lessons behind this chapter

System Design School teaches these mechanisms from first principles and breaks them in a lab. This chapter defends what you did with them. An interviewer moves between those two registers without warning.
