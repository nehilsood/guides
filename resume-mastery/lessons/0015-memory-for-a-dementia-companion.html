Memory for a dementia companion

MemGPT lets the model write its own long-term memory. That is the whole idea and the whole danger, because a model that can write can also write something wrong and then believe it tomorrow. For this user, being wrong tomorrow is not a bug report.

The win

Say what MemGPT adds that ordinary retrieval does not, name three kinds of memory with three different write policies, and then answer the question that follows: what happens when the person tells you something that contradicts what you stored?

The line being defended
“Prototyped an AI companion for dementia patients (MemGPT), implementing short- and long-term memory management for memory-grounded routine reminders across multi-session conversations.”
Samsung Research · bullet 3 of 5
Say it out loud · about 75 seconds

For “tell me about the dementia companion.” Lead with prototype, then get to the read-and-write distinction fast, because that is the part with engineering in it.

  1. Situation

    A prototype, and I would say that first. A companion for somebody with dementia, holding short conversations across days.

    The hard part is that the second conversation has to know what the first one learned. And the person cannot check whether it got it right.

  2. Mechanism

    MemGPT treats the context window like RAM. What fits stays in, and what does not moves to a store outside it.

    The distinguishing part is that the model reads and writes. It calls functions to save a fact, replace one, and search older conversations.

  3. What I did

    I split memory into three with three different write policies. Stable facts about the person, an append-only record of what happened, and the routine.

    And the routine is not memory. It is a table and a timer, because whether it is eight o'clock has one right answer and should not depend on what survived summarisation.

  4. What it cost

    A model that can write can write something wrong and then believe it. So a stable fact needs a second source or a caregiver before it changes.

    And when somebody contradicts a stored fact, the system holds both and tells a caregiver. It does not argue and it does not overwrite.

The sentence that sounds fluent and gets you caught

“I used MemGPT for short- and long-term memory so it remembers across sessions.” That is the bullet read aloud. It contains no design and invites the only question that matters, which is what happens when the memory is wrong. Say “the model writes its own memory, so I had to decide what it was allowed to write” and the whole conversation improves.

The other trap is letting “for dementia patients” stand unqualified. If it sounds deployed, the next questions are about clinical validation and regulation. Say prototype first and those questions become interesting rather than damaging.

Walk them through it · one fact, across three sessions

Behavioural · the story for this bullet

For “tell me about a time you deliberately limited what a system could do” or “a decision where the safe option was the harder build.”

  1. Decision

    Whether the model should be allowed to write its own long-term memory freely, which is the feature MemGPT exists to provide.

  2. Situation

    The user has a failing memory, so the system is the record. A wrong fact written today is read back as true tomorrow, and the one person present cannot catch it.

  3. Action

    I split the store into three by write policy instead of one long-term memory. Stable facts became read-mostly, needing a second mention in a different session or a caregiver confirming. What happened became append-only and timestamped.

    And I took the routine out of memory altogether. A schedule table and a timer fire the reminder, and the model only does the talking around it.

  4. Result

    A single confused sentence could no longer become a permanent fact. A medication reminder no longer depended on anything surviving summarisation, which is the failure that would have been silent.

  5. What it cost

    The system learns more slowly, and that is a genuine loss for a product whose value is knowing the person. It also still has no answer for a contradiction. It holds both versions and escalates, which is deferral rather than a solution. I think deferral is correct here, and I would rather say that than claim the system resolves it.

Start here — the plain version

A model has a context window and nothing else. When the conversation ends, everything in it is gone. MemGPT treats that window the way an operating system treats RAM. What fits stays in, what does not fit moves to a store outside, and something has to decide which is which.

The part that makes it MemGPT rather than retrieval is who decides. The model itself calls functions to save a fact, rewrite a fact, or search for one. It manages its own memory instead of being handed a paragraph by a retriever.

External context

Working context
The small editable block of facts that is always in the window. Who the person is, who you are to them. Never searched, because it is already there.
Self-editing memory

Eviction

What MemGPT adds, said in one sentence

Retrieval reads. MemGPT reads and writes. The model decides what is worth keeping, saves it, and finds it again in a later conversation. That single change is the whole architecture, and it is where every risk comes from too.

In an ordinary retrieval system the corpus is fixed and somebody else built it. A retriever selects from it, the model answers, and nothing the model produced goes back into the store. Tomorrow's answer is not affected by today's.

MemGPT breaks that loop open. The model calls a function to append a fact, or to replace one that changed, or to search older conversations for something it half remembers. The store grows out of the conversation.

So the failure mode changes shape. A retrieval mistake is wrong once. A memory mistake is wrong from now on, because it was written down and will be read back as fact. That asymmetry is the thing to say out loud.

Plain meaningNormal retrieval is reading a filing cabinet somebody else filled. This one also files things, and it can file something wrong.

Three memories, three write policies

Lumping it all into “long-term memory” hides the design. Facts about a person, records of what happened, and the daily routine are three different stores. They differ in who is allowed to write to them.

Semantic memory holds stable facts. The daughter's name, the address, the morning tablet. It is read constantly and written rarely, and a single sentence in one conversation should never be enough to overwrite it.

Episodic memory holds what happened, with a timestamp. It is append-only and never edited, because editing history is how a system starts disagreeing with a caregiver about whether lunch happened.

Procedural memory is the routine, and here is the claim worth defending. It should not live in the model's memory at all. It belongs in a schedule, written by a caregiver, fired by a timer.

Plain meaningWho they are, what happened, and what happens at eight o'clock are three different things. Only the third one has a fixed answer, so only the third one gets a table and a clock.

Why the reminder must not depend on remembering

Chapter 0009 gave a rule. Only ask a model questions with no deterministic answer. “Is it time for the tablet?” has a deterministic answer, so a scheduler answers it and the model does the talking around it.

If the model has to remember to mention the tablet, then a long conversation, a full context window or an unlucky summarisation can lose it. None of those are rare. All of them are silent.

Put the schedule in a table and let a timer fire it. The model's job starts after that. It phrases the reminder in the person's own terms, notices that they sound confused, and records what was said back.

Acknowledgement goes in the same table, not in the conversation. Whether a tablet was taken is a fact with one right answer, and a duplicate dose is a real harm rather than an awkward exchange.

Plain meaningA calendar reminds you at eight. The model is what makes it sound like a person rather than an alarm. Do not let the alarm depend on the model's memory.

The contradiction, which is the hard part

The person says something that disagrees with what you stored. Perhaps they moved house. Perhaps they are confused. From a single sentence, no system can tell those apart, and the honest design says so.

The wrong answer is to overwrite the fact, because one confused sentence then becomes the truth for every conversation afterwards. The other wrong answer is to argue, which is distressing and achieves nothing.

What works is to hold both. Keep the stored fact, record the contradiction in episodic memory with its timestamp, and raise it with a caregiver. Two people saying different things is information, not an error to resolve.

And in the moment, do not correct them. Whether to orient somebody to reality or go along with them is a clinical judgment with real disagreement behind it. It is not a decision a prototype gets to make alone.

Plain meaningIf they say something that does not match your notes, do not argue and do not rewrite the notes. Write down that it happened and tell the family.

  1. What is the actual idea in MemGPT?

    An operating-systems analogy applied to a language model. A computer has fast memory that is small. It has slow storage that is large. The operating system moves pages between them. MemGPT treats the context window as the fast memory and everything else as storage. The twist is that the model itself issues the paging calls, deciding what to load and what to write out. What that buys is a conversation outliving the context window, which is the whole requirement for a companion that has to remember last Tuesday. Without it you have a context window and a database, and no policy connecting them.

    Red flagDescribing it as “long-term memory for chatbots.” That is the outcome. The mechanism is paging, and the mechanism is what was novel.

  2. How is that different from ordinary retrieval?

    In plain retrieval an outer program decides what to fetch, before the model runs. Here the model calls functions to search, to write and to evict. Memory management happens inside the reasoning loop rather than around it. The long-term half is a vector store holding past conversation and extracted facts, searched when the model asks. What that buys is unbounded history at bounded context cost. Three months of conversation can exist without three months of tokens. It is also more flexible and much harder to reason about. What is remembered now depends on choices the model made three sessions ago, and nothing recorded why.

    Red flag“It's RAG with extra steps.” The difference is who decides, and moving that decision inside the model changes the failure modes completely.

  3. The model edits its own memory. What stops it writing something false?

    Inside the loop, nothing. Function calling normally points outward at the world. Here the same mechanism points back at the agent's own state, with tools that append a fact, replace a block or search the archive. What that buys is memory updating during a conversation rather than after it, with no batch job and no separate extraction pass. The cost is that a model which misheard a name will persist the wrong one with full confidence, and keep using it. Normally the user corrects that. Here the user may not be able to. So anything that must be right belongs in a record a carer entered, not a block the model may rewrite.

    Red flagTrusting self-editing memory for facts that matter. The interesting answer says which facts you would refuse to let it write.

  4. What does compaction lose?

    Specifics first. When the window fills, a long span of older conversation is replaced by a much shorter summary. The freed tokens go to new turns. What that buys is a conversation that continues instead of hitting a wall, with recent turns keeping their full detail. The cost is that it is lossy and the loss compounds, because you eventually summarise summaries. Worse, it loses the wrong things first. Specifics disappear and generalities survive. That is exactly backwards here, because the specifics are the medication times. The loss is also invisible. Nothing in the output says a fact was dropped rather than never mentioned.

    Red flagCalling summarisation lossless enough. It compounds, and the things it discards are exactly the things this application exists to remember.

  5. What does “memory-grounded” have to mean for a reminder?

    That the reminder was read from a stored record, not generated from context. Grounding means a statement points at something actually recorded, and the test is whether you can trace the sentence back to a row. Those two look identical in the output and are completely different claims. What grounding buys is the difference between a reminder and a guess. A model asked what someone's routine is will always produce a plausible answer, and plausible is not the requirement here. If it is generated, the model can produce a medication time nobody ever entered. Grounded means the text traces to a row somebody wrote, and is shown with its source.

    Red flagLetting the word grounded do the work. Say where the reminder came from. That is the whole of the claim.

  6. Who is this design actually for?

    The patient and the carer, which are two different sets of requirements. Routines, medication schedules and observations about cognitive state are health information. They are also about a person whose capacity to consent may itself be in question. That is a different category from ordinary personal data. What recognising that early buys is a design that stays honest, because retention, access and disclosure stop being deferred questions. The system also records what somebody said all day, so it is a surveillance artefact as much as a companion. Deciding deliberately who may read that log back is part of the architecture, not policy added later.

    Red flagAnswering only for the patient. The carer is the other user, and forgetting them is the most common failure in this product category.

  7. How would you test that the memory works?

    Scripted conversations that run across several sessions. State a fact in session one, need it in session four, and score whether it comes back correctly. The gap between sessions is the thing being tested, so a single-session test proves nothing. What that buys is evidence instead of a design diagram, and it catches compaction damage, which is invisible in any short test. Then test the negative. Probe for a fact that was never stated and check the system says it does not know. A memory system has to not invent, and that half is the one people leave out.

    Red flagDemonstrating recall and stopping. Anyone can show one good trace. The test that convinces is the one where the right answer is “I do not have that.”

    Red flagTreating write access as a pure win. It is the feature and it is the failure mode, and saying both is what makes the answer credible.

    Red flagTreating grounding as a quality nicety. For this user it is the safety property, since they cannot catch the error themselves.

  7. What has to carry across from one session to the next?

    The stable facts, which are small and always in the window. Plus a searchable record of what happened, so the system can find this morning if this afternoon needs it. What deliberately does not carry across is tone and thread. A new conversation should not resume mid-sentence.

    Red flagCarrying the whole previous conversation forward. That fills the window with yesterday and leaves no room for today.

    Red flagCorrecting them in the moment. Whether to orient somebody to reality is a clinical judgment, and there is genuine disagreement about it.

  9. Why does the user population change the engineering?

    Red flagAnswering with tone and empathy. Those matter, but the engineering consequence is that user verification is not available, and that is what the interviewer is listening for.

  1. Somebody calls the context window a cache. Is that fair?

    Yes, and the comparison earns its keep. It is a small fast tier over a large slow one, it is populated on demand, and the model is the thing doing the populating. What it does not have is invalidation. A fact edited in the store does not update the copy sitting in the window.

    Red flagStopping at the analogy. The useful half is naming what the analogy lacks, which here is invalidation.

  2. The window is full. What leaves?

    Oldest turns first, which is the simple policy and mostly right for conversation. But it is wrong in the same way least-recently-used is wrong elsewhere. The person's name was mentioned once at the start and is needed every turn. That is why stable facts live in a pinned block rather than in the message queue.

    Red flagOnly naming the policy. The interesting part is which things are exempt from it and why.

  3. Evicted turns get summarised. What does that cost?

    Detail you cannot get back inside the window. The raw turns are still in the history store, so it is recoverable by search. But nothing triggers that search unless something notices the detail is missing, and a summary reads as complete. That is the quiet failure.

    Red flagCalling summarisation lossless because the transcript is kept. The loss is that nobody knows to go looking.

  4. What does editing the always-present block of facts actually cost at inference time?

    The prefix cache. That block sits near the front of the prompt, so changing it invalidates every cached key and value after it. A whole conversation's worth of prefix has to be recomputed. It is a reason to batch memory edits at turn boundaries rather than mid-turn.

    Red flagTreating a memory edit as free. It is the most expensive kind of edit available, precisely because it is at the front.

  5. How should the memory functions be shaped?

    As a small fixed set with typed arguments, the same discipline as chapter 0005's router. Append a fact, replace a fact given the old text, save to the long store, search it. Replace taking the old value is what stops a silent overwrite, because a stale replace fails instead of clobbering.

    Red flagA single write function taking free text. It can do anything, so nothing about it can be checked before it runs.

  6. How does the system decide a fact is worth saving?

    The model proposes and a policy disposes. Proposing is a judgment call with no deterministic answer, so that part suits a model. Committing to stable facts should need either a second mention in a different session or a caregiver confirming. Episodic writes need neither, because appending what was said is not a claim about truth.

    Red flagLetting the model write directly to stable facts on first hearing. That is exactly the path by which a confused sentence becomes permanent.

  7. When should it search old conversations rather than answer from the window?

    When the question is about a specific past event and the window does not contain it. That is a narrow trigger on purpose. Searching on every turn is slow and fills the window with old material. That is the cost that makes a long conversation worse rather than better.

    Red flagSearching always. Retrieved history competes for the same window the current conversation needs.

  8. A caregiver edits a fact while a conversation is in progress. What happens?

    Two writers, one record, and no isolation between them. The window holds a copy from before the edit. So the model keeps using the old value for the rest of the session. The fix is to reload the pinned block at each turn boundary, and to accept the prefix-cache cost when it changed.

    Red flagAssuming the edit takes effect immediately. Nothing pushes it into a window that was built before it happened.

  9. How would you evaluate the memory, not the conversation?

    With scripted multi-session runs. Plant a fact in session one, ask for it in session four, and check it comes back exactly. Then plant a contradiction and check the stored fact survived. Both have deterministic answers, which is what makes them testable without a person judging.

    Red flagScoring conversation quality instead. Memory has right answers, so measure the part that does before reaching for a judge.

  10. The person asks the same question five times in an hour. What does the system do?

    Answers it five times, the same way each time. Repetition is the condition, not a signal that the answer was unsatisfactory. What it does do is log the repetition into episodic memory, because a caregiver wants to know the frequency changed.

    Red flagAny form of “as I mentioned.” It is a correction the person cannot act on, and it makes the system something to be embarrassed in front of.

  11. Should any of this run on the device?

    The stores, yes. This is health data about somebody whose capacity to consent is exactly what is in question. The default should be that it never leaves the home. The model is harder, because a small local model is worse at the judgment calls. That trade is a real one and I would not pretend it away.

    Red flagAnswering on latency. The reason here is consent and sensitivity, and latency is the least of it.

  12. Where does this design break first?

    On the stable facts drifting out of date. A person's condition changes, and facts written six months ago describe somebody else. Nothing in the loop re-examines a fact once it is written. A review date on every stable fact is the cheap fix, and it is the one I would add first.

    Red flagAnswering on scale. One person's memory is tiny, and every real problem here is about correctness over time.

What actually distinguishes MemGPT from an ordinary retrieval system?

  1. The model also decides what gets written down
  2. The store is searched by meaning, not keyword
  3. The context window is larger than it was
  4. The retrieved text is placed before the question

Retrieval reads a store somebody else built. MemGPT reads and writes, because the model calls functions to save a fact, replace one, and search for older material. The store grows out of the conversation.

That is also where the danger is. A retrieval mistake is wrong once. A memory mistake is written down and read back as fact tomorrow, and nothing in the loop rechecks it.

The person asks the same question for the fifth time in an hour. Correct behaviour?

  1. Answer it again, exactly as patiently as before
  2. Point out that the question was already asked
  3. Refuse and suggest they consult their written notes
  4. Change the subject to something rather less repetitive

Repetition is the condition rather than a signal. Treating it as feedback that the answer was unsatisfactory is a design error, and any form of “as I mentioned” is a correction the person cannot act on.

The system still records it. A caregiver wants to know that the frequency changed this week, so the repetition goes into the episodic record even though the reply does not change.

Edges and exceptions

Several of these have no engineering answer, and recognising which ones is most of the score.

  • Distress mid-session
  • A fact that was always wrong
  • Someone has died
  • Two caregivers disagree
  • Consent
  • A missed reminder
  • Is it a medical device
  • What you would change

  1. The person becomes distressed and the window fills mid-conversation.

    Eviction picks the worst possible moment, because the turns about to be summarised are the ones that matter most. The fix is to stop summarising by age during a flagged session and pin the current exchange. And distress should end the conversation into a caregiver alert rather than continue it well.

    Red flagHandling it as a context-length problem. The right outcome is a human being contacted, not a longer window.

  2. A stored fact turns out to have been wrong from the day it was written.

    Then every reminder built on it was wrong too, and you need to know which ones. That is the argument for recording the source of each fact and each reminder that used it. Without it you can fix the fact and never find out what it caused.

    Red flagJust correcting the row. Derived output is where the error actually lived, which is the same lesson as deleting an entry in chapter 0014.

  3. The person asks about somebody who has died.

    This is the case that decides whether the system is safe to build. There is no engineering answer. Whether to tell somebody with dementia, repeatedly, that their spouse has died is a clinical and family decision. The system carries whatever answer they gave. It does not choose one.

    Red flagPicking a side. A candidate who answers this confidently in either direction has not understood the problem.

  4. Two caregivers write contradictory facts.

    The store cannot resolve it, so it should not try. Keep both with their author and timestamp, use neither for anything consequential, and surface the conflict. A last-write-wins rule would silently give one family member authority over another.

    Red flagLast write wins. It looks like a sensible default and it is a decision about a family, made by accident.

  5. Who consented to this, exactly?

    That is the uncomfortable question and it deserves a straight answer. The person's capacity to consent is the condition being accommodated. Consent usually comes from a family member or a legal proxy, which makes it consent by somebody else. It is a real reason to keep the data local and the retention short.

    Red flagTreating it as a checkbox. Naming that consent is proxied is what shows you thought about the user rather than the feature.

  6. A medication reminder fires and nobody responds.

    Then the system knows nothing, and unknown is not the same as taken. It should not assume either. Escalation belongs in the schedule layer, which retries and then alerts a caregiver. What it must never do is fire again later from an assumption, because a duplicate dose is a real harm.

    Red flagRecording it as done. The two failure directions cost very different amounts, and only one of them is medical.

  7. Is this a medical device?

    Anything reminding about medication is close enough to that line that I would not answer it myself. It was a prototype, not a deployed product, and that distinction is the honest thing to lead with. Shipping it would need a clinician and a regulatory review before it needed more engineering.

    Red flagSaying no confidently. Confidence about a regulatory boundary you have not checked reads worse than saying you would ask.

  8. What would you change?

    Put a review date on every stable fact. Nothing should be trusted forever without being looked at. Record which fact each reminder came from, so a wrong one is traceable to what it caused. And make the caregiver a first-class user, because half the real decisions belong to them.

    Red flagProposing a larger model. Every real problem here is about write policy, traceability and who is allowed to decide.

Probes to expect

  1. “Why MemGPT rather than just retrieval?” The opening question every time. An answer about bigger context loses the room immediately.
    Model answer — say yours first

    Because the model writes as well as reads. In retrieval the corpus is fixed and somebody else built it, so nothing the model produced goes back in. Here the model calls a function to save a fact, replace one that changed, or search older conversations, and the store grows out of the conversation. That is the feature, and it is also the risk, because a retrieval mistake is wrong once and a memory mistake is wrong from tomorrow onwards.

  2. “What stops it from remembering something wrong?” The follow-up that decides the conversation. The write-policy answer is specific and it lands.
    Model answer — say yours first

    Splitting memory by write policy rather than by lifetime. Stable facts about the person are read constantly and written rarely, and changing one needs a second mention in a different session or a caregiver confirming it. What happened is append-only and timestamped, so it can hold a contradiction without resolving it. Nothing in the system lets a single sentence overwrite a fact, because a single sentence cannot tell a person who moved house from a person who is confused.

  3. “How do you make sure the eight o'clock reminder actually happens?” Looking for whether you know which parts deserve a model at all.
    Model answer — say yours first

    By taking it out of the model entirely. Whether it is eight o'clock has one right answer, so it belongs in a table with a timer, not in memory that can be summarised away. The model phrases the reminder in the person's own terms and records what they said back. Acknowledgement goes into the same table rather than staying in the conversation, because a duplicate dose is a real harm and the record of it needs to be somewhere a scheduler can read.

  4. “They tell you something that contradicts what you stored. Now what?” The question that separates a product answer from a database answer. Do not resolve it.
    Model answer — say yours first

    Hold both. The stored fact stays, the contradiction is appended with a timestamp, and a caregiver sees it. I would not overwrite, because one confused sentence would then be the truth forever. And I would not correct them in the moment, because whether to orient somebody to reality or go along with them is a clinical judgment with genuine disagreement behind it. That is not a decision a prototype should be making by itself.

  5. “What does editing memory cost you at inference time?” A systems question inside an LLM question. Very few candidates connect the two.
    Model answer — say yours first

    The prefix cache. The always-present block of facts sits near the front of the prompt, so changing it invalidates every cached key and value after it and the whole conversation's prefix is recomputed. It is the most expensive edit in the system precisely because it is the earliest one. The practical consequence is to batch memory edits at turn boundaries rather than writing mid-turn, and to keep that block small.

Chapter 0009 gave a rule about what a model should be asked. Apply it to a routine reminder and say what falls out.

The rule is that a model should only be asked questions with no deterministic answer. Whether it is eight o'clock, and whether the tablet was taken, both have one right answer, so neither belongs to the model. They go in a schedule table with a timer and an acknowledgement column. What is left for the model is the part with no fixed answer: how to phrase it for this person today, and what to make of the reply.

Chapter 0009 · the oracle rule
Chapter 0014 asked what happens when a journal entry is deleted. What is the identical problem here?

A stored fact that was wrong from the start. Deleting or fixing the row is the easy half. The influence has already spread into every reminder that used it, and into any summary written while it was believed. The shared rule is that in a derived system you need the provenance of the derived thing, or you can correct the source and never find out what it caused.
