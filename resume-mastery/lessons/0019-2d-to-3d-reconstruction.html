Start here — the plain version

Photographs of an object go in and something viewable from any angle comes out. Before, a person built that by hand in modelling software, which is where three weeks went. After, a program fits it from the photos.

Two ways of representing the result appear in this bullet. One stores the scene inside a small neural network. The other stores it as a few million fuzzy coloured blobs. The second one is why it can run in a browser.

The technology — what each named thing is

The primer above defines the methods. This one defines the pipeline they sit in, starting from the ground, and the arithmetic behind the two numbers. Four named techniques in one bullet is a lot of surface, so the follow-ups matter as much as the definitions.

Every entry answers four things. What it actually is, in plain words. Where this pipeline uses it. What it buys, meaning what goes wrong without it. And the follow-up an interviewer asks once you have said the name.

COLMAP
structure from motion, in practiceYou have forty photographs of an object and no idea where the camera was for any of them. Structure from motion recovers that: it finds features that appear in several images, works out the camera position and orientation that makes all those sightings consistent, and produces a sparse cloud of 3D points as a by-product. COLMAP is the standard open-source implementation. In the app. It runs first, because nothing downstream can begin without camera poses. What it buys. Turning a handful of ordinary photographs into calibrated input, with no rig, no turntable and no measured setup. The follow-up. It fails on texture-less surfaces, reflections and glass, because those give no stable features to match between views. A jar is shiny, so this is the realistic failure mode in this project rather than a theoretical one.
Volume rendering
how a NeRF makes a pixelA NeRF does not store a surface. It stores a function that, given a point in space and a viewing direction, returns a colour and a density. To produce one pixel you shoot a ray out through it, sample many points along that ray, ask the network at each point, and composite the results front to back so that dense points block what is behind them. In the app. It explains both NeRF's quality and its cost in one go. What it buys. Semi-transparency, soft edges and volumetric effects that a mesh cannot represent at all. There is no surface to get wrong. The follow-up. The cost is the sample count. Hundreds of network evaluations per pixel per frame is why plain NeRF cannot render in real time on any hardware, and that fact is what the rest of this list is reacting to.
Multiresolution hash encoding
what made Instant-NGP fastThe original NeRF put a 3D position through a large network, so all the scene's detail had to be stored in network weights and every sample cost a full forward pass. This replaces most of that. The position is looked up in a stack of hash tables at several resolutions, the results are interpolated and concatenated, and only then does a very small network run. In the app. It is the actual mechanism behind the training speed-up in the bullet. What it buys. Training in minutes rather than a day, which changes the process from an experiment into something a pipeline can run per object. The follow-up. Where the speed comes from. The network shrank and the capacity moved into the tables, and gradient updates became sparse because one sample touches only a few table entries instead of every weight.
Gaussian splatting
the representation changeA different answer to the same problem. Rather than a function you query along rays, the scene is stored as a few million 3D Gaussians, each a soft blob with a position, a covariance describing its shape and orientation, an opacity and a colour. Rendering projects each blob onto the image plane and blends them in depth order. In the app. It is the second half of the bullet and the reason real-time rendering became possible. What it buys. Real-time frame rates at comparable quality, which is the whole difference between a research result and something shippable to a browser. The follow-up. Why it is faster. It rasterises instead of ray-marching, so work is proportional to the number of primitives rather than to samples along every ray. That is exactly what graphics hardware was built to do.
Spherical harmonics
how colour varies with angleA real surface does not look the same from every direction — a glossy jar has a highlight that moves as you walk around it. Spherical harmonics are a compact way to describe a function defined over directions, in the way a Fourier series describes a function over time. Each Gaussian carries a few coefficients rather than one flat colour. In the app. It is what keeps specular highlights on a glossy object instead of flattening it into matte plastic. What it buys. View-dependent appearance for a handful of numbers per primitive, rather than storing a separate colour per viewpoint. The follow-up. The order is a size and quality dial. More coefficients per Gaussian means more memory, and memory is what decides whether a scene loads in a browser on a phone.
Image metrics
PSNR, SSIM, LPIPSThree ways to score a rendered image against a real photograph. PSNR is pixel-by-pixel error on a logarithmic scale, and its known weakness is that it rewards blur, because a blurry image has lower average error than a sharp one that is slightly misaligned. SSIM compares local structure, contrast and luminance instead. LPIPS compares features from a deep network and correlates best with what people actually judge to look right. In the app. “Render quality up 30%” is a claim about one of these three. What it buys. A quality claim that can be reproduced by somebody else. The follow-up. Which metric, and thirty percent of what. PSNR is quoted in decibels and does not move by percentages in a way anybody can interpret, so the metric has to be named for the number to mean anything.
Baking
what SNeRG doesConverting a trained radiance field, which only a specialised renderer can evaluate, into a structure an ordinary renderer can draw. In practice a sparse voxel grid holding colour and opacity, plus a very small shader that handles the view-dependent part. The expensive network evaluation is done once, ahead of time, and the result stored. In the app. It is how a field trained on a workstation GPU ends up running inside a phone browser. What it buys. Rendering that needs no neural network at run time at all, which is what makes the delivery target reachable. The follow-up. Baking freezes quality at bake time. You trade the ability to keep improving the model for the ability to render it anywhere, and the resulting file size becomes the real product constraint.
WebGL and WebGPU
what the browser can actually doThe two graphics APIs available to a web page. WebGL is old, based on a mobile graphics standard from 2007, supported essentially everywhere, and has no compute shaders. WebGPU is the modern replacement, with compute shaders and a design that matches how GPUs actually work now, but its support is far newer and less universal. In the app. WebXR ultimately renders through one of the two. What it buys. The choice is really a choice about who can open your link. The follow-up. Which one you targeted decides device coverage directly, and on a consumer product that is a business answer as much as a technical one.
WebXR
the delivery targetThe browser API for presenting to a headset or to a phone held up in augmented reality. It handles the parts a normal page has no concept of: tracking the viewer's head pose, rendering a separate image per eye, and matching the display's refresh cycle. In the app. It is the last word in the bullet, and the reason everything upstream had to be made cheap. What it buys. Immersive viewing with no app to install, from a URL. The follow-up. The frame budget, which is the number that settles every argument here. Stereo at ninety frames a second leaves about five milliseconds per eye per frame, and that single figure is what rules out every ray-marched approach.

three weeks, and what was in itNot a technology, but the contestable half of the headline number. The process being replaced was a person modelling an object by hand in 3D software, and three weeks is an estimate of that. Defining the baseline precisely is what turns the claim from marketing into a measurement. The follow-up. Whether capture, cleanup and review sit inside the 100 minutes. What the three-week number is actually comparing

Not an old algorithm against a new one. A person against a program. Three weeks was somebody modelling an object by hand, and a hundred minutes is a fitting run on a machine.

Lead with that, because otherwise the number sounds like a three-hundred-fold algorithmic speedup and the next question is how. There is no such speedup. There is a different kind of work being done.

The bracketed figure says the same thing more honestly. Ninety-eight per cent less manual effort is a labour claim, and labour is the thing that actually changed. The wall-clock number is a consequence.

It also sets up the real trade, which is worth volunteering. Hand modelling gives you a clean mesh somebody can edit. Reconstruction gives you something that looks right from the angles you photographed and is much harder to fix by hand.

Plain meaningNothing got three hundred times faster. A person stopped doing it and a program started, and those are not the same job.

A radiance field, without the word geometry

A NeRF does not build a shape. It fits a function. Give it a point and a direction you are looking from. It returns a colour and a density.

To render a pixel you walk along the ray behind it, ask that function at many points, and accumulate colour weighted by density until the ray is blocked. Training is minimising the difference between rendered pixels and the actual photographs.

The direction argument is the part worth saying, because it is what makes the result look real. A wet surface is a different colour from different angles, and a representation that ignores direction cannot do that.

And it is a fit per scene, not a model you reuse. Every object is a fresh training run from its own photographs. People who have only read about it usually assume the opposite.

Plain meaningIt does not work out the shape. It learns what you would see from any point, looking in any direction, and then renders by looking.

Why one of these is fast and the other is real-time

Two different speed problems, solved twice. Instant-NGP made training fast. Gaussian splatting made rendering fast. They are not versions of each other and confusing them is the common mistake.

Instant-NGP's trick is where the learning is stored. Instead of a large network holding everything, feature vectors live in hash tables at several resolutions, and a very small network reads them. Lookups are cheap where network evaluations are not.

Splatting changes the representation rather than the training. The scene becomes a few million fuzzy blobs with positions, shapes, opacities and colours. Rendering is projecting them onto the screen and blending, which is what graphics hardware already does.

That is the whole reason it hits frame rate. Marching rays means many samples per pixel. Rasterising means touching each blob once and blending. The second one is built into every graphics card on earth.

Plain meaningOne of them made the learning quick. The other threw away ray marching and drew blobs instead, which is what a graphics card is for.

The stage that actually fails

Almost nothing goes wrong inside the radiance field. What goes wrong is the camera poses, worked out from the photos before any of this starts. Bad poses produce a blurry result and no error message.

Feature matching needs texture. A plain white wall, a reflective surface, a repeating pattern, or photographs taken too far apart, and the pose estimate is wrong or missing for some of them.

The failure looks like a modelling failure. The reconstruction is soft, or has ghosting, or one side is wrong. Every one of those symptoms points backwards at a stage that reported success.

Which makes capture protocol the real deliverable. How many photographs, how much overlap, what lighting, what not to photograph. That is the part that decides whether the hundred minutes produces anything usable.

Plain meaningThe step that works out where each photo was taken from is the one that breaks. When it does, everything after it looks blurry and nothing says why.

    Red flagAnswering with model size. A small network evaluated fifty times per pixel is still fifty times per pixel.

    Red flagDescribing it as compression. It is a change of representation for playback, and the original model is not what gets shipped.

  1. Hash tables collide. Does that not corrupt the result?

    It would if anything tried to resolve the collisions, and nothing does. Two distant points can land on the same entry, and the small network learns to tell them apart from the other resolutions it also reads. Collisions in empty space cost nothing, because gradients there are tiny.

    Red flagAssuming a collision-handling scheme. The absence of one is the design, and it is the part that sounds wrong until you say why it works.

  2. Where do the blobs come from, and how many?

    They start from the sparse points that structure from motion already produced, then the optimiser adds and removes them. Where the reconstruction is poor it clones or splits blobs to add detail. Where they are nearly transparent it deletes them. That control loop is most of why the method works.

    Red flagDescribing a fixed number of blobs. The count changes throughout training and that is the mechanism, not an implementation detail.

  3. What does splatting cost that ray marching does not?

    A depth sort, every frame, for every view. Blending semi-transparent things is order-dependent, so the blobs have to be drawn back to front. On a headset that is two sorts per frame, over hundreds of thousands of items. It is the part that decides whether the frame budget holds.

    Red flagPresenting splatting as free. The sort is the hidden cost and naming it is what shows you rendered with it rather than read about it.

  4. What has to be true for this to load in a browser?

    The asset has to be tens of megabytes, not gigabytes. And it has to render with what a browser has, not with a graphics toolkit. Both representations need reducing for delivery. A baked grid is pruned to occupied space. A splat set is trimmed and its colours stored at lower precision.

    Red flagIgnoring download size. On a phone the first thirty seconds are download, and no frame rate rescues that.

  5. Somebody wants to change the object afterwards. What can they do?

    Very little, and this is the honest cost of the whole approach. Hand modelling produces a mesh an artist can edit. Neither of these produces anything with editable structure. Moving a part of a splat scene means selecting blobs, and nothing about them corresponds to a part of the object.

    Red flagClaiming a mesh can be extracted and edited. You can extract one, and it is usually worse than the render it came from.

  6. How would you state the quality improvement properly?

    Name the metric, give both values, and say what it was measured over. Peak signal-to-noise ratio is decibels on a log scale. A percentage is meaningless on it. If the number came from a perceptual metric, say which one. Those behave differently and track what people see rather more closely.

    Red flagDefending the percentage. Restating it precisely costs one sentence and removes the only easy attack on this bullet.

  7. The bullet names both a baked radiance field and splatting. Why both?

    They are two different delivery paths and using both needs a reason. The plausible one is a sequence. Bake the trained field first, because that is what a browser could run. Then move to splatting once it looked better at the same frame rate. If they ran at once, that is worth explaining.

    Red flagListing both as though they compose. One replaces the representation the other bakes, and anyone in graphics will notice.

  8. What is the real deliverable for making this repeatable?

    A capture protocol. How many photographs, how much overlap between them, what lighting, and what surfaces to avoid. That document is what decides whether the hundred minutes produces something usable, and it is worth more than any parameter choice in the training.

    Red flagAnswering with training hyperparameters. The input quality dominates, and the protocol is the only lever on it.

  9. Where does the hundred minutes actually go?

    Mostly not in the part people expect. Pose estimation over a few hundred photographs is a real chunk. Training is minutes with the hash-table approach. Then baking or trimming for delivery, plus whatever check confirms the result is acceptable. Saying which stage dominates is a good sign you ran it.

    Red flagAssuming training dominates. That was true before the fast encoding and it stopped being true, which is the whole point of it.

  10. The background comes along with the object. Is that a problem?

    Usually yes, for a product catalogue. The field learns the room as readily as the object, because nothing told it which was which. Masking the object during capture or before training is the practical fix, and it is another thing the capture protocol has to specify.

    Red flagAssuming the object is separated for you. Nothing in the method has a concept of an object at all.

  11. A hundred objects rather than one. What changes?

    It becomes a scheduling problem and stops being a research one. Every object is an independent run on a machine with a graphics card. So it parallelises perfectly and the cost is linear. What needs building is the queue, the retry, and a check that catches a bad reconstruction automatically.

    Red flagReaching for a shared model across objects. There is no shared model. Each one is its own fit.

  12. This was a while ago. What has moved since?

    Splatting became the default for anything that has to render in real time, and the baked-grid route is now mostly historical. Saying that yourself is better than being told. It shows the work is dated without suggesting the understanding is.

    Red flagPresenting it as current practice. The field moved fast, and pretending otherwise is the thing that actually damages the claim.

Why does Instant-NGP train so much faster than a plain radiance field?

  1. Most of the capacity sits in lookup tables
  2. It trains on far fewer input photographs overall
  3. The rendered images are at a lower resolution
  4. It skips the slow camera pose estimation step

Feature vectors live in hash tables at several resolutions, indexed by position, and a very small network reads them. A table lookup is far cheaper than evaluating a large network, and training touches that function millions of times.

Pose estimation still runs, and it is a substantial part of the wall-clock time. The number of photographs and the render resolution are unchanged, which is what makes the comparison fair.

What lets Gaussian splatting render at frame rate where ray marching cannot?

  1. It rasterises the scene instead of marching rays
  2. It uses a considerably smaller neural network inside
  3. It renders only the visible front-facing surfaces first
  4. It caches whole frames that were already drawn

Marching a ray means dozens of samples per pixel. Rasterising means touching each blob once and blending it into the pixels it covers, which is exactly what graphics hardware is built to do.

There is no neural network at render time at all. And the blobs are semi-transparent, so front faces do not occlude anything, which is why the method pays a depth sort every frame instead.

Edges and exceptions

Mostly about capture and delivery, because those are where this fails in production rather than in a paper.

  • Glass and metal
  • Something moved
  • Too few photographs
  • A view nobody captured
  • A phone that cannot cope
  • Detecting a bad result
  • Defending 30 per cent
  • What you would change

  1. The object is glass, or polished metal.

    Both stages struggle. Feature matching fails because the surface has no stable texture to match, and what it does have moves with the camera. The field then tries to explain reflections as geometry and produces floating fragments. This is a capture limitation and there is no parameter that fixes it.

    Red flagPromising it works on anything. Reflective and transparent objects are the known hard case and saying so is more convincing than claiming coverage.

  2. Something in the scene moved between photographs.

    The whole approach assumes the scene is still, so a moving thing gets explained as semi-transparent haze in several places at once. Those are the floating fragments people call floaters. The fix is capture discipline rather than anything in the pipeline.

    Red flagTreating floaters as a training artefact to tune away. Most of them are the method faithfully representing inconsistent inputs.

  3. Someone submits twenty photographs instead of two hundred.

    Pose estimation may still succeed, which is the dangerous part, and the reconstruction will be confident and wrong between the views. The useful safeguard is to check coverage before training rather than after. A pose solution that used only half the photographs is a signal worth acting on.

    Red flagRelying on the result looking wrong. From the captured angles it will look fine, which is exactly the problem.

  4. Somebody views it from an angle nobody photographed.

    It will render something, and there is no signal that it is invented. The representation has no notion of unobserved space, so a gap in coverage looks like a smooth surface. For a product catalogue that matters, because the unphotographed side is often the underneath.

    Red flagCalling it interpolation. It is extrapolation with no uncertainty attached, and it is the failure a buyer actually encounters.

  5. The viewer's phone cannot hold the frame rate.

    In a headset that is not a quality issue, it is a comfort issue, and people stop within a minute. The lever is the number of blobs, so ship a reduced set for weaker devices. Deciding that from device capability before download is better than discovering it at runtime.

    Red flagReducing resolution instead. Fewer blobs helps the sort and the blending together, and resolution only helps one of them.

  6. How do you catch a bad reconstruction without a person looking?

    Hold out some photographs, render from their camera positions, and compare. That gives a number per object and it catches the bad cases well. It will not catch a scene that is consistently wrong everywhere, which is why a human check on a sample stays in the loop.

    Red flagChecking only the training views. Those are what it was fitted to, so they always look good.

  7. Defend the thirty per cent.

    Only by restating it. Name the metric, give both values, say how many scenes. If it was peak signal-to-noise ratio then a percentage is the wrong unit, since that number is decibels on a log scale. I would rather correct my own bullet than defend a percentage with nothing attached.

    Red flagStanding behind the figure as written. It is the one number on this line that an expert will question immediately.

  8. What would you change?

    Put a unit on the quality number, or take it out. Say which stage of the hundred minutes dominates, because that is the detail that proves you ran it. And add the held-out view check, since an automatic quality gate is what turns one object into a hundred.

    Red flagAdding another technique to the list. Four named methods in one sentence is already more surface than the sentence can defend.

Probes to expect

  1. “Three weeks to a hundred minutes. How?” The first question and the one that goes wrong if you answer it as an algorithmic speedup.
    Model answer — say yours first

    By replacing a person with a fitting procedure. Three weeks was somebody modelling the object by hand in a 3D package. A hundred minutes is recovering camera poses from photographs, fitting a radiance field, and preparing it for delivery. Nothing got three hundred times faster. The bracketed figure in the bullet says it more honestly, because ninety-eight per cent less manual effort is a labour claim and labour is what actually changed.

  2. “What is a NeRF, in your own words?” A definitional question. Saying it without reaching for the word mesh is what shows you used one.
    Model answer — say yours first

    It fits a function rather than reconstructing a shape. Give it a point in space and a direction you are looking from, and it returns a colour and how solid things are there. To render a pixel you walk along its ray, ask that function at many points, and accumulate colour weighted by density until the ray is blocked. Training minimises the difference between rendered pixels and the real photographs. And it is a fit per scene, so every object is its own training run.

  3. “Why is splatting real-time and a NeRF is not?” Where people conflate the two speed problems. Keep them separate.
    Model answer — say yours first

    Because it stops marching rays. A radiance field needs dozens of samples per pixel, each one a network evaluation. Splatting represents the scene as a few million fuzzy blobs with a position, a shape, an opacity and a colour, and rendering means projecting them onto the screen and blending. Graphics hardware is built for exactly that. The cost it pays instead is a depth sort every frame, per view, because blending semi-transparent things is order-dependent.

  4. “What actually fails in production?” Separates having run this from having read about it. The answer is two stages upstream.
    Model answer — say yours first

    Camera pose estimation, nearly every time. It matches features between photographs, so it needs texture, and a plain wall or a reflective surface or photos taken too far apart all break it. The worst part is that it reports success and produces poses anyway. The symptom appears two stages later as a soft or ghosted reconstruction, which looks like a model problem. That is why the real deliverable was a capture protocol rather than a parameter setting.

  5. “Thirty per cent better quality on what?” The one number with no unit. Correct it yourself before this gets asked.
    Model answer — say yours first

    That is the figure I would restate. If it came from peak signal-to-noise ratio then a percentage is the wrong unit, because that number is decibels on a log scale and a percentage of it does not mean anything stable. The defensible version names the metric, gives both values, and says how many scenes it was measured over. If it came from a perceptual metric instead, that is worth saying, because those track what people actually see rather more closely.

Chapter 0012 made an argument about numbers without a denominator. What is the same argument here?

A percentage with no metric attached is the same failure as an accuracy with no denominator. Thirty per cent better render quality does not say better on what, measured over how many scenes, against which baseline. And if the underlying metric is peak signal-to-noise ratio, then a percentage is not merely unstated but wrong, because that number is decibels on a log scale. The fix in both chapters is identical: name the measure, give both values, and say what it was measured over.

Chapter 0012 · a number needs its denominator
Chapter 0010 did memory arithmetic for a model. Do the equivalent arithmetic for a scene in a browser.

Each blob carries a position, a covariance, an opacity and colour coefficients, which is a couple of hundred bytes. A few hundred thousand of them lands in the tens to low hundreds of megabytes, before any compression. That is a download on a phone rather than an instant load. The levers are the same shape as quantization: fewer items, and fewer bits per item. And unlike a model, the count is tunable per device. That is how a weaker phone still gets a viewable scene.
