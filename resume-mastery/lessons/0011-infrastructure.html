Infrastructure

The strongest infrastructure claim on this résumé is that the same team picked two different deployment targets for two services, and can say why. The weakest is everything that is missing: no messaging layer, no cache, one region, one database. Both halves get asked.

The win

Defend two deployment choices on the property of the workload rather than on preference — and name the four layers your architecture does not have, before an interviewer draws the diagram and notices.

The line being defended
“Python/FastAPI, async SQLAlchemy, PostgreSQL, GKE” — and the deployment claims distributed across the experience bullets: Cloud Run with IAP, Helm, Terragrunt, Cloud Build, Snowflake, BigQuery.

Say it out loud · about 75 seconds

For “walk me through your infrastructure.” Lead with the two-target decision, because it is genuinely good. Then volunteer the gaps, because an interviewer will draw the diagram and see them anyway.

  1. Situation

    Two services at CloudSufi went to two different places, and the reason is the useful part.

    The vendor platform is on Kubernetes. The schematization pipeline is on Cloud Run.

  2. Mechanism

    The deciding property is state. One remembers things between requests and one forgets immediately.

    The platform holds streaming connections and session state per interview. Its Helm release bundles a migration job that must finish before new pods serve.

    That removes the window where new code meets an old schema.

    The pipeline runs one request for forty-five seconds and ends, so a proxy does authentication and there is no cluster to own.

  3. What I did

    Terragrunt provisions the cluster, the managed Postgres and the secret store.

    Helm carries the deployment, the autoscaler, ingress, external secrets and that job as one release.

    The predecessor to the platform actually ran on Cloud Run, and what moved it was session lifetime rather than scale.

  4. What it cost

    Four things this architecture does not have, and I would rather list them myself.

    No messaging, so post-interview scoring is in-process and lost if the pod dies. No cache, though the blind research pass is identical per vendor.

    One region and one Postgres with no replicas. And no identity model beyond a proxy and a service key, on a platform that is multi-tenant by nature.

The sentence that sounds fluent and gets you caught

“It's deployed on GKE with Helm and Terraform.” True, and it describes a deployment rather than a decision. The follow-up is “why Kubernetes?” and the weak answer is scale. The strong answer is session lifetime, and it is available to you because the predecessor was on Cloud Run and moved for exactly that reason.

The other trap is answering “how would you scale this?” with replicas and pods. For this system the first three bottlenecks are third-party rate limits, the connection pool and the model provider's quota. More pods make the first one worse, and saying so is what separates an answer from a reflex.

Walk them through it · one deploy, end to end

The say it out loud block is ninety seconds. This is the ten minutes after that, when they say “walk me through it.” One commit, followed to the moment it serves a live interview. Then the layers this architecture does not have, named before anyone draws the diagram.

The picture. Two house moves. One is a hotel with guests still asleep in the rooms. The other is a self-storage unit. The lorries are identical and the problem is not, and the difference is whether anything is mid-conversation.

The case. A change to the interview platform, which is the hotel. Follow it out. Then contrast it with the schematization pipeline, which is the storage unit, because those two went to different places on purpose.

  1. Underneath

    What happens. Before any code ships, the things it runs on have to exist.

    Concretely. Terragrunt provisions the cluster, the managed Postgres and the secret store, as files rather than as clicks in a console.

    If they ask why. A new environment becomes a directory of values instead of a week of work, and every production change arrives as a diff somebody can review.

  2. The build

    What happens. The commit is built into a container image by Cloud Build.

    Concretely. That image carries the Python version, the libraries and the system packages, so nothing is installed on a machine by hand.

  3. The release

    What happens. A Kubernetes deploy is not one file. It is a deployment, a service, an ingress, an autoscaler, secrets and a job.

    Concretely. Helm bundles all of that into one release. It versions together and it rolls back together.

    If they ask why. One command puts the previous version back. That is the difference between a rollback taking seconds and taking an outage.

  4. The migration

    What happens. Inside that release is a job that runs the database migrations, and it must finish before new pods take traffic.

    Concretely. This is the detail worth having ready. It removes the window where new code meets an old schema.

    If they ask why. A deploy that ships code against the wrong schema fails in a way that is genuinely hard to diagnose. Plain apply has no opinion about ordering. A Helm hook does.

  5. The pods

    What happens. New pods start, take traffic, and the old ones go away.

    Concretely. Credentials are pulled from the secret manager at runtime, so nothing sensitive is in the repository or in the image.

  6. The other one

    What happens. Now the contrast, which is the strongest infrastructure answer on the page.

    Concretely. The schematization pipeline runs on Cloud Run. One request runs for forty-five seconds and ends. A proxy does the authentication and there is no cluster to own.

    If they ask why. The deciding property is state. One service remembers things between requests and one forgets immediately.

  7. Why it moved

    What happens. The platform's own predecessor ran on Cloud Run quite happily, and what moved it was not scale.

    Concretely. The product version holds a streaming connection for the length of a live interview and keeps session state per interview on the server.

    If they ask why. A long-lived connection and an in-memory session change what a deploy means. They also change what scaling down does to somebody mid-sentence.

  8. The pool

    What happens. One trap in this stack is worth naming before it is asked about.

    Concretely. The connection pool is finite. A request that holds a database connection across a slow model call takes it out of circulation for seconds.

    If they ask why. That is the most likely capacity bug here. The service looks idle and the pool is empty.

  9. What is missing

    What happens. Four layers this architecture does not have. I would rather list them than have them found.

    Concretely. No messaging, so post-interview scoring runs in-process and is lost if the pod dies. No cache, although the blind research pass is identical for a given vendor.

    If they ask why. One region and one Postgres with no replicas. And no identity model beyond a proxy and a service key, on a platform that is multi-tenant by nature.

  10. The price

    What happens. Moving to a cluster was not free either.

    Concretely. It is a cluster to own, which is real operational weight for a service at this volume.

    If they ask why. And the migration ordering is forward-only. Rolling the code back does not roll the schema back, so migrations have to stay compatible with the previous version. That is a discipline rather than a guarantee.

Start here — the plain version

Every service on this résumé is one application talking to one database in one region. That is a completely normal shape. It is also the thing a senior interviewer will probe. The interesting questions are all about what happens when it stops being enough.

What is genuinely strong here is that two services went to two different places, for stated reasons. What is worth preparing is the list of layers that are simply absent. Naming them first is far better than having them found.

GKE
Google's managed Kubernetes. You get a cluster of machines and describe what should run on it. Worth it when you need control over pods, scaling and lifecycle.
Cloud Run
Containers without a cluster. It scales to zero, handles one request shape well, and takes most of the operational burden away.
Helm
Packaging for Kubernetes. One release bundles the deployment, autoscaler, ingress, secrets and any jobs, so they version and roll back together.
Terragrunt
A wrapper over Terraform for describing the cloud resources underneath: the cluster itself, the managed database, the secret store.
Migrate job
A Kubernetes job that runs database migrations and must finish before new pods serve traffic. It is what stops a new version meeting an old schema.
HPA
Horizontal pod autoscaler. Adds and removes pods based on a signal like CPU. Useless for a stateful session unless something keeps the session with its pod.
IAP
Identity-Aware Proxy. Authentication in front of a service, so the service itself does not implement login. Used on the schematization pipeline.
External secrets
Pulling credentials from a secret manager into the cluster at runtime, so they are never in the repository or the image.
Connection pool
A fixed set of database connections shared by requests. Finite, which is why holding one across a slow model call is a capacity problem.
Stateful session
Work where the server remembers something between requests. It constrains deploys, load balancing and scaling far more than a stateless request does.
The technology — what each named thing is

The primer above defines the managed products. This one goes a layer down, to the objects and the pipeline those products are made of. An infrastructure claim is the easiest on the résumé to test, because the interviewer can simply ask you to name things.

Every entry answers four things. What it actually is, in plain words. Where this system uses it. What it buys, meaning what goes wrong without it. And the follow-up an interviewer asks once you have said the name.

Pod, Deployment, Service
the three you always needThree objects that between them describe almost any running service. A pod is one or more containers that share a network address and can share a disk, and it is the smallest unit Kubernetes will schedule. A Deployment says how many identical pods should exist, recreates them when they die, and replaces them gradually when the image changes. A Service gives that changing set of pods one stable address and spreads traffic across whichever are currently healthy. In the app. This is the minimum vocabulary for describing what the Helm chart installs. What it buys. A separation of concerns you get for free: what runs, how many, and how it is reached are three independent things you can change without touching the others. The follow-up. Pods are disposable and their addresses change every time one is replaced. The Service exists precisely because nothing should ever hold onto a pod's IP address.
Ingress
the way inA Service is reachable inside the cluster, which is not much use on its own. An Ingress is the rule set that maps an external hostname and URL path to a Service, and terminates TLS on the way through. On GKE it is implemented by a real Google load balancer created on your behalf. In the app. It is the object that makes the cluster reachable from the internet at all. What it buys. One load balancer and one certificate serving many services, routed by host and path, instead of a public address per service. The follow-up. Timeouts live here, and this is where a streaming workload dies. A load balancer with a short idle timeout will cut a long-lived connection regardless of what the application is prepared to do, and that is the very first failure a session-based workload runs into.
Namespace and RBAC
the boundariesA namespace is a partition inside one cluster. Names are unique within it rather than across the cluster, and quotas and limits can be set per namespace. RBAC is the permission system: a role is a list of allowed verbs on particular resource types, and a binding attaches that role to a user or a service account. In the app. Together they are what make one cluster safe to share between environments and teams. What it buys. One cluster instead of five, with the operational and cost savings that implies, without every team being able to delete every other team's work. The follow-up. A namespace is not a security boundary on its own. By default pods in one namespace can reach pods in another over the network. Network policy and RBAC are what actually separate them, and neither is enabled by default.
Rollout strategies
rolling, blue-green, canaryThree ways to replace a running version. Rolling swaps pods a few at a time, so for a while both versions are serving traffic together. Blue-green stands the entire new version up beside the old one and flips all traffic at once, which makes rollback instant and doubles the resources needed. Canary sends a small percentage to the new version, watches the metrics, and widens only if they hold. In the app. The migrate job exists precisely because rolling means two versions share one database. What it buys. Deployment without a maintenance window, and a defined way back when it goes wrong. The follow-up. Two constraints here, not one. A migration the old version cannot survive rules out plain rolling. A live interview session rules out replacing the pod holding it. Draining connections and expand-then-contract schema changes are the two answers.
Cloud Build
cloudbuild-{dev,prod}.yamlGoogle's continuous integration runner. A build is a YAML file listing steps, where each step is a container image with arguments, and every step shares one workspace directory. It triggers on a commit and runs in Google's infrastructure rather than yours. In the app. It is what turns a commit into a container image and then into a Helm release. What it buys. No build servers to own, and native credentials into Artifact Registry and the cluster without secrets being copied around. The follow-up. What the pipeline actually contains, step by step. Build, test, push, deploy is the honest minimum. If there is no test step in it, say so directly rather than letting the word CI imply one that is not there.
Artifact Registry
where images liveGoogle's storage for container images and language packages. The image you built has to be somewhere the cluster can pull it from, and this is that place. Every image has a content-addressed digest, which is its real identity, and any number of human-readable tags pointing at it. In the app. It is the handover point between build and run. What it buys. A single place with access control, vulnerability scanning and retention rules, sitting in the same project as the cluster that pulls from it. The follow-up. Tags against digests. A tag can be moved to point at a different image, so deploying :latest means you genuinely cannot say what is running right now. Pinning the digest is what makes a rollback exact rather than approximate.
Workload Identity
keys you do not haveA binding that lets a Kubernetes service account impersonate a Google service account. A pod running under that Kubernetes account asks the node's metadata server for a token, and gets a short-lived credential for the Google account. No key material is ever stored, mounted or transferred. In the app. It is how pods reach Cloud SQL and Secret Manager. What it buys. Credentials that expire on their own and rotate without anybody doing anything. There is nothing to leak, because there is no file. The follow-up. What it replaces, which is the part worth saying. A downloaded JSON key file that never expires, is hard to rotate, ends up in an environment variable or a laptop, and is the single most common route into a compromised cloud account.
Terraform state
the file that mattersTerraform's own record of what it believes it has created, mapping each resource in your configuration to a real id in the cloud. Without it, Terraform cannot tell a resource it should update from one it should create. It is normally kept in a bucket rather than on a laptop, with a lock so two people cannot write it at once. In the app. Terragrunt's per-environment layout is largely about keeping these separate and configured once rather than copied. What it buys. Shared truth. Everyone and every CI run plans against the same picture of reality, which is what makes infrastructure a team activity rather than one person's machine. The follow-up. Two people applying at once. Without locking, one overwrites the other's view of what exists, and the recovery is manual import rather than simply running it again.
Redis
the in-memory oneA data store that keeps everything in memory, which makes it roughly a thousand times faster than a disk-backed database and means it loses data on restart unless you configure otherwise. It is single-threaded, so operations are atomic without locking, and that is why it is the standard answer for counters, rate limits, queues and distributed locks. In the app. It is the usual answer for state shared between replicas that Postgres should not be asked to hold. What it buys. Coordination between replicas at microsecond cost, which lets stateless services stay stateless. The follow-up. What happens when it restarts. If it is a cache, nothing, the data is refetched. If it is holding sessions or locks, you have just created an outage. Which of the two it is matters far more than the product name.
BigQuery and Snowflake
two warehousesBoth are analytical databases, both store data by column rather than by row, both separate storage from compute, and both speak SQL. The difference is what you manage. BigQuery has no cluster at all: you submit a query and Google finds the machines, billing mainly on how many bytes it had to read. Snowflake gives you named warehouses that you size, start and stop, and bills per second that one is running. In the app. This résumé touches both. What it buys. Scan-heavy analytics at a speed no transactional database reaches, on data nobody has to shard. The follow-up. The cost lever is different in each. On BigQuery you reduce bytes read, with partitioning and clustering. On Snowflake you shut the compute down when nobody is using it.
Observability
logs, metrics, tracesThree signals that answer three different questions. Logs are timestamped events with text, good for detail and expensive at volume. Metrics are numbers sampled over time, cheap to store for years and the right thing to alert on. Traces follow one single request across every service it touched, with timing at each hop, and they are the only one of the three that tells you where the time actually went. In the app. Every latency claim on this résumé was measured with one of these. What it buys. The ability to answer questions you did not anticipate, which is the difference between monitoring and observability. The follow-up. Which you would add first to a system that has none. Metrics tell you something is wrong. Traces tell you where. Most systems have the first and not the second, which is why incidents take hours.

Two services, two targets, two reasons

The vendor platform runs on Kubernetes. The schematization pipeline runs on Cloud Run. That difference is the best infrastructure answer on the page, because it shows the choice was made rather than inherited.

The vendor platform has long-lived streaming connections during interviews, server-side session state per interview, and a migration that must complete before the new version serves. Helm bundles the deployment, the autoscaler, ingress, external secrets and that migrate job into one release. Terragrunt provisions the cluster and the managed database underneath.

The schematization pipeline is the opposite shape. A request arrives, runs for about forty-five seconds, and ends. Nothing is remembered. So it runs on Cloud Run with IAP in front, two vCPU, four gigabytes, a 3600-second timeout and concurrency 80. No cluster to own, authentication handled by the proxy, and it scales to zero.

Say the deciding property rather than the technology. One is stateful and one is not. Everything else follows from that.

Plain meaningOne service remembers things between requests and one forgets immediately. That single difference decides where each one should live.

The migrate job, which is the detail worth having

A deploy that ships new code against an old schema fails in a way that is hard to diagnose. Put the migration inside the release, as a job that must finish first. That removes the race entirely.

Helm's release includes the migrate job alongside the deployment. The job runs to completion before the new pods accept traffic. So there is never a window where a new binary is querying a table that does not have its column yet.

The honest limit is worth volunteering too. This ordering protects the forward direction. It does not make the migration itself reversible, and a rollback of the code does not roll back the schema. That is why migrations have to be written to be compatible with the previous version, not just with the next one.

Plain meaningChange the shape of the database before the new code arrives, not at the same time. And remember that going back is a separate problem.

The four things that are not there

No messaging layer. No cache. One region and one database. No identity system beyond a proxy. Each of those is a real gap and each one has a good answer if you get there first.

No messaging. Background work is an in-process background task handed off before the response returns. That works and it means work is lost if the pod dies mid-flight. A queue would make it durable, and the honest framing is that the failure mode was acceptable rather than that the queue was unnecessary.

No cache. The blind research pass is identical across interviews with the same vendor and it is recomputed every time. Adding a cache there is the obvious win, and it brings stampede and penetration with it.

One region, one Postgres. No replicas, so there is no read scaling and no failover story. That is fine at current volume and it is the first rung of a ladder nobody has climbed.

Authentication is a proxy. IAP in front of the schematization pipeline, and a service-to-service key on the gateway. There is no user identity model, no roles, and no per-tenant authorisation, which for a multi-tenant vendor platform is a question worth having an answer to.

Plain meaningFour layers most mature systems have, that these do not. Say them yourself and they read as known trade-offs rather than blind spots.

The async database trap

Async SQLAlchemy over asyncpg is on the résumé, and the question it invites is about pooling. A connection held across a model call is the most likely capacity bug in this whole stack.

A pool is a fixed number of connections. A request that takes one, then awaits a model call for several seconds, then releases it, has held a scarce resource for the duration of something that did not need a database at all.

Under load that exhausts the pool, and the symptom is requests queuing for connections rather than for the model. It looks like a database problem and it is a code-structure problem. The fix is to scope the session tightly around the query, not around the handler.

The related rule from chapter 0001 is the other half. Work that outlives its request cannot borrow the request's session, because the middleware has already closed it. Nine places in that codebase open their own for exactly that reason.

Plain meaningDo not hold a seat at the table while you go and make a phone call. Someone else needed that seat.

  1. Name the Kubernetes objects a web service needs, and say what each does.

    A pod is one or more containers sharing a network address, and it is the smallest thing Kubernetes will schedule. A Deployment says how many identical pods should exist, recreates them when they die, and replaces them gradually when the image changes. A Service gives that changing set one stable address and spreads traffic across whichever are healthy. An Ingress maps an external hostname and path to that Service and terminates TLS. What the split buys is independence. What runs, how many, and how it is reached are three things you change separately. Pods are disposable and their addresses change, which is exactly why nothing holds a pod's IP.

    Red flagSaying “we deploy containers to Kubernetes.” Name the objects. Four nouns is the whole answer and not having them is very visible.

  2. Rolling, blue-green, canary. What is the difference, and which do you run?

    Three ways to replace a running version. Rolling swaps pods a few at a time, so for a while both versions serve together. Blue-green stands the entire new version up beside the old one and flips all traffic at once, making rollback instant and doubling the resources. Canary sends a small percentage to the new version, watches the metrics, and widens if they hold. What any of them buys is deployment without a maintenance window, and a defined way back. A Deployment rolls by default, and that default is the problem here. A long session gets cut mid-interview, so old pods are drained rather than replaced.

    Red flagReciting the three and not saying which one this workload survives. The overlap window is what the migrate job and the session pinning both exist for.

  3. What does Cloud Build actually do here?

    It is Google's continuous integration runner. A build is a YAML file listing steps, where each step is a container image with arguments and every step shares one workspace. It triggers on a commit and runs in Google's infrastructure rather than yours. Here it builds the image, pushes it to Artifact Registry, then deploys, with a file per environment. What it buys is no build servers to own, and native credentials into the registry and the cluster with no secrets copied around. If there is no test step, say so rather than letting the word CI imply one. An honest description of a thin pipeline beats an implied one that does not exist.

    Red flagSaying “we have CI/CD” and stopping. Both letters are separate claims and the interviewer usually only cares about the second.

  4. What is deployed, the tag or the digest?

    The image you built has to live somewhere the cluster can pull it from, and that is Artifact Registry. Every image there has a content-addressed digest, which is its real identity, plus any number of readable tags pointing at it. A tag is a movable label. If you deploy a tag, you cannot say with certainty what is running, and two clusters on the same tag can differ. What pinning the digest buys is an exact rollback rather than an approximate one. It also makes an incident timeline trustworthy, because the version in the log is the version that ran.

    Red flagDeploying :latest and not flagging it. It is a common shortcut and naming it as one is better than being asked.

  5. What is Workload Identity, and what does it replace?

    A binding that lets a Kubernetes service account impersonate a Google one. A pod running under that account asks the node's metadata server for a token and gets a short-lived credential. No key material is ever stored, mounted or transferred. What it buys is credentials that expire on their own and rotate with nobody doing anything. There is nothing to leak, because there is no file. It replaces a downloaded JSON key file. That file never expires, is awkward to rotate, and ends up in an image, an environment variable or a laptop. Leaked static keys are one of the most common routes into a cloud account.

    Red flagDescribing it as convenience. It is the credential lifetime that matters, and the argument is a security one.

  6. Where does Terraform state live, and why does it matter?

    Remotely, in a bucket, with locking. State is Terraform's record of what it believes it created, mapping each resource in your configuration to a real id in the cloud. Without it, Terraform cannot tell a resource it should update from one it should create. What keeping it remote buys is shared truth. Everyone and every CI run plans against the same picture, which is what makes infrastructure a team activity rather than one laptop. It matters because two people applying at once without a lock means one overwrites the other's view of reality. Recovery is manual import, not a rerun. State is also secret, because it holds resource attributes.

    Red flagLocal state, or state with no lock. Both work until the second engineer arrives, which is the moment this question is really about.

  7. BigQuery and Snowflake are both warehouses. What actually differs?

    Both are analytical databases storing data by column rather than by row, both separate storage from compute, and both speak SQL. Columnar storage is what makes them fast, because a query reading three columns of two hundred pays for three. The difference is what you manage. BigQuery has no cluster at all. You submit a query, Google finds the machines, and you are billed mainly on bytes read. Snowflake gives you named warehouses that you size, start and stop, billed per second one is running. So the cost lever differs. On BigQuery you read fewer bytes, with partitioning and clustering. On Snowflake you turn the compute off.

    Red flagComparing them on speed. They are close enough that the operational and billing models are what you would actually choose on.

  8. The service is slow. What do you look at first?

    Three signals answer three different questions. Metrics are numbers sampled over time, cheap to keep for years and the right thing to alert on. They tell you something is wrong and roughly where in the stack. Traces follow one request across every service it touched, with timing at each hop. They are the only one of the three that shows where the time actually went. Logs are events with text, good for detail and expensive at volume. So the order is metrics, then traces, then logs. Most systems have good metrics and no tracing, which is why incidents take hours. That gap is the honest answer if it is yours.

    Red flagStarting with logs. Grepping is what you do when you already know where to look, and at this point you do not.

  1. What infrastructure do you actually own?

    For the vendor platform, the whole path. Helm charts for the deployment, autoscaler, ingress, secrets and migrate job. Terragrunt for the cluster, the managed Postgres and the secret store. Cloud Build for the pipeline. For the schematization service, a Cloud Run deploy behind IAP.

  2. Why Kubernetes for the vendor platform?

    Long-lived streaming connections during interviews, and server-side session state per interview. Plus a migration that has to complete before the new version serves. Helm gives the deployment, HPA, ingress, external secrets and that job as one release. The predecessor ran on Cloud Run, and session lifetime is what moved it.

    Red flagCiting scale. The volume does not require a cluster. Session lifetime and release composition do.

  3. And why Cloud Run for the schematization pipeline?

    Because it is the opposite shape. A request runs about forty-five seconds and ends, and nothing is remembered between requests. Two vCPU, four gigabytes, a 3600-second timeout, concurrency 80, with IAP handling authentication. There is nothing stateful, so there is nothing a cluster would buy.

    Red flagFraming it as the simpler option. It is the correct option for a stateless workload, and the reason is the property rather than the effort.

  4. Helm and Terragrunt do different jobs. Which is which?

    Terragrunt provisions what is underneath: the cluster, the managed database, the secret store. Helm describes what runs on top of it. The boundary is roughly whether something survives a redeploy of the application. Infrastructure is slow and rare, releases are fast and frequent.

    Red flagTreating them as alternatives. They operate at different layers and using both is the normal arrangement.

  5. Why is the migration a job inside the release?

    So the schema is ready before any new pod serves traffic. It runs to completion first, which removes the window where new code meets an old schema. The limit worth saying is that it protects the forward direction only. Rolling the code back does not roll the schema back.

    Red flagCalling it automated migrations. The ordering guarantee is the feature, not the automation.

  6. How are secrets handled?

    External secrets pulled from the secret manager into the cluster at runtime, provisioned by Terragrunt. Nothing credential-shaped is in the repository or baked into an image. That also means rotating a secret does not need a rebuild, which is the practical benefit people forget to mention.

    Red flagOnly saying they are not in the repo. Rotation without a rebuild is the operational argument.

  7. How does code get from a merge to production?

    Cloud Build, with separate configurations for development and production. It builds the image and rolls the Helm release, which includes the migrate job running first. For the schematization service it is a build and a Cloud Run deploy. Both are one command rather than a runbook.

    Red flagDescribing CI and CD as one thing. Being able to say what happens between merge and traffic is the answer.

  8. Which datastores across all this work?

    PostgreSQL for the vendor platform's relational core. Snowflake as the warehouse the pipeline debugger queries and validates against. BigQuery as the migration target for the lineage work. ChromaDB as the vector store for past incidents. Four stores with four different jobs.

    Red flagListing them flat. Naming what each one is for is what shows they were chosen rather than inherited.

  9. What is missing from this architecture?

    Four things and I would rather list them than be asked. No messaging layer, so background work is in-process and lost if the pod dies. No cache, though the blind research pass is identical across interviews. One region and one Postgres with no replicas. And no user identity model beyond a proxy and a service key.

    Red flagWaiting to be asked. Volunteering the gaps is what makes the rest of the answer credible.

  10. What is the riskiest infrastructure claim?

    Not a claim but an absence. The vendor platform is multi-tenant by nature, since different buyers evaluate different vendors. There is no per-tenant authorisation model beyond what the application does itself. That is the question I would most want to have thought about before being asked.

    Red flagNaming a technology you listed. The exposure here is the layer that is absent, not the one that is named.

Deep dive

Half of these are about the gaps. A senior interviewer spends most of an infrastructure conversation on what is not there.

  • Pooling across a model call
  • Sessions that outlive requests
  • Deploying a stateful service
  • HPA on a stateful pod
  • Rolling a migration back
  • Where a queue would go
  • Where a cache would go
  • The scaling ladder
  • Multi-tenancy
  • Config in charts
  • What you would observe
  • The first thing to add

  1. What happens if a request holds a database connection across a model call?

    It holds a scarce resource for seconds while doing nothing with it. The pool is fixed, so under load it empties and requests queue for connections rather than for the model. It presents as a database problem and it is a code-structure problem. The fix is to scope the session around the query, not the handler.

    Red flagSuggesting a bigger pool. That moves the load onto the database and delays the same failure.

  2. Why can background work not use the request's session?

    Because the middleware opens one session per request and commits or rolls back when the request ends. A background task is handed off before the response returns, so by the time it writes, that session is closed. Using it is a use-after-free with a friendly error message. Nine places in the vendor codebase open their own.

    Red flagTreating it as an async quirk. It is lifecycle: the scope ended and the work did not.

  3. How do you deploy a service holding live interview sessions?

    Session draining is the requirement. Stop admitting new interviews to a pod, let the existing ones finish, then cycle it. A turn is short but a session is long, so a normal rolling update would cut somebody off mid-interview. Version pinning per session is the next pattern I would reach for.

    Red flagDescribing a standard rolling update. It is exactly what does not work here, and that is why the question is asked.

  4. Does the autoscaler help a stateful service?

    Only for adding capacity, not for removing it. Scaling up gives new sessions somewhere to land. Scaling down kills pods holding live sessions unless something drains them first. So the autoscaler and the session lifetime have to be reconciled, and a pure CPU signal does not know a session exists.

    Red flagSaying the HPA handles it. Scale-down is the dangerous direction and a CPU metric is blind to sessions.

  5. You roll back a deploy. What happens to the migration?

    Nothing. It already ran, and the code rollback does not undo it. The ordering guarantee is forward-only. So migrations have to be written compatible with the previous version too. In practice that means additive changes first, and destructive changes in a later release once nothing reads the old shape.

    Red flagAssuming a down migration exists and is safe. Most are not exercised, and running one under pressure is its own incident.

  6. Where exactly would you put a queue?

    Between the interview ending and the scoring pipeline starting. Today that is an in-process background task handed off before the response returns, so if the pod dies the scorecard is simply lost. A queue makes it durable and retryable, and it decouples scoring capacity from serving capacity.

    Red flagAdding a queue everywhere. One specific handoff with a real durability gap is a much better answer.

  7. And a cache?

    On the blind research pass, because it is identical across interviews with the same vendor and its miss path is a multi-second web fan-out. That immediately brings two problems. A popular vendor gives a stampede, so it needs single-flight. And a vendor with no public footprint returns empty forever, which is cache penetration.

    Red flagProposing the cache without its failure modes. Naming stampede and penetration unprompted is the senior half.

  8. One Postgres, one region. What is the ladder from here?

    Read replicas first, since scoring and reporting are read-heavy and can tolerate lag. Then connection pooling in front, because replicas multiply connection pressure. Then partitioning the tables that actually grow, which is evaluations rather than rubrics. Multi-region last, because it changes the consistency story rather than the capacity one.

    Red flagStarting with sharding. It is the last rung and naming it first suggests the ladder has not been thought about.

  9. The vendor platform is multi-tenant. How is that enforced?

    In the application, by scoping every query to a workspace. There are permission and tenancy tests, so it is checked rather than assumed. What does not exist is an enforcement layer below that, like row-level security in the database. So a query written without the filter is a data leak and only a test stands in the way.

    Red flagSaying it is handled. Saying where it is enforced, and what would catch a mistake, is the real answer.

  10. Feature flags live in values files rather than in code defaults. What does that cost?

    The source stops describing what runs. Streaming defaults to false in code and true in both environments, so a reader of the repository gets the wrong answer. It is a good rollout pattern, because enabling is a config change and rollback is a value change. The price is that the default in the source is misleading.

    Red flagOnly praising the pattern. The misleading default is a real cost and naming it shows you read the charts.

  11. What would you put on a dashboard for these services?

    Not error rate, because the gateway always returns success. Internal signals instead: canned-reply rate, fallback-model usage, retry rate, and per-turn latency percentiles. For the pipeline, the fraction of runs exiting on stagnation or exhaustion rather than success. Choosing to always succeed means building your own definition of failure.

    Red flagListing standard golden signals. For a service that never returns an error, error rate is structurally blind.

  12. One thing to add. What and why?

    The queue for post-interview scoring. It closes a real durability gap, where a scorecard can be lost entirely. It is a well-understood component, and it decouples two capacities that currently scale together. The cache is a bigger performance win, and it carries stampede and penetration with it, so it is second.

    Red flagChoosing the biggest win. Choosing the one that closes a correctness gap first is the better instinct and easier to defend.

The vendor platform runs on GKE and the schematization pipeline on Cloud Run. What is the deciding difference?

  1. One holds long sessions, while the other is stateless
  2. One is cheaper to operate at that request volume
  3. One was chosen before the other team had migrated
  4. One runs containers, and the other only plain code

State. The vendor platform holds long-lived streaming connections and server-side session state per interview, and its release bundles a migration that must finish before new pods serve. The pipeline runs one request for about forty-five seconds and remembers nothing.

Cost is not the reason, and both targets run containers. The predecessor to the vendor platform was on Cloud Run, and what moved it was session lifetime rather than scale or price.

The Helm release includes a migration job that runs to completion before new pods serve. What does that guarantee?

  1. The schema is ready before any pod accepts traffic
  2. The database is backed up before the rollout begins
  3. The old pods drain before new ones are started
  4. The migration can be retried without a fresh deploy

Ordering. There is never a window where a new binary queries a table that does not yet have its column, because the job finishes first. That removes a class of deploy failure that is otherwise intermittent and miserable to diagnose.

It says nothing about draining, backups, or rollback. In particular the guarantee is forward-only: rolling the code back does not roll the schema back, which is why migrations still have to stay compatible with the previous version.

Edges and exceptions

Almost all of these are failure questions, because that is what an infrastructure interview is.

  • A pod dies mid-interview
  • The database is unreachable
  • A migration that fails halfway
  • Sticky sessions
  • Ten times the interviews
  • A leaked tenant boundary
  • Cost
  • What you would change

  1. A pod dies during a live interview. What is lost?

    The session state for that interview, and any post-interview scoring already handed off in-process. The conversation cannot resume on another pod because nothing external holds the state. That is the cost of keeping session state in memory, and it is the strongest argument for the queue and for externalising session state.

    Red flagSaying Kubernetes restarts it. A restarted pod does not have the old pod's memory.

  2. Postgres becomes unreachable. What does the gateway do?

    Returns a canned reply and a 200, because after authentication the route never fails. So the interview continues and nothing is persisted. That is right for the conversation. It also means a database outage is invisible from the outside. Which is exactly why error rate is useless here and internal signals are not.

    Red flagDescribing a 500. The design deliberately does not do that, and the consequence for monitoring is the interesting part.

  3. The migrate job fails halfway.

    New pods do not serve, which is the correct outcome. The old version keeps running against the old schema, assuming the migration is transactional or was partially applied in a compatible direction. The dangerous case is a migration that is neither, leaving a schema that matches neither version.

    Red flagAssuming all migrations are transactional. Some DDL is not, and that is where the genuinely bad outcome lives.

  4. Two turns of one interview hit two different pods.

    The second pod has no session, so the interview breaks. Session state is server-side per interview, so requests have to land consistently. That is a load-balancing constraint the architecture depends on, and it is the thing that would break first behind a naive round-robin balancer.

    Red flagAssuming the load balancer handles it. It has to be configured to, and knowing that dependency exists is the point.

  5. Ten times the interviews tomorrow. What breaks first?

    Not the pods. The outbound research, because every interview fans out to third-party search and fetch APIs. Those have their own rate limits, and nothing limits how many interviews are in flight. After that the connection pool, and then the model provider's quota. Adding replicas helps none of those.

    Red flagAnswering with horizontal scaling. The first three bottlenecks are all external limits that more pods make worse.

  6. A query ships without its workspace filter.

    One tenant sees another's data, and only a test stands between that and production. Tenancy is enforced in application code rather than in the database, so there is no second line. Row-level security would make the filter structural rather than conventional, and that is the change I would argue for.

    Red flagCiting code review. Review catches most of them, and structural enforcement catches all of them.

  7. Where does the money actually go?

    Model calls, not infrastructure. A cluster and a managed Postgres at this volume are a rounding error next to per-token costs. That is especially true of the pro-tier scoring pass and the Scout's fan-out. So cost optimisation means caching research and choosing model tiers, not resizing nodes.

    Red flagTalking about node sizing. For an LLM product the infrastructure bill is usually the small half.

  8. What would you change, in order?

    A queue for post-interview scoring, because a scorecard can currently be lost outright. Then row-level security for tenancy, so the boundary is structural. Then a cache on the blind research pass, with single-flight, since that is the biggest cost win. Replicas last, because nothing is read-bound yet.

    Red flagOrdering by size of win. Correctness gaps before performance gaps is the easier order to defend.

Probes to expect

  1. “Why Kubernetes? It sounds like this would run on Cloud Run.” A challenge disguised as a question, and a gift, because the predecessor did run on Cloud Run and moved for a nameable reason.
    Model answer — say yours first

    It did, and the proof of concept stayed there. What moved it was session lifetime. The product holds long-lived streaming connections during an interview and keeps session state per interview on the server, so a deploy or a scale-down can cut somebody off mid-sentence. The release also bundles a migration job that must finish before new pods serve. Our other service, the schematization pipeline, is stateless and is still on Cloud Run for exactly that reason.

  2. “How would you scale this to ten times the traffic?” Most candidates answer with replicas. The first three bottlenecks here are all external, and more pods make one of them worse.
    Model answer — say yours first

    Not by adding pods first. The first limit is outbound research: every interview fans out to third-party search and fetch APIs with their own rate limits, and nothing caps how many interviews are in flight, so more pods make that worse. Second is the connection pool, especially anywhere a session is held across a model call. Third is the model provider's quota. Admission control at the pipeline level comes before any horizontal scaling.

  3. “What is missing from your architecture?” Sometimes asked directly, more often implied. Having the list ready converts an audit into a conversation.
    Model answer — say yours first

    Four things. No messaging layer, so post-interview scoring is an in-process background task and it is lost if the pod dies. No cache, although the blind research pass is identical across interviews with the same vendor. One region and one Postgres with no replicas, so no read scaling and no failover. And no identity model beyond a proxy and a service key, on a platform that is multi-tenant by nature. The queue is the one I would add first, because it closes a correctness gap rather than a performance one.

  4. “How is tenant isolation enforced?” The sharpest of the four gaps, because the product is inherently multi-tenant and the enforcement is conventional rather than structural.
    Model answer — say yours first

    In application code, by scoping every query to a workspace, with permission and tenancy tests covering it. What does not exist is enforcement below that, like row-level security in Postgres. So a query written without the filter is a data leak with only a test in the way. I would argue for making the boundary structural rather than conventional, because that is the difference between catching most mistakes and catching all of them.

  5. “What would a deploy look like during a live interview?” A specific operational question that a candidate who only deployed once will not have thought about.
    Model answer — say yours first

    It needs session draining rather than a rolling update. Stop admitting new interviews to a pod, let the ones in progress finish, then cycle it. A turn is short and a session is long, so a standard rollout terminates somebody mid-interview. The migrate job already handles the schema ordering. What the release does not have is a drain step, and version pinning per session is the pattern I would reach for next.

Chapter 0003's pipeline chose Cloud Run and chapter 0001's chose GKE. State the deciding property, and name the one thing that would flip the schematization service onto a cluster.

The deciding property is state. The vendor platform holds streaming connections and session state per interview, and its release includes a migration that must land first. The schematization service runs one request for about forty-five seconds and remembers nothing. What would flip it is acquiring state or a long-lived connection, most plausibly the WebSocket progress channel becoming a session rather than a per-request stream, or the pipeline needing to resume a partially completed run.

That the standard golden signals are the wrong ones here. After authentication the gateway never fails, so every response is a 200 and error rate cannot move. The lessons behind this chapter

System Design School teaches these mechanisms from first principles and breaks them in a lab. This chapter defends what you did with them. An interviewer moves between those two registers without warning.

  1. SDS 0009 · Cache-aware routing A stateful session has to land on the same pod every turn, which is the load-balancing constraint this architecture quietly depends on.
  2. SDS 0003 · Cache-aside and friends Which of the four things in this stack is actually cacheable, and which one should never go near Redis.
  3. SDS 0005 · Stampede, penetration, avalanche The cache this architecture does not have would bring both failure modes with it on day one.
  4. SDS 0015 · The wait no timeout can see Async SQLAlchemy over asyncpg is exactly where connection pooling bites, and no timeout on the page would show it.
  5. SDS 0020 · The read that beat its own write One Postgres, one region. This is the first rung of a ladder nobody has climbed.
  6. SDS 0022 · A table before a broker The line names no messaging system at all. On GKE, Pub/Sub is the default, and a table in the Postgres you already run is what it has to beat.
  7. SDS 0037 · Terraform from zero — not yet built Terragrunt provisions the cluster and the database, and the layer below it is the cheapest claim on the page to make solid.
  8. SDS 0041 · Multi-tenant RBAC — not yet built Tenancy is enforced in application code with tests behind it, and a structural answer is the obvious next step.
