On-device RAG over a quantized MobileLLM

The word “RAG” here does not mean documents. It means retrieving the right handful of functions out of fifty before a small model has to choose one. That reframing is the chapter, and it is what turns a crowded résumé bullet into a design you can defend.

The win

Explain why fifty functions cannot all go in the prompt, and what you retrieve instead — then answer the question that decides it: what happens when the model picks the wrong one?

The line being defended
“Designed an on-device RAG and function-calling layer over a quantized MobileLLM, covering 50+ TV functions from natural-language queries.”
Samsung Research · bullet 1 of 5

In plain words

A television can do more than fifty things, and each one comes with a written description. A small model running on the set cannot read all fifty descriptions alongside what the person said. So a quick search first picks the few descriptions closest to the request, and only those reach the model. That is the “RAG” in the bullet: look things up before answering, but over the television’s own list of actions, not over documents.

Say it out loud · about 75 seconds

For “tell me about the on-device work.” The reframing is the whole answer, so get to it in the first fifteen seconds and let everything else follow from it.

  1. Situation

    A television that does what you ask it in ordinary language, with a model running on the set itself so nothing leaves the room.

    The hard part is not understanding the sentence. It is that the set has more than fifty things it can do.

    Embed the request, retrieve the handful of function descriptions that match, and only those go in the prompt. Then the model picks one and fills its parameters.

  3. What I did

    I would be clear about the limit though. A valid call to the wrong function is exactly as valid. The schema kills one class of failure and leaves the interesting one.

    Two failures that need different repairs. Either the right function never reached the shortlist, which is recall and no model fixes it. Or the shortlist was right and the model chose badly.

The sentence that sounds fluent and gets you caught

“I built an on-device RAG system with function calling.” It invites “retrieval over what?” and if you hesitate there the whole bullet wobbles. Say “the corpus is the function catalogue” in the same breath and the design immediately makes sense.

The other trap is “covering 50+ functions.” Said as an achievement it sounds like an accuracy claim, and it is a count of the catalogue. Separate them yourself: this many functions were routable, and here is the accuracy, split into retrieval recall and selection.

Behavioural · the story for this bullet

For “tell me about designing under a hard constraint” or “a problem you reframed.”

  1. Decision

    Whether to treat fifty functions as a prompt-engineering problem, or to treat the catalogue as a corpus and retrieve over it.

  2. Situation

    A television had to act on natural language, with a model small enough to run on the set. The catalogue was over fifty functions, each with a description and typed parameters. All of it together was far more than the context could hold.

  3. Action

    I reframed it as retrieval. Embed the request, match it against function descriptions, and put only the nearest few in the prompt.

    That has a second-order effect people miss. The descriptions stop being documentation and become the index. So they have to be written in the words people actually say, rather than in product vocabulary.

  4. Result

    The context problem went away. Adding a new function became writing a description rather than retraining anything. It also made the failure modes separable: recall of the correct function, and selection from a correct shortlist.

  5. What it cost

    A second failure mode that did not exist before. If retrieval misses, the right answer is never available and no model quality recovers it. A single classifier over a fixed catalogue would not have that failure, and it would need retraining on every change. I would make the same trade again, and I would want the recall number reported separately.

Start here — the plain version

Someone says “make it brighter” to a television. The television has to work out which of its many settings that means and change it. No network call, because the model runs on the set itself.

The hard part is not understanding the sentence. It is that the television has fifty-odd things it can do. Each one needs a description and a parameter list. All of that together is far more text than a small model can hold. So something has to narrow fifty down to a few before the model ever sees them.

Why this is retrieval at all

Fifty function definitions do not fit in a small model's context alongside the conversation. So you retrieve the handful that might apply, and the model chooses among those. The corpus is the catalogue.

This is the sentence that makes the bullet make sense. People hear “RAG” and think documents, then wonder what a television has to retrieve. The answer is its own capabilities.

Work the arithmetic out loud, because it converts a vague claim into a constraint. A function definition with a description and two or three typed parameters is not small. Fifty of them is far more than a device model can hold while also holding the user's sentence and any conversation history.

So the pipeline is: embed the request, retrieve the nearest few function definitions, put only those in the prompt, and let the model pick one and fill its parameters.

In plain words

A wrong action can come from two different steps. If the search left the right action off the short list, the model never had a chance, and the fix is a wider search or better-written descriptions. If the right action was on the list and the model still chose badly, the fix is making the choice clearer or asking the person. Storing the model’s numbers at lower precision, so it fits on the set, makes that second mistake more likely.

Where the errors actually come from

Two failures, and they are not the same. Retrieval can fail to include the right function at all. Or retrieval succeeds and the model picks the wrong one from the shortlist.

The first is unrecoverable. If the correct function is not in the retrieved set, no amount of model quality helps, because the right answer was never available. That is a recall problem in the retriever.

The second is a selection problem, and it is where quantization hurts most. Choosing between similar functions depends on small differences in the output distribution, and that resolution is exactly what low-precision weights spend.

Knowing which failure you have changes the fix entirely. Recall failures are fixed by retrieving more candidates or by better descriptions. Selection failures are fixed by better disambiguation, or by asking the user.

What a schema can and cannot guarantee

Constrained output means the model cannot invent a function name or a parameter type. It does not mean the chosen function is correct. The schema protects the shape, not the choice.

This is the same principle as chapter 0001's grounding schema, applied to a different problem. Force the output into the function-call form and an impossible action becomes unrepresentable. The device will never be asked to run something that does not exist.

The limit is the part worth volunteering. A perfectly valid call to the wrong function is exactly as valid, structurally, as a call to the right one. So the schema removes one entire class of failure and leaves the interesting one untouched.

In plain words

When the model is unsure, the choice is between acting on its best guess and stopping to ask the person first. Asking is the safest option, but it makes the television feel slower every time. What decides it is how easy the action is to undo: a brightness change can be put back in a second, a deleted recording cannot. So each action carries its own rule, instead of one “how sure is the model” number applied to everything.

The decision nobody asks about until they do

On a device there is no larger model to escalate to. So when confidence is low, the only options are to guess, to ask, or to do nothing. Each is a product decision with a different cost.

In a server-side system a low-confidence result can go to a bigger model. On a television it cannot, because the whole point is that nothing leaves the device.

The asymmetry that decides it is reversibility. Changing brightness is trivially undone and the cost of being wrong is small, so acting is reasonable. Deleting a recording is not, so confirmation is worth its friction there. A single global confidence threshold treats those two identically and is the wrong design.

  1. What is MobileLLM, and how is it not just a small Llama?

    A family of language models designed from the start for phones and embedded hardware, at under a billion parameters. The finding behind it is that below that size the usual scaling intuitions invert. Depth beats width, so the architecture is unusually deep and thin. It also shares input and output embeddings and uses grouped-query attention, both of which are about fitting rather than quality. What it buys is useful language ability in a few hundred megabytes, which is the only band a television will give a background process. Those choices barely register at seven billion parameters. At three hundred million they decide the result.

    Red flagDescribing it as a compressed large model. It was designed at this size, and that distinction is the whole contribution.

  2. What is grouped-query attention, and what does it save?

    In standard attention every head computes its own keys and values, and all of them must be cached for every token generated so far. Grouped-query attention has several heads share one set of key and value projections, while each keeps its own queries. That shrinks the cache by the size of the group. What it buys is a conversation that can get longer. The weights are a constant, but the key-value cache grows with every token, and on a fixed memory budget that growth is the ceiling. Multi-head is one set per head, best quality and largest cache. Multi-query is one shared set, smallest cache and some quality loss. Grouped sits between, and the group count is the dial.

    Red flagCalling it a speed optimisation. It is a memory one, and on a bandwidth-bound device that becomes speed for a different reason.

  3. Do the memory arithmetic for me.

    Quantization means storing each weight in four or eight bits instead of sixteen. The arithmetic settles the feasibility argument on its own. Take a 350-million-parameter model. At sixteen bits a weight that is about 700 megabytes. At eight bits it is roughly 350. At four bits it is under 200, plus the KV cache on top, which grows with context. A television gives a background process a few hundred megabytes. So four-bit is not a preference here, it is the constraint. What it buys is the project existing at all. There is no version where a sixteen-bit model sits resident beside the actual television software.

    Red flagQuoting a parameter count with no byte count. The bytes are the thing that has to fit, and the conversion is one multiplication.

  4. What actually runs the model on the device?

    A mobile runtime such as ExecuTorch, TFLite or ONNX Runtime Mobile. Each takes its own converted file format and implements its own set of operators, so they are not interchangeable. What one buys is an execution engine measured in megabytes rather than hundreds, with no Python on the device. It usually dispatches to the NPU, a dedicated block of silicon that does integer matrix multiplication extremely efficiently. That is what keeps inference from heating the device or stealing cycles from the interface. The risk lives in conversion. An unsupported operator either blocks the export or falls back to the CPU mid-graph, and that round trip can cost more than the accelerator saved.

    Red flagTreating export as a build step. It is where on-device projects actually stall, and the fix is usually to change the model.

  5. There are only fifty functions. Why retrieve at all?

    Because fifty schemas with descriptions and typed parameters is a large prompt, and prefill is the dominant cost on this hardware. Retrieval uses a second, much smaller model that turns text into vectors, so the query and the catalogue can be compared locally. Those encoders are tens of megabytes, an order below the language model. It puts maybe five candidates in front of the model instead of fifty. What that buys is most of the latency win, because the prompt is what you are paying for. It also keeps the catalogue growable without growing the prompt. The trade is that a function the retriever misses cannot be called at all.

    Red flagSaying fifty is small enough to inline. On a server it would be. The whole point of this bullet is that it is not a server.

  6. What does constrained decoding guarantee, and what does it not?

    At each step the model proposes probabilities for every possible next token. Constrained decoding masks out the ones that would make the output invalid against a schema, before sampling. The invalid continuation is not rejected afterwards. It is never on the table. What that buys is parse failures becoming impossible rather than rare, which removes the retry path entirely. On a device with a few hundred milliseconds of budget there is no room for a second attempt. So it guarantees a parse. It does not guarantee a choice. The model can emit a perfectly formed call to entirely the wrong function, and only the confirmation step in front of the user catches that.

    Red flagOffering it as the correctness story. Well-formed and correct are different properties, and only one of them is enforceable here.

  7. Where does the latency actually go?

    The budget runs from the user finishing speaking to the television doing something. Wake word, transcription, retrieval, prefill, generation, parse, execute. A remote-control interaction has to feel instant, which is a few hundred milliseconds for all of it. What stating it as a budget buys is that every design decision gets justified in milliseconds rather than in preference. It is also the single constraint that rules out the cloud, because a network round trip can consume the whole thing. On this hardware prefill dominates, because the prompt is long relative to the reply. So prompt length matters more than output length here, which reverses the usual server intuition.

    Red flagQuoting a single model latency. The user feels the whole chain, and the model is one link in it.

  1. In two sentences, what does this layer do?

    It turns something a person says to a television into the right action on that television. A small model runs on the set itself. It picks a function from the device's catalogue and fills in its parameters. Nothing leaves the device.

    Red flagLeading with MobileLLM. The model is a constraint, not the product, and naming it first invites the wrong conversation.

  2. What is being retrieved? There are no documents here.

    The function definitions themselves. The catalogue is the corpus. Each function has a name, a description and typed parameters, and the retriever finds the handful most likely to match the request. So it is retrieval over capabilities rather than over content.

    Red flagLetting “RAG” imply a document store. The reframing is the whole reason this design is interesting.

  3. Why not put all fifty functions in the prompt?

    They do not fit. A function definition with a description and a few typed parameters is not small. Fifty of them is far more than a device-sized model can hold alongside the user's sentence. Even if it fit, burying the relevant few among fifty makes the choice harder.

    Red flagOnly citing token limits. The signal argument matters too, and it still applies on a model with a larger window.

  4. How does the retriever decide which functions are candidates?

    By similarity between the request and each function's description, so the descriptions are load-bearing text rather than documentation. A function whose description does not use the words people actually say will not be retrieved, and then it can never be chosen. That makes description quality a recall problem.

    Red flagTreating descriptions as comments. They are the index, and editing one changes behaviour.

  5. What does the model actually return?

    A function name and its arguments, in a constrained format. Not prose. The parameter values are extracted from what the person said, which is the slot-filling half and often the harder one. “Brighter” has to become a named setting plus a direction or an amount.

    Red flagDescribing only function selection. Slot filling is where ambiguity lives, since people rarely state values precisely.

  6. Why run this on the device rather than in the cloud?

    Privacy and latency. What somebody says in their living room never leaves the room, which for a television is the deciding argument. And there is no network round trip, so a short command feels immediate. You accept a weaker model to get both.

    Red flagLeading with cost. It matters at scale and it is not why a consumer device does this.

  7. What does constraining the output format guarantee?

    That the call is structurally valid. The model cannot name a function that does not exist or give a parameter the wrong type, because the format has no shape for it. What it does not guarantee is that the chosen function is the right one. A valid call to the wrong function is exactly as valid.

    Red flagPresenting the schema as correctness. It removes one class of failure completely and leaves the interesting one untouched.

  8. Name the two ways this system gets an answer wrong.

    Retrieval misses the right function, so it was never on the shortlist. Or retrieval succeeds and the model picks the wrong one from it. The first is a recall problem and no model quality fixes it. The second is a selection problem, and it is where quantization hurts most.

    Red flagTreating them as one accuracy number. They have different causes and completely different fixes.

  9. What happens when the model is not confident?

    There is no bigger model to escalate to, so the options are act, ask, or decline. The right choice depends on reversibility. Changing brightness is trivially undone, so acting is fine. Deleting a recording is not, so confirmation earns its friction. One global threshold for both is the wrong design.

    Red flagProposing a single confidence cutoff. The cost of being wrong differs per function, so the threshold should too.

  10. What is the riskiest claim in this bullet?

    “Covering 50+ TV functions” reads as a success rate and it is a coverage count. It says the catalogue had that many entries, not that all fifty were selected correctly. I would separate those two before anyone asks, and give the accuracy figure separately if I have it.

    Red flagLetting a count stand as a quality claim. It is the same shape as a 100% success rate that means completion rather than correctness.

  1. How many functions do you retrieve, and how would you pick that number?

    Few enough to fit comfortably, many enough that the right one is nearly always present. I would tune it by measuring recall of the correct function at each size. Then selection accuracy at each size. Those move in opposite directions. The best number is where their product peaks, not where either is best.

    Red flagOptimising recall alone. A longer shortlist guarantees the answer is present and makes the choice harder, so the two have to be measured together.

  2. You said descriptions are the index. What follows from that?

    That they have to be written in the words people actually say, not in product vocabulary. If the setting is called “backlight” internally and everyone says “brightness,” the description needs both. It also means editing a description is a behaviour change and should be tested like one.

    Red flagWriting descriptions for engineers. They are matched against consumer phrasing, so they should contain consumer phrasing.

  3. Where does the retrieval index live on a television?

    On the device, in the same memory budget as the model. That is what keeps it small. Fifty function definitions and their embeddings is a tiny index, which is why this works at all. A general document corpus would not fit, and that constraint is what makes the catalogue the right corpus.

    Red flagAssuming a vector database. At this size a flat array and a dot product is both sufficient and faster.

  4. How do you stop the model inventing a function name?

    Constrain the decode. The output must match a grammar over the shortlist's function names and parameter types. An invalid name then cannot be generated, because those tokens are never available. That is stronger than validating afterwards, since there is no invalid output to reject.

    Red flagDescribing post-hoc validation. Rejecting a bad output costs a retry, and preventing it costs nothing.

  5. Why is slot filling harder than function selection?

    Because people do not state values. “Make it brighter” gives a direction and no amount. “A bit louder” gives a vague magnitude. The model has to map fuzzy language onto a typed parameter. The sensible default is a relative step, rather than an absolute value it had to guess.

    Red flagTreating parameters as easy once the function is chosen. Selection is a closed choice and slot filling is open-ended.

  6. “Make it brighter.” Then “a bit more.” What has to happen?

    The second utterance has no function in it at all. It only means something relative to the previous turn, so the system needs the last action in context. That is conversation state on a device with a tight context budget. In practice it means keeping a short structured record of recent actions, rather than the raw transcript.

    Red flagTreating each utterance as independent. Follow-ups are the common case in voice, not the exception.

  7. “Turn the volume down and switch to Netflix.”

    Two functions in one sentence. The system has to emit a sequence rather than a single call. That means the output format must permit a list. If it does not, the model will pick one and silently drop the other. That is the worst outcome, because the person thinks both happened.

    Red flagAssuming one call per utterance. Compound commands are ordinary speech, and silently dropping half is worse than failing.

  8. Why does quantization hurt function selection specifically?

    Because selecting between similar candidates depends on small differences in the output distribution. Reduced precision is exactly what erodes those. Fluency survives low bit widths well. So the model still produces a confident, well-formed call. It is just slightly more likely to be the wrong one, which is a failure that looks like success.

    Red flagSaying quantization lowers accuracy generally. The damage is concentrated exactly on the task this system performs.

  9. What is the latency budget for a spoken command?

    Much tighter than a conversation. A person expects a remote control to respond in a few hundred milliseconds, and a television that thinks for two seconds feels broken. That budget covers embedding the request, the retrieval, and the generation. It is also why the model has to be small rather than merely small enough to fit.

    Red flagComparing it to a chat turn. A command is not a conversation, and the tolerance is an order of magnitude lower.

  10. A new feature adds a fifty-first function. What has to happen?

    Write its description, embed it, add it to the index. No retraining, which is the main benefit of doing selection by retrieval rather than by a trained classifier. The risk is that the new description overlaps an existing one. Then both get retrieved, and selection gets harder for a command that used to work.

    Red flagSaying it is free. Adding a candidate makes every neighbouring decision slightly harder, so the regression test is on the old functions.

  11. How would you measure whether this works?

    Two metrics, matching the two failures. Retrieval recall, meaning how often the correct function is in the shortlist. And end-to-end accuracy, meaning how often the right function is called with the right parameters. The gap between them is selection error, which is the part a better model fixes.

    Red flagReporting one accuracy number. Splitting it tells you which half to invest in, and that is the whole point of measuring.

  12. Why not a trained intent classifier instead?

    A classifier over fifty fixed intents would be smaller and faster, and it needs retraining every time a function is added or changed. The retrieval approach handles new functions by writing a description. It also generalises to phrasings nobody thought of, which a classifier trained on a fixed set does poorly.

    Red flagDismissing the classifier. For a fixed catalogue it is a genuinely strong baseline, and the argument is about change rather than accuracy.

This layer is described as RAG. What corpus is being retrieved from?

  1. Retrieval over the function catalogue, not over documents
  2. Retrieval over the model's weights resident in memory
  3. Retrieval over the user's own viewing history instead
  4. Retrieval over a server-side index across the network

The device's own capabilities. Fifty function definitions, each with a description and typed parameters, are far more than a small on-device model can hold alongside the user's sentence. So the retriever narrows fifty to a handful and only those enter the prompt.

Nothing crosses the network, which rules out the last option and is the entire reason the work is on-device. Viewing history is a different system's problem, and it appears in chapter 0014 rather than this one.

Constrained output guarantees the model cannot name a function that does not exist. Why is that not enough?

  1. A schema constrains the shape, and never the chosen value
  2. A schema is checked only after the call has completed
  3. A schema cannot be enforced by a quantized small model
  4. A schema is advisory text the model may freely ignore

A valid call to the wrong function is structurally identical to a valid call to the right one. The schema removes an entire class of failure, which is invented names and mistyped parameters, and leaves selection error completely untouched.

It is the same limit as schema-enforced grounding in chapter 0001: the shape is guaranteed and the value is not. Constrained decoding is also enforced during generation rather than checked afterwards, which is what makes the second option wrong.

Edges and exceptions

Voice systems live in their edges. Most of these are about what happens when the person is not clear.

  • Nothing matches

  • A destructive action
  • Misheard speech
  • Someone else's voice

  1. Someone asks for something the television cannot do.

    Retrieval still returns the nearest few, because top-k always returns k. The model still has to choose from them. Without a similarity floor it will confidently perform the closest available action, which is worse than failing. The fix is a distance threshold below which the answer is that it cannot be done.

    Red flagAssuming it declines naturally. Nothing in the pipeline offers “none of these” as an option unless you build it.

  2. Two functions are both plausible for what was said.

    Then the request was genuinely ambiguous and guessing is the wrong instinct. If both are reversible, pick the more common and make undo obvious. If either is not, ask a single disambiguating question. What you must not do is pick silently and leave the person working out what happened.

    Red flagAlways asking. A question on every ambiguous command makes the product tiring, so reversibility has to decide.

  3. How do you handle a function that deletes something?

    Confirmation, independent of confidence. Reversibility should be a property of the function rather than a threshold on the model's certainty. A confident wrong answer is exactly the case that hurts. Destructive functions get a confirm step even at high confidence, and reversible ones do not get one at low confidence.

    Red flagGating on confidence alone. Confidence is the model's opinion of itself, and it is the least reliable input to an irreversible decision.

  4. Speech recognition mishears the command. What does your layer see?

    A perfectly plausible sentence that is not what was said, and nothing downstream can tell. This layer's input is already the output of another uncertain system, and the errors compound. It argues for the retrieval floor again, since a misheard command often lands nowhere near any function description.

    Red flagTreating the transcript as ground truth. It is another model's best guess, and the two error rates multiply.

  5. A child, or a television advert, says something the set hears.

    Then the system acts on input nobody intended to give it. That is an activation problem rather than a retrieval one, and it sits upstream of this layer. What this layer can contribute is the reversibility rule, so an unintended command changes brightness rather than deleting recordings.

    Red flagClaiming it is out of scope. It is upstream, and the mitigation inside your layer is still worth naming.

  6. Defend “covering 50+ TV functions.”

    It is a coverage count, not an accuracy claim. The catalogue had that many entries and the layer could route to all of them. It does not say all fifty were selected correctly, and I would separate the two. The number that matters is end-to-end accuracy, split into retrieval recall and selection.

    Red flagLetting the count imply quality. It is the same shape as a success rate that means completion, and interviewers read both the same way.

  7. The catalogue grows to five hundred functions.

    Retrieval matters more, not less, and the shortlist size probably has to stay the same. What breaks first is description overlap: at five hundred, many will be near-duplicates and the retriever cannot separate them. That is when you need hierarchy, retrieving a category first and then within it.

    Red flagSaying it scales linearly. Retrieval scales fine and disambiguation does not, and that is the interesting half.

  8. What would you change?

    Add a similarity floor so “I cannot do that” is a real outcome. Make reversibility a property of each function and drive confirmation from it. Then split the accuracy measurement into recall and selection, because right now one number hides which half needs work.

    Red flagProposing a bigger model. The device budget is fixed, and two of these three fixes cost nothing at inference.

Or the shortlist was correct and the model chose badly, which is selection and it is exactly where quantization hurts. Then the response depends on reversibility: a wrong brightness change is trivially undone, and anything destructive should have required a confirmation regardless of confidence.

  3. “Why not just fine-tune a classifier over fifty intents?” A fair challenge with a genuinely strong alternative. Dismissing it is the weak move.
    Model answer — say yours first

    It is a strong baseline and it would be smaller and faster. The argument against it is change rather than accuracy. Every new function means retraining, and a television's catalogue grows with every firmware release. With retrieval, adding a function is writing a description and embedding it. It also generalises better to phrasings nobody anticipated, which a classifier trained on a fixed set handles poorly.

  4. “How do you stop it doing something destructive by mistake?” Looking for whether safety is a threshold or a property. The threshold answer is the common one and it is weaker.
    Model answer — say yours first

    By making reversibility a property of each function rather than a confidence cutoff. Anything destructive gets a confirmation step even when the model is confident, because a confident wrong answer is precisely the case that hurts. Anything trivially reversible acts immediately with a visible undo. A single global confidence threshold treats deleting a recording and changing brightness identically, which is the wrong design.

  5. “Someone asks for something the TV cannot do. What happens?” Tests whether you know top-k always returns k. Most candidates assume a relevance filter that is not there.
    Model answer — say yours first

    Without a similarity floor, retrieval returns the nearest few anyway and the model confidently performs the closest available action. That is worse than failing, because the person did not get what they asked for and something else changed. The fix is a distance threshold below which the honest answer is that the television cannot do it. Nothing in a top-k pipeline offers “none of these” unless you build it.

System Design School teaches these mechanisms from first principles and breaks them in a lab. This chapter defends what you did with them. An interviewer moves between those two registers without warning.
