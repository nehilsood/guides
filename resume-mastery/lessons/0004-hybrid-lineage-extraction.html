Hybrid deterministic-LLM lineage extraction

The best sentence in this codebase is a comment: deterministic extraction handles field mapping tables, zero hallucination risk. That is the whole design. The interview risk is the number beside it, because 99.2% does not measure what the résumé makes it sound like.

The win

Say exactly where a model is allowed to touch your data and where it is not — and answer “99.2% of what?” with the four weights and their sub-metrics, before anyone has to ask twice.

The line being defended
“Built a hybrid deterministic-LLM Lineage Agent (Gemini, Google ADK) for legacy SAP BW to BigQuery migrations, extracting column-level field mappings at 99.2% accuracy against a hand-authored gold standard.”

Say it out loud · about 75 seconds

A spoken answer to “tell me about the lineage agent.” Lead with the fork. The number comes last, with its decomposition attached, so it never sits alone.

  1. Situation

    A client was migrating off a legacy SAP warehouse onto BigQuery, and nobody could say how the old one was wired.

    What existed was a pile of Word documents, with the real answer buried in mapping tables inside them.

  2. Mechanism

    The design is one fork. Code where there is a right answer, the model where there is a judgment.

    The mapping tables get parsed deterministically, so the 516 field mappings are extracted rather than generated. Object identity and cross-references go to the model, because those genuinely need an opinion.

  3. What I did

    Two things I would defend. The model's answers pass guardrails that reject non-SAP names, self-loops, and generic words like TABLE offered as an object name.

    And the model sometimes called merge before extraction. That produced a graph with zero field mappings and no error.

    I fixed it with a before-tool callback rather than a better prompt. A prompt lowers a failure rate. A precondition removes it.

  4. What it cost

    The headline needs a caveat and I would rather give it than have it pulled. The 99.2% is a weighted composite. Node and edge are a quarter each, fields are 0.30, structure is 0.20.

    Inside the field term, most of the weight is count accuracy and a distribution cosine.

    So it is not 99.2% of columns checked one by one. The résumé wording implies more than the metric does.

    The other limit is the sample. Five documents, hand-written answers. Enough to catch a regression, not enough to claim a general accuracy figure.

The sentence that sounds fluent and gets you caught

“It extracts column-level mappings at 99.2% accuracy.” It is the résumé line said out loud, and it invites “so 99.2% of the 516 mappings were correct?” The answer is no, and having to say no to your own sentence is a bad position. Give the four weights in the same breath as the number.

The other trap is “we used guardrails to prevent hallucination.” The guardrails do not prevent hallucination. They reject a specific set of malformed outputs. What prevents hallucination in the mappings is that a model never wrote them, and that is a much stronger sentence.

Start here — the plain version

A company is moving off an old SAP data warehouse onto BigQuery. Nobody remembers how the old one is wired. What exists is a pile of Word documents describing each object, and inside those documents are tables listing which source column feeds which target column.

The agent reads those documents and builds a map of the whole thing. Two kinds of map. Object level is which system feeds which. Field level is which column feeds which column. The second one is the valuable one, and it is the one a language model must not be allowed to invent.

Lineage
Where data came from, hop by hop. If a number in a report looks wrong, lineage is what lets you walk backwards to the column it started in.
SAP BW
The legacy warehouse being migrated off. Its objects have machine-style names like 0WBS_ELEMT, which turns out to matter, because a name that shape can be validated by a regular expression.
Field mapping
One row of the answer: this source column becomes that target column, with this transformation. There are 516 of them across five documents.
Deterministic extraction
Reading the mapping tables with code rather than a model. The tables are structured, so parsing them is a solved problem and the output cannot be invented.
Hybrid
Using code where there is a right answer and a model where there is judgment. Here the split is written into the source file's own docstring.
Cross-reference
A mention of another object inside a document. Deciding whether a mention is really a data flow is a judgment call, which is why a model does it.
Guardrail
A rule that rejects an answer before it reaches the graph. Here: names that do not look like SAP objects, edges that point at themselves, and generic words like “TABLE” offered as an object name.
SequentialAgent
An ADK agent that runs sub-agents one after another. This pipeline has two of them, which is fewer than most people assume when they hear “agentic.”
Before-tool callback
A hook that runs before a tool does. It is how this pipeline guarantees the deterministic half ran, regardless of what order the model decided to call things in.
Gold standard
The hand-written answer the output is scored against. Five documents, written by a person, and small enough that the sample size is a fair question.
The technology — what each named thing is

The primer above names the parts of a lineage problem. This one names the tools and the measurement, starting from the ground. The accuracy figure in the bullet is the most contestable thing here, so it is defined too.

Every entry answers four things. What it actually is, in plain words. Where this system uses it. What it buys, meaning what goes wrong without it. And the follow-up an interviewer asks once you have said the name.

BigQuery
the destination warehouseGoogle's analytical database, the kind you run reports against rather than serve an application from. There is no server to provision and no cluster to size. You load data and write SQL, and Google works out the machines. Storage is columnar, meaning a query that reads three columns of a two-hundred-column table pays for three, which is why it scans terabytes in seconds. In the app. It is the destination that SAP BW is being migrated into. What it buys. Analytics capacity without an analytics platform team, and a cost model tied to what you actually query. The follow-up. Why the shapes do not line up. BW is modelled around InfoObjects, InfoCubes and DSOs, and a great deal of the meaning lives in metadata rather than in the data. BigQuery has tables and columns and nothing else. The mapping work exists precisely because that translation is not mechanical.
Google ADK
Agent Development KitGoogle's open-source Python framework for systems where a model does work across several steps. A bare model call is one question and one answer. The framework supplies the rest: an agent type, a way to attach ordinary Python functions as tools, a shared dictionary carried between steps, and a runner that drives the sequence and records every event. In the app. Parse, extract, cross-reference, merge, with one model call inside. What it buys. Ordering, state passing and an inspectable trace, none of which you have to write. The trace is the part that matters when a document extracts wrongly and you need to know at which step it went wrong. The follow-up. It is not the model. Gemini does the reading. ADK decides what runs, in what order, and what each step is allowed to see.
SequentialAgent
a workflow agentAn agent that runs its children in a fixed order written down in code, passing the shared state along as it goes. No model is consulted about what comes next. It is a for loop with observability bolted on. In the app. Parse, extract, cross-reference, merge is a known order that never varies by document. What it buys. A pipeline you can read, test without a model, and reason about. Each stage can be run alone against a fixed input, which is what makes the accuracy figure reproducible rather than anecdotal. The follow-up. What happens on failure. A sequence has no branches. A stage that cannot produce its output has to write that fact into state and let the next stage decide what to do with it, or one malformed document takes down the whole run.
Before-tool callback
before_tool_callbackA hook the framework runs in the moment between the model asking for a tool and the tool actually running. It receives the tool name and the arguments, and it can inspect them, rewrite them, or refuse outright and return a result of its own. In the app. ensure_deterministic_before_merge uses it as a precondition, so a merge cannot execute on a model result that never went through the regex half. What it buys. An invariant that holds no matter what the model does. The ordering rule stops being a hope about prompt compliance and becomes a condition checked in Python on every single call. The follow-up. Why a callback rather than a line in the prompt. Because this one is enforced by the framework instead of requested of the model, and that is exactly the difference between a guardrail and advice.
Gemini
gemini-2.5-proGoogle's large language model family, used here in its larger reasoning tier and reached through the Google GenAI SDK. The larger tiers cost more per token and are better at multi-step inference over long inputs. In the app. Reading a written specification document and inferring which BW object a given column originally came from. What it buys. The half of the problem no rule can express. Where a name follows SAP convention a regex is better and cheaper. Where the only evidence is a sentence in a Word document written by a person, a model is the only thing that reads it. The follow-up. Why the expensive tier, and say the trade rather than dodging it. A cheaper tier costs less per document and shows up directly as a lower number against the gold standard, and 99.2% is the figure you are defending.
Regular expression
the deterministic halfA small language for describing the shape of text. ^[0-9A-Z][A-Z0-9_]{2,}$ reads as: begin with a digit or a capital letter, then at least two more capitals, digits or underscores, then end, with nothing else allowed. Matching is exact, instant and free. In the app. SAP technical names follow rigid naming conventions, so anything a pattern can identify never reaches the model at all. What it buys. Cost, speed and certainty on the easy majority. It also fixes the answer, so the same column extracts identically on every run, which a model does not guarantee. The follow-up. What it cannot do. A regex confirms that a string looks like an identifier. It has no idea whether that identifier exists, or whether it means what the document claims it means.
.docx
Office Open XMLNot a document in any single-file sense. A .docx is a ZIP archive containing XML parts, with the text living in word/document.xml and styling, numbering, tables and relationships in files beside it. Reading one means unzipping and walking XML, not reading text. In the app. DocParser pulls text and table structure out of specification documents written by people. What it buys. Access to the structure, not just the words. A table's rows and cells survive the parse, and in a specification document the table is usually where the mapping actually is. The follow-up. Where extraction loses information. Tables split across pages, merged cells and floating text boxes all flatten badly. A mapping destroyed at the parse step never reaches the model at all, so it cannot be blamed on the model.
DAG
directed acyclic graphA set of nodes joined by one-way arrows, with the rule that you can never follow the arrows back to where you started. Lineage is naturally one of these. A column is derived from other columns, and nothing can be derived from itself. In the app. is_dag_correct is one of the weights in the evaluation, checking the shape of the extracted graph rather than the labels on it. What it buys. A correctness check that needs no gold standard. You can test acyclicity on a document nobody has ever labelled, which means it works on new data where accuracy cannot be computed at all. The follow-up. Why acyclicity is worth testing on its own. A cycle proves the extraction invented a dependency, because real lineage cannot contain one. It is a hallucination detector that costs nothing to run.
Structured output
response schemaHanding the API a schema in advance so that generation is constrained to fit it. This is not a prompt asking for JSON and it is not a parse-and-retry loop. Tokens that would break the shape are never produced in the first place. In the app. A field mapping is a record with required parts, and a stage returning prose could not be merged with the regex results. What it buys. The whole family of parsing failures disappears — no markdown fence, no preamble sentence, no trailing comma — and so does the code that used to handle them. The follow-up. Shape is not truth. Every field can be present, correctly typed, and entirely wrong. That gap is exactly why the cross-reference step exists downstream of the model rather than trusting its output.
Accuracy
and what it hidesThe share of predictions that match the gold standard, counted over everything the system was asked about. One number, easy to quote, and the one most likely to be challenged. In the app. 99.2% is the headline figure in the bullet. What it buys. A single comparable number across runs, which is genuinely useful for spotting a regression between two versions of the same pipeline. The follow-up. Over what denominator, and against which failure. Precision asks how many of the mappings you produced were correct. Recall asks how many of the real mappings you found at all. A run that quietly skips the hard columns scores beautifully on one and badly on the other, and accuracy is the only one of the three that lets both hide behind a single figure.

The split, and why it is the whole design

Tables get parsed by code. Judgment calls go to the model. That line is drawn once, in a docstring, and everything else follows from it.

The top of tools/field_mapper.py says it in four lines. Deterministic extraction handles field mapping tables, with zero hallucination risk. The LLM handles object identification and cross-reference classification. Validation guardrails reject non-SAP names, self-loops and malformed edges.

That is worth quoting almost verbatim in an interview, because it answers the question before it is asked. The 516 field mappings are not model output. They were parsed out of tables. A model cannot invent a column that is not there, because the model never wrote that part of the answer.

Plain meaningThe boring, exact part is done by a program. The model is only asked the questions that genuinely need an opinion.

Two agents, which is fewer than it sounds

There are two LLM stages, not ten. One parses documents into sections. One merges everything into a graph. Saying the real number is stronger than implying a swarm.

agent.py describes itself as a 2-stage SequentialAgent. The first agent, DocParser, runs parse_and_extract over each .docx. The second identifies objects, classifies cross-references, and calls the merge tool that assembles the graph.

The model is gemini-2.5-pro, set through a LINEAGE_MODEL environment variable. Pinning it there rather than in code is the same lesson as the gateway in chapter 0002: an alias that silently resolves somewhere new is a failure you cannot see.

Plain meaningTwo steps that use the model, not a crowd of them. Read the documents, then join everything up.

The callback, which is the best story here

The model sometimes called merge before it called extraction. The result was a graph with zero field mappings and no error. The fix was not a better prompt. It was a hook that runs extraction anyway.

ensure_deterministic_before_merge is a before_tool_callback. Its own docstring names the failure: prevents 0 field_mappings caused by LLM tool-calling order variance. If merge is called and the deterministic extractions are not in state, it runs them first.

This is the part worth understanding properly. Tool-calling order is not guaranteed. A model that got it right ninety-nine times will get it wrong the hundredth, and the output is not an error. It is a complete, well-formed, empty answer — which is the worst kind, because nothing alerts on it.

Plain meaningThe model occasionally did step two before step one. Rather than asking it more nicely, we made step one run by itself if it had been skipped.

Guardrails, and the failure they catch

The model is asked to name objects. Sometimes it returns the name of a category instead of an object. A denylist of those words is a two-line fix for a whole class of wrong answers.

Three checks sit in field_mapper.py. A regex, ^[0-9A-Z][A-Z0-9_]{2,}$, for what an SAP identifier looks like. A list of known prefixes, including RSDRI, 2LIS_ and BW_. And a reject list.

The reject list is the interesting one. It contains DSO, ADSO, INFOOBJECT, INFOCUBE, TABLE, FIELD, MAPPING. Those are types, not objects. A model asked to name the object will sometimes answer with the kind of thing it is, and the graph would happily grow a node called TABLE.

Plain meaningIf you ask what breed the dog is and it answers “dog,” you throw that answer away rather than adding a dog called Dog.

What 99.2% actually measures

It is not the share of columns mapped correctly. It is a weighted average of four dimensions, and field mapping is 30% of it. Inside that 30%, most of the weight is on counts and distributions rather than on individual columns.

evals/docs/eval_criteria.json is explicit. Node accuracy 0.25, edge accuracy 0.25, field mapping accuracy 0.30, structural accuracy 0.20. The pass threshold is 0.85.

Open the field mapping term and it has three sub-metrics. Count accuracy is one minus the relative error in how many mappings were found. Type distribution similarity is a cosine between the predicted and expected mix of mapping types. Sample match rate is how many of the sampled mappings matched.

So a run that finds the right number of mappings, with the right mix of types, scores well on two of three sub-metrics without any individual column being checked. That is a reasonable metric. It is just not what “column-level field mappings at 99.2% accuracy” sounds like, and the gap is the thing to volunteer.

Plain meaningWe checked that we found about the right number of mappings, of about the right kinds, and that a sample of them were right. We did not check all 516 one by one.

  1. What is BigQuery, and why is mapping into it real work?

    BigQuery is Google's analytical database, the kind you run reports against rather than serve an application from. There is no server to provision and no cluster to size. You load data and write SQL, and Google finds the machines. Storage is columnar, so a query reading three columns of a two-hundred-column table pays for three. That is why it scans terabytes in seconds, and why it costs what it costs. The mapping is real work because the two shapes do not correspond. BW carries meaning in InfoObjects, InfoCubes and DSOs, much of it in metadata rather than data. BigQuery has tables and columns and nothing else. Translating one into the other is a judgement about intent, not a rename.

    Red flagCalling it “Google's data warehouse” and stopping. The interesting half is the modelling mismatch, which is why the agent exists at all.

  2. What is ADK, and what does SequentialAgent do inside it?

    A bare model call is one question and one answer. ADK is Google's Python framework for turning that into a pipeline. It supplies the agent type, the tool wiring, a shared dictionary carried between steps, and a runner that drives the sequence and records every event. What it buys is ordering, state passing and an inspectable trace, none of which you write. The trace is the part that matters when a document extracts wrongly and you need to know which step did it. SequentialAgent is one of its workflow agents. It runs its children in a fixed declared order and threads state between them. No model decides what comes next, so each stage can be run alone against a fixed input.

    Red flagCalling a fixed sequence “agentic.” Exactly one stage here asks a model anything. Saying so is the difference between honest and inflated.

  3. What is a before-tool callback, and what can it actually do?

    It is a hook that runs in the moment between the model asking for a tool and the tool running. It receives the tool name and the arguments. It can inspect them, rewrite them, or refuse outright and return a result of its own. Here it enforces a precondition, so a merge cannot execute on a model result that skipped the deterministic pass. What that buys is an invariant that holds no matter what the model does. The ordering rule stops being a hope about prompt compliance and becomes a condition checked in Python on every call. The framework enforces it, which is exactly what makes it a guardrail rather than advice.

    Red flagDescribing it as logging. A hook that can only watch is not a control, and the whole claim rests on it being able to refuse.

  4. What is a regular expression doing in a pipeline built around a model?

    A regular expression is a small language for describing the shape of text. Matching is exact, instant and free. It is here to catch everything that never needed a model. SAP technical names follow rigid conventions, so a pattern identifies them precisely at no cost. What that buys is speed, money and certainty on the easy majority. It also fixes the answer, so the same column extracts identically on every run, which a model does not guarantee. That leaves the model only the cases where meaning has to be inferred from prose written by a person. It also gives you a second opinion to merge against. The regex is not the fallback here. It is the first pass.

    Red flagPresenting the deterministic half as legacy. It is the cheaper, more reliable half, and hybrid means both run.

  5. What is a .docx file, actually?

    It is not a document in any single-file sense. A .docx is a ZIP archive of XML parts. The text lives in one part, and styling, numbering, tables and images live in others. Reading one means unzipping and walking XML, not reading text. What that buys you is access to the structure rather than just the words. A table's rows and cells survive the parse, and in a specification document the table is usually where the mapping actually is. It also matters because the losses happen here. Tables split across pages, merged cells and floating text boxes all flatten badly. A mapping destroyed at the parse step never reaches the model to be got wrong.

    Red flagTreating document parsing as solved. It is where silent recall loss comes from, and it never shows up as an error.

  6. What is a DAG, and what does checking it prove?

    A directed acyclic graph is a set of nodes joined by one-way arrows. Following those arrows can never bring you back to where you started. Lineage is naturally one, because a column is derived from other columns and nothing can be derived from itself. Checking it proves the shape is possible. A cycle means the extraction invented a dependency, since real lineage cannot contain one. What that buys is a correctness check needing no gold standard. You can run it on a document nobody has ever labelled, which means it works on new data where accuracy cannot be computed at all. It is a hallucination detector that costs nothing.

    Red flagConfusing a shape check with a correctness check. A perfectly acyclic graph can still be entirely wrong about which column feeds which.

  7. 99.2% accuracy of what, exactly?

    Of column-level field mappings, measured against a hand-authored gold standard. Accuracy is the share of predictions that match, counted over everything the system was asked about. What it buys is one comparable number across runs, which genuinely helps spot a regression between two versions. What it hides is which kind of mistake was made. Say the denominator before you are asked, because accuracy is the weakest of the three words available. Precision asks how many of the mappings you produced were right. Recall asks how many of the real ones you found at all. A run that quietly skips the hard columns scores beautifully on the first and badly on the second.

    Red flagLetting the number stand alone. Five documents and a hand-built answer key is a small denominator, and saying so first is stronger than being asked.

    Red flagVagueness here. “It uses both” is the answer of somebody who inherited the design rather than drew it.

  5. How many LLM stages are there?

    Two. It is a two-stage SequentialAgent. One parses the documents into sections. One identifies objects and merges everything into the graph. I would rather say two than let “agentic” imply a swarm. The follow-up about why they are agents is easier to answer honestly at two.

    Red flagLetting the word “agent” do work the architecture does not. Two sequential stages is a fine answer and an overstated one is not.

  6. Why parse the tables rather than ask the model to read them?

    Because the tables have structure and a model does not improve on a parser. A model reading a 40-row mapping table can drop a row, merge two, or invent a plausible column name. None of those produce an error. A parser either finds the table or does not, and its output is checkable.

    Red flag“To save tokens.” True and beside the point. The reason is correctness, and cost is a bonus.

  7. What do the guardrails actually reject?

    Three things. Names that do not match the SAP identifier pattern. Edges that point at themselves. And names from a reject list of generic type words like DSO, TABLE and MAPPING. The last one exists because a model asked to name an object will sometimes answer with the category instead.

    Red flagCalling them validation. They are output filters on a model, which is a specific and more interesting thing to have built.

  8. What is the gold standard, and who wrote it?

    Hand-authored expected outputs for five SAP BW documents, in evals/docs/. A person wrote them by reading the same documents. That makes it a real reference, and it also makes five the sample size, which I would state before being asked.

    Red flagPresenting five documents as a benchmark. It is a regression check on a small, honest sample, and calling it that is stronger.

  9. The 99.2% is an average over what?

    Four weighted dimensions, and the weights matter. Node accuracy takes 0.25 of it, edge accuracy another 0.25 of it. Field mapping accuracy takes 0.30, with structural accuracy on the last 0.20 share. The pass threshold sits at 0.85 overall. So field mappings are under a third of the headline, and the other 70% is about the graph.

    Red flagNot knowing the weights. It is the first follow-up, and a composite score you cannot decompose reads as a number you inherited.

  10. What is the riskiest claim in this bullet?

    The phrase “column-level field mappings at 99.2% accuracy.” It reads as though 99.2% of individual column mappings were checked and correct. The metric is a weighted composite, and the field term is mostly count accuracy and a distribution cosine. I would give the decomposition before anyone asks for it.

    Red flagDefending the phrasing. The engineering is good and the wording oversells it, and those are two separate conversations.

Deep dive

The middle third of these are about the metric rather than the pipeline, because that is where a senior interviewer will spend the time.

  • The two stages in detail
  • Tool-calling order variance
  • Why a callback, not a prompt
  • The reject list
  • Self-loops
  • Decomposing the score
  • Count accuracy
  • The distribution cosine
  • Why 0.85
  • Five documents
  • Pinning the model
  • Where this generalises

  1. Walk me through the two stages.

    Agent one is DocParser. It runs parse_and_extract over each .docx and produces sections. Agent two identifies which SAP objects a section is about, classifies cross-references, and calls the merge tool. The merge tool assembles nodes, edges and field mappings into one graph and exports it.

    Red flagDescribing the parser as an LLM step. It is a document parser wrapped in an agent, and the distinction is the one the chapter is about.

  2. What is tool-calling order variance and how did it bite you?

    The model decides what order to call tools in, and that decision is not stable. It sometimes called merge before the deterministic extraction had run. The merge then had nothing to merge, so it produced a graph with zero field mappings. No exception, no warning, a complete-looking result.

    Red flagCalling it a bug in the model. It is a property of letting a model sequence your pipeline, and the design question is what you do about it.

  3. Why fix it with a callback rather than a clearer prompt?

    Because a prompt makes it rarer and a callback makes it impossible. ensure_deterministic_before_merge is a before-tool hook. If merge is called and the extractions are not in state, it runs them first. Prompt wording moves a failure rate. A precondition removes the failure.

    Red flag“We improved the prompt and it stopped happening.” That is a failure you stopped observing, which is a different thing from a failure you fixed.

  4. Why does the reject list contain words like DSO and TABLE?

    Because those are type names, not object names. Asked which object a section describes, a model sometimes answers with the kind of object it is. Without the list, the graph grows a node called TABLE that several documents appear to reference, and it looks like a real hub.

    Red flagTreating it as a cosmetic filter. A spurious hub node corrupts every structural metric, and structural accuracy is 20% of the score.

  5. Why explicitly reject self-loops?

    Because a document about an object mentions that object many times. So the easiest wrong edge to produce is one from a node to itself. It is also the most damaging, because the graph is supposed to be a DAG. One self-loop makes it not one. A structural check expecting a DAG then fails for a reason unrelated to lineage.

    Red flagSaying it is harmless. It flips is_dag_correct, which is a named sub-metric here.

  6. Decompose the 99.2% for me.

    Four dimensions. Node accuracy at 0.25, built from precision, recall, type correctness and metadata completeness. Edge accuracy at 0.25, matching on the source, target and edge-type tuple. Field mapping accuracy at 0.30. Structural accuracy at 0.20, covering whether it is a DAG, the component count, and cross-reference precision.

    Red flagQuoting the weights without the sub-metrics. The sub-metrics are where the interesting answer is, and the next question goes straight there.

  7. Inside the field mapping term, what is count accuracy actually measuring?

    One minus the relative error in how many mappings were found for a given edge. Say the gold standard has 40 mappings and we found 39 of them. That scores 0.975 on this sub-metric. It says nothing about whether those are the right ones. It is a useful signal for a missing table, and a weak one for correctness.

    Red flagReading it as per-mapping accuracy. Knowing that it is not is the whole reason you can talk about this metric credibly.

  8. And the type distribution similarity?

    A cosine between the predicted mix of mapping types and the expected mix. If the gold standard is mostly direct mappings with a few transformations, and we produce the same proportions, the cosine is high. It catches a systematic bias, like classifying everything as direct. It does not catch two individual mappings swapped.

    Red flagNot being able to say what a metric misses. Every metric misses something, and naming it is the difference between using one and quoting one.

  9. The threshold is 0.85. Why there?

    It is a chosen bar, not a derived one, and I would say so. What makes it defensible is that it gates a regression check on five documents with known answers. If a change drops the composite below 0.85 on those five, something moved and it needs looking at. The absolute value matters less than it being fixed.

    Red flagInventing a justification for 0.85. A threshold used as a regression tripwire does not need a statistical origin story.

  10. Five documents. Is that enough?

    Not to claim a general accuracy figure, and I would not. It is enough to catch a regression, because the answers are hand-written and stable. What it cannot tell you is how the agent behaves on a differently shaped document. That is the honest limit of the number.

    Red flagDefending five as sufficient. Saying what it is sufficient for is both true and more impressive.

  11. Why is the model name in an environment variable?

    So it is pinned and swappable without a code change. LINEAGE_MODEL defaults to gemini-2.5-pro. The reason to care is the failure from chapter 0002. An alias there quietly started resolving to a model that refused a parameter we sent. A named version fails loudly when it disappears.

    Red flagTreating it as configuration hygiene. It is a specific defence against a specific failure you have actually seen.

  12. Where does this hybrid pattern generalise to?

    Anywhere part of the input is structured and part is not. The rule I would state is that a model should only be asked questions that have no deterministic answer. Tables, identifiers and arithmetic are not those questions. Classification, disambiguation and summarisation are. Most document pipelines get this backwards and hand the whole file to the model.

    Red flagGeneralising to “use less AI.” The rule is about which questions have oracles, and that is a sharper and more useful claim.

The model calls the merge tool before it has called deterministic extraction. What happens?

  1. A callback quietly runs the deterministic extraction step first
  2. The merge returns zero field mappings without any warning
  3. The agent silently retries against a much larger model
  4. The document gets rejected and the entire pipeline stops

The callback runs it. ensure_deterministic_before_merge is a before-tool hook: if merge is called and the extractions are not in state, it runs them and then lets the merge proceed.

Zero field mappings without a warning is exactly what happened before the callback existed, and it is why the callback exists. That failure is the dangerous kind, because the output is well-formed and complete-looking. Nothing throws, so nothing alerts.

The 99.2% headline is a weighted average. What is it averaging?

  1. Four weighted dimensions, of which fields are only one
  2. Every column mapping found across the five source documents
  3. The precision and recall of the field mappings alone
  4. The share of documents that parsed without any error

Four dimensions: node 0.25, edge 0.25, field mapping 0.30, structural 0.20. So the field term is under a third of the headline, and the rest is about the graph rather than the columns.

The tempting reading is the second one, because that is what the résumé wording suggests. Inside the field term, count accuracy and a type-distribution cosine carry most of the weight, and only the sample match rate looks at individual mappings.

Edges and exceptions

Half of these are about what the metric cannot see. That is the right emphasis for a bullet whose headline is a number.

  • A table the parser misses
  • Scoring well while being wrong
  • A document in a new format
  • When the gold standard is wrong
  • A legitimate cycle
  • Rejecting a real object
  • Scaling past five documents
  • What you would change

  1. The parser misses a mapping table because the document formats it differently. What happens?

    Those mappings are simply absent, and nothing complains. The deterministic half has no notion of how many tables it should have found. Count accuracy against the gold standard would catch it for the five known documents. For a new document there is no expected count, so the failure is silent.

    Red flagAssuming the guardrails catch it. They filter what the model produced. They do not notice what the parser never produced.

  2. Could the agent score above 0.85 while being meaningfully wrong?

    Yes, and this is the honest answer to the metric question. Find the right number of mappings with the right type mix but the wrong pairings. Count accuracy and the distribution cosine both stay high. Only the sample match rate falls, and it is one sub-metric inside a 0.30 term.

    Red flagSaying no. The interviewer is testing whether you know your own metric's blind spot, and claiming it has none ends that line of credit.

  3. A sixth document arrives from a different SAP team, formatted unlike the other five. What breaks first?

    The deterministic parser, because it is the half that depends on layout. The model half degrades gracefully, since object identification is robust to formatting. That is the trade the hybrid design makes. The reliable half is also the brittle one. It fails by finding nothing, rather than by finding something wrong.

    Red flagClaiming the hybrid is robust. It is correct where it works and brittle at the edges, which is a better property but not the same one.

  4. What if the hand-written gold standard is wrong?

    Then the score is wrong in a direction nobody can see. With five documents there is no way to average that out. The mitigation is that the gold files are small and readable. A disagreement can be settled by opening the source document. I would treat a sudden score drop as a claim about either side until checked.

    Red flagTreating the gold standard as ground truth by definition. Somebody typed it, and that is the same class of risk as everything else here.

  5. What if the real lineage genuinely contains a cycle?

    Then the structural check is wrong rather than the graph. is_dag_correct compares predicted against expected. A gold standard saying cyclic and a prediction saying cyclic still scores correct. What would break is the self-loop guardrail, which rejects an edge unconditionally. A genuine self-referencing object would be dropped.

    Red flagAssuming lineage is always acyclic. It usually is, and a guardrail that assumes it is a rule rather than a heuristic is a thing to know about your own code.

  6. Could the guardrails reject a real object?

    Yes. The identifier regex requires at least three characters of uppercase, digits or underscores, starting with a digit or capital. A legitimately short or unusually named object would be dropped silently. The prefix list is a similar bet. Both are tuned to the five documents we have, and that is a real limit.

    Red flagPresenting the guardrails as safe. They trade recall for precision, and saying which way you traded is the answer.

  7. Scale this to five hundred documents. What changes?

    Three things. The gold standard stops being feasible. Evaluation moves to sampling, plus invariants such as rejecting any node named after a type. The model calls need concurrency and a retry budget. And the graph needs identity resolution, because the same object gets named differently across teams. Five documents never exposed that.

    Red flagAnswering only with infrastructure. The interesting scaling problem here is evaluation, not throughput.

  8. What would you change about this?

    The metric, first. I would add a per-mapping precision and recall alongside the composite, so the headline number and the column-level claim are the same number. Second, a completeness check on the parser, so a missed table is loud rather than silent. Neither is hard, and both close the gap between what we measure and what we say.

    Red flagNaming a model upgrade. The model is not the weak part here, and saying so shows you know where the risk actually sits.

Probes to expect

  1. “99.2% of what, exactly?” The single most likely question on this bullet, because the number is the most specific thing in it. A candidate who cannot decompose a metric they quoted is assumed to have inherited it.
    Model answer — say yours first

    A weighted composite over four dimensions. Node accuracy and edge accuracy at 0.25 each, field mapping accuracy at 0.30, structural accuracy at 0.20, with a pass threshold of 0.85. Inside the field term there are three sub-metrics: count accuracy, a cosine over the mapping-type distribution, and a sample match rate. So it is not 99.2% of columns individually verified, and I would rather say that than have you find it.

  2. “How do you stop the model hallucinating a column that does not exist?” Asked of every LLM extraction system. Most answers are about prompting or validation. The strong answer is that the model was never given that job.
    Model answer — say yours first

    By not asking it. The field mapping tables are parsed deterministically by code, so the 516 mappings are extracted rather than generated. There is no step where a model proposes a column name. The model only handles object identification and cross-reference classification, and those answers pass guardrails before they reach the graph.

  3. “Why is this agentic at all? It sounds like a parser and one model call.” A fair challenge, and the honest answer is more impressive than a defence. This is where overclaiming gets punished.
    Model answer — say yours first

    Largely fair. It is a two-stage sequential agent, and the framework is buying tool orchestration and state rather than autonomy. The one place the agent framing earns itself is the before-tool callback, which is a framework hook I used to make a precondition unskippable. I would not describe this as a swarm, and the résumé does not.

  4. “Tell me about a failure this system had.” An invitation. The zero-mappings bug is the best answer in the chapter because it is silent, specific, and fixed structurally.
    Model answer — say yours first

    Some runs produced a graph with zero field mappings and no error at all. The cause was tool-calling order: the model sometimes called merge before the deterministic extraction had run, so there was nothing to merge. The result looked complete, which is the dangerous kind. I fixed it with a before-tool callback that runs extraction if it has not run, rather than with prompt wording.

  5. “Five documents is a small evaluation set. Does the number mean anything?” Testing whether you will defend a sample size you should concede. Conceding it and saying what it is good for is the winning move.
    Model answer — say yours first

    It means something narrow. Five documents with hand-written expected outputs is a regression gate: if a change moves the composite below 0.85 on those five, something broke. It is not a population estimate, and I would not present it as one. To claim general accuracy I would need sampled per-mapping verification across many more documents, which is the first thing I would build next.

The model occasionally called tools in the wrong order and produced a complete-looking result with nothing in it. Which chapter has the same failure shape, and what is the shared lesson?

Chapter 0001, the Scout's soft-fail. A total search outage there is indistinguishable from a vendor with no public footprint, and the report comes back confident and empty. Same shape here: the graph is well-formed and contains zero field mappings. The shared lesson is that the most dangerous failures return success, and the fix in both cases is to make absence distinguishable from emptiness.

Chapter 0001 · the confident, empty report
The evaluation here is a fixed threshold on a composite score over five known documents. Which System Design School lesson names that pattern, and what does it need to become a real gate?

Lesson 0002's discipline applies directly: a single summary number hides its own distribution. A composite of 0.99 over five documents could be 0.999 on four and 0.96 on one, and the one is what you want to see. To be a real gate it needs the per-document scores reported alongside the mean, and a sample size that makes a drop distinguishable from noise.
