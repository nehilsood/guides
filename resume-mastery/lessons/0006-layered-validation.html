Layered validation on an autonomous path

Three checks, each proving something different, none of them proving correctness. Knowing exactly what EXPLAIN does and does not tell you is the difference between a safety story and a slogan. Two claims in this bullet also need correcting, and both are better corrected by you.

The win

Name what each layer proves, and what none of them can — then say the sentence most candidates never say: a generated query that passes every check can still be wrong.

The line being defended
“Guarded its autonomous path with layered validation — live Snowflake schemas in agent context, table-name checks closing the injection path in LLM-written SQL, and EXPLAIN plus syntax, import, and runtime checks proving each generated fix before it touches production — regression-tested on a 368-scenario offline evaluation suite.”
Innovaccer · bullet 2 of 3
Say it out loud · about 75 seconds

A spoken answer to “how do you validate what the model writes?” The winning move is precision about what each check proves, followed by the sentence nobody expects: none of them proves it is right.

  1. Situation

    The debugger can write a fix and apply it to a production pipeline with nobody watching. So something has to check the fix first.

    No single check proves a fix is correct. So you build several cheap ones, and each rules out a different way of being wrong.

  2. Mechanism

    Three layers. First, the real table definitions go into context before anything is written, so it is not guessing at column names.

    Second, generated SQL is sent to Snowflake as an EXPLAIN. That proves it parses and binds against the live schema, and it never executes.

    Third, Python goes through parso with error recovery on, so we get every syntax error in one pass instead of stopping at the first.

  3. What I did

    The parso choice is the one I would defend. Each round trip to the model costs a generation, so returning four errors at once is one correction cycle rather than four.

    And I would state the limit plainly: EXPLAIN tells you the sentence is grammatical and every word is real. It does not tell you the sentence is true.

  4. What it cost

    Two corrections to my own bullet. It says table-name checks close the injection path. The real barrier is an allowlist permitting only SELECT and EXPLAIN.

    And “regression-tested” is generous for 368 recorded cases scored by cosine similarity, with no threshold published.

    The gap that bothers me most is in the harness. It scores generated code by how similar it reads, when the production path already has a validator that could run it.

The sentence that sounds fluent and gets you caught

“Every generated fix is validated before it touches production.” The flag guarding that layer defaults to off, so the sentence is true of the design and possibly not of the deployment. “There is a validation layer, it sits behind a flag, and here is the default” costs you nothing and cannot be contradicted.

The other trap is “we prevent SQL injection with table-name validation.” An interviewer who cares about security will ask how, and the answer is a keyword denylist plus a statement allowlist. Lead with the allowlist. It is the strong control and it is the one that is actually there.

Walk them through it · one generated fix, end to end

The say it out loud block is ninety seconds. This is the ten minutes after that, when they say “walk me through it.” One model-written fix, followed from the prompt to the moment it is allowed near production. The fix is a stand-in. The layers and the defaults are not.

The picture. Proofreading a letter written in a language you half speak. A spellchecker proves every word is a real word. A grammar checker proves the sentences parse. Neither of them can tell you the letter says something true. That gap is the whole chapter.

The case. The debugger has decided a failed job needs a query changed. A model is about to write SQL that will run against a production warehouse. Follow that query through every gate between the model and the data.

  1. Before it writes

    What happens. The cheapest validation is the one that stops the mistake being made at all. Before the model writes anything, the real schemas go into its context.

    Concretely. The live Snowflake definitions for the tables that query mentions. Actual column names, actual types.

    If they ask why. This is prevention rather than detection, and it is by far the cheapest of the three layers. A model that has been shown the column does not have to guess it.

  2. The allowlist

    What happens. The query comes back and is checked against what it is permitted to be.

    Concretely. There is a keyword denylist with things like DROP and TRUNCATE on it. There is also an allowlist permitting only SELECT and EXPLAIN.

    If they ask why. My résumé says table-name checks close the injection path. That is not what is implemented and I would rather say so. The allowlist is the strong control here, and a denylist only protects against what somebody thought of.

  3. EXPLAIN it

    What happens. The check on the query itself is one line. Put EXPLAIN in front of it and send it to Snowflake.

    Concretely. The database returns a plan without executing anything. If a plan comes back, the query parsed and every table and column in it exists.

    If they ask why. That second half is called binding. A query can be perfect grammar and still fail, because it mentions a column nobody has.

  4. The limit

    What happens. This is the sentence most candidates never say, so say it before you are asked.

    Concretely. EXPLAIN proves the sentence is grammatical and every word in it is real. It does not prove the sentence is true.

    If they ask why. A query can join the wrong two tables, filter on the wrong date, and plan perfectly. Every layer here rules out a different way of being wrong. None of them proves being right.

  5. The Python

    What happens. Some fixes are Python rather than SQL. That code gets parsed, never executed.

    Concretely. It goes through parso rather than the standard library's ast, with error recovery switched on.

  6. Why parso

    What happens. Generated code usually comes back with more than one problem in it.

    Concretely. With ast the first syntax error raises and you learn nothing about the rest. The model fixes that one thing, resubmits, and the next error appears.

    If they ask why. parso keeps parsing after a mistake and returns every error at once. The argument I made was about round trips rather than about parsing. Four errors together is one correction cycle instead of four.

  7. What it costs

    What happens. That is a third-party parser in place of the standard library, and a reviewer was right to ask about it.

    Concretely. It also only catches structure. Imports and runtime behaviour are separate checks and are not covered by this layer.

    If they ask why. A list of checks in a bullet implies one thing proves another. Saying which layer proves what is the answer that survives a follow-up.

  8. The suite

    What happens. Behind all of it sits an offline evaluation suite of 368 recorded scenarios with ideal answers.

    Concretely. They are scored by cosine similarity, which compares meaning. Nothing is run, and no threshold is published.

    If they ask why. Regression-tested is a generous word for that, and I would rather use the accurate one. Offline evaluation and a test suite are different things.

  9. The gap

    What happens. The thing that bothers me most is in the harness rather than in the system.

    Concretely. It scores generated code by how similar it reads, when the production path already has a validator that could run it.

    If they ask why. Similarity to an ideal answer is a reasonable design for free text. For code it measures the wrong property, and the better measure was already sitting there.

  10. The flag

    What happens. One fact matters more than the rest and it belongs at the end rather than hidden.

    Concretely. The feature flag gating this whole validation layer defaults to off.

    If they ask why. So the honest statement is that the layers are built, tested and not on by default. Volunteering that is worth more than any of the layers.

Behavioural · the story for this bullet

For “tell me about a technical choice a reviewer questioned” or “a small decision with a large payoff.”

  1. Decision

    Whether to validate generated Python with the standard library parser, which everybody reaches for, or with a parser that keeps going after the first mistake.

  2. Situation

    Generated code came back with multiple problems at once. Using ast, the first syntax error raised and we learned nothing about the rest. The model fixed one thing and resubmitted, and the next error appeared.

  3. Action

    I switched the validator to parso with error recovery enabled, which returns every error in one pass. The argument I made was about round trips rather than about parsing.

    Each cycle back to the model is a generation, with its latency and cost. Four errors reported together is one cycle. Four errors reported one at a time is four.

  4. Result

    Correction cycles collapsed on any fix with more than one problem, which is most of them. The feedback also got better. Seeing all the errors together makes the shape of the mistake obvious.

  5. What it cost

    A third-party parser instead of the standard library. That is a real dependency and a reviewer was right to ask. It also only catches structure. Imports and runtime behaviour are not covered by this layer. I would rather say that than let a list in a bullet imply otherwise.

Start here — the plain version

A model writes a fix for a broken data job. That fix might be SQL or Python. Before anything runs it against production, something has to check it. The interesting part is that no single check proves a fix is right. So what you build is a set of cheap checks. Each one rules out a different way of being wrong.

Three of them here. Give the model the real table definitions so it is not guessing at column names. Ask the database to plan the query without running it, which catches anything that does not exist. And parse the Python properly, collecting every error rather than stopping at the first.

Snowflake
The data warehouse these pipelines run against. It holds the real tables, so it is also the authority on whether a query makes sense.
EXPLAIN
Asking a database to produce a plan for a query without executing it. If the plan comes back, the query parsed and every table and column in it exists.
Binding
The step where names in a query are resolved against real schemas. A query can be perfect grammar and still fail to bind, because it mentions a column nobody has.
parso
A Python parser used here instead of the built-in ast. Its advantage is error recovery: it keeps parsing after a mistake, so you get every syntax error at once.
Schema context
Putting the real column names and types into the prompt before the model writes anything. Prevention rather than detection, and by far the cheapest of the three layers.
Denylist
A list of forbidden things. Here, SQL keywords like DROP and TRUNCATE. Weak as a security primitive, because it protects against what you thought of.
Allowlist
The opposite, and the stronger one. Permit only SELECT and EXPLAIN, and everything you did not think of is refused by default.
Offline evaluation
Running a fixed set of recorded cases through the system and scoring the answers. Not the same thing as a test suite, and the difference matters in this chapter.
Cosine similarity
A number between minus one and one saying how close two pieces of text are in meaning. Used here to score an answer against an ideal one.
Feature flag
An environment variable switching behaviour without a deploy. The one gating this validation layer defaults to off, which is the single most important fact in the chapter.
The technology — what each named thing is

The primer above names the layers of the guard. This one names what they guard against, starting from the ground. Two different injections are in play here and they are not the same attack.

Every entry answers four things. What it actually is, in plain words. Where this system uses it. What it buys, meaning what goes wrong without it. And the follow-up an interviewer asks once you have said the name.

SQL, in three parts
DQL, DML, DDLSQL is usually taught as one language, but it splits into three groups that do very different amounts of damage. Query language reads and changes nothing: SELECT. Manipulation changes rows: INSERT, UPDATE, DELETE. Definition changes the structure the rows live in: CREATE, ALTER, DROP, TRUNCATE. In the app. The allowlist admits the first group plus EXPLAIN and refuses the other two outright. What it buys. A precise place to draw the line. “Read-only” stops being a vague intention and becomes a list of permitted statement types that a program can check. The follow-up. Which group actually loses data. DROP is loud, obvious and immediately noticed. A DELETE with a slightly wrong predicate is silent, recoverable only from backup, and far more likely to be what a model generates.
Snowflake
the warehouse underneathA cloud data warehouse. Its distinguishing design choice is that storage and compute are pulled apart. The data sits in one place permanently, and a “warehouse” is a compute cluster you size, start and stop independently, with several able to read the same tables at once without fighting. Access is governed by roles and grants. In the app. It holds the real tables, so it is the authority on whether a generated query means anything at all. What it buys. Isolation between workloads and a bill you can switch off, because nothing needs to be running for the data to exist. The follow-up. Cost is charged per second of running compute. That is why a validation step which runs EXPLAIN instead of the query itself is cheap as well as safe, and it is a nice detail to have ready.
SQL injection
the classic oneThe oldest web vulnerability there is. An application builds a query by gluing user input into a string, so a user who types the right punctuation stops being data and becomes syntax. The textbook fix is parameter binding: the query text and the values are sent to the database separately, so a value can never be reinterpreted as code. In the app. The bullet claims the injection path is closed, so the word will come up. What it buys. Nothing here, and that is the point worth making. The follow-up. Binding does not apply to this shape. A model writes the entire statement rather than supplying a value to slot into one, so there is no parameter to bind. The defence has to be a different shape, which is exactly why the allowlist exists.
Prompt injection
the one that actually appliesText that arrives inside the model's context and changes what the model does. It does not need to come from a user. A log line, an exception message, a table comment or a column description can all carry instructions, and the model has no way to tell data from directions. In the app. This system reads failures produced by other systems, which is untrusted input by definition. What it buys. Naming it correctly is what makes the defence make sense. The follow-up. There is no parser that fixes it, and anyone offering one is wrong. The only dependable control is on the far side: assume the generated statement may be hostile and let nothing but a read get through, enforced somewhere the model cannot reach.
Abstract syntax tree
ASTWhat a parser produces after it has understood your code. The text, the whitespace and the comments are gone, and what remains is a tree of typed nodes. An assignment becomes a node with a target and a value, whether it was written on one line or five, with any spacing and any variable names. In the app. Checking what a fix does structurally, rather than matching strings in it. What it buys. Checks that survive formatting. A string search for a dangerous call is defeated by a line break, a comment, an alias or a rename. A tree walk is not. The follow-up. What a tree cannot tell you. It proves the code parses and shows what shape it has. It says nothing whatsoever about whether running it is a good idea.
ast and parso
two Python parsersBoth turn Python source into a tree, and they disagree about failure. ast is in the standard library and raises SyntaxError at the first problem, giving you nothing else. parso recovers: it carries on past a broken construct and hands back both a tree and a list of the errors it found. In the app. Model-written code often has one broken line and nine perfectly good ones. What it buys. You see all ten problems in one pass instead of discovering them one deploy at a time. For a feedback loop that hands errors back to a model, that is the difference between one round trip and nine. The follow-up. The cost of recovery. A recovered tree is a guess about what the author meant, so a check that passes against it is weaker evidence than the same check passing against a clean parse. Know which one you got.
Static and runtime checks
the two halves of “proving”Static means examining code without running it: does it parse, do the imports resolve, is the syntax legal, does it call anything forbidden. Runtime means actually executing it and watching what happens. They prove genuinely different things. In the app. The bullet claims a fix is proved before it touches production, and the word “proved” invites this distinction. What it buys. A cheap first filter. Static checks cost milliseconds and reject the obviously broken majority before anything expensive runs. The follow-up. Where the boundary sits, and be honest about it. Static checks are free and prove little. Runtime checks prove much more and need somewhere safe to execute, which is the expensive piece almost nobody builds first.
Grants and least privilege
the control under all of themDatabase permissions attach to roles, and every connection acts as exactly one role. Least privilege means that role holds only the permissions the job genuinely needs. A role with SELECT on four tables and nothing else cannot drop anything, whatever the query text says, because the engine refuses before it parses intent. In the app. It is the layer that still holds when every check above it has been bypassed. What it buys. Defence that does not depend on your own code being correct. Every other layer here is something you wrote and could have got wrong. This one is enforced by the database. The follow-up. Whether the agent's role is actually restricted. If it connects as something powerful, then the allowlist is the only thing between a bad generation and a truncated table, and an allowlist is code you wrote.
Sandbox
where you would run itAn isolated place to execute code you do not trust. In practice: a container with no network access, a copy of the schema with no real data, or a throwaway database that is destroyed afterwards. The defining property is that the worst outcome is contained. In the app. Any check that runs a fix rather than reading it would need one. What it buys. The ability to promote a static check into a runtime one, which is a large jump in how much you have actually proved. The follow-up. Whether one exists. “We do not execute generated code, we parse it” is a complete and honest answer that nobody will fault. Implying a sandbox you do not have is the kind of claim that unravels in one question.
Offline evaluation
the 368 scenariosA fixed set of recorded cases replayed through the system and scored. It is not a test suite in the usual sense, because the outputs are judged for quality rather than compared for equality — there is rarely one correct fix. In the app. It is the evidence behind the word “regression-tested”. What it buys. A way to change a prompt or a model and know whether things got better or worse, on a system whose output is not deterministic and cannot be asserted against. The follow-up. The scoring function and the pass bar. A suite whose score has never been written down, or which has no threshold that can fail a build, is a harness rather than a regression test. Using the honest word for it is the stronger position.

Layer one: never let it guess a column name

The cheapest validation is the one that stops the mistake being made. Before the model writes a query, the real schemas for the tables that query mentions go into its context.

SchemaLoaderTool does something more careful than dumping a schema file. Given a query, it extracts the referenced tables using SQL lineage, loads the schema for only those tables, and formats it as context.

That selectivity is the design. A warehouse has thousands of tables and you cannot put them all in a prompt. Extracting the tables first means the context holds exactly the definitions that matter, with column names, types, nullability and defaults.

Plain meaningBefore asking somebody to write a query, hand them the actual table definitions. Most wrong column names never get written.

Layer two: ask the database, do not guess

The check on a generated query is one line. Prefix it with EXPLAIN and send it. If a plan comes back, every table and column in that query exists. Nothing is executed.

validate_snowflake_query builds explain {query}, runs it, and returns whether a result came back along with any error. That is the whole function, and its simplicity is the point.

What it proves is precise and worth stating precisely. The query is syntactically valid. Every table exists. Every column exists on the table it is attributed to. The types in the predicates are compatible. That is a large class of errors ruled out by one round trip.

What it does not prove is equally worth stating. It does not run. It says nothing about whether the query returns the right rows, whether the join is the one you wanted, or whether it will finish this decade. A perfectly plannable query can be semantically wrong in every way that matters.

Plain meaningThe database tells you the sentence is grammatical and every word is real. It does not tell you the sentence is true.

Layer three: parso, and why not ast

Python gets parsed rather than executed. The library choice is deliberate: parso keeps going after a mistake and returns every error, where the standard parser stops at the first one.

validate_python_code loads a grammar, parses with error_recovery=True, and iterates the errors. Valid means the error list is empty.

The built-in ast.parse raises a SyntaxError on the first problem and tells you nothing about the rest. That is fine for a human, who fixes one thing and runs it again. It is expensive for a model, because each round trip is a generation. Getting four syntax errors in one response means one correction cycle instead of four.

The bullet also claims import and runtime checks. Be careful here. Parsing proves the code is well-formed, not that its imports resolve or that it runs. Import and runtime coverage comes from the pytest suite around the validation framework, not from validate_python_code itself.

Plain meaningWe read the code properly rather than running it, and we use a reader that reports every mistake rather than the first one.

The injection claim, corrected

The résumé says table-name checks close the injection path. The implemented guard is a keyword denylist plus a SELECT and EXPLAIN allowlist. The allowlist is the strong control, and it is not what the bullet names.

validate_sql_query upper-cases the query and looks for DROP, DELETE, TRUNCATE, ALTER and CREATE. That is a denylist, and denylists are structurally weak. They protect against the things somebody remembered, and a substring test on upper-cased text has obvious gaps.

The control that actually holds is the allowlist: the connector path only runs SELECT and EXPLAIN. A statement that is not one of those never executes regardless of what it contains. That is a much better sentence to say, and it is true.

So the honest version is: the guard is an allowlist on statement type, backed by a keyword denylist, and table-name validation is described in the design notes rather than implemented as the barrier.

Plain meaningThe real protection is that only reading is allowed. The list of banned words is a second, weaker fence, and the résumé names the wrong one.

The 368 scenarios, and what scoring them by similarity means

There are 368 recorded cases with ideal answers. They are scored by comparing meaning, not by running anything. That is a reasonable design for free-text output and it has a specific blind spot.

Each case holds an input — a code block, an error log, a type — and an ideal recommendation with an action, an investigation, a resolution and corrected code. Scoring uses calculate_semantic_score: embed the expected text, embed the actual text, take the cosine, multiply by a maximum and cap it.

The blind spot is direct. Cosine similarity rewards sounding like the ideal answer. Two correct investigations written differently can score badly. A fluent, confident, wrong investigation that uses the right vocabulary can score well. For the corrected_code field especially, similarity is a poor proxy when you could instead run EXPLAIN on it, which is an oracle you already have.

Two more things to say plainly. It is an offline evaluation harness rather than a pytest regression suite, so “regression-tested” is a generous word. And the documentation reports the harness, the dataset shape and the scoring, but no threshold, no CI wiring and no score.

Plain meaningWe check the answer reads like the right answer. We do not check that the answer works, even though for the SQL half we easily could.

  1. What are DDL and DML, and which of them does the allowlist let through?

    SQL is taught as one language. It splits into three groups that do very different amounts of damage. DDL changes structure: create, alter, drop, truncate. DML changes rows: insert, update, delete. Reading is select, and it changes nothing. The allowlist permits select and explain, and refuses both of the other groups. What that buys is a precise place to draw the line. “Read-only” stops being an intention and becomes a list a program can check. Worth adding which group really hurts. Drop is loud and immediately noticed. A delete with a slightly wrong predicate is silent, recoverable only from backup, and far more likely to be what a model writes.

    Red flagListing drop and truncate as the danger. They are the easy half. The quiet writes are the ones a denylist was never going to catch.

  2. What is Snowflake, architecturally?

    A cloud data warehouse whose defining choice is that storage and compute are pulled apart. The data sits in one place permanently. A warehouse is a compute cluster you size, start and stop independently. Several can read the same tables at once without fighting each other. Access is governed by roles and grants. What that buys is isolation between workloads and a bill you can switch off, because nothing needs to be running for the data to exist. Billing is per second of running compute. That is why a validation step which runs explain, rather than the query itself, is cheap as well as safe.

    Red flag“It's a cloud database.” The separation of storage and compute is the whole design, and it is what makes the cost argument work.

  3. What is SQL injection, and how is it normally prevented?

    The oldest web vulnerability there is. An application builds a query by gluing user input into a string. A user who types the right punctuation stops being data and becomes syntax. The standard fix is parameter binding. Query text and values are sent to the database separately, so a value can never be reinterpreted as code. What that buys here is nothing, and that is the point worth making. A model writes the entire statement rather than supplying a value to slot into one. There is no parameter to bind. The defence has to be a different shape, which is exactly why the allowlist exists.

    Red flagOffering parameterised queries as the answer. It is the right answer to a different question, and reaching for it shows you have not thought about this one.

  4. What is prompt injection, and why is it the one that matters here?

    It is text arriving in the model's context that changes what the model does. It does not need to come from a user. A log line, an exception message, a table comment or a column description can all carry instructions. The model has no way to tell data from directions. It matters here because this system reads failures produced by other systems, which is untrusted input by definition. No parser fixes it, and anyone offering one is wrong. The only dependable control is on the far side. Assume the generated statement may be hostile and let nothing but a read through, enforced somewhere the model cannot reach.

    Red flagPromising to sanitise the input. You cannot sanitise a language model's context. Constrain what its output is allowed to do instead.

  5. What is an abstract syntax tree, and what can you prove with one?

    It is what a parser produces after it has understood your code. The text, the whitespace and the comments are gone. What remains is a tree of typed nodes. An assignment becomes a node with a target and a value, whatever spacing or variable names it was written with. What that buys is checks that survive formatting. A string search for a dangerous call is defeated by a line break, a comment, an alias or a rename. A tree walk is not. You can prove it parses and what shape it has. You cannot prove anything about whether running it is a good idea.

    Red flagTreating a clean parse as a passing check. It proves the text is Python. It says nothing about whether the fix is right.

  6. Why parso rather than Python's built-in ast?

    Error recovery. Both turn source into a tree, and they disagree about failure. The standard ast raises on the first syntax error and gives you nothing else. Parso carries on past a broken construct and hands back both a tree and a list of the errors it found. Model-written code is often one broken line among nine good ones. What that buys is seeing all ten problems in one pass instead of one deploy at a time. For a loop that feeds errors back to a model, that is one round trip rather than nine. The cost is that a recovered tree is a guess about what was meant, so a check passing against it is weaker evidence.

    Red flagNaming the library without naming the property. Nobody chooses a parser for its name, and error recovery is the entire reason.

  7. If every check above it were bypassed, what is left?

    The database role. Permissions attach to roles, and every connection acts as exactly one role. Least privilege means that role holds only what the job needs. A role with select on four tables and nothing else cannot drop anything, whatever the query text says. The engine refuses before it considers intent. What that buys is defence that does not depend on your own code being correct. Every other layer here is something you wrote and could have got wrong. This one is enforced by the database. If the agent connects as something powerful, your allowlist is the last line, and an allowlist is code you wrote.

  1. What does “layered validation” actually mean here?

    Three cheap checks that each rule out a different failure. Schemas in context stop wrong column names being written. EXPLAIN catches anything that does not exist in the warehouse. Parsing catches malformed Python. No single one proves the fix is correct, so they are stacked.

    Red flagImplying the layers combine into a correctness proof. They rule out classes of wrongness, and saying that is more precise and more honest.

  2. What does running EXPLAIN on a generated query prove?

    That it parses, and that it binds. Every table named exists. Every column exists on the table it is attributed to. The predicate types are compatible. The database's own planner is the authority, so the check cannot drift from reality the way a cached schema file can.

    Red flagSaying it validates the query. Name the two properties, because the next question is what it does not cover.

  3. And what does it not prove?

    Everything about meaning. It does not execute. So it says nothing about the rows returned, or whether the join is the one intended. It says nothing about whether the query finishes in reasonable time. A query can plan perfectly and be completely wrong. That is the honest limit of the layer.

    Red flagNot having an answer ready. This is the follow-up, every time, and it is the one that shows whether you understood your own guard.

  4. Why parso rather than the standard library parser?

    Error recovery. The ast.parse function raises on the first syntax error and tells you nothing else. parso parses with recovery on and returns every error in one pass. The consumer here is a model, and each round trip costs a generation. Four errors in one response is one correction cycle instead of four.

    Red flag“It is more robust.” Name the property. Error recovery is a specific feature with a specific payoff here.

  5. Why fetch schemas live instead of shipping a schema file?

    Because a file goes stale and nothing tells you. A column gets renamed and the file does not change. The model then writes a query against a table that no longer looks like that. The tool instead extracts the tables a query references and loads only those. So the context is both current and small.

    Red flagMissing the selectivity. Loading only the referenced tables is what makes live loading affordable in a warehouse with thousands of them.

  6. How is the injection path actually closed?

    By an allowlist on statement type. The connector path runs only SELECT and EXPLAIN, so anything else never executes. There is also a keyword denylist covering DROP, DELETE, TRUNCATE, ALTER and CREATE. I would correct my own bullet here, because it names table-name checks and the barrier is the allowlist.

    Red flagLeading with the denylist. Denylists are the weak half, and leading with the weak half invites exactly the bypass question you do not want.

  7. What are the 368 scenarios?

    Recorded failure cases with ideal answers. Each has an input of code block, error log and type, plus an ideal recommendation with action, investigation, resolution and corrected code. It is an offline evaluation dataset rather than a pytest suite, and I would use the word evaluation rather than regression.

    Red flagCalling it a test suite. There is a real difference and the interviewer may know it.

  8. How are those scenarios scored?

    By semantic similarity. Both the expected and actual text get embedded, the cosine is taken, multiplied by a maximum score and capped. So it measures whether the answer reads like the ideal one. It is a reasonable choice for free-text fields and a weak one for generated code.

    Red flagNot naming the mechanism. “We score them” is the answer of someone who did not build the harness.

  9. Where does this validation sit in the debugger's flow?

    Between the fix being proposed and it being applied. The investigation produces corrected code and validation checks it. Only then can the action router send it to a retrigger. The important caveat is that ENABLE_PIPELINE_VALIDATIONS defaults to false. On a default deployment this layer is not in the path at all.

    Red flagDescribing it as always on. The default says otherwise and config is the first thing a careful interviewer reads.

  10. What is the riskiest claim in this bullet?

    Two of them. “Table-name checks closing the injection path” describes a guard that is documented rather than implemented, and the real barrier is the statement allowlist. And “regression-tested” oversells an offline evaluation set scored by cosine similarity with no threshold reported.

    Red flagDefending either phrase. The underlying engineering is good, and the wording is what will not survive a careful reader.

Deep dive

A third of these are about what a check cannot see. That is deliberate, and it is the level this bullet gets interviewed at.

  • Binding versus parsing
  • EXPLAIN is not free
  • Error recovery in practice
  • Selective schema loading
  • Denylist versus allowlist
  • Import and runtime checks
  • Why cosine scoring
  • What cosine rewards
  • Scoring code by similarity
  • Pass rate without a threshold
  • The flag default
  • The layer you would add

  1. Distinguish parsing from binding, and say which one matters more here.

    Parsing is grammar. Binding is resolving names against real schemas. Binding matters more, because a model writing SQL rarely produces ungrammatical SQL. It produces grammatical SQL about a column that does not exist. EXPLAIN is valuable precisely because it reaches the binding stage.

    Red flagTreating them as the same check. The distinction is why a syntax checker would be nearly useless for the SQL half.

  2. What does the EXPLAIN check cost you?

    A round trip to Snowflake, on the critical path of an autonomous fix, plus a live connection with credentials. It also means validation fails when the warehouse is unavailable, and you need a decision about what happens then. Failing closed is right for an autonomous path, and it should be explicit.

    Red flagCalling it free because it does not execute. Planning a query is real work and it is a dependency you have taken on.

  3. Give me a concrete case where error recovery changes the outcome.

    A generated function with two problems. A missing colon on line three and a bad indent on line nine. The ast parser raises on line three and stops, so the feedback names one problem. The model fixes it and resubmits, and only then learns about line nine. parso returns both, so one cycle handles both.

    Red flagAnswering abstractly. A two-error example makes the argument in one sentence.

  4. Why extract tables from the query first rather than load everything?

    Context budget and signal. A warehouse has thousands of tables, and their combined schema does not fit in a prompt. Even if it did, burying the five relevant tables among thousands makes the model's job harder. Extracting first means the context is exactly the definitions that matter.

    Red flagOnly citing token cost. The signal argument is the stronger half and most people miss it.

  5. Why is an allowlist stronger than a denylist here?

    Because a denylist protects against what you remembered. The keyword list covers five statements and a substring test over upper-cased text has obvious gaps. An allowlist permitting only SELECT and EXPLAIN refuses everything nobody thought of, which is the class that actually hurts you.

    Red flagPresenting the denylist as the control. It is defence in depth behind the real barrier, and the ordering matters when you describe it.

  6. The bullet mentions import and runtime checks. Where do those live?

    In the pytest suite around the validation framework, not in validate_python_code. That function parses and reports syntax errors. The test suite covers syntax, indentation, import and runtime error cases as scenarios. I would separate those two things rather than let the bullet imply one function does all four.

    Red flagLetting the list stand as one pipeline. Two mechanisms are being described, and only one of them runs before a fix is applied.

  7. Why score by semantic similarity at all?

    Because most of the output is free text. An investigation and a resolution are prose, and there is no exact match to test against. Embedding both and taking a cosine is a defensible way to score prose at scale. It is the right tool for those fields, and the wrong one for the code field.

    Red flagDismissing it. It is a reasonable choice, and the interesting answer is where it stops being reasonable.

  8. What does cosine similarity actually reward?

    Reading like the ideal answer. Two correct investigations phrased differently can score poorly. A confident, fluent, wrong investigation using the right vocabulary can score well. So the metric is measuring register as much as correctness, and that gap is worth stating before someone else finds it.

    Red flagSaying it measures semantic correctness. It measures semantic proximity, and proximity to a right answer is not the same as being right.

  9. You score corrected code by similarity. What would you do instead?

    Run it through the oracle I already have. For SQL, EXPLAIN the generated fix against the same schema and score binary validity. For Python, parse it. That turns the code field from a fuzzy match into a deterministic check, using machinery already written for the live path.

    Red flagNot connecting the two halves of the chapter. The eval harness ignores a validator the production path already uses, and noticing that is the point of the question.

  10. The harness reports a pass rate. Passing what?

    That is the gap I would flag. EvalSummary carries passed, failed and error case counts plus a pass rate and an average score, so a threshold exists somewhere in the runner. What is not in the documentation is what that threshold is, what it gates, or any recorded score. Without those, it is a harness rather than a gate.

    Red flagQuoting a pass rate you cannot source. If you do not have the number, say the harness exists and the number was not published.

  11. Why would validation default to off?

    Most likely because it was built after the path it guards. Shipping dark is the safe way to introduce a check that can block work. That is a defensible rollout pattern. What is not defensible is leaving it there. If I were still on this system, that flag would be the first thing I changed.

    Red flagGuessing confidently. Say it is the ship-dark pattern, then say what you would do about it, and both halves land.

  12. What layer is missing?

    A blast-radius check. Every current layer asks whether the fix is well-formed. None asks how much it would change. A generated UPDATE touching ten rows and one touching ten million both pass every check here. Counting affected rows before applying is the layer I would add, and it is the one that maps to actual damage.

    Red flagProposing more of the same. Another syntax-level check adds nothing. The missing axis is magnitude, not correctness.

A generated SQL fix passes the EXPLAIN check. What has that established?

  1. That it parses and binds against the live schema
  2. That it returns the rows the author actually wanted
  3. That it runs faster than the query being checked
  4. That it cannot drop or alter any existing table

Parsing and binding. The planner resolved every table and column against the real warehouse and the predicate types were compatible. That rules out a large class of errors in one round trip, and it never executes the query.

It establishes nothing about meaning. A query can plan perfectly and return the wrong rows, join the wrong way, or scan a table for an hour. What stops a destructive statement is a different control entirely: the allowlist that permits only SELECT and EXPLAIN.

How does the 368-scenario suite decide whether an answer was good?

  1. Cosine similarity between embeddings of expected and actual
  2. An identical string comparison against the stored answer
  3. A separate model adjudicating whether the answer holds
  4. Whether the corrected code executed without raising errors

Embeddings and a cosine, multiplied by a maximum score and capped. That is a sensible way to score prose fields like an investigation, where no exact match exists.

The last option is the interesting wrong answer, because it is what the harness should do for the corrected-code field. The production path already has an oracle for that: run EXPLAIN on the generated SQL. Scoring code by how similar it reads is the weakest part of this evaluation.

Edges and exceptions

Every one of these is a way a check passes and the fix is still wrong. That is the honest subject of this chapter.

  • Valid and destructive
  • Snowflake unreachable
  • Parses but never runs
  • Schema changes after validation
  • Bypassing the denylist
  • A scenario set that ages
  • Validation off in production
  • What you would change

  1. Give me a fix that passes every layer and is still dangerous.

    An UPDATE with a predicate that is valid but too broad. It parses, it binds, every column exists, and it changes ten million rows instead of ten. Nothing in this stack measures magnitude. That is the gap, and the missing layer is a row-count estimate before applying.

    Red flagReaching for an exotic example. The boring over-broad predicate is the realistic one and it makes the point better.

  2. Snowflake is unreachable when a fix needs validating.

    The SQL layer cannot run, and the decision is which way it fails. On an autonomous path it has to fail closed. An unvalidated fix is then never applied. Failing open would mean the one time validation mattered most is the time it was skipped. That is the worst possible correlation.

    Red flagSuggesting a cached schema fallback. That reintroduces the staleness problem live loading exists to solve.

  3. Python that parses cleanly but fails immediately on import.

    Passes the parse layer, because parsing is grammar. A missing module or a bad name is a runtime concern and parso never resolves names. The bullet's mention of import checks comes from the pytest suite rather than from this validator. Closing it properly means importing in a sandbox, which is a bigger commitment.

    Red flagClaiming the parser catches imports. It is a structural check and imports are a resolution-time concern.

  4. The schema changes between validation and the retrigger.

    Then the fix was validated against a warehouse that no longer exists in that shape. It is a time-of-check to time-of-use gap. During a migration that is real rather than theoretical. The window is small, and the mitigation is to validate as late as possible. Validate immediately before applying, not at proposal time.

    Red flagDismissing it as unlikely. Naming it as a TOCTOU gap shows you recognised the pattern, which is the whole point.

  5. How would you get a destructive statement past the keyword denylist?

    Several ways, which is the argument against denylists. Comments inside a keyword, a statement type nobody listed, or something reached through a stored procedure. I would not lean on it. The control that holds is the allowlist, because a statement that is not a SELECT or an EXPLAIN never reaches the connector at all.

    Red flagDefending the denylist as sufficient. It is not, you already have something better, and saying so is the strong answer.

  6. The 368 scenarios were recorded once. What happens as the platform changes?

    They age, and a stale case is worse than no case. Ideal answers referencing tables that were since renamed will fail a correct system, and passing them becomes a regression. Any fixed evaluation set needs an owner and a refresh cadence, and neither is documented here.

    Red flagTreating a recorded dataset as permanent. It is a snapshot of a moving system.

  7. You find out validation was off in production the whole time. What do you say?

    That the flag defaults to false and I should have checked which way it was set. Then the useful part. The layers still constrained the model during development. The statement allowlist is a separate control and it is always on. So the destructive path was closed even with validation off, and the correctness checks were not.

    Red flagGetting defensive. Separating which protections were live from which were not is the answer that rebuilds credibility.

  8. What would you change, in order?

    Turn the validation flag on and require it before any autonomous apply. Score the corrected-code field with the validator instead of a cosine, since the oracle already exists. Add a row-count estimate as a blast-radius check. Then publish a threshold so the harness becomes a gate rather than a report.

    Red flagListing them without an order. The ordering is the judgment, and the first one is a config change with the largest payoff.

Probes to expect

  1. “What does EXPLAIN actually prove?” The highest-signal question in this chapter. Most candidates say it validates the query and cannot go further, which reveals the check was adopted rather than understood.
    Model answer — say yours first

    Two things: the query parses, and it binds. Every table exists, every column exists on the table it is attributed to, and the predicate types are compatible. The planner is the authority so the check cannot go stale. It proves nothing about meaning, because it never runs. A query can plan perfectly and return entirely the wrong rows, and that is the honest limit of the layer.

  2. “Can a fix pass all your checks and still break production?” Testing whether you will claim safety you do not have. The right answer names the missing axis rather than defending the existing layers.
    Model answer — say yours first

    Yes, and the realistic case is an over-broad predicate. A statement that parses, binds and touches ten million rows instead of ten passes every layer here, because every layer asks whether the fix is well-formed and none asks how much it changes. The missing layer is blast radius: estimate affected rows before applying. That is the one I would add next.

  3. “How do you prevent SQL injection?” A security-minded interviewer will ask, and the résumé wording points them at the weaker control. Lead with the allowlist.
    Model answer — say yours first

    The barrier is an allowlist: the connector path executes only SELECT and EXPLAIN, so anything else never runs whatever it contains. Behind that there is a keyword denylist for DROP, DELETE, TRUNCATE, ALTER and CREATE, and I would not rely on that half, because a denylist only covers what somebody remembered. I would also correct my own bullet, which names table-name checks.

  4. “Your evaluation scores generated code by similarity. Is that sound?” A sharp question. The strong answer concedes it and connects to machinery already in the system.
    Model answer — say yours first

    For the prose fields it is defensible, since an investigation has no exact match to test against. For the corrected-code field it is the weakest part of the harness. We already have an oracle on the production path: EXPLAIN for SQL and a parse for Python. Scoring the code field with the validator instead of a cosine would make that part deterministic, and it is reusing code that already exists.

  5. “Was this validation actually on?” If the interviewer has read the config, this is coming. Getting there first is worth more than any answer you can give afterwards.
    Model answer — say yours first

    ENABLE_PIPELINE_VALIDATIONS defaults to false, so on a default deployment the layer is not in the path. That is the ship-dark pattern and it is a reasonable way to introduce a check that can block work, but leaving it there is not. Worth separating what was still live: the statement allowlist is an independent control and it is always on, so the destructive path stayed closed even with validation off.

This chapter and chapter 0003 both put a deterministic check behind a model. Name the shared principle, and the one difference in how the two systems use it.

The principle is that a model should never be asked a question that has an oracle. In chapter 0003 the oracle is stat_var_processor.py run as a subprocess, and its verdict drives the retry loop. Here the oracles are EXPLAIN and a parse. The difference is that chapter 0003 feeds the oracle's output back as correction, where this system uses it as a gate. Feeding it back is the stronger pattern, and it is what the eval harness here should do with generated code.

Chapter 0003 · the validator is a subprocess
The validation layer defaults to off, and the debugger it guards can retrigger production. Which chapter's four gates are you relying on instead, and which of them is unaffected?

Chapter 0005's. The screener has to escalate, the solution's action field has to say apply, the action router has to agree, and the retrigger flag has to be on with a threshold. None of those four depends on ENABLE_PIPELINE_VALIDATIONS, so they hold regardless. What is lost with validation off is proof that the fix is well-formed, not the bounds on how often it can act.
