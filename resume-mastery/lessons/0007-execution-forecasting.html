Execution forecasting and dependency resolution

Five lines of pandas, and the whole chapter is in the choice of alpha. This is the smallest system on the résumé and the one where you can most easily sound like you understand statistics or like you do not. It also contains a word that names something never written.

The win

Defend a forecasting choice on its failure mode rather than its accuracy — and have the weekday answer ready, because it is the first thing anyone who has run a scheduler will ask.

The line being defended
“Built the execution-forecasting layer of a daily workflow planner (EWMA, Prophet) — inferring each pipeline's run cadence from execution history to predict its next run date, driving an auto-generated daily execution plan with parent–child dependency resolution in place of manually tracked schedules.”
Innovaccer · bullet 3 of 3

In plain words

This layer guesses when each data pipeline will run next. It takes the gaps in days between past runs, leans hardest on the newest gaps, and adds that typical gap to the last run date. Its weak spot is the calendar: a Monday-to-Friday job has gaps of 1, 1, 1, 1, 3, so after a Friday run it predicts Saturday. Raise that yourself, and say plainly that the calendar-aware fix, Prophet, was designed but never built.

Say it out loud · about 75 seconds

A spoken answer to “tell me about the forecasting layer.” This is a small system, so depth is the only thing that impresses. Get to the weekday failure fast, because owning it is the whole performance.

  1. Situation

    A platform runs thousands of pipelines, and a lot of them have no trustworthy schedule. Somebody kept a spreadsheet of what was supposed to run today.

    The idea was to stop reading intent and start reading evidence.

  2. Mechanism

    Take the distinct days a pipeline ran, difference them into gaps, and take an exponentially weighted mean of those gaps. Add it to the last run.

    Alpha is a half, so the newest gap carries half the weight, the one before a quarter. It adapts to a real change in cadence within a few runs.

    Then two details that matter. The test is greater than or equal, so overdue work stays on the plan.

    And if a pipeline's parent is already scheduled, the child is dropped. The parent will trigger it anyway.

  3. What I did

    The decision I would defend is using history rather than the declared schedule. It is less precise than reading a cron expression. It is also right more often, because configuration drifts and history does not.

  4. What it cost

    The honest limitation, and I would rather raise it. An interval has no calendar in it.

    A weekday job gives gaps of one, one, one, one, three. The weighted mean is about 1.4, so after a Friday run it predicts Saturday, a day that job has never run.

    That is exactly what Prophet would fix, and I should be clear: Prophet is a strategy branch in the design with no implementation behind it. EWMA is what runs.

The sentence that sounds fluent and gets you caught

“We used EWMA and Prophet to forecast execution.” It is the bracket in the résumé read aloud, and it names one library that was never written. The enum branch calls _analyze_with_prophet and that method does not exist. Say “EWMA implemented, Prophet designed for and not built, and here is the failure that motivated it” — which is a better engineering story than two working algorithms would have been.

The other trap is calling this “time series forecasting.” It is a weighted average of date differences. Using the grander phrase invites questions about stationarity and seasonality that the implementation cannot answer, and the plain description is entirely respectable.

Behavioural · the story for this bullet

For “tell me about a time you chose the simpler solution” or “a limitation you shipped with deliberately.”

  1. Decision

    Whether to model calendars properly from the start, or ship an interval average that would be visibly wrong for weekday pipelines.

  2. Situation

    The planner needed to know what was due each day, across thousands of pipelines, many with no trustworthy schedule. The replacement for a hand-maintained spreadsheet had to exist before it could be good.

  3. Action

    I built the interval-average version and put a strategy pattern around it. A calendar-aware method could then be added without changing callers. EWMA at alpha a half, with distinct dates so retry storms could not produce zero-day gaps.

    I also wrote the comparison as greater than or equal rather than equal. Anything missed then stays on the plan, instead of falling off it silently.

  4. Result

    The generated plan replaced the spreadsheet, and its errors became measurable against real execution history rather than invisible. The dependency check stopped children being run twice when a parent was already scheduled.

  5. What it cost

    It is wrong for every weekday pipeline, and it predicts weekends. I knew that shipping it. The strategy slot for a calendar-aware method is still empty. So the honest statement is that I left a known defect behind an interface designed to fix it. That interface is still unused.

Start here — the plain version

A platform runs thousands of data pipelines. In principle each has a schedule. In practice many do not, or have one nobody trusts, and somebody keeps a spreadsheet of what is supposed to run today.

This layer throws the spreadsheet away. It looks at when each pipeline actually ran in the past, works out roughly how often that is, and predicts when it is due next. Anything due today goes on a generated plan. The second half is dependency: if a pipeline is going to be triggered by its parent, it must not also be listed on its own.

Cadence
How often something runs. Daily, weekly, every third day. Here it is not read from a config. It is inferred from the gaps between past runs.
Execution history
The record of when a pipeline actually ran. More trustworthy than a declared schedule, because it is what happened rather than what was intended.
Interval
The number of days between two consecutive runs. The whole forecast is built from a series of these.
EWMA
Exponentially weighted moving average. An average where recent values count for more, with the weight decaying as you go back in time.
Alpha
The decay knob, between zero and one. Here it is 0.5, meaning the newest interval carries half the weight, the one before it a quarter, and so on.
Prophet
A forecasting library that handles seasonality, trends and holidays. It appears in this system as a named strategy with no implementation behind it.
Strategy pattern
Choosing between interchangeable algorithms behind one interface. Useful, and it makes it easy to ship a branch that dispatches to a method nobody wrote.
Parent–child
One pipeline triggering another when it finishes. If the parent is running today, the child will run anyway, so listing it separately would run it twice.
Execution plan
The generated list of what should run today. The output of this layer, and the thing that replaces the hand-maintained spreadsheet.
Cron
The five-field schedule format. Relevant here mainly because its day-of-week numbering differs from the platform's, which is a conversion with an off-by-one in it.

Inferring a schedule instead of reading one

The declared schedule is not the source of truth. What a pipeline actually did is. The whole design follows from preferring evidence over configuration.

The obvious implementation reads each workflow's cron expression and computes the next fire time. That is exact, it is cheap, and it is wrong in this environment, because a large share of pipelines either carry no schedule or carry one that stopped matching reality.

So the analyzer takes execution history, derives the intervals between runs, and forecasts from those. It is less precise than a cron expression and it is right more often, which is the trade worth naming out loud.

The five lines that do the work

Take the distinct days a pipeline ran. Difference them to get gaps. Take an exponentially weighted mean of those gaps. Add it to the last run. If today is on or past that date, it is due.

In code: unique execution dates, diff().dt.days.dropna() for the intervals, intervals.ewm(alpha=0.5).mean().iloc[-1] rounded to an integer, then last_date + timedelta(days=ewm_interval). Finally needs_execution = current_date >= predicted_next_date.

Two small decisions inside that are worth pointing at. Taking unique dates means several runs on one day collapse to one, so a retry storm cannot produce a zero-day interval and drag the average to nothing. And the comparison is greater than or equal, not equal, so a pipeline that was missed yesterday stays on the plan today rather than dropping off it.

In plain words

This one number sets how much the forecast trusts recent gaps over older ones. At 0.5 the newest gap counts for half, the one before for a quarter, then an eighth, so roughly the last three gaps decide the answer. That follows a real change in rhythm within a few runs, but one odd gap, such as an outage, drags the forecast a long way. The 0.5 was picked rather than measured; replaying past runs to see which value would have predicted best is how you would back it up.

What alpha of 0.5 actually chooses

Alpha is the only tuning parameter and it decides how fast the forecast forgets. At 0.5 the most recent gap carries half the weight and everything older shares the rest. That adapts quickly and it is noisy.

Write the weights out, because being able to say them is the difference between using a library and understanding it. The newest interval gets 0.5, the one before 0.25, then 0.125. After four or five observations the older history is contributing almost nothing.

That is a deliberate position. A pipeline whose cadence genuinely changed from weekly to daily is tracked within a few runs. The cost is that one unusual gap moves the prediction a long way, and the most common unusual gap is an outage.

So the honest framing is that alpha 0.5 optimises for adapting to real change, and pays for it by being sensitive to disruption. A smaller alpha would be steadier and slower. I would not defend 0.5 as derived, because it was chosen.

The weekday problem, and the word Prophet

A job that runs Monday to Friday has gaps of one, one, one, one, three. An average of those is not a calendar. It will predict Saturday, and Saturday is a day this job has never once run.

This is the concrete limitation and it is worth volunteering, because anyone who has operated a scheduler will think of it immediately. EWMA models an interval. It has no concept of a week, a weekend, a month end or a holiday. Averaging one, one, one, one and three gives something near one point four, and adding that to Friday lands on the weekend.

That is exactly the gap Prophet fills, and it is why Prophet appears in the design. WorkflowExecutionAnalyzer has an AnalysisMethod enum and dispatches to _analyze_with_prophet for one branch. That method is not defined anywhere in the system.

So the résumé naming both is a claim about intent rather than shipped code. The version to say: EWMA is implemented and running, Prophet is the strategy the design leaves room for, and the weekday case is the reason it exists.

In plain words

The check only looks one step up. If only the grandparent is on the plan, the child is still scheduled on its own, so it can run twice after all.

Dependency resolution, which prevents a double run

If a pipeline is triggered by its parent finishing, and the parent is already on today's plan, then listing the child separately runs it twice. One lookup prevents that.

_is_parent_scheduled asks the event handler for a workflow's parent, and returns true if that parent is in the set of already-scheduled workflows. If it is, the child is left off the plan, because it will be triggered anyway.

Note the shape of the check: it looks one level up, and it consults the set scheduled in this run. That makes it a single-level guard within one planning pass rather than a full dependency graph traversal. For a two-level parent and child relationship that is sufficient and cheap.

  1. What is pandas, and what does ewm(alpha=0.5).mean() compute?

    Pandas is Python's library for tables in memory. A Series is one labelled column and a DataFrame is several sharing an index. The idea that makes it short and fast is simple. Operations apply to whole columns at once, in C, rather than row by row in a Python loop. What it buys here is date arithmetic and missing-value handling that would otherwise be fifty lines. The call computes an average where each older value counts half as much as the one after it. Newest interval a half, the one before a quarter, and so on. What that buys is adaptation without a change detector. A pipeline that moved from weekly to daily is forecast from the daily part. About the last three intervals decide the answer.

    Red flag“A weighted average.” Say the weights. Halving is what makes it forget fast, and forgetting fast is the behaviour you chose.

  2. What is a time series, and what makes this one awkward?

    A time series is data where every observation carries a timestamp and the order is part of the meaning. You cannot shuffle it and you cannot treat the rows as independent samples. The distance between two points is itself information. That is what separates it from an ordinary table, and it is why a whole family of methods exists for the shape. This one is awkward because it is short and irregular. Nine recorded runs give you eight intervals, which is not enough to fit anything with confidence. The thing being modelled is the gap, not a value. A pipeline paused for a month leaves an interval that never meant anything.

    Red flagTalking about seasonality on eight points. With that much history the honest method is a weighted average, and saying so is a strength.

  3. What does Prophet actually fit?

    An additive model, meaning it splits a series into parts that are summed. A piecewise-linear trend that can bend at detected changepoints. Seasonal cycles expressed as Fourier terms. Holiday effects. And noise. It is built for long daily business series with weekly and yearly structure, and it is deliberately usable without tuning. What it would buy is seasonality, which a weighted mean cannot represent at all. A pipeline that skips weekends is a pattern rather than noise. But that is not what this data is. If the branch that would call it has no method body, say so plainly rather than letting the name imply a model that never ran.

    Red flagDescribing Prophet vaguely as “time-series forecasting.” The follow-up is what it assumes about the data, and this data breaks those assumptions.

  4. How would you tell whether the forecast is any good?

    Mean absolute error in days is the number to quote. It is the average size of the miss, in the unit you actually care about. It says how far the predicted date sits from the real one. The percentage version divides by the true interval first, and it is worse here. The consequence is discrete, because the plan is either right for today or it is not. What an error figure buys is a claim that can be falsified, and a way to tell whether a change helped. You also need a baseline. Predicting the last interval again is the one to beat, and plenty of methods do not.

    Red flagQuoting an error with no baseline. Any number sounds good alone, and most forecasting methods lose to repeating the last value.

  5. What is backtesting, and what is easy to get wrong?

    Pretending to stand at a date in the past. You forecast forward from only what was known then, and compare against what actually happened next. Walk that cut-off forward through the history and you get many honest predictions from data you already have. What it buys is an error figure today instead of in three months. Without it, validating a forecaster means waiting for the future to arrive. Everything you need here is already recorded. The mistake is leakage. The forecast must only ever see runs before the cut-off. Fit on the whole history and score against part of it, and the number is meaningless in a way nothing in the output will show.

    Red flagCalling it testing. A test has a right answer. A backtest has a score, and the score needs a baseline beside it.

  6. What is cron, and what is the day-of-week trap?

    Cron is the scheduling syntax used almost everywhere. Five fields: minute, hour, day of month, month, day of week, with a star meaning every. What it buys this system is a stated intention to compare reality against. The gap between the cron expression and the observed run history is itself the signal that something is wrong. The trap is numbering. Cron calls Sunday zero. Python's weekday calls Monday zero. Mixing them shifts every schedule by one day. It is a whole-day error, and it only shows itself on one day in seven, which is exactly how it survives testing and reaches production.

    Red flagWaving at cron as trivia. It is the declared schedule this layer exists to distrust, and the off-by-one is a real defect you can name.

  7. What does “parent–child dependency resolution” have to do?

    Work out whether a pipeline will be triggered by something upstream before deciding it needs its own slot. Pipelines that trigger other pipelines form a directed acyclic graph. Arrows point one way and nothing can be its own ancestor. What walking it buys is a forecast that accounts for why a pipeline runs. Predicting a child from its own history alone ignores that it only runs when its parent does. Doing it properly means a traversal, because a grandparent not running today decides whether the grandchild runs at all. The immediate parent will look perfectly healthy. Checking only that parent is one lookup, and it is a narrower claim.

    Red flagSaying resolution when the code does a lookup. If it checks one level, say one level. The word implies a traversal and the interviewer will ask for it.

  1. In two sentences, what does this layer do?

    It works out how often each pipeline actually runs. It does that from execution history rather than from a configured schedule. From there it predicts the next run date. Anything due today goes onto a generated daily plan, which replaced a hand-maintained one.

    Red flagCalling it machine learning. It is a weighted average over date differences, and dressing it up invites a question you will not enjoy.

  2. Why not just read each pipeline's cron expression?

    Because a lot of them do not have one, or have one that stopped matching what the pipeline really does. History is evidence and configuration is intent. Inferring from history is less precise than a cron expression, and it is right more often in this environment. That is the trade.

    Red flagSaying cron would be harder. It would be easier and exact. The reason is that it is exact about the wrong thing.

  3. Walk me through the prediction, line by line.

    Take the distinct dates the pipeline ran. Difference them to get intervals in days and drop the empty first one. Take an exponentially weighted mean of those intervals and round to an integer. Add that many days to the last run date. If today is on or past it, the pipeline is due.

    Red flagSkipping the rounding. Days are integers here, and the rounding step is where a 1.4-day cadence becomes a one-day one.

  4. What is an exponentially weighted moving average?

    An average where recent observations count for more, with the weight decaying geometrically as you go back. Unlike a simple moving average it has no window. Every past value contributes something, just less and less. The decay rate is the single parameter.

    Red flagDescribing it as a rolling average. The absence of a window is the defining property, and it is why old history never has to be discarded.

  5. Alpha is 0.5. What does that choose?

    How quickly the forecast forgets. At 0.5 the newest interval carries half the weight, the one before a quarter, then an eighth. After four or five observations the older history barely counts. That adapts fast to a genuine change in cadence and it is sensitive to one unusual gap.

    Red flagNot being able to state the weights. They are halves and it is the one piece of arithmetic in this bullet.

  6. Why take unique dates rather than all executions?

    Because several runs on the same day would produce zero-day intervals. A retry storm on one afternoon would drag the mean towards zero and the pipeline would be predicted as due every single day afterwards. Collapsing to distinct days makes the interval a genuine cadence rather than a run count.

    Red flagCalling it deduplication. Name the failure it prevents, because that is what the question is for.

  7. The check is greater than or equal, not equal. Why does that matter?

    Because a pipeline that was missed has to stay on the plan. With an equality test, a workflow whose predicted date was yesterday falls off today and is never scheduled again. Greater than or equal means anything overdue stays overdue until it runs.

    Red flagTreating it as a detail. A one-character difference here is the gap between a planner that recovers and one that silently drops work.

  8. How does the parent-child resolution work?

    Before adding a workflow to the plan, it asks whether that workflow has a parent and whether the parent is already scheduled in this run. If so, the child is left off, because finishing the parent will trigger it. Without that check a child with a scheduled parent would run twice.

    Red flagDescribing it as a dependency graph. It is a one-level lookup against the set scheduled in this pass, and saying so is more accurate.

  9. What is the riskiest claim in this bullet?

    The word Prophet. It reads as two implemented algorithms and there is one. The right framing is that the design uses a strategy pattern with EWMA implemented, and Prophet named as the intended second strategy for seasonality. That is still a real design decision and it survives a follow-up.

    Red flagHoping nobody asks. It is a named library in a bracket, which makes it one of the most askable things on the whole page.

  1. Why EWMA rather than a simple mean of all intervals?

    Because a simple mean treats a gap from six months ago as equal to last week's. Pipelines change cadence, and when one moves from weekly to daily the simple mean takes many observations to catch up. EWMA weights the recent and tracks the change in a few runs.

    Red flagSaying EWMA is more accurate. It is more responsive, and responsiveness costs stability. Naming the trade is the answer.

  2. How would you actually choose alpha rather than picking 0.5?

    Backtest it. The history is already there. Hold out the last known run for each pipeline, predict it at several alphas, and measure the error in days. Then pick the alpha that minimises it across the fleet, or per cadence class. That turns a chosen number into a measured one.

    Red flagDefending 0.5 with reasoning. It was a default. Saying how you would justify it is worth more than pretending it was justified.

  3. The platform is down for ten days. What happens to the forecasts afterwards?

    Every affected pipeline gets one ten-day interval. At alpha 0.5 that carries half the weight immediately. A daily pipeline would then be predicted as roughly five-daily on the next pass. Since the test is greater than or equal it stays on the plan, so it still runs. It recovers over the following few runs.

    Red flagSaying it breaks. The greater-or-equal test saves it. The prediction is wrong for a few days and the scheduling outcome is still right.

  4. A pipeline has run exactly twice. What does the forecast do?

    There is one interval, so the exponentially weighted mean is that interval. The forecast is entirely determined by a single observation. That is not wrong, and it is not a forecast in any useful sense either. It argues for a minimum history before trusting a prediction, and there is no such threshold today.

    Red flagClaiming EWMA handles it gracefully. It returns a number. Whether that number means anything is a separate question and the honest answer is no.

  5. A pipeline has never run. What happens?

    There are no intervals, so the differenced series is empty and taking its last element raises. That is the edge case I would check first in this code. The right behaviour is to fall back to the declared schedule if one exists. Otherwise leave it off the plan rather than fail the pass.

    Red flagAssuming it returns a default. Following the pandas operations through to an empty series is the answer, and it shows you read the code rather than the description.

  6. The interval is rounded to whole days. What does that cost?

    Precision below a day, which does not matter, and an accumulating bias, which can. A true cadence of 1.4 days rounds to one. So the prediction runs ahead of reality and the pipeline is marked due early. With a greater-or-equal test it appears on the plan early and stays there, which is the safe direction.

    Red flagDismissing it because days are the unit. Rounding always biases in one direction, and knowing which direction is safe is the point.

  7. A grandparent triggers a parent which triggers a child. Does the check handle it?

    Only one level. It asks for the immediate parent and whether that parent is in the scheduled set. If the grandparent is scheduled but the parent is not directly on the plan, the child's check passes and it gets scheduled independently. For two-level relationships it is correct, and for deeper chains it needs a traversal.

    Red flagClaiming it resolves the graph. It resolves one edge, which was enough for the shapes present, and saying so is the accurate answer.

  8. Why process workflows through a queue rather than loading them all?

    Memory. The planner runs across the whole fleet. Materialising every workflow with its execution history at once is a large footprint for no benefit. Pulling one at a time keeps the working set to a single workflow. The work is independent per workflow, so nothing is lost.

    Red flagCalling it streaming for its own sake. It is bounded memory over an unbounded fleet, and the reason it is safe is that the work does not need a global view.

  9. There is a day-of-week conversion with a modulo in it. What is that about?

    Cron and the platform number the days differently. The conversion subtracts one and takes the result modulo seven. It is worth mentioning because off-by-one errors in day numbering are silent. A job scheduled a day early every week looks like a business rule rather than a bug.

    Red flagSkipping it as trivial. Calendar off-by-ones are the classic silent failure, and noticing one is a good signal.

  10. How would you know whether the forecasting is any good?

    Compare predicted dates against what actually happened. That needs no new instrumentation, because the history is the ground truth. Two numbers matter. Mean absolute error in days tells you how close it is. The share of pipelines that ran on an unplanned day tells you what the plan missed, and that is what operators feel.

    Red flagProposing only an error metric. A planner is judged on what it missed, not on its average closeness.

A pipeline runs every weekday. EWMA has just seen its Friday run. What does it predict next?

  1. Saturday, since the average interval is near one
  2. Monday, since it detected the weekly working pattern
  3. Tuesday, since it averages over the whole fortnight
  4. Friday, since it repeats the most recent interval

Saturday. The intervals are one, one, one, one, three, and their exponentially weighted mean is about 1.4, which rounds to one. Friday plus one day is Saturday, a day this pipeline has never run.

An interval average has no calendar in it. It cannot represent “not at weekends” because it only ever models the size of a gap. That is precisely the gap Prophet was meant to fill, and it is why the strategy branch exists.

A workflow is due today, and its parent is already on today's plan. What happens?

  1. The child is skipped, as the parent triggers it
  2. Both are scheduled, and the later one is discarded
  3. The child runs first, so the parent reuses it
  4. The parent is skipped, since the child covers it

The child is left off. _is_parent_scheduled looks up the immediate parent and checks whether it is in the set scheduled in this pass. If it is, the child will be triggered when the parent finishes, so scheduling it separately would run it twice.

Worth being precise about the limit: this is one lookup against one level, not a graph traversal. A grandparent-parent-child chain where only the grandparent is planned will still schedule the child independently.

Edges and exceptions

A forecasting layer is mostly edges. Several of these have no good answer in the current code, and saying so is the right move.

  • Month-end jobs
  • Backfills in the history
  • Timezones
  • Trusting the plan
  • Cold start
  • What you would change

  1. A pipeline runs on the last day of every month.

    The intervals are 28, 30, 31, 31 and 30 days. EWMA gives something around 30. Adding 30 days to the 31st of January predicts the 2nd of March. That is wrong in a way that repeats every year. Calendar rules cannot be expressed as an interval, which is the weekday failure in a different costume.

    Red flagTreating it as a new problem. It is the weekday failure again, and recognising the shared cause is the answer worth giving.

  2. Somebody backfills six months of data by running a pipeline fifty times in one afternoon.

    Those collapse to a single distinct date, so the interval series barely notices. That is the unique-dates decision paying off. What it does leave is a large gap before that day and a large gap after it. Those will pull the forecast around for a few runs before it settles.

    Red flagMissing that unique dates already handles most of it. The residual effect is on the neighbouring intervals, not on the fifty runs.

  3. The fleet spans timezones. Does that matter here?

    Yes, because everything is in whole days and a day boundary is timezone-dependent. A run at 23:30 in one zone and 00:30 in another are the same moment and different dates. That would show up as a zero or two-day interval that is not real. Normalising to one zone before taking distinct dates is the fix.

    Red flagSaying it does not matter for daily granularity. Daily granularity is exactly what makes the boundary matter.

  4. Why would an operator trust a generated plan more than their spreadsheet?

    Because the spreadsheet drifts and nothing tells you. It is maintained by hand, it goes stale quietly, and its errors are invisible until something does not run. The generated plan is derived from what actually happened, so it is wrong in ways you can measure. I would rather have a measurably imperfect plan than an unmeasurable one.

    Red flagClaiming it is more accurate. It is more checkable, and that is the better argument and the honest one.

  5. A brand new pipeline is onboarded. How does it get scheduled?

    It does not, by this layer, because there is no history to infer from. That is the cold-start gap and it is real. The sensible design is to fall back to the declared schedule until enough runs exist, then switch to inference. Roughly three or four intervals is where an alpha of 0.5 stops being dominated by one observation.

    Red flagIgnoring cold start. Any system that learns from history has one, and having a threshold in mind is what makes the answer concrete.

  6. What would you change, in order?

    Add a calendar-aware method, because the weekday and month-end failures are the same bug and they are the ones operators see. Then backtest alpha rather than leaving it at a default. Then a staleness rule for decommissioned pipelines. Implementing Prophet is one way to do the first, and a day-of-week histogram would cover most of it far more cheaply.

    Red flagPutting Prophet first as a library rather than as a capability. The requirement is calendar awareness, and there is a much cheaper way to get most of it.

Probes to expect

    Model answer — say yours first

    It predicts a weekend, and I would rather tell you than be asked. The intervals are one, one, one, one, three, and their weighted mean is about 1.4, rounding to one. Friday plus one is Saturday. An interval average has no calendar in it, so it cannot express “not at weekends.” That is exactly the gap a seasonality-aware method fills, and it is why the design has a second strategy slot.

  2. “Why alpha equals 0.5?” Testing whether a parameter was chosen or inherited. Conceding it and describing the experiment is stronger than any justification.
    Model answer — say yours first

    It was a default rather than a derived value, and I would not pretend otherwise. What it buys is fast adaptation: the newest gap carries half the weight, so a genuine cadence change is tracked in a few runs, at the cost of being pulled around by one unusual gap. To justify it properly I would backtest, holding out each pipeline's last run and measuring error in days across several alphas. The history is already there, so it is about a day of work.

  3. “Tell me about the Prophet part.” A direct question about a named library in a bracket. There is one honest answer and it is better than the dishonest one.
    Model answer — say yours first

    Prophet is in the design and not in the implementation. There is an analysis-method enum and a branch that dispatches to _analyze_with_prophet, and that method is never defined. EWMA is the default and the only one that runs. The reason the slot exists is the weekday failure, which needs seasonality rather than a better average. I would also say a day-of-week histogram would cover most of that case far more cheaply than the library would.

  4. “What is the worst thing a wrong prediction causes?” Looking for whether you understand the asymmetry. The design already leans one way and you should be able to say which.
    Model answer — say yours first

    Running something that should not have run. A missed prediction is recoverable because the due test is greater than or equal, so anything overdue stays on the plan until it runs. A spurious prediction puts real work into production early, and for a pipeline with side effects that is the expensive direction. The parent check exists to stop the most likely version of that, which is a child being scheduled when its parent will trigger it anyway.

  5. “A pipeline gets decommissioned. What does your planner do?” A quiet question with an uncomfortable answer, and the uncomfortable answer is the right one.
    Model answer — say yours first

    It keeps predicting it forever. The last interval still exists, the predicted date passes, and because the test is greater than or equal it stays due permanently. So the plan slowly accumulates dead pipelines. The same property that rescues a missed run is what creates the ghosts. The fix is a staleness rule: if the last run is several intervals in the past, stop predicting and surface it for review instead.

The lessons behind this chapter

System Design School teaches these mechanisms from first principles and breaks them in a lab. This chapter defends what you did with them. An interviewer moves between those two registers without warning.

  1. SDS 0002 · p50 is a lie A forecast judged on mean error hides the pipelines it missed entirely, and those are the only ones an operator notices.
  2. SDS 0014 · Idempotency is a key and a clock The whole parent-child check exists to prevent a double run, which is the problem idempotency solves properly.
