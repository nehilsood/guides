Idempotency Is a Key and a Clock

Everybody knows the answer is an idempotency key. Almost nobody can say what happens when two copies of the same request arrive in the same millisecond — and the obvious implementation applies all sixteen of them. The fix is one line of schema, and the failure it cannot catch is a number you have to choose.

The win

Fire sixteen concurrent duplicates of one request and watch the textbook implementation apply the side effect sixteen times out of sixteen. Add a unique index and it applies once — while failing fifteen legal retries with a 500. Then invert the write order and get one apply, zero errors. Finally break it a way no index can catch, with a clock.

Why you, specifically
“Architected a 5-stage multi-agent schematization pipeline (Gemini, Google ADK) with deterministic validation and LLM-feedback retry loops — delivering each PV map pre-built with the data insights behind it, so engineers refine rather than author, cutting a dataset from ~3 hours of hand-mapping to a ~30-minute review pass.”

“LLM-feedback retry loops” is the phrase an interviewer will stop on. A retry loop over a five-stage pipeline means stages get re-driven after a partial failure, and lesson 0012 guaranteed those partial failures exist — a propagated deadline expires mid-turn by design. So the pipeline re-runs stages that already succeeded, and app/pipeline/base.py has said so in a docstring since the first commit: “must be safe to call twice with the same payload — it is not yet.”

The second place this bites is sharper, because it involves money. A voice checkout has one irreversible step, and a retry over a dropped connection places a second order without anybody doing anything wrong.

Both bullets are defended in full in chapter 0003 and chapter 0018 of Résumé Mastery — this lesson is where the mechanism underneath them gets built and broken.

Start here — the plain version

Exactly-once delivery does not exist, and the reason is short. A sender that gets no reply cannot tell whether the request was lost or the response was, so it has to retry. Therefore the receiver has to be able to recognise a repeat. There is no protocol that removes this, only a place to put the recognising.

What you can have is effectively-once: deduplicate on the way in, and make the apply safe to repeat. The dedupe is four decisions — what the key is, what it is scoped to, how you confirm it is the same request, and how long you remember it — plus one mechanism that is not a decision at all, because only the database can settle a tie.

Idempotent
“An operation where a request can be retransmitted or retried with no additional side effects.” A property of the operation, not of the network.
Effectively-once
Dedupe plus an idempotent apply. Describes what an observer sees, never what the wire delivers.
Idempotency key
A token the client mints before its first attempt, identifying an intent. Not a hash of the payload, because two identical payments are two payments.
Key scope
The namespace the key is unique within: one tenant, one operation. Global scope lets a key minted for cancel satisfy a confirm.
Request fingerprint
A hash of the request stored beside the key, so the same key with a different body can be rejected instead of silently replayed.
Key lifetime
How long the record is kept. A correctness parameter: it must outlive the longest retry window any client can produce.
Check-then-act
Read whether the key exists, then write it. Everything between those two statements is a window two callers fit through.
Insert-first
Write the key, and handle the collision. No window, because the check and the write are one statement.
Unique constraint
The database's promise that two rows cannot share a value. The only component in this lesson that can decide a tie.
In-progress
A third record state, between absent and done. Without it a second caller cannot tell “already finished” from “happening right now”.

The window between the read and the write

The implementation everyone writes first is three lines and it reads correctly: look the key up; if you have seen it, return the stored answer; otherwise record it and do the work. It is correct for one caller at a time, which is the condition it is never tested under.

Two callers arriving together both execute the lookup before either executes the write. Both find nothing. Both record the key. Both do the work. Nothing failed, no exception was raised, no log line is out of the ordinary, and the side effect happened twice. Under sixteen callers it happens sixteen times, which is measured below and is not an approximation.

Why this is a database question and not an application one

Any fix in application code is another check-then-act with a smaller window: a lock you take is a read followed by a write, a cache you consult is a read followed by a write. Shrinking the window changes the odds and not the outcome, and an intermittent double-charge is worse than a reliable one because it will be closed as unreproducible.

The tie has to be broken by something that can decide it atomically. That is the unique index — not because indexes are magic, but because the conflict is settled by the same write that stores the row, so there is nothing in between for a second caller to fit through.

Start the database, then check it actually published a port

Port 5432 is the single most likely port on a developer machine to already be taken, usually by another project's Postgres. When it is, docker compose up still reports success and the container still runs — it simply never gets a host binding, and every connection goes to whatever else is listening. The symptom is a password failure for a password that is definitely correct.

This happened on the machine these figures were produced on. The compose file takes SDS_POSTGRES_PORT, and .env.example has the two lines to change. Check with docker compose ps postgres and look for 0.0.0.0:5432->5432 rather than a bare 5432/tcp.

    $ cd anchor/vendor-eval-gateway
$ docker compose up -d postgres
$ docker compose ps postgres --format '{{.Name}}  {{.Status}}  {{.Ports}}'

    A host binding, and a healthcheck that passed

    The thing to check is the arrow. 0.0.0.0:…->5432/tcp means the container is reachable; a bare 5432/tcp with no arrow means it is not, however healthy it claims to be. This output says 55432 rather than 5432 because 5432 was already taken on the machine these figures came from — that is the collision described above, shown rather than tidied away.

    This is the first lesson in the course that needs a real server, and it needs one for a specific reason: a dictionary cannot lose the race. Python's event loop makes a check and a write atomic by accident, so an in-memory store would report this lesson's bug as absent.

  2. Fire sixteen concurrent duplicates of one request — one key, one body, as a client's retry storm would — through three implementations of the same idea.

    $ uv run python -m bench.idempotency --experiment race

strategy                     callers  applied  replayed  in progress   500s  caught
read-then-write, no index         16       16         0            0      0       0
read-then-write + index           16        1         0            0     15       0
insert-first + index              16        1         0           15      0      15

    Sixteen of sixteen, and not one error to investigate

    The first row is the implementation in most codebases. Every caller read an empty table, every caller inserted, every caller applied. The side effect ran sixteen times and the system reported complete success, because from each caller's point of view nothing went wrong.

    The second row adds the unique index and nothing else. It is now correct — one apply — and it produced fifteen integrity errors that reached the caller. Those are 500s returned to a client doing something entirely legal. Correct and unusable.

    The third row swaps the order of two statements. One apply, zero errors, and the same fifteen collisions absorbed and turned into “in progress”. Nothing about the index changed; what changed is who catches the violation.

  3. Find the concurrency at which the naive version starts to break, because “only under heavy load” is the excuse that keeps it in production.

    $ uv run python -m bench.idempotency --experiment sweep | head -10
    The smallest number of simultaneous duplicates that breaks each strategy.

strategy                     callers  applied  replayed  in progress   500s  caught
read-then-write, no index          2        2         0            0      0       0

read-then-write + index            2        1         0            0      1       0
    Before / after · the answer is two

    Not “at high concurrency”. Two simultaneous duplicates apply twice, and the applies track the caller count all the way up. There is no threshold to stay under and no load level at which this is safe.

    Over five runs the 2-, 4- and 32-caller rows were identical every time; 8 and 16 occasionally lose one or two to a straggler that arrives late enough to see the row (8 gave 8,7,8,8,7 and 16 gave 14,16,15,14,16). The wobble is not the finding and it does not soften it — the smallest number ever observed at sixteen callers was fourteen applies of one request.

    That matters for how you argue about it. “We have never seen a double-apply” is not evidence the window is small — it is evidence that duplicates have not yet arrived close enough together, which a single client-side retry storm from lesson 0010 arranges in one outage.

  4. Now the second decision, which has nothing to do with concurrency: what counts as “the same request”.

    $ uv run python -m bench.idempotency --experiment mismatch
    first request  {'vendor': 'acme', 'amount': 100}  ->  apply
honest retry   {'vendor': 'acme', 'amount': 100}  ->  replay, response 'charged 100'
different body {'vendor': 'acme', 'amount': 900}  ->  Conflict: key 'mismatch-1' was first used for a different request
same body, keys reordered  ->  replay (fingerprint sorts keys)
    Reject the third line rather than replaying it

    A caller who reuses a key with a different body has a bug, and the tempting behaviour — return the stored response, since that is what the key says happened — would tell them their new request had been carried out. The Builders' Library is unambiguous: “we find that it is safest to assume that the customer intended a different outcome… we return a validation error indicating a parameter mismatch.”

    The fourth line is the detail that makes it usable. The fingerprint sorts keys before hashing, so a client whose JSON library does not preserve field order still gets a replay rather than a conflict. Get that wrong and you reject honest retries from your most careful callers.

  5. The last decision, and the one the index cannot help with. Make the key's lifetime shorter than the client's retry window.

    $ uv run python -m bench.idempotency --experiment ttl
    A client whose retry window is longer than the key's lifetime.
No unique index can catch this: by the time the retry lands, there is
nothing left to collide with.

ttl  60.00s  (lifetime longer than the window )  applied 1  replayed 1
ttl   0.05s  (lifetime shorter than the window)  applied 2  replayed 0
    Applied twice, with the index present and working perfectly

    Nothing here raced. One caller, two attempts, 300 ms apart. The key was pruned in between, so the second attempt found an empty table and was, as far as the database is concerned, a brand new request. Stripe documents exactly this behaviour rather than hiding it: “we generate a new request if a key is reused after the original is pruned.”

    So the lifetime is a correctness parameter, not a cleanup policy, and the number it has to beat is one lesson 0010 already measured. Full jitter over six attempts produced a median retry window of 2 507 ms and no jitter produced 5 000 ms — but that is one client's window, and the number you need is the longest any client can produce, including the one retrying by hand tomorrow morning.

Underneath

One layer down · why the database has to settle it

Four things. The first is why the problem cannot be removed, the second and third are the two decisions people skip, and the fourth is the mechanism — which is the only part that is not a judgement call.

Exactly-once does not exist, and the proof is one sentence

A sender that receives no reply cannot distinguish a lost request from a lost response. Those two states are identical from where it is standing, and in one of them the work has not been done. So it must retry, and therefore the receiver must be able to recognise a repeat. No protocol removes this — acknowledgements only move the ambiguity to the acknowledgement.

What is achievable is that an observer cannot tell the difference, which is why the right phrase is effectively-once. Malcolm Featonby's definition is the one to hold: “an idempotent operation is one where a request can be retransmitted or retried with no additional side effects, a property that is very beneficial in distributed systems.” Notice it is a property of the operation. Nothing about the network changed.

Where the ambiguity can live, and what each choice costs:

put it in who pays what it costs the network nobody, it cannot be done n/a the sender retries until it hears back duplicate requests the receiver dedupe on a key one row and one write nowhere the user a second charge

Only two of those rows are real choices, and the fourth is what you have by default. Moving the ambiguity to the receiver is the only option that ends with a correct outcome, which is why every payments API converges on the same design.

The key identifies an intent, and the scope is half of it

The key is minted by the client before its first attempt — Featonby again: “a unique caller-provided client request identifier for idempotent operations meets this need”, with the side benefit that the identifier shows up in audit logs. It is deliberately not a hash of the payload, because two identical payments a minute apart are two payments, and a payload hash would silently merge them.

The scope is the half that gets skipped. A key is unique within a namespace, and if that namespace is global then one tenant's UUID can collide with another's, and a key minted for cancel can satisfy a confirm. The constraint in app/db/models.py is therefore on (scope, key) and never on key alone, where scope is tenant plus operation.

The fingerprint closes the remaining gap. Storing a hash of the request beside the key lets you tell a genuine retry from a client bug, and Stripe describes the behaviour plainly: “the idempotency layer compares incoming parameters to those of the original request and errors if they're not the same to prevent accidental misuse.” The implementation detail that matters is sorting the keys before hashing, so that field ordering is not mistaken for a different request.

The lifetime is a correctness parameter, and the index cannot save you

This is the failure worth carrying out of the lesson, because it looks like housekeeping. Stripe prunes keys at 24 hours and states the consequence rather than burying it: “we generate a new request if a key is reused after the original is pruned.” If any client's retry window can outlast your retention, that client's duplicate arrives to an empty table and applies a second time, with the unique index present and behaving perfectly.

Featonby gives the shape of the answer without giving you a number, which is correct: “requirements for retention vary across services and service resources. We have found that, for EC2 instances, it works to limit the time period to the lifetime of the resource, plus an interval after which it is reasonable to assume that any late arriving requests would either have arrived or would no longer be valid.”

The window to size against, from lesson 0010's measurements:

client retry window safe lifetime 6 attempts, no jitter 5 000 ms trivially covered 6 attempts, full jitter 2 507 ms trivially covered a human re-running it tomorrow ~24 h the binding constraint a queue redelivering a backlog minutes to hours check the broker

The automated clients are not the problem — their windows are seconds. The lifetime is set by your slowest retrier, which is usually a person or a message broker, and neither appears in the retry code you would think to read.

Insert first, because the only atomic check is the write itself

Every application-level fix is another check-then-act with a smaller window. Take a lock: that is a read then a write. Consult a cache: read then write. You are shrinking the odds, and an intermittent double-apply is worse than a reliable one because it gets closed as unreproducible.

Inserting first has no window because the check and the write are the same statement; the database decides, and the loser is told. What step 2 measured is that this is not the index's doing — both of the last two rows had the same index and the same fifteen collisions. The difference is entirely who was expecting them. Check-then-act meets the violation on a path that had already concluded the key was free, so it propagates as a 500; insert-first meets it on a path written to expect it, reads the existing row, and answers.

The same fifteen collisions, three ways:

applied user-visible errors what the loser is told read-then-write, no index 16 0 nothing; it also applied read-then-write + index 1 15 500, on a legal retry insert-first + index 1 0 in progress, or the answer

The middle row is the one to recognise in a codebase, because it is correct and it looks like an incident. Somebody adds the constraint after a double-charge, the double-charging stops, and the 500 rate goes up — and the two facts are usually reported by different teams.

The third record state is what makes the last column possible. Absent, in_progress and succeeded are three different answers: without the middle one the loser cannot distinguish “already done, here is the result” from “being done right now, ask again shortly”, and would have to either block or guess. Stripe draws the same line from the other side, declining to store a result at all when “the request conflicts with another request that's executing concurrently”.

Which lands on the sentence worth keeping: the key is the easy decision. The scope says which requests are the same, the fingerprint says they really are, the index says who wins a tie, and the lifetime says how long any of that stays true — and only the third of those is something you can delegate to a library.

Check yourself

With no unique constraint, sixteen concurrent duplicates of one key ran through a read-then-write idempotency check. How many applied the side effect?

  1. All sixteen, since every caller read an empty table
  2. Just one, since the first insert always wins here
  3. About half, since the callers paired up by chance
  4. None of them, because the state column blocked it

All sixteen, and the sweep shows the count tracking the caller count exactly from two upward. Every caller executed its SELECT before any caller executed its INSERT, so all sixteen saw no row, all sixteen recorded the key, and all sixteen did the work. No exception was raised and nothing in the logs was unusual.

Worth knowing that the first version of this measurement reported 1 applied, and was wrong. The connection pool was cold, so establishing connections serialised the callers and they never actually overlapped. The instrument failed in the reassuring direction, which is the direction to distrust.

A key is pruned after 24 hours. A client retries the same request 36 hours later. What does the unique constraint do about the duplicate?

  1. Nothing; there is no row remaining to collide with
  2. Rejects it outright, as the key is still reserved
  3. Replays the response that was stored under that key
  4. Raises a conflict, since the body no longer matches

Nothing at all. The row is gone, so the retry arrives at an empty table and is, correctly as far as the database is concerned, a brand new request. It applies a second time with the index present and working perfectly — measured in step 5, one caller, two attempts, no concurrency involved.

That is why the lifetime is a correctness parameter rather than a cleanup policy. It has to outlive the longest retry window any client can produce, and the binding constraint is almost never the automated retrier — lesson 0010 measured those at two to five seconds. It is the person re-running a failed job the next morning, or a broker redelivering a backlog.

Say it out loud · about 75 seconds

A spoken answer to “your pipeline has retry loops — what stops a stage running twice?” Read it aloud, then say it again with the page covered.

  1. Situation

    Our pipeline re-drives stages after a partial failure, and the deadline work guarantees partial failures exist. So stages that already succeeded get run again.

  2. Mechanism

    Exactly-once delivery is not a thing. A sender cannot tell a lost request from a lost response, so it retries, so the receiver has to deduplicate.

    The usual code reads the key, then writes it. Everything between those two statements is a window that two callers fit through.

  3. What I did

    I fired sixteen concurrent duplicates at it. All sixteen of sixteen applied, with no error raised anywhere. It breaks from two callers upward, not under heavy load.

    Adding a unique index made it correct and returned fifteen 500s to clients doing something legal. Inverting the two statements gave one apply and zero errors.

    Same index, same fifteen collisions. What changed is who was expecting them.

  4. What it cost

    A write before every write, and a row to keep and sweep. The key is scoped to tenant plus operation, never global.

    And the lifetime is a correctness parameter. Prune inside a client's retry window and the duplicate applies twice, with the index working perfectly. No index catches that one.

The sentence that sounds fluent and gets you caught

“We use idempotency keys, so retries are safe.” Complete as a headline and empty underneath, and the follow-up is always the same: “what happens if two copies arrive at once?” If the answer is a lookup followed by a write, you have just described the bug. The version that holds names the order: “the key is inserted first against a unique constraint on tenant, operation and key, and we catch the violation and replay — so the database decides the tie rather than the application.”

The second trap is the one almost nobody survives, because it sounds like operations rather than correctness. Asked how long you keep the keys, “we expire them after a day to keep the table small” invites “and what is your clients' longest retry window?” If the retention is shorter, the duplicate applies again and no index can see it. Say the lifetime and what you sized it against, in the same breath.

Probes to expect

  1. “Your pipeline has retry loops. What stops a stage running twice?” The question behind the résumé bullet. Answering “idempotency keys” is the start of the answer, not the answer — the interviewer is waiting to hear whether you know what happens under concurrency.
    Model answer — say yours first

    Right now, nothing — the stage interface has said so in a docstring since the first commit. So I measured what that costs: sixteen concurrent duplicates of one request applied the side effect sixteen times, with no error raised anywhere, because every caller read the key table before any caller wrote to it.

    The fix is an idempotency key inserted before the work, against a unique constraint on tenant, operation and key, catching the violation rather than checking first. That gives one apply and zero user-visible errors. The version that only adds the constraint is also correct and returns fifteen 500s to clients doing something entirely legal, which is worth knowing because it is what you get if you add the index after an incident and stop there.

    Invites · “What does the loser see?” — in-progress or the stored response, which is why there are three record states.
  2. “How likely is that race really? Surely it needs heavy load.” The push-back that keeps this bug in production. The number makes it unarguable, and it is a small number.
    Model answer — say yours first

    Two callers. I swept it — 2, 4, 8, 16, 32 simultaneous duplicates — and the applies track the caller count throughout; the worst case I ever measured at sixteen callers was fourteen applies of one request. There is no concurrency below which it is safe, and no threshold to stay under.

    “We have never seen it” means duplicates have not yet arrived close enough together, which is a statement about traffic rather than about the code. A client-side retry storm arranges exactly that: an outage ends, every client that was retrying wakes at the same moment, and without jitter they arrive together by construction. That is the lesson before this one, and it is the thing that turns this from theoretical into an incident.

    Invites · “Would a lock fix it?” — a lock is a read then a write, so it shrinks the window rather than closing it.
  3. “What is the key, and what is it scoped to?” Checks whether you have designed one or used one. The scope answer is short and the reason for it is the memorable part.
    Model answer — say yours first

    The client mints it before its first attempt — a v4 UUID — and it identifies an intent, not a payload. It is deliberately not a hash of the body, because two identical charges a minute apart are two charges and a payload hash would merge them silently.

    Scope is tenant plus operation, so the constraint is on the triple rather than on the key alone. A global key space lets one customer's UUID collide with another's, and worse, lets a key minted for cancel satisfy a confirm. Alongside it I store a fingerprint of the request, so the same key with a different body is rejected rather than replayed — and the fingerprint sorts the JSON keys first, or a client whose map ordering varies gets a conflict on an honest retry.

    Invites · “Why reject rather than replay?” — replaying tells them their new request was carried out, which is worse than an error.
  4. “How long do you keep the keys?” Sounds like an operations question and is the one that separates having implemented this from having read about it. If your answer is about table size, the follow-up will end badly.
    Model answer — say yours first

    Long enough to outlive the longest retry window any client of ours can produce, which makes it a correctness parameter rather than a cleanup schedule. I measured the failure: with the lifetime shorter than the window, the same request applied twice — one caller, two attempts, no concurrency — with the unique index present and working perfectly. There is nothing left to collide with.

    Our automated retriers are the easy case; they run six attempts over two to five seconds. The binding constraint is a human re-running a failed dataset the next morning, so 24 hours is the floor and the number came from the slowest retrier rather than the busiest. Stripe prunes at 24 hours and documents the consequence directly — a key reused after pruning starts a new request — which is the right way round: state it rather than let people assume it is safe.

    Invites · “What if a broker redelivers a week later?” — then a day is not enough, and the broker's retention sets yours.
  5. “Could you do this without the database — in Redis, or in memory?” A good-faith question with a precise answer. What you need is not a database, it is one atomic conditional write, and being able to say that shows you understand the mechanism rather than the recipe.
    Model answer — say yours first

    In memory, no — and the reason is instructive. A single-threaded event loop makes the check and the write atomic by accident, so an in-memory store reports this bug as absent. It has no window to lose, which makes it useless as a stand-in for the thing that does.

    Redis, yes, because SET key value NX is exactly the primitive required: one atomic conditional write where the loser is told. What the database gives you on top is durability and the ability to store the response transactionally with the work, which matters when the apply and the record must land together. So the requirement is not “a database”, it is one atomic compare-and-set on the key, plus somewhere durable to keep the answer for as long as the lifetime demands.

    Invites · “What if the process dies between the insert and the apply?” — the row is stuck in-progress, which is why that state needs a timeout of its own.

Recall — from lessons 0011–0013

0011 built a breaker whose half-open state admits exactly one probe. What does that have in common with the in_progress record state here?

Both are a way of saying “someone is already finding out” so that everybody else can wait rather than duplicate the work. The half-open probe exists because if every caller tested recovery at once you would re-create the outage you were recovering from; in_progress exists because if every duplicate proceeded on finding no completed record you would apply the side effect once per caller. In both cases the state is what turns a race into a queue, and in both cases the interesting bug is what happens if the holder dies: a half-open probe that never returns leaves the breaker stuck, and an in_progress row whose process crashed leaves the key claimed and the work undone. Both therefore need a timeout on the intermediate state, which is the detail people leave out of both.

lesson 0011 · exactly one half-open probe
0012's deadline capped the worst turn at 8 001 ms by converting 26 late answers into failures. Why does that make this lesson necessary rather than optional?

Because it manufactures partial failures on purpose. Before propagation, a turn that ran long finished late; after it, the turn is cut off mid-pipeline, which means some stages have completed and written their output and the rest have not. Anything that re-drives that turn — a retry loop, an operator, a queue redelivery — re-runs the stages that already succeeded. So the deadline fix in 0012 does not create the duplicate-apply problem, but it guarantees the conditions for it at a known rate: twenty-six turns in two hundred, every run. A resilience mechanism that converts slowness into partial completion has to be paired with one that makes partial completion safe to repeat, or you have traded a latency bug for a correctness bug.

lesson 0012 · 26 turns of 200, cut off mid-turn
0013 found a check that never fired — “has the deadline passed?” discarded zero of 576. Is there an equivalent trap in this lesson, and did it fire?

Yes, and it is the instrument rather than the mechanism. The first run of the race benchmark reported one apply for the strategy that should have applied sixteen, which would have made the whole lesson wrong in the reassuring direction. The cause was a cold connection pool: establishing sixteen connections is slow enough to serialise the callers, so they never actually overlapped and the window was never opened. Warming the pool before measuring changed 1 to 16. It is the same discipline as 0013's zero, arriving from the other side — there, a clean result meant the check was useless; here, a clean result meant the test was. Both were found by disbelieving a number that made the story tidier, which is the only reliable filter for this class of mistake.

lesson 0013 · a check that discarded nothing

This is the last lesson of the batch, and the redraw test is now set up as an experiment rather than a request. Lesson 0013's diagram was drawn to the current 12-mark ceiling; this one was drawn to eight. Cover the screen and redraw both, give one of the 75-second scripts out loud, then take three probes cold. Tell me which diagram came back and which one fell apart — that answers the ceiling question with evidence, and it is the only part of this workspace I genuinely cannot do for you.

One honest note on the eight-mark constraint: it fitted, but only because this diagram had a naturally symmetric shape — two panels, two callers, two outcomes. It did cost the state machine. There is no room here to draw absent, in_progress and succeeded as states, so they live in the prose and in one label. If your redraw comes back without them, that is the ceiling biting rather than you forgetting, and it is exactly the sort of thing the experiment is meant to surface.
