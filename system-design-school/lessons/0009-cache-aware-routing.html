Cache-Aware Routing

Lesson 0008's win lives in one replica's memory. Add a second replica behind a round-robin balancer and you throw most of it away — and the two obvious fixes fail in opposite directions, which is what makes this a design decision rather than a setting.

The win

Take prefix-cache hit rate from 47 % to 78 % and p99 first-word from 396 ms to 172 across four replicas, by changing which part of the prompt you hash — then find the version that puts every request on one server.

Why you, specifically
“Scale it to a million concurrent avatar interviews… what is the load balancer doing about sticky sessions when the session is stateful?”

That is your own prep note, and it is the question this lesson answers. Every interview turn carries the whole conversation so far, so the cacheable part of a prompt grows with the conversation — and it exists on exactly one machine. A balancer that does not know which one is discarding the largest latency lever you have.

It is also the first lesson here where the naive answer and the clever answer are both wrong, in opposite ways, and the measured middle is the whole content.

That sentence is defended in full in chapter 0002 of Résumé Mastery — this lesson is where the mechanism underneath it gets built and broken.

Start here — the plain version

A load balancer's job used to be simple, because servers were interchangeable: any request could go anywhere, so you spread them evenly and were done. A model server holding a prefix cache is not interchangeable. It has something the others do not — the key-value blocks for conversations it has already seen — and sending the next turn somewhere else means paying full prefill again.

So the balancer has to optimise a different quantity: not “did every server get the same number of requests?” but “did each request land where its prefix already lives?” Those two goals genuinely conflict, and this lesson is about where the balance sits.

Replica
One model server. Several serve the same model behind a balancer, and each holds its own prefix cache — nothing is shared between them.
Round-robin
Send request 1 to replica 1, request 2 to replica 2, and so on. Perfectly even, and completely blind to what each replica holds. The default nearly everywhere.
Least-outstanding-requests
Send to whichever replica has the fewest requests in flight. Genuinely better than round-robin under uneven work, and still cache-blind.
Affinity (or stickiness)
Deliberately sending related requests to the same replica. Here the relation is “same conversation”, because that is what shares a prefix.
Consistent hashing
Choosing a replica by hashing a key, so the same key always lands on the same replica — without a lookup table, and with only a small share of keys moving when a replica is added.
Hash window
Which part of the prompt you feed the hash. Not a standard term, and the single most important decision in this lesson: too short and every request hashes the same, too long and every request hashes differently.
Longest-prefix match
Routing by asking which replica already holds the most leading blocks of this prompt. What real cache-aware balancers do, and it needs a load limit bolted on or it collapses.
Load imbalance
The spread between the busiest and idlest replica. Affinity always costs you some, and the interesting question is how much you will accept.
Cache cliff
What a replica's death does under affinity: its share of conversations lose their prefixes at once and every one of them pays full prefill on its next turn.

Round-robin optimises the wrong number

Round-robin makes request counts equal. That was the right goal when replicas were interchangeable, and it stopped being the right goal the moment a replica started holding state that made it better at some requests than others. Nothing warns you, because the balancer's own metrics look perfect: an even split is exactly what it was asked for.

The cost is not subtle. Across four replicas, with a conversation history that grows every turn, hit rate measured 47 % under round-robin and 78 % with the same requests routed by conversation — and p99 first-word went from 396 ms to 172. Same hardware, same prompts, same total work; the only difference was which machine each request was handed to.

Why round-robin still gets 47 % and not zero

Because part of the prompt is shared by everybody. The rubric preamble is identical across all conversations, so after one request each replica has it cached and every replica hits on that span regardless of routing. Round-robin only loses the conversation-specific part — which in a long interview is most of the prompt, and in a single-turn API call is none of it.

That is the first thing to establish before touching a balancer: how much of your cacheable prefix is per-conversation rather than global? If the answer is “almost none”, round-robin is fine and this lesson is a distraction.

Now cover it and redraw

Sixty seconds. Three spans and three arrows. This is the drawing that answers “what does your load balancer do about sticky sessions” without you having to remember any product's feature name.

  • The three spans, in the right order, with what each is shared by written underneath.
  • Three arrows ending in three different spans — the failure, the answer, the other failure.
  • The two outcomes on the two failures: one replica and round-robin. They fail in opposite directions, which is why the middle exists.
  • 47 to 78 %, and 396 to 172 ms, with the load spread beside them.
Draw the bar before you say anything. Everyone who gets this question wrong starts by talking about the balancer; the answer is a property of the prompt.

Lab — five routers, one workload

Lab 0009 ~20 minutes

47 % to 78 %, and the router that puts everything on one box

Needs: anchor/vendor-eval-gateway no Docker, no server lesson 0008's prefix cache
Modelled, like lesson 0008's second half

The replicas here are FakeUpstream instances with lesson 0008's modelled prefix cache, running in one process. The milliseconds are not measurements of a GPU. What is real is the quantity being compared — the fraction of prompt tokens already resident on the replica the request landed on — which is decided entirely by the router and not at all by the hardware. Quote the hit rates and the ratios; do not quote the absolute latencies.

  1. Run all five routers against one identical workload: 24 conversations of 8 turns each, over 4 replicas, with a short shared preamble so the conversation history is the interesting part.

    $ cd anchor/vendor-eval-gateway
$ uv run python bench/routing.py --replicas 4 --shared 64 --per-turn 128 --turns 8
    24 conversations x 8 turns over 4 replicas · shared preamble 64 tokens

strategy              hit rate  TTFW p50  TTFW p99            per replica
round-robin             49.0%      172m      396m   [48, 48, 48, 48]  48-48
least-outstanding       46.6%      172m      396m   [58, 51, 44, 39]  39-58
hash-whole              46.8%      172m      396m   [45, 43, 53, 51]  43-53
hash-prefix             77.6%      127m      172m   [55, 53, 49, 35]  35-55
prefix-match            79.6%      127m      215m     [192, 0, 0, 0]  0-192
prefix-match-cap        65.8%      127m      396m   [49, 50, 46, 47]  46-50
    Read the table in this order

    The top three rows are the same router. Round-robin, least-outstanding and hashing the whole prompt all land within three points of each other — about 47 % hit rate and a 396 ms p99 — because all three are equally blind to what a replica holds. Consistent hashing is not the fix; hashing the right span is.

    Then the fourth row. Hashing 256 tokens of prefix, which for this workload reaches into the conversation history, gives 77.6 % and cuts p99 by 2.3×. Load went from perfectly even to 35–55, and that is the price.

    Run it more than once. The three hashing rows are deterministic and will reproduce exactly; the load-dependent rows — round-robin, least-outstanding and the capped router — move by a few points between runs, because they depend on the order the event loop happens to dispatch in. Anything you claim from this table should survive that wobble, which is why the claim is “47 to 78” and not “49.0 to 77.6”.

  2. Now look at the two rows you were expecting to be the answer, because they are the interesting failures. Start with prefix-match: it asks each replica which leading blocks it already holds and routes to the longest match, breaking ties on load.

    prefix-match            79.6%      127m      215m     [192, 0, 0, 0]  0-192
    The best hit rate in the table, and it is unusable

    All 192 requests on one replica, and three sitting idle. This is the algorithm real cache-aware balancers use, and it collapsed — because once replica 0 has served one request it holds the shared preamble, so it has the longest match for every conversation forever. The load tiebreak never fires, since the match lengths are never equal.

    Note that its hit rate is the highest of all six, at 79.6 %. A hit-rate dashboard would have called this the winner. The p99 is worse than hash-prefix anyway, and at any real scale it is a single-replica service with three expensive spares.

  3. So bolt a load ceiling onto it: consider only replicas within --slack in-flight requests of the least loaded, then take the longest match among those.

    $ uv run python bench/routing.py --replicas 4 --shared 64 --per-turn 128 --turns 8 --slack 1
    prefix-match-cap        65.8%      127m      396m   [49, 50, 46, 47]  46-50
    Balanced, better than round-robin, and still beaten

    The cap works as designed — load is back to 46–50 — and hit rate lands at 65.8 %: clearly above round-robin's 47, clearly below hashing's 78. Every time the cap fires it sends a request away from the replica holding its prefix, and that request then pollutes a second replica with a copy of the same blocks.

    Which is worth sitting with, because it is the general shape of hybrid policies: a preference that can be overridden produces a cache that is half-populated everywhere. Hashing is worse at balance and better at caching precisely because it is not allowed to change its mind.

  4. Find the regime where none of this matters. Put the shared preamble back to a realistic 512 tokens and shorten the per-turn history, so most of the cacheable prompt is global rather than per-conversation.

    $ uv run python bench/routing.py --replicas 4 --shared 512 --per-turn 64 --turns 6
    strategy              hit rate  TTFW p50  TTFW p99            per replica
round-robin             76.3%      127m      284m   [36, 36, 36, 36]  36-36
least-outstanding       77.6%      126m      284m   [41, 38, 35, 30]  30-41
hash-whole              77.1%      127m      284m   [31, 31, 44, 38]  31-44
hash-prefix             90.5%      105m      185m     [0, 0, 144, 0]  0-144
prefix-match            90.5%      105m      185m     [144, 0, 0, 0]  0-144
prefix-match-cap        86.2%      104m      284m   [39, 38, 35, 32]  32-39
    The regime flipped, and so did which router is a trap

    Round-robin now gets 76.3 % on its own, because a 512-token preamble shared by everyone is cached on every replica after one request each. And hash-prefix — the winner in step 1 — now puts everything on one replica, because 256 tokens of window no longer reaches past the preamble, so the hash is a constant again.

    Same code, same flag, opposite outcome. The correct hash window is a property of your prompts, not of your infrastructure — and it changes when someone edits the system prompt's length, silently, with no deploy to the balancer at all.

  5. Measure the cache cliff. Affinity means a replica's death takes its conversations' prefixes with it — so raise the replica count and watch what share of traffic one failure would strand.

    $ uv run python bench/routing.py --replicas 8 --shared 64 --per-turn 128 --turns 8 | grep -E 'strategy|hash-prefix|round-robin'
    strategy              hit rate  TTFW p50  TTFW p99            per replica
round-robin             32.0%      217m      441m [24, 24, 24, 24, 24, 24, 24, 24]  24-24
hash-prefix             77.0%      127m      172m [29, 45, 29, 25, 26, 8, 20, 10]   8-45
    Two things move, in opposite directions

    Round-robin gets worse as you add replicas — about 47 % at four, 32 % at eight — because a conversation's chance of returning to the replica holding its history is roughly one in N. Hashing is flat at 77 %, because affinity does not care how many replicas there are. So the cost of cache-blind routing grows with your replica count, which makes this argument stronger at scale rather than weaker.

    But look at the load column, because it is the part I did not expect: hashing's spread went from 35–55 at four replicas to 8–45 at eight. Fewer conversations per bucket means more variance, so affinity's imbalance also gets worse with scale — one replica served 45 requests while another served 8. Both sides of the trade grow together, which is exactly why the answer is a policy and not a preference.

    And the cliff is the third cost: one replica of eight dying strands an eighth of conversations, each paying full prefill on its next turn, simultaneously. That is a stampede, and lesson 0005 already told you what to do about it.

  6. Last, prove the top three rows really are one router. Set the think time to zero so every conversation advances in lockstep, and re-run.

    $ uv run python bench/routing.py --replicas 4 --shared 64 --per-turn 128 --turns 8 --think-ms 0 | head -6
    round-robin             79.4%      127m      149m   [48, 48, 48, 48]  48-48
least-outstanding       73.6%      127m      440m   [48, 48, 48, 48]  48-48
hash-whole              46.8%      172m      418m   [45, 43, 53, 51]  43-53
    Round-robin at 79 %, which is a broken benchmark and not a finding

    With zero think time, all 24 conversations take their turns in the same fixed rotation — and 24 divides by 4, so conversation c returns to the same replica every single round. Round-robin became perfect affinity by arithmetic accident, jumping from 47 % to 79.

    The control is the third row. hash-whole did not move: it was 46.8 % with jitter and 46.8 % without, because a hash over text that changes every request scatters regardless of arrival pattern. When one row of a benchmark moves 30 points and another does not move at all, the workload is what changed — not the thing you were measuring.

    This happened while writing the lesson, and for an hour it said routing made no difference. Keep it as the check it is: if a load-balancing experiment shows no effect, suspect the arrival pattern before you believe the result. A synchronised workload is not a workload; real conversations are staggered and think for different lengths of time, which is why the default is 300 ms of jitter.

Underneath

One layer down · why the two obvious fixes fail in opposite directions

Four things. The first explains why round-robin was ever right, and the last is the one that decides whether you should do any of this.

Round-robin is not stupid; its assumption expired

Even distribution is the optimal policy when replicas are interchangeable and work is homogeneous. Both held for a stateless web tier, and both fail here: a replica holding a conversation's blocks is strictly better at that conversation's next turn than any other replica, and the cost of a request now depends on where it lands. The balancer is still solving its problem correctly — equalising counts — and the problem is no longer the one you have.

Which shows up as a hit rate that decays with the size of your fleet:

replicas 4 8 round-robin ~47% 32% P(land on the right replica) ≈ 1/N hash-prefix 78% 77% affinity is independent of N

That is the argument for cache-aware routing in one line, and note which direction it points: the case gets stronger as you scale, so “we are too small to worry about it” is a claim with an expiry date you can compute.

“Hash the prefix” is three different policies, and two are broken

Every prompt has three spans: what all conversations share, what one conversation shares with itself, and what is unique to this request. A hash window is a choice of where to stop, and the failure modes bracket the answer.

Same 256-token window, two prompt shapes, opposite results:

preamble 64 tokens window reaches history → 78% hit, load 35-55 preamble 512 tokens window stops in preamble → 90% hit, load 0-144

The second row is the trap, and it is worth reading twice: the collapsed configuration has the better hit rate. Of course it does — one replica serving everything sees every prefix. Hit rate cannot distinguish affinity from centralisation, so it must never be the only number on the dashboard.

The other direction is quieter. Hashing the whole prompt is a hash over text containing this turn, so it produces a fresh value every request — measured at 46.8 %, statistically indistinguishable from round-robin. It looks like consistent hashing, it is described as consistent hashing in the config, and it is round-robin. The lesson is that consistent hashing is not the mechanism; hashing something that is constant across the requests you want colocated is the mechanism.

Longest-prefix match is what production does, and it needs a governor

Real cache-aware balancers do not hash. They keep, per replica, the set of block hashes they have sent it — the same chained hashes from lesson 0008 — and route to whichever replica holds the longest matching prefix. It is strictly more informed than hashing: it needs no window, and it adapts when prompts change shape.

And on this workload it put every one of 192 requests on one replica. Not because of a bug: once a replica has served one request it holds the globally shared preamble, so it has the longest match for every conversation, forever, and the load tiebreak never fires because the match lengths are never equal. Unbounded, “route to the best cache” is a rule with a fixed point, and the fixed point is one server.

Capping it fixes the load and costs cache:

longest match, no cap hit 79.6% load 0-192 p99 215 ms longest match, cap 1 hit 65.8% load 46-50 p99 396 ms hash on history hit 77.6% load 35-55 p99 172 ms

The capped router is beaten by plain hashing on both hit rate and tail, which is not intuitive until you see why: every time the cap diverts a request, that request installs a duplicate copy of its blocks on a second replica. A preference that can be overridden yields a cache that is half-populated everywhere rather than fully populated somewhere. Hashing wins by being unable to change its mind.

Affinity's three costs, and the one that decides it

Balance, which gets worse with scale: 35–55 at four replicas, 8–45 at eight, because fewer conversations per bucket means more variance. Elasticity: adding a replica remaps a share of keys, and every remapped conversation pays full prefill on its next turn — so autoscaling now has a latency cost, which is an argument for consistent hashing over modulo, since modulo remaps nearly everything. And the cliff: a replica's death strands its conversations' prefixes simultaneously, and they all miss at once, which is a stampede with the shape lesson 0005 described and the same fix.

Against which the deciding question is not about balancers at all. It is: how much of your cacheable prefix is per-conversation rather than global? With a 512-token shared preamble and short turns, round-robin already reached 76 % unaided, because every replica caches the global span after one request each — and the whole apparatus buys ten points at the cost of the cliff. With a short preamble and a long conversation, it is 47 against 78 and the answer is obvious. Same code, same flag, and the regime is set by how somebody writes prompts.

Cache-aware routing is a property of your prompts, not of your infrastructure. Measure the split between globally shared and per-conversation prefix first; if the global span dominates, round-robin is already close to optimal and adopting affinity is a cost with no return. And when it does pay, remember that the highest hit rate in the table belonged to a router that had quietly become a single-node service.

Check yourself

You add a second replica behind round-robin. What happens to prefix-cache hit rate for one ongoing conversation?

  1. It falls, because successive turns go to other replicas
  2. It holds, because each replica caches the same blocks
  3. It doubles, because there is twice the cache available
  4. It rises, because each replica serves a smaller keyspace

It falls, and it keeps falling as you add more: the chance of a turn landing on the replica holding that conversation's history is roughly one in N. Measured at about 47 % across four replicas and 32 % across eight, against a flat 77 % under affinity.

The “same blocks” answer is right about one span and wrong about the one that matters. The globally shared preamble is cached everywhere after one request each, which is why round-robin scores 47 % rather than nothing — but the conversation's own history exists on exactly one replica, and in a long interview that is most of the prompt.

You route by hashing the entire prompt, including this turn's text. What do you get?

  1. Scatter, because the hash changes with every single request
  2. Affinity, because the shared preamble dominates the hash input
  3. Overload, because one replica receives the whole hot keyspace
  4. Nothing, because the block hashes already decide cache location

Scatter. This turn's text differs every request, so the hash does too — measured at 46.8 %, indistinguishable from round-robin's 47, and stable at 46.8 % even when a lockstep workload pushed round-robin up to 79. It is round-robin wearing the word “consistent hashing”.

The overload answer is the other failure and it is real, just not this one: it happens when the window is too short and stops inside the globally shared preamble, making the hash a constant. That put 144 of 144 requests on one replica. The two mistakes bracket the correct window, which is why naming the span you hash matters more than naming the algorithm.

Say it out loud · about 75 seconds

A spoken answer to “the sessions are stateful — what is your load balancer doing about that?” Your own prep notes list this as one of the things that breaks before the GPUs do. Read it aloud, then say it again with the page covered.

  1. Situation

    Every turn of an interview carries the conversation so far, so the cacheable part of the prompt grows as it goes — and it exists in exactly one replica's memory. Nothing is shared between them.

  2. Mechanism

    Round-robin equalises request counts, which is the right goal when servers are interchangeable. They stopped being interchangeable when they started holding state, so the balancer is optimising a quantity that no longer describes the cost.

    The chance a turn lands where its prefix already lives is about one over the replica count. So the loss gets worse as you scale out, not better.

  3. What I did

    I compared five routers on one workload. Round-robin, least-outstanding and hashing the whole prompt all scored about 47 percent hit rate, because all three are cache-blind. Hashing a window that reaches into the conversation history got 78 percent, and cut p99 first word from 396 milliseconds to 172.

    And I rejected the one with the best hit rate. Longest-prefix match scored 79.6 and put all 192 requests on one replica. After the first request that replica holds the shared preamble, so it wins every match forever and the load tiebreak never fires.

  4. What it cost

    Balance, and it degrades with scale. Even at four replicas the spread went from 48-48 to 35-55, and at eight from 8 up to 45 requests. Plus a cache cliff: when a replica dies, its conversations all miss at once on the next turn. That is a stampede, and it needs the coalescing fix.

    And the honest caveat is that whether it is worth it depends on the prompt, not the platform. With a long shared preamble and short turns, round-robin already reached 76 percent on its own, and affinity buys ten points for all of that risk. I would measure the split before adopting it.

The sentence that sounds fluent and gets you caught

“We use consistent hashing so requests stick to the right replica.” Consistent hashing is a property of the function, not of the key, and the key is the entire decision. Hash a window that stops inside the shared system prompt and you have a constant, so one replica takes everything. Hash the whole prompt and you have a fresh value per request, so you have written round-robin. Both are consistent hashing. The follow-up is “what are you hashing?”, and the version that holds names the span: “the leading tokens up to the end of the conversation history, so it is constant per conversation and different between them.”

The second trap is quoting a hit rate as though it settled the question. The best hit rate I measured belonged to the router that had become a single-node service with three idle spares. “We got hit rate up to 80 %” invites “and what happened to your load distribution?” — so say both numbers, in the same sentence, before you are asked.

Note that everything it describes is per-engine: the block table, the hash chain and the eviction all live inside one server, and nothing in it coordinates between replicas. That absence is what makes routing an external problem rather than a serving one, and reading the design with that question in mind is more useful than any balancer's documentation.

For the balancing half: Mitzenmacher, “The Power of Two Choices in Randomized Load Balancing” — why sampling two replicas and taking the less loaded is nearly as good as global knowledge, which is the standard way to add a load governor to a preference like affinity without needing a central view. And Envoy's load balancer reference for what ring-hash and maglev actually guarantee when a replica leaves.

Recall — from lessons 0006–0008

A replica under affinity dies, and its share of conversations all miss on their next turn. Name the failure and give the fix in one sentence each.

It is a stampede: many concurrent requests for values that are absent, arriving inside one miss window whose width is the full prefill time. The fix has the same two parts as lesson 0005 — coalesce so that concurrent requests for the same prefix produce one prefill rather than hundreds, and stagger what can be staggered so the misses do not align. What you cannot do here is the thing that worked for Redis keys, namely serve stale, because there is no stale KV to serve; so the remaining lever is headroom to absorb the prefill burst.

lesson 0005 · stampede and single-flight
Prefix affinity raised hit rate and made load spread worse. Which of those two would you alert on, and why is the answer not “both, equally”?

Load spread, because it is the one that catches both failure modes and hit rate catches neither. A hash window that is too short collapses onto one replica and hit rate goes up while the service becomes single-node; a window that is too long scatters and hit rate falls quietly. Spread moves in an unmistakable direction in the first case and stays flat in the second, which combined with hit rate distinguishes the two. This is the same trap as reporting a median: one number that improves for two opposite reasons is not a signal.

lesson 0002 · one number hiding two behaviours
Both this lesson's win and lesson 0008's depend on the shared prefix being byte-identical. What is the deployment event that breaks both at once, and what does it look like on a dashboard?

A prompt change. Editing the shared preamble invalidates every block after the edit — the hashes are chained — so every replica goes cold simultaneously, and if the edit changes the preamble's length it can also move the correct hash window and silently break routing. On a dashboard it is a first-word spike lasting about one request per replica, which has healed before anyone looks, plus a step change in load spread that nobody is watching. A prompt change is a deploy and needs the same treatment.
