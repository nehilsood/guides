SSE vs WebSocket for Tokens

Your gateway already streams. This lesson opens the wire and reads it, prices what streaming actually costs, and then breaks it on purpose — not the way the internet says it breaks, but the way it broke when measured.

The win

Read your own tokens as bytes, put a real reverse proxy in front of them, and find the one line in app/gateway.py that is the difference between a 390 ms first word and a 3.8 second one.

Why you, specifically
“Built a custom OpenAI-compatible LLM gateway powering those interviews at ~2.1 s median time-to-first-word under a hard 8 s per-turn budget.”

That sentence only means anything because the gateway streams. Time-to-first-word is not a metric a non-streaming endpoint has — without stream=true, first word and last word are the same instant, and your 2.1 s claim collapses into whatever the full completion takes. Streaming is the reason your best number exists.

That sentence is defended in full in chapter 0002 of Résumé Mastery — this lesson is where the mechanism underneath it gets built and broken.

Start here — the plain version

When a model answers, it does not finish and then hand you a paragraph. It produces one token at a time, for seconds. Streaming means forwarding each token to the client as it appears instead of collecting them all and sending one response at the end. Nothing about the total time changes — the generation still takes as long as it takes. What changes is when the human sees the first word.

There are two mainstream ways to push a sequence of things down an already-open HTTP connection, and this lesson is about why the boring one is the right one for tokens, what it costs in bytes, and what it cannot do.

Streaming
Sending a response in pieces as they become available, over one connection that stays open. The opposite is unary or buffered: one request, one whole response.
SSE — Server-Sent Events
A tiny text format for streaming over ordinary HTTP. The server sets Content-Type: text/event-stream and then writes frames until it is done. One direction only: server to client.
Frame
One SSE message. In practice one line beginning data:, then a blank line. The blank line is the delimiter, not decoration — omit it and the client waits forever for a message that has already arrived.
WebSocket
A different protocol that starts as an HTTP request and then upgrades the connection into a two-way byte channel. Both sides can send at any time.
TTFW — time-to-first-word
How long from sending the request until the first token reaches the client. The metric on your résumé. Only streaming has one.
Reverse proxy
A server that sits in front of yours and forwards requests to it — nginx, an ingress controller, a load balancer terminating TLS. Your traffic goes through at least one, usually without you choosing it.

Streaming is a latency trade, and it has a price

The generation takes as long either way. What streaming changes is when bytes leave, and it pays for that with a great many more of them. Both of these are measured figures from the lab below, on one completion of 1 251 characters:

One completion, delivered two ways. Same model, same text, same 3.8 s of generation.
stream=falsestream=true
Time to first word3 774 ms390 ms
Time to last word3 774 ms3 785 ms
Pieces on the wire1 response182 frames
Bytes on the wire1 46137 655

So: 9.7× better first word, at 25.8× the bytes. That is the whole deal, and it is the honest answer to “why do you stream?” — not “because it is faster”, which it is not. The total is very slightly worse, by the cost of writing 182 small pieces instead of one large one.

The 182nd frame is not a token

Worth knowing before you count anything: a 180-token completion produces 182 frames. One hundred and eighty carry text, then one carries an empty delta with finish_reason: "stop", and the last is the literal sentinel data: [DONE] — fourteen bytes, not JSON at all, and not part of any specification. It is an OpenAI convention that the whole ecosystem now depends on, which is why your gateway emits it.

Lab — read the frames, then delete one line

Lab 0007 ~25 minutes

390 ms, and how to lose it

  1. Start the gateway with a deterministic upstream. This is not a detail you can skip — see the expectation below it.

    Why sigma zero, and not the default

    The fake upstream's TTFW is lognormal with sigma=0.45, which on this machine produced a spread of 143 to 854 ms across five runs of an identical request. The effect this lab is hunting is a couple of hundred milliseconds. Measuring it against that noise band is how you conclude the opposite of the truth — which happened here, twice, before the sigma came out.

  2. Read the raw bytes of the first frame. Not the parsed events — the bytes.

    You should see

    The frame ends 0a0a — two newlines, the delimiter. Everything before it is one JSON envelope, 224 bytes, wrapped around the four characters the . Note the first frame is the only one carrying “role”:“assistant”; the rest send content alone and are 204 bytes.

  3. Price the trade. Run the same request streaming and not, and record first-word, last-word and bytes for each.

  4. Now put a real reverse proxy in front of it, configured the way a default install is, and re-measure. Port 8080 is stock nginx with proxy_buffering at its default, which is on.

    This is the step that was supposed to break, and does not

  5. Try harder to break it with buffering. Port 8082 buffers into 128 KB buffers — larger than the entire 37 KB response, so there is room to hold all of it. Port 8083 drops the upstream connection to HTTP/1.0, which is nginx's own default and cannot use chunked encoding.

    Still nothing

  6. Turn on compression. Port 8084 is the same proxy with gzip on — which is not perverse, it is the obvious fix for the 25.8× you measured in step 3.

    A real win, and it is large

    Still 393 ms to first word, and the wire cost falls from 37 655 to 2 588 bytes — 14.6× less traffic, which very nearly cancels the cost of streaming. The reason it compresses so well is exactly the reason it was so big: 182 near-identical envelopes are close to the best case a dictionary compressor will ever see.

  7. Delete one line from your own gateway. In app/gateway.py, remove “X-Accel-Buffering”: “no” from the StreamingResponse headers, restart, and re-run everything.

    app/gateway.py — the line to delete 
            return StreamingResponse(
            _stream_chunks(upstream, prompt, completion_id, req.model),
            media_type="text/event-stream",
            headers={
                "Cache-Control": "no-cache",
                # delete the next line, restart, and measure again
                "X-Accel-Buffering": "no",
            },
        )
    direct    :8000        390 (389-416)     3792 (3788-3821)     182    37655     -
stock 4k  :8080        395 (394-397)     3793 (3790-3799)     182    37655     -

    The failure

    Compression is what breaks streaming, not buffering. Only the gzip lane moved, and it moved by 9.7× — back to exactly the number stream=false gave you in step 3. You have a streaming endpoint that no longer streams.

The decision this leaves you with

The header is a defence you did not choose, against a filter you did not know was there, in a proxy you may not own. It is one line and it is worth keeping. But it is not a design, and if the proxy in front of you is someone else's ingress controller then the durable version of this fix is proxy_buffering off on their side of the boundary, agreed with them, in code you can both see.

Underneath

One layer down · why compression breaks a stream and buffering does not

A frame is a text line and a blank line, and that is the entire protocol

SSE has no framing layer. There is no length prefix, no opcode, no mask, no header per message — the delimiter is \n\n and the field is data:. That is why it needs chunked transfer encoding underneath: HTTP has to be able to send a body of unknown length, and the chunk sizes do the work that SSE declines to do.

Which makes the envelope, not the protocol, the reason streaming is expensive:

completion text 1 251 chars frames 182 (180 tokens + stop + [DONE]) wire bytes 37 655 → bytes per character 30.1

Thirty bytes of JSON per character of answer. Almost none of that is SSE — data: plus \n\n is eight bytes of the 224. The rest is the completion id, the created timestamp, the model name, the object type, the choice index and the finish reason, re-sent around every token because the chunk schema was designed to look like the non-streaming response rather than like a stream.

In plain words

A proxy is the server that sits in front of yours, and its buffer is a holding area for the part of your reply the client has not picked up yet. It passes tokens on as they arrive and does not wait for the end, so here it cost about 3 ms. It only adds delay when the client reads too slowly to empty it.

Buffering is a read-ahead, not a wait

The reason the buffering lanes did not move is that proxy_buffering on does not mean “accumulate the response and forward it at the end”. It means nginx is allowed to read from the upstream as fast as the upstream will produce, storing what the client has not yet taken. The buffers exist to decouple a fast backend from a slow client — which is a real and valuable thing, because it lets your worker finish and move on rather than being held open at the speed of somebody's phone.

The measurement, five runs each, sigma zero, header present:

direct 390 ms stock 4 KB buffers 393 ms (+3) 128 KB buffers 392 ms (+2) HTTP/1.0 upstream 392 ms (+2) → buffering costs about 3 ms, which is the proxy hop

Buffering only becomes a delay when the buffers cannot be handed onward — a client too slow to drain them, at which point nginx spills to a temp file on disk and you get a genuinely different failure. That is a back-pressure problem, and it is not what happens to a laptop on a loopback interface.

In plain words

Compression shrinks text by spotting repeats, so it likes to see more text before it sends anything. Our frames are nearly identical, so gzip at the proxy kept holding them, and every token arrived at once at 3 796 ms instead of the first one at 393 ms. The fix is one header the gateway sends, X-Accel-Buffering: no, which switches off the nginx machinery that holds the bytes back.

Compression cannot flush what it has not finished looking at

Deflate is a sliding-window compressor: to emit a byte it wants to know whether the bytes after it repeat something already seen. Given a 220-byte frame that is 97 % identical to the previous one, the useful thing to do is wait for more input. So a compressor asked to stream must be told, explicitly and per message, to stop optimising and emit what it has — a sync flush. Skip that and it does exactly what it should: it holds your tokens as raw material.

What the header actually changed, gzip lane only:

header present 393 ms 182 frames arriving 19 ms apart 2 588 B header deleted 3796 ms 182 frames arriving together 940 B → ratio 9.7×, and the compression got better

Note the direction of the byte column. Withholding the flush is what makes compression work well — 940 bytes against 2 588 — so the broken configuration is the efficient one. Streaming and compression are in genuine tension, and X-Accel-Buffering: no resolves it by disabling nginx's output-postponing chain, which the gzip filter sits inside. The header is not a compression setting; it just happens to switch off the machinery compression uses to hold bytes back.

In plain words

Pick the transport by asking what the client might need to say while the answer is still arriving. On a one-way stream it cannot speak, so anything it wants to change has to go out as a separate request. That only matters when the client has something to say mid-answer, such as a user pressing a button to cut the answer short.

What WebSocket buys is a direction, not a speed

Nothing in the lab is a reason to reach for WebSocket. It would not have been faster, it would not have compressed better, and it would have been broken by exactly the same proxies. Its one structural advantage is that the client can send while the server is still sending — and for a token stream there is precisely one message worth sending on that channel: stop.

That matters more than it sounds. When an SSE client disconnects, generation upstream does not stop because it was asked to; it stops when something notices the write failed, if anything does. Every token after that point is billed and discarded. With SSE, cancellation is a second HTTP request against a completion id you had to invent and track; with WebSocket it is one frame on the connection already in your hand. If your product has a barge-in button, that is the argument — and it is an argument about control, not about throughput.

Streaming is a property of the path, and compression is its natural enemy. Your endpoint can be perfect and your client can still see one lump at the end, because a filter three hops away is doing its job well. The two ratios worth carrying out of here are 9.7× — what streaming buys, and what losing it costs, the same number twice — and 25.8×, the bytes it costs before compression and 1.8× after.

Check yourself

Your streaming endpoint works on your laptop and delivers every token at once in staging. Which proxy setting is the likeliest cause?

  1. Response compression, which buffers to build a compressed stream
  2. Response buffering, which holds output until a buffer fills
  3. Protocol downgrade, which prevents the use of chunked encoding
  4. Read timeout, which truncates output before the last token

Compression. A deflate stream wants more input before it emits anything, so unless it is given an explicit per-message flush it holds your frames as raw material — measured here at 3 796 ms to first word against 393, with the response getting smaller as it got slower.

Buffering is the tempting answer and it is the one the internet gives, which is why this lesson measures it: stock 4 KB buffers cost 3 ms, and buffers larger than the whole response cost 2 ms. proxy_buffering is a read-ahead so a fast backend need not wait for a slow client, not an instruction to accumulate and forward at the end.

Streaming the same completion cost 25.8× the bytes of one non-streaming response. Where did the extra bytes go?

  1. Into one JSON envelope repeated around every single token
  2. Into the extra headers each separate frame must carry
  3. Into the blank lines that terminate each event frame
  4. Into a longer completion produced by the streaming path

The envelope. Every one of the 182 frames re-sends the completion id, created timestamp, model name, object type, choice index and finish reason around roughly seven characters of text — 224 bytes to carry four characters in the first frame, and 30 bytes per character across the whole completion.

The blank-line answer is the right instinct aimed at the wrong scale: the delimiter plus the data: prefix is eight bytes of 224, about 3 %. SSE itself is close to free. The expensive decision was wrapping a stream in a schema shaped like a request-response body, and it is why the whole thing compresses 14.6×.

Say it out loud · about 75 seconds

A spoken answer to “you say 2.1 seconds to first word — how does that actually work, and what did it cost you?” This is the question your best résumé number invites, so it is the one to have cold. Read it aloud, then say it again with the page covered.

  1. Situation

    The gateway is OpenAI-compatible and it streams, which is the only reason time-to-first-word is a number we have at all. Without streaming, first word and last word are the same instant and the metric does not exist.

  2. Mechanism

    It is server-sent events over one ordinary HTTP connection. The server writes a line starting data: and then a blank line, per token, and the blank line is the delimiter — that is the whole protocol. Chunked transfer encoding underneath is what lets HTTP carry a body whose length nobody knows yet.

    Which means it is one-way. The client cannot say anything back on that connection, and that turns out to be the only real reason anyone picks WebSocket instead.

  3. What I did

    I measured both ways on one completion. First word at 390 milliseconds streaming, against 3.8 seconds unbuffered — call it nine and a half times better. Then I put a stock nginx in front and tried to break it.

    And the thing everyone blames did not break it. Response buffering cost three milliseconds. Buffers bigger than the whole response cost two. What broke it was gzip: first word went to 3.8 seconds, all 182 frames arriving in one flush, and the fix was one header our gateway already sets.

  4. What it cost

    Streaming is not free. The same answer costs twenty-six times the bytes, because each frame re-sends the whole JSON envelope around about seven characters — roughly thirty bytes per character of output. Compression brings that back to under twice, which is why we want gzip on and why the collision matters.

    And the honest limitation is cancellation. When a client hangs up mid-stream we keep generating and keep paying, because SSE gives us no channel to be told to stop. That is the argument for WebSocket, and it is about control rather than speed.

The sentence that sounds fluent and gets you caught

“We stream over SSE, so the client sees tokens as they are generated.” The first clause is a fact about your code and the second is a claim about a network path you do not control. Between your StreamingResponse and a browser there is at least one proxy, and a single compression filter turns that sentence into a 3.8-second lie that returns 200 and passes every test you wrote. The follow-up that finds it is “how do you know?”, and the only answer that holds is a first-word percentile measured at the client.

The other trap is the confident version of the folklore: “you have to turn off proxy buffering or streaming breaks.” Widely repeated, and it cost three milliseconds when measured. Saying it invites “have you seen that happen?”, and the version that holds is: “buffering is a read-ahead and it was fine — what actually broke it was compression, and I have the table.”

Probes to expect

  1. “Your users say the response hangs and then dumps everything at once. Where do you look?” They want a path, not a guess. Walk the hops from the model to the browser and name what each one can do to a stream. Getting to compression rather than stopping at buffering is the whole signal here, and saying you measured it is what makes it credible.
    Model answer — say yours first

    First I would confirm which one it is, because “hangs then dumps” and “slow first token” have different causes. If the frames all arrive together, generation was fine and something in the path accumulated them — so I walk the hops: our own handler, then any proxy, then the client library. On our side I check that the frames leave when they are produced, which I can do with curl -N against the pod directly.

    Then the proxy, and I would go to compression before buffering. I have measured this: stock nginx buffering cost three milliseconds, and turning on gzip took first word from 393 ms to 3 796 — all 182 frames in one flush, status 200, nothing else wrong. The last hop to rule out is the client, since curl without -N reproduces the same symptom entirely locally.

    Invites · “So how would you catch it next time?” — a time-to-first-word percentile measured at the client, not in the handler, because every server-side signal in that failure was healthy.
  2. “Why SSE and not WebSocket?” A protocol tour scores nothing. The answer is that SSE is sufficient because the data flows one way, and the interesting half is naming the case where that stops being true. Do not claim a performance reason; there is not one.
    Model answer — say yours first

    Because the traffic is one-directional and SSE is ordinary HTTP. It goes through our existing gateway, ingress, auth and observability with no special handling, and reconnection with Last-Event-ID is in the protocol rather than in my code. WebSocket would be a second transport to operate for no gain — it is not faster, it does not compress better, and it is broken by the same proxies.

    Where that flips is cancellation. Right now if a client hangs up mid-generation we keep producing tokens and keep paying for them, because there is no channel for the client to say stop — it has to be a second HTTP request against the completion id. If we shipped barge-in, where a user interrupts the avatar mid-sentence, I would want that channel and I would move.

    Invites · “What happens today when the client disconnects?” — honestly, we generate to completion unless something notices the write failed, so we pay for tokens nobody read.
  3. “You quote 2.1 seconds median time-to-first-word. How is that measured?” The trap from lesson 0002, wearing a streaming costume. Where the clock starts and stops decides the number, and measuring inside the handler flatters you by exactly the amount of the failure in this lesson. Name the instrument, then name what it cannot see.
    Model answer — say yours first

    Wall clock from the request leaving the client to the first frame arriving at it, and it has to be at the client, because everything downstream of our handler is invisible from inside it. The gateway logs its own first-frame time as gateway.ttfw, which is useful for splitting our latency from the model's, but it is not the user's number — in the compression failure I measured, the handler's figure stayed at 390 ms while the client saw 3 796.

    I would also be careful about what counts as the first frame. My first measurement of the gzip path read 14 milliseconds, which was the compression header arriving, not a token. The instrument has to look at the first decoded data: line or it reports a number better than reality.

    Invites · “And the p95 and p99?” — the question median always invites, which is lesson 0002, and the answer needs an open-loop generator or it is flattering me.
  4. “Twenty-six times the bytes sounds bad. Would you stop streaming?” A test of whether you can price a tradeoff rather than recite it. The answer is no, and the reason is that the cheap fix already exists and you measured it — but you should say when the answer would be yes.
    Model answer — say yours first

    No, because compression takes it back. The uncompressed cost was 37 655 bytes against 1 461 for one response, but gzip brought that to 2 588 — under twice the non-streaming size, for a first word nine and a half times sooner. That is not a close decision, and it stays open because the same header that keeps streaming alive is what lets both wins coexist.

    Where I would reconsider is a client paying per byte on a metered connection, or an internal service-to-service hop where no human is waiting. Streaming to something that only acts on the finished text buys nothing and costs the envelope, so those calls should be stream=false — and some of ours probably still are not.

    Invites · “Which of your callers are machines?” — a question about whether streaming became a default rather than a decision, and the answer is that it did.
  5. “A million concurrent sessions. What does the connection model do to you?” Straight out of your own prep notes. The move is to convert sessions into concurrent generations before saying anything about infrastructure, then name what a long-lived connection costs the layer in front. Do not answer with replicas.
    Model answer — say yours first

    First I would separate concurrent sessions from concurrent generations, because they differ by a lot. If a turn takes eight seconds and a person speaks every thirty, in-flight generations are about eight thirtieths of a million — call it 267 000. That is the number that sizes anything, and it is the one people skip.

    Then the connection model bites before the model servers do. Each in-flight turn holds an open connection for the whole generation, so the gateway is holding hundreds of thousands of sockets and the proxy in front is doing the same — and because the session is stateful, the load balancer's placement decision is not free either, which is the routing problem in the next lesson. The honest answer is that I have measured the single-node path carefully and have not measured this, and the first thing I would look at is file descriptors and proxy connection limits rather than GPUs.

    Invites · “And what decides which replica a session lands on?” — prefix-cache affinity, which is lesson 0009, and round-robin actively throws the win away.
