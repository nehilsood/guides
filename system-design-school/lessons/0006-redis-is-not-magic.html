Redis Is Not Magic

You have spent four lessons treating Redis as a fast box that remembers things. It is a single-threaded event loop with two different durability mechanisms and a fork-based snapshot that can stall your p99. This lesson makes you lose data on purpose, then configure it not to.

The win

You will kill Redis mid-write and lose data, measure exactly how much each durability setting costs you, and understand why “Redis is fast” and “Redis occasionally pauses for a second” are both true statements about the same process.

Why you, specifically
“Owned an AI vendor-evaluation platform end-to-end (Python/FastAPI, async SQLAlchemy, PostgreSQL, GKE)…”

“End-to-end” is the claim being tested here. Adding a cache in lesson 0003 made Redis part of your platform, and owning a datastore means being able to answer what happens when it restarts, how much it can lose, and what it does to your tail latency while it saves. If Redis were on your résumé today, this is the question you would get.

That sentence is defended in full in chapter 0001 of Résumé Mastery — this lesson is where the mechanism underneath it gets built and broken.

Start here — the plain version

Redis keeps everything in memory, which is why it is fast, and memory disappears when a process dies. So the question this lesson answers is the one you have to be able to answer about any store you own: if this restarts right now, what have I lost?

Redis offers two ways to put data on disk so the answer is not “everything”. One takes a periodic photograph of the whole dataset (RDB). The other appends every write to a log and replays it on startup (AOF). Each has a cost, and both costs land on your latency rather than on a bill — which is why “how durable is it” and “how fast is it” are the same question here. The other thing worth knowing up front: Redis handles one command at a time, so a single slow command makes every other client wait.

In-memory
Data lives in RAM. Fast to read, and gone on restart unless something wrote it to disk.
Single-threaded
One command runs at a time. This is mostly why Redis is quick — no locking — and it means one expensive command blocks everyone, so your cache's worst latency is whatever the worst command anybody runs is.
Durability
How much you are willing to lose if the process dies this second. Answered in units of time, not in adjectives.
RDB
A snapshot: the whole dataset written to one compact file every so often. Cheap to load, and you lose everything written since the last one.
AOF
Append-only file: a log of every write command, replayed on startup to rebuild the data. Loses much less, and the log has to be written as you go.
fsync
Telling the operating system to actually put bytes on the physical disk now, rather than when it feels like it. The expensive part of durability is this, not the writing.
appendfsync
How often to do that: always (before replying — safest, slowest), everysec (once a second — the default, risks about a second), no (whenever the OS decides — fastest, risks tens of seconds).
fork and copy-on-write
How a snapshot avoids blocking: Redis clones itself, and the clone writes the file while the original keeps serving. The cloning itself is not free, and on a large dataset it can pause everything briefly — a self-inflicted spike in your slowest requests.

Single-threaded, and that is the point

Redis executes commands on one thread, one at a time. This sounds like a limitation and is mostly the reason it is fast:

  • No lock contention, no context switching between commands. The cost of coordinating multiple threads over a shared hash table exceeds the benefit for operations that take microseconds.
  • Every command is atomic for free. INCR cannot interleave with another INCR. This is why Redis is a plausible place to put a distributed lock — though lesson 0005's single-flight lock is only plausible, not safe, and lesson 0030 explains why.
  • Everything is in memory, so the work per command is genuinely tiny.

The corollary is the part that matters operationally: one slow command blocks everything. A KEYS * on a large keyspace, or a big set intersection, stalls every other client for its whole duration. Your cache's p99 becomes hostage to the worst command anyone runs against it.

Two durability mechanisms, three fsync policies

RDB — point-in-time snapshots

Redis fork()s, and the child writes the entire dataset to a compact binary file while the parent keeps serving. Copy-on-write means the parent does no disk I/O at all.

The costs are specific. You lose everything written since the last snapshot — typically minutes. And fork() on a large dataset takes real time: the Redis documentation is blunt that it “may result in Redis stopping serving clients for some milliseconds or even for one second if the dataset is very big and the CPU performance is not great.” On a service with an 8-second turn budget and a cache in the hot path, a one-second stall is a p99 event caused entirely by your durability configuration.

AOF — append-only log

Every write command is appended to a log and replayed on restart. Since Redis 7.0 this is a multi-part affair: a base snapshot plus incremental files, tracked by a manifest. Durability is governed by appendfsync:

From the Redis persistence documentation. The default is everysec, and it is the right default.
appendfsyncfsync happensWorst-case lossCost

What the docs actually recommend

Both, together. RDB alone if you can tolerate losing a few minutes in a disaster. AOF alone is discouraged — the docs want an RDB snapshot around anyway, for faster restarts and as insurance against bugs in the AOF engine. And note the compose file in this repo runs with --save "" and --appendonly no: no persistence at all, which is a defensible choice for a pure cache and a catastrophic one for anything else.

    Do not try to see this with redis-cli --latency

    The obvious move is to watch --latency across the bgsave, and it does not work. The decision this leaves you with

Underneath

One layer down · what fsync actually promises, and what forks cost

Above, durability is a setting. One layer down it is a syscall with a specific and surprisingly narrow contract, and a background save is a fork() whose cost is proportional to something other than the thing you would guess.

write() is not durability, and fsync() is not certainty

When Redis appends to the AOF, the write() returns as soon as the bytes are in the kernel page cache. At that moment the data has already survived one class of failure completely: kill -9 the Redis process, or let it segfault, and the bytes are still there, because they are no longer the process's problem. What it has not survived is losing the machine.

fsync() is the request to push those pages to the device. That is the whole of the guarantee — and it stops at the device. If the drive has a volatile write cache and does not honour a flush, fsync() can return before anything is on stable media, and neither Redis nor the kernel can tell. You are running these labs inside a Docker Desktop VM, which adds a virtualised block layer on top of that. So the honest statement is not “always means no data loss” but “always means Redis has done everything it can ask for.”

everysec is a window, not a delay

The name reads like a one-second lag. It is not: a background thread issues an fsync roughly once a second, so at any given instant the amount of un-fsynced data is somewhere between zero and one second's worth, depending where in the cycle you are.

Which is why this is one of the few things in this course you cannot reliably demonstrate. Writing a key and immediately kill -9-ing the container, with no sleep at all, the value survived — the fsync thread happened to have run inside the tens of milliseconds Docker took to deliver the signal.

write → kill immediately → key survived (this run) write → sleep 1.2 s → kill → key survived (always)

A single trial proves nothing about a probabilistic window, and reporting “I killed it and lost data” from one run would be exactly the kind of claim that falls apart when someone repeats it. Reason about the window; do not try to photograph it.

Where the 3.8× goes

The throughput numbers are almost uninteresting on their own. The latency is where the mechanism shows:

everysec p50 = 0.087 ms 306 748 rps always p50 = 0.623 ms 80 128 rps per-write fsync cost = 0.623 − 0.087 = 0.536 ms throughput ratio = 306 748 / 80 128 = 3.83×

That 0.536 ms is one device round trip, paid on the critical path of every single write, and it is why always is a decision about your workload's write rate rather than a general recommendation. At 80 000 writes a second it is still an enormous amount of Redis — the question is whether you need the last second.

Why a “background” save shows up in your latency

BGSAVE forks. The child inherits the parent's address space copy-on-write, so at the instant of the fork nothing is copied and the snapshot looks free. Then every page the parent writes to has to be duplicated before the write can proceed, so the extra memory a background save consumes is proportional to how much you write while it runs — not to the size of the dataset. On a write-heavy instance that can approach a second full copy of the keyspace, which is the real reason a Redis box needs headroom well beyond maxmemory.

And fork() itself is not free: the kernel has to copy the parent's page tables, so the stall scales with how much memory the process maps. On a large instance that is a measurable pause in a single-threaded server, which means your persistence configuration is a latency feature of your read path. It is the same trade as always, moved from throughput to tail latency.

One artefact worth knowing because it changes what you look for on disk: since Redis 7.0 the AOF is multi-part. There is no single appendonly.aof any more — the lab leaves behind an appendonlydir/ holding appendonly.aof.1.base.rdb, appendonly.aof.1.incr.aof and a manifest. A rewrite writes a new base and starts a fresh increment rather than rewriting one file in place.

Durability is a question about which of four boxes the data is in, and every knob here buys a boundary crossing at a stated price. everysec costs nothing measurable and leaves a window; always costs 0.54 ms per write and closes it; RDB costs a fork stall and copies pages in proportion to your write rate. None of them make the disk honest.

Check yourself

AOF is enabled with default settings and the machine loses power. How much do you lose?

  1. Roughly one second of writes, given the default fsync policy
  2. Nothing at all, because Redis fsyncs on every single write
  3. Everything since the last RDB snapshot was written to disk
  4. Only the writes which had not yet reached any replica

The default appendfsync is everysec, which flushes once per second on a background thread. A power loss can therefore cost up to about a second of writes. That is the documented, intended tradeoff — the docs describe it as “both fast and relatively safe”.

“Nothing at all” describes appendfsync always, which the docs call “very very slow, very safe”. If you need it you can have it, but you will pay for it, and step 5 of the lab told you roughly how much on your own disk.

Why can an RDB snapshot hurt your p99 even though the parent process does no disk I/O?

  1. Because the fork can pause the main thread noticeably
  2. Because snapshots are written by the main thread itself
  3. Because the RDB file gets rewritten entirely from scratch
  4. Because every client connection is dropped during the save

fork() is not free. On a large dataset the kernel has page tables to copy, and the docs warn this can stall Redis for milliseconds or, on a big dataset with weak CPU, up to a second. Since Redis is single-threaded, a stalled process is a stalled cache for every client at once.

“Written from scratch” is true and is not the reason — the child does that work, and copy-on-write is precisely the mechanism that keeps it off the parent. The cost is the fork itself, which is why this surprises people who have read that snapshots are asynchronous.

Say it out loud · about 75 seconds

A spoken answer to “what happens to your data if Redis dies?” — which is really a question about whether you have ever thought about it. Read it aloud, then say it again with the page covered.

  1. Situation

    We put an embedding cache in front of the retrieval hop. It took a real Redis restart before anyone asked what was in there, and whether we minded losing it.

  2. Mechanism

    A write lives in one of four places: the client, the Redis process, the kernel's page cache, or the disk. write() returning only gets you to the page cache — so a kill -9 is survivable, and losing the machine is not.

    fsync is the only thing that crosses the last boundary. appendfsync is just a choice about when to call it: whenever the kernel feels like it, once a second, or before the client hears back.

  3. What I did

    I killed it with SIGKILL and lost the data, on purpose, to see it. Then I benchmarked all three policies. everysec came out indistinguishable from no fsync at all — about 300 000 writes a second either way. always came out at 80 000, with p50 going from 0.09 to 0.62 milliseconds.

    So durability is nearly free and full durability is not: that half a millisecond is one device round trip on every write.

  4. What it cost

    And then I chose not to turn it on. The embeddings are derived: a cold cache is a 167-millisecond latency blip, not lost data. So AOF would buy nothing, and cost fsync on the hot path plus fork stalls from snapshots.

    The rubric scores are the opposite: nothing recomputes them, so one second of loss is a correctness bug. Those live in Postgres. The decision is per data class, not per cluster.

The sentence that sounds fluent and gets you caught

“We turned on AOF, so it's durable.” Two different things can be wrong with that at once. If it was turned on with CONFIG SET during an incident and never written to the config file, it reverted at the next restart and INFO agreed with you right up until you looked. And even with it on, everysec leaves a window — a window, not a delay, so at any instant you have between zero and one second of writes unflushed.

The version that holds: “AOF is on in the config file, not just on the running server, at everysec — so we can lose up to a second, and that is a decision we made about this data rather than a default we inherited.”

Probes to expect

  1. “Your Redis restarts. What breaks?” For your embedding cache: nothing breaks, latency rises to the uncached baseline until it warms. Being able to say “nothing, and here is why that is by design” is a much stronger answer than describing a durability setup you did not need.
    Model answer — say yours first

    Nothing breaks — and that is a deliberate property, not luck. Everything in there is a derived embedding, recomputable in about 167 ms, so a restart is a cold cache and a latency blip on the first request per key. The gateway degrades to the uncached path and keeps serving, which I proved by stopping Redis with the service running.

    If the answer were “we lose rubric scores”, the fix would not be AOF. It would be that the rubric scores never belonged in a cache.

    Invites · “How long is that blip, and how many keys deep?” — which is a question about your cold-start thundering herd, so it walks straight into lesson 0005.
  2. “Would you put the rubric scores in Redis?” No. They are the output of record and belong in Postgres, where you have transactions and a durability story you can audit. Cache the expensive inputs, persist the audited outputs.
    Model answer — say yours first

    No. They are not derived from anything — if we lose one we cannot recompute it, we have to re-run an evaluation — so the acceptable loss window is zero, and Redis's best offer at a price I would pay is one second.

    I could take appendfsync always and close it, and it measured 80 000 writes a second, which is plenty. But then I would be paying 0.54 ms of fsync per write to make a cache behave like a database that is already sitting next to it and does this properly, with transactions I also want.

    Invites · “What would make you change your mind?” — write volume Postgres could not take, and a loss window someone had actually agreed to in writing.
  3. “Redis is single-threaded. Is that a problem at your scale?” Not for throughput at cache-sized workloads — but one slow command blocks all clients, so the real answer is about banning KEYS, watching slowlog, and keeping values small.
    Model answer — say yours first

    Not at our scale, and single-threaded is mostly why it is fast — no locks, no context switching, and every command is atomic for free, which is what makes a Lua script a usable unit of work.

    What it does mean is that one slow operation stalls everything. A KEYS * on a large keyspace is an outage, not a slow query. And it makes persistence a latency concern: a fork() for a snapshot pauses the one thread for as long as it takes the kernel to copy the page tables.

    Invites · “So what is your slowest command?” — the honest answer is that I should have SLOWLOG on a dashboard and do not yet.
  4. “How would you scale this cache past one node?” Replication for read scale and failover; Redis Cluster for sharded keyspace. The routing question underneath it is consistent hashing, which is lesson 0026 — say that you know the mechanism has a name and you will get there.
    Model answer — say yours first

    The first move is not a second node, it is checking whether I need one, because a single Redis is doing 300 000 writes a second on a laptop. If the constraint is memory rather than throughput — which for an embedding cache it will be — then it is Redis Cluster and the keyspace gets hashed across shards.

    What that costs is multi-key atomicity: my keys are independent single-key GET/SETs, so I get away with it, but the moment anything wants two keys in one transaction they have to share a hash slot.

    Invites · “How do keys map to shards, and what happens when you add one?” — consistent hashing, and that is lesson 0026, where I implement the ring and measure how many keys move.

Recall — from lessons 0002–0005

You are about to recommend appendfsync always. What must you measure first, and how?

Write latency percentiles under realistic concurrency, with an open-loop generator. A closed-loop test will throttle itself around the fsync stalls and report a flattering p99 — the exact failure from lesson 0002. Also measure the cold path, since always makes every write slower, not just the tail.

lesson 0002 · coordinated omission
A one-second fork stall hits a cache serving a hot key that has just expired. What do you get?

A stampede. The stall widens the miss window enormously, so far more concurrent requests pile into the miss path — and if your single-flight lock lives in Redis, the lock acquisition is stalled too, so coalescing fails at the exact moment you need it. This is why the in-process asyncio.Lock layer from lesson 0005 is worth having underneath the Redis one.

lesson 0005 · stampede
Your Redis has maxmemory-policy noeviction and AOF enabled, and memory fills. What is the failure?

Writes start returning OOM command not allowed while reads keep succeeding — the quiet failure from lesson 0004. AOF changes nothing about it: durability and eviction are orthogonal. A full cache with perfect durability is a cache that durably remembers a stale working set.

lesson 0004 · noeviction
Which of the four things you cached in lesson 0003 would justify turning persistence on?

None of them. Embeddings are pure and recomputable, retrieval results are derived and TTL'd, completions are regenerable, and rubric scores should never have been in Redis to begin with. The whole cache is disposable by construction — which is the correct outcome, and knowing it is why you can leave persistence off with confidence rather than by accident.
