Lock, Retry, or Don't Read

The optimistic-versus-pessimistic argument assumes a gap between reading a value and writing it back. Measured across five contention levels and two gap lengths, optimistic never once beat the lock — and the strategy that appears in neither camp beat both by twelve times, because it removes the gap the argument is about.

The win

Run the same sixteen writers four ways and watch the fastest one produce the wrong answer. Then find that optimistic locking started 136 transactions to make 16 writes — exactly 16×17÷2, not approximately — and lost to the lock at every contention level tested. Then fix the whole thing with one statement that never reads at all, and finish on the clause that is for a completely different problem.

Why you, specifically
“Owned an AI vendor-evaluation platform end-to-end (Python/FastAPI, async SQLAlchemy, PostgreSQL, GKE) — live avatar interviews scored against a weighted rubric, with a two-pass Scout/Evaluator pipeline (Gemini, Tavily) grounding every vendor claim in a cited source.”

“Two-pass” is the phrase this lesson lives in. Two passes over the same vendor means two writers for one rubric score, and the interview question that follows is never about the model — it is “what happens when both passes finish at once?”

“Weighted rubric” is the second half, and it is worse. A weighted score is a value computed from other values, so it is the exact shape that invites a read, a computation and a write — which is the gap. And a rubric has an invariant across rows, which lesson 0016 already showed is invisible to everything except the strongest isolation level.

The claim is defended in full in chapter 0001 of Résumé Mastery. This lesson is where the four available answers get measured against each other.

Start here — the plain version

Two workers want to change the same number. There are only three things you can do about it: make one of them wait, let both try and make the loser repeat its work, or write the change in a way that does not depend on having read the old value first.

The first two have names and a literature. The third has neither, is shorter than both, and is the right answer more often than the argument between them suggests — because the argument takes the gap for granted and the third option deletes it.

Pessimistic locking
SELECT … FOR UPDATE. Take the row, then nobody else can, until you commit. Assumes a conflict is likely enough to be worth preventing.
Optimistic locking
Read a version, write with WHERE version = :seen. Assumes a conflict is unlikely, and pays a whole repeated transaction when it happens.
Version column
An integer incremented on every write. The mechanism behind optimistic locking, and the reason the conflict arrives as a row count rather than an error.
Atomic write
One statement that computes from the current value: SET score = score + 1. No read, so no gap, so nothing to defend.
The gap
The interval between reading a value and writing the value that depends on it. Every strategy here is an answer to it, and one of them deletes it.
Contention level
How many writers can reach one row at once. The axis the whole argument is supposedly about, and the one nobody measures.
SKIP LOCKED
Return rows nobody else has locked, rather than waiting. For handing out work, not for protecting a value.
NOWAIT
Error immediately rather than waiting for a lock. The third option in the same clause, and the one for when waiting is worse than failing.
Work queue
A table of jobs that many workers pull from. Superficially the same problem as a contended row, and actually the opposite one.

Four answers, and the fastest one is wrong

Start with the measurement rather than the argument. Sixteen writers, one row, each adding one, with a forty-millisecond gap between reading the value and writing it back. Three of the four strategies produce sixteen. The fourth produces one, and it is ten times faster than the correct ones — which is exactly why it is what most code does.

That speed is not a coincidence or a trade. It is the whole reason the bug persists: the broken version is fast because it does no coordinating, and nothing in a load test distinguishes “fast because it is efficient” from “fast because it is not doing the work”.

Why the usual framing sets you up to lose

The received wisdom is that optimistic locking wins under low contention and pessimistic wins under high, so you pick by measuring your conflict rate. That is a testable claim, and this lesson tests it across five contention levels and two gap lengths.

It did not reproduce. Optimistic never beat the lock at any point in the table — it was equal where conflicts were rare and considerably worse where they were common. The reason is in the next section and it is not subtle, but it is invisible if you reason about the two strategies rather than measuring them.

Counts are exact; wall clock is not

The attempts and conflicts columns have been identical on every run taken — they are decided by ordering, not by timing. The wall column moves by a few hundredths of a second. Where an argument below rests on a count, it is safe; where it rests on a duration, the step says so.

  1. Start Postgres and run all four strategies against the same sixteen writers on one row.

    $ cd anchor/vendor-eval-gateway
$ docker compose up -d postgres
$ uv run python -m bench.contention --experiment strategies

strategy     final  lost  applied  attempts  conflicts     wall
naive            1    15       16        16          0    0.07s
for-update      16     0       16        16          0    0.70s
optimistic      16     0       16       136        120    0.75s
atomic          16     0       16        16          0    0.06s

'attempts' is transactions started, so for the optimistic row it is
the work you paid for and threw away. 'atomic' does no read at all,
which is why it has nothing to lose and nothing to retry.
    The wrong answer is ten times faster than the right ones

    Row one is the shape most application code has. Sixteen writers applied, fifteen updates lost, zero errors, 0.07 s — and that speed is the reason it survives. Nothing in a load test tells you whether a fast path is efficient or simply not doing the coordination.

    Rows two and three are both correct and cost about the same in wall clock, which is the first surprise. The difference is in the attempts column: the lock started 16 transactions and optimistic started 136. Same answer, eight and a half times the work.

    Row four is the one that is missing from most discussions of this topic. It is correct, it is as fast as the broken version, and it is shorter than either of the two strategies people argue about — because it never reads the value it is changing.

  2. Check where 136 comes from, by halving the writers. If it is arithmetic rather than an artefact, the shape will hold.

    $ uv run python -m bench.contention --experiment strategies --writers 8 | sed -n '4,8p'
    strategy     final  lost  applied  attempts  conflicts     wall
naive            1     7        8         8          0    0.05s
for-update       8     0        8         8          0    0.35s
optimistic       8     0        8        36         28    0.38s
atomic           8     0        8         8          0    0.05s
    36 and 28, which are the numbers the arithmetic predicts

    Under total contention the writers succeed strictly one at a time, so the n-th writer loses to the n−1 already ahead of it. The total work is therefore 1 + 2 + … + N, which is N(N+1)÷2: eight writers give 36 and sixteen give 136. The conflicts are the same sum less the successes, N(N−1)÷2: 28 and 120.

    Both figures are exact on every run, which makes this a derivation you can do in an interview rather than a benchmark result you have to have memorised. The practical form: doubling the contention quadruples the wasted work, because it is quadratic in the number of writers.

  3. Now test the claim everybody repeats: that optimistic wins when conflicts are rare. Spread the same sixteen writers over a rising number of rows.

    $ uv run python -m bench.contention --experiment contention | sed -n '4,10p'
     rows            for-update            optimistic                atomic
            wall / attempts       wall / attempts       wall / attempts
    1           0.72s / 16            0.74s / 136           0.06s / 16
    2           0.36s / 16            0.37s / 72            0.05s / 16
    4           0.18s / 16            0.19s / 40            0.05s / 16
    8           0.09s / 16            0.10s / 24            0.05s / 16
   16           0.05s / 16            0.05s / 16            0.05s / 16
    It did not reproduce, at any point in the table

    Read the optimistic column against the for-update column, row by row: 0.74 against 0.72, 0.37 against 0.36, 0.19 against 0.18, 0.10 against 0.09, 0.05 against 0.05. Optimistic is equal at best and never faster. The claimed crossover is not there.

    The reason is structural rather than a measurement artefact, and it is one sentence: both strategies hold a pooled connection for the whole of the gap, so they queue against each other in exactly the same way. The only difference between them is what happens on a collision — one waits, the other repeats — and waiting is cheaper than repeating.

    Where optimistic genuinely wins is a case this bench cannot contain: a gap you cannot hold a transaction across, such as a form a person has open for three minutes. That is a real and important use, and it is not a throughput argument at all.

    Every cell in the first two columns scaled by roughly five and their relationship did not change. Optimistic still never wins. So the result is not an artefact of a short gap, which was the most plausible reason to distrust the previous step.

    Look at the atomic column while you are here: 0.21 s in every row, unchanged by contention. It is flat because the arithmetic happens inside the statement, so there is no interval during which anybody else's write is a problem. Every other column is a strategy for surviving an interval; this one does not have the interval.

  5. Now the clause that gets recommended for this problem and is for a different one: many workers pulling jobs from a table.

    $ uv run python -m bench.contention --experiment queue

each holding its claim for 40 ms before committing.

clause                      claimed  duplicates  idle takes     wall
FOR UPDATE                       32           0           8    1.51s
FOR UPDATE SKIP LOCKED           32           0           8    0.20s

Both are correct -- no run is claimed twice either way. Plain FOR
UPDATE queues every worker behind the same row, so the workers are a
single-file line holding N connections to do one connection's work.
    Seven times faster, and the duplicates column is zero in both rows

    The zero is the important number. SKIP LOCKED did not make anything correct — plain FOR UPDATE was already correct and claimed no job twice. What it changed is which row each worker took: without it, all eight workers queue behind whoever holds the first row, so eight connections do one connection's work.

    The Postgres documentation is unusually blunt about the limitation, and it is worth being able to quote: “Skipping locked rows provides an inconsistent view of the data, so this is not suitable for general purpose work, but can be used to avoid lock contention with multiple consumers accessing a queue-like table.”

    Which is why recommending it for a contended rubric score is wrong. A queue has other work waiting behind the locked row; a contended value does not. Skipping is only safe when the thing you skipped was interchangeable.

Underneath

One layer down · the gap is the whole subject

Four things. The first is what the four strategies actually differ on, the second is why optimistic retries are quadratic, the third is why the textbook claim did not reproduce, and the fourth is why the clause everybody recommends is for a different problem.

Every strategy is an answer to the same interval

Read a value, compute something from it, write the result. The interval between the read and the write is the only thing any of these four strategies is about, and they exhaust the possible responses: ignore it, prevent anybody else entering it, detect afterwards that somebody did, or arrange not to have one.

Putting it that way makes the fourth option obvious, and it is missing from most treatments of this topic because the topic is usually named “optimistic versus pessimistic” — a framing that presupposes there is an interval to defend. For anything expressible as a function of the current value, there is not. SET score = score + 1 has no gap, so the entire argument is inapplicable.

The limit is worth stating precisely, because it is what an interviewer will probe. The atomic form works when the new value is a function of the old one that the database can compute. If the new value comes from a model, a person, or anything else outside the statement, you are back to having a gap and back to the argument.

Optimistic retries are quadratic, and the number is exact

Under total contention on one row, the writers succeed strictly one at a time, because each successful write increments the version and invalidates every read taken before it. So the first writer succeeds on attempt one, the second has lost once and succeeds on attempt two, and the n-th has lost n−1 times.

The sum, and what arrived:

writers predicted attempts measured predicted conflicts measured 2 2x3/2 = 3 3 2x1/2 = 1 1 8 8x9/2 = 36 36 8x7/2 = 28 28 16 16x17/2 = 136 136 16x15/2 = 120 120

Exact on every run, because these counts are decided by ordering rather than timing. The consequence to carry: the cost is quadratic in the number of contending writers, so doubling the contention quadruples the wasted work — and the retry budget has to grow linearly with it, which lesson 0016 measured from the other side when a budget of eight silently dropped eight of sixteen writes.

The textbook crossover did not reproduce, and the reason is the pool

The received version is that optimistic locking wins under low contention because it avoids the cost of taking a lock. Measured across five contention levels and two gap lengths, it never won: equal at sixteen rows, 0.74 against 0.72 at one row, and equal or slightly worse at every point in between.

The explanation is that the thing being avoided is not the expensive part. An uncontended row lock is one extra clause on a statement you were issuing anyway — it is microseconds. What actually costs is holding a connection for the length of the gap, and both strategies do that identically, which is lesson 0015's ceiling applying equally to both.

What each strategy pays for, per write:

lock taken connection held work repeated on conflict naive no for the gap none; it overwrote instead for-update yes for the gap none; the loser waited optimistic no for the gap the entire transaction atomic yes, us one stmt none; there is no gap

The middle column is the same for the three that read first, which is why their timings converge. The argument is about the last column and the cost is in the middle one. That is the whole of why the crossover is not where it is supposed to be — and it also predicts where optimistic genuinely wins: when you cannot hold a transaction across the gap at all, because the gap spans a person, a request boundary, or a queue.

SKIP LOCKED answers a different question, and says so

It is routinely recommended for lock contention, which is true in the way that changes the subject. It does not protect a value and it does not prevent a lost update; it changes which row a worker takes when the one it wanted is busy. Measured on a work table it took the same thirty-two jobs seven times faster with zero duplicate claims — and plain FOR UPDATE also had zero duplicate claims.

The Postgres documentation states the limitation without being asked, which is the sentence worth carrying: “Skipping locked rows provides an inconsistent view of the data, so this is not suitable for general purpose work, but can be used to avoid lock contention with multiple consumers accessing a queue-like table.” The same paragraph gives NOWAIT as the third option: “the statement reports an error, rather than waiting, if a selected row cannot be locked immediately”.

Three ways of not waiting, and what each is for:

clause when the row is locked use it when (none) wait for it you need that specific row NOWAIT fail immediately waiting is worse than failing SKIP LOCKED take a different row the rows are interchangeable

The last row is the test, and it is one question: is the row you skipped interchangeable with the one you took? For a queued job, yes — the work still gets done by somebody. For a rubric score, no — skipping it means the score is not written, and nothing tells you.

Which lands on the sentence worth keeping: optimistic and pessimistic are two answers to a gap, and the best answer is usually not to have one. The argument is real, it is narrower than it is presented, and it applies only where the new value cannot be computed from the old.

Check yourself

Sixteen writers add one to the same row with optimistic locking. The bench started 136 transactions to make sixteen writes. Where does 136 come from?

  1. Every writer retries once for each writer ahead of it
  2. Postgres reran them on each conflict it chose to detect
  3. The connection pool forced them to run in eight batches
  4. Each transaction was simply far too slow to finish first

Each successful write increments the version, invalidating every read taken before it, so the writers succeed strictly one at a time and the n-th has lost n−1 times. The total is 1 + 2 + … + 16, which is 16×17÷2 = 136, and the conflicts are 16×15÷2 = 120. Both figures were exact on every run.

The consequence worth carrying is that the cost is quadratic: doubling the contention quadruples the wasted work, and the retry budget has to grow linearly with the writer count — which is the same failure lesson 0016 found from the other side when a budget of eight dropped eight of sixteen writes.

Adding SKIP LOCKED took the same thirty-two jobs in 0.20 s instead of 1.51 s, with zero duplicate claims either way. What did it actually change?

  1. Which row each worker took, not whether any was correct
  2. It dropped the row lock so workers no longer waited
  3. It let two workers claim the very same job concurrently
  4. It moved the whole queue into memory instead of Postgres

Only which row. Plain FOR UPDATE was already correct — the duplicates column is zero in both rows — it just made all eight workers queue behind whoever held the first job, so eight connections did one connection's work. SKIP LOCKED still takes a lock; it simply does not wait for one somebody else holds.

Which is why it is the wrong recommendation for a contended value. The test is whether the row you skipped was interchangeable with the one you took: for a queued job it is, and for a rubric score it is not — skipping there means the score is never written, and nothing reports it.

Say it out loud · about 75 seconds

A spoken answer to “two passes write the same rubric score — optimistic or pessimistic locking?” Read it aloud, then say it again with the page covered.

  1. Situation

    A Scout pass and an Evaluator pass both write one rubric score. Two writers, one row, by design rather than by accident.

  2. Mechanism

    Both strategies are answers to the same thing: the gap between reading a value and writing what depends on it.

    One prevents anybody else entering the gap. The other detects afterwards that somebody did, and repeats the whole transaction.

  3. What I did

    I measured four, not two. The read-modify-write we had applied all sixteen writes and left a total of one, with no errors.

    Optimistic cost 136 transactions for 16 writes, which is n times n plus one over two. It never beat the lock at any contention level.

    So I removed the gap instead. One statement that adds to the current value: same answer, twelve times faster.

  4. What it cost

    It only works when the new value is a function of the old one. A verdict written by a model is not.

    For those we take the lock, because our two passes contend by design and repeated work is quadratic in the writers.

The sentence that sounds fluent and gets you caught

“We use optimistic locking because contention is low.” The received answer, and the follow-up is “how low, and how did you measure it?” If the number does not exist, the position is a preference. Worse, the measured version does not support it: across five contention levels optimistic never beat the row lock, because both hold a connection for the whole gap and only the collision behaviour differs. The version that holds names the real boundary: “optimistic when the gap spans something we cannot hold a transaction across — a person, or two requests — and a lock otherwise.”

The second trap is offering SKIP LOCKED as a fix for a contended row. It sounds current and it answers a different question, and the person asking will know, because the documentation itself says it gives “an inconsistent view of the data”. Skipping a row is only safe when that row was interchangeable with the one you took instead — true of a queued job, false of a score somebody is waiting for.

Probes to expect

  1. “Two workers write the same row. Optimistic or pessimistic?” Phrased as a two-way choice on purpose. The answer that scores is the one that notices there are four options and that the question presupposes a gap.
    Model answer — say yours first

    Both of those are answers to the same thing — the gap between reading the value and writing what depends on it — so my first question is whether the gap has to exist. If the new value is a function of the old one, it does not: one statement that adds to the current value has no gap, and I measured it at 0.06 s against 0.70 for the lock, with the same correct answer.

    Where the gap is unavoidable, because the new value comes from a model or a person, I take the lock. I measured optimistic across five contention levels and it never beat the row lock — equal where conflicts are rare, and 136 transactions for 16 writes where they are common. The case for optimistic is not throughput; it is a gap you cannot hold a transaction across at all.

    Invites · “Why 136?” — it is a triangular number, and it is exact.
  2. “Surely optimistic wins when contention is low?” The standard follow-up, stated as fact. Disagreeing is only safe if you have the measurement, and this is the one place in the batch worth disagreeing.
    Model answer — say yours first

    That is what I expected and it did not reproduce. Sixteen writers spread across one, two, four, eight and sixteen rows: optimistic was equal at best and never faster, and I re-ran it with a gap five times longer in case the gap was too short to matter. Same verdict.

    It would not, and that is the part worth saying plainly. Recall — from lessons 0015–0017

0015 measured a connection pool as a queue with a computable ceiling. How does that explain why optimistic never beat the lock here?

Because both strategies hold a connection for the whole of the gap, so they draw from the same queue in the same way and the pool's ceiling applies to both equally. The thing optimistic avoids is taking a row lock, and an uncontended row lock is one extra clause on a statement you were issuing anyway — microseconds against a gap measured in tens or hundreds of milliseconds. So the saving is real and irrelevant, and the two strategies converge to within a hundredth of a second at every contention level tested. It also predicts where optimistic genuinely does win, which the bench cannot show: when the gap spans something you cannot hold a transaction across at all, such as a person with a form open. There the comparison is not lock-versus-version, it is version-versus-nothing, because holding a pooled connection for three minutes is not an option anybody would offer.

lesson 0015 · the pool as a shared ceiling
0016 found that a retry budget of eight silently dropped eight of sixteen writes. This lesson derived N(N+1)/2. Are those the same fact?

Two halves of it. The derivation says the n-th writer must lose n−1 times before it wins, so the total work is triangular and the worst-case retries any single writer needs is N−1. The budget failure is what happens when the loop is allowed fewer than that: with sixteen writers and a budget of eight, the ninth writer and everything after it runs out of attempts, and exactly eight writes are dropped. So the formula gives both the aggregate cost and the minimum safe budget, and the second is the one that turns into a bug. The practical form is a pair: budget at least the contention level, and expect quadratic wasted work while you do. And when the contention level is unbounded, the pair has no solution, which is the argument for removing the gap rather than defending it — the point both lessons converge on from different directions.

lesson 0016 · a retry budget smaller than the contention
0017's fix was to move the model call out of the transaction, which reopened the lost-update problem. Which of this lesson's four strategies closes it again?

Atomic where the value allows it, and the version column where it does not — and notably not the lock, which is what the held transaction was doing accidentally. That is the whole reason these two lessons are adjacent. Holding a transaction across a model call protects the read-modify-write at a cost of 0.9 turns a second instead of 5.5; moving the call out restores the throughput and removes the protection. Putting the arithmetic inside the statement gives you both, because the write no longer depends on a value anybody remembered. Where the new value genuinely comes from the model and cannot be expressed as a function of the old one, the version column is the right replacement: it is checked at write time, so it needs no transaction spanning the call, and it converts the lost update into a retry whose budget you size from the contention level. A lock would work too and would reintroduce exactly the wait 0017 removed.
