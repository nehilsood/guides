Cache-Aside and Friends

There is no cache layer anywhere on your résumé. You run a latency-budgeted RAG service that embeds the same queries repeatedly, so that absence is conspicuous. Four strategies exist, they fail in different ways, and picking between them is a two-question decision once you know what the questions are.

The win

You will put a cache-aside layer in front of the retrieval hop, watch the 165 ms disappear on the second identical query, and be able to say out loud why write-through would have been the wrong choice here.

Why you, specifically
“RAG & Evaluation: embeddings, hybrid search, re-ranking, on-device RAG…”
“Infrastructure: GCP (Vertex AI, BigQuery, GKE), Kubernetes, Docker, FastAPI, PostgreSQL, async SQLAlchemy, CI/CD”

Two skill lines, and between them no cache of any kind. An interviewer reading “embeddings” and “hard 8 s budget” in the same document will assume you cache embeddings, then ask which strategy — and the answer “we used Redis” is not an answer to that question.

Start here — the plain version

A cache is a small, fast store that keeps copies of answers you already worked out, so that the second time someone asks the same question you can hand back the saved answer instead of doing the work again. That is all it is. Redis is one; a dictionary in memory is one.

The four “strategies” this lesson names sound like four technologies. They are not. They are the four answers to two questions: who talks to the database — your code, or the cache? and when does a write reach the database — now, or later? Pick an answer to each and you have picked a strategy. The reason it matters is that they fail in different ways, and the one everybody defaults to is the one that keeps working when the cache dies.

Hit / miss
The answer was already in the cache / it was not, so you had to do the real work.
Hit rate
The share of requests that were hits. The single number that says whether a cache is earning its place.
TTL
Time to live — how long an entry may be used before it is thrown away. Your promise about how stale an answer is allowed to get.

The four strategies

Every caching design answers two questions: who talks to the database, and when does the write land. That is all. The four named patterns are just the four combinations worth using.

The distinctions that actually matter in a review. “Modal behaviour” is the number of distinct code paths a request can take — and therefore the number you have to test.
StrategyReadsWritesFails badly when
Cache-aside
a.k.a. side cache, lazy loading		 App checks cache; on a miss the app fetches and populates it. App writes the store and invalidates the key. Many clients miss at once — the stampede in lesson 0005. Also: only cached data is fast, so you have two performance modes.
Read-through
inline cache		 App asks the cache; the cache fetches on a miss. Unchanged — writes bypass. The cache becomes a hard dependency. If it is down, you are down, whereas a side cache degrades to slow.
Write-through From cache. Synchronously to cache and store, before acknowledging. Every write pays both latencies. Excellent consistency, worse write budget.
Write-behind
write-back		 From cache. To cache immediately; the store is updated asynchronously. The cache dies holding unflushed writes and they are gone. Fastest writes, real durability risk.
The key is the contract

A cache key must include everything the value depends on. An embedding cached under sha256(text) alone is a landmine: the day you change embedding models, every stale vector is silently wrong and your retrieval quality degrades with no error anywhere. Key it as emb:{model_version}:{sha256(normalised_text)}. Version in the key, always.

In plain words

Cache-aside means your own code checks the cache before doing the real work. A hit hands back the saved answer in 47 ms, a miss does the work and saves the result in 175 ms, and a dead Redis is simply skipped at about 172 ms. That third path is why this design keeps answering when the cache fails.

Lab — cache the retrieval hop

Lab 0003 ~15 minutes

Add cache-aside to embed

  1. Start Redis. This is the first lesson that needs a service, so this is also the step where you start Docker Desktop if it is not already running.

  2. Measure the uncached hop twice with the same query, so you have a baseline that is not a guess.

    { "ms": 166.3, "embed_calls": 1 }
{ "ms": 165.8, "embed_calls": 2 }
    The problem, stated in numbers

    embed_calls went to 2 and the second call cost the same 165 ms. You just paid full price to compute a vector you already had. In a live interview, candidates repeat phrasings constantly.

  3. Write the cache. Create app/cache.py — this is the one file in Tier 1 you author yourself, and it is deliberately short.

    app/cache.py 
    from __future__ import annotations

import hashlib
import json
from collections.abc import Awaitable, Callable

import redis.asyncio as redis
import structlog

log = structlog.get_logger(__name__)

EMBED_MODEL_VERSION = "fake-embed-v1"


class EmbeddingCache:
    """Cache-aside in front of a pure function.

    The value is a deterministic function of (model version, normalised text),
    so there is no invalidation story to get wrong — which is exactly why this
    is the right first cache to add.
    """

    def __init__(self, url: str, ttl_seconds: int = 3600) -> None:
        self._redis = redis.from_url(url, decode_responses=True)
        self._ttl = ttl_seconds
        self.hits = 0
        self.misses = 0

    def key(self, text: str) -> str:
        # Model version in the key. Without it, changing embedding models
        # leaves every stale vector silently wrong and nothing errors.
        digest = hashlib.sha256(text.strip().lower().encode()).hexdigest()[:32]
        return f"emb:{EMBED_MODEL_VERSION}:{digest}"

    async def get_or_compute(
        self, text: str, compute: Callable[[], Awaitable[tuple[float, ...]]]
    ) -> tuple[float, ...]:
        k = self.key(text)

        # A cache that can take down the service it accelerates is not a
        # cache, it is a dependency. Every Redis call here is best-effort.
        try:
            cached = await self._redis.get(k)
        except Exception as exc:
            log.warning("cache.get_failed", error=str(exc))
            cached = None

        if cached is not None:
            self.hits += 1
            return tuple(json.loads(cached))

        self.misses += 1
        value = await compute()

        try:
            await self._redis.set(k, json.dumps(value), ex=self._ttl)
        except Exception as exc:
            log.warning("cache.set_failed", error=str(exc))

        return value

    @property
    def hit_rate(self) -> float:
        total = self.hits + self.misses
        return self.hits / total if total else 0.0

  4. Wire it into the retrieval hop. In app/retrieval.py, give Retriever an optional cache and route embed through it.

    app/retrieval.py — changes only 
    def __init__(
    self,
    embed_ms: float = 120.0,
    search_ms: float = 45.0,
    cache: "EmbeddingCache | None" = None,   # new
) -> None:
    ...
    self._cache = cache

async def embed(self, text: str) -> tuple[float, ...]:
    if self._cache is None:
        return await self._embed_uncached(text)
    # Cache-aside: the *application* owns the miss path.
    return await self._cache.get_or_compute(
        text, lambda: self._embed_uncached(text)
    )

    Rename the existing body to _embed_uncached. Then in app/state.py, build the cache from settings.redis_url and pass it to the Retriever.

  5. Measure again. Same two calls as step 2.

    before — second identical query

    166ms

    Full embed plus search, every time.

    after — second identical query

    46ms

    Search only. The 120 ms embed is gone, and embed_calls stayed at 1.

    You should see

    embed_calls stuck at 1 across both requests, and the second call costing roughly the search_ms figure alone. If embed_calls increments, your key is not stable — print it and compare.

  6. Now prove the degradation story, which is the half of caching that gets skipped. Kill Redis with the server still running.

    You should see

    A cache.get_failed warning in the server log and a response that still succeeds at about 166 ms. That is the entire argument for cache-aside over read-through: you degraded to slow rather than to down. Restart with docker compose start redis.

Two performance modes now exist

Before this lab your retrieval hop always cost 165 ms. Now it costs 46 ms or 166 ms depending on state you cannot see from outside. The Amazon Builders' Library calls this modal behaviour, and it is the hidden cost of every cache: your service has two personalities, and load tests usually only exercise the warm one. Whenever you add a cache, ask what happens on the cold path at full production traffic — that question is lesson 0005.

Underneath

One layer down · why this strategy, and the two things it does not protect you from

In plain words

The usual danger with cache-aside is timing: a slow reader can put an old value back just after a writer cleared it, and the cache serves it until it expires. That cannot happen here, because an embedding depends only on the text and the model version, and both are in the key. Change either and you get a new key.

The race cache-aside leaves open — and why it cannot fire here

The classic cache-aside hazard is a stale write that outlives the truth:

reader GET k → miss writer UPDATE k → v2 in the database writer DEL k → cache invalidated reader SET k, v1 → the cache now serves v1 until its TTL expires

Nothing is out of order and nothing errored. The reader simply computed before the write and wrote after the invalidation, so a strictly stale value is installed by the invalidation protocol. This is the real reason people reach for write-through, and the reason cache-aside needs an argument rather than a preference.

Here it cannot happen, and the reason is worth saying precisely, because it is the property that made this the right first cache in the course: the value is a pure function of the key. The vector is determined entirely by the model version and the normalised text, both of which are in the key. There is no v2 for this key — if the function changes, the model version changes, so the key changes and the old entry is simply unreferenced. A cache whose keys already contain everything that determines their values has no invalidation problem to get wrong.

Which is also why search is not cached and embed is. Both are cacheable in the mechanical sense. Only one of them is cacheable without a staleness argument, because search depends on a corpus that changes underneath the key.

In plain words

Stopping Redis cleanly is the easy failure: the connection is refused at once. A Redis that goes silent instead makes the client wait out its default 5-second timeout, and a miss makes two calls, so up to ten seconds against an 8-second turn. The fix is an explicit timeout, shorter than the work the cache saves.

The default that will cost you five seconds

The degraded mode in the lab is the friendly failure. docker compose stop redis closes the port, so the kernel replies with a RST and the client fails instantly. A Redis that is unreachable rather than closed — a partition, a hung node, a security-group change, a full conntrack table — sends nothing at all, and then you wait for a timeout.

Measured on redis-py 8.1.0, one GET against three states of the same client:

reachable → 15.4 ms port closed (RST) → 0.8 ms black-holed (no reply) → 5001.6 ms

Five seconds, because socket_connect_timeout and socket_timeout both default to 5. Against an 8-second per-turn budget that is most of the turn spent waiting for a cache that was supposed to make things faster — and a miss does two calls, a GET and a SET, so the worst case is ten seconds and a breached budget caused entirely by the optimisation.

So the cache code above is incomplete as written, and knowingly so: it needs an explicit timeout, sized against the budget rather than against the library's idea of patience. A cache lookup that is allowed to take longer than the work it is avoiding has stopped being a cache. That sizing argument is lesson 0012, and this is the number that motivates it.

Cache-aside is the right choice because the miss path is yours — that is what buys the degradation mode. It is safe here because the key contains everything that determines the value, so the invalidation race has no way to fire. And it is not yet safe against a slow Redis, because nobody has set a timeout.

Check yourself

Your Redis instance dies at peak load. With cache-aside on the retrieval hop, what happens?

  1. Requests get slower, because the app fetches it directly
  2. Requests fail, since the cache is now a dependency
  3. Requests succeed and stay fast, using a local fallback
  4. Requests block until the cache finishes coming back up

Cache-aside keeps the application in charge of the miss path, so an unreachable cache is just a permanent miss — provided every Redis call is wrapped, as in the lab. You degrade to slow. With read-through the cache sits inline and owns the fetch, so losing it means losing the read path entirely: you degrade to down.

That single difference is usually the whole reason to choose cache-aside for something on a latency budget, and it is worth being able to state in one sentence.

Why is an embedding a better first cache target than a retrieval result?

  1. It is pure, so no staleness budget is needed
  2. It is smaller, so many more of them fit
  3. It is slower, so each hit saves much more
  4. It is rare, so the hit rate climbs higher

Purity is the reason. An embedding depends only on the input text and the model version, both of which you can put in the key, so it can never go stale — there is simply no invalidation logic to get wrong. A retrieval result depends on the corpus, so caching it means committing to a staleness budget and defending it.

“It is slower” is nearly right and still the wrong reason: embed at 120 ms is indeed the bigger half of the hop, but you would cache a pure 5 ms function ahead of an impure 500 ms one, because correctness risk beats latency saving. Cache the things that cannot be wrong first.

Say it out loud · about 75 seconds

A spoken answer to “you mentioned a cache — what did you cache and why?” Read it aloud, then say it again with the page covered. The three numbers are the whole thing; if you lose everything else, keep those.

  1. Situation

    The retrieval hop was 165 milliseconds of an 8-second turn, and about 120 of that was embedding the query. Same questions kept coming back, and we were paying to embed them every time.

  2. Mechanism

    Embedding is a pure function — the same text and the same model always give the same vector. So the model version and a hash of the normalised text go in the key, and then there is nothing that determines the value which is not already in the key.

    That is why it is the right thing to cache first: it has no invalidation story to get wrong. If the function changes, the key changes.

  3. What I did

    Cache-aside, so the miss path stays in my code rather than inside the cache. Three latencies came out of it: 47 milliseconds on a hit, 175 on a miss, and 172 with Redis stopped entirely.

    That third number is the one I care about. I killed Redis with the service running and it kept answering — degraded to the uncached path, logged a warning, and recovered on its own when Redis came back. No restart.

  4. What it cost

    A miss is now slower than having no cache, by one round trip — about eight milliseconds. Cheap, but it is real and I would rather say it than be told it.

    The version I first wrote had a bug I only found by measuring. The client’s default timeout is five seconds. A Redis that hangs rather than refusing would burn five of my eight seconds waiting for the thing meant to make it faster. So it needs a timeout smaller than the work it avoids.

The sentence that sounds fluent and gets you caught

“We use Redis for caching.” It answers nothing and invites all three of the real questions at once: what is in the key, what happens on a miss, and what happens when Redis is gone. Naming the strategy is the cheapest possible upgrade — cache-aside tells a listener you know there are four of them and that you picked one.

The second trap is claiming graceful degradation without having caused it. “If Redis is down we just fall through to the database” is true of cache-aside by construction and false of read-through, and the person asking usually knows which one you built. Say that you stopped it on purpose and what the latency was.

Probes to expect

  1. “You cache embeddings. What is in the cache key?” If the model version is not in your answer, they have found a real bug. Say the key structure out loud: emb:{model_version}:{sha256(normalised_text)}.
    Model answer — say yours first

    Two things: the model version and a SHA-256 of the normalised query text — stripped and lowercased. So emb:fake-embed-v1:<hash>.

    The model version is the field that matters. Without it, changing embedding models leaves every previously cached vector valid-looking and semantically wrong — retrieval quality degrades and nothing errors, which is a failure mode with no signal at all. With it in the key, a model change is a cache miss rather than a bug.

    Invites · “What determines the value that is not in the key?” — the answer here is nothing, which is exactly why this cache has no invalidation problem. Normalisation is the sneaky one: change strip/lower and you silently change the key space.
  2. “What happens to your 8 s budget when the cache is cold — say, right after a deploy?” Modal behaviour. Every request takes the slow path simultaneously, which is worse than the pre-cache baseline because you also sized capacity around the warm path.
    Model answer — say yours first

    Every request pays the full uncached hop, so 165 milliseconds instead of 47 — which against an 8-second budget is survivable on its own. The problem is not the cost per request, it is that all of them pay it at once, and for a popular key they pay it concurrently.

    I measured that: 200 concurrent requests for one cold key produced 200 identical embedding calls. So the real answer to “what happens after a deploy” is a thundering herd, and the fix is single-flight plus jittered TTLs rather than a bigger cache.

    Invites · “So how do you warm it?” — and the honest answer is that warming and single-flight solve different halves: warming reduces how often you are cold, single-flight bounds what being cold costs.
  3. “Would you cache the LLM completions too?” The senior answer is conditional: at temperature 0, keyed on the full prompt plus system prompt plus model version, for the rubric path only. Never for anything conversational.
    Model answer — say yours first

    Only where the prompt is genuinely deterministic, which for us is a small slice. A completion is a function of the prompt and the sampling parameters and the model version, so all three have to be in the key or the cache is lying — and at temperature above zero it is lying by design, because the whole point is that the same prompt gives different output.

    The place it does pay is not a response cache at all, it is the prefix cache: the shared system prompt is identical on every request, and caching its KV state cuts time-to-first-word without pretending two completions are the same.

    Invites · “What is your prefix-cache hit rate?” — which is lesson 0008, and it is a question about the GPU bill rather than about latency.
  4. “Why not write-through?” Because nothing is being written. Embeddings are derived, not authored — write-through answers a question this workload does not ask.
    Model answer — say yours first

    Because there is no write. Nothing in the system updates an embedding — they are computed on demand from text, so there is no write path for a write-through cache to sit in front of. Write-through answers “how do I keep the cache consistent with writes”, and I do not have that question.

    What I do have is the read-side race cache-aside is famous for: a reader that misses, then a writer that updates and invalidates, then the reader installing its stale value. That cannot fire here because the key contains everything that determines the value — there is no second version of the same key.

    Invites · “Where in your system would you use write-through?” — somewhere with real mutation and a read-your-writes requirement, like rubric scores, and there the answer is that they should not be in a cache at all.
