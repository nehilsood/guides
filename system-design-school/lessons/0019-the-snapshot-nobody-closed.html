System Design School / Tier 1 · Postgres / Lesson 0019 / Needs Postgres

The Snapshot Nobody Closed

One session, holding no lock and running no query, stopped vacuum from removing any of 499 900 dead rows and let a 143-page table grow to 7 213. Under asyncpg — the driver this whole stack runs on — a plain READ COMMITTED transaction that has read anything at all is enough. And the query plan never changed: only the buffers line showed it.

The win

Leave one transaction open and watch VACUUM report every dead row as not yet removable. Find that the same SELECT holds vacuum back under asyncpg and not under psql, and prove why with one extra statement. Watch a query keep its plan while its buffers grow elevenfold. Close the session and find that the table does not get smaller. Then set the timeout that fixes it, and see which transaction pays.

Why you, specifically
“RAG & Evaluation: embeddings, hybrid search, re-ranking, on-device RAG, MLflow, LLM-as-a-judge, A/B testing, guardrail design”

Evaluation is the half of that line with real work behind it: a 368-scenario harness, an A/B at eight runs an arm, a bake-off replaying one payload through the real code path. Every one of those produces rows, and the tables they land in only ever grow. A run is inserted as running and updated when it finishes, so every run leaves one dead row version behind. Nobody deletes anything.

That is the table shape where vacuum is the only thing standing between you and unbounded growth. It is also the shape that attracts long-lived sessions: a notebook left open on the results, a judge loop that reads a rubric and then awaits a model, a report that runs for an hour. Any one of them is enough, and none of them shows up where people look.

The claim is defended in full in chapter 0012 of Résumé Mastery. This lesson is what happens to the tables underneath it.

Start here — the plain version

An UPDATE in Postgres does not overwrite a row. It writes a new version and leaves the old one where it was, because somebody might still be reading it. Lesson 0016 showed both versions sitting on disk. Something has to come back later and remove the old ones, and that is vacuum.

Vacuum is only allowed to remove a version that no open transaction anywhere could still need. So the oldest open snapshot in the database draws a line, and nothing newer than that line gets removed from any table, however long ago it died. One forgotten session is enough to stop the whole mechanism, and it is not waiting on anything, so nothing that watches for waiting reports it.

Dead row version
The old copy an UPDATE or DELETE leaves behind. Still on disk, still read by scans, invisible to new transactions.
Vacuum
The process that removes dead versions and marks their space reusable. Autovacuum runs it for you when enough rows have changed.
Snapshot
The list of which transactions a statement is allowed to see. Held for a statement in READ COMMITTED, for the whole transaction in REPEATABLE READ.
The horizon
The oldest snapshot still open anywhere. Vacuum may not remove anything newer. VACUUM VERBOSE prints it as the removable cutoff.
backend_xmin
The column in pg_stat_activity showing the snapshot one session is holding. If it is set, that session is part of the horizon.
Idle in transaction
A session that has begun a transaction and is sending nothing. Not waiting, not running. Just open.
Portal
The server's handle on a statement being executed. The extended protocol, which asyncpg always uses, leaves one open after the statement finishes.
Bloat
Space a table occupies beyond what its live rows need. Every scan reads it anyway, and plain vacuum does not give it back.
Visibility map
One bit per table page saying every row on it is visible to everyone. Set only by vacuum, and the reason an index-only scan can skip the table.
EXPLAIN (ANALYZE, BUFFERS)
Run the query and report the plan, the time, and how many 8 kB pages it touched. The last number is the one bloat moves.

One session, and nothing that watches will see it

Start with what the session is not doing. It holds no row lock, so no lock monitor lists it. It runs no query, so no slow-query log records it. Its state is idle in transaction, which looks like the least interesting thing on the server. It is the most expensive thing on the server, and the cost lands on every other table.

The surprise in this lesson is how little it takes. The received version is that you need a long REPEATABLE READ transaction or a write to hold vacuum back, and that a READ COMMITTED session releases its snapshot after every statement. That is true under psql. Under asyncpg, which is what async SQLAlchemy runs on, it is not, and the reason is one sentence of the wire protocol.

Why the plan will not warn you

The original plan for this lesson assumed bloat would flip the planner to the wrong plan. Measured, it did not: the latest-runs query kept exactly the same plan on a bloated table as on a clean one, and returned exactly the same twenty rows.

That is the worse outcome, not the better one. A plan that changes is a plan somebody notices. A plan that stays the same while doing eleven times the work is one only BUFFERS can show you, and most people never add it.

Lab — hold one session open, then try to clean up after it

Lab 0019 ~20 minutes

Six open transactions, one protocol message, and a table that does not shrink

Needs: anchor/vendor-eval-gateway Docker · Postgres ~20 min
Counts are exact; ids and milliseconds are not

Every row count and every page count below has repeated on every run: they are decided by what was written, not by timing. The transaction ids in steps 1 and 2 are different every time, because every transaction on the server takes the next one. The ms columns wobble. Where an argument rests on a count, it is safe; where it rests on a duration, the step says so.

  1. Start Postgres, then leave a transaction open six different ways and ask vacuum what it could remove behind each one.

    $ cd anchor/vendor-eval-gateway
$ docker compose up -d postgres
$ uv run python -m bench.vacuum --experiment horizon
    transaction left open                 xid       xmin      vacuum could not remove
begin-only                            -         -              0 of 4999
simple-select                         -         -              0 of 4999
extended-select                       -         154182      4999 of 4999
select-for-update                     154187    154187      4999 of 4999
update                                154193    -           4999 of 4999
repeatable-read                       -         154199      4999 of 4999
sqlalchemy session, one select        -         154204      4999 of 4999

what pg_stat_activity shows while it is open:
  idle in transaction  50 xids behind  open 1.0 s  last query: SELECT score FROM vac_hot WHERE id = 1
    Rows two and three are the same SELECT, and only one of them stops vacuum

    The first two rows hold nothing, and that is what the received wisdom predicts: a READ COMMITTED transaction takes a fresh snapshot for each statement and drops it afterwards. Row three is the same statement, through asyncpg, and vacuum can remove none of the 4 999 dead rows behind it.

    The last row is the one that matters for this codebase. An ordinary async SQLAlchemy session, one read, then an await on something else — lesson 0017's shape, exactly — holds the horizon for as long as it stays open. It is not a long query or a REPEATABLE READ transaction. It is the default.

    Look at the last line too. idle in transaction, fifty transactions behind after one second, last query a finished SELECT. That is what the culprit looks like in pg_stat_activity, and the column worth sorting by is how far behind it is rather than how long it has been open.

  2. Find out why the driver matters, by sending the two kinds of message down one connection in turn.

    $ uv run python -m bench.vacuum --experiment portal
    one connection, one READ COMMITTED transaction, left open between statements:
  after fetch("SELECT 1")   extended: Parse, Bind, Execute   backend_xmin   154206   holds the horizon
  after execute("SELECT 1") simple: one Query message        backend_xmin        -   holds nothing
  after fetch("SELECT 1")   extended again                   backend_xmin   154206   holds the horizon
    Held, released, held again, by the same statement

    The protocol documentation explains it in one paragraph: “An unnamed portal is destroyed at the end of the transaction, or as soon as the next Bind statement specifying the unnamed portal as destination is issued. (Note that a simple Query message also destroys the unnamed portal.)” A portal keeps the snapshot it ran under, so while it survives, the snapshot does.

    The parenthesis is the testable part, and this step tests it. A simple query destroys the portal and the pin disappears; the next extended one creates a portal and the pin comes back. psql only ever sends simple queries. asyncpg only ever sends extended ones, which is also why it is fast: the same mechanism that caches your statements keeps your snapshot.

    The xmin is the same number twice because nothing else committed in between. On a busy server the second one would be newer.

  3. Now let it cost something. Update every row a hundred times, vacuuming after every round as autovacuum would, first with nothing held and then with one idle session open.

    $ uv run python -m bench.vacuum --experiment bloat
    NOTHING HELD   (5000 rows, 72 pages to start)
  round   pages   dead, not removable   scan buffers   scan ms
      1     143                     0            143      0.45
     10     143                     0            143      0.35
     25     143                     0            143      0.33
     50     143                     0            143      0.35
    100     143                     0            143      0.34

ONE IDLE SESSION OPEN   (5000 rows, 72 pages to start)
  round   pages   dead, not removable   scan buffers   scan ms
      1     143                  4999            143      0.43
     10     786                 49990            786      0.62
     25    1857                124975           1857      1.26
     50    3643                249950           3643      2.24
    100    7213                499900           7213      3.21
  closed   7213                     0           7213      2.07   <- the session is gone, the pages are not
  FULL       72                     0             72      0.46   <- rewrote the table in 31 ms, under an ACCESS EXCLUSIVE lock
    Flat at 143 with vacuum allowed to work; 7 213 with one session open

    The first table is the healthy case and it is worth noticing how healthy: 143 pages after one round and 143 after a hundred. Every round's dead versions are removed and their space reused by the next round. That is vacuum doing its job, and it is why most tables never need thinking about.

    The second table is the same work with one idle session. The dead column grows by exactly 4 999 a round and never falls, and the table grows fifty times over. Every sequential scan reads every one of those pages, which is why the scan column rises with it.

    Then the line that surprises people. Close the session, vacuum again, and every dead row is removed — and the table is still 7 213 pages. The scan still reads all 7 213 of them, fifty times the healthy table's 143, because empty pages are still pages. The milliseconds wobble between runs; that buffer count does not. The bloat outlives its cause. Only VACUUM FULL gets the space back, and it does that by rewriting the whole table under a lock that blocks every reader.

  4. Now the query people actually run against a results table: the latest twenty runs for one vendor. Read its plan with and without an index, and then with the horizon held.

    $ uv run python -m bench.vacuum --experiment plan
                                       scan             rows   buffers  heap fetches        ms
no index                           Seq Scan           20      1667                   8.174
(vendor_id, started_at) index      Index Scan         20        23                   0.045
covering index, vacuumed           Index Only Scan    20         4             0     0.034
after 5 batches, nothing held      Index Only Scan    20         4             0     0.022
after 5 batches, horizon held      Index Only Scan    20        44            40     0.048
  ... session closed, vacuumed     Index Only Scan    20         4             0     0.026
    Before / after · the plan is identical, the work is eleven times larger

    The first three rows are the ordinary story. Without an index the query reads all 1 667 pages to return twenty rows, and on a table that only grows, that number only grows. An index on (vendor_id, started_at) takes it to 23. A covering index, one that also carries the columns the query returns, takes it to 4 and never touches the table at all.

    Rows five and six are this lesson. The same query, the same plan — Index Only Scan, twenty rows — and forty heap fetches. The plan's name says it does not read the table. The counter says it read it forty times: once for each of the twenty live rows and once for each of their twenty dead predecessors, because vacuum could not mark those pages all-visible.

    Close the session, vacuum, and it is back to 4. Nothing about the query was wrong. Only BUFFERS could have told you anything was happening.

  5. Fix it with the setting the documentation names for exactly this, applied through the application's own pool, and then find out what the application is told.

    $ uv run python -m bench.vacuum --experiment timeout
$ docker compose logs postgres 2>&1 | grep -o 'FATAL: .*idle-in-transaction timeout' | tail -1
    idle_in_transaction_session_timeout = off (Postgres default)
  vacuum during the call: 0 removed, 4999 not yet removable
  the turn that held it: committed
idle_in_transaction_session_timeout = 2000 ms
  vacuum during the call: 4999 removed, 0 not yet removable
  the turn that held it: failed: InterfaceError: connection is closed (sqlstate None)
FATAL:  terminating connection due to idle-in-transaction timeout
    Vacuum proceeds, and the transaction that held the line is the one that pays

    The turn is lesson 0017's bug: read, then a 3.6 s model call with the transaction still open. With the timeout off, vacuum removes nothing during the call and the turn commits normally, so nobody would ever connect the two. With it at two seconds, vacuum removes all 4 999, and the turn fails.

    Read what it fails with. connection is closed, with no SQLSTATE and no mention of a timeout. The reason exists only in the server log, the second command’s output. An on-call engineer looking at the application's error rate sees connections dropping and starts suspecting the network.

    The setting is in app/db/pool.py as PoolSpec.idle_in_tx_timeout_ms and in Settings as DB_IDLE_IN_TX_TIMEOUT_MS. It defaults to 0 so no earlier lesson changes. The value has to be longer than the longest await you intend to hold a transaction across, which is a reason to have none.

  6. Finally run the tests, one of which checks the documentation's parenthesis rather than trusting it.

    $ uv run pytest tests/test_horizon.py -q 2>&1 | tail -1
    14 passed in 0.45s
    Six of the fourteen are one test, and two of those six must hold nothing

    test_which_open_transactions_hold_the_horizon runs step 1's table as six parametrised cases. Two of them assert that the transaction holds nothing, which is what makes the other four worth believing: a check that only ever expects a pin would pass against a probe that reported one for everything.

    test_a_simple_query_releases_the_snapshot_an_extended_one_took is step 2 as an assertion. If the portal were not what holds the snapshot, its middle assertion would fail. And test_the_heap_line_is_read_not_the_toast_line exists because VACUUM VERBOSE reports the table and then its TOAST table, and reading the wrong line reports a healthy vacuum off an empty relation.

Underneath

One layer down · what vacuum is allowed to remove

Four things. The first is the rule vacuum follows, the second is what actually holds it back, the third is how to see it in a plan, and the fourth is why fixing it does not give the space back.

Vacuum follows one rule, and one session sets it for everyone

The vacuuming chapter states the rule in a clause: “the row version must not be deleted while it is still potentially visible to other transactions.” Potentially is the word doing the work. Postgres does not track which session could see which version; it tracks the oldest snapshot still open, and treats everything newer than that as potentially visible to it.

That makes the horizon a single number for the whole cluster, not per table. A session reading the vendors table holds back vacuum on eval_runs, because a snapshot is a view of every table at once. The idle_in_transaction_session_timeout entry says so directly: “Even when no significant locks are held, an open transaction prevents vacuuming away recently-dead tuples that may be visible only to this transaction; so remaining idle for a long time can contribute to table bloat.”

The growth is arithmetic, so the table size is predictable before you measure it:

rows 5 000, rows per page 5 000 / 72 pages = about 69 each round leaves dead 4 999 rows / 69 = about 72 pages with the horizon held 143 + 99 rounds x 72 = about 7 270 pages measured 7 213 pages with vacuum allowed steady at 2 x 72 = 143 pages

Within one per cent, and the shape is the useful part: held, the table grows linearly with your write rate multiplied by how long the session stays open. At a thousand updates a second, an hour-old notebook is 3.6 million dead rows. The healthy case settles at about twice the live size, because each round reuses the space the previous round's dead versions freed.

What holds the horizon is the snapshot, not the transaction id

Two separate things can pin it, and pg_stat_activity has a column for each. backend_xid is a transaction id, assigned only when a transaction writes or locks a row. backend_xmin is the snapshot it is still using. Either one is enough, and a read-only transaction that never gets an id can still hold a snapshot — which is the case people miss, because “read-only” sounds free.

The protocol is what decides whether a finished statement's snapshot is still held. The extended protocol runs a statement through a portal, and the documentation is precise about how long one lives: “An unnamed portal is destroyed at the end of the transaction, or as soon as the next Bind statement specifying the unnamed portal as destination is issued. (Note that a simple Query message also destroys the unnamed portal.)”

Six ways to leave a transaction open, measured in step 1:

transaction left open xid xmin stops vacuum BEGIN, nothing - - no BEGIN; SELECT (psql) - - no BEGIN; SELECT (asyncpg) - set yes the portal keeps it BEGIN; SELECT ... FOR UPDATE set set yes BEGIN; UPDATE (simple) set - yes the id alone is enough BEGIN REPEATABLE READ; SELECT - set yes by definition

Rows two and three are one statement and differ only in the message that carried it. The practical consequence: under async SQLAlchemy, every transaction that has read anything holds the horizon until it ends. The rule that follows is lesson 0017's, arriving for a third reason — a transaction held across an await costs a pooled connection, every row lock it took, and vacuum for the whole database.

A plan tells you what it did; BUFFERS tells you what it cost

The query in step 4 kept one plan throughout, and the reason an index-only scan can read the table is stated in the index chapter: “If it's set, the row is known visible and so the data can be returned with no further work. If it's not set, the heap entry must be visited to find out whether it's visible, so no performance advantage is gained over a standard index scan.” The bit is the visibility map's, and only vacuum sets it.

So a held horizon does two separate things to one query. It leaves dead versions for the index to step over, and it stops vacuum marking pages all-visible, which silently turns an index-only scan back into an ordinary one. Neither changes the plan's name. The documentation's own advice for this, “The numbers provided by BUFFERS help to identify which parts of the query are the most I/O-intensive”, is the whole diagnostic.

The same twenty rows, four ways, from step 4:

state plan buffers heap fetches no index Seq Scan 1 667 - covering index, vacuumed Index Only Scan 4 0 horizon held, 5 batches Index Only Scan 44 40 closed, then vacuumed Index Only Scan 4 0

Forty is exactly two per row returned: each live row and its dead predecessor. The name of the plan is a promise about what it can skip, and the counters are what it actually skipped. Read the second, and add BUFFERS to every EXPLAIN ANALYZE you run, because without it this row and the one below it look identical.

Vacuum reclaims space; it does not return it

This is the part people get wrong after they have fixed the cause. The vacuuming chapter is explicit that plain vacuum “will not return the space to the operating system, except in the special case where one or more pages at the end of a table become entirely free and an exclusive table lock can be easily obtained.” The space is reused by future rows in the same table, which is fine for a table that will grow back into it and useless for one that will not.

Getting it back means rewriting the table, and the chapter prices that too: “VACUUM FULL requires an ACCESS EXCLUSIVE lock on the table it is working on, and therefore cannot be done in parallel with other use of the table,” and it needs extra disk “approximately equal to the size of the table” while it runs. Thirty milliseconds on 7 213 pages here; on a production results table, an outage. For a table that only grows and is never pruned, the structural answer is to partition it by time, and the partitioning chapter names this exact benefit: dropping a partition “is far faster than a bulk operation. These commands also entirely avoid the VACUUM overhead caused by a bulk DELETE.”

Which lands on the sentence worth keeping: vacuum can only clean up to the oldest open snapshot, and under your driver any read in an open transaction is one. Keep transactions short, bound the idle ones, and watch how far behind the oldest session is rather than how long it has been open.

Check yourself

A worker using async SQLAlchemy begins a READ COMMITTED transaction, runs one SELECT, then awaits a model call for an hour. What stops vacuum from removing dead rows in other tables?

  1. The snapshot its unclosed portal keeps
  2. A shared lock its SELECT holds
  3. The transaction id it got first
  4. Autovacuum skips any table being read

The snapshot. asyncpg sends every statement through the extended protocol, which leaves an unnamed portal open until the next Bind or the end of the transaction, and a portal keeps the snapshot it ran under. So backend_xmin stays set for the whole hour, and the horizon is one number for the whole database, so every table is held back, not just the one it read.

The distractors are each a real mechanism that is not the one at work. A plain SELECT takes no row lock. A read-only transaction is never given an id at all — which is exactly why people assume it is harmless. Autovacuum does run; step 3 showed it running and removing nothing.

The idle session is closed and VACUUM runs again. It removes every dead row, and the table is still 7 213 pages instead of 143. Why?

  1. Plain vacuum marks space reusable and keeps the file
  2. Autovacuum has not yet visited the table since then
  3. The index still points into pages that held them
  4. Statistics stay stale until the next ANALYZE has run

Plain vacuum reclaims space inside the table for future rows; it does not shrink the file, except for empty pages at the very end when it can take a lock easily. After the session closed, the scan in step 3 still read all 7 213 pages against the healthy table's 143, because empty pages are still pages.

Getting the pages back takes VACUUM FULL or another rewrite, under an ACCESS EXCLUSIVE lock that blocks reads for the duration. That is why the fix for a table that only grows is structural — partitions you drop — rather than a better vacuum schedule.

Say it out loud · about 75 seconds

A spoken answer to “your results table keeps growing even though autovacuum is on — what do you look at?” Read it aloud, then say it again with the page covered.

  1. Situation

    Every eval run is a row inserted as running and updated when it finishes, and nothing is ever deleted. So every run leaves one dead version for vacuum.

  2. Mechanism

    Vacuum may only remove a version no open snapshot could still see. So the oldest open snapshot anywhere is a line nothing newer crosses, in any table.

  3. What I did

    I held one idle session under our driver, asyncpg. One plain SELECT in READ COMMITTED was enough, because the extended protocol keeps its portal and the portal keeps the snapshot.

    Vacuum removed none of 499 900 dead rows and the table went from 143 pages to 7 213. The plan never changed. Only the BUFFERS line showed it.

  4. What it cost

    The fix is an idle-in-transaction timeout, and it kills the transaction that held the line. The client just sees a closed connection.

    And the pages stay afterwards. Getting them back means a full rewrite under an exclusive lock, so the real fix is partitioning the table by time.

The sentence that sounds fluent and gets you caught

“It's a read-only transaction, so it can't be holding anything back.” The received answer, and it is half true: a read-only transaction never gets a transaction id. What vacuum respects is the snapshot, and under asyncpg a finished SELECT keeps one for as long as the transaction stays open. The follow-up is “what does backend_xmin say for that session?”, and if you have not looked, the position is a guess. The version that holds: “any open transaction that has read anything, under the extended protocol, holds the horizon until it ends.”

The second trap is “once we closed the session, vacuum cleaned it up.” It removed the rows and kept the pages. If the interviewer asks what the table's size did afterwards, the answer is nothing, and saying so is the part that sounds like you have seen it happen.

Probes to expect

  1. “Autovacuum is on and the table still grows. Why?” The opening question, and the weak answer tunes autovacuum. The strong one asks what vacuum is not being allowed to remove.
    Model answer — say yours first

    The first thing I would check is not autovacuum's settings but whether it is allowed to remove anything. VACUUM VERBOSE prints a line saying how many rows are “dead but not yet removable” and how old the removable cutoff is. If that number is large, autovacuum is running fine and being held back by an open snapshot somewhere.

    In the lab, one idle session was enough to keep 499 900 dead rows unremovable and grow a table from 143 pages to 7 213, with autovacuum's work being done after every round. Tuning its thresholds would have made it run more often and remove exactly as little.

    Invites · “How do you find the session?” — pg_stat_activity, sorted by how far behind backend_xmin is.
  2. “It's only a SELECT. How can it block vacuum?” Stated as disbelief, and the expected answer is “REPEATABLE READ”. The better one names the protocol, because it applies to READ COMMITTED too.
    Model answer — say yours first

    Because what vacuum respects is the snapshot, not locks and not transaction ids. Under READ COMMITTED people expect the snapshot to be dropped when the statement ends, and under psql it is. Under asyncpg it is not: the extended protocol runs the statement through a portal, and the documentation says an unnamed portal lives until “the end of the transaction, or as soon as the next Bind”. The portal keeps its snapshot.

    I checked that rather than inferring it. The same parenthesis says a simple query destroys the portal, so I sent one down the same connection: the pin disappeared, and came back with the next extended statement. So under async SQLAlchemy, any transaction that has read anything holds the horizon until it commits.

    Invites · “So what do you change?” — shorter transactions first; a timeout second, as the backstop.
  3. “How would you find the session that is doing it?” Practical, and the trap is sorting by duration. A long-running query that took its snapshot a second ago is not the problem.
    Model answer — say yours first

    pg_stat_activity, filtered to sessions where backend_xmin or backend_xid is set, and sorted by age() of those rather than by xact_start. Age counts the transactions committed since the snapshot was taken, which is what predicts the bloat. A report that has been running for an hour but refreshed its snapshot a second ago is less harmful than a notebook idle since lunch.

    The one to recognise is idle in transaction with a last query that is a finished SELECT. That is exactly what it looked like in the lab: fifty transactions behind after one second. And the same view is not the only place: a replica with hot_standby_feedback on pins the primary's horizon from another machine, and shows up in pg_stat_replication instead.

    Invites · “What else pins it?” — replicas with feedback on, and replication slots. Lesson 0020 measures the first.
  4. “Would you set idle_in_transaction_session_timeout? To what?” A yes is expected. What is being tested is whether you know what it kills and what the application sees when it does.
    Model answer — say yours first

    Yes, on the application's own connections rather than server-wide, and above the longest await we intend to hold a transaction across — which, after moving model calls out of transactions, is none. So something like ten seconds: far above a legitimate gap between statements and far below a forgotten session.

    The part worth saying is what it costs. In the lab the timeout let vacuum remove all 4 999 rows, and the held turn failed with connection is closed and no SQLSTATE. The reason is only in the server log. So it has to ship with the application recognising that failure, or it looks like a network problem to whoever is on call.

    Invites · “What about a long report query?” — that is statement_timeout or transaction_timeout; this one only fires while idle.
  5. “The table is already bloated. How do you get the space back?” The trap is “run VACUUM”. The follow-up after that is always “and did the table get smaller?”
    Model answer — say yours first

    Plain vacuum will not do it. It removes the dead rows and marks the space reusable inside the table, and the documentation is explicit that it “will not return the space to the operating system” except for empty pages at the very end. In the lab, after the session closed and vacuum ran, the table was still 7 213 pages with zero dead rows.

    Getting it back means rewriting the table: VACUUM FULL, which takes an ACCESS EXCLUSIVE lock and roughly the table's size again in disk while it runs, or an online rewrite tool. For a results table that only grows, I would not want to be doing either on a schedule. I would partition it by time, so retention is dropping a partition — which removes a file and leaves nothing to vacuum.

    Invites · “Why not just DELETE old runs?” — because a DELETE is more dead rows, and vacuum is what just failed.

Recall — from lessons 0016–0018

0016 showed an UPDATE leaving two row versions on disk, one visible. Which transaction decides when the invisible one can go?

None of the ones involved in the update. The old version stays until no open snapshot anywhere could still see it, so the transaction that decides it is whichever one is oldest in the whole database, reading any table at all. That is the step from 0016 to this lesson: 0016 established that an update is an insert plus a tombstone, and this one shows that the tombstone's lifetime is set by a stranger. It also explains why 0016's readers could be so relaxed about writers — “reading never blocks writing” is true, and the bill for it is paid here, in versions that have to be kept for as long as any reader might want them. A long REPEATABLE READ transaction in 0016 was a correctness tool; left open, it is a vacuum problem for every table.

lesson 0016 · an UPDATE is an insert plus a tombstone
0017's transaction across an await cost two things. This lesson found a third. What are all three?

A pooled connection, held for the length of the call, which is what dropped throughput from 5.5 turns a second to 4.0 even with a row per worker; every row lock the transaction had taken, which is what dropped it to 0.9 on a shared row; and now the vacuum horizon for the entire database, because under asyncpg the SELECT that began the transaction left a portal holding its snapshot. The third is the worst of the three because it is invisible where the other two are not: a held connection shows up as pool wait, a held lock shows up as lock wait, and a held snapshot shows up as a table getting slowly bigger weeks later, in a table the transaction never touched. The fix is the same for all three — move the call out of the transaction — which is a good argument for doing it even where the first two costs look affordable.

lesson 0017 · the await inside the transaction
0018's atomic SET score = score + 1 was twelve times faster than the lock. Does it produce less for vacuum to clean up?

No, and it is worth being exact about why. Every UPDATE writes a new row version and leaves the old one dead, whether it read first or not, so the atomic write leaves exactly as many dead versions as the read-modify-write did. What it changes is how long the transaction is open: one statement, a few milliseconds, then gone. So it does not reduce the garbage, it lets the horizon move past the garbage sooner, which is what makes it collectable. The strategy that genuinely produces more work for vacuum is optimistic locking under contention, because every one of the 120 conflicting attempts was a transaction that started, and every one that got as far as writing left something behind. The general point: vacuum's load is the write rate, and its ability to keep up is the oldest open transaction, and those are two different numbers to watch.
