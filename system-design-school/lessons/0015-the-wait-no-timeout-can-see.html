The Wait No Timeout Can See

Five connections is SQLAlchemy's default and nobody chose it. Under forty concurrent requests it adds 660 ms to the tail of every call while the database stays idle and every query stays fast — and not one timeout in your code is able to see it. Then a proxy in front of it breaks your driver in a way that reads like a driver bug and is not.

The win

Take request p99 from 1 947 ms to 112 ms without touching a single query — the query time is identical in every row of the table. Then put a transaction pooler in front and watch eleven of twelve clients fail with prepared statement "__asyncpg_stmt_d__" does not exist, and fix it twice: once in the driver, once in the proxy, with a measured price for each.

Why you, specifically
“Python/FastAPI, async SQLAlchemy, PostgreSQL, GKE” — and the deployment claims spread across the experience bullets: Cloud Run with IAP, Helm, Terragrunt, Cloud Build.

That stack line is four words long and it contains this entire lesson. Async SQLAlchemy over asyncpg is the exact combination where pooling bites, because async code raises concurrency by one or two orders of magnitude and leaves the pool at five. A threaded application with twenty workers could never ask for more than twenty connections; an async one asks for as many as there are requests in flight.

The deployment half makes it worse in a way that is arithmetic rather than opinion. Every replica carries its own pool, so the number Postgres has to satisfy is pool size times replica count, and horizontal scaling multiplies it. That is the moment somebody puts a pooler in front, and the second half of this lesson is what happens next.

The claim is defended in full in chapter 0011 of Résumé Mastery. This lesson is where the two numbers underneath it get measured.

Start here — the plain version

A database connection is expensive to create and cheap to keep, so applications keep a handful open and lend them out. That collection is a pool, and the lending is the whole subject: when they are all out, the next caller does not fail and does not proceed. It waits, in a queue that exists inside your own process.

There are up to three of these queues between your code and a row on disk, each with its own limit, and an answer that names only one of them is the answer of somebody who has read about pools rather than run out of connections.

Checkout
Taking a connection from the pool. The part that can block, and the part that appears in no query log anywhere.
pool_size
How many connections are kept open. SQLAlchemy's default is 5, which is a number you inherited rather than chose.
max_overflow
Extra connections opened under load and discarded afterwards. Default 10, so the real ceiling is fifteen.
pool_timeout
How long a caller waits before giving up. Default 30 s — four times this system's entire turn budget, so it never fires.
Transaction pooler
A proxy that lends server connections to client connections, so many application instances can share few backends. PgBouncer is the usual one.
Prepared statement
SQL parsed and planned once on the server, then executed many times by name. Fast, and attached to one server connection.
Statement cache
The driver remembering which statements it has prepared. asyncpg keeps one, and so, separately, does SQLAlchemy's dialect.
max_connections
Postgres's own ceiling, default 100. Every pool in every replica is spending from it, and it is the only one of the three that is shared.

The queue nobody put in the design

An async request handler that touches the database does four things: it asks the pool for a connection, runs its query, returns the connection, and answers. Only the second of those appears in any database instrument. The first one is where the time goes.

This is worse than an ordinary hidden cost, because it is hidden in the direction that makes it look like somebody else's fault. The query log says every query was fast. pg_stat_statements agrees. CPU on the database is low and the connection count is flat at five, because five is all it is allowed to be. Every instrument you have is reporting a healthy database, and it is right. The queue is in your process, in front of it.

Why no timeout in the request path catches this

Lesson 0012 put a deadline on every stage and propagated what was left of it. That deadline is checked around the call, and the call has not started: the coroutine is suspended inside engine.connect(), waiting for somebody else to finish. A stage timeout of 1 600 ms fires 1 600 ms after the connection was obtained, not after it was requested.

The pool has its own timeout, and it defaults to thirty seconds against an eight-second budget. So the bound exists, is above every other bound in the system, and is therefore dead code. The request dies of its deadline and the deadline gets the blame.

In plain words

The drawing has two halves. On top, each bar is one pool size under the same forty requests: the part that shrinks is time spent waiting in line for a free connection, and the part that never changes is the database doing the work. Underneath, a middleman program (the proxy) gives each transaction, one unit of database work, whichever server connection is free. So a query the driver prepared and saved on one connection is missing when the next transaction lands on another.

Lab — take 1 947 ms to 112, then break the driver

Lab 0015 ~30 minutes

A pool sweep, a bound that is dead code, and a proxy that forgets

  1. Start both services and confirm each one published a port, because a failure later should be a finding rather than a collision.

  2. Sweep the pool size against a fixed load, and keep the wait and the query as separate columns. That separation is the entire experiment.

    40 concurrent requests, 4 queries each, 20 ms per query.
'waited' is time spent queueing for a connection, before the database
was asked anything. No query log contains it.

 pool   p50 wait   p99 wait   p50 query   p99 total    req/s  predicted
    2       959ms      1853ms         97ms       1947ms     20.5       20.7
    5       363ms       666ms         91ms        755ms     52.9       55.2
   10       187ms       293ms         92ms        384ms    103.3      108.8
   20        94ms       105ms         94ms        194ms    202.5      212.5
   40         0ms         0ms        110ms        112ms    351.6      363.2
    The query column does not move

    Read the table by column rather than by row. p50 query is 97, 91, 92, 94, 110 — flat, and the last one is the largest. The database did the same work at the same speed in every row. Meanwhile p99 total falls from 1 947 ms to 112, a factor of seventeen, and every millisecond of that came out of the wait column.

    The row to sit with is pool 5, because that is the default and therefore what you are running unless you changed it. At the default, the median request spent 363 ms queueing and 91 ms querying — eighty per cent of the request was spent in a queue inside the application process.

    predicted is pool size divided by how long a connection is held: 5 ÷ 0.091 s = 55/s against 52.9 measured. That is not a coincidence and it is not tuning — it is Little's law, and it says your maximum throughput was decided by two numbers, one of which you never chose.

  3. In plain words

    How long should a request wait in line for a connection before giving up? The pool’s default is thirty seconds, but a whole request only gets eight, so that limit never fires and does nothing. Set it very low and it turns away requests that would have finished in time. The right limit is the time the request still has left.

    Now check the bound. The pool has its own timeout, so find out what it is worth at three settings: the default, the whole turn budget, and something smaller than the wait.

    A pool of 5 against 160 concurrent requests,
with the pool's own timeout set 3 ways.

 pool_timeout  served  refused   p99 total   slowest
        30.0s     160        0       3049ms     3050ms
         8.0s     160        0       3054ms     3055ms
         0.5s      30      130        559ms      559ms
    Before / after · and this time bounding it is the wrong answer

    The first two rows are identical, and that is the finding: setting the pool timeout to the entire turn budget changed nothing, because the wait is three seconds and the bound is eight. A limit above every other limit in the system is dead code with a configuration entry.

    The third row is the trade, and it goes the other way from lesson 0013. There, bounding the queue cost no goodput and bought the tail. Here it costs 130 of 160 requests refused to save a wait that fitted inside the budget anyway. Same mechanism, opposite verdict.

    Which gives the rule that survives both lessons: the bound belongs at what is left of the deadline when the connection is asked for, not at the budget and not at a round number. Above that it does nothing; below it you refuse work you could have finished.

  4. Now the second half. Send the same parameterised query through the proxy, which is what every deployment with more than a couple of replicas ends up doing.

    12 clients, 8 identical parameterised queries each.
The query is the same every time, which is exactly when a driver
decides to prepare it once and reuse it.

path                               cache    ok   failed   first error
postgres, direct                     100    12        0
pgbouncer, transaction pooling       100     0       12   InvalidSQLStatementNameError: prepared statement "__
pgbouncer, cache disabled              0    12        0

The driver is not broken and neither is the pooler. The statement was
prepared on one server connection and executed on another.
    Nothing changed except the port

    Same driver, same query, same database. The only difference between row one and row two is which port the client dialled. The failure count wobbles between nine and twelve of twelve across runs — the survivors are the clients that happened to keep landing on the backend where their statement was prepared, out of a pool of four.

    The third row is the fix everybody finds first: turn asyncpg's statement cache off. It works, and step 6 measures what it costs.

  5. Then fix it the other way, in the proxy rather than the driver.

    path                               cache    ok   failed   first error
postgres, direct                     100    12        0
pgbouncer, transaction pooling       100    12        0
pgbouncer, cache disabled              0    12        0
    Twelve of twelve, with the driver cache left on

    One setting in the proxy, and the middle row goes from total failure to no failures at all, keeping the performance the cache buys. PgBouncer's own documentation is plain about it: “You need to change max_prepared_statements to a non-zero value to enable this support.”

  6. Measure the price of the fix everybody reaches for first, so you can say what it costs rather than that it is free.

    400 identical queries on one direct connection, timed.
This is what the usual fix costs.

 statement cache       p50       p99      total
             100    0.156ms    0.323ms      69.2ms
    0 (disabled)    0.274ms    0.322ms     110.5ms
    Seventy-six per cent slower, on a number that is already small

    Per query it is a tenth of a millisecond, which sounds like nothing and is nothing until you count the queries. A five-stage pipeline that issues a dozen statements per stage pays this sixty times a turn, and the p99 column shows why the median is the honest one to quote here: the tail barely moves, so this is a steady tax rather than an occasional spike.

    The reason it is cheap at all is that the statement still gets parsed, just not kept — the work saved by a prepared statement is parse and plan on a query the planner finds easy. Against a query with a genuinely expensive plan the gap is much wider, and this bench is not evidence about those.

  7. Finally, run the tests for this lesson, four of which need the server and two of which do not.

    Two of them are decidable without connecting to anything

    The two that need no database are the ones about the two statement caches: one is a connect argument and the other travels in the URL, and passing the second one as a keyword to create_async_engine is rejected outright. That is the whole content of “I disabled the statement cache and it still failed”, and it is a test rather than a comment because comments do not fail.

Underneath

One layer down · three pools, and the one that forgets

There are three pools between your code and the disk

The application pool lends connection objects to coroutines. A proxy, if there is one, lends server connections to client connections. And Postgres has max_connections, which is neither of those — it is a count of backend processes, each with its own memory, which is why the answer to running out is never simply to raise it.

They fail differently, and telling them apart in an interview is most of the answer. Running out of the first is a wait with no error. Running out of the second is a wait, then query_wait_timeout. Running out of the third is an immediate, loud FATAL: sorry, too many clients already, which is the only one of the three anybody notices without looking.

The wait is invisible by construction, not by oversight

So the signature to recognise is a specific pair of facts: request latency up, query latency flat. When those two appear together, the time is being spent somewhere between them, and there are only a few places that can be — the pool, the proxy, or the event loop itself.

Little's law as a ceiling rather than an estimate, from step 2:

pool hold time ceiling = L/W measured 2 0.097 s 20.6/s 20.5 5 0.091 s 55.0/s 52.9 10 0.092 s 108.7/s 103.3 20 0.094 s 212.8/s 202.5

Every row is within five per cent, and the measured value is always the lower one, which is what you would expect from a ceiling. The useful consequence: you can compute your maximum throughput per replica before deploying anything, from two numbers you already have. If the hold time includes a model call, the ceiling is a couple of requests a second and no amount of horizontal scaling hides that.

In plain words

A transaction pooler is a middleman that lends your app a real database connection for one transaction, then takes it back and lends it to someone else. Anything the database was keeping for you on that connection, such as a prepared statement (a query parsed once and saved by name), is missing when your next transaction lands on a different connection. The fix is either to stop the driver saving statements, which costs a little time on every query, or to let the proxy keep track of them, which PgBouncer can do from version 1.22.

A transaction pooler changes what a connection remembers

Session pooling lends a backend for as long as the client stays connected, which behaves exactly like no proxy and therefore solves nothing worth solving. The documentation calls it the “most polite method”. Transaction pooling is the one people deploy: “A server connection is assigned to a client only during a transaction. When PgBouncer notices that the transaction is over, the server will be put back into the pool.”

The same twelve clients, four ways, measured:

path driver cache proxy tracks ok postgres, direct on n/a 12/12 pgbouncer, transaction pooling on no 0/12 pgbouncer, cache disabled off no 12/12 pgbouncer, max_prepared_statements=200 on yes 12/12

Two fixes, in two components, with different costs. Turning the driver cache off costs 0.156 ms → 0.274 ms per query, forever. Letting the proxy track them costs nothing per query and requires PgBouncer 1.22 or later. The sentence that sounds like knowledge and is out of date is “asyncpg does not work behind pgbouncer” — it was never a fact about the driver.

When you need a proxy is arithmetic, not judgement

The number the server has to satisfy is (pool_size + max_overflow) × replicas, and with SQLAlchemy's defaults that is fifteen per replica. Against the default max_connections of 100, with some reserved for superuser access, the seventh replica is the one that cannot start. Nothing about the traffic changed; the deployment got wider.

What each number is actually for:

number owned by what it protects pool_size your process the database, from you max_overflow your process a burst, briefly and expensively pool_timeout your process nothing, at its default default_pool_size the proxy the database, from all of you max_connections the server the machine's memory

Only the last row is shared, and it is the one none of the others can see. That is the structural point: every pool is sized locally against a limit that is global, which is why this breaks on a deploy rather than under load.

Which lands on the sentence worth keeping: a connection pool is a queue, and you chose its latency when you chose its size. The database was never the bottleneck in any row of that table, and no instrument pointed at the database could have told you.

Check yourself

A pool of five against forty concurrent requests. The median query took 91 ms and the median request took 454 ms. Where did the other 363 ms go?

  1. Waiting for a connection, before any query ran
  2. Inside the database, which slowed under the load
  3. In the network between the pool and Postgres
  4. Parsing the statement again on every single call

Queueing for a connection, inside the application process. The query column across the whole sweep is 97, 91, 92, 94, 110 ms — flat, with the largest value in the fastest row. The database did identical work at identical speed while the request p99 moved by a factor of seventeen.

This is why the pair of facts matters more than either one: request latency rising while query latency stays flat locates the problem between them. Every database-side instrument agrees the database is healthy, and every one of them is correct.

Twelve asyncpg clients through pgbouncer in transaction mode fail with prepared statement "__asyncpg_stmt_d__" does not exist. What is actually wrong?

  1. Nothing broke; the statement moved between server connections
  2. The asyncpg driver caches statements far too aggressively
  3. Postgres cannot prepare statements behind any connection proxy
  4. Twelve clients simply overwhelmed a four-connection server pool

Both components did exactly what they document. The driver prepared the statement on the backend it was given; the proxy took that backend back at the end of the transaction and handed the client a different one for the next. The error message is literally true — on that connection, the statement does not exist.

There are two fixes and they live in different components: statement_cache_size=0 in the driver, which costs about 0.1 ms per query forever, or max_prepared_statements in the proxy, which costs nothing and needs PgBouncer 1.22 or later. Knowing there are two is the part that is worth having.

Say it out loud · about 75 seconds

A spoken answer to “you run async SQLAlchemy over Postgres — what is your pool size and why?” Read it aloud, then say it again with the page covered.

  1. Situation

    Async code raises concurrency by an order of magnitude. The pool default stays at five, and nobody chose it.

  2. Mechanism

    A pool is a queue. When it is empty the caller waits, and that wait happens before any query is sent.

    So no query log records it. Neither does the stage timeout, because the call has not started yet.

  3. What I did

    I swept the pool size against fixed load and kept the wait and the query in separate columns.

    At the default, the median request spent 363 milliseconds queueing and 91 querying. The query column was flat in every row.

    I size it from Little's law now: pool divided by hold time. Five over ninety-one milliseconds predicted 55 a second, and 53 arrived.

  4. What it cost

    Every replica carries its own pool, so the server sees pool times replicas. Fifteen each against a hundred means the seventh deploy fails.

    That is when a transaction pooler goes in, and it breaks prepared statements. Two fixes: the driver's cache, or the proxy tracking them.

The sentence that sounds fluent and gets you caught

“We use connection pooling, so connections aren't an issue.” This says you have a pool, which you got for free, and nothing about its size. The follow-up is “what happens when it is empty?”, and if the answer is a shrug the next one is worse. The version that holds names the behaviour and the number: “it queues rather than failing, so we size it from Little's law and put the timeout on what is left of the request deadline rather than on thirty seconds.”

The other trap is answering the proxy question from memory. “asyncpg doesn't work behind pgbouncer” is repeated constantly, was only ever true of one pooling mode, and stopped being true in PgBouncer 1.22. If you say it, expect to be asked which mode and which version, and to discover that the person asking runs both.

Probes to expect

  1. “What is your connection pool size, and where did the number come from?” Almost always asked as small talk and almost never followed up when the answer is a number with a reason. It is a cheap way to find out whether you have ever run out of connections.
    Model answer — say yours first

    It comes from Little's law: the pool is the concurrency limit, so the ceiling is pool size divided by how long a connection is held. I measured the hold time at about 91 ms for our read path, so five connections caps a replica at roughly 55 requests a second, and 53 is what arrived.

    The reason it matters more in an async service is that nothing else limits the requests in flight. A threaded app with twenty workers can never ask for a twenty-first connection; an async one asks for as many as there are requests, so the pool becomes the queue. At the default of five under forty concurrent requests, eighty per cent of the median request was spent waiting for a connection and the query time never moved.

    Invites · “So why not make it enormous?” — because every connection is a Postgres backend process, and the limit is shared across replicas.
  2. “Request latency is up but every query is fast. Where do you look?” The diagnostic version, and the one that separates people who have read about pools from people who have been paged about one. The pair of facts in the question is the clue.
    Model answer — say yours first

    Between the two, and there are only a few candidates: the connection pool, a proxy, or the event loop being blocked. I would measure checkout time directly, because nothing measures it by default — time the call that acquires a connection, separately from the query.

    The reason it hides so well is that it is on the wrong side of every database instrument. The query log has no statement to record, pg_stat_statements has no execution, and the connection count is flat at the pool size, which reads as stable rather than saturated. Even the per-stage timeout misses it, because that wraps a call which has not started. I have measured this one: 363 ms of a 454 ms request, with the database idle.

    Invites · “How would you have alerted on it?” — on the ratio of request time to query time, not on either alone.
  3. “You have six replicas. How many connections is that, and is it a problem?” Arithmetic, and the answer is expected to be immediate. Getting it wrong slowly is worse than getting it wrong fast.
    Model answer — say yours first

    Fifteen per replica at SQLAlchemy's defaults, because the ceiling is pool_size plus max_overflow, so ninety. Against a default max_connections of 100 with a few reserved for superusers, the seventh replica is the one that cannot start — and it fails at deploy time rather than under load, which is why it surprises people.

    The fix is not a bigger max_connections, because each connection is a backend process with its own work memory, so you are trading a hard limit for a memory ceiling and a slower server. It is a transaction pooler, which decouples client connections from server connections — two hundred clients over four backends in the configuration I have been running. That has its own cost, which is the next question.

    Invites · “What does the pooler break?” — anything the server remembers between transactions.
  4. “What breaks when you put pgbouncer in transaction mode in front of an app?” Checks whether you understand the mechanism or have memorised a list. The mechanism produces the list; the list does not produce the mechanism.
    Model answer — say yours first

    Anything the server remembers between transactions, because a backend is lent for one transaction and then handed to somebody else. That is prepared statements, session-level SET, temporary tables, LISTEN/NOTIFY and session-scoped advisory locks — and the list falls out of the one sentence rather than needing to be memorised.

    Prepared statements are the one you hit first, because a fast driver creates them without being asked. I measured it: twelve asyncpg clients through a transaction pooler, and nine to twelve of twelve fail per run with “prepared statement does not exist”. The survivors are the ones that happened to land back on the same backend, which is exactly the variability that gets it filed as a flake in staging.

    Invites · “How do you fix it?” — in the driver or in the proxy, and the two have different prices.
  5. “Would you bound the wait for a connection, and at what?” Looks like a tuning question and is a design one. There is a wrong answer that sounds careful, which is to set it to the request budget.
    Model answer — say yours first

    At what is left of the request deadline when the connection is asked for, not at the budget. I measured all three: the default of thirty seconds and a bound set to the whole eight-second budget produced identical results — 160 of 160 served, p99 about three seconds — because the wait was shorter than either. A bound above every other bound in the system is a configuration entry with no behaviour.

    And bounding it too tightly is worse than not bounding it. At half a second the same run refused 130 of 160 requests that would have finished comfortably inside the budget. That is the opposite verdict from the load-shedding lesson, and the thing that distinguishes them is whether the queued work is already dead: there the queue was deeper than the budget, so refusing cost nothing.

    Invites · “So how do you know what's left?” — you propagate it, which is the deadline object from two lessons ago.
