The Update That Was Never Refused

Eight writers each add one to the same number. The answer is one, every writer reported success, and nothing anywhere raised an error. Raising the isolation level does not fix that — it converts a silent wrong answer into a loud one you now have to handle, and there is a third failure that the strongest level catches and the middle one does not.

The win

Lose seven of eight updates with no error raised anywhere, then watch REPEATABLE READ refuse seven of them instead and still return one. Write the retry loop that actually fixes it, then break that by running sixteen writers against a retry budget of eight — exactly eight survive. Finally find the anomaly that snapshot isolation is structurally unable to see.

Why you, specifically
“Prototyped an AI companion for dementia patients (MemGPT), implementing short- and long-term memory management for memory-grounded routine reminders across multi-session conversations.”

“Across multi-session conversations” is the phrase that puts this lesson in that project. Two sessions with the same patient, overlapping in time, both reading a memory record and both writing it back. A memory system with three tiers has three different write policies, and the one that promotes a fact from short-term to long-term is a read-modify-write on a row somebody else is also editing.

The failure mode is the one this lesson measures and it is specific to that domain: a promoted memory is not lost loudly. It is simply not there next session, and nothing in the logs says why. For a companion whose entire value is remembering, a silently dropped write is the worst available bug — it is indistinguishable from the model having forgotten.

The claim is defended in full in chapter 0015 of Résumé Mastery. This lesson is where the concurrency underneath it gets reproduced.

Start here — the plain version

Two things happening at once on one row have to be ordered somehow, and there are only two ways to do it: make one wait, or let both proceed and deal with the consequences. Postgres almost always chooses the second, which is why readers never block and why an update you thought you made can vanish.

Isolation levels are not a dial from “fast” to “safe”. They are a choice about what the database refuses. A weaker level refuses nothing and hands you a wrong answer; a stronger one refuses the transaction and hands you an error to retry. Neither is free and only one of them is honest.

MVCC
Multiversion concurrency control. Every update writes a new version of the row rather than overwriting it, so readers can carry on seeing the old one.
ctid
A row version's physical address. It changes on every update, which is how you can watch a new version being written.
xmin (on a row)
The transaction that created this version. Compare it against your snapshot and you have the whole visibility rule.
Lost update
Two read-modify-writes where the second overwrites the first with a value computed before it. Nothing fails; the number is just wrong.
Non-repeatable read
Reading the same row twice in one transaction and getting different answers, because somebody committed in between.
Phantom read
The same query matching a different number of rows the second time. A non-repeatable read about a set rather than a row.
Snapshot isolation
What Postgres calls REPEATABLE READ. One snapshot for the whole transaction, and a conflict check on what you wrote.
40001
serialization_failure. Not a bug report — an instruction to run the whole transaction again.

Nothing failed, and the answer is wrong

The code is three lines and every one of them is ordinary. Read the current score. Add one. Write it back. Two workers doing that at the same time both read the same value, both add one to it, and both write the same result. One update is gone and the database has no opinion about it, because from where it is standing two transactions each wrote a number and both writes succeeded.

Why raising the isolation level is not the answer, only the first half of it

At REPEATABLE READ the same eight writers produce a final value of one as well — but seven of them now fail with 40001 instead of quietly succeeding. Nothing has been fixed yet. What has changed is that the database is now telling you, and an application that does not catch that error has traded a silent wrong answer for an error rate.

The fix is the retry loop you write next, and the documentation says so in one sentence: “Applications using this level must be prepared to retry transactions due to serialization failures.” The level is half the change. The half nobody quotes is in your code.

In plain words

Postgres never changes a row in place: an update writes a new copy and leaves the old one, so readers never wait for writers. Which copy a reader sees depends on its snapshot, the list of whose changes it is allowed to see. Read committed takes a new one for every statement; repeatable read keeps one for the whole transaction. The levels then differ in what they refuse: nothing, a clashing write, or a read that someone else’s write made out of date.

Lab — lose seven of eight, then find out who was refused

Lab 0016 ~30 minutes

A snapshot you can read, a level that lies, and a retry loop with a budget

  1. Start Postgres and look at what a snapshot actually is, with two readers at different levels watching one writer.

    $ cd anchor/vendor-eval-gateway
$ docker compose up -d postgres
$ uv run python -m bench.isolation --experiment mvcc | head -19
    One row, one writer, and two readers at different isolation levels.
Nothing below is a lock. xmin:xmax:in-flight is the whole of what a
transaction is allowed to see.

reader   READ COMMITTED
         id before its first read: none -- reads do not get one
         snapshot 6697:6697:, sees ctid (0,11) score 0
writer   updates the row and has NOT committed
reader   still ctid (0,11), score 0 -- and it never waited
writer   commits
reader   now ctid (0,12), score 7  <- a different row version

reader   REPEATABLE READ
         id before its first read: none -- reads do not get one
         snapshot 6699:6699:, sees ctid (0,12) score 7
writer   updates the row and has NOT committed
reader   still ctid (0,12), score 7 -- and it never waited
writer   commits
reader   now ctid (0,12), score 7  <- unchanged
    The address changes, and only one reader notices

    Three things to take from this. First, ctid moves from (0,11) to (0,12): the update wrote a new physical row and left the old one in place. Second, both readers saw the old value while the writer was uncommitted, and neither waited — the documentation's claim that “reading never blocks writing and writing never blocks reading” is not a slogan, it is what you are looking at.

    Third, and the one people miss: the read-only transaction reports no transaction id at all until something asks for one. Ids are assigned lazily to transactions that write, which is why a long-running report is cheaper for the transaction counter than it looks — and why asking for the id, as this bench does, is the act that creates it.

  2. Ask for the one isolation level the SQL standard says permits a dirty read, and find out what each layer does with the request.

    Asking for the one level the standard says allows a dirty read.

via SQLAlchemy: refused -- Invalid value 'READ UNCOMMITTED' for isolation_level.
via raw SQL:    accepted, and the server reports 'read uncommitted'

writer set the row to 42 and has NOT committed
reader at 'read uncommitted' sees: 0

The level was named, accepted, reported back, and ignored. A dirty
read has nowhere to happen under MVCC: an uncommitted row version is
not visible to anybody else, so there is nothing there to read.
    Refused by one layer, accepted and ignored by the other

    Two different refusals, and the second is the interesting one. SQLAlchemy will not let you name the level; Postgres accepts it, reports it back when asked, and behaves as READ COMMITTED anyway. A configuration audit that greps for the setting finds it and passes.

    The reason is structural rather than a decision: under MVCC an uncommitted row version is not visible to any other transaction, so there is no mechanism by which a dirty read could occur. Three of the four standard levels are implemented because the fourth has nothing to implement. That is a much better answer than reciting the table.

  3. Now the failure. Eight writers, one row, each adding one, with a gap between reading the value and writing it back.

    8 concurrent writers, each adding 1 to the same score,
with a 50 ms gap between the read and the write.
The correct answer is 8.

isolation level            final applied  lost refused  what the application has to do
READ COMMITTED                 1       8     7       0  nothing -- and that is the problem
REPEATABLE READ                1       1     0       7  catch 40001 and run it again
SERIALIZABLE                   1       1     0       7  catch 40001 and run it again
REPEATABLE READ + retry        8       8     0       0  this is that loop, and it is the fix
    Row one: eight successes, seven lost, zero errors

    Read the first row slowly. Every writer applied. Nothing was refused. Seven updates are gone. There is no log line to search for, no exception to catch, and no metric that moves — the write succeeded, it was simply overwritten by a value computed before it.

  4. In plain words

    A retry loop only helps if it is allowed enough tries. When writers fight over one row they win one at a time, so the last of sixteen has to lose fifteen times first. With a limit of eight, the last eight writers give up and their updates vanish without an error. The limit has to be at least the number of writers that can collide; if that number has no ceiling, the writers have to stop fighting over the row.

    Then break the fix. Double the writers without touching the retry budget, which defaults to eight.

    $ uv run python -m bench.isolation --experiment lost --writers 16 | sed -n '6,9p'
    READ COMMITTED                 1      16    15       0  nothing -- and that is the problem
REPEATABLE READ                1       1     0      15  catch 40001 and run it again
SERIALIZABLE                   1       1     0      15  catch 40001 and run it again
REPEATABLE READ + retry        8       8     0       8  this is that loop, and it is the fix
    Before / after · exactly eight survive, and eight is the retry budget

    Not approximately eight. Exactly eight, on every run. Under total contention the writers succeed one at a time, so the n-th writer has to lose n−1 times before it wins; with a budget of eight, the ninth writer and everything after it runs out of attempts and is dropped.

    So the retry count is not a robustness setting you can pick from a blog post. It has to be at least the number of writers that can contend for one row, and if that number is unbounded then a fixed retry count silently discards writes above it. Re-run with --max-retries 16 and the final value is 16.

    This is lesson 0010's arithmetic arriving in a database. There the question was how many attempts fit in a latency budget; here it is how many fit under a contention level. Both have the same shape: a retry count chosen without reference to the thing it is retrying against.

  5. Now the three classic anomalies, each run at all three levels, in one grid.

    anomaly               READ COMMITTED            REPEATABLE READ           SERIALIZABLE
non-repeatable read   CHANGED (0 then 5)        same (0 then 0)           same (0 then 0)
phantom read          CHANGED (2 then 3 rows)   same (2 then 2 rows)      same (2 then 2 rows)
write skew            BROKEN (total 1.2 > 1.0)  BROKEN (total 1.2 > 1.0)  refused (40001; stayed 0.6)

REPEATABLE READ fixes the first two and not the third, because it is
snapshot isolation: it checks what you WROTE, never what you READ.
    The cell to remember is the middle of the bottom row

    The first two rows are the table everybody has seen. The third is the one that is worth the lab. Two evaluators each check the rule total weight across this vendor must stay at or below 1.0, each find room for 0.6, and each write to a different row. Neither modified anything the other read, so there is nothing for a version check or a row lock to catch, and the invariant ends at 1.2.

    REPEATABLE READ cannot see this by construction. Postgres names it honestly — “implemented using a technique known… as Snapshot Isolation” — and snapshot isolation resolves conflicts on writes. Both transactions wrote to rows nobody else touched. SERIALIZABLE tracks read-write dependencies as well, which is why it is the only cell in that row that refuses.

Underneath

One layer down · visibility, and what each level refuses

A snapshot is two numbers and a list

Postgres keeps every version of every row until it is proven unreachable, so “what can I see” is decided per transaction rather than per row. The whole rule is xmin:xmax:in-flight: work from transactions below xmin is visible, work at or above xmax is not, and the transactions listed in between were running when the snapshot was taken and are therefore invisible whatever they do next.

That is why no reader waits. The documentation states the benefit directly: “in MVCC locks acquired for querying (reading) data do not conflict with locks acquired for writing data, and so reading never blocks writing and writing never blocks reading.” The cost is on the other side of the same sentence — the superseded versions stay on disk, and something has to remove them later. That something is lesson 0019.

The levels are a choice about what gets refused

The usual presentation is a ladder from fast to safe, with a table of anomalies. It is more useful upside down: each level is a decision about what the database will refuse to do, and refusing is work it pushes back to you.

READ COMMITTED refuses nothing, which is why the measured first row had zero errors and a wrong answer. It is the default in Postgres and therefore the default in every ORM on top of it, so it is what you are running unless somebody decided otherwise. REPEATABLE READ refuses transactions that modify rows changed since the snapshot — the documentation is precise about the reason: a transaction at that level “cannot modify or lock rows changed by other transactions after the repeatable read transaction began”. SERIALIZABLE refuses more, on the basis of read-write dependencies, and raises a different message for it.

In plain words

Write skew breaks a rule that spans several rows, such as a total weight that must stay at or below 1.0. Two transactions each read the total, each see room for 0.6, and each write to a different row, so neither touches a row the other wrote. Repeatable read only refuses a write to a row someone else changed, so both commit and the total ends at 1.2. Serializable also tracks what each one read, and fails one of them with an error the code is expected to retry.

Snapshot isolation checks what you wrote, never what you read

This is the sentence that makes write skew stop being a curiosity. REPEATABLE READ detects a conflict when two transactions write the same row. In write skew they do not: each reads a set, each concludes there is room, each writes somewhere else. Both transactions are individually correct with respect to what they saw, and the state they produce together is one no serial order could have reached.

Postgres gives the canonical shape in its own documentation — transaction A sums class = 1 and inserts the result into class = 2 while B does the mirror image — and the error it raises is deliberately a different one: “could not serialize access due to read/write dependencies among transactions” rather than “due to concurrent update”. Two messages, two mechanisms, and reading which one you got tells you which kind of conflict you have.

The practical consequence is a rule you can state in an interview: if your invariant spans rows, a row-level mechanism cannot enforce it. Not a version column, not FOR UPDATE on the row you are writing, not an idempotency key. Either SERIALIZABLE, or a lock on something that represents the whole set, or a constraint the database can check.

The retry loop is the fix, and it has a budget nobody sizes

Every serialization failure is an instruction rather than a report. The documentation is unambiguous on both levels — “applications must not depend on results read during a transaction that later aborted; instead, they should retry the transaction until it succeeds” — and the single most common way to write that loop wrong is to retry inside the failed transaction, where every statement returns 25P02 until you roll back.

The second most common way is the one measured in step 4, and it is quieter: a retry count that is smaller than the contention. Under full contention on one row the writers succeed strictly one at a time, so the n-th writer must lose n−1 times. A budget of eight against sixteen writers dropped exactly eight writes, and it dropped them the same way the original bug did — by giving up and reporting nothing useful.

Which lands on the sentence worth keeping: an isolation level decides what you are told, and your code decides whether the work happens.

Check yourself

Eight concurrent writers each add 1 to the same score at READ COMMITTED. The final value is 1. How many errors did the application see?

  1. None at all; every writer reported complete success
  2. Seven, since that many writers were refused outright
  3. One, raised when the final writer tried committing
  4. Eight, one from every writer touching that score

Zero. Every writer read a value, added one to it and wrote the result, and every one of those writes succeeded. Seven of them were then overwritten by a value that had been computed before they landed. There is no error to catch, because nothing went wrong from the database's point of view.

That is what distinguishes this from lesson 0014's double-apply, which is its mirror image: there a request applied twice, here one applied zero times while reporting success. Both come from a gap between a read and a write, and neither produces a log line to search for.

REPEATABLE READ stopped the non-repeatable read and the phantom in the measured grid. Why did it not stop the write skew?

  1. It only compares what you wrote, never what you read
  2. Both writers chose rows that nobody else had touched yet
  3. Postgres cannot see this one without taking a table lock
  4. The time between the two reads was simply too short

Because it is snapshot isolation, and snapshot isolation resolves conflicts on writes. The two evaluators each read the same total, each concluded there was room, and each wrote to a different row — so there is no write-write conflict anywhere for it to find. The invariant ended at 1.2 against a limit of 1.0, with no error raised.

The second option is true and is not the reason: it describes the situation rather than the mechanism. SERIALIZABLE catches it because it tracks read-write dependencies as well, and it says so in a different error message — “read/write dependencies among transactions” rather than “concurrent update”.

Say it out loud · about 75 seconds

A spoken answer to “two workers update the same row — what isolation level do you use?” Read it aloud, then say it again with the page covered.

  1. Situation

    Two sessions promote the same memory record. Both read it, both write it back, and one of those writes disappears.

  2. Mechanism

    Postgres defaults to read committed, which refuses nothing. Both writes succeed and the second one overwrites a value computed before it.

    A stronger level does not make that correct. It makes the database refuse one of them, so you find out.

  3. What I did

    I measured it. Eight writers adding one each: the answer was one, with zero errors raised anywhere.

    At repeatable read the answer was still one, and seven writers got a 40001. The fix is the retry loop, not the setting.

    Then I broke the loop. Sixteen writers against a budget of eight, and exactly eight survived.

  4. What it cost

    The retry count has to be at least the number of writers that can contend. Below that it drops writes quietly.

    And snapshot isolation only compares writes. An invariant across two rows needs serializable, because write skew is invisible to it.

The sentence that sounds fluent and gets you caught

“We use REPEATABLE READ, so we don't get lost updates.” Half true and the wrong half. It stops the lost update by refusing the transaction, so the follow-up is “what happens to the seven writers that get refused?” If there is no answer, those writes are as gone as they were before. The version that holds says both halves: “repeatable read turns the lost update into a 40001, and we retry the whole transaction with a budget sized from the contention level.”

The second trap is recommending SERIALIZABLE as the safe default. It is the only level that catches write skew and it refuses more, so the honest version names the trade rather than the guarantee: it costs retries under contention, and the number of retries you need is a property of your workload rather than of the level. If you cannot say what your retry budget is, you have not deployed it, you have configured it.

Probes to expect

  1. “Two workers read a row, modify it, and write it back. What happens?” Deliberately open. The interviewer is waiting to hear whether you say “one update is lost” or whether you also say that nothing fails, which is the part that makes it hard to find.
    Model answer — say yours first

    At the default level, one of them wins and the other is silently overwritten. I measured it — eight writers each adding one to the same score produced a final value of one, with zero errors and every writer reporting success. That is the part that matters operationally: there is nothing to alert on, because from the database's side two transactions wrote a number and both writes committed.

    It is the mirror image of an idempotency failure. There a request applies twice; here it applies zero times while reporting success. Same cause both times: a gap between the read and the write that somebody else fits through.

    Invites · “So raise the isolation level?” — that changes what you are told, not what happens.
  2. “Would REPEATABLE READ fix that?” The obvious follow-up, and the answer that sounds right is wrong by itself. The measured version is short and unarguable.
    Model answer — say yours first

    Not on its own. At repeatable read the same eight writers produced a final value of one again — identical to the broken run — except that seven of them failed with 40001 instead of succeeding quietly. Nothing is more correct yet; the database has just started telling you.

    The fix is the retry loop, and Postgres's documentation puts it in one sentence: applications at this level “must be prepared to retry transactions due to serialization failures”. With the loop, all eight land. So the level and the loop are one change, and shipping only the first converts a data bug into an error rate.

    Invites · “How many retries?” — which is the question almost nobody has measured an answer to.
  3. “How many times would you retry, and where does that number come from?” Sounds like a tuning detail. It is the second bug hiding underneath the fix, and it fails the same way the original did.
    Model answer — say yours first

    At least the number of writers that can contend for one row, because under full contention they succeed one at a time and the n-th has to lose n−1 times. I broke it deliberately: sixteen writers against a budget of eight, and exactly eight survived — on every run. The other eight were dropped as quietly as the original lost updates were.

    Which means the loop is not a general answer. If the number of contending writers is unbounded, no fixed budget is safe, and the right move is to stop contending — a single statement that computes from the current value rather than from a remembered one, so there is no gap and no retry.

    Invites · “What does that statement look like?” — one UPDATE with the arithmetic in it, and no SELECT at all.
  4. “What is write skew, and which level catches it?” The question that separates reading the isolation table from understanding the mechanism underneath it. The table says SERIALIZABLE; the follow-up is always why.
    Model answer — say yours first

    Two transactions each check a rule, each find room, and each write to a different row. Individually both were correct about what they saw; together they break the invariant. I ran it — two evaluators each adding weight 0.6 under a limit of 1.0, ending at 1.2 with no error at both read committed and repeatable read.

    Repeatable read cannot catch it by construction, because it is snapshot isolation and it resolves conflicts on what you wrote. These two wrote to rows nobody else touched. Serializable also tracks read-write dependencies, and it says so in a distinct message. The rule I take from it: if the invariant spans rows, a row-level mechanism cannot enforce it — not a version column, not FOR UPDATE.

    Invites · “What if you can't use SERIALIZABLE?” — lock something that represents the set, or make it a constraint.
  5. “Why does Postgres not implement READ UNCOMMITTED?” A trivia question with a structural answer. Reciting “it maps to read committed” gets a nod; saying why gets a follow-up conversation.
    Model answer — say yours first

    Because under MVCC there is nothing there to read. An uncommitted row version is not visible to any other transaction — visibility is decided by comparing the writing transaction against your snapshot — so a dirty read has no mechanism to happen through. The level is accepted and ignored: I asked for it and the server reported it back as ‘read uncommitted’ while behaving as read committed, which means a configuration audit that greps for the setting passes.

    The layer above is stricter than the database: SQLAlchemy refuses the value outright rather than passing it on. Two components, two different answers to the same request, and only one of them is visible from the application.

    Invites · “What else does the database accept and ignore?” — a fair question, and worth knowing for your own stack.
