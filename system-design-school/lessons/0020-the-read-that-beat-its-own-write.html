The Read That Beat Its Own Write

A replica 0.2 ms behind returned the old value 493 times in 500 to a client that read straight after writing, and none to one that took a little longer about it. Same replica, same lag. What protects a read is not how far behind the replica is but how fast your own next statement is — and under write load, the slow client missed most of them too.

The win

Add a streaming replica, send reads to it, and watch an idle test pass while a loaded one fails. Find that the ORM's own overhead was the only thing keeping the idle case correct. Then fix read-your-writes with a token taken after the commit, break it by taking the token one statement too early, and price the alternative that moves the wait onto every write — including what that write does when the replica is gone.

Why you, specifically
“Python/FastAPI, async SQLAlchemy, PostgreSQL, GKE” — and the deployment claims spread across the experience bullets: Cloud Run with IAP, Helm, Terragrunt, Cloud Build.

One Postgres, one region, and a stack that scales horizontally everywhere except the database. When the question comes — “what is the first thing you do when reads outgrow it?” — the answer everybody gives is a read replica, and it is the right first rung. The follow-up is what separates having read about replicas from having run one: “and what breaks?”

What breaks is the sentence the whole evaluation flow depends on. A vendor's score is written and the page that shows it is loaded a moment later. Send that read to a replica and, under load, most of the time it shows the score from before. Nothing errors. The page is simply wrong, and a refresh fixes it, which is exactly the kind of bug that gets closed as cannot reproduce.

The claim is defended in full in chapter 0011 of Résumé Mastery. This lesson is the first rung of the scaling ladder that chapter does not yet climb.

Start here — the plain version

A replica is a second Postgres server that keeps a copy of the first by replaying its log of changes. You can read from it, which takes load off the original. You cannot write to it. By default the original does not wait for the copy: it tells your application “committed” the moment the change is safe on its own disk, and the copy catches up a little later.

“A little later” is the whole lesson. If your application writes something and immediately reads it back from the copy, the read can arrive before the change has. No error is raised and the old value comes back looking perfectly ordinary. The question is how often, and what you can do about it that does not throw away the reason you added the copy.

Primary
The server that accepts writes. There is one of them.
WAL
The write-ahead log: every change, in order, before it is applied. The primary streams it to the replica.
Replay
The replica applying the WAL it has received. A change becomes visible there only when its commit record is replayed.
Replication lag
How far behind replay is. Reported as time and as bytes, and neither is a promise about the next read.
Read-your-writes
The guarantee that after you write something, your own reads show it. The one a replica silently removes.
LSN
Log sequence number: a position in the WAL, printed like 6/9C4E4A0. Bigger is later.
Write token
The LSN recorded after a write commits, carried to the next read so the replica can be asked whether it has caught up with that write.
synchronous_commit
How much the primary waits for before saying “committed”. At remote_apply it waits for the replica to replay the change.
hot_standby_feedback
Whether the replica tells the primary which old rows its queries still need. Trades the replica's queries against the primary's vacuum.

The replica is not slow; your next statement is fast

The usual way to think about replicas is through lag: if the replica is a few milliseconds behind, reads are a few milliseconds stale, and nobody cares about a few milliseconds. That framing is wrong in a specific way. Staleness is not spread evenly over reads; it lands entirely on the reads that come straight after a write, which in a request handler are exactly the ones that matter.

So the number to measure is not the lag. It is the gap between your commit returning and your read arriving, and whether that gap is shorter than replay. On this machine the replica was 0.2 ms behind when idle, and a lean client's next statement was faster than that nearly every time.

Why an idle test will pass and tell you nothing

Through async SQLAlchemy, with a pool checkout per statement, the idle replica returned the new value 500 times in 500. That looks like proof the replica keeps up. It is proof that SQLAlchemy is slow enough: the checkout, the commit and the reset on return add up to more than 0.2 ms.

Raw asyncpg on held connections, same replica, same moment: 493 stale in 500. And under write load the SQLAlchemy client failed too, because the lag grew past its overhead. A correct result that depends on your client being slow is not a property you can keep.

In plain words

Read the drawing as two timelines: the primary (the server you write to) on top, the replica (the read-only copy) below. Any read that lands between “COMMIT returns” and “replayed” gets old data. The bottom lines are the fix (make that one read wait for that one write), the same fix taken one statement too early, and the option that makes every write wait instead.

Lab — a replica, a read, and the three ways to wait for it

Lab 0020 ~25 minutes

An idle test that lies, a token that works, and a commit that waits for nobody

  1. Start the primary and the replica, then write a row and read it straight back from the replica, idle and under write load, with and without a pause in between.

    Idle it looks solved; under load it is wrong most of the time

    The idle rows are what a developer sees on a laptop: one stale read in two thousand, and a replica a fifth of a millisecond behind. Under write load the same code returned the old value 391 times in 500 when it read straight after the write. Across five runs that row has been between 324 and 408.

    The pause column shows the shape rather than a threshold. A millisecond helps a lot, five helps less than you would think, and only at fifty does it reliably disappear — because lag under load is not a number, it is a distribution, and one run's replay_lag column went from 3 ms to 29 between adjacent rows. Any fixed sleep is a bet on the tail of that distribution.

  2. Now explain the idle rows. Run the same idle read through two clients: the ORM with a pool checkout per statement, and raw asyncpg on connections it keeps open.

    idle replica, read sent straight after the write:
  sqlalchemy, pool checkout per statement   stale    0 of 500
  raw asyncpg, connections held open        stale  493 of 500
  replay lag at the end: 0.23 ms

  3. Now the fixes, all five ways, idle and loaded: read the replica anyway, read the primary, a token read inside the transaction, a token read after commit, and synchronous_commit = remote_apply.

    Before / after · three correct answers, each paying in a different place

    Every idle row is zero, so idle testing cannot tell any of these apart. Under load: the plain replica read is wrong 387 times in 500, and three of the fixes are right every time. Reading the primary is correct and removes the reason you added a replica. The token is correct and moves the cost onto the read: 29 ms at p99 in this run, and between 26 and 52 across five. remote_apply is correct and moves it onto the write: 52 ms at p99 in this run, and between 29 and 54 across five.

    Then the row that should worry you. A token read one statement too early — inside the transaction instead of after COMMIT — is correct in every idle run and returned stale data 5 times in this run, and between 5 and 54 across five. It points at a position before the commit record, so the replica can replay up to it and still not show the row. That is a bug with the worst possible profile: it cannot be found on a quiet machine.

  4. Price remote_apply properly: stop the replica, commit with it on and with it off, and give up after three seconds.

    synchronous_commit = local         committed in 8.7 ms
  wrote v = 1; another session on the primary now reads v = 1
synchronous_commit = remote_apply  client gave up after 3 s
  wrote v = 2; another session on the primary now reads v = 2
  server said: canceling wait for synchronous replication due to user request
  server said: The transaction has already committed locally, but might not have been replicated to the standby.
    The commit waits for a server that is not there, and giving up does not undo it

    With the replica stopped, an ordinary commit is unaffected and a remote_apply commit does not return. The documentation says so plainly: such commits “may never be completed if any one of the synchronous standbys should crash.” A replica added to take read load off the primary has become something that can stop the primary accepting writes.

    The second line is the one to remember. The client gave up, and the write had already happened: another session reads v = 2, and the server's own detail message says so — “The transaction has already committed locally, but might not have been replicated to the standby.” The client got an error for a write that succeeded. That is lesson 0014's lost response, coming out of the database itself, and a retry here would apply it twice.

Underneath

One layer down · what “committed” means with a replica

A read is stale when it beats replay, and your client decides that

The documentation describes the default precisely: “Streaming replication is asynchronous by default, in which case there is a small delay between committing a transaction in the primary and the changes becoming visible in the standby. This delay is however much smaller than with file-based log shipping, typically under one second.” Under one second is a reassuring phrase for a dashboard and an alarming one for a request handler, where the next statement arrives in well under a millisecond.

So staleness is a race between two intervals that have nothing to do with each other: how long replay takes, which the database decides, and how long your code takes between the commit and the read, which you decide without meaning to. Step 2 held the first constant and changed only the second, and the result went from none to nearly all.

A read straight after its own write is stale when gap < lag. Measured:

client gap, commit to read lag stale of 500 raw asyncpg, held connection under 0.2 ms 0.2 ms 480 to 495 sqlalchemy, checkout per stmt over 0.2 ms 0.2 ms 0 or 1 sqlalchemy, under write load over 0.2 ms 3-29 ms 287 to 408 any client, 50 ms pause 50 ms 3-29 ms 0 or 1 of 100

Rows two and three are the same code, and the only thing that changed is the lag. The right column is set by the ratio, not by either number, which is why reasoning about lag alone predicts none of it — and why the only fix that does not depend on the ratio is one that waits for the specific write rather than for time to pass.

In plain words

A token is a bookmark in the primary’s change log, saved just after your write is confirmed. The next read waits until the replica has replayed the log up to that bookmark, so it is sure to see the write. Take the bookmark one statement early, while the write is still open, and it can point before the write’s “done” marker: the read then returned old data 5 to 54 times in 500, but only under load.

A token has to point past the commit record, and the wait must not hold a snapshot

The token is a WAL position, and a change becomes visible on a replica only when its commit record is replayed. pg_last_wal_replay_lsn() is documented as “the last write-ahead log location that has been replayed during recovery”, so the comparison is only meaningful if the token is at or beyond the commit record. Read inside the transaction, it is not.

The order of records in the log for one write, and where each token lands:

WAL, in order token read here replica at the token shows UPDATE ryw_demo ... row change - - inside the txn -> the old value, sometimes COMMIT record - - after COMMIT -> the new value, always

The early token is wrong only when the replica's first poll lands between the row change and the commit record. Idle, those two are written microseconds apart and the poll never fits between them. Loaded, the commit record queues behind other sessions' WAL and it does: 5 to 54 stale reads in 500 under load, none idle. A bug whose failure rate rises with traffic is found by customers.

The wait has a trap of its own, found by this lesson's own flaky test. Under asyncpg, an open transaction that has read anything holds a snapshot — lesson 0019's portal — and a poll loop inside one transaction is exactly that. The hot-standby chapter says what a held snapshot does to replay: “a long-running query could cause other sessions on the standby server to not see recent changes on the primary, if it delays application of WAL records.” Measured with a vacuum on the primary during the wait: replay paused for 30.5 s and the session was killed. The wait was waiting for itself. wait_for_replay now ends a transaction per poll.

In plain words

remote_apply fixes stale reads for every reader by charging the writer instead. Under load, write p99 (the time only 1 in 100 writes exceeds) rose to 29 to 54 ms, from 4 to 12. If the replica stops, commits stop returning, and a client that gives up gets an error for a write that was in fact saved.

remote_apply moves the wait onto the write, and the wait is not a rollback

The configuration chapter says what it buys: “Setting synchronous_commit to remote_apply will cause each commit to wait until the current synchronous standbys report that they have replayed the transaction, making it visible to user queries. In simple cases, this allows for load balancing with causal consistency.” That is read-your-writes for every reader at once, bought by making every write wait for the slowest synchronous replica.

Two costs follow, and both were measured. Under load the write's p99 went to between 29 and 54 ms across five runs, against 4 to 12 for the same writes without it. And with the replica gone the commit does not finish — “Such transaction commits may never be completed if any one of the synchronous standbys should crash” — while cancelling the wait does not undo it. The same chapter says waiting transactions “will be marked fully committed once the primary database recovers.” The write is durable; only the acknowledgement is missing.

Four ways to read your own write, and where each one pays:

route stale, loaded who waits and what it costs replica, as-is 287-408 of 500 nobody wrong answers, silently primary 0 nobody the replica takes no reads token after commit 0 the one read 26-52 ms p99; primary on timeout remote_apply 0 every write 29-54 ms p99; stops if replica dies

The last two rows pay the same replay lag at the tail — roughly 26 to 54 ms at p99 either way — and differ only in who is charged. The token is the only row that charges the caller who needs the guarantee and nobody else. Consistency is a cost somebody pays; the design question is who, and whether they asked for it. Lesson 0029 gives read-your-writes its proper place among the other session guarantees.

Which lands on the sentence worth keeping: a replica does not return stale data because it is slow; it returns it because your read is fast, and the only fix that does not depend on the race is waiting for your own write. Take the token after the commit, and never wait inside a transaction.

Check yourself

An idle replica 0.2 ms behind returned stale data 0 times in 500 through SQLAlchemy and 493 times through raw asyncpg, reading straight after each write. What made the difference?

  1. How long each client took between writing and reading
  2. Raw asyncpg reading from a stale local result cache
  3. SQLAlchemy quietly sending all its reads to the primary
  4. The pool warming up the replica's buffer cache first

The gap. A read is stale when it arrives before replay reaches the write, so what matters is the ratio of your client's gap to the replica's lag. SQLAlchemy's checkout, commit and reset on return took longer than 0.2 ms, so it lost the race to the log almost never; asyncpg on a held connection sent the read at once and won the race almost every time.

None of the distractors happened: asyncpg has no result cache, both clients read from the replica, and buffer warmth changes how fast a read is served, not what it can see. The consequence is the lesson's warning — an idle test that passes through the ORM is evidence about the ORM, not about the replica.

With synchronous_commit = remote_apply and the replica stopped, the client gives up on COMMIT after three seconds. What state is the write in?

  1. Committed on the primary and visible to other sessions
  2. Rolled back because the replica has not acknowledged it
  3. Held in limbo until the replica has started again
  4. Visible only to the session that attempted the commit

Committed. The commit is durable on the primary before the wait begins; the wait is only for the replica's acknowledgement. Cancelling it withdraws the client from waiting and nothing else, and the server says so in its own message: “The transaction has already committed locally, but might not have been replicated to the standby.” In the lab, another session read the new value immediately.

That makes it lesson 0014's problem exactly: the client received an error for a write that succeeded. A naive retry applies it twice, which is why a synchronous commit that can time out needs an idempotency key as much as any network call does.

Say it out loud · about 75 seconds

A spoken answer to “reads have outgrown your Postgres — you add a read replica. What breaks?” Read it aloud, then say it again with the page covered.

  1. Situation

    One Postgres, and read load growing. A streaming replica is the right first move, and sending reads to it is the part that breaks.

  2. Mechanism

    Replication is asynchronous by default. The primary says committed before the replica has replayed it, so a read straight after a write can see the old value.

  3. What I did

    I measured it. Idle, through our ORM, zero stale reads in 500. Through raw asyncpg on the same replica, 493. The ORM's overhead was hiding it.

    Under write load the ORM missed most of them too. So each write carries a token: the log position after commit. The replica read waits until replay passes it. Zero stale, 25 to 50 milliseconds at p99.

  4. What it cost

    The token has to be read after the commit. Inside the transaction it was wrong up to 54 times in 500, and only under load.

    The alternative, remote_apply, puts that wait on every write. With the replica down, writes stop.

The sentence that sounds fluent and gets you caught

“Replication lag is under a millisecond, so reading from the replica is fine.” The lag was 0.2 ms and a client reading straight after its write missed it 493 times in 500. The follow-up is “fine for which reads?”, and the honest answer is: fine for reads nobody just wrote, which are not the ones users notice. The version that holds: “fine for reads that do not follow the caller's own write; those wait for a token or go to the primary.”

The second trap is offering synchronous replication as the easy fix. It is correct, and the interviewer's next question will be “what happens to writes when the replica goes down?” If the answer is not “they stop, and a client that gives up gets an error for a write that committed”, you have described the setting without having run it.

Probes to expect

  1. “Your replica is a fraction of a millisecond behind. Why would anybody see stale data?” A setup. The weak answer argues the lag is small; the strong one says staleness is a race and names the other runner.
    Model answer — say yours first

    Because staleness is not about the lag on its own. It is a race between replay and the caller's next statement, and a read straight after a write is usually faster than a fraction of a millisecond. I measured it: 0.2 ms of lag, and a raw asyncpg client missed its own write 493 times in 500.

    The same replica through our ORM missed none, because the pool checkout and reset took longer than replay. That is the dangerous part: the idle test passes for a reason unrelated to the replica. Under write load the ORM path failed most of the time as well.

    Invites · “So how do you fix it?” — wait for the specific write, not for time to pass.
  2. “How do you give a user read-your-writes with a replica in the path?” The core question. Three answers are common; the one that scores says where each one charges the cost and picks deliberately.
    Model answer — say yours first

    A write token. After the commit returns, read the primary's WAL position and carry it with the session. A read that follows goes to the replica and waits until pg_last_wal_replay_lsn() has passed the token, with a short timeout and the primary as the fallback. Under load that was zero stale reads at 26 to 52 ms p99, and it charges only the reads that need the guarantee.

    The detail I would call out is after the commit. I also measured the token read one statement earlier, inside the transaction: it points before the commit record and returned stale data 5 to 54 times in 500 under load, never when idle. And the wait itself has to run outside a transaction, or its own snapshot can pause the replay it is waiting for.

    Invites · “Why not just read the primary after a write?” — you can, for a window; it works and it gives back part of what the replica was for.
  3. “Why not use synchronous replication and make the problem go away?” Sounds like a simplification. It is a test of whether you know what synchronous commit does to availability.
    Model answer — say yours first

    remote_apply does make it go away — every commit waits until the replica has replayed it, so every reader sees it. It costs every write that wait: under load the write p99 went to 29 to 54 ms, against 4 to 12 without it. That is the price when things are healthy.

    The price when they are not is worse. With the replica stopped, the commit does not return at all, and when the client gave up after three seconds the write had already committed on the primary — the server's own message says so. So a replica added for read capacity can halt writes, and a client timeout produces an error for a write that succeeded, which needs idempotency to retry safely.

    Invites · “How would you make it survive a replica failure?” — more than one synchronous candidate, and accept that it is now an availability design.
  4. “Analysts want to run hour-long reports on the replica. Any problem?” Sounds like the textbook use of a replica. It is the question that connects replicas to vacuum, and the one-sided answer is the failure.
    Model answer — say yours first

    Yes, and it is a forced choice. The replica replays the primary's vacuum, and if a report still needs rows vacuum removed, one side loses. With hot_standby_feedback off, the default, the replica pauses replay and then cancels the report — after 2.5 s in my lab with the delay at two seconds. With it on, the primary is told what the report needs and vacuum there removed 0 of 5 000 dead rows.

    And off has a second cost people miss: while replay is paused for that report, every other session on the replica is reading stale data, for up to thirty seconds by default. So for hour-long reports I would give them their own replica with feedback off and a long delay, and keep the replica that serves the application on short queries only.

    Invites · “Where have you seen that bloat before?” — lesson 0019: an open snapshot is an open snapshot, whichever machine it is on.
  5. “Where does a read replica sit on your scaling ladder, and what is the next rung?” A framing question. What is being tested is whether you know what a replica does not scale.
    Model answer — say yours first

    It is the first rung after the cheap ones — pool sizing, indexes, caching — and it scales exactly one thing: read capacity. Writes still go to one server, the WAL still comes from it, and every replica adds a sender on the primary and another pool each application instance has to hold, so lesson 0015's pool-times-replicas arithmetic now applies twice.

    It also changes the semantics, which the earlier rungs did not: from here on some reads can be in the past, and every read path has to say whether it can tolerate that. The next rungs are partitioning the data so writes split, and then sharding across servers, and each costs more than the last in exactly this way — more guarantees that used to be free and now have to be designed.

    Invites · “What would you partition first?” — the results table from 0019, by time, because it only ever grows.
