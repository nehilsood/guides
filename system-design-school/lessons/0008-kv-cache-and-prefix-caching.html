KV Cache and Prefix Caching

The memory a conversation occupies on an accelerator is arithmetic, not a mystery, and you can do it on paper. Then the part that is not arithmetic: why a shared system prompt is nearly free, and why fixing a typo in it costs you 8× your first word.

The win

Compute exactly how many conversations fit on one 80 GiB card — and answer “scale it to a million concurrent” with a number instead of the word Kubernetes.

Why you, specifically
“Built a custom OpenAI-compatible LLM gateway powering those interviews at ~2.1 s median time-to-first-word under a hard 8 s per-turn budget.”

Lesson 0001 accounted for that 2.1 s hop by hop and stopped at the model call, treating it as one opaque number. It is not one number: it is prefill, which is proportional to how long your prompt is, plus the first step of decode. Everything you can do to move time-to-first-word without changing models happens inside prefill, and prefix caching is the largest lever there is.

That sentence is defended in full in chapter 0002 of Résumé Mastery — this lesson is where the mechanism underneath it gets built and broken.

Start here — the plain version

A model generating text re-reads everything before the token it is writing. Doing that from scratch for every token would be quadratic and hopeless, so instead it keeps the intermediate results — two tensors per layer, called keys and values — and reuses them. That store is the KV cache, it lives in the accelerator's memory, and it grows by a fixed number of bytes for every token in the conversation.

Which makes it the real capacity limit of a serving system. Not requests per second, not CPU: how many conversations of what length fit in the memory left over after the model's weights. And it is why sharing the beginning of a prompt across requests is worth so much.

TTFW — time-to-first-word
Request sent to first token received. Roughly the queue, plus prefill, plus one decode step. The metric on your résumé.
Block (or page)
A fixed run of tokens — 16 by default in vLLM — that the cache is allocated and reused in. Nothing is cached per-token; everything is cached per-block, which is why a shared prefix ending mid-block wastes the tail of it.
Hit rate
Here, the fraction of prompt tokens that were already cached — not the fraction of requests that hit. Prefill time is proportional to tokens, so tokens is the only unit in which the percentage means anything.

In plain words

How much card memory one conversation takes is a multiplication, not a guess. The factor people get wrong is how many separate sets of keys and values each layer stores. On Llama-3 that is a quarter of the figure people tend to plug in, so the wrong number makes the answer four times too big. Get it right and an 8k-token conversation on Llama-3-8B takes about one gigabyte, so an 80-gigabyte card holds about sixty.

First: the arithmetic, which is exact

One formula, and every term in it comes out of the model's config.json:

The whole of the first half 
bytes = 2 × layers × kv_heads × head_dim × seq_len × dtype_bytes

The leading 2 is keys and values. kv_heads is num_key_value_heads, not num_attention_heads — that is the single most common error in this calculation, and on a Llama-3-class model it inflates the answer fourfold.

Llama-3-8B is 32 layers, 8 KV heads, head dimension 128. At fp16 that is 2 × 32 × 8 × 128 × 2 = 131 072 bytes per token, or 128 KiB — and at an 8k context, exactly one gibibyte per conversation. Worth memorising, because it makes every follow-up mental arithmetic.

Prefill sets the first word; decode sets the rest

These are two different bottlenecks and they respond to different things, which is why TTFW and tokens-per-second move independently. Prefill processes the prompt in one compute-bound pass, so it scales with how long your prompt is. Decode then produces one token per step, each step reading the entire KV cache, so it is limited by memory bandwidth and barely cares about prompt length at all.

Prefix caching is a prefill optimisation and nothing else. It cannot make your tokens arrive faster once they have started; it can only make them start sooner. Anybody who tells you it improved their tokens-per-second has measured something else.

Lab — do the arithmetic, then break your own prompt

Lab 0008 ~25 minutes

60 conversations a card, and an 8× typo

  1. Compute the cache for the model class you actually serve, and find how many conversations fit on one card.

    Llama-3-8B: 32 layers, 8 KV heads, head_dim 128

  fp16: 131,072 B/token (128 KiB) · weights 16 GiB · 60 GiB left for KV
      ctx   2,048:    0.250 GiB/sequence  ->    240 sequences
      ctx   8,192:    1.000 GiB/sequence  ->     60 sequences
      ctx 131,072:   16.000 GiB/sequence  ->      3 sequences
    You should see

    Sixty conversations on an 80 GiB card at an 8k context. Three at 128k. That second number is the one that should change how you think about long-context marketing: the context window is a capacity decision, and a 16× longer window costs 16× the memory per user.

  2. Now halve the cache with quantization, and see what it buys.

    More than double, not exactly double

    60 to 136, because quantizing the weights too frees another 8 GiB that all becomes cache. This is why “quantized KV” appears on every serving-cost list: it is the one lever that changes the arithmetic instead of working around it.

  3. Try the 70B model, which is what an interviewer will reach for when they say “a big model”.

    The weights do not fit, so the question changes

    A 70B model at fp16 needs 140 GiB just for weights on an 80 GiB card. Before KV cache is discussed at all, you are into tensor parallelism across at least two cards — and then the KV is 2.5 GiB per conversation, which is 2.5× the 8B model.

    This is the most useful thing in the first half of the lab, and it is worth being able to say fast: “which model” is a capacity question, not a quality question. Moving from 8B to 70B costs you the model's memory once and then 2.5× per user forever.

  4. Answer your prep notes' question with arithmetic. A million concurrent sessions, an 8 s turn, a human speaking every 30 s.

    Say the first number before you say anything else

    A million concurrent sessions is not a million concurrent generations. At an 8 s turn and a 30 s speaking cadence it is 267 000 in-flight decodes — and that is the number that sizes everything. Getting to it out loud, in one line of arithmetic, is the whole test in that question.

    Then the wall: 260 TiB of KV cache and about 4 400 accelerators, for cache alone. Which is the honest answer — not “add replicas”, but “at this shape it is physically impossible, so what changes?” The list is short: a much smaller model, quantized KV, shorter contexts, session eviction, and prefix sharing. Everything after this step is that last item.

  5. Vary the length of the shared system prompt and watch what a hit is worth. Each row resets the cache first, measures one cold request, then six warm ones.

     shared  cold TTFW  warm TTFW   saved  hit rate
      0       104m        97m    1.1x     0.0%
    128       142m        97m    1.5x    64.2%
    512       276m        98m    2.8x    79.1%
   1024       456m        99m    4.6x    82.3%
   2048       815m        99m    8.3x    84.0%
    The column that matters is the one that does not move

    Warm TTFW is flat at about 98 ms no matter how long the shared prefix is. 128 tokens or 2 048, it makes no difference — because on a hit you prefill only this turn's 48 tokens either way. The cold column, meanwhile, grows linearly with the prefix.

    Which inverts the instinct people bring to prompts. A longer shared system prompt does not cost you latency on a hit; it makes prefix caching more valuable, and moves the entire cost onto the miss path. “Keep the prompt short” is the wrong rule. “Keep the prompt identical” is the right one.

  6. So make it non-identical. Warm the cache with a 2 048-token prefix, then change one word at the very top of it — a capital letter will do.

    warm, prefix unchanged                     97 ms
one word changed at the top, 1st call     817 ms
same edited prefix, 2nd call              100 ms
    An 8.4× regression from a typo fix, and it heals itself

    One character, and the whole prefix is cold: 97 ms to 817. The chained hash is why — each block's hash covers its parent's, so an edit in block one invalidates blocks two through one hundred and twenty-eight as well.

    And look at the third line. The next call is back to 100 ms, because the edited prefix is now the cached one. The spike lasts one request per replica and then disappears, which is what makes it so hard to attribute: by the time anyone opens a dashboard the metric has recovered, so a prompt change and a TTFW spike look unrelated. On your system a prompt change is a deploy, and this is what it costs.

Underneath

One layer down · why a prefix and never a suffix

The formula is six factors and one of them is a trap

Notice what is absent from the formula: batch size, throughput, and the model's parameter count. Cache size per token depends only on the model's shape. Parameters matter separately, as the weights you subtract from the card first, which is why the 70B case fails on weights before KV is even discussed.

In plain words

A token’s stored keys and values depend only on that token and the ones before it, so the start of a prompt can be reused by any request that begins the same way. The server checks this with a fingerprint (a hash) for each block that also covers the block before it. So one changed character at the top makes every later block miss, and the rule is to keep the shared start exactly the same, character for character.

A prefix is reusable because attention is causal; a suffix never is

In a decoder-only model, the key and value vectors for token i are computed from tokens 1…i and nothing after. So the KV entries for the first 2 048 tokens of a prompt are identical regardless of what follows them — which is the entire licence to cache them. The same is not true in the other direction: the entries for the last 48 tokens depend on all 2 048 before them, so two prompts sharing an ending share nothing at all.

Serving systems enforce that with a hash chain rather than by comparing text. vLLM hashes each full block over its parent block's hash plus its own token ids, so block n's identity encodes the whole prefix up to n. Two requests hit the same block only if every token before it also matched.

Two consequences worth saying out loud. The hash covers token ids, so anything that changes tokenisation — whitespace, a capital letter, a reordered field — is a full invalidation. And because the key also folds in the model version and any adapter identity, a model upgrade is a cold cache by construction, not by accident: the same text under new weights must miss, or you would be serving KV computed by a different model.

Prefill and decode are limited by different hardware, so they do not trade

Prefill runs the whole prompt through the network at once: large matrix multiplications, high arithmetic intensity, compute-bound. Decode runs one token at a time and must read the entire KV cache to do it, so it moves a lot of memory to do very little arithmetic — memory-bandwidth-bound. They are so different that serving systems increasingly run them on separate machines.

The cache is the capacity limit, so a hit is memory as well as latency

Sixty conversations a card is not a soft number: exceed it and a request cannot be admitted, whatever your CPU is doing. This is why prefix caching pays twice. Blocks shared between conversations are stored once, so a thousand sessions sharing a 2 048-token system prompt hold one copy of its 256 MiB rather than a thousand — and the memory you get back is more sessions.

Check yourself

You start caching the KV blocks of a shared system prompt. Which measurement improves?

  1. Time to first word, because prefill skips the cached tokens
  2. Time between tokens, because decode reads a much smaller cache
  3. Total generation time, as fewer output tokens must be produced
  4. Output quality, as the model sees a consistent instruction set

Time to first word, and only that. Prefix caching removes prefill work — measured here as a flat warm TTFW of about 98 ms whether the shared prefix was 128 tokens or 2 048, against a cold cost that grew to 815.

The inter-token answer is the tempting one because it sounds like the same idea, and it is wrong for a structural reason worth knowing: decode still reads the whole KV cache at every step, cached or not. A block being reused does not make it smaller. Inter-token latency stayed at 18 ms per token in every row of that table.

You fix a typo in the first line of a 2 048-token shared system prompt. What happens to the cache?

  1. Every cached block following the edit is invalidated at once
  2. Only the single block holding the edited token is invalidated
  3. Nothing changes, since the hash covers whole prompts not blocks
  4. Only the decode phase slows, because prefill was already cached

All of it. Each block's hash is computed over its parent block's hash plus its own token ids, so changing anything in block one changes the identity of every block after it. Modelled here as 97 ms to 817 — and then back to 100 ms on the very next call, because the edited prefix immediately becomes the cached one.

The single-block answer is what a per-block hash without chaining would give you, and it is worth understanding why nobody builds it that way: identical token runs appearing at different positions are not interchangeable, because their keys and values depend on everything before them. The chain is what makes the reuse correct rather than merely fast.

Say it out loud · about 75 seconds

A spoken answer to “you got median time-to-first-word to 2.1 seconds — what actually moved it, and how would you scale it?” The second half is straight out of your prep notes, and the arithmetic is the whole test. Read it aloud, then say it again with the page covered.

  1. Situation

    Every call in our evaluation pipeline sends the same rubric preamble before the claim being scored. So most of the prompt is identical across requests, and only the tail differs.

  2. Mechanism

    First word is mostly prefill: the one pass that builds the key-value cache for the prompt. Prefill is proportional to prompt length. Decode is separate and memory-bound, so it sets the gap between tokens instead.

    Because attention is causal, the cache entries for the first N tokens do not depend on anything after them. So a shared prefix can be reused and a shared suffix cannot, and servers enforce that by hashing each block over its parent's hash.

  3. What I did

    I did the arithmetic rather than guessing. Two, times thirty-two layers, times eight key-value heads (not thirty-two, that is the mistake), times head dimension one twenty-eight, times two bytes. That is 128 kilobytes a token, so one gigabyte per conversation at an eight-thousand-token context, so about sixty conversations on an eighty-gigabyte card.

    Then I restructured prompt assembly so the shared preamble is byte-identical, moving the varying fields out. The same arithmetic answers the million-session question: eight seconds a turn against thirty seconds of speech is 267 thousand concurrent decodes, or 260 terabytes. So the answer is a smaller model and quantized cache, not more replicas.

  4. What it cost

    Two things. The cache is memory taken from batch size, so a longer context window is fewer concurrent users — sixty at eight thousand tokens, three at a hundred and twenty-eight thousand. Long context is a capacity decision, and we price it that way now.

    The prompt became something you cannot casually edit. Changing one character at the top invalidates the whole prefix. In my model that was an eight-fold first-word spike, lasting one request per replica and then healing. So it never looks like the prompt change that caused it. A prompt edit is a deploy.

The sentence that sounds fluent and gets you caught

“We cache the prompt, so repeated requests are faster.” There are at least three caches that sentence could mean — the KV cache on the accelerator, a response cache keyed on the whole prompt, and the embedding cache from lesson 0003 — and they have three different invalidation rules and three different failure modes. The follow-up is “which cache?”, and not being able to answer it suggests you inherited the flag rather than chose it. Name it: “the KV cache, at block granularity, on the shared prefix.”

The other trap is the confident capacity answer: “we'd scale it horizontally.” With 267 thousand concurrent decodes at a gigabyte of cache each, horizontal means four thousand accelerators, and saying so is the difference between having done the arithmetic and having heard the word. The version that holds names the number first and the mitigation second.

Probes to expect

  1. “How much memory does one conversation cost on the GPU?” A pure arithmetic question, and it is astonishing how many people answer it with an adjective. Give the formula, then a number, then the capacity consequence. If you name kv_heads rather than attention heads you have already separated yourself from most candidates.
    Model answer — say yours first

    It is computable: two — for keys and values — times layers, times key-value heads, times head dimension, times sequence length, times bytes per element. On a Llama-3-8B shape that is thirty-two layers and eight key-value heads at head dimension one twenty-eight, so 128 KiB per token, which at an 8k context is exactly one gibibyte per conversation.

    The reason I care is capacity. An 80 GiB card minus 16 of weights and a few for activations leaves about sixty conversations, and that is the real concurrency limit of a replica — not CPU and not requests per second. It is also why the key-value head count matters: using attention heads instead would have told me fifteen, and I would have provisioned four times the hardware.

    Invites · “And at 128k context?” — three conversations a card, which is the answer to why long context is priced the way it is.
  2. “Your system prompt is 2 000 tokens. Isn't that wasteful?” A trap that rewards knowing the mechanism. The instinctive answer is yes, and it is wrong on a cache hit. But the correct answer has a real condition attached, and stating the condition is the point.
    Model answer — say yours first

    Not on a hit, and that surprised me too. Because it is the same prefix every call, its key-value blocks are already resident, so prefill only covers the part that differs — in my measurements first-word time was flat whether the shared prefix was 128 tokens or 2 048. And the blocks are shared, so a thousand concurrent sessions store one copy of it rather than a thousand.

    The condition is that it has to be byte-identical and it has to be at the front. Anything varying near the top — a timestamp, a tenant name — invalidates everything below it, and then that 2 000 tokens is pure cost on every single request. So the rule I follow is not “keep it short”, it is “keep it identical, and put anything that varies after it”.

    Invites · “What varies in yours today?” — which is a question about whether I have actually read the prompt-assembly code, and the honest answer is that I found two fields that should move.
  3. “Scale it to a million concurrent interviews. What breaks first?” Your prep notes flag the red flags on this one: jumping to replicas and a queue, no KV arithmetic, treating a stateful streaming service as stateless REST. Do the concurrency conversion out loud before you draw anything — that step is the test.
    Model answer — say yours first

    First, a million concurrent sessions is not a million concurrent generations. If a turn takes eight seconds and a person speaks every thirty, then eight thirtieths are in flight — about 267 000 concurrent decodes. That is the number that sizes everything, and it is four times smaller than the one in the question.

    Then the key-value cache is what breaks, before the gateway and long before CPU. At a gibibyte per conversation that is 260 TiB of cache, roughly four thousand accelerators for cache alone, which is not a scaling plan — so the design has to change shape. Smaller model, quantized cache to halve the bytes, shorter contexts with aggressive session eviction, and prefix sharing so the common preamble is stored once. Those are multiplicative, and together they are the difference between impossible and expensive.

    Invites · “How do sessions land on replicas, then?” — because prefix reuse only works if the same conversation returns to the same replica, which is lesson 0009.
  4. “First word is fine but the answer reads slowly once it starts. What do you do?” A test of whether you know prefill and decode are different bottlenecks, or just have one story about latency. The wrong move is to reach for prefix caching, which is the lever you just learned and does nothing here.
    Model answer — say yours first

    That is decode, not prefill, so everything I would do for first-word time is irrelevant to it. Decode generates one token at a time and reads the whole key-value cache at each step, so it is bound by memory bandwidth rather than compute — in my measurements inter-token latency did not move at all when prefix caching took first word from 815 ms to 99.

    The levers that do apply are different: a smaller or quantized cache so each step moves fewer bytes, a smaller model, better batching so the bandwidth is amortised across concurrent sequences, or simply generating fewer tokens by asking for a shorter answer. I would measure inter-token latency separately from first word before touching any of them, because they are two metrics and one number hides both.

    Invites · “Why would batching help if it adds queueing?” — because decode is bandwidth-bound, so concurrent sequences share the weight reads; and it is a genuine latency-versus-throughput trade.
  5. “You said the cache has a fixed ceiling. What happens when it fills?” This is lesson 0004 in new clothes, and saying so is the strong move. A prefix cache is a hard-ceilinged, heavily skewed cache with an eviction policy, so the whole eviction lesson applies — only a miss costs GPU-seconds instead of a Redis round trip.
    Model answer — say yours first

    Something gets evicted, and which something is a policy decision I should be able to defend. It is the same structure as any bounded cache with a skewed access pattern: a small set of blocks — the shared preamble — is worth enormous amounts, and a long tail of per-conversation blocks is worth almost nothing once that conversation ends.

    Which means it has the scan problem too. A burst of one-off long contexts is a sweep of cold blocks under a recency policy, and it can push out the shared prefix that thousands of sessions were hitting — exactly the failure I reproduced in Redis with a batch job under allkeys-lru. The difference is the cost of being wrong: there a miss was a round trip, here it is prefill time and a queue.

    Invites · “So would you pin the shared prefix?” — yes, and that is a real feature in serving stacks; the honest follow-up is that I have not measured the eviction pattern on ours.
