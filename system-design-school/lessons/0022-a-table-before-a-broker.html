A Table Before a Broker

The platform has one Postgres and no queue, and the reflex is to add a broker. Measured, a broker's first cost is that every job is now a second write to a second system, and no order of those two writes survived either a broker hiccup or a killed producer. A table in the same transaction lost nothing. Then the three things that really do make you leave the table: an open transaction eats its headroom, a second reader cannot read a queue, and a log kept in a table silently skipped a sixth to a third of its events.

The win

Give every eval run a scoring job, through a broker in both orders and through a table in the same transaction, and count the runs with no job and the jobs with no run. Hold one transaction open elsewhere and watch the table queue slow down with nothing erroring, then tip over when it runs out of headroom. Then need a second reader and a rerun, build a log in the table, lose events to commit order, and fix it with one line whose price turns out to be the one Kafka's transactional consumers pay.

Why you, specifically
“Python/FastAPI, async SQLAlchemy, PostgreSQL, GKE” — and the deployment claims spread across the experience bullets: Cloud Run with IAP, Helm, Terragrunt, Cloud Build.

The chapter that defends this line is candid about what is missing, and it lists this first: “No messaging, so post-interview scoring is in-process and lost if the pod dies.” The follow-up in any design review is “so what would you add?”, and on GKE the answer everybody reaches for is Pub/Sub, or Kafka if they want to sound serious.

The stronger answer is a table in the Postgres that is already there, and the strongest is knowing exactly when to stop using it. This lesson measures both: what the table buys that no broker can, and the three break points — headroom, fan-out, and ordering — that would send you to Pub/Sub or Kafka, and which one each break point sends you to.

The line is defended in full in chapter 0011 of Résumé Mastery. The same shape — a hundred independent reconstruction runs behind a queue and a quality gate — sits under chapter 0019.

Start here — the plain version

A background job needs somewhere to wait. It can wait in a separate system built for waiting, a broker, or in a table in your own database. The broker scales further and does more. The table has one property the broker can never have: the job can be written in the same transaction as the thing that caused it, so either both exist or neither does.

That property is worth a lot, and it is not free for ever. A table queue lives with everything else in the database, so the database's housekeeping problems become its problems. And a queue forgets each job once it is done, which is fine until something else needs to read the same jobs, or read them again.

Broker
A separate service that holds messages between producers and consumers: Pub/Sub, Kafka, RabbitMQ. Redis stands in for one here.
Dual write
One logical change written to two systems in two steps. Something can always fail between them.
Horizon
From lesson 0019: the oldest snapshot any session still holds. Rows deleted after it cannot be cleaned up.
Headroom
How much faster consumers can work than jobs arrive. The margin that absorbs anything that makes each job slower.
Fan-out
Every message delivered to several independent readers, each getting all of them.
Replay
Reading messages again after they were processed: a rescore, a backfill, a bug fixed.

The first cost of a broker is a second write

brandur, writing in 2015 about why anyone would put a job queue in Postgres, gives the reason in one sentence: “storing jobs in a database allows a program to take advantage of its transactional consistency; when an operation fails and rolls back, an injected job rolls back with it.” The same article is the classic account of how that queue dies, and this lesson measures both halves on Postgres 17, a decade and a SKIP LOCKED later.

The first half is about the thing people do instead. With a broker, an eval run is written to Postgres and its scoring job is published somewhere else, and those are two writes to two systems with nothing coordinating them. Commit first and a failure before the publish leaves a run nobody will score. Publish first and a failure before the commit leaves a job for a run that does not exist. Both were produced on demand here.

Lab — a broker, a table, and a log that loses events

Lab 0022 ~30 minutes

Two writes in two systems, one idle session, and an id that is not a position

  1. Give 2 000 eval runs a scoring job each, three ways: commit the run and then push the job to a broker, push first and then commit, or insert the job in the same transaction. Once with the broker pausing for 1.5 s partway through, and once with the producer process killed twelve times.

    Each order has its own failure, and the table has neither

    When the broker stalled, committing first left 24 eval runs that will never be scored: the run is in Postgres and the publish timed out after it. Publishing first survived the stall — a failed publish rolled the run back — which makes it look like the right order. The kills show why it is not. A producer killed after its publish and before its commit left 5 jobs for runs that do not exist, and committing first lost 5 more runs the same way.

    The same transaction had zero of either, in both tests, in every run. There is no order to get wrong when there is one write. Across four runs the stall orphaned 20 to 24, the kills 5 to 8 committing first and 2 to 6 publishing first.

  2. Now the table's own failure. Feed the queue 400 jobs a second with four consumers claiming them, then open one idle transaction elsewhere — lesson 0019's forgotten session — for 40 seconds, then close it.

    The queue is empty, and every claim reads hundreds of pages to find that out

    The backlog column is zero almost throughout. The queue is keeping up. And the buffers column went from 1 page per claim to 884 in forty seconds of one idle session, because every job deleted since that session's snapshot is still in the index, and a claim walks past all of them to reach the first live one. At 400 jobs a second that is 400 more dead entries every second, with nothing allowed to remove them.

    And nobody would notice. The median claim went from 1.5 to 1.7 ms, throughput did not move, and nothing errored. Closing the session took the buffers back to 47 within ten seconds and to 6 in twenty. This run had headroom: four consumers can claim roughly three times as fast as 400 a second, so a slower claim cost nothing anyone could see.

  3. Take the headroom away. The same experiment at 1 100 jobs a second, close to what four consumers can do, with the session held for 60 seconds.

    Before / after · the same idle session, and the only difference is the margin

    The claim got slower steadily — 1.9 ms to 4.8 ms at the median, the buffers climbing by about 290 every ten seconds — and forty seconds into the hold the consumers could no longer keep up. Twenty seconds later they were claiming 733 a second against 1 100 arriving, with 4 400 jobs behind. It compounds, because every job that waits is one more to claim through the same dead entries. That is brandur's death spiral, starting on Postgres 17 with SKIP LOCKED. This is the worst of three runs: in all three the consumers began to fall behind between 40 and 60 seconds into the hold, and by 60 seconds the backlog was 339, 587 and 4 400.

    Then the part the 2015 article does not show: closing the session fixed it within ten seconds. The median went straight back to 1.8 ms, the buffers to 197, and the consumers cleared the backlog at 1 535 a second. Nothing was tuned. The queue did not need a bigger machine; it needed the one idle transaction to end, which lesson 0019's idle_in_transaction_session_timeout does automatically.

  4. A second consumer arrives: the audit trail needs every scored run as well as the scorer. Then the rubric changes and everything must be rescored. A queue, a queue with a copy per reader, and a log with an offset per reader.

    A queue is read once, by one reader; a log is read by everyone, as often as they like

    The queue gave the audit trail none of the 1 000, because the scorer deleted each one as it finished — which is what acknowledging means. A copy per reader works, at double the writes and double the deletes, and every new reader means changing every producer. Neither can do a rerun: the rows are gone.

    The log wrote each event once, deleted nothing, and gave each reader all 1 000 by keeping a position per reader in consumer_offsets. A new reader starting from zero is a rerun, for free. This is the first break point that sends you to a broker, and it tells you which: fan-out alone is Pub/Sub’s shape, a subscription per reader; fan-out plus replay is Kafka’s.

  5. Build that log in the table and tail it the obvious way, WHERE id > :last, while eight producers insert and commit. Beside it, a reader that only reads rows from transactions older than every running one. Then again, with one unrelated writer left idle for three seconds.

    8 producers x 250 events, each in its own transaction, holding it 0-4 ms after the insert before commit. Two readers tail the log as it grows.

    The id reader lost more than a quarter of the log, and nothing anywhere said so

    583 of 2 000 events were never read, and in nine runs the count was between 324 and 709. Each one is a row whose id was handed out before a neighbour's and whose transaction committed after it. The reader saw the neighbour, moved its position past both, and the late row became visible behind it. No error, no gap anybody checks for. It is the most dangerous result on this page, because it looks exactly like a working consumer.

    The second reader missed nothing in any run, with about a millisecond more lag. The second pair of rows is its price: one unrelated transaction left open for three seconds held every event behind it for over two seconds at the median, because nothing newer than the oldest running writer is safe to read. Correct costs you the slowest writer in the database.

Underneath

One layer down · what a queue, a broker and a log each promise

In plain words

Saving the eval run and handing its job to a broker, a separate service that queues work for the workers, are two saves to two systems. Whichever goes first, a failure between them leaves a run with no job or a job with no run. Writing the job as a row in the same transaction as the run (writes saved whole or not at all) leaves no gap.

Two systems, two writes, and no order that survives both failures

A write to Postgres and a write to a broker share nothing: no transaction, no lock, no common clock. Each order leaves a window after the first write, and each of the two failures measured here — the broker stalling, the producer dying — lands in one of the windows. Retrying the second write narrows its window and adds a new one, because the retry loop can die too.

Each order against each failure, measured across four runs:

order broker stalls 1.5 s producer killed 12 times commit, then publish 20-24 runs with no job 5-8 runs with no job publish, then commit 0: failed publish rolls 2-6 jobs whose run never the run back committed same transaction 0 and 0 0 and 0

Publishing first looks safe until something other than the broker fails, which is why it is the order people defend. The only row with no bad cell is the one with one write. When a broker is unavoidable, the fix is to make it one write again — write the event to a table in the same transaction and have something relay the table to the broker. That is the outbox, and lesson 0027 builds it.

In plain words

Postgres leaves a deleted row behind as a dead entry until cleanup removes it. One transaction left open elsewhere stops that cleanup, so every finished job stays in the index (the sorted list a claim searches) and each claim steps over all of them, even on a nearly empty queue. Nobody notices until the consumers run out of spare capacity and fall behind. The fix is a timeout that ends idle transactions, not a bigger database.

A queue can be empty and still read a thousand pages per job

brandur's 2015 diagnosis was that dead jobs pile up in the index while a long transaction is open: “As dead tuples continue to accumulate in the index, Postgres enters a hot loop as it searches the B-tree, comes up with an invisible tuple, and repeats the process again and again,” and “every time a job is successfully worked a new dead tuple is left in the index, making the next job that much harder to lock.” That article predates SKIP LOCKED by a release. The mechanism survives it, because SKIP LOCKED skips rows other sessions have locked, not rows that are dead.

A queue is read once; a log is read by everyone, as often as they like

Acknowledging a job deletes it, so a queue has exactly one reader per job and no history. The brokers are defined by which of those two they relax. Pub/Sub's documentation describes fan-out as a topic with several subscriptions, where “each of the subscriber applications gets the same set of published messages from the topic,” and it can replay, but only if you planned for it: “to seek to a time in the past and replay previously-acknowledged messages, you must configure message retention on the topic, or configure the subscription to retain acknowledged messages.” Kafka makes the log itself the thing: “The consumer controls its position in this log,” so fan-out and replay are the default rather than options.

In plain words

A row gets its id when it is inserted but becomes visible only when its transaction commits, so ids can appear out of order. A reader that resumes after the last id it saw will skip a row that commits after a higher-numbered one, and never return to it. The fix is to read only rows from transactions older than every one still running. The price is that one slow writer anywhere makes every reader wait.

An id is handed out at insert and seen at commit

A bigserial comes from a sequence, and the documentation is explicit that sequence changes are “immediately visible to other transactions, and are not undone if the calling transaction rolls back.” The row itself is visible only when its transaction commits. So ids are assigned in one order and become readable in another, and a reader that treats the highest id it has seen as a position will step over every row that was slower to commit than its neighbour. A plain Kafka producer does not have this problem, because the broker assigns the offset when it appends the record. A transactional one brings it straight back, and Kafka's answer is this lesson's: a read_committed consumer only reads up to the “last stable offset (LSO), which is the one less than the offset of the first open transaction,” so it “will not be able to read up to the high watermark when there are in flight transactions.”

Two producers, and what each reader does with them:

time producer A producer B by id by committed txid t1 insert, gets id 1 - - - t2 - insert, gets id 2 - - t3 - commit reads 2, at = 2 A still running: waits t4 commit - id > 2: nothing reads 1, then 2 row 1 is never read

The fix uses the snapshot's xmin, which the documentation defines as the “lowest transaction ID that was still active. All transaction IDs less than xmin are either committed and visible, or rolled back and dead.” Read only rows written below it, in writer order, and nothing can later appear behind the reader. The price is that one open writer anywhere in the database holds every reader — over two seconds at the median in step 5 — and a lesson 0021 worker holding a lock through a model call is exactly such a writer. Kafka pays the same price per partition; a table log pays it for the whole database.

Which lands on the sentence worth keeping: start with a table, because one write cannot disagree with itself; leave it when a second reader, a rerun, or ordered history is the requirement, and know which broker each of those points to. Throughput is the reason people give, and it is the last one that arrives.

Check yourself

During a 1.5 s broker stall, publishing the job first and committing the run second lost nothing, while committing first lost 20 to 24 runs. Why is publishing first still not safe?

  1. A producer dying between publish and commit orphans its job
  2. The broker delivers the job once its stall has finished
  3. The run's transaction holds a lock the consumer waits on
  4. Publishing first doubles the load on the whole of Postgres

Each order has a window after its first write. Publishing first survives a broker failure because a failed publish can roll the run back, but a producer killed after its publish and before its commit leaves a job for a run that never existed: 2 to 6 of them in twelve kills across four runs. Swapping the order moves the window; it does not remove it.

The distractors describe things that did not happen: in this lab the paused broker never executed the abandoned pushes, nothing waited on the run's lock, and the order of two writes does not change how many there are. Only one write in one transaction has no window at all.

A reader tails a log table with WHERE id > :last ORDER BY id while several producers commit concurrently. It raises no errors and never read 583 of 2 000 events. What happened to them?

  1. They committed after rows with higher ids were already read
  2. They were rolled back and their ids were reused afterwards
  3. They were removed by vacuum before the reader ever arrived
  4. They exceeded the batch size limit and were quietly dropped

An id is taken from the sequence when the row is inserted, and the row becomes visible when its transaction commits. A producer that inserted first and committed second leaves its row behind a higher id the reader has already passed, and id > :last will never look back. The rows are all there, committed, and unread.

Sequence values are never reused, vacuum does not remove live rows, and a batch limit only defers rows to the next read. The fix is to read only rows written by transactions older than every running one, ordered by writer — at the cost of waiting for the slowest writer in the database.

Say it out loud · about 75 seconds

A spoken answer to “your background scoring is lost if the pod dies. What would you add?” Read it aloud, then say it again with the page covered.

  1. Situation

    Scoring runs in-process, so a pod restart loses it. It needs a durable queue, and we already run Postgres.

  2. Mechanism

    A broker makes every job a second write to a second system. Commit first and a failure loses the job; publish first and a failure leaves a job for nothing.

  3. What I did

    I measured both. Committing first orphaned 20 to 24 runs on one short broker stall, and publishing first left jobs for runs that never committed.

    A jobs table in the same transaction had zero of either. So I would start there, with an idle-transaction timeout, because one open session made every claim read over a thousand pages.

  4. What it cost

    A queue has one reader and no history. The day a second service needs the events, that is Pub/Sub; if it needs replay too, Kafka.

The sentence that sounds fluent and gets you caught

“Postgres isn’t a queue, so we’d put Pub/Sub in front of the scoring.” The follow-up is “how does the job get into Pub/Sub if the interview write fails?”, and the honest answer is that it does, or does not, depending on which write happened first. You have added a system and a consistency problem to solve a durability problem. The version that holds: “a jobs table in the same transaction, until a second reader or replay needs a log.”

The second trap is building the log yourself and tailing it by id. It works in every test with one producer, and with eight it skipped more than a quarter of the events. If you propose a table log, say how the reader avoids commit-order gaps before anybody asks.

Probes to expect

  1. “Why not just use Pub/Sub? You’re on GCP already.” The opener. It tests whether you can argue against the default on something other than cost.
    Model answer — say yours first

    Because the job would stop being atomic with the write that causes it. I measured the dual write: committing the interview and then publishing orphaned 20 to 24 runs during one 1.5-second broker stall, and publishing first left jobs for runs that never committed when the producer was killed. A jobs table in the same transaction had zero of either in every run.

    Pub/Sub is the right answer the day a second service needs the same events — that is a subscription each, and a table queue cannot do it. Until then it adds a system and a consistency problem to solve a durability problem.

    Invites · “And when you do need Pub/Sub?” — write to a table in the transaction and relay it: the outbox, lesson 0027.
  2. “Doesn’t a Postgres queue fall over under load?” The folklore question. The strong answer names the actual failure, which is not load.
    Model answer — say yours first

    Not from throughput first — four consumers claimed 1 100 a second on a laptop. What kills it is an open transaction elsewhere. Every job deleted after that transaction's snapshot stays in the index, so each claim walks past them: one idle session took claims from a few pages to over 1 600 on a queue that was nearly empty.

    With headroom that is invisible. At 1 100 a second the median claim went from 1.9 to 4.8 ms and the consumers fell up to 4 400 jobs behind; closing the session fixed it within ten seconds. So the defence is an idle-in-transaction timeout on every pool, plus an alert on the oldest transaction's age, not a bigger database.

    Invites · “How did you find the idle session?” — lesson 0019's pg_stat_activity query.
  3. “Could you use the same table for the audit service as well?” A fan-out question in disguise. The test is whether you know a queue has one reader.
    Model answer — say yours first

    Not as a queue: the scorer deletes each job as it finishes, and the audit reader got 0 of 1 000. A copy per reader works, doubling writes and deletes and coupling every producer to every reader.

    What it needs is a log: append-only, never deleted, with a position per reader, which gave both 1 000 and made a rerun free. I can build that in a table, but it needs a careful reader, and this is the point where I would seriously consider Pub/Sub — or Kafka if replay matters.

    Invites · “What is careful about the reader?” — ids are not commit order.
  4. “You have an events table with a serial id. Why can’t consumers just remember the last id they read?” Sounds trivial. It is the question that separates having built one of these from having read about it.
    Model answer — say yours first

    Because an id is handed out at insert and the row becomes visible at commit. A producer that inserts first and commits second leaves its row behind a higher id the reader has already passed, and it is never read. With eight producers, 324 to 709 of 2 000 events were skipped, silently, across nine runs.

    The fix is to read only rows written by transactions older than the snapshot's xmin, ordered by transaction id then row id, because nothing can be added below that. It missed nothing, and its cost is that one open writer anywhere holds every reader — over two seconds in the lab.

    Invites · “How does Kafka avoid it?” — the broker assigns the offset at append, in order.
  5. “So when would you move to Kafka?” The closing question. A list of features loses; three conditions, each tied to something you measured, wins.
    Model answer — say yours first

    When I need a log rather than a queue and the table version’s costs start to bite. Replay: rescoring every stored interview against a changed rubric. Several independent readers, each at its own pace. Ordered history per key.

    And the price of the table log is what pushes it: its safe reader waits for the slowest writer in the database, so a single slow transaction stalls every consumer. Kafka gives those three without that coupling, and costs brokers, partitions and operations I do not run today. For fan-out alone, Pub/Sub is enough.

    Invites · “And the job still has to get into Kafka atomically?” — yes: an outbox table, lesson 0027.
