The Await Inside the Transaction

The bug is the indentation of one line. A transaction opened before a model call instead of after it costs two scarce things at once — a pooled connection and every row lock it has taken — for the entire second that somebody else's GPU is thinking. Throughput falls from 5.5 turns a second to 0.9, and seventeen of twenty-four turns blow the budget.

The win

Move three statements into a different order and take throughput from 0.9 turns a second to 5.5, the worst lock wait from 24.7 seconds to 4 milliseconds, and the count of turns over the 8-second budget from seventeen to zero. Then find the second ceiling underneath the first, watch two perfectly ordinary workers deadlock, and read the log line the database was writing the whole time.

Why you, specifically
“Built its custom OpenAI-compatible LLM gateway, then moved the inference path from REST to streaming Gemini Live, cutting end-to-end turn latency 47 % at p50 (4.1 s to 2.2 s) and 52 % at p90 (5.1 s to 2.4 s), with zero mid-interview session drops.”

Those are latency numbers for a turn that lasts seconds, which is what makes this lesson's bug specific to your system rather than generic advice. A web request holds a transaction for milliseconds and the damage is invisible; a turn that calls a model holds it for two to four seconds, and that is the number on the résumé.

It is also the likeliest live bug in the stack, because the shape that causes it is the shape a careful person writes. You open a session, you fetch the context you need, you call the model, you write the result, and you commit — one clean unit of work. Every step of that reasoning is correct except where the session begins.

The claim is defended in full in chapter 0002 of Résumé Mastery. This lesson is where the thing that would quietly undo those numbers gets measured.

Start here — the plain version

A transaction is a claim on resources that lasts until you commit. Two of those resources are scarce and neither of them is the database's CPU: the connection it is using, and the locks it has taken. Both are held for the whole life of the transaction, whether or not the transaction is doing anything.

An await makes that duration much longer without making it look longer. The event loop moves on, the code reads as if it is one continuous block, and nothing in the syntax hints that you have just parked two shared resources for the length of a network call to somebody else.

Row lock
Taken by SELECT … FOR UPDATE or by an UPDATE, and held until commit. There is no shorter option: a lock you can release before the write is not a lock.
Lock wait
Time a statement spends waiting to take a lock somebody else holds. It appears in the slow-query log as a slow SELECT, which is where the trail goes cold.
Held transaction
One kept open across an await on something other than the database. The subject of this lesson, and a thing you can see in a diff.
Effective concurrency
How many calls are genuinely in flight. Throughput times call duration, which is Little's law again, and usually smaller than any limit you configured.
deadlock_timeout
How long Postgres waits before checking for a deadlock at all. Default 1 s; this compose file sets 1 s explicitly so the lab does not take ten.
Deadlock
Two transactions each holding what the other needs. Postgres detects it and kills one with 40P01 — after it has finished waiting.
log_lock_waits
A Postgres setting that logs any wait longer than deadlock_timeout. Off by default, on in this compose file, and the only place the truth is written down.
Lock ordering
Always taking locks in the same sequence. The one structural defence against deadlock, and it is a code convention rather than a setting.
Unit of work
The span a transaction is meant to cover. The mistake is not having one, it is drawing its boundary around a call to somebody else's service.

One await, two resources

The code that causes this reads well. Open a session, take the row you are about to modify, call the model, write the result, commit. It is a single unit of work with a clear boundary, which is precisely the advice people are given about transactions, and it is correct in every respect except one: the boundary was drawn around a call that leaves the machine.

What makes it hard to see is that two different scarce resources are consumed and they fail in two different ways. The row lock serialises everybody who wants that row. The pooled connection — which lesson 0015 just finished measuring — serialises everybody who wants the database at all. Give each worker its own row and the lock contention vanishes entirely, and throughput is still a third of what it should be.

Why this survives review, and survives staging

In a diff it is an indentation. The statements are identical, the SQL is identical, and the only difference is which side of the async with the model call sits on. There is no linter for it and no test that fails, because with one worker it is perfectly correct and slightly slower.

It also does not reproduce at low concurrency. One turn holds a connection for a second and nobody notices; five turns against a pool of five is the first moment it exists. So it arrives in production as a latency regression with no corresponding deploy to the database, which is how the database ends up being investigated first.

Now cover it and redraw

Sixty seconds. Twelve marks, the standing ceiling. This one is the easiest diagram in the batch to redraw and the easiest to redraw wrongly — the temptation is to make the two transactions different lengths of the same shape rather than different shapes.

  • Two timelines where the model call is the same width in both and only the transaction bar moves.
  • The top one holding two things, not one. Say both out loud as you draw it.
  • The three numbers: 0.9 → 5.5, 24.7 s → 4 ms, 17 of 24 → 0.
  • That a row each only removes one of the two, and the ceiling is min(pool, quota).
Draw the model-call box first, in both rows, identical. Everything else on this diagram is about what is wrapped around it, and if the boxes end up different sizes you have drawn a lesson about speed instead.

    Neither worker did anything strange. Each locked a row, called the model, and locked a second row — and they happened to pick the two rows in opposite orders, which is a thing that happens when the rows come from a set rather than from a literal.

    The timing is the part worth carrying. The call is about a second and the answer arrived at two, because Postgres does not look for a deadlock until deadlock_timeout has elapsed — one second here, and ten by default. Detection is cheap; the waiting in front of it is not, and at the default setting this pair would have sat there for ten seconds against an eight-second budget.

    The defence is a code convention rather than a setting: take locks in a consistent order, usually by sorting the ids before locking. Holding no locks across the call removes the window entirely, which is the same fix as everything else in this lesson.

Underneath

One layer down · why one line costs two resources

Four things. The first is what a transaction actually holds, the second is why the ceiling is a minimum of two numbers, the third is why the evidence is in a log nobody enables, and the fourth is why the fix creates a problem that lesson 0016 already solved.

A transaction holds locks and a connection, and an await extends both

Row locks are taken by the statement and released by the commit. There is no intermediate option, and there should not be — a lock you could release before writing would not be protecting anything. So the duration of the lock is the duration of the transaction, exactly, and anything that lengthens the second lengthens the first.

The connection is the part people miss, because it is not a database concept at all. It belongs to lesson 0015's pool, and a transaction cannot span connections, so the connection is pinned for the transaction's life. This is why the row-per-worker cell still lost a third of its throughput: zero lock contention and the pool still saturated, because twenty-four transactions were each holding one of five connections through a one-second call.

An await is what makes this invisible. The event loop moves on, so nothing appears blocked and CPU stays low; the code reads as one continuous block; and the two resources being held are both held by an object that is not doing anything. A synchronous version of the same bug ties up a thread, which at least shows up as a thread pool at its limit.

The ceiling is a minimum, and the smaller number is usually the default

Two limits apply to the same work and the effective one is whichever is smaller. The provider quota is the number that gets discussed, because somebody negotiated it and it appears in a contract. The pool size is five because that is what SQLAlchemy ships.

Calls actually in flight, against the two limits, from step 2:

pool quota min turns/s in flight binding limit 2 8 2 1.7 1.7 the pool 5 8 5 3.9 3.9 the pool 8 8 8 5.5 5.5 either 16 8 8 5.5 5.5 the quota

In-flight calls track the pool exactly until the pool passes the quota, and then stop. The useful consequence is that the number you would quote in a capacity conversation is wrong in three of these four rows, and it is wrong in the direction that makes you think you have headroom.

The database wrote it down, under a name nobody greps

Every wait longer than deadlock_timeout is logged, if log_lock_waits is on. It is off by default, which means the clearest evidence of this bug is usually not being collected — and the place people look instead is the slow-query log, where a lock wait appears as a slow SELECT with no explanation.

That misdirection is worth naming, because it is why this gets escalated to a database team. Query timings show a statement taking seconds. The database shows low CPU, few connections and no expensive plans. Both observations are correct, and the cause is a transaction that has issued no statement for a second and is waiting on a GPU somewhere else.

Where the second in a two-second deadlock actually went:

phase elapsed who is doing it lock row A / row B ~0 ms both workers, successfully await the model call ~1 000 ms the provider wait for the second lock ~1 000 ms deadlock_timeout, before any check detect the cycle and choose a victim <1 ms Postgres total ~2 036 ms measured

Detection is free and the wait in front of it is not. At the default deadlock_timeout of 10 s that middle row is ten times longer, so a deadlock would be reported after the eight-second budget had already expired — the request fails as a timeout and the deadlock never appears in the story.

The fix reopens lesson 0016's problem, on purpose

Moving the model call out of the transaction means the read and the write are no longer atomic. Something can change the row in between — which is precisely the gap lesson 0016 measured, where eight writers produced a total of one.

That is not an argument for putting the transaction back. It is the reason the two lessons are adjacent. The correct combination is a short transaction and a write that does not depend on a remembered value: either a single statement that computes from the current one, or a version check that fails loudly and retries. Holding a lock across a model call is a way of avoiding lesson 0016 by making lesson 0015 worse.

The four combinations, and only one of them is shippable:

transaction scope write style correct throughput spans the call read-modify-write yes 0.9/s spans the call atomic delta yes 0.9/s after the call read-modify-write NO 5.5/s after the call atomic or versioned yes 5.5/s

The third row is the dangerous one, because it is what you get by applying this lesson without the previous one: six times the throughput and a silent lost update. The two changes are one change, and shipping half of them replaces a latency bug with a correctness bug.

Which lands on the sentence worth keeping: a transaction's boundary is a claim on shared resources, so it should never contain a call you do not control. Everything else in this lesson is that sentence with numbers attached.

Check yourself

A transaction spans the model call, but every worker updates its own row, so no two workers ever contend for a lock. Throughput was still 4.0 instead of 5.5. Why?

  1. The transaction holds a pooled connection for the whole call
  2. Postgres locked the whole table because every row was touched
  3. The model provider throttled the calls once they all overlapped
  4. Each worker waited on the deadlock detector before it committed

The pool. A transaction cannot move between connections, so the connection is pinned for its whole life — including the second it spends waiting for a model. Twenty-four workers holding a transaction each, against a pool of five, is lesson 0015's queue arriving through a different door.

This is the cell that makes the bug hard to reason about: removing the obvious resource contention leaves two-thirds of the damage in place. The two costs have to be removed separately, and only shortening the transaction removes both.

Two workers lock two rows in opposite orders with a one-second model call in between. The 40P01 arrived after 2 036 ms. What was most of that time?

  1. Waiting on the deadlock detector, whose timer is one second
  2. Network round trips to the model provider, which were slow
  3. Postgres rebuilding its lock table after the conflict was found
  4. The retry loop running the whole transaction a second time

About a second of model call and then about a second of deadlock_timeout, because Postgres does not look for a deadlock until that timer expires. Detecting the cycle and choosing a victim is sub-millisecond; the waiting in front of it is the entire cost.

The compose file sets the timer to one second so the lab is quick. The default is ten, which against an eight-second turn budget means the deadlock is reported after the request it belongs to has already failed as a timeout — and so it never appears in the incident write-up at all.

Say it out loud · about 75 seconds

A spoken answer to “what is the most expensive mistake you have found in an async service?” Read it aloud, then say it again with the page covered.

  1. Situation

    Our turn path opens a database session, reads a score, calls the model, writes the score, and commits. One clean unit of work.

  2. Mechanism

    The transaction holds two scarce things until it commits: the row locks it took, and the pooled connection it is using.

    An await does not release either. So both are held for the whole second the model is thinking.

  3. What I did

    I measured all four combinations. Transaction inside the call gave 0.9 turns a second; moving it after gave 5.5.

    Worst lock wait went from 24.7 seconds to four milliseconds, and turns over the budget went from seventeen of twenty-four to none.

    Giving every worker its own row only recovered half of it. The pool was the other ceiling.

  4. What it cost

    The read and the write are no longer atomic, so the row can move underneath. That is a lost update if you leave it there.

    We write a delta rather than a remembered value. The two changes are really one change.

The sentence that sounds fluent and gets you caught

“We keep transactions short.” Everybody says this and almost nobody has measured it. The follow-up is “short in what units?”, and the honest answer for most async services is “short in statements, seconds long in wall clock”. The version that holds names the boundary rather than the length: “no transaction scope contains an await on anything but the database, so the longest one is a write and a commit.” That is checkable, and it is a grep.

The second trap is diagnosing this as a database problem, which is where it usually gets sent. Database CPU is low, connections are flat, no query has a bad plan, and every one of those observations is correct. If you find yourself saying “the database was fine”, the next sentence has to be about what was holding its resources while doing nothing — otherwise you have reported the symptom as a conclusion.

Probes to expect

  1. “Walk me through what a request does against the database in your turn path.” Sounds like an architecture warm-up. The interviewer is listening for where you say the transaction begins relative to the model call, and most people say it without noticing.
    Model answer — say yours first

    The important part is what the transaction does not contain: the model call happens first, holding nothing, and the transaction is a write and a commit. It used to be the other way round, which is the version most people write, because wrapping the whole unit of work in one session looks like the careful thing to do.

    I measured what that cost. Twenty-four concurrent turns went from 0.9 a second to 5.5 by moving one line, and seventeen of the twenty-four had been blowing the eight-second budget. The reason is that the transaction holds two scarce things until commit — its row locks and its pooled connection — and an await releases neither.

    Invites · “What did that break?” — the read and the write stop being atomic, which is the previous lesson's problem.
  2. “If every worker writes a different row, does the problem go away?” A good-faith question that sounds like it should end the conversation. The measured answer is no, and it is the most useful thing in this lesson.
    Model answer — say yours first

    It removes half of it. I ran exactly that case — a row per worker, so zero lock contention — and throughput was 4.0 instead of 5.5. The remaining loss is the connection pool: a transaction cannot span connections, so it pins one for its whole life, and twenty-four transactions holding one each against a pool of five is a queue.

    Which is the thing worth knowing about this bug: two resources, two failures, and they have to be removed separately. Only shortening the transaction removes both, and it removes them regardless of the row layout — the two shortened rows in my table were identical to each other.

    Invites · “So how big should the pool be?” — which is a Little's law question with a computable answer.
  3. “How would you have found this from monitoring?” The diagnostic version. Most answers describe what they would look at now that they know the answer; the good one names why the obvious places are empty.
    Model answer — say yours first

    Not from the database dashboard, which is the problem. CPU is low, the connection count is flat at the pool size, and no query has a bad plan — all correct, because the transaction doing the damage is issuing no statements. The lock waiting shows up in the slow-query log as a slow SELECT, which sends the investigation in the wrong direction.

    The place it is actually recorded is log_lock_waits, which is off by default. With it on I got fifty-three lines in five minutes saying “still waiting for AccessExclusiveLock on tuple … after 1000 ms”. So my answer is: turn it on, and alert on the ratio of request time to query time, because the signature of this class of bug is that the first rises while the second does not.

    Invites · “What else is off by default that you'd turn on?” — a genuinely good conversation to be invited into.
  4. “Two of your workers deadlocked. What happened and what do you change?” Checks whether you know that a deadlock is an ordering bug rather than a load problem, and whether you know what the detector costs.
    Model answer — say yours first

    Two transactions took the same two rows in opposite orders, which happens as soon as the rows come from a set rather than from literals. I reproduced it: two workers, two rows, a model call in between, and one of them got 40P01 after about two seconds — roughly a second of model call and roughly a second of deadlock_timeout, because Postgres does not look for a cycle until that timer expires.

    Two changes. The structural one is consistent lock ordering, which usually means sorting the ids before locking anything — a code convention, not a setting. The one that removes the window entirely is holding no locks across the call, which is the same fix as the rest of this. And the setting matters too: at the default ten-second timeout, the deadlock is reported after an eight-second budget has already expired, so it never appears in the incident at all.

    Invites · “Would you lower deadlock_timeout then?” — it also controls the lock-wait log, and lowering it costs a check on every waiter.
  5. “You moved the model call out of the transaction. What did that break?” The question that separates a fix from an understanding. If the answer is “nothing”, the interviewer now knows you have not thought about what the transaction was doing.
    Model answer — say yours first

    Atomicity of the read and the write. The transaction was, incidentally, protecting against the row changing between reading the score and writing it back — so shortening it reopens exactly the lost-update case I can measure separately: eight concurrent writers, final value one, no errors raised.

    So it is one change rather than two. The transaction gets short and the write stops depending on a remembered value — either a single statement that computes from the current value, or a version check that fails and retries. Shipping only the first half buys six times the throughput and a silent correctness bug, which is a strictly worse trade than the one I started with.

    Invites · “Which of those two would you pick?” — the single statement, unless the new value is not expressible as a function of the old one.

Recall — from lessons 0014–0016

0015 measured 363 ms of a 454 ms request spent waiting for a connection. This lesson's row-per-worker case lost throughput with no lock contention at all. Are those the same finding?

The same mechanism reached by a different route, and the difference is what makes this one worse. In 0015 the connection was held for the length of a query, so the pool's hold time was about ninety milliseconds and the ceiling was around fifty requests a second per replica. Here the connection is held for the length of a model call, so the hold time is a thousand milliseconds and the same pool of five yields about five turns a second — a tenfold reduction in ceiling from one line of code, with no change to the pool configuration at all. That is the useful way to carry it: the pool size is only half of the ceiling and the hold time is the other half, and the hold time is the half that a code change can move by an order of magnitude. It also explains why raising the pool is a poor response: it treats the visible number rather than the one that moved.

lesson 0015 · the pool as a queue
0016 showed eight writers producing a total of one because the read and the write were not atomic. This lesson's fix separates them further apart. Is that a contradiction?

No, but it is a trap, and it is the reason the two lessons are adjacent rather than in either order alone. Holding the transaction across the model call was, incidentally, protecting the read-modify-write; shortening it removes that protection and reopens the lost update exactly as 0016 measured it. The resolution is that the transaction was never the right protection, only an expensive accidental one: the correct pair is a short transaction plus a write that does not depend on a remembered value. Either a single statement computing from the current value, or a version check that fails loudly and retries with a budget sized from the contention. Applying this lesson without the previous one is the worst of the four combinations — six times the throughput and a silent wrong answer — which is why the derivation table in Underneath has four rows and only one of them is shippable.

lesson 0016 · the gap between read and write
0014 found a bug that needed a real database because an event loop made the check and the write atomic by accident. Does the event loop help or hurt here?

It hurts, and for the mirror-image reason. In 0014 the single-threaded loop made two operations in one coroutine atomic with respect to each other, which hid a race that a real database exposes. Here the loop is what allows a coroutine to hold two shared resources while doing nothing at all: the await yields, so the process stays busy, CPU stays low, nothing appears blocked, and a transaction sits open for a second. A synchronous version of this bug ties up a worker thread, which at least surfaces as a thread pool at its limit — a signal somebody would notice. So the event loop hides this one in the same way it hid 0014's: by making the cost invisible from inside the process. The general form worth keeping is that async removes the symptom that would have made you look, in both directions, and the only reliable answer is to measure the resource rather than the process.

lesson 0014 · the event loop hiding a race

One thing to bring back from this one, and it is a grep rather than a number. Search your own codebase for a session or transaction scope that contains an await on anything that is not the database — a model call, an HTTP client, a queue publish, a storage write. In an async codebase that search takes a couple of minutes and it is the highest-yield thing in this batch.

If you find one, the number worth measuring is not throughput. It is how long the transaction is open for, in milliseconds, against how long the statements inside it take. A ratio above about ten says this lesson applies to you.
