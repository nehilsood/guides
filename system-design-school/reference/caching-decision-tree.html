Caching Decision Tree

Every caching decision in Tier 1, compressed to the questions worth asking and the answers that follow from them.

Should this be cached at all?

  1. Is it expensive to produce? If it costs 2 ms, stop. You will spend more on the round trip than you save.
  2. Does the same input recur? Measure the repeat rate before assuming. A cache on a workload with no repetition is pure overhead — that is lesson 0005's penetration lab.
  3. Is it a pure function of things you can put in the key? If yes, cache it aggressively and stop worrying — there is no invalidation story to get wrong.
  4. If not pure, what staleness is acceptable? You must be able to answer in a unit of time. “Fresh-ish” is not an answer, it is a future incident.
  5. Is it the output of record? Then no. Cache expensive inputs; persist audited outputs in a database.

Which strategy?

If…UseBecause
The value is derived and on a latency budgetCache-asideA dead cache degrades you to slow rather than to down.
You want one code path and can accept a hard dependencyRead-throughLess application logic, one fewer failure mode to test — but the cache is now load-bearing.
Writes must be immediately visible and consistentWrite-throughConsistency at the cost of every write paying both latencies.
Write throughput dominates and some loss is tolerableWrite-behindFastest writes. The cache dying takes unflushed data with it.

  • Version anything that changes the value. Model, prompt template, tokeniser, schema.
  • Normalise the input so trivially different inputs hit the same entry.
  • Hash long keys, but keep the prefix human-readable so --scan --pattern stays useful.
  • Never key on a mutable object's identity — only on its content.

The single-flight bug

A per-key lock without a re-check inside the lock does not fix a stampede — it serialises it. 200 parallel 600 ms calls become 200 sequential ones, and the last caller waits two minutes. Always re-read the cache after acquiring.

Eviction

Redis maxmemory-policy. The default is noeviction — writes fail, reads keep working, dashboards stay green.
PolicyChoose when
allkeys-lruA subset of keys is far hotter than the rest, and access patterns churn. Redis's own suggested default.
allkeys-lfuSkew is stable and periodic scans (batch jobs) would otherwise flush your hot set. Tune with lfu-log-factor, lfu-decay-time.
allkeys-lrmRedis 8.6+. Read-heavy, and you want to shed data nobody has updated, regardless of read frequency.
allkeys-randomAll keys equally likely — a repeating full cycle over the keyspace.
volatile-ttlYour code can mark disposable entries with short TTLs. More explicit than LFU, costs memory per expiry.
noevictionOnly when Redis is a store of record, not a cache — and then you need alerting on used_memory.

Counters to alert on: evicted_keys, keyspace_hits / keyspace_misses (hit rate), used_memory vs maxmemory, current_eviction_exceeded_time. Both LRU and LFU are sampled approximations — maxmemory-samples defaults to 5; raise to 10 for closer-to-true LRU at some CPU cost.

  • Redis is single-threaded: one slow command blocks every client. Ban KEYS, watch slowlog, keep values small.
  • Enable AOF with CONFIG SET on the live server first — editing the config and restarting can lose data.
  • Test the ungraceful restart. kill -9, not stop. A clean shutdown may save even when periodic saving is off, which will fool you.
  • Durability and eviction are orthogonal. A full cache with perfect durability durably remembers a stale working set.
